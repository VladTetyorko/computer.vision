# vision-web

Angular SPA (driving adapter): the product UI — Wall/Map/Devices/Live/Settings tabs — served by Spring Boot off the classpath. No Java; see docs/WEB-PLAN.md for the full plan.

**Depends on:** none internally (talks to vision-api's REST surface only, over HTTP) · Angular 21 (`@angular/core|common|forms|router|cdk`), `hls.js`, `leaflet` (the live map inset and the `/map` fleet overview, both lazy — see Gotchas), `rxjs` (only where it earns its place — WS/preload) · dev/test: `@angular/cli`, `@angular/build`, `vitest`, `jsdom`, `@types/leaflet`. Map tiles come from four public providers (OSM, CARTO, OpenTopoMap, Esri — see `ui/leaflet-loader.ts#MAP_LAYERS`), none needing an API key.
**Used by:** vision-app (packages this module's `dist/` alongside the API jar; vision-api itself ships no static resources — see vision-api/MODULE.md Gotchas)
**Build/test:** `./mvnw -B -pl vision-web clean install` (npm ci + `ng build --configuration production` + `ng test --watch=false`, ~15s warm / longer on first Node provisioning). `-DskipWeb=true` on any reactor build skips Node provisioning and the Angular build entirely (fast backend-only cycles); `-DskipTests` skips just the Vitest run. Dev loop: `npm start` (`ng serve`, proxies `/api` and `/actuator` to `:8080` via `proxy.conf.json`). Tests: `npm run test:ci` (`ng test --watch=false`) — **not** raw `npx vitest run`, which bypasses the Angular CLI's test builder (zoneless TestBed setup, jsdom env) and fails everything.

## API surface

### `src/app/core/api/` — typed REST client (WEB-PLAN §0.5: mirrors Java DTOs exactly, no component calls `fetch` directly)

- `models.ts` — wire types 1:1 with `com.drones.vision.api.dto`: `Device` (mirrors `DeviceResponse`: id, name, capabilities, protocol, uri, options, state), `RegisterDeviceRequest`, `ActiveStream`, `StartStreamRequest`, `StartStreamResult`, `DiscoveredDevice` (mirrors `DiscoveredDeviceResponse`; `suggestedCategory?: string` is a category slug), `ScanRequest`, `ScanResult`, `ApiErrorBody`. `Capability = 'VIDEO'|'TELEMETRY'|'PTZ'|'AUDIO'`. **No `DeviceType`/`type` field anywhere** — removed server-side; categories are asset-level data.
  - **Asset-side DTOs** (docs/CYCLES-PLAN.md §2 — landed the mirroring this file previously deferred): `AssetSummary` (mirrors `AssetSummaryResponse`), `AssetDetails` (extends `AssetSummary` with `devices`/`recentUsages`, mirrors `AssetDetailsResponse`), `AssetUsage` (mirrors `AssetUsageResponse`; `endedAt` absent = open usage), `TelemetrySample` (mirrors `TelemetrySampleResponse`; every field but `at` is optional), `GeoPosition` (mirrors `GeoPositionResponse`), `Category` (mirrors `CategoryResponse`), plus `AssetStatus` union. Same `@JsonInclude(NON_NULL)` convention as everything else here: absent, not `null`, typed `?:`.
  - **Simulation DTOs** (docs/CYCLES-PLAN.md §4, §9): `StartSimulationRequest` (mirrors `dto.StartSimulationRequest`; `transport?: 'direct' | 'rtsp'`, fixed lowercase — the backend matches case-insensitively but this app only ever sends these two) and `SimulationResponse` (mirrors `dto.SimulationResponse`; `streamId`/`viewUrl` absent when not auto-started). **`videoPath` is now optional** (docs/CYCLES-PLAN.md §9, CU-a/CU-b): omitting it entirely is what registers a fully synthetic, moving VIDEO+TELEMETRY test drone with no video file at all — see `pages/devices/simulate-logic.ts#buildTestDroneRequest`.
  - **Warehouse DTOs** (docs/CYCLES-PLAN.md §8's pinned contract — CW-b, coded against the contract before CW-a, the backend half, ships): `LifecycleState = 'ACTIVE'|'DEACTIVATED'|'DELETED'` is now the **one** lifecycle axis shared by `Device.state` and `AssetSummary.lifecycle?` — the old separate `DeviceState` type is gone (devices can be `DELETED`/archived too, not just assets). `AssetSummary.lifecycle` is optional (not required like `Device.state`): CW-a lands this field server-side in parallel, so a pre-CW-a backend simply omits it — every reader treats an absent value as `'ACTIVE'` (`pages/devices/warehouse-logic.ts#buildAssetRows`), never a crash. `SettableLifecycleState = Exclude<LifecycleState,'DELETED'>` + `SetLifecycleStateRequest {state}` back every `POST .../state` call; `DeviceEdit`/`AssetEdit` (all fields optional, PATCH bodies); `AssignDeviceRequest {deviceId}`; `AssetDeletionResponse` (mirrors `AssetDeletion`: assetId, displayName, devicesDeleted, usagesRetained, streamsStopped) — told to the user verbatim, not swallowed into a bare confirmation.
  - **Detections DTOs** (docs/MVP1-PLAN.md §C8 bullet 4): `BoundingBox` (mirrors `dto.BoundingBoxResponse`: x, y, width, height, each normalized [0,1]), `Detection` (mirrors `dto.DetectionResponse`: label, confidence, box, modelId, modelVersion), `DetectionResult` (mirrors `dto.DetectionResultResponse`, the body element of `GET /api/streams/{streamId}/detections`: streamId, frameSequence, capturedAt, inferenceMillis, detections) — every field required (the backend DTO carries no `@JsonInclude(NON_NULL)` optional fields). Backs `core/detections-store.ts`.
  - **`TelemetrySample.deviceId`** (docs/CYCLES-PLAN.md §11, CD-a — landed server-side ahead of this UI cycle): every sample now carries the telemetry device it came from, never absent (mirrors `dto.TelemetrySampleResponse#deviceId`). This is what makes multi-telemetry grouping possible — `pages/asset-detail/asset-detail-logic.ts#groupTelemetryByDevice` is the one place that groups a usage's mixed samples back apart by source.
  - **`whepUrl`** (docs/MVP2-PLAN.md §L, L-a — U3 consumes it): `ActiveStream`, `StartStreamResult`, and `SimulationResponse` each gain an optional `whepUrl?: string`, independent of `viewUrl` — mediamtx's own **absolute origin URL** for the WHEP viewing endpoint, never app-relative and never proxied (unlike `viewUrl`; see each field's own doc comment). `ui/player.ts`'s `whepUrl` input is fed straight from this field — never rewritten.
  - **Flight-plan wire shape** (docs/CYCLES-PLAN.md §7, CT-a/CT-b — U3): `RouteMode = 'loop'|'bounce'|'once'`, `WaypointRequest {latitude, longitude, altitudeMeters?}`, `TelemetryPlanRequest {speedMps?, routeMode?, route: WaypointRequest[]}` (mirrors `dto.StartSimulationRequest.TelemetryRequest`/`WaypointRequest` exactly). `StartSimulationRequest` gains an optional `telemetry?: TelemetryPlanRequest` — built by `ui/flight-plan-logic.ts#buildTelemetryRequest`, threaded through by `pages/devices/simulate-logic.ts#buildSimulationRequest`/`buildTestDroneRequest`'s own new optional `telemetry` form field.
  - **`UsageTimeline`** (docs/MVP2-PLAN.md §R, R-a/R-a2/R-b — mirrors `dto.UsageTimelineResponse`, body of `GET /api/usages/{usageId}/timeline`): `{usage: AssetUsage, from: string, to: string, telemetry: TelemetrySample[], detections: DetectionResult[]}`, no `NON_NULL`-style optionality (`from`/`to` are always server-resolved; both lists always present, possibly empty). Backs `pages/replay/**` — see that section below.
- `vision-api.ts` — `VisionApi` (`@Injectable providedIn: 'root'`): `listDevices(includeDeleted = false)`, `registerDevice(req)`, `listStreams()`, `startStream(deviceId, req?)`, `stopStream(streamId)`, `scan(req?)`, `listAssets(includeDeleted = false)`, `getAsset(assetId)`, `usageTelemetry(usageId, limit = 200)`, **`usageTimeline(usageId, {fromMs?, toMs?, maxPoints?} = {})`** (docs/MVP2-PLAN.md §R, R-b — each option only added to the query string when given; `pages/replay/replay.ts`'s only call site always passes `maxPoints: 2000`, the server's own clamp ceiling, once up front), `streamDetections(streamId, limit = 50)` (docs/MVP1-PLAN.md §C8 bullet 4), `startSimulation(req)`, `stopSimulation(assetId)` (docs/CYCLES-PLAN.md §4), plus the docs/CYCLES-PLAN.md §8 warehouse set: `updateDevice(id, edit)` (PATCH), `setDeviceState(id, state)` (POST `.../state`), `deleteDevice(id)` (DELETE, archive), `updateAsset(id, edit)`, `setAssetState(id, state)`, `deleteAsset(id)` → `AssetDeletionResponse`, `assignDevice(assetId, deviceId)` (POST `.../devices`), `unassignDevice(assetId, deviceId)` (DELETE `.../devices/{deviceId}`). `includeDeleted` is only added to the query string when `true` (today's default behavior is otherwise unchanged). All promise-returning (`firstValueFrom`) so components hold signals, not subscriptions.
- `../api-error.ts` — `describeHttpError(error: unknown): string`, pure and unit-tested; maps status codes to specific sentences, prefers the backend's `ErrorResponse.message` when present.
- `../poll-scheduler.ts` — `PollScheduler` (`@Injectable providedIn: 'root'`) and `shouldPoll(documentHidden)` (docs/CYCLES-PLAN.md §9, CU-b item 3 — see "Poll scheduler consolidation" in Status below for the full merge writeup). One shared `setInterval` (`TICK_MS = 1_000`) drives every "poll while the tab is visible" consumer in the app: `schedule(periodMs, callback, options?)` registers a task and returns an unsubscribe function; the underlying timer starts lazily on the first registration and stops when the last one unsubscribes. A hidden tab is a no-op tick for every task (due times are left untouched, so nothing fires a catch-up burst on return) — the exact "pause, don't drop" contract every poller already had individually. `telemetry-logic.ts` re-exports `shouldPoll` from here so its existing import path keeps working. **`options.ignoreHidden`** (docs/MVP2-PLAN.md §E, E-b, new): opts a single task out of the pause-on-hidden contract above, defaulting to `false` for every pre-existing caller. `core/events-store.ts` is the one deliberate user — see that file's own doc comment (and its "Events" section below) for why a poll whose job is noticing something *while the tab is backgrounded* cannot itself pause when backgrounded.
- `../events-logic.ts` / `../events-store.ts` — detection events (docs/MVP2-PLAN.md §E, E-b — see the dedicated "Detection events" section below for the full feature writeup: the Wall rail, the asset detail Events section, the fleet map's event markers, and the Settings notification toggle).
- `../leaflet-warmup.ts` — `LeafletWarmup` (`@Injectable providedIn: 'root'`, `schedule()` idempotent): warms the Leaflet chunk (`import('leaflet')`) on `requestIdleCallback` (docs/CYCLES-PLAN.md §9, CU-b item 2), called once from `App`'s constructor via `afterNextRender`. A plain dynamic import — same as every host component's own `initMap()` — so this only moves *when* the chunk is fetched (idle, after first paint), never *whether*; Leaflet still never touches the initial bundle. Deliberately not folded into `IdlePreload` below: that class only knows how to preload router chunks, and Leaflet isn't a route, it straddles two of them (`live`, `map`).
- `../fleet-store.ts` — `FleetStore`: the app's single poller (5s, via `PollScheduler`, paused when tab hidden) and single source of truth for `devices`/`streams` signals, `liveDeviceIds`, `reachable`; `register/start/stop/simulate/stopSimulation` funnel through `run()` so a failure produces exactly one toast. `simulate`/`stopSimulation` (docs/CYCLES-PLAN.md §4) both refresh devices/streams on success and return `null`/`false` on failure — same shape as `register`/`stop` — but deliberately push no success toast themselves: the caller (`DevicesPage`) knows whether a `streamId` came back and wants a **Watch** action, which only it can construct (needs the `Router`).
  - **Warehouse mutations** (docs/CYCLES-PLAN.md §8 — CW-b's seam choice): every device/asset lifecycle mutation is a thin `run()`-wrapped `FleetStore` method, mirroring how C4 added `simulate()`/`stopSimulation()`, rather than a new page-scoped store — `devicesSignal` already lives here, and every mutation changes what it should read afterward (deleting an asset also archives its devices, per `AssetDeletion#devicesDeleted`, so it belongs next to the refresh it triggers). `updateDevice`/`setDeviceState`/`deleteDevice` and `updateAsset`/`setAssetState`/`deleteAsset` all refresh devices/streams on success and toast a plain confirmation (`deleteAsset`'s names what survived: devices archived / usages retained / streams stopped, from `AssetDeletionResponse`). `listDevicesIncludingArchived()`/`listAssetsIncludingArchived()` are read-only `run()`-wrapped proxies to `includeDeleted=true` that deliberately **never** write `devicesSignal` — they only back the Devices page's "show archived" toggle, so Wall/Live keep seeing only non-archived devices regardless of that toggle. `assignDevice`/`unassignDevice` bypass `run()` for their own try/catch so a `409` gets a specific sentence instead of `describeHttpError`'s generic conflict message (device-already-owned / the ≥1-device-per-asset rule) — still exactly one toast either way. CW-a (the backend half) is not live while this lands: every one of these degrades a 404 to that same one toast, never a broken page.
- `../telemetry-logic.ts` / `../telemetry-store.ts` — live telemetry for `/live/:deviceId` and wall tile chips (docs/CYCLES-PLAN.md §2). `telemetry-logic.ts` is pure and unit-tested: `findOwningAsset`, `selectOpenUsage` (the `recentUsages` entry with no `endedAt`), `deriveTrail` (chronological lat/lon points, skipping samples with no position), `ageSeconds`/`isStale` (>5s), **`groupTelemetryByDevice`/`telemetryDevices`** (docs/MVP2-PLAN.md §R, R-b — moved here from `pages/asset-detail/asset-detail-logic.ts` when the replay cockpit needed the identical per-device grouping; that page re-exports both so its own import site keeps working verbatim — see `pages/replay/**` below), plus a re-export of `shouldPoll` from `poll-scheduler.ts` (see above) for backward-compat import paths. `TelemetryStore` (`@Injectable()`, **not** `providedIn: 'root'` — see Gotchas) orchestrates: `track(deviceId)` resolves the device's owning asset (`listAssets()` + `getAsset()` per asset — a device belongs to ≤1 asset) and its open usage, then polls `GET /api/usages/{usageId}/telemetry?limit=200` every 2s (and ticks a 1s clock for `sampleAgeSeconds`) via `PollScheduler`; `reset()` stops and clears. Exposes `samples`, `hasTelemetry`, `latest`, `trail`, `sampleAgeSeconds`, `stale`. All lookups/polls silently degrade on error (no toast — telemetry is best-effort context, not a user-initiated action); callers render a "no telemetry" state instead. `map-store.ts` (docs/CYCLES-PLAN.md §6) reuses `selectOpenUsage` and `deriveTrail` (via its own `map-logic.ts`) directly rather than this class, since it starts from an already-known asset id, not a device id — see `pages/map/**` below.
- `../detections-logic.ts` / `../detections-store.ts` — the Live page's detections strip (docs/MVP1-PLAN.md §C8 bullet 4), mirroring `telemetry-logic.ts`/`telemetry-store.ts`'s split exactly. `detections-logic.ts` is pure and unit-tested: `deriveChips(results, maxChips = 8)` — from `results` (newest first, as `VisionApi` returns them), one chip per **distinct** label capped at `maxChips`, each carrying the most recent confidence recorded for that label (a label that keeps reappearing across frames still only produces one chip); `cvStatus(latestCapturedAt, nowMs)` → `'on'` (fresh, within `CV_STATUS_FRESH_SECONDS`=5) or `'off'` (stale or no result ever) — the CV status dot's only two states, derived purely from recency, never a new backend concept. `DetectionsStore` (`@Injectable()`, **not** `providedIn: 'root'`, same reasoning as `TelemetryStore`) polls `GET /api/streams/{streamId}/detections?limit=50` every 2s while visible via `PollScheduler`; `track(streamId)`/`reset()` mirror `TelemetryStore`'s API. Exposes `results`, `chips` (a `computed` over `deriveChips`), `status` (a `computed` over `cvStatus`, ticking its own 1s clock so the dot can go `'off'` passively between polls, exactly like `TelemetryStore.stale()`). Silent-degrade on error/empty — no toast, the dot naturally reads `'off'`.
- `../device-logic.ts` — `findVideoDevice(devices): Device | undefined`, the watch-target resolution (first `VIDEO`-capable device on an asset). Started in `pages/devices/simulate-logic.ts` (docs/CYCLES-PLAN.md §4); lifted here when docs/CYCLES-PLAN.md §6's `/map` tab needed the identical resolution for its own marker-popup Watch action and this codebase has no precedent for one page importing another page's module — every cross-page dependency runs through `core/` instead. `pages/devices/devices.ts`, `pages/map/map-store.ts`/`map.ts`, and (docs/CYCLES-PLAN.md §11) `pages/asset-detail/asset-detail.ts` all import it from here now.
- `../warehouse-logic.ts` (docs/CYCLES-PLAN.md §11, CD-b) — the **generic** device/asset lifecycle logic, lifted out of `pages/devices/warehouse-logic.ts` for the same cross-page reason as `device-logic.ts` above: the new asset detail page's own header (asset rename/lifecycle) and Hardware section (device rename/lifecycle) need the identical state machine `pages/devices/devices.ts`'s warehouse table already had. `RESTORE_TARGET_STATE`, `DeviceLifecycleAction`/`AssetLifecycleAction`, `availableDeviceActions`/`availableAssetActions` (the per-lifecycle-state action-menu matrix), `buildDeviceRenameEdit`, `AssetEditForm`/`buildAssetEdit` — unchanged behavior, just relocated; `pages/devices/warehouse-logic.ts` re-exports all of them so its own existing import sites keep working verbatim, and keeps only the Devices-page-specific view-model builders (`WarehouseRow`/`AssetRow`/`AssetListRow`, their `build*`/`filter*ByArchived` pairs, `mapDeviceOwners`) that only that page's rendering needs.
- `../stream-info-logic.ts` (docs/MVP2-PLAN.md §U-info, folded into CD-b) — pure derivations behind `ui/stream-info-panel.ts`: `describeSource(device)` → `{protocolLabel, description}`, a human-readable "MJPEG · 192.168.0.107:8080" / "File · flight.mp4 (looped)" / "Simulated · Pattern generator, no camera" line instead of a bare URI (credentials in an `rtsp://user:pass@…` URI are never surfaced in this primary description — `hostOf` parses `new URL(uri)` and reads only `hostname[:port]`; the raw URI, credentials included, stays reachable in the panel's "Technical details" disclosure). `sessionDurationSeconds`/`formatDuration` turn a raw `startedAt` timestamp into a live-ticking "12s" / "4m 07s" / "1h 03m" duration. `formatLatency(seconds)` renders `ui/player.ts`'s own measured `behindLive` (piped up via its `latencyChanged` output, never re-measured) as "~2.3s behind live" / "measuring…".
- `../toast.service.ts` — `ToastService.ok/info/error(text)`, auto-dismissing signal-backed toast list; rendered by `ui/toast-host.ts`. `ok(text, action?)` additionally accepts an optional `ToastAction { label, onClick }` (docs/CYCLES-PLAN.md §4 — the simulation wizard's **Watch** action); `toast-host.ts` renders it as an inline button that runs `onClick` and dismisses the toast. `info`/`error` don't take one — only a success toast the user asked for earns a follow-up action. **Deliberately left out of the CU-b poll-scheduler consolidation** (see Status below) — its `setTimeout` per toast is a one-shot auto-dismiss, not a recurring poll.
- `../settings-store.ts` — `SettingsStore`: built-in + custom `PipelineProfile`s, `effective()` (draft-over-profile), plus `mapLayer: WritableSignal<MapLayerId>` (docs/CYCLES-PLAN.md §9, CU-b item 6 — `'standard'|'night'|'relief'|'satellite'`, default `'night'`; set directly, e.g. `settings.mapLayer.set('satellite')`, same convention as `wallDensity`) — all persisted to `localStorage['vision.settings.v1']`; a corrupt/unknown persisted `mapLayer` is ignored (falls back to the default) rather than adopted. **`eventNotifications: WritableSignal<boolean>`** (docs/MVP2-PLAN.md §E, E-b, new, default `false`) — the user's own opt-in for browser detection-event notifications; `pages/settings/settings.ts#toggleEventNotifications` is the only call site that ever sets it `true` (and the only place `Notification.requestPermission()` is called, from the direct user gesture most browsers require), a corrupt/non-boolean persisted value is ignored like every other field here.
- `../idle-preload.ts` — `IdlePreload` (`PreloadingStrategy`): preloads lazy route chunks on browser idle; opt out via route `data: { preload: false }`. As of docs/CYCLES-PLAN.md §9, CU-b item 2, **no route opts out any more** — every tab chunk (including `/map` and `/debug`, previously excluded) is idle-preloaded; see Status below for why that's safe against the initial-bundle budget.

### Routes (`app.routes.ts`) — one lazy `loadComponent` chunk each

`/wall` (default) · `/map` · `/devices` · **`/assets/:assetId`** (docs/CYCLES-PLAN.md §11, CD-b — the Devices page's asset-first list "Open" target; param renamed from `:id` to `:assetId` in docs/MVP2-PLAN.md §V, V-b — see Gotchas) · `/assets/:assetId/replay/:usageId` (docs/MVP2-PLAN.md §R, R-b — the asset detail page's usage history "Replay" target for a finished usage; its own lazy chunk — see `pages/replay/**` below) · `/live/:deviceId` · `/settings` · `/debug` · `**` → not-found (`data: { preload: false }` — an unknown path is never worth pre-fetching). Every real tab/route is idle-preloaded (docs/CYCLES-PLAN.md §9, CU-b item 2 — see `core/idle-preload.ts` above, including `/assets/:assetId`/the replay route even though neither is a nav tab, only ever reached from Devices/Map/an asset's own usage history); Leaflet is additionally warmed on its own idle callback (`core/leaflet-warmup.ts`) since it isn't a route itself. Tab order in `app.ts`'s `tabs` array (and the header nav it renders): Wall, Map, Devices, Settings, Debug — `/assets/:assetId` and the replay route are deliberately not tabs (detail pages reached by "Open"/"Replay", not top-level sections). **Both `/assets/:assetId` and the replay route below now name their params to match their own component's input names exactly** (`assetId`/`usageId`) — `withComponentInputBinding()` binds a route param to a component input only when the names match (`RoutedComponentInputBinder` looks up `data[templateName]` by the input's own public name); every `router.navigate([...])` call site in this app already addresses `/assets/:assetId` positionally (`this.router.navigate(['/assets', assetId])`, `pages/devices/devices.ts`/`pages/map/map.ts`), not by param name, so the rename needed no call-site changes.

### `src/app/pages/devices/**` — asset-first inventory + the single "+ Add source" flow (docs/CYCLES-PLAN.md §4, §8, §9, §11)

- `warehouse-logic.ts` — pure, Angular-free logic behind the Devices page's own view models, unit-tested. The **generic** lifecycle-action-menu state machine and edit-request builders moved to `core/warehouse-logic.ts` in docs/CYCLES-PLAN.md §11 (CD-b — the asset detail page needs them too; re-exported here so this page's own imports keep working verbatim, see that file's entry above). What's left, specific to this page's rendering:
  - `mapDeviceOwners(assets: AssetDetails[])` — deviceId → owning asset, generalizing `simulate-logic.ts#mapSimulatedDevices` from just the `simulated` category to every asset the page loads (ownership isn't on `Device` itself).

### `src/app/pages/replay/**` — flight-replay cockpit (docs/MVP2-PLAN.md §R, R-b)

`/assets/:assetId/replay/:usageId`, the asset detail page's usage-history "Replay" target for one **finished** usage — a referee's use case: "verify where the machine was at minute 7."

- `replay-logic.ts` — pure, unit-tested (mirrors `ui/player-recovery.ts`/`ui/flight-plan-logic.ts`'s split of pure state/derivation from the component that drives it); every function here re-derives its answer from an already-fetched `UsageTimeline` plus a scrub-time signal, so scrubbing never re-fetches:
  - `nearestSample(samples, atMs)` — the telemetry sample nearest `atMs` (binary search, no interpolation — "the closest recorded reading, not a synthesized one"). Backs the map marker and the per-device telemetry panels alike.
  - `trailPrefix(samples, atMs)` — the flight trail drawn "up to" the scrub position: every positioned sample with `at <= atMs`, in `core/telemetry-logic.ts#deriveTrail`'s same gap-skipping shape.
  - `nearestDetectionResult(detections, atMs)` / `isDetectionNear(result, atMs, toleranceMs = DETECTION_MATCH_TOLERANCE_MS = 2000)` — the detection result nearest the scrub time, and whether it's close enough to count as "right now" rather than a leftover from a distant part of the flight (a legacy/streamless usage's empty `detections[]`, or a flight where CV only ran intermittently, both read honestly as "no detection data near this moment", never a fabricated reading).
  - `bucketDetections(detections, fromMs, toMs, bucketCount = DEFAULT_DETECTION_BUCKETS = 120)` → `DetectionDensityBucket[]` (`{atMs, count}`) — buckets only the *positive* frames (`detections.length > 0`) into equal-width slots, returning only the non-empty ones, ascending by time; backs the scrub bar's density strip (one element per bucket, not per detection, so a flight with hundreds of positive frames stays cheap to render) and the click-to-jump target (each bucket's `atMs` is its earliest result's `capturedAt`).
  - `clampToRange(atMs, fromMs, toMs)` / `advancePlaybackClock(atMs, deltaRealMs, speed, fromMs, toMs)` — the playback clock: advances by `deltaRealMs * speed` (wall-clock ms since the last `requestAnimationFrame` tick), clamped to `toMs`; reaching the end **stops** playback (`playing: false`) rather than looping. Stateless per call — a speed change between ticks (the 1×/4×/16× buttons) just changes the next tick's multiplier, nothing to reconcile.
- `replay-map.ts`/`.html`/`.css` — `ReplayMap` (`<vision-replay-map>`), purely presentational (no store/DI — driven by `[trail]`/`[markerPosition]`/`[markerHeadingDegrees]`/`[fullTrail]` inputs from `ReplayPage`'s own scrub-time `computed`s). A fourth home for the shared Leaflet bootstrap (`ui/leaflet-loader.ts`: `importLeaflet`/`ensureLeafletStylesheet`/`MAP_LAYERS`/`mapLayerTileLayer`/`droneDivIcon`), alongside `ui/live-map.ts`/`pages/map/fleet-map.ts`/`ui/flight-plan-dialog.ts`. Lives in `pages/replay/` (not `ui/`) since only this page uses it — mirrors `ui/live-map.ts`'s own original home before a second page needed it (see that module's doc comment). Unlike `LiveMap`'s always-on auto-follow, this map fits the view to the **whole** route once on load (`[fullTrail]`, independent of the scrub-bounded `[trail]`) — replay is reviewed, not chased; `autoFollow` (default off) optionally recenters on the marker as the scrub position moves, and "Fit route" re-runs the fit on demand.
- `replay.ts`/`.html`/`.css` — `ReplayPage`. Route inputs `assetId`/`usageId` match their path params (`assets/:assetId/replay/:usageId`) exactly — see Routes above; `pages/asset-detail/asset-detail.ts`'s own `assetId` input now follows the identical pattern too, since docs/MVP2-PLAN.md §V, V-b (see Gotchas). **Fetches once, scrubs in memory** (docs/MVP2-PLAN.md §R, R-b's own "no re-fetch per drag frame" requirement): `load()` calls `getAsset(assetId)` (display name/devices, for panel labels) and `usageTimeline(usageId, {maxPoints: 2000})` (the server's clamp ceiling) exactly once per route activation via one `effect()` (no poller); every panel below is a `computed()` over the cached `timeline` signal and the `atMs` scrub signal.
  - **Open usages redirect rather than render** (docs/MVP2-PLAN.md §R, R-b: "open one = watch live instead"): if the fetched usage's `endedAt` is absent, the page shows a notice + a **Watch live** link instead of the cockpit — covers a stray direct link to an open usage's replay URL, not just the history row (which already only offers Replay for finished ones).
  - **Playback** drives `atMs` via `requestAnimationFrame`, not `PollScheduler` — mirrors `ui/player.ts`'s own precedent of a raw browser timer for a playback clock tied to one view's lifecycle rather than a "re-fetch while visible" poll (see Gotchas' `PollScheduler` heartbeat note). `togglePlay()`/`pause()`/`setSpeed()` plus the pure `advancePlaybackClock` (`replay-logic.ts`) drive each frame; reaching the end auto-pauses; the Play button relabels **Replay** once at the end, restarting from `fromMs` on the next press.
  - **Scrubbing** is a plain `<input type="range">` (`onScrub`, `[min]`/`[max]` = the window bounds in epoch ms, `[step]` ≈ 1/1000th of the window's span so it feels continuous regardless of flight length) — dragging pauses playback and takes over; no HTTP call in the handler, just `atMs.set(...)` against the already-cached `timeline`. The detection density strip (`bucketDetections`) overlays the same track, each bucket a small `--density`-scaled marker (`bucket.count / maxBucketCount()`, one hue — `var(--warn)` — opacity-ramped, not a rainbow) whose click calls `jumpTo(bucket.atMs)`.
  - **Telemetry-at-scrub, per source device**: mirrors `asset-detail.html`'s own per-device panels almost verbatim, except every value comes from `nearestSample(telemetryByDevice.get(deviceId), atMs)` (the scrub-time reading) rather than "latest" — each panel also names the exact recorded sample's own timestamp (`sampleAtScrubFor`/`sampleTimeMs`) so the reading's precision (or gap) is never hidden.
  - **Detections-at-scrub** lists `nearestDetectionResult(...)`'s own `label · confidence` chips only when `isDetectionNear` — otherwise one of three honest empty states, all distinct: **no detections recorded for this flight** (`timeline.detections` is empty outright — a legacy usage, or one from a streamless asset, per R-a's own documented gap before R-a2), **no detection data near this moment** (detections exist elsewhere in the flight but not near the current scrub time), or **nothing detected at this instant** (the nearest inference frame ran and simply saw nothing) — three different facts, never collapsed into one generic "—".

  - **WHEP-first, HLS-fallback** (docs/MVP2-PLAN.md §L/§U3): when `whepUrl` is set, POSTs an SDP offer to it (`Content-Type: application/sdp`, non-trickle — gathers ICE, bounded to `ICE_GATHERING_TIMEOUT_MS`=3s, before sending), applies the SDP answer via `RTCPeerConnection`, waits for `ontrack`. Any failure *before a track ever arrives* (POST error, ICE `failed`/`disconnected`, or no track within `WHEP_NO_TRACK_TIMEOUT_MS`=6s) falls back to the exact same HLS `beginAttach` path `src` has always used — **load-bearing**, not an edge case, see Gotchas. `behindLive` is pinned to `0` the instant a track arrives (a real number, not `null` — the detection-overlay matcher needs one) though the visible badge reads `'live · WebRTC'` rather than `'0.0s behind'`. `RTCPeerConnection`/`fetch` are browser built-ins — no dynamic import, no extra chunk; the WHEP code still only ships in whichever *lazy* chunk imports `Player` (never the initial bundle, since `Player` is never `providedIn: 'root'`).
  - **Indefinite self-recovery**, driven by `player-recovery.ts`'s pure state machine (`reduceRecovery`, wrapped by `reduceTransportRecovery` for the transport decision — see that module's own entry below) rather than ad hoc component state: before ever having played, a missing playlist (a fresh stream's normal 404-until-muxed) stays a gentle `waiting` retried on a fixed `COLD_START_RETRY_DELAY_MS` (1.5s) cadence — "no error flash on fresh streams". Once attached, a **stall watchdog** (`isStalled`, no fragment/segment progress for `STALL_WATCHDOG_MS` = 8s — reset on every hls.js `FRAG_BUFFERED`/native `progress` event, or WHEP's own `ontrack`/frame-progress equivalent) or any other fatal hls.js/native/WHEP error moves to `reconnecting`: destroy the current attachment (HLS or WHEP, whichever is active) and reattach after a **capped exponential backoff** (`reconnectDelayMs`: 1s, 2s, 4s, …, capped at 30s, held there indefinitely — never gives up while `src`/`whepUrl` stay set, including across a backend restart that outlasts any single attempt window). `error` is now reserved for the one truly unrecoverable case (this browser can play neither transport at all) — a fatal error/stall never lands there. The visible state chip (`phase()`, one of `idle`/`connecting`/`waiting`/`playing`/`reconnecting`/`error`) replaces the old plain `state`; its "playing" badge additionally names the live transport and, for HLS once it's noticeably behind, quantifies it (`'live · WebRTC'` / `'live · HLS'` / `'live · HLS · 4.2s behind'` — see `live-edge-logic.ts#behindLiveChipLabel` below, docs/MVP2-PLAN.md §V, V-b). A **"Retry now"** button during `reconnecting` cancels the pending backoff and reattaches immediately, on whichever transport is currently active.
  - **HLS live-edge tuning** (docs/MVP2-PLAN.md §V, V-b — `HLS_LOW_LATENCY_MODE`/`HLS_LIVE_SYNC_DURATION_COUNT`/`HLS_LIVE_MAX_LATENCY_DURATION_COUNT`/`HLS_MAX_LIVE_SYNC_PLAYBACK_RATE`/`HLS_MAX_BUFFER_LENGTH_SECONDS`/`HLS_BACK_BUFFER_LENGTH_SECONDS`, named constants with their own doc-comment block right above `beginAttach`): `lowLatencyMode: true` (unchanged) plus **segment-count**, not duration-based, sync/catch-up tuning (`liveSyncDurationCount: 2`, `liveMaxLatencyDurationCount: 4` — hls.js's own default for the latter is `Infinity`, i.e. it does not forcibly resync a drifted playhead *at all* unless this is set) — segment-count rather than a fixed-seconds target specifically because V-a shrinks segment/part duration server-side as part of this same latency push, and a duration-based target would need re-tuning every time that number changes; a count-based one scales automatically either side of that landing, and works identically against a stock (non-LL) playlist that never advertises `PART-HOLD-BACK` at all. `maxLiveSyncPlaybackRate: 1.5` additionally turns on hls.js's own gentle rate-based catch-up (nudges `video.playbackRate` above `1`, capped at `1.5`, while behind-but-in-range) — this player already had `lowLatencyMode: true` before this cycle but never raised this off its inert default of `1`, so the catch-up mechanism has been silently off until now. `maxBufferLength: 10` (down from hls.js's own `30`s, VOD-sized default) bounds the forward-buffer target sensibly for a player that is never seeked into a past buffer; `backBufferLength: 30` is unchanged, just promoted to a named constant.
  - **Snap-to-live** (docs/MVP2-PLAN.md §V, V-b — `ui/live-edge-logic.ts#shouldSnapToLive`/`SnapToLiveReason`): after a recovery reattach reaches `playing` again (`'recovered'` — read directly off `player-recovery.ts`'s own state, `transportState().recovery.phase === 'reconnecting'`, checked *before* the `firstSegment` event is applied — not a parallel flag) or the tab regains visibility while still `playing` (`'visibilityRestored'`, detected by diffing `document.hidden` on the existing 1s latency-sampling timer rather than a dedicated `visibilitychange` listener — mirrors `core/poll-scheduler.ts`'s own "check `document.hidden` from an existing heartbeat" precedent), the player forward-seeks the `<video>` to `hls.liveSyncPosition` (falling back to the end of the native `seekable` range for Safari's native-HLS path, same fallback shape as `measureBehindLive`) instead of leaving playback wherever its buffer already sits. `'recovered'` always snaps (a reattach's buffer is freshly built from nothing — see the function's own doc comment for why trusting the still-`null` `behindLive` measurement at that exact moment would be pointless); `'visibilityRestored'` only snaps once the current measurement clears `SNAP_TO_LIVE_THRESHOLD_SECONDS` (3s) — hysteresis against reseeking a tab glanced away from for under a second. Never called for a `webrtc` transport (WHEP has no seekable buffer to fall behind — `behindLive` is pinned to `0`).
  - **Behind-live chip, honestly, with hysteresis** (docs/MVP2-PLAN.md §V, V-b — `ui/live-edge-logic.ts#shouldShowBehindLive`/`behindLiveChipLabel`): the HLS badge only quantifies "…s behind" once `behindLive` clears `BEHIND_LIVE_SHOW_THRESHOLD_SECONDS` (4s), and only stops once it drops back below the *lower* `BEHIND_LIVE_HIDE_THRESHOLD_SECONDS` (2s) — the two-threshold dead band is what stops the chip flickering between `'live · HLS'` and `'live · HLS · 4.1s behind'` as the per-second measurement jitters across one single cutoff. The hysteresis flag (`showBehindLive`, a signal) updates once per latency sample, not on every render, and resets to hidden on every fresh attach (`teardownMedia`) — a new attach starts the judgment over, it doesn't inherit the previous one's verdict.
  - **Client-side detection overlay** (item 6): optional `detections: input<DetectionResult[]>([])` / `boxesMode: input<BoxesMode>('overlay')` draw a `<canvas>` positioned over the `<video>` (`shouldDrawOverlay`/`selectDetectionResult`, `detection-overlay-logic.ts`) — boxes stay pixel-perfect at any video bitrate (unlike the server's burned-in pixels) and are hoverable (a small label+confidence tooltip, hit-tested against the last-drawn box rects on `mousemove`). **Sync**: `selectDetectionResult(results, nowMs, latencySeconds, slackBatches=1)` matches by `capturedAt` against the player's own measured `behindLive` (`0` for a live WHEP track — near-zero latency still picks the freshest batch correctly) — the newest result whose `capturedAt` isn't *ahead* of the estimated on-screen instant (`nowMs - latencySeconds*1000`), plus one observed batch-interval of slack for scheduling jitter, falling back to the oldest available result if every one looks "future" (e.g. right after attach, before latency has settled). `'burned'`/`'off'` both suppress the canvas — there is no server-side toggle to disable burn-in itself (out of scope this cycle, "no server change" per the plan), so the two states differ only in what they claim about intent, not in rendering; see the module's own doc comment. Callers that never pass `detections` simply see the canvas draw nothing — fully additive.

### `src/app/pages/map/**` — the `/map` fleet overview tab + docked live preview (docs/CYCLES-PLAN.md §6, §9)

The referee's tournament overview and the crew's "where is it" view: every asset with a known position on one map, rather than one device at a time like `/live/:deviceId`.

### Detection events — rail, per-asset section, map markers, notifications (docs/MVP2-PLAN.md §E, E-b)

The final MVP2 UI cycle: "a person was seen at 14:03 — where?" E-a's own scoping note carries forward unchanged here — **this feed is detection events only**. `EventPublisherPort`'s generic `Event`s (`PIPELINE_ERROR` etc., the docs/MVP2-PLAN.md §U-info ask) are not exposed by `GET /api/events` (a fire-and-forget/write-only port with no read side, per E-a's own MODULE.md) — no page here fakes an errors feed; the player state chip (docs/MVP2-PLAN.md §V, V-b) remains the connectivity surface, and every events surface below is labeled "detection events" rather than implying it covers pipeline health too.

- **`core/events-logic.ts`** — pure, unit-tested (40 spec cases; 61 total across this feature — see the tests bullet below), mirrors `core/telemetry-logic.ts`'s split of derivation from the injectable that drives it:
  - **Merge/dedupe/cursor** — `mergeEvents(existing, incoming, maxRetained = MAX_RETAINED_EVENTS = 200)` upserts by id (`incoming` always wins — `EventController`'s `sinceMs` cursor guarantees a repeated id is always a fresher read, never a stale duplicate), re-sorts newest-first by `lastSeen`, trims oldest-first. `advanceCursor(currentSinceMs, incoming)` adopts the newest batch's `lastSeen` (`incoming[0]`, since `EventController` returns newest-first), never regresses; `DetectionEventRepositoryPort#findRecent`'s `sinceInclusive` is genuinely inclusive, so re-requesting the exact cursor instant on the next poll is correct, not an off-by-one risk.
  - **Filtering** — `filterEvents(events, {label?, assetId?})`, `distinctLabels(events)` (alphabetical, backs the Wall rail's label `<select>`).
  - **Human-facing** — `capitalizeLabel`, `formatConfidence` (0..1 → whole-percent string), `relativeTimeLabel(atIso, nowMs)` (reuses `stream-info-logic.ts#formatDuration` rather than a second duration renderer, suffixed " ago"), `describeEventSource(event, devices, streams)` (the streaming device's own name when resolvable via `FleetStore`'s snapshots, else a short id fragment — `DetectionEvent` itself carries no display name).
  - **Navigation** — `resolveEventTarget(event, streams)` → `{kind: 'asset'|'live', id}` or `undefined`: prefers the asset detail page when `assetId` resolved, falls back to the live cockpit when the event's `streamId` is still an active stream (a device with no asset yet can still be watched live), else nothing to navigate to — the Wall rail renders an unresolvable event as a disabled row rather than guessing.
  - **Map markers** — `selectEventMarkers(events, max = MAX_EVENT_MARKERS = 30)`: only events carrying a `position` (most never get one — E-a stamps it only when telemetry was available at open time), capped to the most recent `max` (assumes `events` is already newest-first, true for everything `EventsStore.events()` hands out).
  - **Notification decision** — `shouldNotify({event, alreadySeen, notificationsEnabled, permission, documentHidden})`: `!alreadySeen && event.state === 'OPEN' && notificationsEnabled && permission === 'granted' && documentHidden` — every gate independently necessary, see the function's own doc comment for why each exists. `eventNotificationText(event)` → `{title, body}` for the native `Notification` (e.g. `"Person detected"` / `"87% confidence"`).
- **`core/events-store.ts` — `EventsStore`.** The one deliberately-shared singleton this cycle's plan explicitly permitted ("a small shared events-store singleton is acceptable if justified — document cost"), unlike `TelemetryStore`/`DetectionsStore`/`FleetMapStore`'s page-provided precedent:
  - **Why shared, not page-scoped**: three unrelated pages (Wall's rail, the fleet map's event markers, the asset detail page's assetId-filtered fallback) all want the *same* `GET /api/events` feed. A page-scoped instance per consumer (mirroring `TelemetryStore`) would mean re-fetching the full recent-events window on every tab switch (no continuous `sinceMs` cursor) and — worse — would let an already-seen event re-fire a browser notification just because the user happened to navigate between pages in between polls (no continuous "seen id" dedupe set). One long-lived `providedIn: 'root'` instance keeps both continuous across navigation.
  - **Cost, documented per the plan's own ask**: only ever *injected* from lazy route components (`WallPage`/`MapPage`/`AssetDetailPage`, plus `FleetMap` reading the already-activated singleton), never from `app.ts` or any other eager path — so it tree-shakes into whichever chunk the bundler shares across those lazy consumers, not the initial bundle (confirmed: the initial-bundle delta this cycle is +0.27 kB raw, matching only the two new eager `VisionApi` method bodies — see Status below).
  - **`activate()`/`release()` — "O(visible) discipline" (bullet 5)**: a refcounted pair, not `providedIn: 'root'`'s usual "poll from app boot forever" (`FleetStore`'s own posture). `WallPage`/`MapPage`/`AssetDetailPage` each call `activate()` in their constructor and `release()` on `DestroyRef.onDestroy` — the first `activate()` since the last full `release()` triggers an immediate poll and starts the shared 5s cadence; the poll stops entirely the moment the refcount returns to zero. No events poll ever runs while the user is on Devices/Settings/Debug/Live/Replay, however long that lasts.
  - **`ignoreHidden: true` — the one deliberate exception to "pause while hidden" in this app.** Every other poller (`FleetStore`, `TelemetryStore`, `DetectionsStore`, `FleetMapStore`) pauses while `document.hidden` to save battery/network — the right default when the only cost of pausing is "the display is a few seconds stale until the tab returns". This store cannot follow that default: bullet 4's entire premise is alerting the user *while they are not looking*, and a poll that itself paused the instant the tab backgrounds could, by construction, only ever discover new events while already visible — making `shouldNotify`'s own `documentHidden` gate permanently unsatisfiable. So `EventsStore`'s poll registration passes `{ignoreHidden: true}` to `PollScheduler.schedule` (a new opt-in option, see that file's own entry above) and keeps running at the same 5s cadence for as long as ≥1 of the three pages above is mounted underneath — the SPA route doesn't unmount just because the OS-level window/tab loses focus, which is exactly the scenario (a second monitor, another tab, a backgrounded browser) this exists for.
  - **Dedupe** (`seenIds`, a plain `Set<string>` — every id ever observed in a poll response, whether or not a notification fired for it) is what makes `shouldNotify`'s `alreadySeen` gate work across the whole session, not per-poll: an event already returned once (and therefore already shown in the rail, if the tab was visible then) can never fire a delayed notification later just because the tab happened to go background afterward.
  - Errors silently degrade (background enrichment, not a user-initiated action — same convention as every other poller here); a `new Notification(...)` construction failure (some environments accept the permission grant but still throw) is caught and swallowed rather than breaking the poll loop.
- **Wall rail (bullet 1) — `pages/wall/wall.ts`/`.html`/`.css`.** A 300px sticky right-hand rail (responsive: moves below the grid under 1000px, mirroring `pages/map/map.css`'s own `.rail` breakpoint), newest-first, capped to the 20 most recent (post-filter) via `WALL_EVENTS_DISPLAY_LIMIT` — the full retained 200 live in `EventsStore`, the rail only ever shows a "recent activity" slice. An OPEN event's row gets a pulsing `.dot.live` (the same class/animation `styles.css` already defines for every other "this is happening right now" indicator in the app — no new visual language invented) and an accent left-border (`.event-row.open`); CLOSED rows are plain. Two `<select>` filters (label, asset — options derived from whatever's currently in the feed via `distinctLabels`/a page-local `availableAssets` computed keyed by `describeEventSource`) drive `filterEvents`; empty states are honest and distinct: "no events yet" (feed is genuinely empty) vs. "no events match this filter" (feed has data, the filter excluded all of it). Each row is a `<button>`, disabled when `resolveEventTarget` can't resolve anything (an event with neither a live `assetId` nor a still-active stream) — `(click)="openEvent(event)"` navigates to the asset detail page or the live cockpit per that function's own kind. `WallPage`'s constructor calls `events.activate()`/registers `events.release()` on destroy (bullet 5) plus its own 1s `PollScheduler` clock so `relativeTime()` labels keep ticking between the 5s events poll itself.
- **Asset detail Events section (bullet 2) — `pages/asset-detail/asset-detail.ts`/`.html`/`.css`.** A `span-2` card between Telemetry and Usage history, `displayedEvents = computed(() => live() ? streamEventsSignal() : filterEvents(events.events(), {assetId: assetId()}))` — exactly the plan's own two-branch spec: while the asset is actively streaming, a **dedicated per-stream poll** (`pollStreamEvents`, `STREAM_EVENTS_POLL_INTERVAL_MS = 5_000`, calling `VisionApi.streamEvents(streamId)` directly — mirrors `DetectionsStore`'s own per-stream precedent, but inlined as a page-local `PollScheduler` registration rather than a new injectable class, since this page already inlines its asset-poll/clock registrations the same way) gives the precise, complete history for *that* stream; otherwise, the page filters the shared global feed (`EventsStore`, activated/released exactly like `WallPage`) by `assetId` — strictly less precise (bounded by the global feed's own 200-event retention and 50-per-poll limit) but the only option once there's no live `streamId` to ask about directly. Rows reuse the identical `.event-list`/`.event-row` markup/CSS as the Wall rail, minus the click affordance (informational here, not a navigation target — the page is already the asset's own detail view).
- **Fleet map event markers (bullet 3) — `pages/map/fleet-map.ts`/`.css`, `map.ts`/`.html`.** A second, independent Leaflet marker layer (`eventMarkerHandles`, keyed by event id, `zIndexOffset: -100` so they sit visually behind the asset/drone markers) driven by `computed(() => selectEventMarkers(events.events()))` — `FleetMap` injects `EventsStore` directly (root singleton, trivial anywhere) rather than duplicating the activate/release lifecycle; `MapPage`'s own constructor is the one call site that activates/releases it for this page, exactly like `WallPage`/`AssetDetailPage`. **Deliberately excluded from auto-fit** — `fitToMarkers`/the fingerprint-gated re-fit effect still only ever look at `store.markers()` (asset markers), unchanged; a stray old event elsewhere on the map must never yank the fleet view away from where the assets actually are. A small pulsing amber/red dot (`.event-marker-dot`, OPEN pulses via the same `@keyframes` idiom as `styles.css`'s `.dot.live`, CLOSED is static) with a popup: label, state chip, peak confidence, first/last-seen (both `relativeTimeLabel`, computed at popup-build time — not independently ticking between the 5s events poll like the Wall rail's clock-backed one, a deliberate small simplification since a map popup is glanced at, not stared at), and an **Open asset** button when `assetId` resolved (`.event-asset-btn[data-asset-id]`, wired through the same single delegated map-container click listener `watch-btn`/`preview-btn` already use, emitting a new `openEventAsset = output<string>()` that `MapPage.openEventAsset()` forwards straight to its existing `openAsset()`/`router.navigate(['/assets', id])`).
  - **Honest gap, not a shortcut** (the plan's own fallback instruction, followed literally): clicking an event marker links to the asset detail page, **not** a replay moment, even though R-b's replay route (`/assets/:assetId/replay/:usageId`) exists and would be the more satisfying answer to "where was it at 14:03". - **Notification opt-in (bullet 4) — `pages/settings/settings.ts`/`.html`.** A "Notifications" card, third from the top (before "Detection profile"): one checkbox, `SettingsStore.eventNotifications` persisted. `toggleEventNotifications(checked)` is the **only** place `Notification.requestPermission()` is ever called — turning the toggle **off** never touches the browser permission at all (just this app's own opt-in flag); turning it **on** calls `requestPermission()` when the current grant is `'default'` (most browsers require a direct user gesture for the prompt to appear at all, which a checkbox click is and a background poll is not), and only actually sets `eventNotifications` to `true` if the result is `'granted'` — a `'denied'` browser-level refusal leaves the setting off with an explanatory toast rather than a checkbox that silently reverts with no stated reason. `notificationPermission()` (a plain method, not a signal — this app has no precedent for polling `Notification.permission` for external changes, and a mid-session revoke from browser chrome is a rare, refresh-recoverable edge case not worth a new polling concern) reads `'unsupported'` when the global doesn't exist at all, driving a small explanatory line under the toggle for `'denied'`/`'unsupported'`.
- **Poll cadence summary (bullet 5)**: events poll at 5s while ≥1 of Wall/Map/asset-detail is mounted (`EventsStore.activate`/`release`, `ignoreHidden: true` so it also keeps running while the tab itself is backgrounded — see that class's own doc comment above for why); the asset detail page's *additional* per-stream poll (also 5s) runs only while that specific asset is actively streaming, on top of — not instead of — the shared global poll (bullet 2's page still activates `EventsStore` too, since its own header/other pages/future features may want the global feed's dedupe state warm regardless of which branch `displayedEvents` is currently reading).

### `src/app/pages/debug/**` — the raw API console (WEB-PLAN W5)

Deliberately outside the "no component calls `fetch` directly" rule: this page's entire purpose is issuing raw, possibly-malformed requests and showing the raw failure, so `VisionApi`/`FleetStore`'s typed shapes and single-toast error handling would work against it.

- `debug-api.service.ts` — `DebugApiService` (`@Injectable providedIn: 'root'`), the only thing in this module that touches `HttpClient` outside `core/api/`. `send({method, path, body?})` issues the request with `observe: 'response'`, `responseType: 'text'` (so any body — JSON or not — parses manually downstream) and returns `RawResponse { status, statusText, ms, headers, bodyText, reached }` for both success and error paths uniformly (a non-2xx is not a thrown exception here, it's data). `reached` is `false` only when the request never got a response at all (network failure / status 0). Request body text is sent as parsed JSON when it parses, verbatim otherwise — a malformed body is something this console must let you send, not reject client-side. Not used by any other page.
- `debug-endpoints.ts` — pure, Angular-free: `DEBUG_ENDPOINTS`, one entry per route in vision-api/MODULE.md's controller table (14 total), each with `method`/`path`/`label` and (POSTs only) a pretty-printed `exampleBody`. `prefillForEndpoint(id)` is what the endpoint `<select>` uses to fill method/path/body; path templates carry `{placeholder}` segments through untouched for the user to hand-edit. `methodHasBody(method)` gates the body textarea (POST/PUT/PATCH).
- `debug-response.ts` — pure: `formatResponseBody(text)` pretty-prints JSON with a raw-text fallback (never throws) plus an explicit `(empty body)` case; `isSuccessStatus(status)` for the 2xx badge.
- `debug-history.ts` — pure: `pushHistoryEntry(history, entry, limit = 20)`, newest-first, capped, non-mutating. Backs the last-~20-requests log; clicking a row re-fills the form (`DebugPage.replay()`) but does not re-send.
- `debug.ts`/`.html`/`.css` — `DebugPage`, three cards: the console above; Health (`GET /actuator/health` parsed for `status`/`components[].status`, up/down chips, raw JSON in a `<details>`); Last scan (`POST /api/discovery/scan` with `{}`, raw `ScanResultResponse` including `failedMethods`). ## Conventions

- Standalone components only, `changeDetection: ChangeDetectionStrategy.OnPush` everywhere, signals for all component state, zoneless (`provideBrowserGlobalErrorListeners()`, no `zone.js`).
- `api/models.ts` is the **only** place wire shapes are declared — when a Java DTO changes, fix this file first, then chase usages (`grep -rn` the changed field name under `src/`).
- HTTP errors are reported once, by the layer that knows what the user attempted (`FleetStore.run()`), never by an interceptor.

## Gotchas

- **`AssetDetailPage.assetId`'s route-input binding — flagged by R-b as suspicious-but-not-chased-further, fixed by docs/MVP2-PLAN.md §V, V-b.** R-b's own writeup (kept below, for the record) correctly identified the mechanism but stopped short of checking the actual runtime effect; V-b did, with a throwaway `RouterTestingHarness` spec (`navigateByUrl('/assets/probe-…', AssetDetailPage)`, then asserted on `instance.assetId()`, deleted again once confirmed — not part of this app's permanent suite, since this app has no other page-component-level specs to fold it into): **the mismatch was not inert.** `withComponentInputBinding()` called `setInput('assetId', undefined)` on every activation exactly as predicted, `assetId()` read back as `undefined`, and the page's own `effect()` called `this.api.getAsset(undefined)` — which Angular's `HttpClient` happily serializes to a `GET /api/assets/undefined` request. Concretely, **every real navigation to the asset detail page (Devices list "Open", Map rail "Open") hit the "Unknown asset" empty state instead of the actual asset**, unconditionally, regardless of whether the asset existed — the page was not silently degraded, it was **fully broken** for its one real entry point. The fix: `app.routes.ts`'s path segment renamed `assets/:id` → `assets/:assetId`, matching `AssetDetailPage.assetId`'s own public input name exactly (the same fix the replay route already modeled, see the Routes entry above) — the alternative option (alias the input to `id`) was rejected as the less-consistent one, since it would leave `assets/:assetId/replay/:usageId` and `assets/:assetId` naming the same path segment two different ways. No call site needed touching: every `router.navigate([...])` to this route is positional (`['/assets', assetId]`, `pages/devices/devices.ts`/`pages/map/map.ts`), not param-name-based. Re-ran the same probe spec after the fix to confirm `assetId()` now reads the real value before deleting it. **Original R-b finding, for the record**: "`app.routes.ts`'s `assets/:id` route produces `params = {id: '…'}`, but `AssetDetailPage` declares `readonly assetId = input.required<string>()` (public name `assetId`, no alias) — the two names don't match, so … the binder calls `setInput('assetId', undefined)` on every activation rather than leaving it unset. Whether this is actually inert in practice … wasn't chased further."
- **`ng test` ≠ `vitest run`.** This project's Vitest specs depend on Angular's zoneless `TestBed` bootstrap, which `@angular/build:unit-test` wires up; invoking `vitest` directly skips that and every spec fails with `TestBed.initTestEnvironment()`/`PlatformLocation` JIT errors. Always use `npm run test:ci` / `npm test` / the Maven `npm-test` execution.
- **WHEP fails for a LAN viewer against the dockerized stack only when `VISION_WEBRTC_HOST` is left unset — this is expected, not a bug, and it's now the operator's choice, not a hard limit** (docs/MVP2-PLAN.md §L, and §V's V-e, which closed this gap after this Gotcha was first written). mediamtx in Docker advertises `127.0.0.1` ICE candidates by default (`MTX_WEBRTCADDITIONALHOSTS: "${VISION_WEBRTC_HOST:-127.0.0.1}"` in `docker-compose.yml`), so with `VISION_WEBRTC_HOST` unset, a browser on a *different* machine than the Docker host still always fails the WHEP exchange and silently lands on HLS via `Player`'s fallback (`ui/player-recovery.ts#reduceTransportRecovery`) — this is the entire reason that fallback exists and is treated as load-bearing, not an edge case. Setting `VISION_WEBRTC_HOST` in `.env` to the Docker host's own real LAN IP (see `vision-app/MODULE.md`'s "WHEP viewing" section for how an operator finds it and how to list more than one) makes WHEP work for LAN viewers pointed at that IP too, not just same-host ones. Don't "fix" a LAN demo showing `HLS` in the transport chip without first checking whether `VISION_WEBRTC_HOST` is actually set for that stack — an unset value is still expected same-host-only behavior, not a bug; once it *is* set, only a viewer entirely off that configured LAN/host (a different network, cellular data, a remote friend) should still show `HLS`. This app (`vision-web`) needed no change for V-e — the player's existing try-WHEP-then-HLS fallback already covers both the unset and the off-LAN cases identically; V-e is purely a compose/`.env` configuration lever.
- **`ui/player.ts`'s WHEP path gathers ICE non-trickle** (`waitForIceGatheringComplete`, bounded to `ICE_GATHERING_TIMEOUT_MS`=3s) rather than implementing WHEP's optional trickle-ICE PATCH exchange — simpler, and irrelevant to the LAN caveat above (a hung/incomplete gather just means a candidate-poor offer, not a different failure mode). If a future cycle needs faster/more-complete ICE negotiation, trickle is the documented gap, not a bug.
- **`ui/flight-plan-dialog.ts` is a modal (`position: fixed`, `z-index: 150`)**, not a page section — deliberately mounted only via `@if` in each host page's template (not always-in-DOM-but-hidden) so its own `afterNextRender` (and therefore Leaflet's `import('leaflet')`) only fires once the dialog is actually opened, matching every other map component's "chunk fetched on first use" convention. `150` sits above the toast host (`z-index: 100`) and the app header (`20`) on purpose — a toast fired while the dialog is open would otherwise render behind it; the dialog itself never toasts, so this is mostly theoretical, not exercised today.
- **`DiscoveredDevice.suggestedCategory` stays a bare `string`.** Even though `Category` is now mirrored (docs/CYCLES-PLAN.md §2), discovery's suggestion is still typed as a plain slug, not `Category`/an enum — there is still no page that lists `GET /api/categories` to validate against, so don't tighten this without adding that consumer first.
- **Leaflet's own CSS is loaded at runtime, not imported as a component stylesheet.** `public/leaflet/leaflet.css` is a manual copy of `node_modules/leaflet/dist/leaflet.css` (kept in sync by hand when the `leaflet` version bumps — there is no build step that does this automatically); `angular.json`'s `assets` glob copies it to `dist/leaflet/leaflet.css` like any other static asset. `ui/leaflet-loader.ts#ensureLeafletStylesheet()` (shared by both `LiveMap` and `FleetMap` since docs/CYCLES-PLAN.md §6) injects a `<link>` pointing at it the first time a map is created; idempotent, so either component can call it regardless of which one's map is created first. This is deliberate: importing the real file (14.8 kB raw) as a component `styleUrl` would trip the `anyComponentStyle` budget (10 kB error) and, if imported globally instead, would grow the initial bundle — a runtime-injected `<link>` to a plain static asset is invisible to both.
- **`::ng-deep` in `live-map.css` and `fleet-map.css`** targets DOM Leaflet creates itself (tiles, custom marker/popup/flag divIcons) — those elements never get Angular's `_ngcontent-*` attribute because Angular didn't render them, so emulated view encapsulation would otherwise silently no-op those rules. Still the standard, if deprecated, workaround for third-party-owned DOM inside an Angular component; scoped under `:host` to limit its reach. Each component still carries its **own** copy of the small rules that give Leaflet-owned elements their look (e.g. `.drone-arrow`'s geometry/color) — `ui/leaflet-loader.ts` shares the *JS* that builds/configures Leaflet objects, but per-component scoped CSS can't be shared the same way, so this one bit of duplication is intentional. `fleet-map.css`'s popup rules also lean on global classes (`.chip`, `.btn`) from `src/styles.css` for the parts that match existing chip/button styling — those aren't `::ng-deep`'d because a *global* stylesheet already reaches Leaflet-owned DOM without needing to. **The `vision-tiles`/`DARK_TILE_CLASS` CSS-invert dark tint is gone** (docs/CYCLES-PLAN.md §9, CU-b item 6) — "dark" is now the real CARTO Dark Matter tile layer (`Night`, the default), not a filter over OSM; don't reintroduce the filter if OSM ever needs re-tinting for some other reason without checking whether a `Night`-style real layer is the better fix first.
- **`allowedCommonJsDependencies: ["leaflet"]`** in `angular.json` — Leaflet ships UMD only (no `module`/`exports` field), so without this the build emits (non-fatal) "not ESM, can cause optimization bailouts" warnings.
- **`InMemoryTelemetryRepository#findByUsage` (vision-app, not this module) returns the *first* `limit` samples of an ever-growing list, not the most recent.** At the sim's 1 Hz, a usage older than ~200 s will make `GET /api/usages/{id}/telemetry?limit=200` keep returning the same frozen earliest window forever, so `TelemetryStore.latest()`/`sampleAgeSeconds()` will appear to go stale permanently past that point in a long-running demo. This is a backend devsupport-adapter limitation (out of `vision-web/**`'s scope to fix), not a frontend bug — worth knowing before blaming the OSD's staleness indicator. `pages/asset-detail/asset-detail-logic.ts#groupTelemetryByDevice`/`freshestSample` (docs/CYCLES-PLAN.md §11) read from the exact same `usageTelemetry` response, so the asset detail page's per-device panels/"source: …" caption inherit this identical frozen-window ceiling — not a new bug, the same one wearing a new UI.
- **CDK virtual scroll (`pages/devices/devices.ts`, docs/CYCLES-PLAN.md §11) is this app's first actual use of `@angular/cdk`** beyond it sitting in `package.json` unused (it was pinned ahead of time for exactly this — see WEB-PLAN W6). `*cdkVirtualFor` is a classic structural directive (not the newer `@for` control-flow block — Angular has no virtualized `@for` equivalent), so it coexists in the same template as `@if`/`@for`/`@switch` elsewhere on the page without conflict; the one real constraint is that `<cdk-virtual-scroll-viewport>` needs a **fixed height** (`.asset-viewport`, `height: min(64vh, 26rem)`) and becomes its own self-scrolling region — a deliberate, necessary break from this page's otherwise full-document scroll, not an oversight.
- **`ui/live-map.ts` used to live at `pages/live/live-map.ts`.** Moved in docs/CYCLES-PLAN.md §11 (CD-b) when `pages/asset-detail/asset-detail.ts` needed the identical single-asset map inset — see that file's own MODULE.md entry and `core/device-logic.ts`'s doc comment for the "no page imports another page's module" precedent this follows. If a search for `live-map.ts` under `pages/` comes up empty, this is why.
- **`@angular/cdk/scrolling` alone costs ~17 kB raw / ~4 kB transfer of *eager* bundle**, confirmed by isolating it (temporarily stripping the import and its one call site, rebuilding, restoring) — this is what pushes the initial bundle from 284.67 kB (before this cycle) to 301.91 kB, past the 300 kB *warning* threshold (not the 360 kB error one, which stays comfortably out of reach). None of it is `@angular/cdk/scrolling`'s own code appearing in an eager chunk *by name* (grep for `CdkVirtualScroll`/`ScrollDispatcher`/etc. in the initial chunks finds nothing — post-minification identifiers don't preserve those names), so this is very likely the module's own base dependencies (`Platform`, bidi/RTL support) that Angular's build resolves into a shared vendor chunk regardless of how few lazy chunks reference them. This is a deliberate trade-off, not an oversight: docs/CYCLES-PLAN.md §11 item 4 explicitly asks for "CDK virtual scroll on the asset list", and this is the first time this app has used any `@angular/cdk` submodule beyond what shipped inert in `package.json` — the cost is real but the warning margin (1.91 kB over 300, vs. a 60 kB cushion to the 360 kB error) leaves comfortable room.
- **`PollScheduler`'s heartbeat is 1 s (`TICK_MS`, `core/poll-scheduler.ts`).** Every cadence registered via `schedule(periodMs, callback)` should be a multiple of 1,000 ms (every current caller's is: 1s/2s/5s) — a period that isn't lands on the next tick at or after its due time, not exactly on it, which is a few-hundred-ms slip once, not a growing drift (each task's own `nextDueAt` is recomputed from the tick that actually ran it, not from a fixed schedule).
- **`M` toggles the Live page's map inset** (docs/CYCLES-PLAN.md §9, CU-b item 4) via a page-scoped `document` `keydown` listener in `LivePage`'s constructor — ignored while an `INPUT`/`TEXTAREA`/`SELECT` has focus or a modifier key is held, and removed on `DestroyRef.onDestroy`, so it can never fire from another route. Keep that ignore-list in sync if a future page adds more form-field-like custom elements.
- `frontend-maven-plugin` provisions a **pinned** Node/npm into `target/node` per the `pom.xml` properties (`node.version`, `npm.version`) — doesn't use whatever Node is on `PATH`.
- `dist/` (Angular build output) is copied verbatim into `target/classes/META-INF/resources` by `maven-resources-plugin` in `prepare-package`; nothing here compiles Java (`No sources to compile` in `mvn` output is expected, not a failure).

**Player recovery, concretely**: `reduceRecovery(state, event)` is a pure reducer over `PlayerPhase = 'idle'|'connecting'|'waiting'|'playing'|'reconnecting'|'error'`. Before ever playing, a missing playlist (`playlistNotReady`) stays `waiting`, retried every 1.5s indefinitely (no cap — the old `FIRST_SEGMENT_RETRY_LIMIT=40` gave-up-after-40-tries behavior is gone, replaced by "poll until ready" per the plan's literal wording). Once attached, a stall watchdog (`isStalled`: no `FRAG_BUFFERED`/native `progress` event for 8s) or a genuine fatal error moves to `reconnecting`, which schedules a reattach after `reconnectDelayMs(attempt)` — capped exponential, 1s→2s→4s→…→30s, held at 30s indefinitely. `error` is now reached only for "this browser can play neither native HLS nor hls.js" — never for a transient network/backend hiccup, which is the whole point: the player never gives up on its own while `src` stays set, verified conceptually against "must survive a backend restart" (an outage of any length is just a longer run of 30s-spaced retries, not a terminal state).

**Detection overlay sync, concretely**: `selectDetectionResult(results, nowMs, latencySeconds, slackBatches=1)` estimates the on-screen frame's capture instant as `nowMs - latencySeconds*1000` (`latencySeconds` is `ui/player.ts`'s own measured `behindLive`, piped in as an input — never re-measured), then picks the newest of the newest-first `results` whose `capturedAt` doesn't run ahead of that instant, with one observed inter-batch interval of slack for scheduling jitter; falls back to the oldest result if every one looks "future" (the brief window right after attach before latency has settled). Boxes are drawn on a `<canvas>` sized to the video element's own box, mapped through `object-fit: contain`'s letterbox rect (`Player#letterboxRect`) so they land pixel-correct regardless of aspect ratio; hover hit-tests the last-drawn rects for a label+confidence tooltip.

**Multi-telemetry, concretely**: `TelemetrySampleResponse.deviceId` (CD-a, already server-side) means one usage's `GET /api/usages/{id}/telemetry` response can legitimately mix samples from more than one TELEMETRY-capable device. `groupTelemetryByDevice` regroups them by source for the asset detail page's per-device panels; the map, by contrast, deliberately keeps using `TelemetryStore.latest()`/`trail()` (the whole mixed stream, unfiltered) for its marker/trail — since the backend returns samples chronologically regardless of source, the *last* sample in that flat list already **is** the freshest across every source, which is exactly what item 3 asks the marker to show, with zero new store code needed. `freshestSample` (a separate, explicit "max by timestamp across per-device groups" computation, `O(devices)`) backs only the page's "source: <device name>" caption — a transparency nicety, not the map's actual position math.

## V-b — player live-edge tuning (docs/MVP2-PLAN.md §V)

The user directive behind §V ("the user should see the latest available shot, not a buffered 10 seconds ago") splits into a backend half (V-a: encoder/mediamtx/proxy, `adapters/adapter-publish-hls`/compose, concurrent with this task and not depended on) and this UI half: make `ui/player.ts`'s HLS path actually try to stay near the live edge — hls.js ships with almost none of that tuning enabled by default — and stop it silently drifting stale after a stall recovery or a backgrounded tab, instead of just watching a `behindLive` number climb. Also folds in a pre-existing, previously-flagged-but-unfixed bug (below) that R-b found while wiring the replay route but didn't chase to its actual runtime effect.

**New files**: `ui/live-edge-logic.ts` (+`.spec.ts`, 16 cases). **Reshaped**: `ui/player.ts` (HLS live-edge config constants, snap-to-live wiring, behind-live chip hysteresis — no rewrite of the WHEP/recovery machinery itself), `app.routes.ts` (`assets/:id` → `assets/:assetId`).

**hls.js config, concretely** — every value lives as a named constant with its own doc-comment block directly above `beginAttach` in `ui/player.ts` (not restated in full here; see that file):
- `lowLatencyMode: true` — unchanged from before this cycle.
- `liveSyncDurationCount: 2` / `liveMaxLatencyDurationCount: 4` — **segment-count**, not the duration-based `liveSyncDuration`/`liveMaxLatencyDuration` (hls.js throws a config error if you mix the two families). Chosen over duration because V-a shrinks segment/part duration server-side as part of this very same latency push (legacy ~6s segments → LL-HLS parts ~200ms) — a fixed-seconds target would need re-tuning every time that number changes on a given deployment; a count-based one scales automatically on either side of that landing, and behaves identically against a stock playlist that never advertises `PART-HOLD-BACK` at all (confirmed by reading hls.js's own `LatencyController` source directly, not assumed: `synchronizeToLiveEdge` computes its own `maxLatency` from `liveMaxLatencyDurationCount * targetduration` whenever the duration variant is unset). The load-bearing finding here: hls.js's own default for `liveMaxLatencyDurationCount` is **`Infinity`** — meaning without this, hls.js never forcibly reseeks a drifted playhead at all, regardless of how far behind it gets. This player had `lowLatencyMode: true` before V-b but nothing else, so that forced-catch-up mechanism has been silently off since it was first added (U3).
- `maxLiveSyncPlaybackRate: 1.5` — hls.js's own gentle rate-based catch-up (nudges `video.playbackRate` above `1`, capped at `1.5`, while behind-but-within-range, closing the gap without a visible seek jump); gated only by `lowLatencyMode` + a live playlist (verified in hls.js source — not further gated by actual LL-HLS tags), so this activates today, before V-a lands anywhere. Default is `1` (inert) — another mechanism that was silently off.
- `maxBufferLength: 10` (down from hls.js's own `30`s default, sized for VOD scrubbing headroom this player never uses) / `backBufferLength: 30` (unchanged, just promoted to a named constant).

**Snap-to-live, concretely** (`ui/live-edge-logic.ts#shouldSnapToLive`/`SnapToLiveReason`, wired from `ui/player.ts`): two reasons, both read off state the recovery reducer already owns rather than inventing parallel component flags —
- `'recovered'`: fired the instant `player-recovery.ts`'s own `transportState().recovery.phase === 'reconnecting'` is observed (read *before* the `firstSegment` event is applied, at the exact hls.js `FRAG_BUFFERED` / native `playing` callback that would otherwise transition to `playing`) — a stall or fatal error already tore the previous attachment down and rebuilt it from nothing (`teardownMedia`), so there's no actual stale buffer to correct, but also no cost to landing exactly on `hls.liveSyncPosition` instead of trusting wherever the fresh attach's own start-position logic lands it. Always snaps, deliberately ignoring the (almost always still-`null` at that instant) measured latency.
- `'visibilityRestored'`: fired when `document.hidden` flips `true`→`false` between two ticks of the *existing* 1s latency-sampling timer (`startLatencySampling`) — no new `visibilitychange` listener; diffing `document.hidden` off an already-running heartbeat mirrors `core/poll-scheduler.ts`'s own precedent for checking it, just on `ui/player.ts`'s own per-second timer instead of `PollScheduler`'s (this file already deliberately does not pause that timer while hidden — see the pre-existing Status/Gotchas note on why). Only snaps once the fresh measurement clears `SNAP_TO_LIVE_THRESHOLD_SECONDS` (3s) — a tab glanced away from for under a second shouldn't yank the video out from under the viewer.
- Both funnel into `snapToLiveEdge()`: `video.currentTime = hls.liveSyncPosition` when hls.js is the active engine, falling back to the end of the native `seekable` range for Safari's native-HLS path (mirrors the pre-existing `measureBehindLive`'s own fallback shape). Never called for a `webrtc` transport — WHEP has no seekable buffer to fall behind (`behindLive` is pinned to `0`), and in practice `maybeSnapToLive` is only ever invoked from HLS/native code paths in the first place.

**Behind-live chip, concretely** (`ui/live-edge-logic.ts#shouldShowBehindLive`/`behindLiveChipLabel`): the chip's quantified tail (`'live · HLS · 4.2s behind'`) only appears once `behindLive` clears `BEHIND_LIVE_SHOW_THRESHOLD_SECONDS` (4s), and only disappears again once it drops below the *lower* `BEHIND_LIVE_HIDE_THRESHOLD_SECONDS` (2s) — the two-line dead band (a `showBehindLive` signal, not recomputed from a single comparison on every render) is what stops the label flickering between `'live · HLS'` and the quantified form as the once-a-second measurement jitters near a single cutoff. Below the show threshold the chip reads a plain `'live · HLS'` — the old unconditional-whenever-known behavior (`'{behind}s behind · HLS'`, shown any time latency was measured at all, even at `0.3s`) is gone; sub-few-second HLS latency isn't worth quantifying at a glance, and `'live · WebRTC'` already sets the "just say live" precedent this now matches. Word order also changed to put the transport right after "live" in both cases (`'live · WebRTC'` / `'live · HLS'` / `'live · HLS · Xs behind'`), per the task brief's own example format — previously HLS's behind form read `'{X}s behind · HLS'`, transport last.

**Route-param bug, concretely** — see the Gotchas entry (rewritten in place, not duplicated here) for the full writeup: `app.routes.ts`'s `assets/:id` didn't match `AssetDetailPage.assetId`'s input name, and — confirmed empirically with a throwaway `RouterTestingHarness` spec, not just re-reasoned from the router source — this was not inert: every real navigation to the asset detail page landed on the "Unknown asset" empty state, unconditionally. ## E-b — detection events: rail, per-asset section, map markers, notifications (docs/MVP2-PLAN.md §E)

The final MVP2 UI cycle. E-a (backend) shipped `GET /api/events`/`GET /api/streams/{streamId}/events` — plain polling, newest-first by `lastSeen`, a `sinceMs` cursor — and explicitly flagged one scoping gap for this cycle to respect: pipeline-error `Event`s (`PIPELINE_ERROR` etc.) are **not** on this API at all (a write-only port with no read side), so nothing here fakes an errors feed; every surface below is detection events only, labeled as such. Full feature writeup (every file, every design decision): the dedicated "Detection events" section under **API surface** above, plus `core/events-logic.ts`'s/`core/events-store.ts`'s own doc comments. This entry is the Status-page summary: what shipped, the numbers, and the deviations.

**New files**: `core/events-logic.ts` (+`.spec.ts`, 40 cases — merge/dedupe/cursor, filtering, human-facing formatting, navigation-target resolution, map-marker selection, the notification decision), `core/events-store.ts` (+`.spec.ts`, 14 cases — the shared `EventsStore` singleton). **Reshaped**: `core/poll-scheduler.ts` (+`.spec.ts`, +2 cases — new opt-in `ScheduleOptions.ignoreHidden`), `core/api/models.ts` (`DetectionEvent`/`DetectionEventState`), `core/api/vision-api.ts` (+`.spec.ts`, +3 cases — `events()`/`streamEvents()`), `core/settings-store.ts` (+`.spec.ts`, +2 cases — `eventNotifications`), `pages/wall/wall.ts`/`.html`/`.css` (events rail), `pages/asset-detail/asset-detail.ts`/`.html`/`.css` (Events section), `pages/map/fleet-map.ts`/`.css`, `pages/map/map.ts`/`.html` (event markers + wiring), `pages/settings/settings.ts`/`.html` (notification toggle).

**The one genuinely new architectural piece**: `EventsStore` breaks from every prior store in this app (`TelemetryStore`/`DetectionsStore`/`FleetMapStore`, all page-provided, one instance per route activation) by being a `providedIn: 'root'` singleton with its own `activate()`/`release()` refcounting instead — the plan's own text explicitly permitted this ("a small shared events-store singleton is acceptable if justified — document cost"), and the reason is concrete: three unrelated pages want the *same* feed, and a page-scoped instance per consumer would mean losing the `sinceMs` cursor and the notification-dedupe `seenIds` set on every tab switch, which is both wasteful (re-fetching the same recent window) and actively wrong (letting an already-seen event re-notify later purely because the user changed tabs). The refcounting (`activate`/`release`, called from `WallPage`/`MapPage`/`AssetDetailPage`'s own constructor/`DestroyRef`) is what still delivers "O(visible) discipline" (bullet 5) despite the singleton shape: no poll runs at all while none of those three pages is mounted.

**The one deliberate exception to "pause while hidden"**: `PollScheduler.schedule` gained an opt-in third parameter, `{ignoreHidden: true}` (default `false`, every pre-existing caller unaffected — see that file's own 2 new spec cases). `EventsStore` is its only user. This exists because bullet 4's browser-notification feature is fundamentally incompatible with pausing on hidden: the whole point is alerting the user *while they are not looking*, and a poll that itself stopped the instant the tab backgrounds could, by construction, never discover anything to notify about while backgrounded — `shouldNotify`'s own `documentHidden` gate would be permanently unsatisfiable. Every other poller in this app keeps the old default (pausing is strictly better for them — the only cost is a display going a few seconds stale, no feature depends on it continuing while hidden).

**How the notification gating actually works, end to end**: `EventsStore.pollOnce()` runs every 5s (via the `ignoreHidden` registration above) for as long as ≥1 of Wall/Map/asset-detail is mounted. Each poll's `incoming` batch is checked, per event, against a single `seenIds: Set<string>` — every id ever observed in *any* poll response, regardless of whether a notification ever fired for it. `shouldNotify({event, alreadySeen, notificationsEnabled, permission, documentHidden})` (the pure decision function, `core/events-logic.ts`) then requires, all five, together: the id is genuinely new (`!alreadySeen`); `event.state === 'OPEN'` (a CLOSED event arriving for the first time — e.g. right after the session begins — is history, not news); `SettingsStore.eventNotifications()` is `true` (the user's own opt-in, `pages/settings/settings.ts`); `Notification.permission === 'granted'` (the browser's own opt-in — `settings.ts#toggleEventNotifications` is the **only** call site that ever calls `Notification.requestPermission()`, and only from the checkbox's own click handler, since most browsers require a direct user gesture for the prompt to appear); and `document.hidden` is `true` at the instant of the check (the visible app already shows the event in whichever rail is on screen — a notification on top would be noise, not news). Every gate is independently necessary and independently unit-tested (`shouldNotify`'s own 6 spec cases cover each one refusing in isolation). A passing event fires `new Notification(title, {body, tag: event.id})` — `tag` is belt-and-braces against a genuine double-fire (e.g. two overlapping polls), on top of, not instead of, the `seenIds` dedupe.

**Honest gap, followed as specced, not shortcut** — map event markers (bullet 3) link to the asset detail page, not a replay moment at the event's `firstSeen`, even though R-b's `/assets/:assetId/replay/:usageId` route exists. Resolving event→usage needs a `usageId`, and **no current API exposes one from an event**: `AssetUsageResponse` (verified by reading the Java DTO source directly) carries no `streamId` on the wire at all — R-a2 added `streamId` onto the *domain* `AssetUsage`, but it was never threaded onto this response DTO. The plan's own fallback instruction ("if resolving event→usage isn't possible from current APIs, link to asset detail instead and document the gap honestly") was followed literally rather than worked around with a guess.

**Poll cadence, concretely (bullet 5)**: the shared global feed polls every 5s while ≥1 of Wall/Map/asset-detail is mounted (`EventsStore`, `ignoreHidden: true`, see above). The asset detail page's own Events section additionally runs a **second**, page-local 5s poll (`pollStreamEvents`, `VisionApi.streamEvents(streamId)`) whenever that specific asset is actively streaming — a dedicated per-stream query, more precise than filtering the global feed, inlined as a plain `PollScheduler` registration (mirroring how that page already inlines its asset-poll/clock registrations) rather than a new injectable class. Neither poll runs at all on Devices/Settings/Debug/Live/Replay.
