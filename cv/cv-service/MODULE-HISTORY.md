## docs/plans/active/CV-ORCHESTRATION-PLAN.md — wave W5b.5

**2026-09-13** (trace replay, plan §8 E23). New `tools/trackeval/trace.py`: `read_trace(path) -> Recording`, the last leg of decision E23 — turns a saved `CvTrace` JSON (the file `station/vision-web`'s "Save trace" downloads, wave W5.4) into the same `recording.Recording` shape `tools/trackeval/recording.py`'s real-footage path already replays, reading `frame[].detections` (this wave's own new wire field, W5b.0-W5b.3 up the stack) rather than `world[]` — the tracker's own already-associated fold would prove nothing replayed back through the tracker. `frame[]` is sorted by `sequence` (a trace's JSON order is not guaranteed to be capture order); `width`/`height` come from the first frame's `frameWidth`/`frameHeight`, `ValueError` when absent/zero (a pre-W5b trace); `fps` is the median consecutive `capturedAtMillis` delta, `ValueError` on fewer than 2 frames, but a non-positive median delta is deliberately NOT an error — `fps` becomes `0.0`, the same "unknown" sentinel `metrics.summarize_recording` already special-cases, needed because the real Java-generated wire-contract fixture (`station/vision-api`'s `CvTraceResponseWireContractTest`, copied into `tests/trackeval/fixtures/cv-trace.wire.full.json`) happens to stamp both its frame examples with one fixed timestamp. No `CameraPose` exists on a `CvTrace` at all, so every `RecordedFrame` this reader builds keeps `recording.py`'s own zero-pose default — replay runs without ego-motion compensation, disclosed in `tools/trackeval/README.md`'s new "Replaying a saved trace" section. `tools/trackeval/__main__.py` gained `--trace FILE` (no CLI path replayed a `Recording` at all before this wave — the smallest addition, not a second tool): reads the trace, calls `recording.replay_recording`, prints `metrics.summarize_recording`'s cost/structural fields through a new minimal `_print_recording_summary` (no IDSW/FM/MT table — a trace carries no ground truth, same as any real-footage replay). New `tests/trackeval/test_trace.py` (10 tests, pure stdlib, no `numpy` needed) against a hand-written `tests/trackeval/fixtures/min-trace.json` (3 frames, deliberately out of sequence order in the file, a couple of boxes) and against the copied Java fixture; `test_main.py` gained one `--trace` CLI test. Full `pytest -q`: **1504 passed, 7 skipped** (+11 over W5b.1's 1493); the 30 golden fixtures and `BASELINE.md` remain untouched (`git status --short -- cv/cv-service/tools/trackeval/` shows only `__main__.py` modified and `trace.py` new). `trace.py` itself is 120 lines, under the wave's own ≤~150-line budget.

## docs/plans/active/CV-ORCHESTRATION-PLAN.md — wave W5b.1

**2026-09-13** (trace replay, plan §8 E23). `FrameLedger` grew `detections: tuple[object, ...]` + `frame_width`/`frame_height: int`, populated by `session.process()`'s new `trace`/`frame_width`/`frame_height` keyword arguments — the same `request.trace` `_tracked_response` already gates the wire's `response.ledger` attachment on, threaded one call further in. `detect.full`'s own `Key.DETECTIONS` is read straight off `FrameContext` right after `orchestrator.run()` returns, exactly once, never `detect.roi`'s separate `Key.DETECTIONS_ROI` — proved by a new test that traces the exact ROI-rescue scenario `test_roi_rescue_recovers_an_unmatched_confirmed_track_under_its_own_id` already covers and asserts the ledger's `detections` stays empty even though the frame's own `boxes` shows a recovered track. Attachment point chosen deliberately at `session.process()` (not the aggregator, not the servicer): `Key.DETECTIONS` and the frame's own request only meet there, it is the exact same "built after the run, from `ctx` and `ledger`" shape `_object_states` already uses two lines below it, and it needed no new key or contributor. Populated ONLY when tracing (unlike `entries`/`objects`, which are unconditional) — the plan's own wave-row text says so, and it keeps an untraced frame's ring entry exactly as cheap as before this wave. All 1493 pre-existing tests plus 3 new ones pass; the 30 golden fixtures and `BASELINE.md` under `tools/trackeval/` are untouched (`git status --short` shows no diff there) confirming the trace-off wire response is unaffected.

## docs/plans/active/CV-ORCHESTRATION-PLAN.md — wave W1

CV-ORCHESTRATION wave **W1 (the wire mirror) is complete on the cv-service side**: every `DetectionResponse` now carries `objects[]` — one `ObjectState` per LIVE track plus one per DORMANT identity — and, when `FrameRequest.trace` is set, that frame's whole `FrameLedger` on field 28. `detections[]` is untouched and the 30 golden fixtures plus `BASELINE.md` are again byte-identical and were never regenerated (`FrameOutcome.objects` is deliberately absent from `golden.py`'s explicit dump list, because it describes state the fixtures already pin through `boxes`). A DORMANT identity reaching the wire is the state this platform could not express at all before — an id the book has retired but the gallery still remembers — asserted end-to-end in `tests/grpc/test_object_state_wire.py`.

W1 added a little genuinely new state, all of it written where the fact was already computed and then discarded, and read only by the mirror: `Track.label_tally`/`.label_stability`/`.confidence_smoothed`/`.displacement_x`/`_y`, `Recovery.match_distance`/`.gallery_considered`, `CostAssignment.costs`, and `Prediction.horizon_seconds`. None of it is read by any decision in `track.py`, `assign.py`, `memory.py` or the scheduler — the unchanged fixtures are the evidence. `Key.PREDICTIONS` changed payload from `list[Box]` to `list[Prediction]` for the last of those: the extrapolation interval is knowable only before the fold, because by the time the mirror runs every touched track's `last_seen` has already advanced to now.

## docs/plans/active/CV-ORCHESTRATION-PLAN.md — wave W0

This doc's own defaults were stale until this wave, found by reading `config.py` rather than trusting the doc: the ASSOCIATE associator is `cost`, not `bytetrack` (`config.py:90`), and the ROI rescue ships ON (`config.py:370`) — see the TRACKING-V2 wave C5c entry below for when and why those were set. A reader who trusted the old rows would have mis-predicted both which code path runs and what a frame costs. "Recovery is `cost`-only" was also wrong: ASSOCIATE recovers through `memory.gallery` (whole-gallery `ObjectMemory.match`, registered on the `cost` roster only), but FOLLOW recovers too, through a targeted `ObjectMemory.match_identity` re-anchor inside the follow contributor — gallery resolution is unconditional in every mode, what differs is which recovery question gets asked.

CV-ORCHESTRATION wave **W0 is complete**: the 2 362-line per-frame chain in `session.py` is now `cv_service/orchestration/` — contributors with declared inputs/outputs, a Kahn-ordered orchestrator, a frame budget, one aggregator that is the sole writer of `Track`, a per-frame ledger ring, and an `Inspect` RPC to read it. **Zero behavioural delta**: the 30 golden per-frame fixtures in `tools/trackeval/` and `BASELINE.md` are byte-identical and were never regenerated. Push mode now also reports `DetectionResponse.dropped_frames`.

Three responsibilities did **not** become contributors, and the reason is the same each time — moving them would have changed an outcome, which W0 forbids. Label election runs inside `Track._observe` inside `TrackBook.apply`, so it is surfaced as aggregator evidence instead of being lifted out. ORU re-update is per-track, not per-frame, so `Key.CORRECTIONS` has no registered writer in W0. FOLLOW ships as ONE contributor rather than the plan's `follow.verify`/`follow.predict`/`follow.coast` split, because its five outcomes share the post-fold bookkeeping that now rides on `Proposal.settle`; every `TrackBook.apply` call site did move to the aggregator. `emit.raw` is likewise not a contributor (it would be a second writer of `OBSERVATIONS`); the aggregator's no-proposal branch is that path.

Two real defects surfaced during the move, both caught by the golden fixtures rather than by review: the budget never marked the aggregator eligible (every frame would have emitted zero boxes), and `Proposal` collapsed "no observations" with "do not book" (which would have frozen every scene the moment detections stopped, since `apply([])` is what ages a live track).

## docs/plans/done/TRACKING-V2-PLAN.md — wave C5c

The ASSOCIATE-mode associator default and the ROI-rescue default were set by measurement in this wave. `config.py` has set the associator default to `cost` since this wave: measured, both `cost` and `bytetrack` score IDSW 0, and `cost` is pure stdlib and therefore selectable from capability level L1 (`bytetrack` remains one env var away). The ROI re-detection rescue (`CV_TRACK_ROI_ENABLED`) was flipped ON in this wave on measurement: `small_target` fragmentation dropped 19 → 2 and coverage rose 32 → 78 frames, with no row worse.
