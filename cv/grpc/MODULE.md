# adapter-cv-grpc

gRPC client to the Python CV service:
- `GrpcDetectionPort implements DetectionPort` over the generated `Inference/DetectStream` bidi stub (`proto/vision/v1/cv.proto`). Implements **both** `detect` forms: the 3-arg one takes a `CameraAttitude` and is the only place `FrameRequest.camera_pose` is ever populated (docs/conclusions/CV-RATE-BUDGET.md §5, gap 3); the 2-arg one delegates to it with `null`. Delegates wire encode/decode to `DetectionFrameCodec` and per-stream bidi-call state to `DetectionStreamSession` (see API surface below) — `GrpcDetectionPort` itself is just the `DetectionPort` entry point. This is the **push** transport (JVM sends frames); see `GrpcPulledDetectionPort` below for the **pull** transport (worker pulls frames from mediamtx itself).
- `GrpcPulledDetectionPort implements PulledDetectionPort` (docs/plans/active/MEDIA-SOT-PLAN.md wave M4) over the generated `Inference/DetectPulled` bidi stub — the pull-mode sibling of `GrpcDetectionPort`. There is no frame payload on this wire at all: the worker dials the pulled source (typically a mediamtx RTSP path) itself and decodes/infers on its own schedule; this class only carries declarative control state out (`PullControl`: model/threshold/target-fps/detect-width/tracking/camera-pose, restated on every message) and unsolicited `DetectionResponse`s back. Delegates per-stream bidi-call state to `PulledDetectionSession` (see API surface below and **Pull mode** section) — deliberately **not** a mode flag on `DetectionStreamSession`, since pull responses are unsolicited and there is no sequence→future correlation map to share.
- `GrpcModelRegistryPort implements ModelRegistryPort` over the generated `Training/ListModels`+`Training/PromoteModel` blocking stubs (docs/plans/done/CV-TRAINING-PLAN.md Phase 2 §7) — the ingest/promote half of the offline-train→rsync→promote loop.
- `GrpcTrainingPort implements TrainingPort` over the generated `Training/StartTraining` **server-streaming** blocking stub — drives a (optional, GPU-training-host-only) fine-tune job and relays its progress stream to a caller-supplied `Consumer<TrainingProgress>`. Never wired against the GB4005 inference box (docs/plans/done/CV-TRAINING-PLAN.md's "constraint that shapes everything" — GB4005 leaves `Training/StartTraining` `UNIMPLEMENTED`).
- `GrpcDatasetUploadPort implements DatasetUploadPort` over the generated `Training/UploadDataset` **client-streaming** async stub — ships a YOLO-format dataset straight onto the wire as a streamed zip archive (docs/plans/done/CV-TRAINING-V2-PLAN.md §1/§6), replacing the old platform-side filesystem-zip export step. The archive is framed in `GrpcCvSettings.uploadChunkBytes()`-sized chunks (256 KiB default) and never fully materialized in memory or on disk.
- `GrpcCvSettings` — plain, framework-free settings record (docs/plans/active/LAYERING-REFACTOR-PLAN.md §2.2/§2.3/§5.1, wave E4) that is now the single source for every `vision.cv.*` tunable this module needs: `GrpcDetectionPort`'s response timeout/keepalive/channel-shutdown-timeout/plaintext/detectWidth/jpegQuality/wireFormat, `GrpcDatasetUploadPort`'s upload timeout/chunk size, (docs/plans/active/MEDIA-SOT-PLAN.md wave M4) three pull-specific fields, and (docs/plans/active/CV-RECONNECT-PLAN.md wave R1) three push/channel reconnect-cadence fields — see API surface below.
- `CvChannelSupervisor implements AutoCloseable` (docs/plans/active/CV-RECONNECT-PLAN.md wave R1) — the single owner of "is the shared cv-service channel reachable, and if not, keep trying at a bounded cadence." Watches a `ManagedChannel`'s connectivity state and gates `GrpcDetectionPort#detect` through it — see **Reconnect / gate design** below. `describe()` (docs/plans/active/SYSTEM-STATUS-PLAN.md §4.2, wave S2) is **public** (was package-private) so `CvStatusProvider` can reuse its exact outage sentence rather than reformatting it — see that class's own javadoc for why "never reformatted" matters.
- `CvUnavailableException extends IllegalStateException` (docs/plans/active/CV-RECONNECT-PLAN.md wave R1) — stackless; thrown by `GrpcDetectionPort#detect` while `CvChannelSupervisor`'s gate is closed.
- `CvStatusProvider implements SubsystemStatusPort` (`vision-platform`, docs/plans/active/SYSTEM-STATUS-PLAN.md §4.2, wave S2) — `cv-service`'s health self-report backing `GET /api/system/status`. Constructor takes a `Supplier<CvChannelSupervisor>` rather than the supervisor directly: `vision-app`'s `CvChannelSupervisor` bean is conditional on a narrower expression (`vision.cv.reconnect.enabled` on top of the channel-enabling flags, docs/plans/active/CV-RECONNECT-PLAN.md §3.3) than this provider is wired under, so the supplier can legitimately answer `null` for the one edge case where the channel exists but reconnect supervision was turned off specifically — reported as `Health.UNKNOWN`, not a crash and not a silent "CV is off" (that's the separate, unconditionally-wired `Health.DISABLED` bean in `vision-app`'s `SystemStatusWiring` for when CV is off entirely). `available()` → `Health.OK`; otherwise `Health.DOWN` with `detail = describe()` verbatim and `since = now - outageFor()`.
- `GrpcPulledGeolocationPort implements PulledGeolocationPort` (docs/plans/active/VISUAL-GEO-V2-PLAN.md §3.1, H3) over the generated `Geolocation/LocalizeStream` bidi stub — pull-only, no frame payload on the wire in either direction (D2), the geolocation sibling of `GrpcPulledDetectionPort`. Delegates wire encode/decode to `GeoFixCodec` and per-stream bidi-call state to `GeolocationSession` (see API surface below and **Visual geolocation** section). **The one structural difference from `GrpcPulledDetectionPort`: its `CvChannelSupervisor` is required, not nullable** — a closed gate makes `open()` throw `CvUnavailableException` synchronously, before any session/IO is created, since a geolocation session is long-lived (not per-frame) and a caller (H5's runner) should never have to wait out a round trip to learn cv-service is down.
- `GrpcReferenceIndexPort implements ReferenceIndexPort` (docs/plans/active/VISUAL-GEO-V2-PLAN.md §3.1, D10, H3) over the generated `Geolocation/BuildReferenceIndex` (genuinely bidi streaming), `Geolocation/ListRegions` and `Geolocation/DeleteRegion` RPCs — the region-ingest half of the geolocation client, independent of `GrpcPulledGeolocationPort` (the two never share state). `build()` is non-blocking per the port's own contract: it starts one background virtual thread (`Thread.ofVirtual()`, same one-off idiom `DefaultStreamService`/`UsageTracker`/`DefaultDiscoveryService` already use) that frames and streams the zip archive, and returns a live `SubmissionPublisher<IngestProgress>` immediately. See **Visual geolocation** section below for the `region.json` manifest-content decision and the `IngestProgress.summary()` left-`null` decision.
- `GeoFixCodec` — package-private, static-only, the geolocation sibling of `DetectionFrameCodec`: `Telemetry`/`GeoPrior`/`GeoSessionConfig` → wire `GeoTelemetry`/`GeoPrior`/`GeoControl`, and wire `GeoFix` → kernel `VisualFix`. Owns D6's one and only pitch-sign conversion — see **Visual geolocation** below.
- `GeolocationSession` — package-private, one open `LocalizeStream` bidi call per `StreamId`, the geolocation sibling of `PulledDetectionSession` but structurally simpler: `PulledGeolocationPort` has no `reconfigure` method at all, so `GeoSessionConfig` is captured once as a **final** field (only `telemetry` is a hot field), unlike `PulledDetectionSession`'s two independently-hot fields.
- `NoopGeolocationPort implements PulledGeolocationPort` (D9, `vision.geo.visual.enabled=false` fallback) — `open()` returns a hand-rolled single-item `Flow.Publisher` (`SubmissionPublisher` has no synchronous single-item convenience) delivering exactly one refused `VisualFix` (`position == null`, `refusal` naming "disabled") then completing normally — never `onError`, matching `VisualFix`'s own "a refusal, not an error" contract. `telemetry()`/`close()` are no-ops.
- `GeoUploadSettings` (docs/plans/active/VISUAL-GEO-V2-PLAN.md §3.6) — plain settings record for `GrpcReferenceIndexPort`'s upload: `uploadTimeout` (default 30 min — covers the whole bidi call including cv-service's own encode/index/calibrate compute, not just the transfer) and `uploadChunkBytes` (default 256 KiB, matching `GrpcCvSettings.uploadChunkBytes()`). Deliberately a separate record from `GrpcCvSettings`, not a field added to it — the geolocation feature is independently flag-gated and must never force a dependency between the two features.

**Depends on:** vision-domain, vision-platform (explicit, for `SubsystemStatusPort`/`SubsystemStatus`/`Health` — previously only reached transitively via vision-perception), vision-proto (which brings io.grpc:grpc-{netty-shaded,protobuf,stub}, com.google.protobuf:protobuf-java) · **Used by:** vision-app (`WiringConfiguration#detectionPort`, gated by `vision.cv.enabled` per `docs/plans/done/MVP1-PLAN.md` §C7.4; `GrpcModelRegistryPort`/`GrpcTrainingPort`/`GrpcDatasetUploadPort`/`GrpcPulledDetectionPort` beans are a later vision-app wiring wave — not wired yet, see Status; `CvChannelSupervisor` wiring is docs/plans/active/CV-RECONNECT-PLAN.md wave R2, not built by this wave; `CvStatusProvider` is wired by `vision-app`'s `SystemStatusWiring`, docs/plans/active/SYSTEM-STATUS-PLAN.md §4.2, wave S2, mirroring `CvWiring#cvGrpcChannel`'s own enabling condition and its negation; `GrpcPulledGeolocationPort`/`GrpcReferenceIndexPort`/`NoopGeolocationPort` bean registration + `vision.geo.visual.*` property binding is H5, not built by H3)
**Camera pose** (docs/conclusions/CV-RATE-BUDGET.md §5, gap 3). `DetectionFrameCodec.encode(frame, config, attitude)` stamps `FrameRequest.camera_pose` from a `CameraAttitude`, mapping yaw/pitch/roll/hfov/vfov/timestamp field-for-field. `vfov_degrees` passes `0` straight through when unknown — the wire's own spelling of "derive it from the horizontal FOV and the frame aspect ratio", which is what cv-service's `pose_gmc` does with it. A `null` **or `!known()`** attitude sets **no** `camera_pose` at all rather than a zeroed one: cv-service gates on `hfov_degrees > 0`, so a zeroed pose would be ignored anyway, at the cost of a submessage per frame. The 2-arg `encode` overload stays pose-free, so every pre-existing call site is byte-identical on the wire.

No gated/skippable tests in this module — no docker, no optional native lib, no external prerequisite. `CvChannelSupervisorTest` is real-TCP-loopback throughout (docs/plans/active/CV-RECONNECT-PLAN.md wave R1) — a real `ManagedChannel` to a dead port is what actually exercises `TRANSIENT_FAILURE`/`SHUTDOWN`/reconnect churn; an in-process channel never fails and so can't drive the gate's state machine at all. `GrpcPulledGeolocationPortTest`'s closed-gate test reuses this same real-TCP-loopback-against-a-dead-port technique for one case; every other geolocation/tiles test is in-process (control-plane-sized messages).

## API surface
### `com.drones.vision.adapter.cvgrpc`
- `record GrpcCvSettings(...)` — plain, framework-free settings record (docs/plans/active/LAYERING-REFACTOR-PLAN.md §1.3/§2.2/§2.3, wave E4); the single source for every `vision.cv.*` tunable this module needs. - `enum WireFormat { AUTO, JPEG, BGR24 }` — **public** (docs/plans/active/CV-RATE-CONTROL-PLAN.md wave R3); how a *downscaled* frame reaches cv-service. `WireFormat resolve(String authority)` answers for itself unless `AUTO`, which returns `BGR24` for a loopback authority (`localhost`, `127.*`, `[::1]`, case-insensitive, port stripped) and `JPEG` otherwise; `static WireFormat parse(String)` maps a configured value, blank/`null` → `AUTO`.

  - **Async stub, not blocking — the one class in this module that isn't `newBlockingStub`.** `Training/UploadDataset` is client-streaming; grpc-java's blocking stub only supports unary and server-streaming calls (`GrpcModelRegistryPort`'s two RPCs and `GrpcTrainingPort#startTraining` all use `newBlockingStub`; this class uses `TrainingGrpc.newStub(channel)` instead). A private `UploadAckObserver` (`StreamObserver<UploadAck>`) captures the terminal ack/error and releases a `CountDownLatch(1)` that `upload()` blocks on — the bridge back to `DatasetUploadPort`'s synchronous contract. `UploadAckObserver`'s fields are plain (not `volatile`/atomic): they're written on the gRPC callback thread and read by the caller only after `CountDownLatch.await()` returns, and the JDK guarantees that ordering is itself a safe-publication point (`countDown()` happens-before a successful `await()` return) — no extra synchronization needed.
  - `GrpcCvSettings.uploadTimeout()` (default 300s) — per-call deadline (`AbstractStub#withDeadlineAfter`) covering archive framing *and* the round trip, applied via `stub.withDeadlineAfter(...)` the same way `GrpcModelRegistryPort.CALL_TIMEOUT_SECONDS` bounds its calls. Unlike `GrpcTrainingPort#startTraining` (deliberately undeadlined — a training job's length is unbounded), an upload is genuinely bounded work, so a fixed deadline is safe. Because the deadline guarantees the response observer eventually sees a terminal signal one way or another, `UploadAckObserver.awaitAck()`'s `CountDownLatch.await()` call is itself unbounded — a second, redundant timeout was deliberately not layered on top.
  - **Framing — the archive is never fully materialized in memory or on disk.** `upload()` opens a `java.util.zip.ZipOutputStream` directly over a private `ChunkingOutputStream` (extends `OutputStream`) that buffers writes into a `GrpcCvSettings.uploadChunkBytes()`-sized (262,144 = 256 KiB default) array and emits one `DatasetChunk{dataset_id, content}` via the request observer's `onNext` every time the buffer fills, plus a final (possibly smaller) chunk when the zip is closed (`ZipOutputStream.close()` → `finish()` then `out.close()`, which is `ChunkingOutputStream.close()` → its own `flush()`). Only this one rolling buffer ever exists — the whole archive is never held in memory or written to disk, matching docs/plans/done/CV-TRAINING-V2-PLAN.md §D's design decision (small chunks over an existing channel, no message-size tuning needed). Zip entries, written in this exact order: `data.yaml` (the caller's `dataYaml` string, UTF-8), then per `ExportEntry` in list order, `images/<imageName>` (raw bytes) then `labels/<stem>.txt` — `<stem>` is `imageName` with everything from its last `'.'` onward stripped (no `'.'` ⇒ the whole name), matching **byte-for-byte** the naming logic `FilesystemDatasetExport#labelName` used (adapter-persistence — read directly, not depended on, since adapters must never depend on each other; that class and its zip-export step are slated for deletion in a later wave per docs/plans/done/CV-TRAINING-V2-PLAN.md's delete list, at which point this module becomes the sole owner of that naming convention).
  - **Failure semantics**:
    - **`UploadAck.ok=false`** (cv-service reachable but refused — corrupt archive, unsafe entry, size-cap breach): throws `IllegalStateException("cv-service rejected the dataset upload: " + message)` — same "reachable but refused" convention `GrpcModelRegistryPort#promote` uses for `Ack.ok=false`.
    - **Transport failure or deadline exceeded**: the raw `StatusRuntimeException` captured off the response observer's `onError` propagates to the caller **unwrapped** — never re-wrapped, matching every other RPC in this module.
    - **Stream closed with no ack at all** (a defensive case that shouldn't happen given the generated client-streaming contract, but guarded anyway): `IllegalStateException` naming the dataset id.
    - **This thread interrupted while awaiting the ack**: `IllegalStateException` with the `InterruptedException` as cause; the thread's interrupt flag is restored first.
    - Both the `ok=false` and transport-failure shapes are exactly what `DefaultTrainingJobService#recordFailure` (vision-application) turns into an honest `FAILED` training-job message.
  - **No client-side caching or de-duplication**: every `upload()` call is an independent RPC; re-uploading the same dataset id is the *server's* own idempotent replace (docs/plans/done/CV-TRAINING-V2-PLAN.md §2), not something this client tracks or short-circuits — verified by `GrpcDatasetUploadPortTest#uploadIsNotCachedOrDeduplicatedOnTheClient` (two `upload()` calls, same args, against a fake that counts invocations — asserts exactly two RPCs).
  - **Production-robustness note, not fixed here**: if writing the zip throws a *`RuntimeException`* (not `IOException`) — e.g. the request observer's `onNext` throwing because the server already tore the call down mid-upload — that exception propagates straight out of `upload()` uncaught, bypassing `UploadAckObserver.awaitAck()` entirely. In that specific race the caller sees this secondary symptom instead of the real terminal `StatusRuntimeException` the response observer's `onError` would otherwise have captured. Not exercised by any test here (none of the four required scenarios provoke it — the fake servicer only ever errors *after* the client finishes writing and calls `onCompleted()`); flagged as the same class of "known minor gap" `GrpcTrainingPort`'s javadoc documents for `onProgress.accept()` throwing.

### `ModelInfo` &rarr; `ModelRef` mapping and the `stage`/`metrics` gap
`ModelRef` (vision-domain, frozen — this task could not and did not modify it) is `(id, version)` only; it has no field for the wire `ModelInfo`'s `stage` (`"production"` vs. `"available"`) or `metrics` map. `models()` therefore necessarily **drops `stage`/`metrics`** on every mapped entry — this is not an oversight, it is the frozen domain type's shape. docs/plans/done/CV-TRAINING-PLAN.md §8's planned `GET /api/cv/registry/models` REST endpoint is explicitly documented there as needing `ModelRegistryPort.models() + stage/metrics` — i.e. that later REST wave already expects to need more than this port alone provides (e.g. a parallel raw-`ModelInfo` read path, or a domain change), and closing that gap is out of this adapter's scope.

## Failure semantics — `GrpcModelRegistryPort`
Both RPCs are blocking calls; neither swallows a transport problem into a misleadingly-empty/quiet result:
- **Transport failure or deadline exceeded** (cv-service unreachable, restarting, or hung): the raw `StatusRuntimeException` propagates to the caller of `models()`/`promote()` — same failure *shape* as `GrpcDetectionPort#detect`'s transport-failure path (an unwrapped `StatusRuntimeException`, not a custom exception type). **Deliberately not degraded to an empty list**: a caller cannot otherwise distinguish "cv-service has no models registered" from "couldn't reach cv-service at all," and silently returning empty on the latter would make a genuine outage look like a legitimately-empty registry. `models()` returns an empty list only when cv-service actually answers with a `ModelList` containing zero entries.
- **`promote()` explicitly refused** (`Ack.ok=false`): throws `IllegalStateException` with a message naming the ref and cv-service's own refusal text (`Ack.message`) — the same "reachable but answered no" convention `FlightCommandPort`'s MAVLink implementations use for a vehicle explicitly refusing a command (`MavlinkFlightCommander`, see adapter-mavlink), applied here at the port-contract level since `ModelRegistryPort`'s javadoc does not itself specify an exception for this case.
- **Malformed `ModelInfo`** (blank `id`/`version` from cv-service): `ModelRef`'s own compact constructor throws `IllegalArgumentException`, which fails the *entire* `models()` call (not just that one entry) — a malformed roster response is treated as a cv-service bug worth surfacing loudly, not a per-entry failure to silently skip (unlike `GrpcDetectionPort`'s per-response malformed-detection handling, which *does* fail just one future — the two cases differ because `models()` returns one list from one call, there is no per-entry future to fail independently).

## Failure semantics — `GrpcTrainingPort`
`startTraining` is one blocking call that consumes a whole streaming RPC, so its failure shape is different from either sibling class above:
- **Transport failure, at any point in the stream** (the training host process dying, the connection breaking, or the calling thread being interrupted — see **Cancellation** in API surface above): the raw `StatusRuntimeException` propagates out of `startTraining`, after every message that had already arrived was already delivered to `onProgress` — never swallowed into a quiet early return.
- **The server ends the stream with no terminal `SUCCEEDED`/`FAILED` message**: not an error. `hasNext()` simply returns `false`, `startTraining` returns normally, and every `RUNNING` message seen so far has already reached `onProgress`. This is cv-service's own documented cancellation behavior (see `docs/plans/done/CV-TRAINING-PLAN.md` Phase 2's frozen contract) and exactly matches `TrainingPort`'s own javadoc ("cancellation ends the stream with no terminal message ... `onProgress` simply stops being called and `startTraining` returns") — no synthetic terminal `TrainingProgress` is invented to paper over the gap.
- **Malformed `TrainingProgress`** (e.g. blank `job_id`): the domain record's compact constructor throws `IllegalArgumentException`, propagating out of `startTraining` uncaught — same "surface the cv-service bug loudly" posture `GrpcModelRegistryPort` takes for a malformed `ModelInfo`, not a per-message skip.
- **`onProgress` itself throwing**: propagates out of `startTraining` too, but see API surface above's "Known minor gap" — the underlying call is not proactively cancelled in this case (only interruption is).

## Correlation design
`DetectStream` is bidirectional streaming, so there is one open call per `StreamId`, not per frame:
- A private `DetectionStreamSession` (one per `StreamId`, held in a `ConcurrentHashMap<StreamId, DetectionStreamSession>`) owns the request `StreamObserver<FrameRequest>`, lazily opened on the first `detect()` for that stream.
- Each frame is sent as one `FrameRequest`, keyed in a `ConcurrentHashMap<Long, CompletableFuture<DetectionResult>>` by `sequence` (`VideoFrame.sequence()`, per-stream-monotonic). The matching `DetectionResponse` (matched back by its own `sequence` field) completes that specific future — proven under out-of-order server replies (`detectCorrelatesInterleavedResponsesBySequence`).
- **The mapped `DetectionResult.streamId()` is the session's own (domain) `StreamId`, not a re-parse of the response's wire `stream_id` string.** Correlation never depends on the server echoing that field correctly, and this avoids a `StreamId.of(...)` parse failure on a malformed echo turning into a crash instead of a clean per-frame failure.
- gRPC stream observers are not thread-safe: every write to a session's request observer (including the lazy open) is serialized through that session's own monitor (`synchronized` block). Concurrent `detect()` calls for the *same* stream from multiple threads are safe (`concurrentDetectCallsForSameStreamCompleteWithoutCorruption`); different streams never contend on the same lock.
- **`DetectionStreamSession.send(long sequence, FrameRequest request)` takes an already-built `FrameRequest`**, not a `VideoFrame`/`PipelineConfig` pair — `detect()` builds the wire request first (`DetectionFrameCodec#encode`, see **Payload shrinking** below) and only then does `sessions.computeIfAbsent(...)`/`session.send(...)`. This is deliberate: it keeps request *construction* (which can fail per-frame, e.g. a bad downscale) entirely decoupled from session *lifecycle* — a conversion failure never creates or touches a `DetectionStreamSession`.

## Payload shrinking for large `BGR24` frames (CP-b, `docs/main/CYCLES-PLAN.md` §CP-b)
The RTSP/file RX path produces full-resolution raw `BGR24` frames (e.g. 1280×720 ≈ 2.7 MB uncompressed) — too large to push over gRPC at a useful detection rate. This logic lives in `DetectionFrameCodec#encode` (docs/plans/active/LAYERING-REFACTOR-PLAN.md §5.1: split out of `GrpcDetectionPort` into its own ~195-line pure encode/decode class); `GrpcDetectionPort.detect()` calls it before touching the session machinery:
- A `BGR24` frame **wider than the codec's `detectWidth`** (constructed from `GrpcCvSettings.detectWidth()`, default `GrpcCvSettings.MAX_DETECT_WIDTH=640`px — an adapter-internal wire-payload tuning knob, not a `PipelineConfig` field; independent of `cv-service`'s own `CV_IMGSZ` inference size, see `cv/cv-service/MODULE.md`) is downscaled to exactly `detectWidth` wide (aspect preserved, `Math.round`-ed height) via Java2D bilinear `drawImage`, then JPEG-encoded (`ImageIO`, explicit `ImageWriter`, quality = `GrpcCvSettings.jpegQuality()`, default `GrpcCvSettings.JPEG_QUALITY=0.8f`) and sent as `IMAGE_ENCODING_JPEG` with the *scaled* width/height. **Constructor-configurable via `GrpcCvSettings`** (docs/plans/done/REMOTE-CV-PLAN.md P1 item 5; docs/plans/active/LAYERING-REFACTOR-PLAN.md wave E4 moved the constants and validation there) so per-network tuning (e.g. 480px over a slow VPN link) needs no rebuild — see API surface above; a later vision-app wiring wave threads `vision.cv.detect-width`/`vision.cv.jpeg-quality` through.
- `DetectionFrameCodec.wrapBgr24(width, height, ByteBuffer)` turns the source bytes into a `BufferedImage` by allocating a fresh `TYPE_3BYTE_BGR` image and bulk-copying into its backing `DataBufferByte` array (`data.get(pixels)`) — the same idiom `adapter-overlay`'s `Java2DOverlayRenderer.renderBgr24` already uses, chosen over hand-building a `Raster`/`ComponentColorModel` (tried first, worked, but was strictly more code for the same result: `TYPE_3BYTE_BGR`'s own band layout is already byte0=B/byte1=G/byte2=R, i.e. exactly `PixelFormat.BGR24`'s packed-no-padding layout, so no per-pixel reordering is ever needed either way).
- `JPEG` frames and `BGR24` frames already `≤640`px wide (the default `detectWidth`) pass through byte-identical, exactly as before this existed (only `>`, not `≥`, triggers the downscale — a frame exactly `detectWidth`px wide is untouched).
- **What the downscaled frame is encoded AS is now a choice** (docs/plans/active/CV-RATE-CONTROL-PLAN.md wave R3): `WireFormat.BGR24` skips the JPEG encode here **and** the matching decode inside cv-service, which together were the bulk of the ~25 ms of *non-inference* round trip measured on loopback (docs/conclusions/CV-RATE-BUDGET.md §3 — 53.8 ms of round trip contained only 29 ms of inference). The wire has carried `IMAGE_ENCODING_BGR24` since the first version of the contract and `cv-service`'s `inference/detector.py` has always decoded it; only this side re-encoded unconditionally, because the downscale path was written when every deployment was remote. `TYPE_3BYTE_BGR`'s backing array is already packed BGR with no row padding — the layout the wire declares — so the raw branch is a handover, not a conversion. Payload: `3 × detectWidth × scaledHeight` (≈691 KB at 640×360) against ≈40 KB of JPEG. The shipped `AUTO` picks raw for loopback and JPEG otherwise; `vision.cv.wire-format` overrides.
- **No coordinate mapping back to the original resolution is needed or performed.** Detection boxes come back normalized to `[0,1]` and `DetectionResult` never references the source frame's pixel dimensions — the sequence-keyed correlation `DetectionStreamSession` already does is entirely oblivious to whether a given frame was sent raw or downscaled.
- **Runs synchronously on the calling thread**, inside `detect()`, before the request/session machinery is touched — deliberately not offloaded to an executor. It's CPU-bound (no I/O), bounded at roughly 15ms for a 720p frame, and it *replaces* serializing/transmitting several MB of raw pixel data with encoding and sending a couple hundred KB — net caller-thread cost versus the pre-existing fast path is roughly flat, not new added latency, so `GrpcDetectionPort`'s class javadoc "never blocks" framing still holds in practice even though this one step is technically synchronous CPU work.
- A conversion failure (the encoder throwing, or `wrapBgr24`'s bulk `ByteBuffer.get(byte[])` throwing `BufferUnderflowException` on malformed/too-short source data) is caught in `detect()` and fails only that one frame's returned stage — **no `DetectionStreamSession` is created or touched**, so an already-open session for that stream (if any) is completely unaffected and the very next `detect()` call for the same `StreamId` proceeds normally (verified: `detectConversionFailureFailsOnlyThatFrameAndSubsequentGoodFrameOnSameStreamSucceeds`).

## Tracking (docs/plans/done/TRACKING-PLAN.md §4.A/§4.B wave T4, docs/extracts/TRACKING-ORCHESTRATION.md §5.1/§5.2/§6; capability ladder + ORU added docs/plans/active/TRACKING-V3-BAND1-CONTEXT.md §2, wave J2)
`DetectionFrameCodec` is where the tracking engine's frozen wire contract meets the domain — no policy, pure field mapping, both directions.

**`encode`/`toWireTrackingConfig`: `PipelineConfig.tracking()` → `FrameRequest.tracking` (and, reused verbatim, `PullControl.tracking` — see **Pull mode** below).** Every outbound request carries a wire `TrackingConfig`, unconditionally — mode `OFF` included. This adapter always states what it wants; cv-service decides when to spend the detector (docs/plans/done/TRACKING-PLAN.md §3). The proto's "absent `tracking` ⇒ `TRACKING_MODE_OFF`" additivity affordance exists for a client built before this wave, not this one. Field-by-field:
- `mode`/`engineId`/`verifyEveryMillis`/`maxAgeFrames`/`minHits` map 1:1.
- `redetectIouPercent` (domain `int`, `[0,100]`) → `redetect_iou_threshold` (wire `float` ratio) via `/ 100f` — the one unit conversion in this mapping.
- `followFps` has **no wire field at all** and is never sent — it is the Java-side sampler's own rate (TRACKING-ORCHESTRATION.md §4.3: "cv-service must never care how often it is fed"), not a cv-service knob. Do not add one.
- `capabilityLevel` → `capability_level`, `reupdateMaxGapMillis` → `reupdate_max_gap_millis` (wave J2) map 1:1, both `int`s already in the wire's own units — no conversion. Both default to `0` on `TrackingConfig.off()`/`.defaults()`, the proto zero-value, so a deployment that configures neither sends a byte-identical request to before this wave (invariant B2, verified: `capabilityLevelAndReupdateMaxGapDefaultToZeroWhenUnconfigured`). `capabilityLevel` is a **ceiling, not a demand** (E12) — this adapter has no opinion on what cv-service does with it, it only carries the number.
- `lock` (nullable `TargetLock`): present → maps to a wire `TargetLock` (`lockSeq`/`trackId`/`pointX`+`pointY`/`release`, whichever one of the three forms the domain record's own validation guarantees is set); absent (`null`) → the wire `TrackingConfig.lock` field is left **unset** (`hasLock() == false`), not a zero-valued present one — "no lock held" has exactly one wire spelling. The wire `TargetLock.box` field is never set by this adapter: the domain `TargetLock` has no box component (docs/plans/done/TRACKING-PLAN.md §4.D — the PATCH surface accepts only `trackId`/point/`release`), so the wire's optional explicit-box override is a cv-service-only affordance this adapter has nothing to populate it from.

**`decode`: two independent mappings, per docs/extracts/TRACKING-ORCHESTRATION.md's own split between per-detection and per-frame facts.**
1. **Per detection** (wire `Detection` fields 4-9, plus `reupdated` field 14 since wave J2) → `Detection.track()` (nullable `TrackRef`). `track_id == 0` — the wire's untracked sentinel — always short-circuits to `track() == null`, checked *before* looking at any other track field, so a malformed response with `track_id == 0` but a populated `track_state`/`source`/velocity still decodes untracked rather than a guessed `TrackRef(0, …)` (verified: `trackIdZeroDecodesToUntrackedDetectionRegardlessOfOtherTrackFields`). An `UNSPECIFIED`/`UNRECOGNIZED` wire `TrackState` or `DetectionSource` on an otherwise-tracked detection (`track_id != 0`) also decodes to `track() == null` — never a guessed state/source — mirroring this module's existing `JOB_STATE_UNSPECIFIED → RUNNING` "never guess terminal" posture (`GrpcTrainingPort`), except here the defensive fallback is "no fact" rather than "a specific guessed fact", because unlike a job's terminal state there is no safe default track state to guess. `reupdated` maps straight through to `TrackRef.reupdated()` — this track's gap was reconstructed by ORU on this frame; it carries no validation of its own and is simply unreachable whenever `track_id == 0` short-circuits first.
2. **Per frame** (wire `DetectionResponse` fields 8-12: `tracker_millis`/`detector_ran`/`tracker_engine_id`/`locked_track_id`/`detector_reason`; plus fields 22-26 since wave J2: `reupdate_millis`/`reupdated_tracks`/`detection_lag_millis`/`capability_level_served`/`capability_level_reason`) → `DetectionResult.tracking()` (nullable `TrackingTelemetry`) — **the headline requirement of T4** (TRACKING-ORCHESTRATION.md §5.2: "T4 must map it or the field is decoded and dropped"), extended by J2 to close the identical gap for the five V3 fields. Returns `null` — tracking off for this result, byte-identical to this class's pre-tracking behavior — only when **all ten** fields are simultaneously at their proto zero-value (the original five, plus `reupdate_millis=0`, `reupdated_tracks=0`, `detection_lag_millis=0`, `capability_level_served=0`, `capability_level_reason=""`). This is the shape an old, pre-V3 (or pre-tracking) cv-service's response has, and is indistinguishable at the wire level from a hypothetical modern server explicitly reporting all-default values — but the latter never legitimately happens: a T1-built cv-service reports `detector_ran`/`detector_reason` on **every** response regardless of mode (even `OFF` runs the detector every frame, reason `ALWAYS`), so "all ten zero" only actually occurs against a server that predates tracking (or V3) entirely. Verified against both an empty-detections and a one-detection response (`responseWithNoTrackFieldsAtAllDecodesByteIdenticalToPreTrackingBehavior`, `responseWithNoDetectionsAndNoTrackFieldsDecodesTrackingNull`), and again with every V3 field explicitly (not just implicitly) zeroed (`allZeroResponseIncludingV3FieldsStillDecodesTrackingNull`, invariant B3).
   - **`capability_level_served == 0` is not a level served, it is "this server never reported one."** `TrackingCapability` validates `levelServed` in `[1,5]`, so `toTrackingTelemetry` special-cases `capabilityLevelServed == 0` → `TrackingTelemetry.capability() == null` rather than constructing a `TrackingCapability` that would throw out of `decode()` on a perfectly ordinary pre-V3 (or V3-but-nothing-reported-yet) response. A non-zero level with an empty `capability_level_reason` is normal and means "served exactly as requested" — only a non-empty reason signals a downgrade happened (invariant B5, verified: `servedLevelBelowWhateverWasRequestedSurvivesDecodeIntact`, `capabilityLevelServedZeroDecodesCapabilityNullEvenWhileTrackingIsActive`).

**`detector_reason` is meaningful only when `detector_ran` is true** (docs/plans/done/TRACKING-PLAN.md §4.G): when `detector_ran` is false the wire `detector_reason` is ignored entirely and the domain `reason` is always `null` (a tracker-only `FOLLOW` frame's `detector_reason` is legitimately `UNSPECIFIED` on the wire — not an error, just meaningless — so this adapter does not even look at it in that case). When `detector_ran` is true, an `UNSPECIFIED`/`UNRECOGNIZED` wire `detector_reason` is a genuine contract violation (a server claiming a pass ran but giving no reason) and is **not** guessed as `ALWAYS` or any other value — `toDetectorReason` maps it to `null`, and `TrackingTelemetry`'s own compact constructor then rejects `detectorRan=true, reason=null`, so the malformed response fails to decode at all (caught per-response by `DetectionStreamSession#onResponse`, exactly like any other malformed field — see **Failure semantics** below).

**Malformed track fields fail only that one frame's future — no special-casing needed.** Both `TrackRef`'s and `TrackingTelemetry`'s own compact-constructor validation (a non-finite velocity, `detectorRan=true` with a null `reason`, etc.) throws `IllegalArgumentException` straight out of `decode()`, which `DetectionStreamSession#onResponse` already catches per-response — this wave added no new failure-handling code, it rides the mechanism `decode()` already had for a malformed confidence/box value. Verified both as a pure decode-level assertion (`DetectionFrameCodecTest#malformed*`) and end-to-end through a real session, proving the session itself survives and serves the next frame normally (`GrpcDetectionPortTest#malformedTrackFieldFailsOnlyThatFrameAndSubsequentGoodFrameOnSameStreamSucceeds`).

**§5.D measurement — FOLLOW-at-15fps in-flight behavior against `maxInFlightInferences=2`: not measurable at this layer, deferred to T8's vision-app E2E, as the plan's own escape hatch allows.** `cv/grpc` has **no `maxInFlightInferences` concept anywhere in its source** — grep confirms zero references. `GrpcDetectionPort#detect`/`DetectionStreamSession#send` never block, never queue, and never cap how many `CompletableFuture`s are pending at once for a stream; the existing `concurrentDetectCallsForSameStreamCompleteWithoutCorruption` test already drives 50 concurrent in-flight `detect()` calls through one session without incident, far past the bound the plan asks about. The actual bound — "at most 2 concurrent `DetectionPort` calls in flight, skip sampled frames past it" — is enforced entirely by `StreamPipeline` in `vision-application` (docs/plans/done/TRACKING-PLAN.md §5.D itself says so: "`StreamPipeline` already recomputes `sampleEveryNthFrame`..."), a different module, out of this task's file scope. This adapter has nothing to measure; the number belongs to T8's real end-to-end test against a live `StreamPipeline` driving real `FOLLOW`-mode traffic.

## Failure semantics
- **Transport failure** (`onError` from the server — e.g. the CV service process restarting): every still-pending future for that stream fails immediately with the transport exception (`StatusRuntimeException`), and the `DetectionStreamSession` entry is dropped from the map. The next `detect()` for that `StreamId` transparently opens a fresh call — no explicit reconnect step needed by the caller. This is the recovery mechanism a caller's retry/backoff (`docs/plans/done/MVP1-PLAN.md` §C7.3 / `StreamPipeline`'s outage-probe policy, see contexts/vision-perception/MODULE.md §StreamPipeline) depends on.
- **Server ends the stream normally** (`onCompleted` with no error): treated the same as a transport failure — pending futures fail with `IllegalStateException`, session dropped — because a live bidi call is never expected to complete server-side on its own.
- **Hung or unreachable service, and — critically — a session opened while the CV service is down entirely** (no error, just silence): a bidi call has no natural per-call deadline, so every pending future instead gets its own `GrpcCvSettings.responseTimeout()`=2s-default timeout via `CompletableFuture.orTimeout` (a `GrpcCvSettings` field, not yet exposed as a `vision.cv.response-timeout` Spring property — that's a later `vision-app` wiring wave, docs/plans/active/LAYERING-REFACTOR-PLAN.md F4). **The timeout is now terminal for the whole session, exactly like a transport error**: the first pending future to time out cancels the underlying call (`ClientCallStreamObserver.cancel`), fails every other still-pending future for that stream immediately (they don't wait out their own individual timers), and drops the `DetectionStreamSession` from the map — so the next `detect()` for that `StreamId` opens a fresh call instead of resending onto a call that may never produce a transport signal at all. **This was a real, verified bug before this fix**: a session opened while cv-service was down could sit half-open forever — no `onError`, no `onCompleted`, ever — because relying solely on transport `onError` assumed the transport always eventually reports failure, which is not guaranteed (see Gotchas below for the concrete mechanism that made this reproducible). A response arriving after a future's own timeout (or after the session was already torn down) is silently ignored (its sequence is no longer in the pending map).
  - **Recovery contract with `StreamPipeline`:** the pipeline's outage/backoff (contexts/vision-perception/MODULE.md §StreamPipeline) probes at most every `INITIAL_BACKOFF_NANOS`=1s, doubling to `MAX_BACKOFF_NANOS`=10s, and treats every `DetectionPort#detect` failure — including a timeout — as "this probe failed, try again later." This adapter's contract with that policy is: **every probe after a torn-down session gets a fresh call**, so once the CV service is actually reachable again, the very next probe (not some later one) succeeds — the pipeline never needs to know a session ever existed, and never needs its own reconnect logic.
  - **Teardown is idempotent per session** (a package-private `AtomicBoolean torndown` per `DetectionStreamSession`, guarding a single `failAllAndDrop`/`endAndClose` path): a timeout and a transport error (or `streamEnded`/`close()`) racing each other — e.g. the server's `onError` and a pending future's own timeout landing on different executor threads at nearly the same instant — resolve to exactly one teardown; whichever trigger wins does the real work (drop from `sessions`, fail every pending future once), every other trigger for the same session is a no-op. Verified under a genuine race in `timeoutRacingTransportErrorTearsDownSessionOnceAndFailsPendingSiblingsFast` (a server thread firing `onError` at ~`RESPONSE_TIMEOUT_SECONDS` while the client's own timeout fires independently).
  - **Design choice: plain fail-fast RPCs (no `withWaitForReady()`) plus fresh-call-per-probe-after-teardown**, not a wait-for-ready call kept alive across the outage. Once the session is unconditionally torn down on any terminal signal (transport error *or* timeout), a wait-for-ready call would add complexity (an RPC that itself never fails, so *only* our own timeout would ever end it — no different in the end, since we already treat every timeout as terminal) without a corresponding benefit; plain fail-fast keeps the two failure paths (`onError`, timeout) symmetric and lets the channel's own connectivity management do the reconnect work, which is all `StreamPipeline`'s probe cadence needs. See Gotchas for a now-fixed dependency version skew that used to prevent the channel itself from ever recognizing a failed connection attempt, independent of anything in this class.
- **Unsupported `PixelFormat`** (only `JPEG`→`IMAGE_ENCODING_JPEG` and `BGR24`→`IMAGE_ENCODING_BGR24` are mapped; `RGB24`/`YUV420P`/`H264_PACKET`/`UNKNOWN` are not): fails fast with `IllegalArgumentException` — no session is opened/touched, no gRPC call is made at all.
- **Malformed response** (e.g. a confidence/box value outside the domain's validated range, causing the `DetectionResult`/`Detection`/`BoundingBox` record constructors to throw — **including, since docs/plans/done/TRACKING-PLAN.md T4, a malformed track field**: a non-finite velocity failing `TrackRef`'s compact ctor, or `detector_ran=true` with an `UNSPECIFIED` `detector_reason` failing `TrackingTelemetry`'s — see **Tracking** above): caught per-response and fails just that one future — never crashes the stream or affects other pending futures on the same session.
- **Port already closed**: `detect()` returns an already-failed stage (`IllegalStateException`) without touching any session.

## Stream lifecycle
Chose the **explicit hook** over idle eviction: `streamEnded(StreamId)` fails any still-pending futures for that stream with a `CancellationException`, half-closes the request observer (`onCompleted()`, best-effort), and drops the session. It is optional — an ended stream that's never told so just keeps its call open until `close()`; the next `detect()` for that id would simply keep reusing it. **A future wiring/resilience task should call `streamEnded` when a `StreamPipeline` stops**, so the CV-side call doesn't linger; this class does not (and cannot, from here) know when a stream ends on its own. `streamEnded`/`close()` share the same per-session `torndown` CAS guard as the timeout/transport-error paths (see Failure semantics), so a `streamEnded` racing a concurrent timeout or transport error is also exactly-once — not just idempotent across repeated *external* calls as before, but idempotent against *every* internal trigger too.

Note: `CompletableFuture.get()` reports a future completed via `completeExceptionally(new CancellationException(...))` by throwing that `CancellationException` **directly**, not wrapped in `ExecutionException` (a JDK special case for cancellation-shaped completions) — callers using `.get()`/`.join()` on a `streamEnded`-cancelled future should catch `CancellationException`, not `ExecutionException`.

## Reconnect / gate design (`CvChannelSupervisor`, docs/plans/active/CV-RECONNECT-PLAN.md wave R1)

**The problem this closes**: a fail-fast gRPC RPC issued while the channel is `TRANSIENT_FAILURE` returns the cached failure immediately — it does not itself trigger a new connect attempt. Left alone, only the channel's own reconnect backoff (which escalates towards ~120s) ever retries, so once cv-service goes down, recovery latency after it comes back is unbounded and depends on where in that escalation the restart happened to land; meanwhile every `detect()` in between pays a full encode + session lookup only to fail on a connection everyone already knows is dead. `CvChannelSupervisor` is the fix: one instance per shared `ManagedChannel`, watching connectivity and forcing a *bounded* retry cadence, that `GrpcDetectionPort#detect` consults before doing any work at all.

**State machine — the gate is sticky-closed until `READY`, never `CONNECTING`:**
```
OPEN   --TRANSIENT_FAILURE-->                    CLOSED
CLOSED --CONNECTING / IDLE (reconnect churn)-->   CLOSED
CLOSED --READY-->                                 OPEN
OPEN   --SHUTDOWN-->                              CLOSED (terminal)
CLOSED --SHUTDOWN-->                              CLOSED (terminal)
```
`available()` is deliberately **not** `state() == READY` — it is this separate sticky flag. Every reconnect attempt cycles `TRANSIENT_FAILURE -> CONNECTING -> TRANSIENT_FAILURE`; a gate that reopened on `CONNECTING` would let one probe through per cycle and reproduce the exact log-flood/wasted-encode problem this class exists to fix, just at a slower rate. The gate starts, and stays, **open** until the first `TRANSIENT_FAILURE` is ever observed — so `IDLE`/`CONNECTING` during cold start (before cv-service has ever been reached even once) never blocks a probe; only an *observed regression* closes it. `notifyWhenStateChanged`'s one-shot callback is re-armed on every invocation (`onStateChange`), and an `IDLE` transition is deliberately turned back into a connect request (`channel.getState(true)`) so the supervisor keeps watching — and keeps forcing reconnects — even with no `detect()` call currently in flight to revive the channel on its own. `SHUTDOWN` is terminal: a shut-down channel never transitions back to `READY`, so the gate stays closed for the rest of this supervisor's life once it observes one, and — unlike a `TRANSIENT_FAILURE` outage — no reconnect loop is scheduled for it (`onShutdown` bumps `generation` and cancels the heartbeat instead, orphaning whatever chain was already running rather than starting a new one; forcing `resetConnectBackoff()` against a permanently dead channel on a timer would be pure waste). This closes a real gap found in review: the first cut of `onStateChange`'s `SHUTDOWN` case returned without touching `available` at all, so a channel shut down while the gate was open left `available()` `true` forever — `CvWiring` declares the detection port bean with `destroyMethod = ""`, so `GrpcDetectionPort#close()` is never invoked by Spring and only the channel bean's own destruction actually shuts the channel down, meaning this path is reachable in production, not just in theory.

**`start()` applies the transition logic to the channel's already-current state, not only to future ones.** The gate's `READY`/`TRANSIENT_FAILURE`/`SHUTDOWN` handling lives in one private `applyTransition` method shared by `start()` and `onStateChange()`. `start()` calls `channel.getState(true)`, runs that initial state through `applyTransition` immediately, and only then arms `notifyWhenStateChanged` — because that callback only fires on a change *away from* the state it is armed with, so a supervisor started against a channel that is already `TRANSIENT_FAILURE` (or already `SHUTDOWN`) would otherwise leave the gate open until some later transition happened, which may be a long time or never. Today's `vision-app` wiring always builds the supervisor next to a fresh `IDLE` channel so this specific ordering hasn't bitten in production, but this class is wired as a Spring bean whose construction order relative to the channel bean is not something it should have to depend on — regression-tested by `startClosesGateImmediatelyAgainstAnAlreadyFailingChannel`, which drives a raw channel into `TRANSIENT_FAILURE` before a supervisor ever sees it and asserts the gate is closed synchronously, with no wait for a transition.

**Bounded recovery arithmetic**: while closed, the gate calls `ManagedChannel#resetConnectBackoff()` on its own schedule — wait `reconnectInitialBackoff` (1s default), force a reconnect attempt, double the wait (capped at `reconnectMaxBackoff`, 10s default), repeat. Worst case from cv-service restarting to the gate reopening is therefore bounded by `reconnectMaxBackoff` itself (10s), not by gRPC's own unbounded-in-practice escalation. A caller's own probe backoff on top of that (`StreamPipeline`'s, capped at `MAX_BACKOFF_NANOS`=10s — contexts/vision-perception/MODULE.md §StreamPipeline) then needs at most one more cycle to notice the gate reopened, for an **~20s bounded worst case** end to end.

**Generation-counter staleness guard.** The forced-reconnect chain and the outage heartbeat are both self-rescheduling `ScheduledExecutorService` tasks; each closure captures the `generation` value live when it was scheduled and re-checks it (against the supervisor's current `generation`, an `AtomicLong`) before doing any work and before scheduling its own successor. Both `onReady` (the gate reopening) and `onShutdown` (the channel dying instead) bump `generation`, since either one ends whatever outage a live chain was scheduled for — orphaning that chain rather than needing to cancel it. This avoids two things a naive implementation would otherwise need: a shared mutable `currentBackoff` field visible across threads (backoff is threaded through the recursive task's own parameter instead), and reliance on `ScheduledFuture#cancel()` winning a race against a task that is already dequeued and running (it can't guarantee that on its own) — a stale task's generation check simply fails and it quietly does nothing, no lock, no coordination with whoever is running it.

**Logging**: WARNING once on entering an outage (`onTransientFailure`), INFO once on recovery naming the outage duration and attempt count (`onReady`), INFO heartbeat every `outageLogInterval` (60s default) while the outage continues, each heartbeat itself generation-guarded so a heartbeat tick that fires just after recovery is silently skipped rather than logging a stale "still unreachable".

**How the three pieces fit together**: `CvChannelSupervisor` owns the read model (`available()`/`state()`/`outageFor()`/`reconnectAttempts()`) and the reconnect loop; `GrpcDetectionPort#detect` (three-arg constructor only — see API surface) checks `supervisor.available()` **before** `DetectionFrameCodec#encode` and before touching the `sessions` map, so a known outage costs neither a downscale/JPEG-encode nor a new gRPC call; a closed gate fails the returned stage with `CvUnavailableException`, built from `supervisor.describe()` — the same string named above (authority, live `state()`, `outageFor()`, `reconnectAttempts()`) — so `StreamPipeline#describeFailure` (which uses `getMessage()` verbatim for the `PIPELINE_ERROR` event operators see) names the outage without this module needing to know anything about that event shape.

**Channel lifecycle**: `CvChannelSupervisor` never shuts the channel down (matches every port in this module except `GrpcDetectionPort` itself) — `close()` only stops its own watch loop and its own `cv-channel-supervisor` scheduler thread.

**`CvUnavailableException extends IllegalStateException`, genuinely stackless**: a closed-gate failure is an expected, frequent-during-an-outage condition, not a bug — capturing a stack trace on every rejected `detect()` during a real outage would be pure waste (the trace is always "gate check in `GrpcDetectionPort#detect`", never useful). The task's literal instruction was `super(message, null, false, false)`, but `IllegalStateException` does not itself re-declare `RuntimeException`'s protected 4-arg constructor, so `super(message)` plus `@Override public synchronized Throwable fillInStackTrace() { return this; }` is used instead — the standard alternative for a stackless exception whose supertype doesn't expose the writable-stack-trace constructor, verified to produce the identical observable outcome (`getStackTrace().length == 0`, `CvUnavailableExceptionTest#hasNoStackFrames`).

## Pull mode (`DetectPulled`, docs/plans/active/MEDIA-SOT-PLAN.md wave M4)

Everything above this section (Correlation design, Payload shrinking, Failure semantics, Stream lifecycle, Reconnect / gate design) describes the **push** transport, `DetectStream`/`GrpcDetectionPort`/`DetectionStreamSession` — untouched by this wave, still green, still the default (`vision.cv.frame-transport=push`). The reconnect gate is likewise push-only today: `GrpcPulledDetectionPort` takes no `CvChannelSupervisor` and has no gate (wiring one in, if pull mode needs the same bounded-recovery story, is a later wave — not R1's scope). This section is the **pull** transport, `DetectPulled`/`GrpcPulledDetectionPort`/`PulledDetectionSession`, added alongside it as a second, independent path. The two never call each other and share no runtime state — only the wire-mapping helpers in `DetectionFrameCodec` (`toWireTrackingConfig`/`toWireCameraPose`, widened from `private` to package-private this wave) are reused, because `PullControl.tracking`/`.camera_pose` are the identical wire messages `FrameRequest.tracking`/`.camera_pose` already are.

**Why `PulledDetectionSession` is a sibling class, not a mode flag on `DetectionStreamSession`.** `DetectStream` is request→response: every `FrameRequest` the client sends gets exactly one matching `DetectionResponse`, correlated by `sequence` in a `ConcurrentHashMap<Long, CompletableFuture<DetectionResult>>`. `DetectPulled` responses are **unsolicited** — the worker decodes and infers on its own schedule and mints `sequence` itself, monotonically per pull; nothing on the client side ever asked for a particular response. There is therefore no correlation map to build in `PulledDetectionSession` at all: every `DetectionResponse` that arrives is decoded and pushed straight onto the session's own `Flow.Publisher`, in receipt order. Reusing `DetectionStreamSession` with an `if (pullMode)` branch would have meant carrying that whole correlation map, its `whenComplete` self-removal, and its per-future timeout machinery into a class that structurally cannot use any of it — a mode flag would be lying about what the class does.

**What replaces correlation: restated desired state, merged from two independent callers.** `PullControl` is declarative, same doctrine as `TrackingConfig` and for the same reason (docs/plans/active/MEDIA-SOT-PLAN.md §5.1): cv-service's `LatestOnlyMailbox` can silently drop a message with no error and no retry, so a one-shot control message is unsafe — every `PullControl` this class sends restates the *complete* current desired state. The wrinkle pull mode adds that push mode never had: `reconfigure(StreamId, PipelineConfig)` and `attitude(StreamId, CameraAttitude)` are two **independent** `PulledDetectionPort` methods, called by different callers at different cadences (a config PATCH vs. telemetry arriving at its own rate) — unlike push mode's `detect(frame, config, attitude)`, which always receives both together for one frame. `PulledDetectionSession` therefore holds `volatile currentConfig`/`currentAttitude` fields and merges both into every outbound message's `controlBuilder(stop)`, so a `reconfigure()` call restates the last-known attitude and an `attitude()` call restates the last-known config's hot fields. A response arriving after only one side has ever been set (e.g. `attitude()` called before any `open()` even ran — not reachable via the port, since `open()` always sets `currentConfig` first) is not a real scenario given the interface's own call order, but `controlBuilder` guards `config == null`/`attitude == null` defensively anyway.

**Wire mapping, field by field:**

| `PullControl` field | Source | Restated on |
|---|---|---|
| `stream_id` | `StreamId.value().toString()` | every message |
| `source_url` | the `open()` caller's `sourceUrl` | **first message only** (`start()`); never again |
| `rtsp_transport` | *(not set by this adapter)* | never — wire default `""` = server default; no Java-side config exists for this in wave M4 |
| `model_id`/`model_version` | `PipelineConfig.model()` | every message, once a config exists |
| `confidence_threshold` | `PipelineConfig.confidenceThreshold()` | every message |
| `target_fps` | `PipelineConfig.inferenceFps()` | every message — the closest existing domain field to "the Java rate controller's output" the plan describes; `DetectionRateController` (vision-application, `feat/cv-rate-control`) is out of this wave's file scope, so whatever `PipelineConfig` a caller passes to `reconfigure()` is what rides the wire as-is |
| `detect_width` | `GrpcCvSettings.detectWidth()` | every message — the same downscale-target knob push mode uses, repurposed as "how wide the worker should downscale locally" |
| `tracking` | `PipelineConfig.tracking()`, via `DetectionFrameCodec.toWireTrackingConfig` (reused, widened to package-private) | every message |
| `camera_pose` | last-known `CameraAttitude`, via `DetectionFrameCodec.toWireCameraPose` (reused, widened to package-private) — set only when `attitude.known()` | every message once an attitude has ever been supplied |
| `stop` | `false` normally, `true` only in `endAndClose()`'s final message | — |

**docs/plans/active/TRACKING-V3-BAND1-CONTEXT.md §2, wave J2**: `capability_level`/`reupdate_max_gap_millis` ride the `tracking` row above for free — `toWireTrackingConfig` is one shared method, so this class needed **zero** changes to gain both new request fields; verified by reading (not assuming) this class's `controlBuilder` still calls `DetectionFrameCodec.toWireTrackingConfig(config.tracking())` unmodified.

**Failure semantics — the honest three-way split this wave's own contract asks for:**
- **Transport failure** (`onError`, e.g. `UNAVAILABLE` because the pulled source is unopenable or stalled past the worker's `CV_PULL_STALL_TIMEOUT_MILLIS`): surfaces to the subscriber via `SubmissionPublisher#closeExceptionally` and drops the session — **no internal retry**. Reopening with backoff is deliberately left to the caller: docs/plans/active/MEDIA-SOT-PLAN.md decision D5 says the existing generic `SupervisedPublisher<DetectionResult>` (vision-application, a later wiring wave) already gives `VideoSourcePort` reopen-with-backoff for free and is meant to wrap this port's output verbatim.
- **Server ends the call with no `stop=true` ever sent**: treated exactly like a transport failure (a live bidi call is never expected to complete server-side on its own) — same `closeExceptionally` path. If this session's own `endAndClose()` already tore it down first (the expected case — `stop=true` was sent, the server naturally answers with `onCompleted`), the shared `torndown` CAS guard makes the server's `onCompleted` a no-op instead of a spurious second failure.
- **A malformed `DetectionResponse`** (e.g. a non-finite confidence failing `Detection`'s compact ctor): unlike `DetectionStreamSession`, there is no pending future to fail for just this one item, because responses are unsolicited. Logged at WARNING and dropped; the session and its publisher both keep running for the next response. This is the natural pull-mode translation of push mode's "a malformed response fails only that one frame" posture — there being no per-response future is exactly the structural difference the file scope called out, and dropping-with-a-log is what "fail only this one" becomes when there is nothing left to fail.

**Backpressure**: same latest-wins `publisher.offer(result, (subscriber, dropped) -> true)` policy `FfmpegGrabLoop`/`MjpegVideoSource`/etc. use for `VideoSourcePort` — a slow subscriber never blocks delivery of the next `DetectionResponse`; the adapter, not the caller, owns the drop.

**Six new diagnostic fields (`DetectionResponse` 16–21) — mapped nowhere yet, and that gap is real, not an oversight.** `DetectionFrameCodec.decode(StreamId, DetectionResponse)` (unchanged, reused verbatim by `PulledDetectionSession.onResponse`) only ever read fields 1–15; `decode_millis`/`source_fps`/`achieved_fps`/`dropped_frames`/`missed_deadlines`/`capture_skew_millis` are on the wire object this class receives but are not carried into the returned `DetectionResult` by anything in this module. The reason is structural, not an omission this wave could have closed: `DetectionResult` (`vision-domain`, frozen for this wave — `M2` owns it and it is not in this wave's file scope) is `(streamId, frameSequence, capturedAt, detections, inferenceLatency, tracking)` — there is no field for any of the six. docs/plans/active/MEDIA-SOT-PLAN.md itself only assigns two of the six a named destination (`DetectionRateResponse` gains `transport`/`decodeMillisP50`, wave M5's read-model); the other four (`source_fps`, `achieved_fps`, `dropped_frames`, `missed_deadlines`) have **no named destination anywhere in the plan** as written — wave M5 (`vision-application/pipeline`, `DetectionRate`/`DetectionRateWindow`) is where that decision belongs, not here.

## Visual geolocation (`LocalizeStream`/`BuildReferenceIndex`, docs/plans/active/VISUAL-GEO-V2-PLAN.md §3.1, H3)

**D6 — the one and only pitch-sign conversion.** `Attitude.gimbalPitchDegrees()` is positive-up (aircraft pitch convention: level = 0, straight down = -90); `rectify.py`'s `camera_pitch_deg` wants degrees-from-nadir (straight down = 0, level with the horizon = 90). `GeoFixCodec.toWireGeoTelemetry` is the only place in this codebase that performs `pitch_from_nadir = 90 + gimbalPitchDegrees` — pinned at both boundary cases by `GeoFixCodecTest#cameraPitchDegConvertsAttitudesPositiveUpGimbalPitchToRectifyPysDegreesFromNadir` (gimbalPitch=-90 → 0/nadir; gimbalPitch=0 → 90/horizon), naming both conventions explicitly in the test name and assertions per the plan's requirement.

**H8 — the gimbal-less fallback (docs/plans/active/VISUAL-GEO-V2-PLAN.md §9.11 defect 2, §9.12).** `Attitude.gimbalPitchDegrees()` is populated only from MAVLink `GIMBAL_DEVICE_ATTITUDE_STATUS` (#285) / `MOUNT_ORIENTATION` (#265); an airframe with no gimbal sends neither, so the field stayed `null` and `camera_pitch_deg` never reached the wire at all — which is why the H7 demo measured `rectified` false on 323/323 fixes until a #285-emitting airframe appeared. `GeoFixCodec` now falls back: when `gimbalPitchDegrees` is absent it uses `Attitude.pitchDegrees()` (the airframe's own pitch, #30) **plus** a configured fixed camera-mount pitch offset, then applies the same single `90 + pitch` conversion. A measured gimbal pitch is earth-frame and absolute, so the mount offset is deliberately **not** added to it. The offset is `vision.geo.visual.mount-pitch-degrees` (`VisionGeoVisualProperties#mountPitchDegrees`, default `0.0`, validated finite in vision-app; threaded in through `GrpcPulledGeolocationPort` → `GeolocationSession` → this codec) — no magic number in code, per CLAUDE.md rule 1. The result is deliberately **unclamped**: `localize.py` already gates rectification on `camera_pitch_deg >= rectify_min_pitch_deg` and `rectify.py#horizon_crop` returns `None` when too few ground rows survive, so a nose-up fallback degrades to `rectified=false` rather than fabricating a warp. Pinned by `GeoFixCodecTest`'s three fallback cases plus `aMeasuredGimbalPitchIsEarthFrameSoTheMountOffsetNeverAppliesToIt`.

**Fields deliberately left absent on `GeoTelemetry`**: `gps_radius_meters` (no HDOP-to-meters conversion formula exists anywhere in this codebase — inventing one here would repeat exactly the "unsourced conversion formula" `contexts/vision-flight`'s `DefaultTrackCorrectionService` already refused to invent for its own `gps_radius_meters`-shaped gap, H2a's dated amendment, CLAUDE.md rule 1 "no magic numbers") and `horizontal_fov_deg` (`GeoSessionConfig` carries no per-session hfov; the wire's own comment says `0/absent` = the region's assumed default, exactly this codec's intent).

**`GrpcPulledGeolocationPort`'s required supervisor.** Unlike every `PulledDetectionPort`/`DetectionPort` adapter in this module (where `CvChannelSupervisor` is an optional, nullable constructor argument — `null` means no gate), this port's constructor requires one. `open()` checks `supervisor.available()` first, before constructing a `GeolocationSession` or issuing any RPC — a closed gate throws `CvUnavailableException` synchronously. This is stricter than the detection ports because a geolocation session is long-lived (opened once per stream, held for the stream's life) rather than per-frame — deferring the failure into the publisher's `onError` would make a caller (H5's runner) wait out a full round trip just to learn what the supervisor already knew.

**`GrpcReferenceIndexPort#build`: non-blocking, by construction.** `ReferenceIndexPort#build`'s contract requires an immediate return of a live `Flow.Publisher<IngestProgress>` — unlike the harvested `feat/visual-geo` branch's `build(...)`, which blocked the calling thread for the whole build via a `CountDownLatch`. This class instead starts one `Thread.ofVirtual()` background thread per `build()` call that does all the archive-framing/upload work; the response side (`ProgressObserver`, running on a gRPC callback thread) owns delivering progress and closing the publisher — normally on the server's own terminal `SUCCEEDED`/`FAILED` + `onCompleted`, exceptionally on a transport `onError`. The writer thread's own `catch` blocks additionally call `requestObserver.onError(...)` and `publisher.closeExceptionally(...)` directly for a local failure (archive `IOException`, or the caller's lazy `tiles` iterator itself throwing) — it does not wait for gRPC to notice the abandoned call and echo an error back.

**`region.json`'s content — a documented decision, not a frozen schema.** Neither the plan nor the proto names a field-level schema for the manifest zip entry; cv-service's own landing step (`cv_service/geo/pack.py#land_pack`) validates it only as syntactically valid JSON (`json.loads`), and its only confirmed reader (`servicers.py#_region_info`, backing `ListRegions`) reads just `region_meta.get("name")` (falling back to the region id when absent) — `zoom`/bounds/tile-derived stats for `ListRegions`/`localize.py` all come from a separately cv-service-built `tiles.json`, not from `region.json`; `localize.py#_load_region` requires `region_meta` only to be non-`None` (i.e. parse successfully), reading no specific key beyond that. `GrpcReferenceIndexPort#manifestJson` writes `region_id`/`name`/`zoom`/`bounds` — a superset of the confirmed-required `name` — hand-built (no JSON library dependency added for four fields) purely for forward-compatibility/on-disk diagnostics; no Java or Python code path in this codebase depends on the extra fields being present.

**`IngestProgress.summary()` is left `null` even on the terminal `SUCCEEDED` update.** The wire's terminal `ReferenceIndexProgress` sometimes carries a populated `ReferenceIndexStats`, but that message alone has no region identity/bounds/zoom/`built_at` (unlike `RegionInfo`, which has all of those) — synthesizing the missing fields (a fabricated bounding box, zoom 0, "now" as `built_at`) would be exactly the invented-data pattern this codebase's own conventions refuse elsewhere (same H2a precedent as D6's absent fields, above). `ReferenceIndexSummary`'s own contract permits a `null` summary even on `SUCCEEDED`, and the one real consumer today (`DefaultReferenceRegionService.ProgressSubscriber`) never reads this field anyway — it drops its in-flight job the instant `SUCCEEDED` arrives and defers to `list()` (backed by `ListRegions`'s full `RegionInfo`) from then on.

**No `reconfigure` — `GeolocationSession` is structurally simpler than `PulledDetectionSession`.** `PulledGeolocationPort` has exactly three methods (`open`/`telemetry`/`close`) — `GeoSessionConfig` (region/target-fps/prior) is fixed for a session's whole life and captured once as a `final` field; only `telemetry` is a hot field restated on every outbound `GeoControl`. `source_url` is sent on `start()`'s first message only and never restated, same convention as `PulledDetectionSession`'s `source_url`.

**Malformed-`GeoFix` handling mirrors `PulledDetectionSession`'s "never guess" posture**: a response that fails `VisualFix`'s own compact-constructor validation (e.g. `GEO_STATUS_FIX` with no latitude) is logged at WARNING and dropped by `GeolocationSession#onResponse` — there is no pending future to fail for an unsolicited response, and the session keeps running for the next fix. A *refused* fix (non-empty `refusal`, `position == null`) is not a malformed response and is delivered like any other — `VisualFix`'s own contract: "a refusal, not an error."

## Conventions
- Plain class, no Spring, no framework annotations — matches every other adapter in this repo.
- Logging via `System.Logger` (not java.util.logging/SLF4J directly), same idiom as `adapter-publish-hls`'s `MediamtxStreamPublisher`: INFO on opening a stream, WARNING on unexpected completion/response timeout (with cause where there is one), DEBUG for a best-effort `onCompleted()`/`cancel()` failure during teardown. **Transport error is the one exception, changed wave R1**: `DetectionStreamSession#onTransportError` logs WARNING with the failure message plus the gRPC status code (`Status.fromThrowable(t).getCode()`) only — not the full throwable, which is logged separately at DEBUG — because a transport error during a real outage now fires once per reopened session per reconnect probe, and the full stack trace was pure repeated noise for a condition `CvChannelSupervisor`'s own WARNING/heartbeat already names at the channel level; the WARNING message itself was reworded from "will reopen on next detect()" to "will retry with backoff" to match that a caller's *next* `detect()` is what actually retries, not this class on its own.
- **`CvChannelSupervisor`'s own logging** (see **Reconnect / gate design** below): WARNING once on entering an outage, INFO once on recovery (naming outage duration + attempt count), INFO heartbeat every `outageLogInterval` while the outage continues — a different cadence from the per-session logging above, deliberately: this is the one place a real outage's duration is visible without correlating multiple per-stream WARNING lines by hand.
- Field-by-field proto↔domain mapping, no shared DTOs: `BoundingBox`/`Detection` both exist as distinct domain and generated-proto types in the same file; proto's `com.drones.vision.proto.v1.Detection`/`BoundingBox` are always referenced fully-qualified (or via `var`) at the two or three call sites that need them, since Java has no import aliasing and the domain names are the ones used everywhere else. **docs/plans/done/TRACKING-PLAN.md T4 added six more colliding simple names** (`TrackingConfig`, `TrackingMode`, `TrackState`, `DetectionSource`, `DetectorReason`, `TargetLock` — both a domain and a proto type share each name): same rule, domain types imported unqualified (they're the ones every method signature/local variable uses), proto types always fully-qualified at their handful of construction/switch sites in `DetectionFrameCodec`. `TrackRef`/`TrackingTelemetry` have no proto counterpart (the wire has no matching message for either — they're each assembled from several flat wire fields) and are imported unqualified with nothing to disambiguate.
- `ModelRef` for a mapped `Detection` comes from the *response*-level `model_id`/`model_version` fields (the wire `Detection` message itself carries no model info) — the same `ModelRef` instance is reused for every detection in one response.
- **HTTP/2 keepalive on the real-TCP channel (docs/plans/done/REMOTE-CV-PLAN.md "Transport decisions" P1):** `GrpcCvSettings` fields, same idiom as `responseTimeout` — `keepAliveTime` (default 20s, ping interval including on an idle stream), `keepAliveTimeout` (default 5s, ack deadline before the channel considers the connection dead), `keepAliveWithoutCalls` (default `true`, ping even with no RPC in flight — the case that most needs it, e.g. a stream mid-outage-backoff). Applied only in the `(host, port, GrpcCvSettings)` constructor's `ManagedChannelBuilder` — a real-transport concern, not applied on the bring-your-own-channel constructor (tests inject in-process channels). Not yet exposed as `vision.cv.*` Spring properties — the plan: a later `vision-app` wiring wave (docs/plans/active/LAYERING-REFACTOR-PLAN.md F4) maps `VisionCvProperties` onto `GrpcCvSettings`. The matching cv-service server-side permit options live in `cv_service/grpc/server.py`'s `_KEEPALIVE_SERVER_OPTIONS` — see `cv/cv-service/MODULE.md`.
- **`PulledDetectionSession` follows the same logging/lock/CAS idioms as `DetectionStreamSession`** (docs/plans/active/MEDIA-SOT-PLAN.md wave M4): `System.Logger`, INFO on opening the call, WARNING on transport error/unexpected completion/malformed response, DEBUG for a best-effort teardown-write failure; a `writeLock` monitor serializes every write to the request observer (gRPC stream observers are not thread-safe); a `torndown` `AtomicBoolean` CAS makes teardown exactly-once however it is triggered. One deliberate difference: `endAndClose()` sends real data (`PullControl{stop=true}`) via `onNext`, not just `onCompleted()`, so — unlike `DetectionStreamSession#endAndClose`, which calls `onCompleted()` outside `writeLock` — this method's `onNext`+`onCompleted()` pair runs *inside* `writeLock`, since an unsynchronized `onNext` racing a concurrent `reconfigure()`/`attitude()` write would violate the observer's single-writer contract.

## Gotchas
- **FIXED (docs/plans/done/REMOTE-CV-PLAN.md P0 item 1): the `io.grpc:grpc-core` version skew that used to wedge a real gRPC channel permanently in `CONNECTING` after a genuine TCP connect failure is resolved at the root pom.** Previously, `grpc-core` was not pinned by `${grpc.version}` anywhere in this repo — it came from Spring Boot 4.1's imported `io.grpc:grpc-bom` (`spring-boot-dependencies` pins `grpc-java.version`=1.80.0), since the root pom only overrode `grpc-netty-shaded`/`grpc-protobuf`/`grpc-stub` explicitly; `grpc-netty-shaded:1.64.0`'s compiled bytecode against `grpc-core:1.80.0` threw `NoSuchMethodError: io.grpc.internal.ManagedClientTransport$Listener.transportShutdown(Status)` deep inside Netty's transport-shutdown notification on a real connect failure, silently swallowed by Netty's own listener-dispatch logging, so the channel never learned the attempt failed. **The fix: the root `pom.xml`'s `dependencyManagement` now imports `io.grpc:grpc-bom:${grpc.version}` (scope `import`, type `pom`) *before* the individual `grpc-netty-shaded`/`grpc-protobuf`/`grpc-stub` pins** — Maven's first-declaration-wins rule for imported BOM entries makes this bom import win over `spring-boot-dependencies`' own `grpc-bom` import (declared later, transitively, via the `spring-boot-starter-parent` chain), aligning the *whole* `io.grpc` family (`grpc-core`, `grpc-inprocess`, `grpc-api`, `grpc-context`, `grpc-util`, …) to `${grpc.version}`=1.64.0 in one place — not just the three artifacts previously pinned individually. Pinning `grpc-core` alone inside this module's own `pom.xml` was tried in an earlier task and rejected (it fixed `grpc-netty-shaded`'s connect-failure path but broke `grpc-inprocess:1.80.0`, which needs 1.80.0-only APIs like `io.grpc.internal.DisconnectError` against a downgraded `grpc-core:1.64.0`, throwing `NoClassDefFoundError`) — the root-level bom import avoids that failure mode entirely because it re-aligns every `io.grpc` artifact together, not just one. **Verified** with `mvn -pl cv/grpc dependency:tree -Dverbose | grep grpc` and the same for `vision-app`: every `io.grpc:*` line resolves to `1.64.0` with no `(version managed from …)` skew remaining (`grpc-core` and `grpc-inprocess` both included). **The real dead-endpoint-then-server-starts scenario is now a passing test**: `GrpcDetectionPortTest#detectRecoversAfterRealConnectFailureOnceServerStarts` binds nothing to a TCP port, asserts `detect()` fails, then starts a real gRPC server on that exact port and asserts a subsequent `detect()` on the *same* `GrpcDetectionPort`/channel succeeds — stable across repeated runs (recovers in 1-2 reopen attempts, ~1-2s wall time). One nuance worth knowing if this test is ever touched: a fail-fast RPC issued while the channel is in `TRANSIENT_FAILURE` returns near-instantly rather than blocking, so the retry loop needs an explicit `Thread.sleep` between attempts to give the channel's own reconnect-backoff timer (and this class's per-`detect()`-call fresh-session-open, which itself re-attempts the TCP connect) real wall-clock time — a tight retry loop with no sleep observes only fast, repeated `UNAVAILABLE` failures and never recovers within a short bound.
- The `grpc-inprocess` test dependency in this module's `pom.xml` is deliberately left unversioned so it resolves via the same root-level `grpc-bom` import to `1.64.0` — do not add an explicit version pin here, it is redundant now that the BOM already aligns it. See `cv/vision-proto/MODULE.md`'s Gotchas for the analogous (actually harmless) protobuf Java/Python version-line divergence.
- `FrameRequest`/`DetectionResponse` carry `timestamp_millis` (a `long`), so `VideoFrame.capturedAt()`'s sub-millisecond precision (`Instant.now()` often has nanosecond resolution) does not round-trip — expected and harmless in production (millisecond precision is enough), but tests must build frames with a millis-truncated `Instant` or round-trip equality assertions will flake.
- Proto `float` fields (`confidence`, `BoundingBox.x/y/width/height`) widen to `double` on the domain side with normal float-to-double imprecision (e.g. `0.1f` != `0.1d` bit-for-bit) — tests assert those fields with a small delta, not record `.equals()`.
- `pending.values().forEach(future -> future.completeExceptionally(cause))` (used by both the transport-error and `endAndClose` paths) relies on each future's own `whenComplete`-registered self-removal (attached when the future was created in `send()`) to actually drain the `pending` map — there is no separate explicit `pending.clear()`, so if that `whenComplete` registration were ever removed, failed sessions would leak map entries.
