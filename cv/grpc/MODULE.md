# adapter-cv-grpc

gRPC client to the Python `cv-service`: every driven port vision-perception/vision-learning declare for reaching it — `DetectionPort` (push), `PulledDetectionPort` (pull), `ModelRegistryPort`, `TrainingPort`, `DatasetUploadPort`, `PulledGeolocationPort`, `ReferenceIndexPort` — over three gRPC services generated from `proto/vision/v1/cv.proto`: `Inference` (`DetectStream`, `DetectPulled`, `Inspect`), `Training` (`ListModels`, `PromoteModel`, `StartTraining`, `UploadDataset`), `Geolocation` (`LocalizeStream`, `BuildReferenceIndex`, `ListRegions`, `DeleteRegion`). The proto also declares a fourth service, `Detector` (`Detect`) — cv-service's own W4 pooled-detector scaling RPC, called only cv-service-to-cv-service; nothing in this module calls it.

**Depends on:** vision-domain · vision-platform (`SubsystemStatusPort`/`SubsystemStatus`/`Health`, for `CvStatusProvider`) · vision-proto (brings `io.grpc:grpc-{netty-shaded,protobuf,stub}`, `com.google.protobuf:protobuf-java`)
**Used by:** vision-app (`CvWiring#cvGrpcChannel`/`#cvTrainingChannel`, gated by `vision.cv.enabled`; `TrainingWiringConfiguration`; `VisualGeoWiringConfiguration`; `SystemStatusWiring`)
**Build/test:** `./mvnw -B -pl cv/grpc test`. Control-plane RPCs (`Training`/`Geolocation` list/promote/delete) use in-process fakes; `CvChannelSupervisorTest` and one recovery case each in `GrpcDetectionPortTest`/`GrpcPulledGeolocationPortTest` use real-TCP-loopback — an in-process channel never enters `TRANSIENT_FAILURE`/`SHUTDOWN`, so only a real socket can drive the reconnect gate's state machine. No docker, no native lib, nothing skippable.

### `com.drones.vision.adapter.cvgrpc` — types

- `record CvTarget(String host, int port)` — one gRPC target; compact-ctor validated (non-blank host, port in `[1,65535]`). `static parse(String "host:port")` / `static List<CvTarget> parseAll(List<String>)`.
- `final class CvChannels` — static channel-building helper (`GrpcDetectionPort#buildChannel` delegates here). `static ManagedChannel forTarget(CvTarget, GrpcCvSettings)` — one address, plaintext/keepalive per settings. `static ManagedChannel forTargets(List<CvTarget>, GrpcCvSettings)` — 1 target delegates to `forTarget`; 2+ builds one channel over a package-private `StaticTargetsNameResolver`/`StaticTargetsNameResolverProvider` (scheme `cv-static-targets`, resolves synchronously to every address at once, bypassing `NameResolverRegistry`) so grpc-java's own default `pick_first` policy tries targets in order and fails over past a refused connection **on its own — no load-balancing logic is invented here**; `CvChannelSupervisor` needs zero changes since it still watches one `ManagedChannel`.
- `enum WireFormat { AUTO, JPEG, BGR24 }` — how a downscaled frame reaches cv-service. `resolve(String authority)` — `AUTO` resolves to `BGR24` for a loopback authority (`localhost`/`127.*`/`[::1]`, case-insensitive, port stripped, decided from host **text**, never DNS-resolved — a slow resolver must not stall channel construction) and `JPEG` otherwise (the conservative default: raw 640×360 `BGR24` is ~691 KB against ~40 KB JPEG, free over loopback, indefensible over a radio link). `static parse(String)` — blank/`null` → `AUTO`.
- `final class DetectionFrameCodec` — package-private, pure wire↔domain conversion for `GrpcDetectionPort`, no gRPC call machinery. `(int detectWidth, float jpegQuality, WireFormat wireFormat)`; 2-arg ctor defaults `JPEG` (an `AUTO` reaching this class is treated as `JPEG` — resolution is the caller's job).
  - `FrameRequest encode(VideoFrame, PipelineConfig)` — downscales+re-encodes a wide `BGR24` frame (see Payload shrinking), always sets `FrameRequest.tracking` (see Tracking), unconditionally including `TrackingMode.OFF`, and always sets `FrameRequest.trace = config.trace()` — a pure per-request restatement; this class makes no trace policy decision, `TraceDemandPort`/`PipelineTrace` (`contexts/vision-perception`) decide the value per stream, flipping it on while something is actually consuming the trace (a `GET /api/streams/{id}/cv/trace` poll or its SSE subscriber) and back off otherwise. Throws `IllegalArgumentException` for an unsupported `PixelFormat`, `IOException` on encoder failure, or propagates a `RuntimeException` for malformed/too-short source data.
  - `static DetectionResult decode(StreamId, DetectionResponse)` — stateless; maps per-detection track fields onto `Detection.track()`, per-frame fields onto `DetectionResult.tracking()`, the six pull-mode diagnostic fields onto `DetectionResult.pullTelemetry()` (see Gotchas — `dropped_frames` is no longer pull-exclusive), and `response.getObjectsList()` (field 27) onto `DetectionResult.objects()` via the private `toObjectStates` (see "The per-identity mirror" below). One decode path serves both `DetectStream` and `DetectPulled` responses; no branch on which RPC produced the response.
- `final class DetectionStreamSession` — package-private; one open `DetectStream` bidi call per `StreamId`. `(StreamId, InferenceStub, ConcurrentHashMap<StreamId,DetectionStreamSession> sessions, long responseTimeoutMillis)`, every collaborator passed in explicitly. Owns the request observer, its write lock, the sequence→future correlation map, and the idempotent teardown guard (see Correlation design, Failure semantics, Stream lifecycle). `onResponse` checks `response.getStreamId()` against this session's own `streamId` before touching `pending` — see "`DetectionResponse.stream_id` checking" below.
- `final class GrpcDetectionPort implements DetectionPort, AutoCloseable` — the `DetectionPort` entry point; delegates encode/decode to a `DetectionFrameCodec`, per-stream state to a `ConcurrentHashMap<StreamId,DetectionStreamSession>`. Three constructors: `(String host, int port, GrpcCvSettings)` builds a `ManagedChannel` (plaintext default `true` — cv-service is reached over a private network) and delegates to the 2-arg form; `(ManagedChannel, GrpcCvSettings)` — bring-your-own-channel, delegates to the 3-arg form with `supervisor=null` (no gate); `(ManagedChannel, GrpcCvSettings, CvChannelSupervisor)` — **canonical**; `supervisor` nullable, `null` means no gate, non-null is expected to already be watching this same channel — this constructor does not call `supervisor.start()`, the caller owns that. `wireFormat` is resolved from `channel.authority()`, not a host string, so every constructor path gets the same answer (an in-process test channel reports `localhost`). `CompletionStage<DetectionResult> detect(VideoFrame, PipelineConfig)` — never blocks (see Correlation design/Failure semantics/Reconnect). `void streamEnded(StreamId)` — optional lifecycle hook, idempotent. `void close()` — idempotent; ends every open stream, then shuts the channel down (awaits `channelShutdownTimeout`, then `shutdownNow()`); never touches a supervisor passed to the 3-arg constructor — that lifecycle belongs to the caller.
- `final class PulledDetectionSession` — package-private; one open `DetectPulled` bidi call per `StreamId`. `(StreamId, InferenceStub, ConcurrentHashMap<StreamId,PulledDetectionSession> sessions, int detectWidth)`. No sequence→future correlation map — see Pull mode. `onResponse` checks `response.getStreamId()` against this session's own `streamId` before decoding — see stream_id checking below; a mismatch is logged and dropped like a malformed response, an empty wire value is accepted.
  - `Flow.Publisher<DetectionResult> publisher()` — backed by a plain `SubmissionPublisher`.
  - `void start(URI sourceUrl, PipelineConfig)` — opens the call, sends the first `PullControl` (the only message carrying `source_url`).
  - `void reconfigure(PipelineConfig)` / `void attitude(CameraAttitude)` — restate the full desired state (see Pull mode). Every restated `PullControl` also carries `trace = config.trace()` — same `TraceDemandPort`-driven value as `DetectionFrameCodec#encode`.
  - `void endAndClose()` — sends `PullControl{stop=true}`, half-closes, completes the publisher normally; shares the `torndown` CAS guard with the transport-failure path.
- `final class GrpcPulledDetectionPort implements PulledDetectionPort` — not `AutoCloseable`; takes only a pre-built `ManagedChannel` (`(ManagedChannel, GrpcCvSettings)`) — no host/port constructor, matching every other non-`GrpcDetectionPort` class's "shared channel, never closed here" convention (`DetectPulled` is a second RPC on the same `Inference` service `DetectStream` uses — wiring is expected to hand this the identical channel). Holds one `PulledDetectionSession` per `StreamId`. `open(StreamId, URI, PipelineConfig)` closes any previous live session for the id first (defensive — an id must not have two live pulls). `reconfigure`/`attitude`/`close(StreamId)` are no-ops for an id with no open pull, per the port's own contract.
- `final class GrpcModelRegistryPort implements ModelRegistryPort` — not `AutoCloseable`, never shuts its channel down. `(ManagedChannel)` delegates to `(ManagedChannel, Duration.ofSeconds(CALL_TIMEOUT_SECONDS))`; `(ManagedChannel, Duration callTimeout)` is canonical, sourced from `vision.cv.registry.call-timeout` — deliberately not routed through `GrpcCvSettings`. `List<ModelRef> models()` / `void promote(ModelRef)` — both blocking, deadline-bounded. `static final long CALL_TIMEOUT_SECONDS = 10` — looser than `GrpcCvSettings.responseTimeout` (2s) since these are infrequent control-plane calls, but still bounded so a hung/unreachable cv-service cannot block the calling thread forever. `ModelRef` (vision-domain, frozen) is `(id, version)` only — no field for wire `ModelInfo`'s `stage`/`metrics`, so `models()` always drops both; a future REST endpoint needing them will need a parallel raw-`ModelInfo` read path or a domain change, out of this adapter's scope.
- `final class GrpcTrainingPort implements TrainingPort` — not `AutoCloseable`, never closes its channel. `(ManagedChannel)`, the only constructor, same shared-channel contract. `void startTraining(TrainingJobSpec, Consumer<TrainingProgress> onProgress)` — **blocks the calling thread for the job's lifetime** (per the port's own Threading contract), driving the server-streaming `Training/StartTraining` blocking-stub iterator. **No per-call deadline exists on this class** — a training job can run for many epochs; relies entirely on the shared channel's own HTTP/2 keepalive to detect a genuinely dead connection. `JOB_STATE_UNSPECIFIED`/`UNRECOGNIZED` map defensively to `JobState.RUNNING`. No explicit cancel handle — a caller cancels by interrupting the thread; the generated blocking iterator reacts to interruption on its own (cancels the call, surfaces `StatusRuntimeException(CANCELLED)`).
- `final class GrpcDatasetUploadPort implements DatasetUploadPort` — not `AutoCloseable`, never closes its channel. `(ManagedChannel, GrpcCvSettings)`; `settings` supplies `uploadTimeout()`/`uploadChunkBytes()`. `DatasetUpload upload(DatasetId, String dataYaml, List<ExportEntry>)` — blocks the calling thread, bounded by `uploadTimeout` (default 300s). **The one class in this module using an async stub, not blocking** — `Training/UploadDataset` is client-streaming, which grpc-java's blocking stub cannot do; an internal `UploadAckObserver` bridges the async callback back to a synchronous return via `CountDownLatch(1)`. The archive is **never fully materialized in memory or on disk**: `ZipOutputStream` writes over a private `ChunkingOutputStream` that emits one `DatasetChunk` every `uploadChunkBytes` (262,144 = 256 KiB default) and a final chunk on close. Zip entries in order: `data.yaml`, then per `ExportEntry`, `images/<name>` then `labels/<stem>.txt` (`<stem>` = name with everything from the last `'.'` stripped). No client-side caching/dedup — a repeat `upload()` is an independent RPC; re-upload idempotency is the server's job.

- `final class GeolocationSession` — package-private, one open `LocalizeStream` call per `StreamId`; structurally simpler than `PulledDetectionSession` — no `reconfigure`, `GeoSessionConfig` captured once as a `final` field, only `telemetry` is hot. `publisher()`, `start(URI sourceUrl)`, `telemetry(Telemetry)` (restates the full desired state), `endAndClose()` (idempotent via the same `torndown` idiom).
- `final class GrpcPulledGeolocationPort implements PulledGeolocationPort` — not `AutoCloseable`, bring-your-own-channel only. `(ManagedChannel channel, CvChannelSupervisor supervisor, double mountPitchDegrees)` — **channel and supervisor both required** (`NullPointerException` on either `null`) — the one structural difference from every detection-port sibling, where the supervisor is nullable. A closed gate makes `open()` throw `CvUnavailableException` **synchronously, before any session/IO**, since a geolocation session is long-lived (not per-frame) and a caller should never wait out a round trip to learn cv-service is down. `mountPitchDegrees` (from `vision.geo.visual.mount-pitch-degrees`) is carried unread into each session, consumed only by `GeoFixCodec`. `open`/`telemetry`/`close` mirror the pull-detection port's contract.
- `final class NoopGeolocationPort implements PulledGeolocationPort` — the `vision.geo.visual.enabled=false` fallback. `open()` delivers exactly one refused `VisualFix` (`position=null`, `refusal` naming "disabled") then completes normally — never `onError`, matching `VisualFix`'s "a refusal, not an error" contract. `telemetry`/`close` are no-ops.
- `final class GrpcReferenceIndexPort implements ReferenceIndexPort` — not `AutoCloseable`, bring-your-own-channel, never closes it. `(ManagedChannel, GeoUploadSettings)`. `Flow.Publisher<IngestProgress> build(RegionIngestSpec, Iterable<Tile>)` — **non-blocking**, returns immediately; starts one `Thread.ofVirtual()` background thread per call that frames and streams the zip archive (`region.json` manifest + tiles), while the response side owns delivering progress/closing the publisher. `tiles` is consumed lazily, once, never assumed re-iterable. `List<ReferenceIndexSummary> list()` — blocking `ListRegions`, 10s deadline (a separate constant from `GrpcModelRegistryPort`'s own). `void delete(String regionId)` — blocking `DeleteRegion`, same deadline; `Ack.ok=false` throws `IllegalStateException` naming cv-service's refusal text.
- `CvChannelSupervisor implements AutoCloseable` / `CvUnavailableException extends IllegalStateException` / `CvStatusProvider implements SubsystemStatusPort` — see Reconnect / gate design below for the first two. `CvStatusProvider(Supplier<CvChannelSupervisor>, Supplier<GrpcCvInspectClient>)` backs `GET /api/system/status`'s cv-service row — both collaborators are `Supplier`s rather than the concrete objects, since `vision-app` can legitimately wire the channel without reconnect supervision or an Inspect client enabled; a `null` supervisor still answers `Health.UNKNOWN` (never a crash, distinct from the unconditionally-wired `Health.DISABLED` bean for CV off entirely). `available()` → `Health.OK` with `detail = "cv-service channel is " + state() + capacityDetail()`; otherwise `Health.DOWN` with `detail = describe()` verbatim and `since = now - outageFor()`. `capacityDetail()` (private) appends `"; N streams, M sessions, K gate permits (<detector-client>)"` from `GrpcCvInspectClient#processFacts()` when the `inspect` supplier is present and reachable — folded into the existing free-text `detail` string, **not** new structured fields on `SubsystemStatus` (a cross-cutting record shared by every subsystem provider; widening it would leak one subsystem's shape into every other), degrading silently to `""` on a `null` client or a `StatusRuntimeException` (capacity is an enrichment, never a precondition for reporting reachability). This is how a cv-service absence is reported to the rest of the app — there is no second channel for it.
- `GrpcCvInspectClient(ManagedChannel)` / `(ManagedChannel, Duration callTimeout)` — public, final; thin blocking-stub wrapper over the generated `Inference/Inspect` RPC; never closes its channel (same convention as `GrpcModelRegistryPort`). `InspectResponse processFacts()` → `inspect("", 0)`, cv-service's process-wide facts (detector-client kind, live session count, gate permits, stream ids being served) — the only method `CvStatusProvider` calls. `InspectResponse inspect(String streamId, int frames)` — a specific stream's own facts plus up to `frames` of its `FrameLedger` history (`0`=whole ring); `found=false` means no live session for that id. **This class has no reader for `InspectResponse.ledgers`/`.session` today** — only `processFacts()`'s process-wide shape is consumed; `inspect(streamId, frames)` exists for a future caller (cv-service-side trace cross-check), unused in production. 5s call deadline (`CALL_TIMEOUT_SECONDS`), tighter than `GrpcModelRegistryPort`'s 10s since a status poll must not itself become the slow part of `GET /api/system/status`. Propagates a raw `StatusRuntimeException` on failure — `CvStatusProvider` is the sole catcher.

### Correlation design (`DetectStream`)
`DetectStream` is bidirectional streaming — one open call per `StreamId`, not per frame. A `DetectionStreamSession` (one per `StreamId`) owns the request observer, lazily opened on first `detect()`. Each frame is sent as one `FrameRequest`, keyed in a `ConcurrentHashMap<Long, CompletableFuture<DetectionResult>>` by `sequence`; the matching `DetectionResponse` (matched by its own `sequence`) completes that future — correct even under out-of-order server replies. **The mapped `DetectionResult.streamId()` is the session's own domain `StreamId`, never a re-parse of the response's wire `stream_id` string** — correlation never depends on the server echoing that field correctly. gRPC stream observers are not thread-safe: every write to a session's request observer is serialized through that session's own monitor; concurrent `detect()` calls for the *same* stream are safe, different streams never contend. `DetectionStreamSession.send(sequence, FrameRequest)` takes an already-built request — request *construction* (which can fail per-frame) stays decoupled from session *lifecycle*: a conversion failure never creates or touches a session.

### Payload shrinking for large `BGR24` frames
The RTSP/file RX path produces full-resolution raw `BGR24` (e.g. 1280×720 ≈ 2.7 MB) — too large to push at a useful detection rate. In `DetectionFrameCodec#encode`, before session machinery is touched: a `BGR24` frame **wider than `detectWidth`** (default 640px — an adapter-internal wire knob, independent of cv-service's own `CV_IMGSZ` inference size) is downscaled (aspect preserved, Java2D bilinear) then, depending on `WireFormat`, either JPEG-encoded (`ImageIO`, quality from `jpegQuality`, default 0.8) or sent raw as `BGR24` bytes. `JPEG` frames and `BGR24` frames already `≤detectWidth` pass through byte-identical (only `>`, not `≥`, triggers downscale). `WireFormat.BGR24` skips the JPEG encode here **and** the matching decode inside cv-service — together the bulk of the non-inference round trip on loopback; payload is `3 × detectWidth × scaledHeight` (≈691 KB at 640×360) against ≈40 KB JPEG. No coordinate mapping back to source resolution is needed — detection boxes come back normalized `[0,1]`. Runs synchronously on the calling thread inside `detect()` (CPU-bound, ~15ms for 720p — net cost versus the pre-existing fast path is roughly flat, since it replaces transmitting several MB with encoding+sending a few hundred KB). A conversion failure fails only that one frame's stage — no session is created or touched, an already-open session for that stream is unaffected.

### Tracking wire mapping
`DetectionFrameCodec` is where the tracking wire contract meets the domain — pure field mapping, no policy, both directions. **`encode`**: every outbound request carries a wire `TrackingConfig` unconditionally (mode `OFF` included — this adapter always states what it wants; cv-service decides when to spend the detector). `mode`/`engineId`/`verifyEveryMillis`/`maxAgeFrames`/`minHits`/`capabilityLevel`/`reupdateMaxGapMillis` map 1:1; `redetectIouPercent` (domain `int` `[0,100]`) → `redetect_iou_threshold` (wire `float` ratio) via `/100f`, the one unit conversion. `followFps` has **no wire field** and is never sent — it is the Java-side sampler's own rate, not a cv-service knob. `lock` present → wire `TargetLock`; absent → `TrackingConfig.lock` left **unset**, not zero-valued present (`toWireTrackingConfig` is reused verbatim by `PulledDetectionSession.controlBuilder` for `PullControl.tracking`, so both transports get every field for free from one method).

**`decode`**: two independent mappings. **Per-detection** — wire `Detection` fields 4-9, `identity_confidence`/`dormant_millis` (fields 10-11) plus `reupdated` → `Detection.track()` (nullable `TrackRef`); `track_id == 0` always short-circuits to untracked, checked before any other track field; an `UNSPECIFIED`/`UNRECOGNIZED` `TrackState`/`DetectionSource` on an otherwise-tracked detection also decodes untracked — never a guessed state. `identity_confidence > 0` means this bind was recovered from cv-service's L4 follow memory, at that score; both fields read `0`/`0.0` for a fresh acquisition or for any response predating this capability (a pre-L4 server sends proto zeros) — decoded verbatim, never re-derived from `lockedTrackId` bouncing. **Per-frame** — wire `DetectionResponse` fields 8-12 plus 22-26 (`reupdate_millis`/`reupdated_tracks`/`detection_lag_millis`/`capability_level_served`/`capability_level_reason`) → `DetectionResult.tracking()` (nullable `TrackingTelemetry`); `null` iff **all ten** are simultaneously proto-zero (the shape a pre-tracking or pre-V3 cv-service produces — a modern server always reports `detector_ran`/`detector_reason` on every response, so this only actually happens against an old server). `capability_level_served == 0` means "never reported," not a level served — special-cased to `TrackingTelemetry.capability() == null` rather than constructing a `TrackingCapability` that would throw (`levelServed` validates `[1,5]`); a non-zero served level below whatever ceiling was requested decodes intact, never clamped. `detector_reason` is read only when `detector_ran` is true — otherwise ignored entirely (a tracker-only frame's `detector_reason` is legitimately meaningless on the wire); when `detector_ran` is true, an unset reason is a genuine contract violation and is **not guessed** — `TrackingTelemetry`'s own compact ctor rejects it, failing that one response's decode. A malformed track field (non-finite velocity, etc.) fails only that one frame's future via the same per-response catch every malformed field already used.

**No `maxInFlightInferences` concept exists anywhere in this module** — that bound (skip sampled frames past N concurrent in-flight `detect()` calls) is enforced entirely by `StreamPipeline` in vision-application, a different module; this adapter never blocks, queues, or caps pending futures per stream. **Nor does any demand-gating or stale-box-clearing logic live here** — whether detection is even wanted (`DetectionPolicyPort`/`DetectionDemandPort`, opt-in `DetectionPolicy.ALWAYS` vs. viewer demand) and when a stale overlay gets cleared are both `contexts/vision-perception`'s `StreamPipeline` concerns; this adapter transmits and decodes whatever it is asked to, unconditionally.

### The per-identity mirror
`DetectionFrameCodec#decode` maps `DetectionResponse.objects` (field 27) onto `DetectionResult#objects()` in a separate per-object try/catch loop (`toObjectStates`/`toObjectState`), independent of the `detections[]` mapping above it — a malformed `ObjectState` never touches `detections[]`, and a bad `detections[]` entry never touches `objects[]`. Group presence (`identity`/`kinematics`/`belief`/`provenance`/`memory`/`lock`/`timing`, and the three optional boxes inside `kinematics`) is checked with the generated `hasX()` and decodes to a `null` component when absent — never a zero-valued record, matching `ObjectState`'s own "absent means not computed, not off" contract. `Kinematics.box` is the one submessage field treated as required despite having wire presence: an absent `box` on a present `kinematics` group is rejected (`IllegalArgumentException`) rather than accepted as a phantom zero box, since the domain's `Kinematics#box()` must not be `null`.

Two enums are mapped by dedicated `private static` switch **expressions**, no `default` branch, `case X_UNSPECIFIED, UNRECOGNIZED -> null`, the same discipline `toTrackState`/`toDetectionSource`/`toDetectorReason` already use — `toObjectLifecycle`/`toEvidenceSource`. A `null` result from either (an unspecified/unrecognized `ObjectLifecycle` on the object itself, or an unspecified/unrecognized `EvidenceSource` on a *present* `provenance`) is folded into the same `IllegalArgumentException` funnel every nested record's own compact-ctor rejection already uses, so `toObjectStates`' single catch clause handles all three failure shapes uniformly: **drop only that one object**, log at WARNING naming the stream id, the object's wire id, and the exception message, and keep decoding the rest of `objects[]`. This never fails the whole frame — `detections[]` decodes exactly as before regardless of what `objects[]` contains, verified by a dedicated round-trip-identical test.

`ObjectState#streamId()` is always the `decode` call's own `streamId` parameter, never parsed off the wire per-object — there is no per-object stream id on the wire to parse in the first place (`ObjectState.stream_id` exists on the message but is not read; a mismatch there is exactly the class of thing `DetectionResponse.stream_id` checking, below, guards against at the response level instead).

### Frame ledger decode
`DetectionResponse.ledger` (field 28) is decoded by the private `toFrameLedger(StreamId, DetectionResponse)`, which returns `Optional.empty()` when `!response.hasLedger()` (a stream not currently under trace demand), else maps `response.getLedger()` field-for-field onto the domain `FrameLedger` — `entries` via `toLedgerEntry` (one `LedgerEntry` per wire entry, `toLedgerOutcome` a `null`-on-unspecified/unrecognized switch expression, same discipline as `toObjectLifecycle`), `objects` via a `LinkedHashMap<Long,List<ObjectEvidence>>` built off `wire.getObjectsMap()`, `detections` via `toDetectorBox` mapping each wire `TracedDetection` onto the domain `DetectorBox` (`label`/`confidence`/`box` only — no track fields exist on either side to carry), `frameWidth`/`frameHeight` copied straight across. **Unlike `toObjectStates`, a malformed ledger drops the WHOLE ledger** (one `try/catch(RuntimeException)` around the entire method, logged at WARNING), not just the offending entry/object — this is the warm debug tier only, never on the durable/live-overlay path, so losing one frame's trace to a decode error costs nothing a viewer of `detections[]`/`objects[]` would notice, and the coarse fallback is simpler than reproducing `toObjectStates`'s per-entry salvage for a tier where salvage buys nothing. `DetectionResult#ledger()` is fed straight into `contexts/vision-perception`'s `FrameLedgerRing` by `StreamPipeline#onDetectionResult` (that module's own MODULE.md). `wire.getDetectionsList()`/`getFrameWidth()`/`getFrameHeight()` are proto3 defaults (`[]`/`0`/`0`) on any response cv-service did not populate them on — untraced, or a pre-W5b cv-service — decoding straight through with no extra guard, the same "0/empty means not carried" contract the domain record itself states.

### `DetectionResponse.stream_id` checking
Both `DetectionStreamSession#onResponse` and `PulledDetectionSession#onResponse` compare the wire `stream_id` against their own session's `StreamId` (`streamId.value().toString()`) **before** doing anything else with the response. A non-empty, differing value is a mismatch: logged at WARNING naming both ids, and the response is dropped. An **empty** wire value is explicitly not a mismatch — "this server did not say," a legitimate older-peer shape this check must not break.

In `DetectionStreamSession`, the check runs *before* `pending.remove(sequence)` — a mismatched response leaves its future (if one is still pending for that sequence) untouched in the map, so it times out exactly like a sequence that genuinely never got any response, via that future's own `CompletableFuture#orTimeout` (armed independently of map membership back in `#send`). Removing the entry first would not shorten that timeout; it would only make a dropped response indistinguishable, for the map's own bookkeeping, from a real completion. In `PulledDetectionSession`, there is no pending-future concept to protect (see Pull mode) — the check runs before `decode`, and a mismatch is logged and dropped exactly like a malformed response, the session and publisher otherwise unaffected.

### Failure semantics — push detection (`GrpcDetectionPort#detect`)
- **Transport failure** (`onError`): every pending future for that stream fails immediately with the `StatusRuntimeException`, the session is dropped from the map. The next `detect()` for that `StreamId` transparently opens a fresh call — this is the mechanism a caller's own retry/backoff (vision-perception's `StreamPipeline`) depends on.
- **Server ends the stream normally** (`onCompleted`, no error): treated the same as a transport failure — a live bidi call is never expected to complete server-side on its own.
- **Hung/unreachable service, including a session opened while cv-service is down entirely** (no error, just silence): every pending future gets its own `responseTimeout` (2s default) via `CompletableFuture.orTimeout`. The timeout is **terminal for the whole session**, exactly like a transport error: the first future to time out cancels the call, fails every other pending future immediately, and drops the session — so the next `detect()` opens fresh rather than resending onto a call that may never produce a transport signal. A response arriving after its future's own timeout (or after teardown) is silently ignored.
- **Teardown is idempotent per session** (`AtomicBoolean torndown` CAS) — a timeout and a transport error racing each other resolve to exactly one teardown.
- **Design choice**: plain fail-fast RPCs (no `withWaitForReady()`), fresh call per probe after teardown — once any terminal signal unconditionally tears the session down, a kept-alive wait-for-ready call adds complexity for no benefit; the channel's own connectivity management does the reconnect work `StreamPipeline`'s probe cadence needs.
- **Unsupported `PixelFormat`**: fails fast with `IllegalArgumentException`, no session opened, no call made.
- **Malformed response** (a confidence/box/track value failing a domain record's compact ctor): caught per-response, fails just that one future — never affects other pending futures on the same session.
- **Port already closed**: `detect()` returns an already-failed stage without touching any session.

### Failure semantics — control-plane (`GrpcModelRegistryPort` / `GrpcTrainingPort` / `GrpcDatasetUploadPort`)
- `GrpcModelRegistryPort`: a transport failure or deadline exceeded propagates the raw `StatusRuntimeException` — **deliberately not degraded to an empty list**, since a caller must be able to tell "no models registered" from "couldn't reach cv-service." `promote()` refused (`Ack.ok=false`) throws `IllegalStateException` naming cv-service's own message. A malformed `ModelInfo` fails the whole `models()` call (no per-entry list, unlike `detect()`'s per-frame failures).
- `GrpcTrainingPort#startTraining`: a transport failure at any point propagates after every message already delivered to `onProgress`. The server ending the stream with no terminal `SUCCEEDED`/`FAILED` is **not an error** — `startTraining` returns normally; this is cv-service's documented cancellation behavior. A malformed `TrainingProgress` propagates `IllegalArgumentException` uncaught. If `onProgress` itself throws, the underlying call is **not** proactively cancelled (known minor gap — only thread interruption cancels it).
- `GrpcDatasetUploadPort#upload`: `Ack.ok=false` → `IllegalStateException`; transport failure/deadline → the raw `StatusRuntimeException` unwrapped; stream closed with no ack at all → `IllegalStateException` naming the dataset id; caller thread interrupted while awaiting the ack → `IllegalStateException` wrapping the `InterruptedException` (interrupt flag restored first). Known minor gap: a `RuntimeException` while writing the zip (not `IOException`) propagates straight out, bypassing the ack-await path — the caller sees this secondary symptom instead of the real terminal signal; not exercised by any test.

### Stream lifecycle
Chose the **explicit hook** over idle eviction: `streamEnded(StreamId)` fails any pending futures with `CancellationException`, half-closes the request observer (best-effort), drops the session — optional; an ended stream never told so just keeps its call open until `close()`. `streamEnded`/`close()` share the same `torndown` CAS guard as the timeout/transport-error paths, so any of these racing each other is exactly-once. Note: `CompletableFuture.get()` on a `streamEnded`-cancelled future throws `CancellationException` directly, not wrapped in `ExecutionException` — callers must catch the right type.

### Reconnect / gate design (`CvChannelSupervisor`)
**The problem**: a fail-fast RPC issued while the channel is `TRANSIENT_FAILURE` returns the cached failure immediately without triggering a new connect attempt — left alone, only the channel's own reconnect backoff (escalating towards ~120s) ever retries, so recovery time after cv-service comes back is unbounded. `CvChannelSupervisor` (one per shared `ManagedChannel`) watches connectivity and forces a *bounded* retry cadence; `GrpcDetectionPort#detect` (3-arg constructor only) consults `supervisor.available()` **before** encoding or touching the sessions map, so a known outage costs neither a downscale/encode nor a call. `GrpcPulledGeolocationPort` requires a supervisor unconditionally (see Visual geolocation); every other port in this module accepts no supervisor at all and is ungated.

**State machine — sticky-closed until `READY`, never reopens on `CONNECTING`:**
```
OPEN   --TRANSIENT_FAILURE-->  CLOSED
CLOSED --CONNECTING/IDLE-->    CLOSED   (reconnect churn)
CLOSED --READY-->              OPEN
OPEN/CLOSED --SHUTDOWN-->      CLOSED   (terminal)
```
`available()` is a separate sticky flag, not `state()==READY` — every reconnect cycles `TRANSIENT_FAILURE → CONNECTING → TRANSIENT_FAILURE`, and a gate reopening on `CONNECTING` would let one probe through per cycle. The gate starts, and stays, open until the first `TRANSIENT_FAILURE` is ever observed, so cold start never blocks a probe. `SHUTDOWN` is terminal — no reconnect loop is scheduled for it (`onShutdown` bumps `generation`, cancels the heartbeat, orphaning any running chain). `start()` applies the transition logic to the channel's **already-current** state before arming `notifyWhenStateChanged` (that callback only fires on a *change*), so a supervisor started against an already-`TRANSIENT_FAILURE`/`SHUTDOWN` channel closes the gate immediately rather than waiting for some later transition.

**Bounded recovery arithmetic**: while closed, the gate calls `resetConnectBackoff()` on its own schedule — wait `reconnectInitialBackoff` (1s default), force a reconnect attempt, double (capped at `reconnectMaxBackoff`, 10s default), repeat, indefinitely — there is no give-up state short of `SHUTDOWN`. Worst case cv-service-restart-to-gate-reopen is bounded by `reconnectMaxBackoff` itself, not gRPC's own escalation. A caller's own probe backoff (`StreamPipeline`, capped at 10s) then needs at most one more cycle to notice — **~20s bounded worst case end to end**.

**Generation-counter staleness guard**: the forced-reconnect chain and outage heartbeat are self-rescheduling tasks; each closure captures the `generation` (`AtomicLong`) live when scheduled and re-checks it before doing work or scheduling a successor. `onReady`/`onShutdown` both bump `generation`, orphaning any live chain instead of needing `ScheduledFuture#cancel()` to win a race it can't guarantee to win.

**Logging**: WARNING once entering an outage, INFO once on recovery (duration + attempt count), INFO heartbeat every `outageLogInterval` (60s default), each heartbeat itself generation-guarded so a tick firing just after recovery is silently skipped.

**Channel lifecycle**: `CvChannelSupervisor` never shuts the channel down — `close()` only stops its own watch loop and scheduler thread. `CvUnavailableException extends IllegalStateException` is genuinely stackless (`fillInStackTrace()` overridden to return `this` — `IllegalStateException` has no protected 4-arg ctor to chain a `(message, cause, false, false)` super call to) — a closed-gate rejection is expected and frequent during a real outage, not a bug worth a stack trace.

### Pull mode (`DetectPulled`), and which transport is live
The pull sibling of push (`DetectStream`/`GrpcDetectionPort`/`DetectionStreamSession`, described above) — the two never call each other and share no runtime state except the wire-mapping helpers in `DetectionFrameCodec` (`toWireTrackingConfig`/`toWireCameraPose`, package-private). The reconnect gate is push-only today — `GrpcPulledDetectionPort` takes no `CvChannelSupervisor`.

**Which transport is live**: `vision.cv.frame-transport` (`vision-app`, `VisionCvProperties`/`CvWiring`) selects the transport, default `push` — `GrpcDetectionPort`/`DetectStream` is the default live path for every stream. `GrpcPulledDetectionPort`/`DetectPulled` is wired instead when set to `pull`, or unconditionally when `vision.geo.visual.enabled` is `true` (visual geolocation always dials its own source and has no push counterpart).

**Why a sibling class, not a mode flag**: `DetectStream` is request→response, correlated by `sequence` in a future map. `DetectPulled` responses are **unsolicited** — the worker decodes and infers on its own schedule and mints `sequence` itself; there is no correlation map to build at all. Every response is decoded and pushed straight onto the session's `Flow.Publisher` in receipt order.

**What replaces correlation**: every `PullControl` restates the complete current desired state (same doctrine as `TrackingConfig` — cv-service's `LatestOnlyMailbox` can silently drop a message with no error). `reconfigure(StreamId, PipelineConfig)` and `attitude(StreamId, CameraAttitude)` are two independent methods called by different callers at different cadences (unlike push mode's `detect(frame, config, attitude)`, always together); `PulledDetectionSession` holds `volatile currentConfig`/`currentAttitude` and merges both into every outbound message.

**Wire mapping**: `stream_id` on every message; `source_url` on the first message only, never restated; `rtsp_transport` not set by this adapter (server default); `model_id`/`model_version`/`confidence_threshold`/`target_fps`/`detect_width`/`tracking` on every message once a config exists; `camera_pose` on every message once an attitude has been supplied; `stop` only in `endAndClose()`'s final message.

**Failure semantics**: transport failure → `SubmissionPublisher#closeExceptionally`, session dropped, **no internal retry** (reopen-with-backoff is deliberately the caller's job — `SupervisedPublisher<DetectionResult>` in vision-application). Server ending the call with no `stop=true` ever sent → same path (the shared `torndown` guard makes a server `onCompleted` racing this session's own `endAndClose()` a no-op instead of a spurious second failure). A malformed `DetectionResponse` — no pending future to fail, so it's logged at WARNING and dropped; session and publisher keep running. Backpressure: same latest-wins `offer(result, (sub, dropped) -> true)` policy every `VideoSourcePort` adapter uses.

**Dropped-frame / diagnostic reporting**: `DetectionResponse` fields 16-21 (`decode_millis`/`source_fps`/`achieved_fps`/`dropped_frames`/`missed_deadlines`/`capture_skew_millis`) are cv-service's per-frame pull-loop diagnostics, decoded onto `DetectionResult.pullTelemetry()` — see Gotchas for the one field (`dropped_frames`) that is no longer pull-exclusive on the wire and what that means for the decode.

### Visual geolocation (`LocalizeStream`/`BuildReferenceIndex`)
**The one pitch-sign conversion**: `Attitude.gimbalPitchDegrees()` is positive-up (aircraft convention: level=0, straight down=-90); cv-service's rectification wants degrees-from-nadir (straight down=0, level=90). `GeoFixCodec.toWireGeoTelemetry` performs `pitch_from_nadir = 90 + gimbalPitchDegrees` — the only place in this codebase this conversion happens.

**Gimbal-less fallback**: `gimbalPitchDegrees()` is populated only from MAVLink gimbal-attitude messages; an airframe with no gimbal sends neither, so the field stays `null` and `camera_pitch_deg` never reaches the wire at all. `GeoFixCodec` falls back to `Attitude.pitchDegrees()` (the airframe's own pitch) plus a configured fixed camera-mount offset (`vision.geo.visual.mount-pitch-degrees`, default 0.0), then applies the same `90 + pitch` conversion — deliberately **not** added to a real measured gimbal pitch, which is already earth-frame absolute. Result is deliberately unclamped — cv-service's own rectification gates on minimum pitch and degrades to `rectified=false` rather than fabricating a warp.

**Fields deliberately left absent on `GeoTelemetry`**: `gps_radius_meters` (no HDOP-to-meters conversion formula exists anywhere in this codebase — inventing one here would repeat the same refused invention `vision-flight`'s `DefaultTrackCorrectionService` already declined for its own `defaultRawRadiusMeters`, per CLAUDE.md rule 1) and `horizontal_fov_deg` (`GeoSessionConfig` carries no per-session hfov; `0`/absent on the wire already means "assume the region's default").

**`GrpcPulledGeolocationPort`'s required supervisor** — stricter than the detection ports because a geolocation session is long-lived (opened once per stream, held for its life), not per-frame; deferring the failure into the publisher's `onError` would make a caller wait out a full round trip to learn what the supervisor already knew.

**`GrpcReferenceIndexPort#build` is non-blocking by construction** — one `Thread.ofVirtual()` background thread per call does the archive-framing/upload; the response side owns delivering progress and closing the publisher (normally on the server's terminal message, exceptionally on transport error); the writer thread's own failure path also directly closes the publisher rather than waiting for gRPC to notice an abandoned call.

**`region.json`'s content is a documented choice, not a frozen schema** — neither the plan nor the proto names a field-level schema; cv-service validates it only as syntactically-valid JSON and reads just `name` (falling back to the region id). This adapter writes `region_id`/`name`/`zoom`/`bounds` for forward-compatibility/diagnostics; no code path depends on the extra fields.

**`IngestProgress.summary()` is left `null` even on the terminal `SUCCEEDED` update** — the wire's terminal message carries stats but no region identity/bounds/zoom/`built_at`; synthesizing the missing fields would be the same invented-data pattern refused elsewhere in this codebase. The one real consumer never reads this field anyway (it defers to `list()` once `SUCCEEDED` arrives).

**No `reconfigure`** — `GeolocationSession` is simpler than `PulledDetectionSession`: `GeoSessionConfig` is fixed for a session's whole life, only `telemetry` is a hot field. Malformed-`GeoFix` handling mirrors pull-detection's "never guess" posture: logged and dropped, session keeps running. A *refused* fix (`refusal` set, `position=null`) is delivered like any other response — `VisualFix`'s own contract, not an error.

## Conventions
- Plain classes, no Spring, no framework annotations.
- `System.Logger`, not `java.util.logging`/SLF4J directly: INFO on opening a stream, WARNING on unexpected completion/response timeout, DEBUG for a best-effort teardown-write failure. Transport-error WARNING logs the failure message plus gRPC status code only, not the full throwable (DEBUG) — during a real outage this fires once per reopened session per reconnect probe, and `CvChannelSupervisor`'s own WARNING/heartbeat already names the condition at the channel level.
- Field-by-field proto↔domain mapping, no shared DTOs. Several simple names collide between domain and generated-proto types (`Detection`, `BoundingBox`, `TrackingConfig`, `TrackingMode`, `TrackState`, `DetectionSource`, `DetectorReason`, `TargetLock`) — domain types are always imported unqualified (every signature uses them), proto types always fully-qualified at their handful of construction/switch sites in `DetectionFrameCodec`/`GeoFixCodec`.
- `ModelRef` for a mapped `Detection` comes from the *response*-level `model_id`/`model_version` (the wire `Detection` message itself carries none) — one `ModelRef` instance reused for every detection in a response.
- HTTP/2 keepalive (`keepAliveTime`/`keepAliveTimeout`/`keepAliveWithoutCalls` on `GrpcCvSettings`) is applied only on the real-transport `(host, port, GrpcCvSettings)` constructor's `ManagedChannelBuilder` — never on a bring-your-own-channel constructor (tests inject in-process channels, which have no meaningful keepalive concept).

## Gotchas
- **The root `pom.xml`'s `io.grpc:grpc-bom` import must stay declared before individual `grpc-netty-shaded`/`grpc-protobuf`/`grpc-stub` version pins.** Maven's first-declaration-wins rule for imported BOM entries is what makes this project's own bom import win over Spring Boot's own (transitively later) `grpc-bom` import, keeping the whole `io.grpc` family (including `grpc-core`, unpinned individually) on one version. Reordering it, or pinning `grpc-core` alone inside this module, silently re-skews `grpc-core` against `grpc-netty-shaded` and wedges a real `ManagedChannel` permanently in `CONNECTING` after any genuine TCP connect failure — with no exception surfaced anywhere (Netty swallows the resulting `NoSuchMethodError` inside its own listener-dispatch logging). Verify with `mvn -pl cv/grpc dependency:tree -Dverbose | grep grpc` if this is ever touched — every `io.grpc:*` line should resolve to the same version with no "(version managed from …)" note. The `grpc-inprocess` test dependency in this module's `pom.xml` is deliberately left unversioned so it resolves through this same bom — do not add an explicit pin.
- `FrameRequest`/`DetectionResponse` carry `timestamp_millis` as a `long`, so `VideoFrame.capturedAt()`'s sub-millisecond precision does not round-trip — harmless in production, but tests must build frames with a millis-truncated `Instant`.
- Proto `float` fields (`confidence`, `BoundingBox.x/y/width/height`) widen to `double` with normal float→double imprecision — compare with a delta, not `.equals()`.
- `pending.values().forEach(f -> f.completeExceptionally(cause))` (transport-error and `endAndClose` paths) relies on each future's own `whenComplete`-registered self-removal to drain the `pending` map — there is no separate `pending.clear()`.
- A closed-gate `detect()` failure (`CvUnavailableException`) is expected during a real outage and carries no stack trace by design — do not "fix" a missing stack trace on this exception.
- **`dropped_frames` (wire field 19) is no longer pull-mode-exclusive on the wire, but `toPullTelemetry`'s decode still treats it as if it were.** cv-service now increments this field under `DetectStream` too, from the same `LatestOnlyMailbox.dropped` counter push mode's own `_StreamReader` already maintains — not only under `DetectPulled`. `DetectionFrameCodec`'s `toPullTelemetry` decides "this is a pull response" by checking that all six diagnostic fields (16-21) are proto-zero; a push response that genuinely dropped a frame (`dropped_frames > 0`) but has the other five still at zero will fail that check and decode a non-`null` `PullTelemetry` on what is actually a push stream — a latent decode defect, not yet fixed or covered by a test. **It stays latent only because nothing reads `pullTelemetry()` on a push result** — `StreamPipeline#recordPullTelemetry` is reached solely from the pull-mode driver's subscriber, and no API or web surface reads the accessor. It becomes a live defect the moment a push path consults it, and the value it would see is actively wrong, not merely present: `PullTelemetry(0, 0f, 0f, n, 0, 0)` feeds `decodeMillis = 0` into `recordPullTelemetry`'s capacity ceiling. The fix belongs on the decode side — discriminate on the RPC that produced the response rather than on an all-zero field probe, since the wire no longer supports that inference. See `cv/cv-service/MODULE.md`'s own account of this field (API surface, `DetectionResponse`) for the server-side half.
- **`GrpcModelRegistryPort.CALL_TIMEOUT_SECONDS`/`GrpcReferenceIndexPort.CALL_TIMEOUT_SECONDS`/`GrpcCvInspectClient.CALL_TIMEOUT_SECONDS` are three independent constants** (10s, 10s, 5s) — not shared, and none routed through `GrpcCvSettings`.

## Status
Fully implemented and wired into `vision-app`: push detection (`GrpcDetectionPort`, gated by `vision.cv.enabled`), reconnect gate (`CvChannelSupervisor`), model registry, offline-training relay, dataset upload, system-status reporting (`CvStatusProvider`/`GrpcCvInspectClient`), pull-mode detection, visual geolocation (pull-mode fix streaming + reference-index ingest), and ordered multi-target failover (`CvTarget`/`CvChannels`, `vision.cv.inference.targets`/`.training.target`, both commented-out by default so an unconfigured deployment's channel is unchanged).

Known gaps: `ModelRef` cannot carry `stage`/`metrics` (frozen domain type — a future registry-detail REST endpoint needs a parallel read path); `PixelFormat.YUV420P` (simulation sources) is not sendable to cv-service today — `StreamPipeline` would need to convert before sampling, or this adapter would need a conversion step; `GrpcPulledDetectionPort` has no reconnect gate yet (push-only); `GrpcCvInspectClient#inspect(streamId, frames)`'s per-session ledger-history reply (`InspectResponse.ledgers`/`.session`) has no reader yet — only `processFacts()`'s process-wide shape is consumed; `toPullTelemetry`'s push/pull discriminator is stale against the current wire (see Gotchas).
