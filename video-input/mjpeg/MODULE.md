# adapter-mjpeg

MJPEG HTTP ingest (RX) and file-loop transmit simulator (TX) — `docs/main/CYCLES-PLAN.md` §5, the second protocol under the RX/TX doctrine (§0). Internally restructured per `docs/plans/active/LAYERING-REFACTOR-PLAN.md` §5.1/§7 (wave E4): TX split into HTTP-server-lifecycle / per-viewer-decode-encode-pace, plus a framework-free `MjpegSettings` covering every `vision.mjpeg.*` tunable.

**Depends on:** vision-domain, org.bytedeco:javacv, org.bytedeco:ffmpeg-platform-gpl (TX decode only — RX is pure JDK `java.net.http`/`com.sun.net.httpserver`, no native library) · **Used by:** *(none yet — vision-app wiring lands in a follow-up F1 task per the plan's §7 table, which also adds `VisionMjpegProperties`)*
**Build/test:** `./mvnw -B -pl video-input/mjpeg test` — 46 tests across 7 classes: `MjpegStreamParserTest` 14, `JpegDimensionsTest` 7, `MjpegSettingsTest` 3 (defaults pin every literal byte-identical + compact-constructor validation), `MjpegVideoSourceTest` 8 (incl. the h2c-header regression test and a settings-readTimeout-wiring test), `MjpegFeedTransmitterTest` 11 (incl. a `maxViewerThreads`-bound-pool smoke test), `MjpegRoundTripIntegrationTest` 3 (no docker — TX/RX round-trip in-process; default loop=true past file duration; a custom `transmit.loop=false` settings completes after one pass; a custom `transmit.jpeg-quality` measurably shrinks encoded frames). Verified via repeated live runs: 0 failures.

## API surface
### `com.drones.vision.adapter.mjpeg`
- `final class MjpegVideoSource implements VideoSourcePort` — RX. Supports protocol `"mjpeg"` with an `http`/`https` `StreamDescriptor.uri()`. `MjpegVideoSource()` (delegates to `MjpegSettings.defaults()`); `MjpegVideoSource(MjpegSettings)`. `supports(StreamDescriptor)`, `open(StreamId, StreamDescriptor): Flow.Publisher<VideoFrame>`, `close(StreamId)`.
  - Option: `timeout` — connect timeout in **milliseconds**, default `settings.readTimeout()` (lenient parse: missing/blank/malformed falls back to the default). Only bounds the initial TCP connect; once streaming, the connection is expected to stay open indefinitely (no request-wide timeout — see Gotchas).
  - nested `private static final class StreamRuntime` — one dedicated platform thread (`mjpeg-video-<id>`) per `open()`, running a blocking `java.net.http.HttpClient` synchronous GET + `MjpegStreamParser` read loop; feeds a `SubmissionPublisher<VideoFrame>` (buffer capacity from `settings.publisherBufferCapacity()`, drop-newest `offer`). Every extracted JPEG part is emitted as `PixelFormat.JPEG` **passthrough** (no decode) with `width`/`height` from `JpegDimensions.parse`; a part whose dimensions can't be determined is silently skipped (never fatal). A non-2xx HTTP status, connect failure, or malformed multipart framing surfaces once via `onError` and ends the loop (the port's "unrecoverable failure" contract — this loop simply ending *is* this adapter's self-close). `close()`: CAS-guarded idempotent, closes the live response body (unblocks a pending socket read) before interrupting + bounded-joining (`settings.closeJoinTimeout()`) the read thread.
- `final class MjpegFeedTransmitter implements FeedTransmitterPort, java.io.Closeable` — TX. `MjpegFeedTransmitter()` (delegates to `MjpegSettings.defaults()`); `MjpegFeedTransmitter(MjpegSettings)` — no target base to inject, unlike `adapter-rtsp`'s `RtspFeedTransmitter`; it serves its own ephemeral HTTP port. Supports `FeedSpec.protocol()` `"mjpeg"` with a `source()` whose URI scheme is `file`. `supports(FeedSpec)`, `start(FeedId, FeedSpec): StreamDescriptor`, `stop(FeedId)`, `close()`.
  - Option: `loop` — `"true"`/`"false"`, default `settings.transmit().loop()` (today `true` — opposite of `MjpegVideoSource`, same rationale as `RtspFeedTransmitter`: a transmitted simulation feed exists to be watched indefinitely).
  - Owns one `MjpegHttpServerHost` per transmitter *instance* (shared HTTP server, one per instance not per feed) and, per accepted viewer connection, one `MjpegViewerSession` (decode/encode/pace). `start()` returns `StreamDescriptor("mjpeg", http://<settings.transmit().bindHost()>:<port>/feed-<id>, Map.of())`.
  - `stop(id)`: idempotent; closes that feed's in-flight viewer exchanges + interrupts/bounded-joins (`settings.transmit().viewerJoinTimeout()` each) their grab-loop threads, removes the context — **does not** stop the shared server (a later `start()` may reuse it).
  - `close()`: stops every active feed, then delegates to `MjpegHttpServerHost.close()` (shuts down the shared server + dispatch pool). Idempotent, safe with zero feeds ever started.
  - nested `private static final class FeedRegistration` — per-feed bookkeeping (`activeExchanges`, `activeThreads`, both `ConcurrentHashMap.newKeySet()`); on each accepted connection, sets response headers (`Content-Type` from `MjpegViewerSession.CONTENT_TYPE`) and delegates the actual grab/decode/pace loop to a fresh `MjpegViewerSession`. Each viewer's handling thread is **temporarily renamed** `mjpeg-feed-<feedId>-<n>` for the duration of its request (restored in a `finally` block once the connection ends) — see Gotchas.
- `final class MjpegHttpServerHost` (package-private) — owns the shared `com.sun.net.httpserver.HttpServer` lifecycle: lazy start on first use (`ensureStartedPort()`), `createContext`/`removeContext`, and `close()` (the only path that actually stops the server + its dispatch `ExecutorService`). Dispatch pool: `Executors.newCachedThreadPool()` when `settings.transmit().maxViewerThreads()` is absent (today's unbounded default), else `Executors.newFixedThreadPool(n)` — either way the **default** (unprefixed) thread factory, so `mjpeg-`-prefixed thread assertions stay meaningful (see Gotchas).
- `final class MjpegViewerSession` (package-private) — one viewer's grab→decode→encode→pace→write loop: opens its own `FFmpegFrameGrabber` against the feed's source file, converts via `Java2DFrameConverter`, JPEG-encodes via an explicit `ImageWriter`/`ImageWriteParam` at `jpegQuality` (constructor parameter), and paces output at the source's native frame rate (duplicated timestamp-delta approach, see `adapter-rtsp`). `stream(OutputStream, BooleanSupplier stopRequested)` runs until EOF-and-not-looping or the stop signal fires. Also hosts the module's `ensureQuietLogging()` FFmpeg-log-level guard (called once, eagerly, from `MjpegFeedTransmitter`'s constructor). `CONTENT_TYPE` (package-private constant) is the full `multipart/x-mixed-replace; boundary=...` header value `FeedRegistration` sets.
- `final class MjpegStreamParser` (package-private, pure) — hand-rolled `multipart/x-mixed-replace` parser operating on any `InputStream`, no HTTP/network dependency, unit-testable with a plain `ByteArrayInputStream`. `MjpegStreamParser(String boundaryToken)`; `static MjpegStreamParser forContentType(String contentTypeHeaderValue)`; `static String extractBoundaryToken(String contentTypeHeaderValue)`; `static String normalizeBoundaryToken(String raw)` (strips quotes and any leading `--` a non-conformant server may already have embedded); `byte[] nextPart(InputStream in)` — returns the next part's raw JPEG bytes, or `null` at a clean end (EOF or an explicit `--boundary--` marker). Uses `Content-Length` when a part declares it (exact read via `InputStream.readNBytes`, correctly looping over short/fragmented reads); scans forward for the next boundary when absent. Does no internal buffering — callers should wrap their raw stream in a `BufferedInputStream` for efficiency.
- `final class JpegDimensions` (package-private, pure) — `static int[] parse(byte[] jpeg)`: walks the JPEG marker chain to find the `SOF0`(`0xC0`)/`SOF2`(`0xC2`) start-of-frame marker and reads its declared width/height directly (big-endian, 1-byte precision then 2-byte height then 2-byte width) **without decoding any pixel data**. Returns `null` for anything not a well-formed/complete-enough JPEG (missing SOI, truncated before SOF, entropy-coded data (`SOS`, `0xDA`) reached with no SOF seen first).
- `record MjpegSettings(Duration readTimeout, int publisherBufferCapacity, Duration closeJoinTimeout, Transmit transmit)` — framework-free, compact-constructor validated, `static defaults()` reproduces every literal this module hardcoded before this record existed. Nested `record Transmit(String bindHost, OptionalInt maxViewerThreads, float jpegQuality, boolean loop, Duration viewerJoinTimeout)`, `static defaults()`. `maxViewerThreads` empty = unbounded (today's `newCachedThreadPool()`; there was never a literal cap to preserve — same "absent = today's behavior" idiom as `adapter-v4l2`'s optional driver-default fields).

## Conventions
- Plain classes, no Spring — instantiated directly by `vision-app`'s wiring configuration (a later task; not wired anywhere yet). Neither adapter class imports a `Vision*Properties` type (per `LAYERING-REFACTOR-PLAN.md` §1.3 rule 5) — `vision-app` will map its own properties record onto `MjpegSettings` in the follow-up F1 wave.
- Every tunable both classes use flows through `MjpegSettings`/`MjpegSettings.Transmit`, injected as a single constructor argument; each class also keeps a no-arg convenience constructor (`this(MjpegSettings.defaults())`) so existing call sites/tests are unaffected until `vision-app` wiring lands — this mirrors the multi-constructor idiom already used by `adapter-cv-grpc`'s `GrpcDetectionPort`.
- RX has **no FFmpeg/native dependency at all** — it is pure `java.net.http` + the hand-rolled parser, matching `docs/main/CYCLES-PLAN.md` §5's "transparent, dependency-free" requirement. TX is the only half that touches JavaCV/FFmpeg (file decode), hence the module still needs the `javacv`/`ffmpeg-platform-gpl` dependencies.
- `MjpegViewerSession`'s real-time pacing (timestamp-delta sleep) and `ensureQuietLogging()` guard are **deliberately duplicated** (not shared) from `adapter-rtsp`'s `FfmpegVideoSource`/`RtspFeedTransmitter` and `adapter-publish-hls`'s `MediamtxStreamPublisher` — per `CLAUDE.md`'s rule that adapters never depend on each other.
- Lenient option parsing throughout (`timeout`, `loop`): missing/blank/malformed values silently fall back to the settings default, same idiom as every other adapter in this codebase.
- Idempotent close/stop via `AtomicBoolean` CAS everywhere (`MjpegVideoSource.StreamRuntime`, `MjpegFeedTransmitter.FeedRegistration`, `MjpegHttpServerHost` guarded by its own lock, and `MjpegFeedTransmitter` itself via its `feeds` bookkeeping).

## Gotchas
- **RX forces `HTTP_1_1` on its `HttpClient`.** The JDK default (HTTP/2 preferred) adds `Upgrade: h2c` + `HTTP2-Settings` headers to plain-`http://` requests; embedded MJPEG servers (real-world ESP32-CAM, 2026-07-23) reject those with `400 Bad Request` even though browsers/curl work against the same URL. Do not remove the explicit version pin. Related field note: ESP32-CAM's stream endpoint serves ~one client at a time and can wedge (accepts TCP, never answers) when stale half-closed connections pile up — a device power-cycle clears it; not something this adapter can fix.
- **RX sets no request-wide HTTP timeout, only a connect timeout.** `HttpRequest.Builder.timeout(Duration)` bounds the *entire* exchange including body reads — setting it would kill a legitimately infinite MJPEG stream after that duration. Only `HttpClient.Builder.connectTimeout` is used; a server that accepts the TCP connection but then never sends headers can still hang past the configured connect timeout's nominal budget (mitigated only by `close()`'s explicit stream-close + thread interrupt).
- **Testing "connection refused" is racy against a just-stopped `com.sun.net.httpserver.HttpServer`** in this environment: binding an `HttpServer`, calling `stop(0)`, and immediately connecting to that same port was empirically observed to still succeed at the TCP level (the OS accept backlog appears to outlive `stop(0)`'s return by a few ms), leaving the client waiting forever for HTTP headers that never arrive. `MjpegVideoSourceTest` instead connects to `192.0.2.1` (TEST-NET-1, RFC 5737, guaranteed unroutable) to reliably exercise the connect-timeout/`onError` path — do not reintroduce the stop-and-reuse-the-port pattern for this kind of test.
- **TX's per-viewer thread rename is deliberate and load-bearing for thread-leak tests.** `MjpegHttpServerHost`'s dispatch pool always uses the JDK's **default**, unprefixed thread factory (whether cached or fixed-size) specifically so its pool threads never start with `mjpeg-`; only the temporary rename inside `FeedRegistration#handle` (restored in `finally`) uses that prefix. This means a thread dump (or a test asserting no `mjpeg-`-prefixed thread remains) reflects genuinely active per-feed/per-stream work, never idle HTTP infrastructure threads that `stop(id)` intentionally leaves alive (see below).
- **`stop(FeedId)` never shuts down the shared `HttpServer`** — only `close()` (via `MjpegHttpServerHost.close()`) does. A transmitter instance that has stopped every one of its feeds still holds its ephemeral port and dispatch thread pool open, ready for a future `start()`. Callers that want the port fully released (e.g. end of a test, or JVM shutdown wiring in the later task) must call `close()`.
- **`MjpegViewerSession` now explicitly sets JPEG compression quality** via `ImageWriter`/`ImageWriteParam` (`MODE_EXPLICIT` + `setCompressionQuality(jpegQuality)`) instead of the old bare `ImageIO.write(image, "jpg", out)`. `MjpegSettings.Transmit.defaults().jpegQuality()` is `0.75f` because that is the standard JPEG writer's own implicit default — verified byte-identical output at the default setting; only a non-default `jpegQuality` changes encoded bytes (see `MjpegRoundTripIntegrationTest`'s quality-wiring test).
- **`MjpegSettings.Transmit.maxViewerThreads()` has no literal default to preserve** (`OptionalInt.empty()` = unbounded `newCachedThreadPool()`, today's actual behavior) — unlike every other field in this record, its "default" is the *absence* of a bound, not a number. A production concern flagged, not fixed here (E-phase is internal-only, no behavior change): the unbounded default means a malicious or buggy client opening unbounded concurrent viewer connections against one feed has no built-in ceiling; the follow-up F1 wave should consider whether `VisionMjpegProperties` should ship a non-empty default once this is wired into `vision-app`.
- **JavaCV/FFmpeg decode is still guarded only by `MjpegViewerSession`'s own grabber lifecycle** — no cross-viewer/cross-adapter static lock is taken (unlike `adapter-rtsp`'s documented FFmpeg static-lock gotcha), because each viewer owns an independent `FFmpegFrameGrabber` against a local file (fast, bounded I/O) rather than a live network source that could hang indefinitely; a wedged file open here would still only block that one viewer's own thread, never the shared server.
- **JPEG dimension parsing intentionally covers only `SOF0`/`SOF2`** (baseline and progressive), per the task spec, not the full `SOF0`–`SOF15` family. `ImageIO`'s built-in JPEG writer (used by both `adapter-simulation` and this module's TX side) always emits baseline (`SOF0`), so this covers every JPEG this platform itself produces; a real ESP32-CAM's JPEGs are also baseline in practice.
- `MjpegStreamParser` is stateful per connection (tracks whether the stream position is already parked right after a just-scanned boundary token) — a single instance must only ever be driven by one `InputStream` for one connection's lifetime, exactly like `adapter-rtsp`'s per-open `StreamRuntime`/`FeedRuntime` are never shared across opens. Same rule now applies to `MjpegViewerSession`: not reusable across viewer connections.
