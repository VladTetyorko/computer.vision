# adapter-rtsp — history

Wave-by-wave narrative. Current contract lives in [`MODULE.md`](MODULE.md); this file only explains *why*, with dates/branches/test counts where the source material had them.

## docs/plans/active/LAYERING-REFACTOR-PLAN.md — wave E1

Internal restructuring only, no behavior change. The pre-split 912-line `FfmpegVideoSource` was split five ways:
- `FfmpegSettings` — new public record, every environment/tuning literal this module previously scattered across `private static final` constants on `FfmpegVideoSource`/`RtspFeedTransmitter`. `static defaults()` reproduces every one of those old literals exactly — a structural move, not a retune. A nested `Transmit` record covers `RtspFeedTransmitter`'s own encoder tunables.
- `FfmpegGrabberOptions` — new package-private class, the promoted `configureRtspOptions`/`configureSrtOptions`/`configureUdpOptions` option seams plus a new `newGrabber` factory; still holds every FFmpeg AVOption name/protocol-vocabulary constant (out of config-extraction scope per §1.3), now takes an `FfmpegSettings` parameter for every default value.
- `FfmpegGrabLoop` — new package-private class, the promoted former nested `private static final class StreamRuntime` (it was already `static`, so this was a physical file move, not a behavior change — zero references back to the `FfmpegVideoSource` instance that created it). Owns its own `System.Logger`: the WARN-on-open-failure log (see MODULE.md Gotchas) now logs under `FfmpegGrabLoop`'s class name instead of `FfmpegVideoSource`'s — the only observable, non-test-asserted difference from the move.
- `RealtimePacer` — new package-private class, the timestamp-delta real-time pacing logic that was previously duplicated verbatim between `FfmpegVideoSource`'s grab loop and `RtspFeedTransmitter`'s transmit loop; both now share one instance-per-loop implementation (intra-module sharing, not a cross-adapter dependency).
- `FfmpegVideoSource` — narrowed to ~130 lines: `supports`/`open`/`openAny`/`close` plus the shared `ensureQuietLogging()` guard. Gained an additive `FfmpegVideoSource(FfmpegSettings)` constructor; the pre-existing no-arg constructor is unchanged (`this(FfmpegSettings.defaults())`).
- `RtspFeedTransmitter` gained an additive `RtspFeedTransmitter(URI, FfmpegSettings)` constructor (the pre-existing one-arg constructor is unchanged); its encoder settings and thread-join timeout now read from `FfmpegSettings`/`FfmpegSettings.Transmit` instead of five separate `private static final` constants, and its transmit loop now uses the shared `RealtimePacer` instead of a duplicated inline pacing block. `vision-app`'s two call sites (`new FfmpegVideoSource()`, `new RtspFeedTransmitter(properties.mediamtx().rtspBase())`) were not touched and still compile — neither constructor overload was removed.

Two module tunables were deliberately **not** promoted into `FfmpegSettings`, flagged rather than silently decided: `FfmpegGrabberOptions.DEFAULT_UDP_OVERRUN_NONFATAL` (a fixed survive-vs-abort posture, not a scalar the frozen `vision.rtsp` key table names) and the SRT `pbkeylen` pin (living documentation of libsrt's own already-built-in default — a protocol/spec constant per §1.3, not a deployment choice). One genuine literal *collapse* happened alongside the moves: `FfmpegSettings#transport()` now feeds both the RX side's `rtsp_transport` default and the TX side's previously separately-hardcoded `"tcp"` push transport, and `FfmpegSettings#closeJoinTimeout()` now feeds both halves' previously-identical-but-separate 20s thread-join bound.

A later wave (§7, F1) adds a Spring `VisionRtspProperties` record in `vision-app` and binds it to `FfmpegSettings` — out of scope for this wave, and this module gained no Spring dependency doing this work.

**Tests**: `./mvnw -B -pl video-input/rtsp clean test`, run twice consecutively: **48/48 green, 0 failures, 1 skipped** (`FfmpegVideoSourceLiveManualTest`, `@Disabled` by design), docker IT (`MediamtxDockerIntegrationTest`) ran and passed both times. New: `FfmpegSettingsTest` (8 methods — `defaults()` reproduces every pre-existing literal exactly, `microsOption` conversion, compact-ctor validation for both the outer record and `Transmit`), `RealtimePacerTest` (3 methods — first-call-never-sleeps, a real ~100ms-delta sleep with a generous lower bound only, `reset()` behaves like a fresh instance). Moved (production code moved, tests followed, import/reference updates only — same assertions): the 9 RTSP-V-c/SRT/UDP option-seam unit tests from `FfmpegVideoSourceTest` into new `FfmpegGrabberOptionsTest`, now calling `FfmpegGrabberOptions.configure*Options(..., FfmpegSettings)` instead of the old `FfmpegVideoSource.configure*Options(...)` static methods and comparing against `FfmpegSettings.defaults()`'s fields instead of the old `DEFAULT_*` string constants. `FfmpegVideoSourceTest` itself now covers only real-loopback/end-to-end `open()`/`openAny()` behavior (12 methods, down from 21 — the difference is exactly the 9 moved tests).

## docs/plans/active/DRONE-INFRA-PLAN.md — wave A (I-h)

`FfmpegVideoSource#supports` extended to accept `srt`/`udp` (scheme must match the protocol string, unlike `rtsp`'s any-URI acceptance); `configureSrtOptions`/`configureUdpOptions` added, gated strictly by `uri.getScheme()` the same way `configureRtspOptions` already was.

**SRT option verification**: every AVOption name/default was checked against this module's actual pinned `ffmpeg-platform-gpl` 6.1.1-1.5.10 native binary — extracted the published jar, grepped `libavformat.so.60`'s strings for `SRTO_LATENCY`/`SRTO_PASSPHRASE`/`SRTO_STREAMID`/the `caller`/`listener`/`rendezvous` mode constants (all present, confirming `--enable-libsrt`), not assumed from FFmpeg's own docs. `setOption` vs. the `srt://` URL's query string were both actually tried; `setOption` was kept for one idiom across rtsp/srt/udp. A standalone probe confirmed `setOption` genuinely reaches the SRT protocol's own private AVOptions in this exact JavaCV/FFmpeg build: setting `mode=listener` via `setOption` measurably reached the SRT listener accept code path, not the caller-connect path.

**UDP wedging — a genuine production finding, not just a test flake**, found in three escalating stages while developing `udpMpegtsLoopbackDeliversAtLeastOneFrame`:
1. UDP has no protocol-level EOF. A first draft sent a fixed 30-frame (~1.5s) burst then closed the sender, which reliably left the receiver's native `avformat_find_stream_info` blocked on a `read()` that would never be satisfied again. Not a production concern by itself (a real encoder streams continuously). Fixed in the test by streaming continuously (bounded by `MAX_LOOPBACK_SENDER_FRAMES`=400 frames at `LOOPBACK_SENDER_FRAME_INTERVAL_MILLIS`=50ms pacing, up to ~20s) until the receiver confirms a frame, rather than a fixed burst.
2. The severe finding: `FFmpegFrameGrabber`/`FFmpegFrameRecorder#start()` both synchronize on a shared, static, process-wide lock (the `avcodec` class object) for their entire native call — verified via a real thread dump. With only the stage-1 fix, a full `mvn test` run of this class occasionally left a later, completely unrelated test method permanently blocked (`jstack` showed it waiting on that exact lock, held by a udp receiver thread stuck inside `avformat_open_input` with `bytes read:0`). Fixed in production code: `configureUdpOptions` now always applies FFmpeg's own `timeout` AVOption (default `FfmpegSettings#udpTimeout()`=5s — `DEFAULT_UDP_TIMEOUT_MICROS`="5000000" pre-LAYERING-REFACTOR §5.1, verified present in this build's binary strings: `"set raise error timeout, in microseconds (only in read mode)"`).
3. The `timeout` fix's own sharp edge: it removes the demuxer's patience for a receiver that starts *before* any data has arrived. Verified via a verbose (`AV_LOG_DEBUG`) standalone reproduction: with `timeout` set, an idle receiver's `avformat_find_stream_info` can return almost immediately with `"Did not find a video or audio stream"` rather than waiting out its own budget. Fixed in the test (legitimately test-harness sequencing, not a production gap) by starting the sender first and waiting for a `started` signal before opening the receiver, retried up to `UDP_LOOPBACK_MAX_ATTEMPTS`=3 times as a further defensive margin.

**Net effect, verified**: `./mvnw -B -pl video-input/rtsp clean test`, run three times consecutively — 37/37 green, 0 failures, 1 skipped, ~22-28s total each time (down from single runs occasionally taking 95s+ with a failure, and one early draft that genuinely wedged the whole forked JVM for 10+ minutes, requiring a manual `kill -9`).

**SRT listener deadlock**: a first draft of the SRT test opened a real `srt://0.0.0.0:<port>` listener alongside a continuously-streaming caller sender, mirroring the udp loopback test. That listener open reliably hit libsrt's own defensive native error `"no sockets to check, this would deadlock"` and never returned, holding the shared lock forever — confirmed via `jstack` to cascade into a later, completely unrelated test method stalling indefinitely (needed a manual `kill -9` to recover). Investigation establishing this as an environment/library interop issue, not this task's code:
1. `--enable-libsrt` confirmed in the bundled binary's own recorded build config string; `srt` confirmed as a registered runtime protocol via `avio_enum_protocols`.
2. Both option-application mechanisms compared — `setOption("mode","listener")` and an equivalent `srt://…?mode=listener` URL query string — hit the identical failure, which is itself informative: it shows `setOption` genuinely reaches the SRT protocol's own private AVOptions in this build (the listener code path is actually reached, not silently falling back to caller).
3. Explicit `127.0.0.1` vs. `0.0.0.0` listener hosts, and swapping which JavaCV class played the listener role, made no difference.
4. A completely independent, non-JVM `ffmpeg` CLI process pair (the Ubuntu system package, not this module's bundled dependency) on the same machine completed a full `srt://` listener+caller round trip successfully, ruling out a machine-wide network/firewall/epoll restriction (this machine has full capabilities/no sandboxing, confirmed via `/proc/1/status`).
5. A JVM-hosted grabber-as-**caller** against that same real external listener also failed (`avformat_open_input() error -5`), but — unlike the listener path — failed *fast*, and this module's own `udp://` loopback (stage 2 above) reliably succeeds via the exact same JVM-hosted mechanism, ruling out something generically wrong with JVM-hosted JavaCV networking.

Given the demonstrated severity (a whole-class-wedging risk, not just one flaky test), the SRT test does not attempt a live listener open in this JVM at all — `srtCallerConnectAttemptReachesRealFfmpegSrtCodeAndFailsCleanlyWhenNobodyIsListening` (`FfmpegVideoSourceTest`) exercises only the caller role.

**New test methods (8)**: `supportsSrtAndUdpOnlyWithAMatchingSchemeUri`; `configureSrtOptionsAppliesDefaultsAndInfersListenerModeForAnAnyAddressHost`, `configureSrtOptionsInfersCallerModeForARealHost`, `configureSrtOptionsHonorsDeviceOptionOverridesAndSetsPbkeylenWhenAPassphraseIsGiven`; `configureUdpOptionsForcesMpegtsFormatAndAppliesLowLatencyDefaults`, `configureUdpOptionsHonorsDeviceOptionOverrides`; `udpMpegtsLoopbackDeliversAtLeastOneFrame`; `srtCallerConnectAttemptReachesRealFfmpegSrtCodeAndFailsCleanlyWhenNobodyIsListening`.

**Honesty note carried forward**: an ad hoc local A/B check found `setFormat("mpegts")` just as reliable as auto-probing on this module's quiet loopback test (5/5 either way) — the explicit format hint was kept on contract-correctness grounds (docs/plans/active/DRONE-INFRA-PLAN.md I-h assumes MPEG-TS for `udp`), not a measured reliability delta on a real lossier/jitterier link.

## docs/plans/done/MVP2-PLAN.md — V-c (+ RX-side open-failure observability)

**V-c: RTSP demuxer latency tuning.** Scope: `rtsp` protocol only, `file` untouched (`fileProtocolNeverReceivesRtspDemuxerTuning` pins that contract directly against a real `FFmpegFrameGrabber`'s untouched defaults). The task brief asked to tighten several demuxer options; this wave found and corrected two errors in that brief's own framing, verified by reading real FFmpeg 6.1.1 source fetched during the task (`libavformat/options_table.h`, `demux.c`, `rtsp.c`), not assumed from blog-post folklore:
1. The "several-second RTSP default" is real, but belongs to `analyzeduration` (unset → 5s, **7s specifically for mpegts payload** via `avformat_find_stream_info`), not `max_delay`. Bounding it to 1s here was the single biggest change in this wave.
2. `max_delay`'s own RTSP-specific default is already a modest 100ms (`libavformat/rtsp.c`'s `DEFAULT_REORDERING_DELAY`) — the brief's suggested "500ms, down from a 7s default" would have *loosened*, not tightened, this specific value (the real 7s figure belongs to `analyzeduration`'s mpegts branch). `FfmpegSettings#maxDelay()` was set to 100ms as living documentation against a future FFmpeg version silently changing `DEFAULT_REORDERING_DELAY`, not as a further tightening.

Options changed (all via the same device-option-override idiom as the pre-existing `rtsp_transport`/`timeout`): `probesize` 5,000,000→32768 bytes (`setOption`), `analyzeduration` 5-7s→1s (`setOption`), `reorder_queue_size` adaptive (0 under tcp / 500 under udp) →0 explicit (`setOption`), `max_delay` 100ms implicit→100ms explicit (`setMaxDelay` — confirmed via JavaCV's own source that `setOption` would be silently overwritten here).

**Tests**: run twice consecutively, **29/29 green, 0 failures, 1 skipped** both times — `FrameConverterTest` 8, `FfmpegVideoSourceTest` 13 (9 pre-existing + 4 new: `configureRtspOptionsAppliesDefaultLowLatencyDemuxerTuning`, `configureRtspOptionsHonorsDeviceOptionOverrides`, `configureRtspOptionsFallsBackToDefaultMaxDelayOnAMalformedOverride`, `fileProtocolNeverReceivesRtspDemuxerTuning`), `RtspFeedTransmitterTest` 6 (unchanged, `file`-only, untouched by this task), `MediamtxDockerIntegrationTest` 1 (docker-gated, confirmed actually running against a real mediamtx container both runs — this is what exercises the new RTSP RX options against a genuine live RTSP connection end-to-end).

**Same wave, RX-side open-failure observability**: found investigating a real "frozen video" report — a dead RTSP-loopback simulation feed. Before this fix, `FfmpegVideoSource.StreamRuntime#runGrabLoop`'s catch block (an unrecoverable `grabber.start()`/`grabImage()` failure) only called `publisher.closeExceptionally(e)`, with zero application-level logging anywhere in this class. `vision-application`'s `SupervisedPublisher` (§S-a) retries such a failure forever with 1s→30s backoff and logs nothing itself either — so a permanently-dead source (e.g. a TX feed transmitter that never came back after a JVM restart, see `DefaultSimulationService`'s own Gotcha in `contexts/vision-simulation/MODULE.md`) produced an endless, silent retry loop: the only visible symptom was FFmpeg's own native stderr (suppressed to `AV_LOG_ERROR` by `ensureQuietLogging`) and a repeating 404 nobody could see in application logs. Fixed by adding a `LOG` field and a WARN-per-failed-attempt with a `consecutiveOpenFailures` counter (current-state description: MODULE.md Gotchas). Does **not** fix the underlying "nothing re-publishes a dead TX feed" gap — see `contexts/vision-perception/MODULE.md`'s own Gotcha for the actual root cause. Re-ran: **29/29 green, 0 failures, 1 skipped** (unchanged counts — no new tests added, consistent with this codebase's existing precedent of not unit-testing `System.Logger` output text itself, e.g. adapter-publish-hls's V-c lag logging).

## docs/main/CYCLES-PLAN.md — C1 (file RX) / C3 (RtspFeedTransmitter TX)

This doc lives at `docs/main/`, not `docs/plans/<active|done>/` — it predates the `docs/plans/` convention and is the original doctrine/build reference for this module's TX/RX split, so it is cited here by its real path rather than forced into the `docs/plans/...` heading pattern.

Original build of the module's two halves, establishing the doctrine still in force today: every protocol adapter has an RX and a TX half. **RX** — `file` protocol (C1): FFmpeg decode of a local file, looped, real-time paced, giving a zero-hardware simulated drone. **TX** — `RtspFeedTransmitter` (C3): the first full TX/RX pair, pushing a file loop to mediamtx so this module's own RX half (or any real RTSP client) ingests it exactly like live hardware; simulation infrastructure, not egress, unrelated to `StreamPublisherPort` (viewer-facing egress). Why TX exists: zero-hardware demos, E2E tests of the full protocol path (encoder → wire → demuxer → pipeline), and operator rehearsal ("replay yesterday's flight as if it were live"). Entry-point principle (KISS): simulating a drone is one call/one dialog — a video file path (+ optional home lat/lon) → a registered, categorized, optionally already-streaming asset, no manual device/descriptor plumbing. §1b: a source loops only when explicitly asked — the simulation layer is the one that asks explicitly.

**TX/RX same-process contention** (see MODULE.md Gotchas for the current-state description) was found while exercising this C3 pairing outside the module's own checked-in tests: a from-scratch minimal repro confirmed the RX side alone (no TX in-process) and the TX side alone (no RX in-process) both run cleanly for 12+ seconds; only the combination, in one process, stalls. `vision-app`'s eventual `transport=rtsp` wiring (§3) will run both halves in one process by design, so that wiring task should budget time for the short-RX-timeout workaround or further investigation.
