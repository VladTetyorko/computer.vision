# adapter-rtsp

FFmpeg ingest **and** transmit adapter (IP cameras, drone companions, and local-file simulation) via JavaCV/FFmpeg. Despite the module name (kept for historical/build reasons), it covers:
- **RX** (`VideoSourcePort`), via `FfmpegVideoSource`: `rtsp` (real RTSP/RTP cameras), `file` (a local video file played back as a simulated live source — drone simulation with zero hardware), `srt` (SRT, low-latency drone video over lossy cellular/long-range links, docs/plans/active/DRONE-INFRA-PLAN.md I-h) and `udp` (raw UDP/MPEG-TS, the classic ground-station/encoder output, same doc).
- **TX** (`FeedTransmitterPort`, `docs/main/CYCLES-PLAN.md` §0/§3): pushes a local video file to a real RTSP target (e.g. mediamtx) so this module's own RX half (or any real RTSP client) ingests it like live hardware — simulation infrastructure, not egress — via `RtspFeedTransmitter`.

**Depends on:** vision-domain, org.bytedeco:javacv, org.bytedeco:ffmpeg-platform-gpl · **Used by:** vision-app
**Build/test:** `./mvnw -B -pl video-input/rtsp test` — `FrameConverterTest`, `FfmpegVideoSourceTest` (real-loopback/end-to-end `open()`/`openAny()`), `FfmpegGrabberOptionsTest` (per-protocol option-seam unit tests — applies grabber options without calling `start()`, no live server needed), `FfmpegSettingsTest`, `RealtimePacerTest`, `RtspFeedTransmitterTest`, `MediamtxDockerIntegrationTest` (docker-gated genuine TX→wire→RX round trip through both halves; skips cleanly without docker), `FfmpegVideoSourceLiveManualTest` (`@Disabled` by design — no live camera/RTSP server in CI, see its class javadoc to re-enable manually).

## API surface
### `com.drones.vision.adapter.rtsp`

Every public constructor is either the module's original signature or a pure-addition overload — no protocol/option/default behavior differs between the two.

- `final class FfmpegVideoSource implements VideoSourcePort` (~130 lines — the thin `VideoSourcePort` entry point only) — supports protocol `"rtsp"` (any URI) and `"file"`/`"srt"`/`"udp"` (URI scheme must itself match the protocol string — `supports()` checks `uri.getScheme()` for these three, unlike `rtsp` which accepts any URI). `supports(StreamDescriptor)`, `open(StreamId, StreamDescriptor): Flow.Publisher<VideoFrame>`, `close(StreamId)`.
  - `FfmpegVideoSource()` — uses `FfmpegSettings.defaults()`; the constructor `vision-app`'s wiring calls.
  - `FfmpegVideoSource(FfmpegSettings settings)` — additive overload for constructor-injecting tunables; not yet wired by `vision-app` (planned: docs/plans/active/LAYERING-REFACTOR-PLAN.md §7 F1 adds a Spring `VisionRtspProperties` binding).
  - **Listen vs. dial** (docs/plans/active/DRONE-INFRA-PLAN.md I-h): `rtsp` always dials out (the app connects to the camera). `file` opens a local path (neither). `srt` dials out as `caller` (default) or binds/listens as `listener` when `mode=listener` is given or inferred. `udp` always binds/listens — UDP is connectionless, so opening `udp://host:port` for reading means "receive datagrams sent to this host:port", never "connect to a remote peer".
  - package-private test seam: `Flow.Publisher<VideoFrame> openAny(StreamId id, URI uri, Map<String,String> options)` — runs the exact production grab loop (via `FfmpegGrabLoop`) against any URI (skips the protocol check), letting tests exercise the real FFmpeg decode path against a local file.
  - package-private constants `PROTOCOL_RTSP`/`PROTOCOL_FILE`/`PROTOCOL_SRT`/`PROTOCOL_UDP` and `OPTION_LOOP`/`DEFAULT_LOOP` — shared within the module by `FfmpegGrabberOptions`/`FfmpegGrabLoop` (registry dispatch keys).
  - `static synchronized void ensureQuietLogging()` — idempotent native-log-quieting guard; `RtspFeedTransmitter` calls this directly rather than duplicating it.
- `final class FfmpegGrabberOptions` (package-private, static-methods-only, ~400 lines incl. javadoc) — every per-protocol `FFmpegFrameGrabber` option/default seam. Every FFmpeg AVOption *name* (`OPTION_RTSP_TRANSPORT`, `OPTION_SRT_MODE`, `SRT_MODE_CALLER`/`SRT_MODE_LISTENER`, `OPTION_UDP_FIFO_SIZE`, ...) lives here as a constant (registry/protocol vocabulary); every tunable **default value** comes from an injected `FfmpegSettings` parameter.
  - `static FFmpegFrameGrabber newGrabber(URI uri, Map<String,String> options, FfmpegSettings settings)` — the single grabber-construction entry point `FfmpegGrabLoop` uses; dispatches to the three `configure*Options` methods below by `uri.getScheme()`, or applies none for `file`.
  - package-private test seam: `static void configureRtspOptions(FFmpegFrameGrabber grabber, Map<String,String> options, FfmpegSettings settings)` — applies every RTSP-only grabber option without calling `start()`, so a test can assert exactly what a real grabber would be started with, no live camera/RTSP server needed. Mirrors adapter-publish-hls's `MediamtxStreamPublisher.configureRecorder` seam.
  - package-private test seam: `static void configureSrtOptions(FFmpegFrameGrabber grabber, URI uri, Map<String,String> options, FfmpegSettings settings)` — applies every SRT-only grabber option, same no-`start()` idiom.
  - package-private test seam: `static void configureUdpOptions(FFmpegFrameGrabber grabber, Map<String,String> options, FfmpegSettings settings)` — applies every UDP-only grabber option plus forces `setFormat("mpegts")`, same no-`start()` idiom.
  - RTSP options (all optional, defaults sourced from `FfmpegSettings`, applied only when `uri.getScheme()` is `"rtsp"`):
    - `rtsp_transport` (default `FfmpegSettings#transport()`="tcp") and `timeout` in **microseconds** (default `FfmpegSettings#openTimeout()`=10s; applied to both the RTSP demuxer's `timeout` option and the generic `rw_timeout` option) — `rtsp_transport` is a **hard-forced** transport choice, not a soft `rtsp_flags=prefer_tcp` preference; this module never sets `rtsp_flags` at all.
    - `loop` (`"true"`/`"false"`, default `false`, `FfmpegVideoSource.DEFAULT_LOOP` — a business default, not a `FfmpegSettings` tunable; malformed values fall back to the default, same lenient idiom as every other option here) — on graceful EOF (`grab()` returns `null`) with `loop=true` and no stop requested, the grabber is **restarted** (`FFmpegFrameGrabber.restart()`, i.e. `stop()`+`start()`, which reopens the file from the beginning) instead of completing the publisher; the frame `sequence` keeps climbing monotonically across restarts, it is never reset. Default `false` — a source loops only when explicitly asked (docs/main/CYCLES-PLAN.md §1b).
    - **RTSP-only low-latency demuxer tuning, never applied to `file` sources** (all four affect one-time connect-time stream-info probing only, not steady-state decode once streaming has started): `probesize` bytes (default `FfmpegSettings#probesizeBytes()`=32768, vs. FFmpeg's own 5,000,000-byte default), `analyzeduration` microseconds (default `FfmpegSettings#analyzeDuration()`=1s — FFmpeg's own unset default resolves to 5s, **and up to 7s specifically when the payload is detected as mpeg/mpegts**, a common RTSP payload for IP cameras/drone companions; this is the actual multi-second RTSP-connect-stall lever, not `max_delay` below), `reorder_queue_size` packets (default `FfmpegSettings#reorderQueueSize()`=0 — under this module's `rtsp_transport=tcp` default, FFmpeg's own adaptive logic already resolves an unset value to `0`, so pinning it is a no-op for today's behavior; it matters only if a device override ever sets `rtsp_transport=udp`, where FFmpeg's unset default is 500 packets — pinning `0` favors latency over reorder tolerance for that case too), `max_delay` microseconds (default `FfmpegSettings#maxDelay()`=100ms — **applied via `FFmpegFrameGrabber.setMaxDelay(int)`, not `setOption`**, see Gotchas; FFmpeg's own RTSP-specific unset default already resolves to the same 100ms `DEFAULT_REORDERING_DELAY`, so this pins rather than tightens FFmpeg's own already-conservative jitter tolerance). All four follow the same device-option-override idiom as `rtsp_transport`/`timeout` (`options.getOrDefault(key, default)`), with lenient malformed-value fallback (`FfmpegGrabberOptions.intOption`) for `max_delay`'s integer parse specifically, since it must reach an `int`, not a string option.
  - **SRT options** (docs/plans/active/DRONE-INFRA-PLAN.md I-h, `configureSrtOptions`, only applied when `uri.getScheme()` is `"srt"`) — this module's pinned `ffmpeg-platform-gpl` 6.1.1-1.5.10 native binary confirms `--enable-libsrt` (every AVOption name below verified present in `libavformat.so.60`, not assumed from FFmpeg's docs):
    | Option | Maps to | Default | Notes |
    |---|---|---|---|
    | `latency` | FFmpeg `latency` AVOption | `FfmpegSettings#srtLatency()`=120ms | **Unit conversion**: this module's option is milliseconds (docs/plans/active/DRONE-INFRA-PLAN.md I-h's contract unit); FFmpeg's own `latency` AVOption is **microseconds** — `configureSrtOptions` multiplies by 1000 before calling `setOption`. 120ms matches libsrt's own built-in default exactly. |
    | `mode` | FFmpeg `mode` AVOption (`caller`/`listener`) | inferred via `defaultSrtMode(URI)`: `listener` for an any-address host (`0.0.0.0`/`::`/unset), `caller` otherwise | Only `caller`/`listener` exposed (not FFmpeg's third `rendezvous`) per the frozen contract. |
    | `streamid` | FFmpeg `streamid` AVOption | none (absent = unset) | Pure passthrough. |
    | `passphrase` | FFmpeg `passphrase` AVOption | none (absent = no encryption) | Pure passthrough; when set, `configureSrtOptions` also sets FFmpeg's `pbkeylen` AVOption to `DEFAULT_SRT_PBKEYLEN`="16" (a fixed `FfmpegGrabberOptions` constant, **not** promoted into `FfmpegSettings`) — not strictly required (libsrt already defaults an unset `pbkeylen` to 16 bytes when a passphrase is set) but pins the key length as living documentation rather than relying on an unstated library default. |
    - `loop` is accepted but has no useful effect for `srt` (a live source has no bounded content to restart from).
    - **Applied via `setOption`, not the `srt://` URL's query string** — both are documented FFmpeg mechanisms; this module chose `setOption` for one idiom across rtsp/srt/udp. Verified that `setOption` actually reaches the SRT protocol's own private AVOptions in this exact JavaCV/FFmpeg build (a `mode=listener` set via `setOption` measurably reached the SRT listener accept code path, not the caller-connect path — see the SRT Gotcha below).
  - **UDP/MPEG-TS options** (docs/plans/active/DRONE-INFRA-PLAN.md I-h, `configureUdpOptions`, only applied when `uri.getScheme()` is `"udp"`):
    | Option | Maps to | Default | Notes |
    |---|---|---|---|
    | `fifo_size` | FFmpeg `fifo_size` AVOption (packets of 188 bytes) | `FfmpegSettings#udpFifoSizePackets()`=512 (~96KB) | vs. FFmpeg's own unset default of 7×4096=28,672 packets (~5.4MB) — tightened for latency, same intent as the RTSP tuning above. |
    | `overrun_nonfatal` | FFmpeg `overrun_nonfatal` AVOption | `FfmpegGrabberOptions.DEFAULT_UDP_OVERRUN_NONFATAL`="1" (true; a fixed posture, **not** promoted into `FfmpegSettings`) | vs. FFmpeg's own default `false` — a full receive ring buffer survives (drops) instead of aborting the whole stream. |
    | `buffer_size` | FFmpeg `buffer_size` AVOption (OS `SO_RCVBUF`, bytes) | none (absent = OS default) | Pure passthrough — a system-level knob this module has no basis to override by default. |
    - **Format always forced to `mpegts`** via `FFmpegFrameGrabber.setFormat("mpegts")` — a raw `udp://` URL carries no container self-description the way `rtsp://`'s SDP `DESCRIBE` does, so an explicit hint removes format auto-detection as a failure mode entirely; docs/plans/active/DRONE-INFRA-PLAN.md I-h's contract already assumes MPEG-TS for `udp`.
    - **An internal `timeout` AVOption (default `FfmpegSettings#udpTimeout()`=5s) is always applied and is *not* one of the three options above** — not exposed via `StreamDescriptor#options()`, a safety default only. A genuine production-robustness fix, not a test convenience — see the Gotcha below ("a udp source can wedge every other video source in the process").
    - `loop` is accepted but has no useful effect for `udp` (same reasoning as `srt`).
- `final class FfmpegGrabLoop` (package-private — one dedicated grab thread per `open`; zero references back to the `FfmpegVideoSource` instance that created it — every dependency, including `FfmpegSettings`, is passed in through its own constructor) — one dedicated platform thread (`rtsp-video-<id>`, not virtual — decoding is CPU-bound) per open, running a blocking `FFmpegFrameGrabber` loop via `FfmpegGrabberOptions.newGrabber`; feeds a `SubmissionPublisher<VideoFrame>` built with `FfmpegSettings#publisherBufferCapacity()`=4 and `publisher.offer(frame, (subscriber, dropped) -> true)` for drop-newest backpressure. Computes `loop`/`paced` once per open (constructor) from the descriptor's options/URI scheme. Owns its own `System.Logger` (WARN-on-open-failure log, see Gotchas). `close()` joins its grab thread bounded by `FfmpegSettings#closeJoinTimeout()`=20s.
  - **Real-time pacing (`file` URIs only)**, via the shared `RealtimePacer` (below): a local file decodes as fast as disk I/O allows, but a simulated drone must feed frames at the file's own rate, like a live camera. Whenever `uri.getScheme()` is `"file"`, the grab loop calls `pacer.paceTo(grabber.getTimestamp())` every frame; `pacer.reset()` on every loop restart, so the first frame of each pass is never delayed. `rtsp`/`srt`/`udp` URIs are never paced — the network already paces a live source.
- `final class RealtimePacer` (package-private, stateful, not thread-safe — one instance per grab/transmit loop) — the timestamp-delta real-time pacing logic shared between `FfmpegGrabLoop` (`file` sources) and `RtspFeedTransmitter`'s transmit loop. `void paceTo(long timestampMicros)` — sleeps the difference between the media-timestamp delta and the wall-clock time actually spent since the previous call, clamped to zero (never a negative sleep); the first call after construction or `reset()` never sleeps. `void reset()` — call after a loop restart (e.g. `loop=true` on EOF), since the restarted media's timeline starts over too.
- `record FfmpegSettings(...)` (public — every environment/tuning literal this module uses; docs/plans/active/LAYERING-REFACTOR-PLAN.md §2.2's frozen `vision.rtsp` property-key contract) — plain, framework-free, compact-constructor validated (non-blank `transport`, positive durations/counts, non-null `transmit`). `static FfmpegSettings defaults()`: `transport`="tcp", `openTimeout`=10s, `probesizeBytes`=32768, `analyzeDuration`=1s, `reorderQueueSize`=0, `maxDelay`=100ms, `udpTimeout`=5s, `udpFifoSizePackets`=512, `srtLatency`=120ms, `publisherBufferCapacity`=4, `closeJoinTimeout`=20s, and a nested `Transmit` record (`gopSeconds`=2, `preset`="ultrafast", `fallbackFps`=15.0, `connectTimeout`=5s, `tune`="zerolatency") for `RtspFeedTransmitter`-only tunables. `static String microsOption(Duration)` — converts a duration to the whole-microsecond decimal string every microsecond-resolution FFmpeg AVOption in this module expects.
  - `transport` feeds both `FfmpegGrabberOptions.configureRtspOptions`'s RX-side `rtsp_transport` default **and** `RtspFeedTransmitter`'s TX-side hardcoded push transport (one field, two consumers); `closeJoinTimeout` likewise feeds both `FfmpegGrabLoop` and `RtspFeedTransmitter`'s `FeedRuntime` thread-join bound.
  - **Two module tunables deliberately not promoted here** (a judgment call, flagged for the next reader rather than silently decided): `FfmpegGrabberOptions.DEFAULT_UDP_OVERRUN_NONFATAL` (a fixed survive-vs-abort posture, not a scalar the frozen §2.2 key table names) and the SRT `pbkeylen` pin (living documentation of libsrt's own already-built-in default — a protocol/spec constant, not a deployment choice). Both stay as named constants in `FfmpegGrabberOptions` next to the option they configure.
- `final class FrameConverter` (package-private, stateless) — `static ByteBuffer copyBgr24(Frame frame)`: copies a JavaCV `Frame`'s BGR24 pixel data into a fresh, tightly-packed heap `ByteBuffer` (strips row stride padding). Throws `IllegalArgumentException` for null frame, missing image data, invalid dimensions, non-3-channel data, or a non-byte-backed image buffer.
- `final class RtspFeedTransmitter implements FeedTransmitterPort` — `supports(FeedSpec)`: protocol `"rtsp"` and `spec.source()` scheme `file`. `start(FeedId, FeedSpec)`: validates the source file exists/is readable (`IllegalArgumentException` otherwise, synchronously — the only blocking part), then starts one dedicated platform thread (`rtsp-feed-<id>`) and returns immediately with `StreamDescriptor("rtsp", <rtspTargetBase>/feed-<id>, Map.of())` — does not wait for the first frame to reach the wire. `stop(FeedId)`: idempotent, CAS-guarded, interrupt + bounded (`FfmpegSettings#closeJoinTimeout()`=20s) thread join.
  - `RtspFeedTransmitter(URI rtspTargetBase)` — uses `FfmpegSettings.defaults()`; the constructor `vision-app`'s wiring calls (e.g. `rtsp://localhost:8554`).
  - `RtspFeedTransmitter(URI rtspTargetBase, FfmpegSettings settings)` — additive overload for constructor-injecting encoder/timeout tunables; not yet wired by `vision-app`.
  - Options: `loop` (`"true"`/`"false"`, **default `true`** — the opposite of `FfmpegVideoSource`'s default `false`, because a transmitted simulation feed exists to be watched/rehearsed indefinitely; same lenient malformed-value-falls-back-to-default parsing idiom).
  - Real-time pacing: shares `RealtimePacer` with `FfmpegGrabLoop`'s own `file`-source pacing.
  - Encoder settings deliberately duplicated from `adapter-publish-hls`'s `MediamtxStreamPublisher` (adapters must not depend on each other): format `"rtsp"`, `rtsp_transport`=`FfmpegSettings#transport()`, `timeout`=`FfmpegSettings.Transmit#connectTimeout()`=5s, codec `AV_CODEC_ID_H264`/`"libx264"`, `preset`=`FfmpegSettings.Transmit#preset()`="ultrafast", `tune`=`FfmpegSettings.Transmit#tune()`="zerolatency", pixel format `AV_PIX_FMT_YUV420P`. **Deviation:** frame rate/GOP are derived from the source file's own reported frame rate (`grabber.getFrameRate()`, falling back to `FfmpegSettings.Transmit#fallbackFps()`=15.0 fps if unusable) rather than `MediamtxStreamPublisher`'s fixed 15fps, and no explicit per-frame `setTimestamp` call is made — the recorder's own auto-incrementing per-`record()`-call PTS is collision-free by construction here (unlike `MediamtxStreamPublisher`, which must reconcile an arbitrary/bursty upstream cadence against a fixed nominal rate).
  - GOP = `round(frameRate * transmit.gopSeconds())`, `gopSeconds`=2 (same constant as `MediamtxStreamPublisher`) — i.e. one keyframe roughly every 2 real seconds, **regardless of source file loop length**; see Gotchas for why this matters to RX-side test/consumer code.
  - `ensureQuietLogging()` is **not** re-duplicated a third time: the constructor calls `FfmpegVideoSource.ensureQuietLogging()` directly — both classes live in this same module/package, so this is intra-module reuse, not the cross-adapter-module dependency the duplication rule guards against.

## Conventions
- Plain classes, no Spring — instantiated directly by `vision-app`'s wiring config (`WiringConfiguration#ffmpegVideoSource`).
- **Logging: `System.Logger`, not SLF4J** — `private static final System.Logger LOG = System.getLogger(...)`, matching every other adapter in this codebase (e.g. `adapter-publish-hls`'s `MediamtxStreamPublisher`). `FfmpegGrabLoop` owns the RX-side `LOG` field.
- Grab loop uses **`grabber.grabImage()`, never `grab()`** (both `FfmpegGrabLoop` and `RtspFeedTransmitter`; `adapter-mjpeg`'s transmitter does the same): `grab()` also returns audio/data frames, and mp4 muxers interleave audio up to ~0.5s *ahead* of video — pacing on those look-ahead timestamps slept until wall-clock caught up with the audio track, starving a real 30fps AAC-carrying clip down to ~2 emitted fps (regression-tested against a fixture with a muxed silent AAC track: `fileWithAudioTrackIsPacedByVideoTimestampsNotStalledByAudioLookahead`). `grabImage()` skips non-video packets, so pacing sees only the video track's monotonic timeline. Loop runs until `stopRequested` or `grabImage()` returns `null` (graceful EOF, unless `loop=true` restarts).
- `close()`: sets `stopRequested`, interrupts the grab thread (best-effort — native `grab()` may not respond, and a paced source may be mid-sleep, resolved on the next loop iteration), joins up to `FfmpegSettings#closeJoinTimeout()`=20s, releases the grabber, closes the publisher. Idempotent via `AtomicBoolean closed`.
- **Native FFmpeg log level pinned to ERROR**: `FfmpegVideoSource`'s no-arg constructor calls the idempotent package-private `static void ensureQuietLogging()`, which calls `avutil.av_log_set_level(avutil.AV_LOG_ERROR)` once per JVM (a `synchronized` static-boolean guard makes every call after the first a no-op). This silences FFmpeg's default AV_LOG_INFO chatter (codec/format banners) *and* AV_LOG_WARNING noise — the driver for ERROR over WARNING is swscale's benign per-frame `deprecated pixel format used, make sure you did set range correctly` spam whenever yuvj-tagged media (MJPEG streams, many mp4s) is decoded, which JavaCV's high-level API cannot avoid per-context; native errors still print. Deliberately duplicated in `adapter-publish-hls`'s `MediamtxStreamPublisher` (adapters must not depend on each other) — see that module's MODULE.md Gotchas for the empirical reasoning behind choosing plain `av_log_set_level` over `org.bytedeco.javacv.FFmpegLogCallback.set()`. `RtspFeedTransmitter` reuses this same guard directly (`FfmpegVideoSource.ensureQuietLogging()`) rather than duplicating it a third time.
- `adapter-publish-hls`'s in-code comment still refers to this class by an old pre-rename name (`RtspVideoSource`, not `FfmpegVideoSource`) — stale, flagged here so it isn't mistaken for a real second class.

## Gotchas
- **RX-side open-failure visibility**: every unrecoverable open/grab failure (e.g. an RTSP `DESCRIBE` 404 against a path nothing is publishing to) logs one `WARNING` from `FfmpegGrabLoop` — `"Video source error for stream <id> at <uri> (consecutive failure <n>); will be retried with backoff by the stream supervisor, dropping frames until it recovers"`, with the causing exception attached — via a local `Map<StreamId, AtomicInteger> consecutiveOpenFailures` (a logging aid only, not a supervision mechanism: this class has no idea what backoff delay the caller is actually using). Reset to zero the moment `grabber.start()` succeeds, removed entirely on an explicit `close(StreamId)`. `vision-application`'s `SupervisedPublisher` (docs/plans/done/MVP2-PLAN.md §S-a) retries a failed `open()` forever with 1s→30s exponential backoff and logs nothing itself — this WARN is the only application-log-level signal of a permanently-dead source. This does **not** fix "nothing re-publishes a dead TX feed" — see contexts/vision-perception/MODULE.md's own Gotcha for that root cause.
- **Mandatory copy**: `FFmpegFrameGrabber` reuses its native image buffers across `grab()` calls. Every grabbed frame's payload MUST be copied via `FrameConverter.copyBgr24` before being wrapped in an immutable `VideoFrame` (whose compact constructor stores the buffer for the record's lifetime) — never hand out the raw `Frame#image` buffer directly.
- Backpressure is drop-**newest**-on-full via `SubmissionPublisher.offer(..., onDrop -> true)` with a buffer capacity of only 4 — a slow subscriber never blocks capture, per `VideoSourcePort`'s latest-wins contract.
- First FFmpeg-touching test in a fresh module pays real cost for native library extraction — `FfmpegVideoSourceTest.AWAIT_SECONDS`=60 is deliberately generous for exactly this reason; once extracted, runs are fast (~2s for the whole class in this environment, most of it the pacing test's deliberate real-time waits).
- `resolveFilename(URI)` special-cases the `file:` scheme (via `Paths.get(uri)`) for both the `openAny` test seam and the real `"file"` protocol — the same code path serves both.
- **Pacing and loop both key off `uri.getScheme()`/options, not the descriptor's `protocol()` string** — `openAny` (used by every FFmpeg-path test, and indirectly by `open()`) computes `paced` from `uri.getScheme().equals("file")` directly, so a `"file"`-protocol descriptor and a raw `file:` URI passed through the test seam behave identically.
- `FFmpegFrameGrabber.restart()` (used for `loop=true`) is JavaCV's own `stop()`+`start()`; `stop()` fully releases the native `AVFormatContext` and `start()` reopens from the constructor-set filename, so it naturally reopens a file at position 0 — no manual seek/rewind needed.
- The pacing test (`fileSourceIsPacedToItsNativeFrameRate`) only asserts a generous **lower** bound on wall-clock time (0.5× the frame-rate-implied duration) — deliberately never asserts an upper bound, since CI scheduling jitter must not flake the test.
- **Running `RtspFeedTransmitter` (TX) and `FfmpegVideoSource` (RX) concurrently in the same JVM process against the same mediamtx path triggers same-process JavaCV/FFmpeg native contention.** With the RX side left at its default RTSP `timeout`/`rw_timeout` (10s), the transmitter's grab/record loop silently stalls for ~10s (matching the RX side's configured timeout, not the TX's own 5s `connectTimeout`) before mediamtx drops the now-stale publisher connection ("i/o timeout") and the transmitter's next `record()` fails with `av_interleaved_write_frame() error -32` (EPIPE) — reproduced via a standalone harness outside this module's own test suite (not checked in as an automated test). Reducing the RX side's `timeout` option (e.g. to `"2000000"` = 2s) reliably eliminates it; `MediamtxDockerIntegrationTest` demonstrates the fix by passing an explicit short `timeout` option on the RX-side `StreamDescriptor`. This matters once RX+TX run together in one process (not yet true of `vision-app`'s wiring, planned per `docs/main/CYCLES-PLAN.md` §3) — budget time to apply the same short-RX-timeout workaround, or investigate further (see `bytedeco/javacv#1063` for a related report of hangs when multiple recorders/grabbers interact under connection trouble).
- **Mid-GOP RX connects are normal, not a bug**: `RtspFeedTransmitter`'s encoder emits a keyframe only once per `FfmpegSettings.Transmit#gopSeconds()`=2 real seconds, regardless of how short the looped source file is. An RX side that connects between keyframes will log transient `decode_slice_header`/"Missing reference picture" warnings until the next keyframe arrives and decoding self-heals — expected RTSP-viewer behavior, not a failure. Test/consumer code must **not** react to "no frames yet" by tearing down and reopening the subscription impatiently: doing so restarts the wait against a new, differently-phased mid-GOP landing and can never land on a keyframe at all if the reconnect cadence and the GOP period fall into a synchronized "beat frequency". Stay on one subscription for the full timeout budget instead; only reopen on a genuine `onError`/`onComplete`.
- **`max_delay` must go through `setMaxDelay(int)`, not `setOption`.** Verified against JavaCV 1.5.10's own source (`FFmpegFrameGrabber#startUnsafe`): `max_delay` is a real, generic FFmpeg AVOption that a `setOption("max_delay", ...)` call *would* apply during `avformat_open_input` — but JavaCV unconditionally overwrites it immediately afterwards with `oc.max_delay(this.maxDelay)`, its own `maxDelay` Java field (default `-1`), silently discarding anything set the `setOption` way. `probesize`/`analyzeduration`/`reorder_queue_size` have no such dedicated setter in JavaCV and no post-open override, so `setOption` is correct (and the only option) for those three. Anyone adding a new demuxer/grabber option to this module should check JavaCV's own source the same way before assuming `setOption` is sufficient.
- **A `udp` source with nobody ever sending it a packet can wedge every *other* video source in the same JVM process.** `FFmpegFrameGrabber`/`FFmpegFrameRecorder#start()` synchronize on a shared, static, process-wide lock (the `avcodec` class object) for their entire native call — confirmed via a real thread dump. UDP has no protocol-level EOF/connection signal, so a receiver's native `avformat_find_stream_info` blocks on a `read()` that may never be satisfied; since this module's stream supervisor retries a failed `open()` indefinitely (1s→30s backoff), a udp source that never receives a single packet (misconfigured, or a drone that never powers on) would, without a bound, hold that lock on every retry, silently blocking every *other* video source's own open/reconnect attempts in the same `vision-app` JVM. **Fixed**: `configureUdpOptions` always applies FFmpeg's own `timeout` AVOption (default `FfmpegSettings#udpTimeout()`=5s, not exposed via `StreamDescriptor#options()` — a safety bound only), making a dead/silent udp source fail cleanly within ~5s instead of blocking forever. **Sharp edge of that fix**: it also removes the demuxer's patience for a receiver that starts *before* any data has arrived — an idle receiver's `avformat_find_stream_info` can return almost immediately with `"Did not find a video or audio stream"` rather than waiting out its own budget for the sender to start, unlike the old unset/block-forever default. A real drone/encoder is already streaming before the app connects to it, so this is not a production gap, but anything that opens a udp receiver before its sender exists must account for the fast-fail. Given the shared process-wide lock, **any new protocol/option added to this module should treat "does a `start()` failure mode exist that can block indefinitely" as a mandatory question** — an unbounded block in *any* one stream's native open call is not a local problem, it is a whole-process one.
- **A JVM-hosted SRT *listener* open via JavaCV does not complete in this development environment, and a stuck one poisons the same process-wide JavaCV lock as the udp Gotcha above.** Opening a real `srt://0.0.0.0:<port>` listener reliably hits libsrt's own defensive native error `"no sockets to check, this would deadlock"` (from its epoll-wait helper) and never returns, holding the shared lock forever. This is a native/environment interop issue, not a bug in this module's option-application code (`setOption` itself is confirmed reaching the SRT protocol's own private AVOptions correctly — see the SRT options table above); a completely independent, non-JVM `ffmpeg` CLI process pair on the same machine completes a full `srt://` listener+caller round trip successfully, ruling out a machine-wide network/firewall restriction. SRT's own `listen_timeout` AVOption exists but would **not** have prevented this specific failure — it is a native defensive error that fires early, not a genuine timeout being exceeded. **Consequence**: this module deliberately never opens a live SRT listener in its own test suite or in any harness in this environment; only the caller role is exercised live (`srtCallerConnectAttemptReachesRealFfmpegSrtCodeAndFailsCleanlyWhenNobodyIsListening` in `FfmpegVideoSourceTest`, a caller against a nothing-listening port, which fails cleanly and fast). This means there is currently **no automated coverage of a full SRT round trip actually delivering a frame** in this environment — `configureSrtOptions`'s own option-application correctness (including `mode` inference) is still fully covered by unit tests that touch no network. Anyone revisiting this should re-verify with the same `jstack`-during-a-full-class-run technique before trusting a live SRT listener test again, since the failure mode (whole-suite wedge) is easy to miss running the SRT test in isolation.
