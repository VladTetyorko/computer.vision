# MVP2 — from demo to daily tool

Companion to [ARCHITECTURE.md](../../../ARCHITECTURE.md), [CYCLES-PLAN.md](../../main/CYCLES-PLAN.md) (delegation model, TX/RX doctrine, UI personas all apply unchanged). MVP1 ([MVP1-PLAN.md](MVP1-PLAN.md)) is complete.

**Milestone:** the platform stops being a one-session demo. It survives a restart with its fleet and history intact, plays back yesterday's flight, streams to the browser with sub-second latency, ingests a real webcam and real MAVLink telemetry, and tells the operator when something interesting was seen — while the UI gets *simpler*, not busier.

Themes (user-set + proposed):

1. **UX finish & polish** — the three pending UI cycles are MVP2's front door, not leftovers: CU-b (fast & simple + map layers), CD-b (asset-first devices + self-recovering player + crisp vector boxes), CT-b (flight-plan map editor).
2. **New connection protocols** — per the §0 TX/RX doctrine, each lands as a pair: MAVLink telemetry (the first *real drone* protocol), USB/V4L2 cameras (real hardware with zero network), WebRTC egress (viewer side — sub-second latency vs HLS's multi-second lag).
3. **Something more** — persistence (Postgres finally does work; fleet + history survive restarts), flight replay (map + telemetry scrub over a recorded usage), detection events & alerts (the CV vertical starts *telling* you things, geolocated on the map).

## U-info — user-needed info, not plumbing *(user feedback 2026-07-23, folded into U2/E-b)*

- **Session facts:** started → *duration* (live-ticking), usage link.
- **Share:** copyable view URL (the HLS/WHEP link), not internal ids.
- **Errors where the user is looking:** pipeline errors (e.g. "camera returned HTTP 400") next to the player, not only in server logs — the events feed (E-b) is the mechanism; until then the player state chip (U2 item 5) covers connectivity.
- IDs/URIs stay reachable in a collapsed "Technical details" disclosure (debugging still matters, it's just not the front door).

## L — low-latency viewing (WebRTC/WHEP)

mediamtx already serves WebRTC (WHEP) for every published path — the backend only has to *say so*. `StreamPublisherPort`'s view-URL surface gains a WHEP URL beside the HLS one (`/api/streams` + asset/stream DTOs); compose/host ports documented. Player work happens in U3: try WHEP first (sub-second), fall back to HLS automatically; state chip shows which transport is live. **Estimate: L-a S, player part folded into U3.**

**L-a done** — `StreamPublisherPort#whepUrl(StreamId): Optional<URI>` (default empty, mirroring `viewUrl`), implemented by `MediamtxStreamPublisher` (formats `{whepViewBase}/{streamId}/whep`, mediamtx needs no extra per-stream config to serve it) and surfaced as `whepUrl` on `StartStreamResponse`/`ActiveStreamResponse`/`SimulationResponse` (nullable/omitted exactly like `viewUrl`, independently). New property `vision.publish.mediamtx.whep-base` (default `http://localhost:8889`, host-mode default `http://localhost:18889` in `application.properties`, mirroring `rtsp-base`/`hls-base`'s naming). One correction to the brief's framing: **WHEP is not proxied like HLS is** — `HlsProxyController`'s reverse-proxy trick only works because HLS is a plain byte-fetch protocol; WHEP is a POST/SDP + ICE exchange that a stateless proxy cannot forward, so `whepUrl` is always mediamtx's own absolute origin URL, never app-relative — this is a deliberate, documented asymmetry with `viewUrl`, not a gap. `docker-compose.yml` maps `18889:8889` (WHEP HTTP) and a mandatory 1:1 `8189:8189/udp` (ICE media — cannot be renumbered, mediamtx bakes its listening port into the ICE candidates it sends) plus `MTX_WEBRTCADDITIONALHOSTS=127.0.0.1` so those candidates are browser-reachable from a containerized mediamtx at all; this makes WHEP work for a browser on the same host as Docker but **not** across a LAN (a friend's laptop reaching this host's real IP still gets ICE candidates saying `127.0.0.1`) — HLS remains the cross-host-reliable fallback, exactly the case U3's try-WHEP-then-HLS player logic exists for. Full detail: `adapters/adapter-publish-hls/MODULE.md` (Gotchas), `vision-app/MODULE.md` ("WHEP viewing" section), `vision-api/MODULE.md` (DTO notes).

## V — glass-to-glass latency *(user directive 2026-07-23: "user should see the latest available shot, not a buffered 10 seconds ago — make video as fast as possible to get to the user")*

The chain: source RX → StreamPipeline (latest-wins already, negligible) → `MediamtxStreamPublisher` FFmpeg re-encode + RTSP push → mediamtx → viewer transport → player. WHEP (U3) is the sub-second answer where it works (same-host through compose; LAN falls back to HLS), so the HLS fallback path's latency is what actually needs shrinking — it is multi-second *by configuration*, not by necessity.

### V-a — backend: encoder + mediamtx + proxy *(scope: `adapters/adapter-publish-hls/`, `docker-compose.yml`)*

- **Encoder (MediamtxStreamPublisher):** audit the FFmpeg push settings for latency: keyframe interval/GOP must be short enough for short HLS segments (segment can never be shorter than a GOP), `tune zerolatency`/no B-frames/no lookahead, no unnecessary encoder buffering — without regressing the CRF quality fix (commit a963521).
- **mediamtx:** enable low-latency HLS (`hlsVariant: lowLatency`, part duration ~200ms, segment ~1s) via compose `MTX_*` env; document host-mode equivalents for a non-compose mediamtx.
- **Proxy audit:** `HlsProxyController` must stream pass-through (no whole-body buffering, no caching of live playlists) — verify and fix if it buffers.
- **Honest numbers:** document expected end-to-end latency per path (WHEP / LL-HLS / legacy HLS) in MODULE.md; measurement method included.
- **Done when:** HLS viewing latency drops from multi-second (5–15s typical) to ~1–2s on the demo stack, WHEP unaffected. **Estimate: S/M.**

**V-a done** — `MediamtxStreamPublisher`'s `GOP_SECONDS` 2→1 (now matches mediamtx's 1s `hlsSegmentDuration` exactly — the biggest lever, since a segment can never be shorter than its keyframe interval), plus `sc_threshold=0` (closed, strictly periodic GOP — no scene-cut-triggered early keyframes perturbing segment boundaries) and an explicit, independently-tested `setMaxBFrames(0)` (redundant with the pre-existing `tune=zerolatency`, which — verified against x264's own source — already implied zero B-frames/lookahead; added as living documentation of that fact, not a behavior change). `maxrate`/`bufsize`/`crf` (commit a963521) untouched, no quality regression. **Genuine surprise, found by actually pulling and inspecting the image rather than assuming**: `bluenviron/mediamtx:latest` (`v1.19.2` at the time of this task) already defaults to `hlsVariant: lowLatency`/`hlsSegmentDuration: 1s`/`hlsPartDuration: 200ms`/`hlsSegmentCount: 7` — mediamtx needed no behavior change at all. `docker-compose.yml`'s `mediamtx` service still gained explicit `MTX_HLSVARIANT`/`MTX_HLSSEGMENTDURATION`/`MTX_HLSPARTDURATION`/`MTX_HLSSEGMENTCOUNT` env vars anyway, purely to *pin* those already-correct defaults against a future image update silently drifting away from them — env var naming verified against mediamtx's own Go source (`internal/conf/env/env.go`), and the `hlsSegmentCount` floor of 7 under `lowLatency` verified against `gohlslib`'s muxer validation (it refuses to start below that). ### V-c — backend: latency measurement + RTSP ingest tuning *(scope: `adapters/adapter-rtsp/`, `adapters/adapter-publish-hls/`)*

V-a shrank the encoder/mediamtx/proxy side of the chain by configuration audit and produced *estimated* (not measured) numbers, because no packet-capture tooling exists in the build environment. V-b then tuned the player's live-edge behavior. What's still missing is (1) an actual, ongoing **measurement** — not an estimate — of at least one real segment of the pipeline, so a future change can be judged against a number instead of re-deriving the same component-additive reasoning every time, and (2) the RTSP **ingest** side (adapter-rtsp), which V-a never touched — FFmpeg's demuxer-side defaults (probe/analyze/reorder/delay tuning) govern how fast a real IP-camera RTSP connection starts flowing and how it behaves under network jitter, independent of anything V-a did to the encoder/mediamtx/proxy chain downstream.

- **Measurement (adapter-publish-hls):** at the point a frame is handed to the encoder (`FFmpegFrameRecorder.record`), measure `now - videoFrame.capturedAt()` — capture→ingest→pipeline→overlay→publisher-handoff lag, the one span of the whole chain this process can actually observe both ends of without a browser-side clock. Track a small rolling window per stream (ring buffer or EWMA); log a p50/p95 summary at INFO roughly every 30s per stream, per-frame at DEBUG. Document how to read it together with V-b's own "behind live" chip to split capture→encode lag (this measurement) from encode→browser lag (everything V-a/V-b already reason about). Unit-test the tracker's math as a pure class — no clock/mocking needed.
- **RTSP ingest tuning (adapter-rtsp):** for the `rtsp` protocol only — never `file`, which is paced local-file playback, not a live network case — set low-latency demuxer options on the grabber: bounded `probesize`/`analyzeduration` (FFmpeg's own defaults are multi-MB/multi-second — fast connect matters for a real camera far more than for this repo's own file-based simulation/docker-IT sources), a bounded `max_delay` (RTP reorder-wait), and a small `reorder_queue_size`. Read what transport/timeout handling already exists first — don't regress it. Follow the existing per-device option-override plumbing (`options.getOrDefault(key, default)`, same idiom `rtsp_transport`/`timeout` already use) rather than inventing new plumbing. Verify each option actually does what's assumed for this JavaCV/FFmpeg version — `setOption` vs. a dedicated setter matters, per this codebase's own honesty-rule precedent (V-a's `mediamtx`-defaults surprise) — and document what was verified vs. skipped rather than cargo-culting option names from generic advice.
- **Done when:** both adapters build green with the new measurement/tuning in place, and MODULE.md explains exactly what each number/option means and how it was verified. **Estimate: S/M.**

**V-c done** — **Measurement**: new pure `LagTracker` (adapter-publish-hls) — a fixed-capacity (150-sample) drop-oldest ring buffer with nearest-rank p50/p95, `O(1)` `record()` (no allocation), `O(n log n)` percentile reads (only called from the periodic log path, never per-frame). Wired into `MediamtxStreamPublisher.writeFrame` — the one place every frame reaches `FFmpegFrameRecorder.record` — via primitive-only `now - videoFrame.capturedAt()` millis subtraction (no `Duration` allocation). Logs DEBUG per frame (lazy `System.Logger` supplier, free when disabled) and INFO p50/p95 at most once per 30s per stream (never on the very first call, which only establishes the baseline — a single-sample summary at stream start would be noise). MODULE.md documents precisely how to combine this with V-b's own behind-live chip: this number is *only* capture→encode (this process's own clock, both ends observable); the chip is the *browser's* full glass-to-glass view; a healthy small p50/p95 here alongside a large chip value means the bottleneck is downstream (V-a/V-b's own territory), while a large p50/p95 here means it's upstream (source/ingest/pipeline/overlay) — which is exactly where the second half of this task looks.

**RTSP ingest tuning**: new `configureRtspOptions` seam (adapter-rtsp), applied only inside the pre-existing `uri.getScheme().equals("rtsp")` gate — `file` gets none of it, pinned by a direct test against an untouched grabber's own defaults. Four options, each verified against real FFmpeg 6.1.1 source read during this task (`libavformat/options_table.h`, `demux.c`, `rtsp.c`), not assumed: `probesize` 5,000,000→32,768 bytes, `analyzeduration` (unset, effectively 5s/7s-for-mpegts)→1,000,000µs (1s), `reorder_queue_size` (unset, adaptively 0-under-tcp/500-under-udp)→explicit `0`, `max_delay` (unset, resolves to FFmpeg's own `DEFAULT_REORDERING_DELAY`)→explicit `100000`µs (100ms, pinning that same value). All four follow the existing `options.getOrDefault(key, default)` device-override idiom already used by `rtsp_transport`/`timeout` — no new plumbing invented.

**Two genuine, verified corrections to this row's own framing** (the honesty rule this row itself asked for): (1) the commonly-cited "several-second RTSP default" is real, but it belongs to `analyzeduration`'s `mpegts`-payload branch (verified: `7*AV_TIME_BASE` in `demux.c`), not `max_delay`. (2) `max_delay`'s own RTSP-demuxer default, verified by reading `rtsp.c`, is already a modest 100ms (`DEFAULT_REORDERING_DELAY`) — this row's own suggested "500ms, down from 7s" premise doesn't hold for FFmpeg 6.1.1; implementing it literally would have *loosened*, not tightened, `max_delay`. `DEFAULT_MAX_DELAY_MICROS` instead pins FFmpeg's own already-good 100ms as living documentation (same spirit as V-a's redundant `setMaxBFrames(0)`), reasoned explicitly against the far/jittery-source case this row asked about: `max_delay` is what gives a late RTP packet a chance to arrive in order before the demuxer force-delivers, so shrinking it further trades latency for robustness on exactly the links this row cares about. `reorder_queue_size=0` is similarly a no-op pin for this module's actual `rtsp_transport=tcp` default (TCP already implies `0` there) but a real, honestly-flagged trade-off if a future device option ever overrides transport to `udp` (loses FFmpeg's own 500-packet jitter tolerance in exchange for latency). Existing `rtsp_transport`/`timeout` handling (including the documented same-process TX/RX native-contention workaround) was read first and left untouched, both in value and in its existing `uri.getScheme()`-based gating; this module never set `rtsp_flags=prefer_tcp` to begin with (transport is already hard-forced, not merely preferred), so there was nothing to preserve there.

### V-d — backend: cv-service parallel per-stream inference *(scope: `cv-service/`)*

Documented since CP: `Inference.DetectStream` handles one stream's frames as `for request in request_iterator: infer(request); yield response` — receiving the next frame off the network only starts *after* the current frame's inference finishes and its response is handed back to gRPC, so inference and network transfer never overlap within a stream even though the Java side (`adapter-cv-grpc`) allows more than one frame in flight; and every open stream's `detect()` calls run fully unbounded against every other stream's, with nothing protecting the CPU as more streams are added.

- **Within a stream**: decouple receive→infer→respond so a frame can be inferred while the next is in transit — bounded, latest-wins (never a growing backlog: a frame that arrives while one is already waiting replaces it, dropped, never inferred). Read `adapter-cv-grpc/MODULE.md`'s correlation design first and state plainly what it means for response ordering here (does the Java side tolerate reordering, or must this stay strictly in-order per stream?).
- **Across streams**: bound total concurrent inferences with a process-wide gate (semaphore or small executor), sized and justified against what OpenVINO/PyTorch's own intra-op thread usage actually is — verify, don't assume.
- Keep the sync `grpc.server` unless `grpc.aio` is genuinely cleaner *and* keeps the Dockerfile/tests simple — justify whichever. Echo mode (no model) keeps working unchanged; warmup unchanged; graceful stream teardown (client cancel) leaves no thread/queue behind.
- **Done when**: an interleaved two-stream test proves concurrent progress (total wall time less than the serial sum with a slow fake model), a latest-wins drop is proven, teardown leaves no leaked thread, and per-stream ordering holds (or documented reordering-tolerance is proven from the Java side instead). **Estimate: S/M.**

**V-d done** — Design: a background reader thread (`_StreamReader`) per active `DetectStream` call drains the request stream into a 1-slot `LatestOnlyMailbox` (silently replaces an unconsumed waiting frame, `.dropped` counts it), decoupling network receive from inference within that stream; a process-wide `InferenceGate` (plain `threading.Semaphore`, default `min(2, cpu_count // 2)` floored at 1, overridable via `CV_MAX_CONCURRENT_INFERENCES`) bounds how many `detect()` calls may run concurrently across every open stream. ## S — stream stability *(user feedback 2026-07-23, post-MVP2)*

User-reported: (1) stopping a stream from /live freezes the Angular app; (2) a started stream must stay alive aggressively — source hiccups, viewer navigating away, or the browser being closed must never end it; only an explicit Stop may.

### S-c — UI: cross-transport reconnect pacing *(scope: vision-web)* — ✅ done

S-b fixed the *reported* freeze (an explicit Stop now holds, absorbing) but explicitly left one gap open, in its own words: "a rapid flapping-connection-defeats-backoff-via-the-legitimate-`firstSegment`-resets-`attempt` rule scenario *unrelated to an explicit stop* is a known, still-open gap … solving it well needs new state (some notion of 'stayed connected long enough to count as a real recovery, not just a blip')." Live evidence against a zombie stream (listed by the API but not actually publishing — WHEP POST dies with status 0, HLS playlist never appears) shows the predicted shape: the player cycles indefinitely at ~1s — WHEP OPTIONS+POST fail, HLS attach fails, a new attach cycle starts and re-tries WHEP with backoff effectively reset. Multiple dead streams (e.g. several wall tiles pointed at gone devices) multiply this into a request carousel against a backend that can least afford it.

- **Cross-cycle escalating backoff**: the full attach cycle (a WHEP attempt, immediately followed by an HLS attempt when WHEP fails pre-play) shares one escalating capped backoff — 1s → 2s → … → 30s, indefinite — that does not reset merely because a new cycle starts. The cold-start playlist poll (currently a flat 1.5s) folds under the same pacing once a cycle has genuinely failed a transport; a never-yet-live stream's first, still-hopeful wait keeps its gentle fixed cadence.
- **WHEP retry damping**: once WHEP has failed pre-play within an attach session, stop re-POSTing to the same WHEP URL on every cycle — retry it only on a cooldown, so a dead/zombie endpoint sees a handful of requests per minute, not one every second. A later genuine HLS recovery may re-arm a WHEP upgrade attempt.
- **Sustained-playback backoff reset (closes the flagged gap)**: the backoff/attempt counter resets only once playback has been genuinely healthy for a sustained window (a few seconds of continued frame progress), not on the first segment/track — a connection that flaps (plays briefly, fails again before the window elapses) no longer pins retries back at 1s.
- Keep intact, unmodified in behavior: the absorbing `stopped` state (S-b), the permanent-per-attach-cycle WHEP→HLS fallback semantics (U3), snap-to-live + the behind-live chip (V-b), the stall watchdog.
- Tests: reducer specs replaying the zombie-stream trace shape (WHEP fail + HLS fail cycling — inter-attempt delays escalate to the 30s cap, WHEP attempts damped); a flapping stream (fail → brief success under the sustained-window threshold → fail — no reset to 1s); genuine recovery (sustained success → reset); the stopped state and every pre-existing spec unaffected.
- **Done when:** a zombie stream's request rate drops from ~1/s to a few/minute, a flapping connection can no longer pin retries at 1s, and the full pre-existing suite (408 specs) plus new coverage stays green. **Estimate: S/M.**

**Done-note.** Implemented as a **second, independent** pure state machine (`ui/player-recovery.ts#PacingState`/`advancePacing`/`cyclePacingDelayMs`/`shouldAttemptWhep`) layered *on top of* the existing `RecoveryState`/`reduceRecovery`/`TransportRecoveryState`/`reduceTransportRecovery` — not a rewrite of them: those four stay byte-for-byte unchanged (`firstSegment` still resets `RecoveryState.attempt` immediately, exactly as before, still driving the chip's local per-cycle bookkeeping), so all 408 pre-existing specs pass verbatim, unmodified. `PacingState {cycleAttempt, playingSinceMs, lastWhepAttemptAtMs}` is the new saga-wide counter `ui/player.ts` actually uses for delay/WHEP-retry decisions: `cycleAttempt` bumps once per *cycle* (one WHEP attempt if due, immediately followed by an HLS attempt on pre-play failure — U3's permanent-per-cycle fallback, unchanged) that ends without a sustained recovery, and survives every cycle boundary including a WHEP→HLS fallback; `cyclePacingDelayMs` (reusing `reconnectDelayMs`'s exact 1s→…→30s-capped schedule) reads it for the next cycle's delay. `shouldAttemptWhep` gates each cycle's WHEP attempt behind a **60s wall-clock cooldown** since the saga's last one (chosen over a fixed cycle-count specifically so it bounds the *absolute* request rate directly, independent of the backoff schedule's own shape — see the function's own doc comment for the concrete math), re-armed immediately by a genuine sustained recovery. Sustained-playback reset (closing the flagged gap): a new `'healthTick'` event, dispatched every ~2s by the existing HLS/WHEP watchdog intervals while `phase === 'playing'` (no new timer), only zeroes `cycleAttempt` once an *unbroken* `'playing'` streak has lasted `SUSTAINED_PLAYBACK_RESET_MS` (5s) — a flapping connection dispatches `'cycleFailed'` before reaching that window, clearing the streak marker, so it never resets. Enabling "a later cycle may retry WHEP" at all required a new `beginNextCycle` method that every scheduled retry (`scheduleColdStartRetry`'s escalating branch, `scheduleReconnect`) now goes through instead of calling `beginAttach` directly — before this task, once demoted to `hls`, `ui/player.ts` never routed a subsequent retry back through `initialTransportState(true)` at all, so WHEP was in practice permanently abandoned for the attach lifetime, not merely "damped" (see the S-c Status entry's own Deviations for why this was a necessary precondition, not scope creep).
