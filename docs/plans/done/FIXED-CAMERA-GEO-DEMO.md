actually executed**, not a script of what should work. Everything below marked ✅ was run against a

## 1. What this feature is, in one paragraph

A camera that does not move, whose position and aim are known, turns a tracked object's
bounding-box **bottom-centre** — its ground-contact point — into a latitude/longitude on the shared
tactical map. The half that turns a ray into a ground point (`GeoProjection`) has shipped for
months. The half that turns a *pixel* into a ray (`FixedCameraGeo`) is new, and is what makes a
detection's position inside the frame finally matter.

## 5. ✅ Executed: the calibration solver, including every refusal

Landmarks were generated by forward-projecting known pixels through a **known** pose (camera at
50.4501/30.5234, 12 m AGL, yaw 214°, pitch 8.5°, hfov 62°, 1920×1080), so the solve has a truth to
be checked against rather than merely a plausible-looking answer.

**Three consistent points → solved, and the recovered pose is right:**

```
200 {"solved":true,"quality":"GOOD","rmsErrorPixels":0.0144,"reason":null,
     "pose":{"yawDegrees":213.99868,"pitchDegrees":8.49967,"hfovDegrees":61.99814,
             "source":"CALIBRATED",…}}
```

Truth was 214 / 8.5 / 62. Recovered to within **0.002°** on all three, at 0.014 px residual. The
pixel→ray→ground→bearing chain closes on itself.

**Two consistent points → solved, but flagged unverifiable:**

```
200 {"solved":true,"quality":"UNDETERMINED","rmsErrorPixels":0.0031,…}
```

**Every refusal path, with §5's frozen reason text verbatim:**

| Input | Response |
|---|---|
| a landmark 1.1 m from the camera | `{"solved":false,"pose":null,"reason":"landmark 1 is 1.1m from the camera"}` |
| four points, one deliberately mis-clicked | `{"solved":false,"pose":null,"rmsErrorPixels":1018.8,"reason":"residual 1018.8px exceeds 25.0px"}` |
| one point | `400 {"error":"BAD_REQUEST","message":"CalibrationRequest requires between 2 and 8 landmarks, got: 1"}` |

In every refusal `pose` is `null`. There is nothing for the wizard to offer a save button for — the
honesty is structural, not a UI convention.

### 5.1 The defect this demo found

The first live run of the two-point path returned this:

```
200 {"solved":true,"quality":"UNDETERMINED","rmsErrorPixels":177.42925195166893,
     "pose":{"yawDegrees":223.993,"pitchDegrees":10.055,"hfovDegrees":58.066,…}}
```

Two mutually inconsistent clicks, a **177-pixel** residual, a pose wrong by **10° of yaw** — and
`solved:true`, savable. Precisely the confident wrong pose the whole design exists to prevent.

The cause was a false premise in the plan's own decision D5: *"with N=2 the fit is exact and the
residual meaningless."* It is not. Two landmarks supply **four** measurements — two bearings and
two depressions — against three unknowns, leaving one redundant degree of freedom, so the residual
measures something real. The solver computed 177 and threw it away.

Fixed in `c21684d8`: the residual ceiling now applies at every N. `UNDETERMINED` survives for N=2
but now means *"consistent, but one redundant measurement is too thin to cross-check — add a third
point"* rather than *"nothing checked this."* Re-run against the rebuilt server:

```
{"solved":false,"pose":null,"rmsErrorPixels":177.43,"reason":"residual 177.4px exceeds 25.0px"}
```

while the consistent pair still solves at 0.003 px and three points still solve `GOOD`. D5, the
solver javadoc, `contexts/vision-map/MODULE.md` and the test suite were all amended together.

**This is the point of executing a demo rather than writing one.** Five waves of careful reading,
1591 module tests and a green full-reactor build did not catch it; one `curl` did.

## 6. ⛔ Not executed: cars on the map

The headline outcome — *a real street clip plays, and cars appear on the tactical map with trails* —
was **not run**. Two things it needs do not exist yet:

1. **A street-traffic clip with 2–3 map-identifiable landmarks.** The operator's errand, named in
   the plan's §10 since it was written. Landmarks must be things whose real latitude/longitude can
   be looked up on a map — a corner, a crossing, a pole — because the calibration wizard's whole
   input is *"this pixel is that map point."* Without them, there is no pose, and without a pose
   there is no projection. `~/Videos/fuel_station.mp4` is a plausible candidate if its location is
   known; nothing in this repo can tell me whether it is.
2. **`cv-service` running.** Compose has `postgres` and `mediamtx` up, but not `cv-service`. No
   detector means no tracked objects means nothing to project — and it would look exactly like a
   projection bug.

A third hazard, named in the plan and worth repeating: **detection is per-stream, off by default,
and demand-gated.** A demo that forgets `PATCH /api/streams/{id}/config` sees an empty map and
blames the projection. D9's demand OR-term makes a calibrated pose *itself* count as demand, so
this is now mostly self-healing — but the per-stream enable is still a real step.

### When the clip exists, this is the sequence

```bash
docker compose up -d postgres mediamtx cv-service
java -jar station/vision-app/target/vision-app-0.0.1-SNAPSHOT.jar \
     --vision.geo.fixed-camera.enabled=true

# 1. register the clip as a file-protocol device + asset, start the stream
# 2. enable detection on that stream:
curl -X PATCH localhost:8080/api/streams/{streamId}/config \
     -H 'Content-Type: application/json' -d '{"detectionEnabled":true}'
# 3. calibrate: open the asset page, click 3 landmarks in the frame and the
#    same 3 on the map, confirm the solve, PUT the pose
# 4. watch:
curl localhost:8080/api/map/tracks    # expect >= 1 track with a growing trail
```

Expected honest outcomes, to be recorded as found and **not** worked around: YOLO may miss cars in
the chosen clip; a shallow camera angle may push every fix past the D6 error ceiling and legitimately
publish nothing; the flat-ground assumption will bend on a sloped street. Each of those is the
system telling the truth, and each belongs in this document when it happens.
