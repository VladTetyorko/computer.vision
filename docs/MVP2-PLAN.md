# MVP2 — from demo to daily tool

Companion to [ARCHITECTURE.md](../ARCHITECTURE.md), [CYCLES-PLAN.md](CYCLES-PLAN.md) (delegation model, TX/RX doctrine, UI personas all apply unchanged). MVP1 ([MVP1-PLAN.md](MVP1-PLAN.md)) is complete.

**Milestone:** the platform stops being a one-session demo. It survives a restart with its fleet and history intact, plays back yesterday's flight, streams to the browser with sub-second latency, ingests a real webcam and real MAVLink telemetry, and tells the operator when something interesting was seen — while the UI gets *simpler*, not busier.

Themes (user-set + proposed):

1. **UX finish & polish** — the three pending UI cycles are MVP2's front door, not leftovers: CU-b (fast & simple + map layers), CD-b (asset-first devices + self-recovering player + crisp vector boxes), CT-b (flight-plan map editor).
2. **New connection protocols** — per the §0 TX/RX doctrine, each lands as a pair: MAVLink telemetry (the first *real drone* protocol), USB/V4L2 cameras (real hardware with zero network), WebRTC egress (viewer side — sub-second latency vs HLS's multi-second lag).
3. **Something more** — persistence (Postgres finally does work; fleet + history survive restarts), flight replay (map + telemetry scrub over a recorded usage), detection events & alerts (the CV vertical starts *telling* you things, geolocated on the map).

## U-info — user-needed info, not plumbing *(user feedback 2026-07-23, folded into U2/E-b)*

The stream info surfaces (Live panel, asset detail) showed raw plumbing — `Source URI`, `Device id`, `Stream id`, `Started` — instead of what a field user needs. Directive: **lead with user-meaning, demote identifiers.** The info surface should show:

- **Protocol chip + human source description** ("MJPEG · ESP32 at 192.168.0.107", "File · X2Twitter…mp4 (looped)", "RTSP · mediamtx"), not a bare URI.
- **Video facts:** resolution, FPS (both available on frames/status where surfaced), transport (HLS now, WHEP after L-a), viewer latency estimate from the player.
- **Telemetry component** (existing OSD panel) and **map component** (existing inset) — on every surface that shows a streaming source, not only /live.
- **CV status:** detections on/off, last detection age, degraded/outage state (StreamPipeline already knows; surface honestly).
- **Session facts:** started → *duration* (live-ticking), usage link.
- **Share:** copyable view URL (the HLS/WHEP link), not internal ids.
- **Errors where the user is looking:** pipeline errors (e.g. "camera returned HTTP 400") next to the player, not only in server logs — the events feed (E-b) is the mechanism; until then the player state chip (U2 item 5) covers connectivity.
- IDs/URIs stay reachable in a collapsed "Technical details" disclosure (debugging still matters, it's just not the front door).

U2 implements what current APIs already serve; gaps (per-stream error/event feed, WHEP URL) land with E-a/E-b and L-a.

## L — low-latency viewing (WebRTC/WHEP)

mediamtx already serves WebRTC (WHEP) for every published path — the backend only has to *say so*. `StreamPublisherPort`'s view-URL surface gains a WHEP URL beside the HLS one (`/api/streams` + asset/stream DTOs); compose/host ports documented. Player work happens in U3: try WHEP first (sub-second), fall back to HLS automatically; state chip shows which transport is live. **Estimate: L-a S, player part folded into U3.**

**L-a done** — `StreamPublisherPort#whepUrl(StreamId): Optional<URI>` (default empty, mirroring `viewUrl`), implemented by `MediamtxStreamPublisher` (formats `{whepViewBase}/{streamId}/whep`, mediamtx needs no extra per-stream config to serve it) and surfaced as `whepUrl` on `StartStreamResponse`/`ActiveStreamResponse`/`SimulationResponse` (nullable/omitted exactly like `viewUrl`, independently). New property `vision.publish.mediamtx.whep-base` (default `http://localhost:8889`, host-mode default `http://localhost:18889` in `application.properties`, mirroring `rtsp-base`/`hls-base`'s naming). One correction to the brief's framing: **WHEP is not proxied like HLS is** — `HlsProxyController`'s reverse-proxy trick only works because HLS is a plain byte-fetch protocol; WHEP is a POST/SDP + ICE exchange that a stateless proxy cannot forward, so `whepUrl` is always mediamtx's own absolute origin URL, never app-relative — this is a deliberate, documented asymmetry with `viewUrl`, not a gap. `docker-compose.yml` maps `18889:8889` (WHEP HTTP) and a mandatory 1:1 `8189:8189/udp` (ICE media — cannot be renumbered, mediamtx bakes its listening port into the ICE candidates it sends) plus `MTX_WEBRTCADDITIONALHOSTS=127.0.0.1` so those candidates are browser-reachable from a containerized mediamtx at all; this makes WHEP work for a browser on the same host as Docker but **not** across a LAN (a friend's laptop reaching this host's real IP still gets ICE candidates saying `127.0.0.1`) — HLS remains the cross-host-reliable fallback, exactly the case U3's try-WHEP-then-HLS player logic exists for. Full detail: `adapters/adapter-publish-hls/MODULE.md` (Gotchas), `vision-app/MODULE.md` ("WHEP viewing" section), `vision-api/MODULE.md` (DTO notes).

## V — glass-to-glass latency *(user directive 2026-07-23: "user should see the latest available shot, not a buffered 10 seconds ago — make video as fast as possible to get to the user")*

The chain: source RX → StreamPipeline (latest-wins already, negligible) → `MediamtxStreamPublisher` FFmpeg re-encode + RTSP push → mediamtx → viewer transport → player. WHEP (U3) is the sub-second answer where it works (same-host through compose; LAN falls back to HLS), so the HLS fallback path's latency is what actually needs shrinking — it is multi-second *by configuration*, not by necessity.

### V-a — backend: encoder + mediamtx + proxy *(scope: `adapters/adapter-publish-hls/`, `docker-compose.yml`)*

- **Encoder (MediamtxStreamPublisher):** audit the FFmpeg push settings for latency: keyframe interval/GOP must be short enough for short HLS segments (segment can never be shorter than a GOP), `tune zerolatency`/no B-frames/no lookahead, no unnecessary encoder buffering — without regressing the CRF quality fix (commit a963521).
- **mediamtx:** enable low-latency HLS (`hlsVariant: lowLatency`, part duration ~200ms, segment ~1s) via compose `MTX_*` env; document host-mode equivalents for a non-compose mediamtx.
- **Proxy audit:** `HlsProxyController` must stream pass-through (no whole-body buffering, no caching of live playlists) — verify and fix if it buffers.
- **Honest numbers:** document expected end-to-end latency per path (WHEP / LL-HLS / legacy HLS) in MODULE.md; measurement method included.
- **Done when:** HLS viewing latency drops from multi-second (5–15s typical) to ~1–2s on the demo stack, WHEP unaffected. **Estimate: S/M.**

**V-a done** — `MediamtxStreamPublisher`'s `GOP_SECONDS` 2→1 (now matches mediamtx's 1s `hlsSegmentDuration` exactly — the biggest lever, since a segment can never be shorter than its keyframe interval), plus `sc_threshold=0` (closed, strictly periodic GOP — no scene-cut-triggered early keyframes perturbing segment boundaries) and an explicit, independently-tested `setMaxBFrames(0)` (redundant with the pre-existing `tune=zerolatency`, which — verified against x264's own source — already implied zero B-frames/lookahead; added as living documentation of that fact, not a behavior change). `maxrate`/`bufsize`/`crf` (commit a963521) untouched, no quality regression. **Genuine surprise, found by actually pulling and inspecting the image rather than assuming**: `bluenviron/mediamtx:latest` (`v1.19.2` at the time of this task) already defaults to `hlsVariant: lowLatency`/`hlsSegmentDuration: 1s`/`hlsPartDuration: 200ms`/`hlsSegmentCount: 7` — mediamtx needed no behavior change at all. `docker-compose.yml`'s `mediamtx` service still gained explicit `MTX_HLSVARIANT`/`MTX_HLSSEGMENTDURATION`/`MTX_HLSPARTDURATION`/`MTX_HLSSEGMENTCOUNT` env vars anyway, purely to *pin* those already-correct defaults against a future image update silently drifting away from them — env var naming verified against mediamtx's own Go source (`internal/conf/env/env.go`), and the `hlsSegmentCount` floor of 7 under `lowLatency` verified against `gohlslib`'s muxer validation (it refuses to start below that). Host-mode (non-compose) mediamtx needs zero extra flags to match, for the same already-default reason — documented in adapter-publish-hls/MODULE.md rather than requiring anything. `HlsProxyController` (vision-api) audited: no whole-body-buffering fix needed (already-documented, deliberate, and harmless at these payload sizes — not "broken"); LL-HLS query-string (`_HLS_msn`/`_HLS_part`/`_HLS_skip`) pass-through was already correct, now regression-tested; **one real gap found and fixed**: the upstream `Cache-Control` header (mediamtx sends `no-cache` on every live LL-HLS playlist) was being silently dropped rather than forwarded — relying on the accident of "no headers at all" usually not being cached by a browser, rather than the guarantee an explicit `no-cache` gives; now forwarded verbatim alongside `Content-Type`. Estimated (not measured — no packet-capture tooling in the build environment; component-additive reasoning from each stage's own configured timing, full table + method in adapter-publish-hls/MODULE.md) glass-to-glass: WHEP unaffected (~200–500ms), stock/legacy HLS (today's actual pre-V-b player) ~2–3s (down from ~5–10s pre-fix), a genuinely LL-HLS-aware player (V-b's job) ~1–1.5s once wired. Tests: `adapters/adapter-publish-hls` 37/37 green (0 skipped, docker-gated `MediamtxDockerIntegrationTest` confirmed actually running against a real mediamtx container, not skipped), `vision-api` 144/144 green (`HlsProxyControllerTest` 6→8). `docker compose config` validates cleanly; a live `docker compose up -d mediamtx` wasn't possible in this run (a concurrent agent's own stack already held host ports 8554/18888), so the same `MTX_HLS*` env vars were instead verified directly against the real pulled image via `docker run`, starting cleanly with `[HLS] started with listener on :8888` in its log. ### V-c — backend: latency measurement + RTSP ingest tuning *(scope: `adapters/adapter-rtsp/`, `adapters/adapter-publish-hls/`)*

V-a shrank the encoder/mediamtx/proxy side of the chain by configuration audit and produced *estimated* (not measured) numbers, because no packet-capture tooling exists in the build environment. V-b then tuned the player's live-edge behavior. What's still missing is (1) an actual, ongoing **measurement** — not an estimate — of at least one real segment of the pipeline, so a future change can be judged against a number instead of re-deriving the same component-additive reasoning every time, and (2) the RTSP **ingest** side (adapter-rtsp), which V-a never touched — FFmpeg's demuxer-side defaults (probe/analyze/reorder/delay tuning) govern how fast a real IP-camera RTSP connection starts flowing and how it behaves under network jitter, independent of anything V-a did to the encoder/mediamtx/proxy chain downstream.

- **Measurement (adapter-publish-hls):** at the point a frame is handed to the encoder (`FFmpegFrameRecorder.record`), measure `now - videoFrame.capturedAt()` — capture→ingest→pipeline→overlay→publisher-handoff lag, the one span of the whole chain this process can actually observe both ends of without a browser-side clock. Track a small rolling window per stream (ring buffer or EWMA); log a p50/p95 summary at INFO roughly every 30s per stream, per-frame at DEBUG. Document how to read it together with V-b's own "behind live" chip to split capture→encode lag (this measurement) from encode→browser lag (everything V-a/V-b already reason about). Unit-test the tracker's math as a pure class — no clock/mocking needed.
- **RTSP ingest tuning (adapter-rtsp):** for the `rtsp` protocol only — never `file`, which is paced local-file playback, not a live network case — set low-latency demuxer options on the grabber: bounded `probesize`/`analyzeduration` (FFmpeg's own defaults are multi-MB/multi-second — fast connect matters for a real camera far more than for this repo's own file-based simulation/docker-IT sources), a bounded `max_delay` (RTP reorder-wait), and a small `reorder_queue_size`. Read what transport/timeout handling already exists first — don't regress it. Follow the existing per-device option-override plumbing (`options.getOrDefault(key, default)`, same idiom `rtsp_transport`/`timeout` already use) rather than inventing new plumbing. Verify each option actually does what's assumed for this JavaCV/FFmpeg version — `setOption` vs. a dedicated setter matters, per this codebase's own honesty-rule precedent (V-a's `mediamtx`-defaults surprise) — and document what was verified vs. skipped rather than cargo-culting option names from generic advice.
- **Done when:** both adapters build green with the new measurement/tuning in place, and MODULE.md explains exactly what each number/option means and how it was verified. **Estimate: S/M.**

**V-c done** — **Measurement**: new pure `LagTracker` (adapter-publish-hls) — a fixed-capacity (150-sample) drop-oldest ring buffer with nearest-rank p50/p95, `O(1)` `record()` (no allocation), `O(n log n)` percentile reads (only called from the periodic log path, never per-frame). Wired into `MediamtxStreamPublisher.writeFrame` — the one place every frame reaches `FFmpegFrameRecorder.record` — via primitive-only `now - videoFrame.capturedAt()` millis subtraction (no `Duration` allocation). Logs DEBUG per frame (lazy `System.Logger` supplier, free when disabled) and INFO p50/p95 at most once per 30s per stream (never on the very first call, which only establishes the baseline — a single-sample summary at stream start would be noise). MODULE.md documents precisely how to combine this with V-b's own behind-live chip: this number is *only* capture→encode (this process's own clock, both ends observable); the chip is the *browser's* full glass-to-glass view; a healthy small p50/p95 here alongside a large chip value means the bottleneck is downstream (V-a/V-b's own territory), while a large p50/p95 here means it's upstream (source/ingest/pipeline/overlay) — which is exactly where the second half of this task looks.

**RTSP ingest tuning**: new `configureRtspOptions` seam (adapter-rtsp), applied only inside the pre-existing `uri.getScheme().equals("rtsp")` gate — `file` gets none of it, pinned by a direct test against an untouched grabber's own defaults. Four options, each verified against real FFmpeg 6.1.1 source read during this task (`libavformat/options_table.h`, `demux.c`, `rtsp.c`), not assumed: `probesize` 5,000,000→32,768 bytes, `analyzeduration` (unset, effectively 5s/7s-for-mpegts)→1,000,000µs (1s), `reorder_queue_size` (unset, adaptively 0-under-tcp/500-under-udp)→explicit `0`, `max_delay` (unset, resolves to FFmpeg's own `DEFAULT_REORDERING_DELAY`)→explicit `100000`µs (100ms, pinning that same value). All four follow the existing `options.getOrDefault(key, default)` device-override idiom already used by `rtsp_transport`/`timeout` — no new plumbing invented.

**Two genuine, verified corrections to this row's own framing** (the honesty rule this row itself asked for): (1) the commonly-cited "several-second RTSP default" is real, but it belongs to `analyzeduration`'s `mpegts`-payload branch (verified: `7*AV_TIME_BASE` in `demux.c`), not `max_delay`. (2) `max_delay`'s own RTSP-demuxer default, verified by reading `rtsp.c`, is already a modest 100ms (`DEFAULT_REORDERING_DELAY`) — this row's own suggested "500ms, down from 7s" premise doesn't hold for FFmpeg 6.1.1; implementing it literally would have *loosened*, not tightened, `max_delay`. `DEFAULT_MAX_DELAY_MICROS` instead pins FFmpeg's own already-good 100ms as living documentation (same spirit as V-a's redundant `setMaxBFrames(0)`), reasoned explicitly against the far/jittery-source case this row asked about: `max_delay` is what gives a late RTP packet a chance to arrive in order before the demuxer force-delivers, so shrinking it further trades latency for robustness on exactly the links this row cares about. `reorder_queue_size=0` is similarly a no-op pin for this module's actual `rtsp_transport=tcp` default (TCP already implies `0` there) but a real, honestly-flagged trade-off if a future device option ever overrides transport to `udp` (loses FFmpeg's own 500-packet jitter tolerance in exchange for latency). Existing `rtsp_transport`/`timeout` handling (including the documented same-process TX/RX native-contention workaround) was read first and left untouched, both in value and in its existing `uri.getScheme()`-based gating; this module never set `rtsp_flags=prefer_tcp` to begin with (transport is already hard-forced, not merely preferred), so there was nothing to preserve there.

## R — flight replay

### R-a — replay API *(scope: `vision-application/`, `vision-api/`)*

- `GET /api/usages/{id}/timeline?fromMs&toMs&maxPoints` → merged, time-ordered `{telemetry[], detections[]}` window with server-side downsampling (equidistant thinning) so a 30-min flight fits one response budget. Depends on P-b for depth, but works against in-memory repos today (short history) — **not blocked**.
- **Done when:** a finished usage returns a scrubbable timeline. **Estimate: S/M.**

**R-a done** — `GET /api/usages/{usageId}/timeline?fromMs&toMs&maxPoints` (`UsageTimelineController`, vision-api) returns `UsageTimelineResponse{usage, from, to, telemetry[], detections[]}`: `from`/`to` (epoch-ms query params, both optional) default to the usage's own `startedAt`/`endedAt` — an open usage defaults `to` to "now" at call time; `maxPoints` defaults to 500, is rejected (400) if ≤0, and is silently clamped to a 2,000 ceiling if larger. Unknown usage id → 404; malformed UUID/non-positive `maxPoints`/`to` before `from` → 400. The application-layer read side (`ReplayService`/`DefaultReplayService`, vision-application) does the port reads + equidistant-index thinning (always keeps first + last, deterministic, identity when the series already fits). Two corrections to the brief's framing, found while reading the real domain model rather than assuming a shape:
  - **`detections[]` is always empty.** `AssetUsage` (vision-domain) carries no `streamId`/`deviceId` — a stream's id is freshly random per start and never persisted onto the usage — so there is no reliable join from a finished usage back to the `DetectionResult`s (keyed by `StreamId`) that belong to it. Querying `DetectionRepositoryPort` with `streamId=null` across the time window was rejected as a "join" that would silently mix in other assets'/streams' detections. This is an honest gap, not an oversight — see `vision-application`/`vision-api`'s MODULE.md Gotchas for the full writeup and what a real fix needs (a persisted usage↔stream/device link, which touches vision-domain and is out of R-a's scope).
  - **Telemetry is a best-effort fetch, not a true time-bounded query**, because `TelemetryRepositoryPort#findByUsage(usageId, limit)` has no `from`/`to` parameters and its `limit` selects the usage's *earliest* samples (a pre-existing port quirk, flagged since P-b). `DefaultReplayService` fetches up to 20,000 samples (generous for a demo-length flight) and filters/thins the window out of that in memory; a usage with more total samples than that will silently lose data past the fetch cutoff even inside a requested window. Documented, not fixed — fixing it means adding a time-bounded query to the port, a deliberate non-goal here per this task's brief (don't change ports mid-task).

## X — new ingest protocols (TX/RX doctrine, CYCLES-PLAN §0)

### X-a — MAVLink telemetry *(scope: new `adapters/adapter-mavlink/`)*

- RX: `TelemetrySourcePort` over MAVLink 2 UDP (the de-facto SITL/telemetry-radio transport): `HEARTBEAT`, `GLOBAL_POSITION_INT`, `SYS_STATUS`/`BATTERY_STATUS`, `VFR_HUD` → domain `Telemetry`. Java library choice justified in MODULE.md (e.g. dronefleet/mavlink); protocol `mavlink`, `uri = udp://host:port`.
- TX (doctrine): `FeedTransmitterPort` half that *emits* a MAVLink stream from a telemetry flight plan — the zero-hardware E2E: TX transmits on a UDP port, RX ingests it, map shows the moving drone. Also the ArduPilot-SITL rehearsal path.
- Tests: golden-bytes decode fixtures; loopback TX→RX integration test (no hardware).
- **Done when:** `sim_vehicle.py`/SITL *or* our own TX pointed at the app puts a moving, battery-reporting drone on the map. **Estimate: M/L.**

**X-a done** — `adapters/adapter-mavlink` (new module): `MavlinkTelemetrySource` (RX, `TelemetrySourcePort`) and `MavlinkFeedTransmitter` (TX, `FeedTransmitterPort`), both wired into `vision-app` (`mavlinkTelemetrySource`/`mavlinkFeedTransmitter` beans, joining `usageTracker`'s `List<TelemetrySourcePort>` and `feedTransmitterRegistry`'s `List<FeedTransmitterPort>` respectively). Library: `io.dronefleet.mavlink:mavlink:1.1.11` (Maven Central's current release — last published 2023-02-27; runtime-dependency-free, ~1.8 MB, already CRC-validates and auto-resyncs past malformed frames internally) — the hand-roll escape hatch wasn't needed. RX maps `GLOBAL_POSITION_INT` (lat/lon ÷1e7, alt mm÷1000 AMSL, hdg cdeg÷100 or null if unknown, vx/vy/vz cm/s÷100 into `extra`), `SYS_STATUS`/`BATTERY_STATUS` (`batteryRemaining` %, last-message-wins), `VFR_HUD` (`groundspeed`, already m/s) and treats `HEARTBEAT` as liveness-only; a shared UDP port sticks to the first system id it ever sees, ignoring any other system's traffic for that runtime's lifetime (documented, not configurable). TX paces `HEARTBEAT`+`SYS_STATUS` at 1 Hz and `GLOBAL_POSITION_INT` at a configurable `positionRateHz` (default 5 Hz) off one background thread's wall-clock deadline checks, following a minimal reimplemented (not shared — adapters never depend on each other) `LOOP`-only flight-route engine (`MavlinkRoute`, equirectangular-approximation technique borrowed from `adapter-simulation`'s `RoutePlan`, code not shared). Tests: 40 in adapter-mavlink (8 golden-bytes decode/unit-conversion, 10 route math, 9+11 `supports()`/validation matrices, 2 loopback integration — moving/battery-reporting drone, and malformed-datagram resilience with noise interleaved into real traffic), 5 in `vision-app`'s extended `AssetWiringTest` (up from 3).

Two corrections to the spec's own framing, found while implementing: (1) **`FeedSpec#source()` had to be repurposed as a UDP *destination*, not a file** — unlike RTSP/MJPEG's transmitters, MAVLink TX has no local media file to read (the telemetry is synthesized from a flight plan) and no path-based multiplexing to auto-derive a target the way RTSP/mediamtx has, so `spec.source()` is the `udp://host:port` this transmitter actively pushes to, and `start()` returns it back verbatim — which also happens to be exactly the address a `MavlinkTelemetrySource` should bind/listen on to receive it, since MAVLink UDP push shares one address for both ends. (2) **Not wired into `SimulationService`/`SimulationTransport`** — that would have touched `vision-application`, outside this task's scope (module + root pom + vision-app wiring only); `SimulationTransport` still has no `MAVLINK` variant, so the one-call `POST /api/simulations` convenience path doesn't yet cover it. Both beans are fully reachable today via the plain device/asset APIs and a real SITL instance or `MavlinkFeedTransmitter` pointed at a registered device — see adapter-mavlink/MODULE.md's "Try it with a real SITL instance". Adding `SimulationTransport.MAVLINK` is the natural next task, mirroring `adapter-mjpeg`'s own module-then-wiring two-task split (docs/CYCLES-PLAN.md §5). `scripts/demo.sh`/`docker-compose.yml` were deliberately left untouched per the task's brief — SITL usage is documentation, not infra.

**X-b done** — `adapters/adapter-v4l2` (new module): `V4l2VideoSource` (RX only, `VideoSourcePort` — no TX half, same n/a as `sim`/`file`), via JavaCV/FFmpeg's `v4l2` demuxer, wired into `vision-app` (`v4l2VideoSource` bean, joining `videoSourceRegistry`'s `List<VideoSourcePort>`). **This brief's own protocol/URI shape did not match reality, and the task's own instruction ("verify against what adapter-discovery actually emits; if discovery emits a different protocol string, match discovery and document") was followed rather than the literal text above**: `adapter-discovery`'s already-shipped `V4l2Scanner` emits `protocol="v4l2"` (not `"usb"`) with a `file:`-scheme URI naming the real device node, e.g. `file:/dev/video0` (not a `v4l2://` scheme URI) — confirmed by reading both `V4l2Scanner`'s source and its own `V4l2ScannerTest`. `DiscoveredDeviceResponse` (vision-api) flattens `suggestedStream` straight through with no rewriting in between, so `V4l2VideoSource.supports()` accepts exactly `protocol="v4l2"` + any `file:`-scheme URI (rejecting both `"usb"` and a literal `v4l2://` scheme, each covered by its own test) — this is what actually makes "Discover → register → stream" work end to end, which the brief's original guess would not have. ### E-a — event pipeline *(scope: domain/application/api thin ripple)*

- Domain: `DetectionEvent` (streamId, assetId?, label, confidence, firstSeen/lastSeen, position? — geolocated from the freshest telemetry sample at event time when available). Application: debounce rule inside the existing detection flow — "label X appears with conf ≥ Y for ≥ N consecutive batches" opens an event, absence for M seconds closes it. Config on `PipelineConfig` with sane defaults (person/car at 0.5, N=3).
- API: `GET /api/events?since=…` (paged, newest first) + per-stream; SSE or simple polling — pick the simplest thing consistent with the house style and justify in MODULE.md.
- **Done when:** walking through a demo clip yields a "person" event with timestamps and (when telemetry exists) a location. **Estimate: M.**

**E-a done** — `DetectionEvent`/`DetectionEventId`/`DetectionEventState`/`EventRuleConfig` (vision-domain), `PipelineConfig` gained a 7th `eventRule: EventRuleConfig` field (6-arg convenience ctor keeps every existing call site compiling). Application: a new per-stream `DetectionEventEngine` (package-private, one instance per running `StreamPipeline`, mirroring `DetectionExtrapolator`'s lifetime) implements the debounce rule — a tracked label reaching `confidenceThreshold` across `consecutiveToOpen` consecutive `DetectionResult`s opens an event (`firstSeen` = the streak's first qualifying result); the label then absent/below-threshold for `absenceToClose` closes it (`lastSeen` frozen at the last real observation, not the closing check's own timestamp). A bounded in-memory `DetectionEventRepositoryPort` (vision-domain, upsert-by-id, mirrors `AuditTrailPort`'s `findRecent`/`findByX` shape) is implemented by `InMemoryDetectionEventRepository` (vision-app devsupport, 500-event-per-stream ring, persistence explicitly deferred — same posture as `InMemoryAuditTrail`).
