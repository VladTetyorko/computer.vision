# vision-flight

Flight sessions, telemetry transport, geofencing, and guarded flight command/manual control.

**What it deliberately does not do**: hold the actual `AssetUsage`/flight-session record (that's `vision-warehouse`'s — this context only *produces* the telemetry samples a usage accumulates, via `TelemetryService`, see below). It does not carry `Telemetry`/`FlightState` as its own types either — both are **`vision-kernel`** records (pure, no ports, read by five contexts). It does not run the video/telemetry ingest pipeline itself (perception's `UsageTracker`/`StreamPipeline` do, subscribing to this context's `TelemetrySourcePort`) and does not resolve who may command what (`VisibilityScope`, checked here as a parameter, lives in `vision-platform`).

**Depends on:** `vision-kernel` (`Telemetry`, `FlightState`, every id, `GeoPosition`…, `VisualFix`/`VisualFixEvidence` — the input `DefaultTrackCorrectionService` gates) · `vision-platform` (`Event`/`EventPublisherPort`/`EventLiveUpdatePort` — `GeofenceMonitor` raises `GEOFENCE_BREACH`, `DefaultTrackCorrectionService` raises `POSITION_DIVERGENCE` via `EventPublisherPort` only, not `EventLiveUpdatePort`, `BatteryMonitor` raises `BATTERY_LOW`, `LinkLossNotifier` raises `LINK_LOST`; `AuditTrailPort`/`AuditEntry`; `VisibilityScope`/`AccessDeniedException`) · **`vision-warehouse`** — a flight command resolves the asset it acts on: `DefaultFlightCommandService` and `DefaultManualControlService` both resolve the target via warehouse's `AssetService#details` before touching a `Device`; `DefaultRemediationService` reads warehouse's `AssetLiveStatePort#latestTelemetry(AssetId)` for the disarmed-only interlock; `DefaultVehicleProfileService` reads warehouse's `AssetService#details` plus **`UsageSessionService#usageBelongsToAsset(UsageId, AssetId)`** — an uncapped boolean membership check, not a foreign repository port; `DefaultReadinessService` reads warehouse's **`MaintenanceQuery#openBlockers(AssetId)`** (WAREHOUSE-UX-CONTEXT.md D6/OQ1 — see Gotchas). No other context.
**Used by:** `vision-perception` (the `UsageTracker`/`GeofenceMonitor` wiring seam, see Gotchas), `vision-api`, `vision-app`, `adapter-mavlink` (`MavlinkVehicleConfigurator` is the `VehicleConfigPort` implementation).
**Build/test:** `./mvnw -B -pl contexts/vision-flight test`

## API surface

### `com.drones.vision.flight.domain.model` — core RC/command
- `record ChannelMap(List<ControlBinding> bindings)` — a full axis/button → RC-channel map; `bindings` defensively copied; `RcChannels apply(List<Double> axes, List<Double> buttons)` — a missing/out-of-range/`null` index reads as `0.0` (never throws), assembles channels 1..N (N = highest `rcChannel` any binding targets, or 1 if empty); an unbound channel *below* N is `RcChannels#IGNORE`, channels above N are simply absent. Maps come from `ControlProfile.forKind(...)` — there is no airframe-blind default.
- `enum CommandResult` — `ACCEPTED`/`NO_ACK`, the outcome of a `FlightCommandPort` call; an explicit refusal is deliberately not a value here — see `FlightCommandPort`'s own javadoc (that case is a thrown `IllegalStateException` instead).
- `record ControlBinding(Source source, ControlInputKind kind, ControlFunction function, int sourceIndex, int rcChannel, int minMicros, int centerMicros, int maxMicros, double deadband, boolean reversed)` — one physical control (`enum Source { AXIS, BUTTON }` — *which array the value is read from*) mapped to one RC channel with linear calibration, labelled by what it does (`function`, non-null). Compact ctor rejects a `kind`/`source` pair the hardware cannot produce (`kind.allows(source)`); `rcChannel` must be within `[1,16]` (**FLEET-RADIO R3, F17** — narrowed from `[1,18]`; ArduPilot reads no channel past 16, so a binding on 17/18 is now rejected here, at construction, rather than accepted and silently truncated at the wire). `int toMicros(double normalized)` — `AXIS` maps `[-1,0]`/`[0,1]` piecewise-linearly through `centerMicros`; `BUTTON` maps `[0,1]` straight onto `[minMicros,maxMicros]` (`centerMicros` plays no part in a button's own mapping); a `SWITCH_2`/`SWITCH_3` **quantizes** to its own detents — `LOW → minMicros`, `MIDDLE → centerMicros`, `HIGH → maxMicros` — honouring `reversed` by flipping the *position*, not the number.
  - `enum Travel { CENTERED, UNIDIRECTIONAL }` + `Travel travel()` — **derived, never stored**: `centerMicros == minMicros` *is* a unidirectional control. Rest is `centerMicros`, so a centred control rests mid-travel (a rover's throttle: stop) and a unidirectional one rests at `minMicros` (a copter's throttle: idle).
  - Factories: `centeredAxis(fn, sourceIndex, rcChannel)`, `unidirectionalAxis(...)`, `button(...)`, `switched(fn, source, kind, sourceIndex, rcChannel)` (2-/3-position only); `CENTER_MICROS = 1500`.
- `enum ControlFunction` — `ROLL | PITCH | THROTTLE | YAW | STEERING | AUX_1..AUX_4`, each with `String label()`. `STEERING` is separate from `ROLL` — a ground vehicle steers, it does not bank.
- `record ControlProfile(ControlProfileId id, VehicleKind kind, String code, String displayName, ChannelMap channelMap, ActionMap actionMap)` — the stick-and-switch layout, the only source of a `ChannelMap`. Two compact-ctor invariants: one physical control appears in at most one of the two maps, and no RC channel is driven twice. `withBindings(ChannelMap, ActionMap)`/`copyAs(ControlProfileId, String)` return edited copies; `boolean isBuiltIn()` delegates to the id.
  - `static forKind(VehicleKind)` — the **built-in** profiles, each with `ControlProfileId.builtIn(kind)` and an **empty** `ActionMap`: **COPTER/PLANE** → `AETR`, centred roll/pitch/yaw + **unidirectional throttle on CH3**; **ROVER** → `S-T-`, centred steering (CH1) + centred throttle (CH3), nothing else bound; **UNKNOWN** → code `----`, displayName `"Unidentified vehicle"`, an **empty `ChannelMap`** (**FLEET-RADIO R2** — was four centred axes before this wave; see Gotchas for why empty, not a guess). No built-in binds an aux channel or an action. `forKind` stays **total and non-throwing for every `VehicleKind`** — including `UNKNOWN` — that invariant is unchanged; what changed is that its `UNKNOWN` output is no longer flyable. The real refusal gate for `UNKNOWN` is `DefaultManualControlService#engage` (below), not this factory — this method's own emptiness is defense in depth, not the mechanism.
- `enum ControlInputKind` — `AXIS | BUTTON | SWITCH_2 | SWITCH_3`, each with `label()`, `List<SwitchPosition> positions()` (empty for `AXIS`), `boolean isSwitched()`, `boolean allows(ControlBinding.Source)`. Deliberately separate from `Source`: an EdgeTX 3-position switch arrives on the *axes* array, a latching toggle on the *buttons* array — "what shape is it" and "where is it read from" are two facts. `SWITCH_3` allows only an `AXIS` source.
- `enum SwitchPosition` — `LOW | MIDDLE | HIGH`, ArduPilot's own three, with `label()`, `SwitchPosition reversed()` (`MIDDLE` its own mirror), `int auxFunctionLevel()` = `ordinal()` (`MAV_CMD_DO_AUX_FUNCTION`'s own encoding). `static of(Source, ControlInputKind, double raw)` — the single quantizer every caller shares: a button is `HIGH` at `raw >= 0.5`; a `SWITCH_3` axis is `LOW <= -0.5`, `HIGH >= 0.5`, `MIDDLE` between; anything else splits at `0.0`. `LOW_MICROS = 1200` / `HIGH_MICROS = 1800`.
- `enum ControlAction` — `ARM`, `DISARM`, `TOGGLE_ARM`, `EMERGENCY_STOP`, `RETURN_TO_HOME`, `SET_MODE`, `AUX_FUNCTION`. Each carries `Parameter parameter()` (`NONE | MODE_NAME | AUX_FUNCTION`), `String label()`, `boolean dangerous()` (a domain fact served to clients, not re-invented by them). `void requireValidParameter(String)` rejects a parameter on a `NONE` action, a missing one on the others, a non-numeric/out-of-`[0,400]` `RCx_OPTION` number.
- `record PositionAction(SwitchPosition position, ControlAction action, String parameter)` — one detent's worth of behaviour; blank `parameter` normalizes to `null`, then `action.requireValidParameter` runs. `static of(position, action)` for the parameterless case; `int auxFunctionNumber()` throws unless the action is `AUX_FUNCTION`.
- `record ActionBinding(ControlBinding.Source source, ControlInputKind kind, int sourceIndex, List<PositionAction> positions)` — one physical control and everything it fires. Refuses an `AXIS` kind, an impossible `kind`/`source` pair, an empty list, a position the kind does not have, two actions on the same position. `static pressButton(sourceIndex, action)`; `Optional<PositionAction> actionAt(SwitchPosition)`; `boolean isControl(Source, int)`.
- `record ActionMap(List<ActionBinding> bindings)` — defensively copied; `static empty()`, `Optional<ActionBinding> find(Source, int sourceIndex)`, `boolean isEmpty()`.
- `record ControlProfileId(UUID value)` — `random()`, `of(String)`; `static builtIn(VehicleKind)` — a **derived, stable** id (UUIDv3 over `"vision:control-profile:built-in:<KIND>"`) so a built-in can be named on the wire without being stored; `boolean isBuiltIn()`.
- `record OwnedControlProfile(UserId owner, ControlProfile profile, boolean active, Instant updatedAt)` — a saved profile and who owns it. **Refuses to wrap a built-in** (`copyAs` it first — built-ins are the floor everyone falls back to). `id()`/`kind()` delegate.
- `enum VehicleKind` — `COPTER | PLANE | ROVER | UNKNOWN`; a *control* taxonomy, not a catalogue — `ROVER` covers boats, `UNKNOWN` is never resolved to a guess. **Deliberately not widened for FLEET-RADIO R2** — see `UnidentifiedReason` immediately below for why the operator-facing "why is it UNKNOWN" distinction lives in a separate, orthogonal type instead of a wider `VehicleKind`.
- `enum UnidentifiedReason` — `UNSUPPORTED_VEHICLE | NOT_A_VEHICLE | NEVER_IDENTIFIED` (**FLEET-RADIO R2**) — *why* a link's `vehicleKind()` came back `UNKNOWN`, kept orthogonal to `VehicleKind` itself so `ControlProfile`/`ChannelMap` resolution stays a pure 4-way control-shape switch while the operator still gets a true reason. `UNSUPPORTED_VEHICLE`: a recognized-but-unflyable airframe (e.g. a submarine, or any future `VehicleClass` this platform doesn't fly/drive) — the remedy is "this platform cannot do this, not now, maybe never". `NOT_A_VEHICLE`: the heartbeating device is an instrument sharing the link (a gimbal, a ground station, an ADS-B transponder) — the remedy is "you commanded the wrong thing, not a vehicle at all". `NEVER_IDENTIFIED`: a genuinely unseen `MAV_TYPE` — the remedy is "an operator who can see the aircraft may proceed by choosing its kind explicitly" (the only one of the three where a manual override is a sane next step). See `ManualControlLink#unidentifiedReason()` and `DefaultManualControlService#engage` below for where this is produced and consumed.
- `record FlightCapability(boolean commandable, boolean armSupported, boolean modeSelectSupported, List<String> selectableModes, VehicleKind vehicleKind)` — a best-effort snapshot of what flight commands a device's aircraft accepts; `armSupported`/`modeSelectSupported` never `true` when `commandable` is `false`; `static notCommandable()` = all-false + empty list + `UNKNOWN`.
- `record GeofenceZone(ZoneId id, String name, ZoneKind kind, List<GeoPosition> polygon, Double maxAltitudeMeters, boolean enabled)` — polygon ≥3 vertices, implicitly closed; `maxAltitudeMeters` nullable, non-negative if present; zones are global (no per-asset/per-group scoping). `boolean contains(GeoPosition)` — ray-casting point-in-polygon treating lat/lon as planar Cartesian (see Gotchas). `withEnabled(boolean)`, `withDetails(...)` return copies.
- `record RcChannels(List<Integer> microsByChannel)` — one 1-based microsecond value per RC channel, the payload `ManualControlPort` relays as a MAVLink `RC_CHANNELS_OVERRIDE` (#70) frame; constants `RELEASE=0`, `IGNORE=0xFFFF`, `MIN_MICROS=1000`, `MAX_MICROS=2000`, `MAX_CHANNELS=16`; `static released(int channelCount)`. **FLEET-RADIO R3 (F17)**: accepts at most `MAX_CHANNELS` (16) entries — ArduPilot's own RC-override handling reads no channel past 16, even though the wire message has 18. The domain's `RELEASE`/`IGNORE` sentinels are uniform across every channel here; the *wire* re-encoding that channels 9+ actually need (F4) is `mavlink-core`'s concern, not this module's — see that module's `RcChannels#wireValue` and its own Gotchas for why, and this module's Gotchas below for why no equivalent method was added here.
- `record ZoneId(UUID value)` — `static random()`, `static of(String)`.
- `enum ZoneKind` — `KEEP_IN | KEEP_OUT`, read by `GeofenceMonitor` to decide what "inside"/"outside" a zone's polygon means for breach purposes.

### `com.drones.vision.flight.domain.model` — vehicle onboarding (probe/readiness/remediation, docs/plans/active/DRONE-ONBOARDING-PLAN.md)
- `enum FlightPhase` — `PREFLIGHT | IN_FLIGHT | LINK_LOST | POSTFLIGHT | ABANDONED | CLOSED`, the frozen §8.1 wire spelling (enum name **is** the wire string); `IDLE` deliberately absent — that is "no `AssetUsage` exists yet", not a phase to stamp on one.
- `final class FlightPhaseRule(Duration silenceWindow, Duration abandonWindow)` — the pure phase-transition function; ctor validates both positive and `abandonWindow >= silenceWindow`. `FlightPhase nextPhase(FlightPhase currentPhase, FlightState state, Duration linkAge, int streamCount)` — the sample-driven half; reads `state.armed()` via `Boolean.TRUE/FALSE.equals(...)`, never unboxes (`armed == null` is never "false"); `streamCount` only gates the never-armed `PREFLIGHT`/`POSTFLIGHT` → `CLOSED` transition. `FlightPhase onSessionClosed(FlightPhase currentPhase)` — the explicit-close half (`IN_FLIGHT`/`LINK_LOST` → `ABANDONED`, everything else → `CLOSED`); **two entry points, not one function**, because "session closed while armed" fires when the platform stops observing, not on a telemetry sample — see Gotchas.
- `record VehicleProfile(String linkKey, Instant observedAt, Integer sysid, String firmware, String firmwareVersion, String vehicleKind, Long capabilityBitmask, List<String> capabilityFlags, List<MessageObservation> messages, List<ParameterReading> parameters, Long linkBytesPerSecond, boolean complete, String incompleteReason)` — the PROBE stage's observed snapshot, keyed by `linkKey` (pre-registration identity, e.g. `"udp://0.0.0.0:14550#7"`) rather than `DeviceId`; `complete == false` requires a non-blank `incompleteReason` and vice versa ("probably fine, didn't check" cannot be represented); `capabilityBitmask` deliberately **not** validated non-negative (a `uint64` high bit is a legitimate negative `long`); null lists normalize to empty.
- `record MessageObservation(int messageId, String name, double hz, long count)` — one passively-inventoried message rate; `name` nullable (unresolved dictionary entry, still counted).
- `record ParameterReading(String name, double value, String type)` — one parameter actually read; only what was actually read — an unanswered request has no entry, never a fabricated zero.
- `final class ParameterAliases` (static) — the same vehicle parameter under the names successive firmware generations give it. `static String canonical(String name)` (first spelling of its group, else `name` itself), `static boolean sameParameter(String a, String b)` (`false` if either is null), `static Set<String> spellingsOf(String name)` (every spelling incl. itself; a singleton for an unaliased name). Groups today: `SYSID_THISMAV`/`MAV_SYSID` and `SYSID_MYGCS`/`MAV_GCS_SYSID` (both renamed by ArduPilot 4.7). Compared at the *comparison*, never by rewriting a `ParameterReading` — see Gotchas.
- `enum ParameterTier { A, B, C }` — `static Optional<ParameterTier> classify(String parameterName)` canonicalises through `ParameterAliases` first, then matches a seeded regex allowlist (representative, not verified-complete — see Gotchas); `boolean everWritable()` — `false` only for `C`. The allowlist is domain code, not a UI convention.
- `record FeatureRequirement(String featureKey, String label, String firmware, Integer requiredMessageId, String requiredMessageName, Double minimumHz, String requiredParameterName, Double requiredParameterValue, Long forbiddenParameterBits)` — one seeded requirement row; `public static final Set<String> FEATURE_KEYS` is the frozen §8.1 eleven-key set, enforced in the compact constructor; `requiredMessageId` present ⇒ `requiredMessageName` non-blank and `minimumHz` non-negative, both required together; a row with neither message nor parameter requirement is valid (e.g. `command-tx`). **FLEET-RADIO R6**: `requiredParameterValue` (must equal exactly, small float tolerance) and `forbiddenParameterBits` (value, rounded to a `long`, must have none of these bits set) generalize `requiredParameterName` from presence-only to value-aware; both are independently nullable but neither may be set without `requiredParameterName`, and `forbiddenParameterBits` must not be negative — enforced in the compact constructor.
- `enum FeatureStatus { READY, DEGRADED, MISSING, UNKNOWN }`, `enum RemedyKind { MESSAGE_INTERVAL, PARAM_WRITE, CLI_SCRIPT, MANUAL }`, `enum ReadinessVerdict { GO, NO_GO, UNKNOWN }` — frozen §8.1 wire spellings, enum name = wire string.
- `record FeatureReadiness(String featureKey, String label, FeatureStatus status, String detail, RemedyKind remedy)` — one `ReadinessReport` row; `featureKey` validated against `FeatureRequirement.FEATURE_KEYS`; `detail` never blank; `remedy` nullable.
- `record ReadinessReport(AssetId assetId, ReadinessVerdict verdict, Instant evaluatedAt, Instant profileObservedAt, List<FeatureReadiness> features, List<String> blockers)` — `profileObservedAt` is `null` when never probed (an honest, renderable `UNKNOWN`, not a 404).
- `enum RemediationResultCode { ACCEPTED, DENIED, NO_ACK, UNSUPPORTED }` — frozen §8.1 `RemediationResult.actions[].outcome` spelling, gives `VehicleConfigPort`'s write/message-interval methods an honest return type.
- `record MessageIntervalOutcome(int messageId, Duration interval, RemediationResultCode outcome, String detail)` — Mechanism A's outcome; not a write, nothing persists past the session.
- `record ParameterWriteOutcome(String parameterName, RemediationResultCode outcome, Double previousValue, Double newValue, String detail)` — Mechanism B's outcome; a read-back that differs from the requested value is `DENIED` with `previousValue` set for the caller to restore to, never `ACCEPTED`.
- `record ParameterDrift(String parameterName, double previousValue, double currentValue, Instant previousObservedAt, Instant currentObservedAt)` — one changed parameter between two `VehicleProfile` snapshots; ctor rejects a blank name, a null timestamp, `currentObservedAt` before `previousObservedAt`, and `previousValue == currentValue` — cannot represent a non-change.
- `final class ConfigDriftCalculator` (pure, private ctor) — `static List<ParameterDrift> diff(VehicleProfile earlier, VehicleProfile later)`: throws `IllegalArgumentException` if `later.observedAt()` precedes `earlier.observedAt()`. Compares parameters present **in both** snapshots by name; present in only one is never reported as drift (absence of evidence is not evidence of a change); unchanged value produces no row. Sorted by `parameterName`.
- `record FlightPassport(UsageId usageId, AssetId assetId, VehicleProfile preflightProfile, VehicleProfile postflightProfile)` — read model, not persisted as its own row; both profiles nullable — a passport for a flight whose snapshot was never captured is still a valid, renderable passport with a `null` half.

### `com.drones.vision.flight.domain.model` — visual-geolocation gating (docs/plans/done/VISUAL-GEO-V2-PLAN.md §3.5/§4.3/§4.5)
- `enum CorrectionStatus { CONFIRMED, PROBABLE, NO_FIX }` — the Java-side §4.3 gate's verdict on one fix.
- `enum CorrectionSource { VISUAL_HEAVY }` — one value today (the HEAVY-A pipeline); a placeholder for a future lighter-weight source.
- `record TrackCorrection(AssetId assetId, UsageId usageId, Instant frameAt, Instant computedAt, CorrectionStatus status, CorrectionSource source, GeoPosition position, Double yawDegrees, Double radiusMeters, Double impliedAglMeters, GeoPosition rawPosition, Double separationMeters, Double sigmaMeters, boolean divergent, Instant divergentSince, String regionId, String tileId, String refusal, VisualFixEvidence evidence)` — one gated, persisted, published correction; `position`/`refusal` mutually exclusive exactly like `VisualFix`; `position.altitudeMeters()` must be `null` (2-D only); `divergent == (divergentSince != null)`, enforced in the compact ctor; `radiusMeters`/`separationMeters`/`sigmaMeters` non-negative if present.
- `final class DivergenceRule` (public, no interface) — the §4.5 divergence alarm state machine, standalone from `DefaultTrackCorrectionService` so its numeric semantics are unit-testable in isolation.
  - `DivergenceRule(double sigma, int consecutiveFixes, Duration clearAfter)` — `sigma` positive finite, `consecutiveFixes` ≥1, `clearAfter` positive.
  - `Outcome evaluate(AssetId, CorrectionStatus, Double separationMeters, Double sigmaMeters, Instant now)` — only a `CONFIRMED` status with both separation/sigma present participates; "qualifying" means `separationMeters > sigma * sigmaMeters`; a non-participating call reports the asset's *current* latched state back unchanged (`risingEdge=false`). State machine: Quiet→(qualifying)→Arming→…→Alarm at the Nth consecutive qualifying fix (rising edge, reported once)→(non-qualifying, `clearAfter` elapses)→Quiet; a non-qualifying fix while merely arming resets the count. Clear-after is lazily evaluated, only re-checked on the next `CONFIRMED` correction for that asset. State is in-heap only, resets on restart — the same honest limitation `GeofenceMonitor`'s breach state carries.
  - `record Outcome(boolean divergent, Instant divergentSince, boolean risingEdge)` (nested) — `divergentSince` non-null iff `divergent`; `risingEdge` requires `divergent`.

### `com.drones.vision.flight.domain.port` (driven — implemented by adapters)
- `FlightCommandPort` (**the one deliberate place the RX-only doctrine, `docs/main/CYCLES-PLAN.md` §0, is broken**): `boolean supports(Device)`; six blocking commands, each sending one MAVLink command and waiting briefly for the aircraft's own ack — `CommandResult setMode(Device, String modeName)`, `CommandResult arm(Device, boolean force)`, `CommandResult disarm(Device, boolean force)`, `CommandResult returnToHome(Device)`, `CommandResult emergencyStop(Device)` (**vehicle-kind-dependent as of FLEET-RADIO R4b** — force-disarm on `COPTER`/`PLANE`/an unidentified kind, *an airborne vehicle will fall*; `MAV_CMD_DO_SET_MODE` into ArduRover's `Hold` on `ROVER`, never a disarm — see Gotchas and `drone-link/mavlink`'s own MODULE.md for the full rationale), `CommandResult auxFunction(Device, int function, int level)` (`MAV_CMD_DO_AUX_FUNCTION` 218; `level` 0/1/2, IAE outside) — plus one non-blocking, never-throwing `FlightCapability capabilities(Device)`. `arm`/`disarm`'s `force` uses the MAVLink `21196` magic value. Throws `IllegalArgumentException` for an unsupported device/firmware or unknown mode; `IllegalStateException` when the aircraft explicitly refuses; a lost/missing ack is neither (`CommandResult#NO_ACK`). One real implementation: `drone-link/mavlink`'s `MavlinkFlightCommander`.
- `ControlProfileRepositoryPort`: `List<OwnedControlProfile> findAllByOwner(UserId)`; `Optional<OwnedControlProfile> findById(ControlProfileId)`; `Optional<OwnedControlProfile> findActive(UserId, VehicleKind)`; `void save(OwnedControlProfile)` upsert; `void activate(UserId, ControlProfileId)` — exactly one active profile per (owner, kind), implementation clears siblings in the same transaction; `void delete(ControlProfileId)` idempotent.
- `GeofenceRepositoryPort`: `GeofenceZone save(GeofenceZone)` upsert; `Optional<GeofenceZone> findById(ZoneId)`; `List<GeofenceZone> findAll()` snapshot, global; `void deleteById(ZoneId)` idempotent.
- `ManualControlLink` — opaque, adapter-owned handle to one engaged `ManualControlPort` relay link; `boolean active()` · `VehicleKind vehicleKind()` — what the vehicle behind the link most recently reported itself to be, read live at `engage` and never stored; an implementation that cannot tell must return `UNKNOWN` · `int rateHz()` — the link's own keepalive cadence, resolved at `engage` and fixed for the link's life; a **floor, not a ceiling**; exists so `vision-api` can report the real rate without depending on `adapter-mavlink`. Not a SAM — a lambda no longer compiles. `default Optional<UnidentifiedReason> unidentifiedReason()` (**FLEET-RADIO R2**) — empty unless `vehicleKind() == UNKNOWN`; the **default implementation** returns `Optional.of(NEVER_IDENTIFIED)` whenever it is, so every pre-R2 implementer (test doubles included) keeps compiling and keeps refusing correctly without an override. Only `drone-link/mavlink`'s real adapter overrides it, to report `UNSUPPORTED_VEHICLE`/`NOT_A_VEHICLE` where its own `VehicleClass` classification can tell the finer story.
- `ManualControlPort` — a streaming, ack-less RC-channel-override relay, the fire-and-forget opposite of `FlightCommandPort`'s request→ack one-shots: `boolean supports(Device)`; `ManualControlLink engage(Device)` — opens a link + starts a fixed-rate sender thread, throws `IllegalArgumentException` if unsupported/unreachable; `void send(ManualControlLink, RcChannels)` — latest-wins mailbox, non-blocking; `void release(ManualControlLink)` — release-sentinel burst then stops the sender. Real implementation: `drone-link/mavlink`'s `MavlinkManualControlSender`.
- `TelemetryLiveUpdatePort`: `void publishTelemetryAppended(AssetId, Telemetry)` — announces one sample appended to an asset's open usage; must not throw, must return quickly.
- `TelemetryRepositoryPort`: `void save(UsageId, Telemetry)` append-only; `List<Telemetry> findByUsage(UsageId, int limit)` — returns the **earliest** samples, not latest (see `vision-events`' Gotchas for the consequence).
- `TelemetrySourcePort`: `boolean supports(Device)`; `Flow.Publisher<Telemetry> open(Device)` — per-open, hot/live, latest-wins backpressure; `void close(DeviceId)` idempotent.
- `VehicleConfigPort` — talks to a vehicle over its own protocol for onboarding; every method takes a `String linkKey` (`"udp://host:port#sysid"`), **not** a `Device` — the pre-registration probe runs before any `DeviceId` exists. `boolean supports(Device)`; `VehicleProfile probe(String linkKey, Duration window)` — never throws for an incomplete answer; `MessageIntervalOutcome requestMessageInterval(String linkKey, int messageId, Duration interval)` — Mechanism A, not a write; `List<ParameterReading> readParams(String linkKey, List<String> parameterNames)`; `ParameterWriteOutcome writeParam(String linkKey, String parameterName, double value)` — Mechanism B, snapshot-before/read-back-after is the implementation's job. One expected implementation: `adapter-mavlink`'s `MavlinkVehicleConfigurator`, riding the same shared socket `MavlinkHeartbeatScanner` already borrows.
- `VehicleProfileRepositoryPort`: `void save(DeviceId, VehicleProfile)` append-only, never overwrites; `Optional<VehicleProfile> findLatest(DeviceId)` — keyed by `DeviceId`; `void save(DeviceId, UsageId, FlightPhase, VehicleProfile)` — the tagged variant `captureSnapshot` uses, still append-only; `Optional<VehicleProfile> findByUsageAndPhase(UsageId, FlightPhase)` — "the newest tagged row for this usage+phase".
- `FeatureRequirementRepositoryPort`: `List<FeatureRequirement> findByFirmware(String firmware)` — empty for a never-seen firmware, read as "every feature `UNKNOWN`", not an error; `List<FeatureRequirement> findAll()`.
- `TrackCorrectionRepositoryPort`: `void save(TrackCorrection)` append-only, never updated in place (the `track_corrections` table is excluded from the audit trigger, telemetry-character, ~1Hz per flying asset); `List<TrackCorrection> findByUsage(UsageId, int limit)` oldest→newest, bounded; `Optional<TrackCorrection> findLatest(AssetId)` freshest across every usage; `int deleteOlderThan(Instant)` / `int trimUsageToMostRecent(UsageId, int maxRows)` — the composition-layer runner's own retention mechanisms; neither is called by `DefaultTrackCorrectionService` itself, only `deleteOlderThan` via `prune`.
- `TrackCorrectionLiveUpdatePort`: `void publishCorrection(AssetId, TrackCorrection)` — mirrors `TelemetryLiveUpdatePort`'s contract exactly; a driving adapter pushes this to the `geo:<assetId>` live topic.

### `application` (root package — flight commands + RC relay)
- `FlightCommandService` (interface) → `DefaultFlightCommandService` — guarded flight command TX, behind `vision-api`'s `FlightCommandController`

## Conventions
- **Validation**: domain records validate in their compact constructor; the application layer uses `Objects.requireNonNull`.
- **The acting user is a method parameter (`UserId actor`/`VisibilityScope scope`)**, never a constructor dependency.
- **Constructor injection only**, collaborators `Objects.requireNonNull`-wrapped.
- **Every port interface's javadoc documents Contract and Threading**; `TelemetrySourcePort` adds a Backpressure section describing the latest-wins drop policy.
- **One public constructor per class**: a new field means updating call sites, or bundling optional data into a settings/collaborators record with a `defaults()` factory — never one more constructor overload (`.claude/skills/java-clean-code/SKILL.md` §3, `CLAUDE.md` rule 10; the withdrawn N-1-arg convenience-constructor idiom this replaces does not appear anywhere in this module). `ManualControlSession` is an interface with no constructors of its own; its sole implementation has exactly one 5-arg constructor.
- **Audit shape**: `AuditEntry.of(actor, action, targetType, targetId, summary, attrs)` with a short `result` token (`ACCEPTED`/`NO_ACK`/`REFUSED:<msg>`/`REFUSED:unidentified-vehicle:<reason>` (FLEET-RADIO R2, `DefaultManualControlService#engage`)/`REFUSED:not-ready:<featureKey>` (FLEET-RADIO R6, same method)/`REFUSED:maintenance-grounded` (WAREHOUSE-UX W5, same method)/`DENIED:out of scope`/`ENGAGE`/`RELEASE`/`WATCHDOG`) plus a human `summary`.

## Gotchas
- **`GeofenceZone.contains` is a planar approximation, not spherical geometry** — accurate at the scale a geofence actually operates at (tens of meters to a few km), **not** valid near the poles or across the antimeridian. No attempt is made to detect/reject a pathological polygon spanning either.
- **`ControlBinding#toMicros` ignores `centerMicros` entirely for `Source.BUTTON`** — a button's mapping is a straight 2-point line from `minMicros` to `maxMicros`.
- **`ChannelMap#apply` never throws on missing input** — an unreported/`null`/short `axes`/`buttons` list reads as `0.0` for whichever bindings fall outside it (a browser gamepad frame that hasn't yet reported every axis/button must not crash the relay).
- **A profile that binds nothing above CH*n* produces an *n*-channel frame, not a 16-channel one with `IGNORE`s.** A rover's frame is 3 channels long and CH4 is simply absent — `mavlink-core`'s `RcChannels#wireValue` (renamed from `channelOrIgnore` in FLEET-RADIO R3) pads the wire frame with `IGNORE` downstream, for any channel past the frame's own length **and** for 17/18 unconditionally. Assert on frame *size* when testing a profile, not on a CH4 value.
- **FLEET-RADIO R3 (F3/F4/F17) — CH9+ used to be silently dropped, and this module's own `RcChannels` deliberately does not grow a wire-encoding method to fix it.** Before this wave, `mavlink-core`'s `ManualControlService.buildFrame` hardcoded chan9..18 to `IGNORE` regardless of what a caller's `RcChannels` carried (F3) — so a CH9 binding here (e.g. a rover mode switch via `ControlFunction.AUX_1`) reached `MavlinkManualControlSender`, reached `mavlink-core`'s own `RcChannels`, and vanished at the very last step. Fixing F3 exposed F4: MAVLink's extension channels (9..16) don't share base channels' `RELEASE=0` sentinel — `0` means "ignore" there, and only `65534` means "release" — so a domain-uniform `RELEASE` constant needs a *wire-position-aware* translation somewhere before it hits the message. That translation (`wireValue(int)`) was added only to `mavlink-core`'s `RcChannels`, not this module's: nothing in this module's own call chain needs wire-level encoding — `MavlinkManualControlSender.toCoreChannels` just copies this module's `microsByChannel` list verbatim into a new `mavlink-core.RcChannels`, and the translation happens entirely on that side. Adding an unused `wireValue`-equivalent here would be exactly the kind of speculative, never-called method `.claude/skills/java-clean-code/SKILL.md` warns against. This module's own range narrowing (`MAX_CHANNELS=16` on `RcChannels`, `[1,16]` on `ControlBinding`) is F17's half of the same fix, enforced independently on both sides of the module boundary so a bad value can never cross it either direction.
- **A stored `ControlProfile`/`ControlBinding` from before this narrowing (CH17/18) fails loudly on load, not silently.** `storage/persistence`'s `ControlProfileEntity` stores `List<ControlBinding>` as JSON (`@JdbcTypeCode(SqlTypes.JSON)`); Hibernate's deserialization re-invokes this record's own compact constructor, so a legacy row bound to channel 17 or 18 throws `IllegalArgumentException` at *read* time. `storage/persistence`'s `JpaOperations.read` has no catch block, so that exception propagates unmodified through the repository and the application service to `vision-api`'s global `ApiExceptionHandler`, which maps `IllegalArgumentException` to HTTP 400 — a human-visible error on the next load of that profile, never a quietly-truncated one. No code in `storage/persistence` needed to change for this — the "fail loudly at read time" behaviour was already the entity's own documented design intent (see its javadoc), and F17's range narrowing simply gives it a real case to catch.
- **A `ControlProfile`'s two invariants are about accidents, not typos** — "the same physical control bound twice" and "the same RC channel driven twice" are both rejected in the compact constructor, so a bad assignment fails at *save*, not at *fly*.
- **A switch-kind `ControlBinding` ignores the raw stick value and sends a detent** — `SWITCH_2`/`SWITCH_3` quantize through `SwitchPosition.of` to `min`/`center`/`max`; `reversed` flips the *position* (`LOW ↔ HIGH`), not the microseconds.
- **`ControlProfileId.builtIn(kind)` is derived, not stored** — a UUIDv3 over a fixed namespace string. The built-in ids are stable across restarts/machines, but changing that namespace string or a `VehicleKind` name silently changes an id, which would make every stored `active` pointer at a built-in dangle. Nothing stores one today (`OwnedControlProfile` refuses to wrap a built-in), which keeps that safe.
- **`ControlProfileService` has no `VisibilityScope` gate, unlike every other service in this module** — deliberate: a stick layout is owned by one user, so the authority question is "is this yours", not "is this asset in your scope".
- **`DefaultManualControlService` depends on `ControlProfileSelector`, not `ControlProfileService`** — and defaults to `builtInOnly()`. A 6-arg construction therefore silently ignores saved profiles; only the 7-arg one honours them. A missed wiring shows up as "my saved layout does nothing", never as a crash.
- **`VehicleKind.UNKNOWN` no longer gets a flyable map (FLEET-RADIO R2)** — before this wave, `ControlProfile.forKind(UNKNOWN)` returned a centred four-axis map, and a centred throttle is ~50% power: not safe on a multirotor. There is no safe *default* for a vehicle that never said what it is, and R1 deliberately did not invent one — R2 stops trying: `forKind(UNKNOWN)` now returns an empty `ChannelMap`, and `DefaultManualControlService#engage` refuses to open a session on an `UNKNOWN`-kind link at all, with a reason (`UnidentifiedReason`) the operator can act on rather than a silently-armed 50%-throttle guess. The fix a genuinely unidentified vehicle needs is still a heartbeat (or an operator who can see it and says what it is), never a better guess baked into this module.
- **The three-way `UnidentifiedReason` distinction exists because "refused" is not one fact.** `NOT_A_VEHICLE` (a gimbal/GCS shares this link), `UNSUPPORTED_VEHICLE` (a real airframe this platform doesn't fly), and `NEVER_IDENTIFIED` (a genuinely unseen `MAV_TYPE`) have three different operator remedies, and collapsing them into one refusal message would make "a gimbal is on your link" indistinguishable from a correct, boring refusal. `VehicleKind` itself stays exactly 4 values (`COPTER|PLANE|ROVER|UNKNOWN`) — a **control-shape** taxonomy that only needs to answer "what `ChannelMap` applies", where all three unidentified cases genuinely need the same answer (none) — while `UnidentifiedReason` carries the operator-facing "why", read once at `engage` refusal time and nowhere else in the control path. Widening `VehicleKind` itself was rejected: every `ControlProfile.forKind`/`ControlProfileSelector`/`ControlProfileRepositoryPort` switch would gain 2 more cases whose channel map is identical to `UNKNOWN`'s (empty), for zero behavioral gain over a second, orthogonal enum consulted only at the refusal boundary.
- **`GeofenceMonitor` must not take perception's `UsageTracker` directly** — `UsageTracker` (perception) declares a plain `BiConsumer<AssetId,Telemetry>` seam and `vision-app` wires `geofenceMonitor::evaluate` into it. Any future "perception needs to react to a flight-context fact" need should reuse this functional-seam pattern, not add a constructor parameter naming the other context's type.
- **`GeofenceMonitor`'s per-`(assetId,zoneId)` breach state is in-heap only and resets on every restart** — an asset already inside a `KEEP_OUT` zone at boot reports a spurious "enter" on the next sample; a zone deleted/disabled mid-breach never gets a synthetic "exit".
- **`GeofenceMonitor`'s enabled-zone cache has two refresh paths, and both matter**: `GeofenceService` calls `refresh()` synchronously after every CRUD write; `evaluate()` also self-populates lazily on its own first call. Skipping either is a real bug, not redundancy.
- **A `KEEP_IN` breach with 2+ enabled `KEEP_IN` zones can fire one event per zone simultaneously** — the "outside every enabled zone" condition is computed once per sample and shared across every zone's own per-zone state entry. Known, accepted edge case.
- **`maxAltitudeMeters` only has an effect on a `KEEP_IN` zone** — a `KEEP_OUT` zone breaches at any altitude per the frozen rule.
- **Command-gate exception mapping is deliberately asymmetric between reads and writes**: a scoped *read* (`capabilities`) hides an out-of-scope asset as 404; a *command* instead 403s and audits the denial.
- **`DefaultFlightCommandService`'s IAE→ISE translation exists so `vision-api`'s exception handler needs no endpoint-specific carve-out** — `IllegalArgumentException`→400 stays global for every other endpoint; only this one call site catches the port's `IllegalArgumentException` and rethrows as `IllegalStateException`.
- **`FlightPhaseRule` has two entry points, not one function** — "session closed while armed" fires when the platform stops observing (the session itself ends), not on any telemetry sample. `nextPhase` is the sample-driven half; `onSessionClosed` is the explicit-close half.
- **A firmware rename is a comparison problem, not a data problem** — `ReadinessService` and `ParameterTier` both route parameter-name comparisons through `ParameterAliases`, and `ParameterReading` is left carrying the exact name the vehicle answered under. Normalising at probe time was rejected: it would make a profile claim a reading the vehicle never gave, breaking `ParameterReading`'s "only what was actually read" invariant. Adding a newly-renamed parameter means one entry in `ParameterAliases.GROUPS` — not a migration, and not a patch at each comparison site. Before this existed, `V18`'s `fleet-identity` row wanted `SYSID_THISMAV` while the probe read `MAV_SYSID`, so the row was `MISSING` on every ArduPilot vehicle of every generation, which made the readiness verdict a constant `NO_GO` (docs/plans/active/FLEET-RADIO-PLAN.md F0). The `V18` row is deliberately **not** rewritten — either spelling now satisfies it.
- **`ParameterTier.PATTERNS` is a representative seed, not a verified-complete enumeration** — illustrative ArduPilot parameter names, not cross-checked against firmware source. Tightening the list only ever removes writability that was never explicitly granted.
- **`RC_OPTIONS` classifies Tier B (FLEET-RADIO R6)**, alongside `RC_FS_TIMEOUT`/`RC*_OVERRIDE_.*` — same "link/failsafe behavior, writable with consent, never flight-critical-geometry" class. Without this, `rc-relay`'s R6 `PARAM_WRITE` remedy would recommend a write `DefaultRemediationService#writeParameter` refuses outright (`ParameterTier.classify` empty/`C` → 400 before the asset is even looked up), an honesty gap the readiness row's remedy would otherwise silently promise and never deliver.
- **The onboarding authority predicate (`canManage`/`canAdminister`) diverges from every pre-onboarding command gate in this module (`includes`)** — the plan's own table, not drift; do not "fix" it into consistency with the older code.
- **`ReadinessService` evaluates only half of "readiness"** — the configuration-derived half. The telemetry-derived half (video/telemetry/GPS/battery/armable) is not merged into `ReadinessReport` — doing so honestly needs a live-telemetry collaborator and named threshold sources for battery/GPS (no magic numbers).
- **FLEET-RADIO R6 — two rows under one key, deliberately, not two new frozen keys.** `FeatureRequirement.FEATURE_KEYS` stays the frozen eleven: a GCS-sysid mismatch and `RC_OPTIONS` ignoring overrides are two independent ways a MAVLink RC override silently fails to reach the servos, but `ReadinessRowResponse` (`vision-api`'s fleet-board wire shape) is a `{featureKey: status}` map that structurally cannot hold two statuses under one key regardless of how many domain keys exist — `V18__feature_requirements.sql`'s own header comment already hit this exact limit once (`preflight-checks`, `GPS_RAW_INT`+`STATUSTEXT`). Extending `FEATURE_KEYS` would not have avoided that wire constraint, only added a key the map still could not carry independently — so both facts are seeded as two rows sharing `rc-relay` (V27) and folded into one `FeatureReadiness` by `DefaultReadinessService#combine` before either ever reaches the wire. The alternative this rejects: inventing e.g. `rc-relay-sysid`/`rc-relay-options` as two new frozen keys, which would still need the exact same fold-into-one-row step at the `vision-api` boundary (a fleet-board tile is one cell per feature) while additionally breaking every existing `FEATURE_KEYS.size() == 11` assumption in this module's own tests and its consumers.
- **`CLEAR_OVERRIDES_BY_RC` (ArduPilot `RC_OPTIONS` bit 14) is adjacent to R6's bit 1 and deliberately not modeled as a readiness blocker.** With it set, an operator touching the physical transmitter sticks silently ends manual control mid-session — but unlike GCS-sysid/`IGNORE_OVERRIDES`, this is the vehicle's *designed* pilot-override behavior, not a link misconfiguration, and this table only ever sees a vehicle's static parameter values, never live-stick telemetry — there is no way to check "is the pilot's own RC currently moving a stick" from a `VehicleProfile`. Surfacing it usefully needs a telemetry-derived signal this service does not have (the same documented gap as the rest of "readiness" — see the entry above). Left as a fact for whoever next extends this table with that telemetry-derived half; V27's own migration header carries the same reasoning.
- **`RemediationResultCode`/`MessageIntervalOutcome`/`ParameterWriteOutcome` are not named in the onboarding plan's own type list** — added because `VehicleConfigPort`'s write/message-interval methods need an honest return type; naming stayed inside the frozen vocabulary rather than inventing new spellings.
- **`linkKeyOf(Device)` is duplicated, not shared, between `DefaultVehicleProfileService` and `DefaultRemediationService`** — both derive `"udp://host:port#sysid"` from `device.stream().uri()` + `options.get("sysid")`. A third caller needing the same derivation should prompt extracting it.
- **`probeCandidate` has no authority/audit model at all** — by design: registration is the last stage, so no `Asset`/ownership exists yet to gate against. This means *any* caller holding a `VehicleProfileService` reference can probe an arbitrary `linkKey` with no scope check — `vision-api`/`vision-app` must restrict which endpoint/role can reach this method, since this module has nothing to enforce it against.
- **`passport`/`driftFromPreviousFlight`'s asset-ownership check (`requireUsageBelongsToAsset`) is deliberately *not* built on `AssetDetails#recentUsages()`'s 20-item cap** — a passport's whole purpose is answering "what was this aircraft's configuration on *that* flight", routinely not one of the last 20. It delegates to warehouse's `UsageSessionService#usageBelongsToAsset(UsageId, AssetId)` — an uncapped boolean, not an `AssetUsage` fetch — throwing `NoSuchElementException` on a `false` result. Filed on `UsageSessionService` rather than `UsageService` deliberately: every `UsageService` method takes a `VisibilityScope` and this check does not (the asset is already scope-gated by the caller) — an unscoped method beside `UsageService`'s all-scoped ones would be a footgun the next reader could copy without noticing. `driftFromPreviousFlight`'s separate "find the previous flight" traversal stays on the capped `recentUsages()` on purpose — two compared flights are adjacent by definition, so the previous one is always well inside any reasonable recent-window size; `current` is resolved from that same capped list (provably safe: if the real current usage fell outside it, every entry remaining would be newer, so the "find an older one" search would find nothing either way).
- **`driftFromPreviousFlight` compares the *previous* flight's `POSTFLIGHT` snapshot against the *current* flight's `PREFLIGHT` snapshot** — not two consecutive `PREFLIGHT`s or `POSTFLIGHT`s. The disarmed-only write interlock means a parameter can only actually change between one flight's landing and the next one's arming, so that is the only pair of snapshots a real drift could show up between.
- **`DefaultTrackCorrectionService` always uses `divergence.defaultRawRadiusMeters()`, never a real HDOP-derived raw radius.** No HDOP→meters conversion exists anywhere in this codebase today (`Telemetry`/`FlightState` carry only the dimensionless `hdop`); inventing an unsourced conversion formula would violate the no-magic-numbers rule, so this service always uses the configured default instead (docs/plans/done/VISUAL-GEO-V2-PLAN.md §4.5 amendment).
- **`TrackCorrectionService#forUsage`/`#latest`'s `VisibilityScope.Kind.GROUPS` case is pass-through (unfiltered), not enforced.** This service's frozen 4-argument constructor has no warehouse dependency to resolve an asset's `Ownership` from, so `UNBOUNDED`/`ASSIGNED_ASSETS` are enforced but `GROUPS` cannot be. The intended real gate is at the `vision-api` edge: resolve the asset via warehouse's scoped `AssetService#details(scope, assetId)` (which does enforce `GROUPS`) *before* calling this service. Until that wiring exists, a MANAGER-scoped caller of this service directly would see every asset's corrections, not just their group's.
- **`first_armed_at`/`last_disarmed_at` on `asset_usages` are schema-only, mapped to no domain field.** They live on `AssetUsage` (`vision-warehouse`'s type). `FlightPassport`/`ConfigDriftCalculator` key entirely off `VehicleProfile.observedAt()` plus `AssetUsage.startedAt()`, never off arm/disarm timestamps — a future "time armed" passport field needs a `vision-warehouse` change, not a `vision-flight` one.
- **WAREHOUSE-UX W5 — maintenance blockers only come from warehouse, and only two `MaintenanceKind` values ever block.** `DefaultReadinessService#maintenanceBlockers` filters `maintenanceQuery.openBlockers(assetId)` defensively to `MaintenanceRecord#isOpen()` and `MaintenanceKind#blocksFlight()` (true only for `GROUNDING`/`INSPECTION_DUE`; `REPAIR`/`NOTE` are informational-only and never appear in `blockers`) rather than trusting `MaintenanceQuery#openBlockers`'s own "open, blocking only" contract alone — the same "defense in depth, not the mechanism" posture this module already applies to `ControlProfile.forKind(UNKNOWN)` (see that Gotchas entry above). A closed record, or an open `NOTE`/`REPAIR` record, is silently invisible here by design, not a bug.
- **WAREHOUSE-UX W5 / FLEET-RADIO R6 `vision-app` wiring breakage — RESOLVED (verified in-tree 2026-09-01, ASSET-FLOWS R1).** `OnboardingWiringConfiguration#readinessService` now passes warehouse's `MaintenanceQuery` bean and `ApplicationServiceWiring#manualControlService` passes `ReadinessService`; the `MaintenanceQuery` bean and its persistence implementation exist and the grounding→readiness gate is wired end to end. Historical detail lives in git history of this file.
- **`LinkLossNotifier.reportLinkLost` has exactly one intended call site, and this wave (S4/BK2) could not wire it.** The already-merged FLEET-RADIO R4/F7 typed link-failure signal (`mavlink-core`'s `MavlinkSession#onLinkFailure`, `PeerId`-carrying) reaches project code today only as the `IOException` a device's supervised `TelemetrySourcePort#open` publisher closes exceptionally with, at perception's `UsageTracker#subscribeTelemetry` — which wraps every telemetry subscription in a `SupervisedPublisher<Telemetry>` and passes a **hardcoded no-op `cause -> { }`** as its `onOutageBegan` callback (`contexts/vision-perception/src/main/java/com/drones/vision/perception/application/pipeline/UsageTracker.java`, the `subscribeTelemetry` method). That callback fires exactly once per outage by construction (`SupervisedPublisher`'s own guarantee), so it is precisely the edge-only signal `reportLinkLost` needs — and the asset id is already in scope there (`asset.id()`, resolved before the port is ever opened), so no cross-context `PeerId→AssetId` resolution port is needed either. `UsageTracker.java` was reserved this wave for a concurrent, unrelated change (an S1 gate), so the fix is documented rather than made: replace that `cause -> { }` with `cause -> linkLossNotifier.reportLinkLost(asset.id(), "MAVLink link to " + asset.name() + " lost")`, threading a `LinkLossNotifier` (already a `vision-app` bean, see `station/vision-app/MODULE.md`) into `UsageTracker`'s constructor (bundled into `UsageTrackerSettings` per this repo's no-overload rule, not a new positional parameter). Until that one-line change lands, `LINK_LOST` events are fully implemented, tested, and wired as far as the bean graph goes, but nothing in production ever calls `reportLinkLost`.
- **`BatteryMonitor` is composed into `GeofenceMonitor`'s existing wiring seam, not a second slot.** `UsageTrackerSettings` has exactly one `Optional<BiConsumer<AssetId,Telemetry>> telemetryObserver` slot; `vision-app`'s `ApplicationServiceWiring#usageTracker` now passes a lambda that calls `geofenceMonitor.evaluate(...)` then `batteryMonitor.evaluate(...)`, both against the same sample — same rationale as the existing `GeofenceMonitor` Gotchas entry above ("must not take perception's `UsageTracker` directly"): a functional seam composes, it does not grow constructor parameters on either side of the module boundary.
