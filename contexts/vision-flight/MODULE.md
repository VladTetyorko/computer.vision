# vision-flight

Flight sessions, telemetry transport, geofencing, and guarded flight command/manual control. Domain +
application in one module (docs/plans/active/DOMAIN-SEPARATION-W1.md §16 — the eight-context split
dissolved `vision-domain` and `vision-application`; this module holds flight's `.domain`/
`.application` packages together, the same layer boundary ArchUnit still enforces).

**What it deliberately does not do**: hold the actual `AssetUsage`/flight-session record any more —
that moved to `vision-warehouse` in **W1.6c** (C9), since every one of its readers
(`AssetDetails`/`DefaultAssetService`/`DefaultAssetStatsService`/`DefaultUsageService`) already lived
there; this context now only *produces* the telemetry samples a usage accumulates. It does not carry
`Telemetry`/`FlightState` as its own types either — both moved to **`vision-kernel`** in the same
wave (pure records, no ports, read by five contexts — the platform's shared payload in exactly the
way `GeoPosition`/`BoundingBox` already are). It does not run the video/telemetry ingest pipeline
itself (perception's `UsageTracker`/`StreamPipeline` do, subscribing to this context's
`TelemetrySourcePort`) and does not resolve who may command what (`VisibilityScope`, checked here as
a parameter, lives in `vision-platform`).

**Depends on:** `vision-kernel` (`Telemetry`, `FlightState`, every id, `GeoPosition`…) ·
`vision-platform` (`Event`/`EventPublisherPort`/`EventLiveUpdatePort` — `GeofenceMonitor` raises
`GEOFENCE_BREACH`; `AuditTrailPort`/`AuditEntry` — every command attempt is audited;
`VisibilityScope`/`AccessDeniedException` — the command/manual-control gates) ·
**`vision-warehouse`** — a flight command resolves the asset it acts on: `DefaultFlightCommandService`
and `DefaultManualControlService` both resolve the target via warehouse's `AssetService#details`
before ever touching a `Device`, so they can apply the scope gate and pick which of the asset's
devices to command; **O3** (docs/plans/active/DRONE-ONBOARDING-PLAN.md) added a second warehouse port
consumer — `DefaultRemediationService` reads warehouse's `AssetLiveStatePort#latestTelemetry(AssetId)`
for the disarmed-only interlock — no new context edge, `AssetLiveStatePort` is warehouse's own public
surface and flight already depended on that module. No other context. **Used by:** `vision-perception`
(the `UsageTracker`/`GeofenceMonitor` wiring seam, see Gotchas), `vision-api`, `vision-app`,
`adapter-mavlink` (O4's `MavlinkVehicleConfigurator` is the expected `VehicleConfigPort` implementation).
**Build/test:** `./mvnw -B -pl contexts/vision-flight test` — 238 tests green (144 pre-O3 + 72 added by O3 + 22 added by O11).

## API surface

### `com.drones.vision.flight.domain.model`
- `record ChannelMap(List<ControlBinding> bindings)` (docs/plans/done/RC-CONTROL-PHASE1-PLAN.md §1/§5) — a full axis/button → RC-channel map; `bindings` defensively copied; `static defaultMap()` returns the frozen v1 table (gamepad axes 0–3 → RC channels 1–4 centered 1500µs, buttons 0–3 → channels 5–8, channels 9–18 unused); `RcChannels apply(List<Double> axes, List<Double> buttons)` — a missing/out-of-range/`null` index reads as `0.0` (never throws), assembles channels 1..N (N = highest `rcChannel` any binding targets, or 1 if empty); an unbound channel is `RcChannels#IGNORE`
- `enum CommandResult` (docs/plans/active/DRONE-INFRA-PLAN.md I-e Stage 1) — `ACCEPTED`/`NO_ACK`, the outcome of a `FlightCommandPort` call; an explicit refusal is deliberately not a value here — see `FlightCommandPort`'s own javadoc, that case is a thrown `IllegalStateException` instead. Pure marker, no dedicated test
- `record ControlBinding(Source source, int sourceIndex, int rcChannel, int minMicros, int centerMicros, int maxMicros, double deadband, boolean reversed)` — one physical gamepad control (`enum Source { AXIS, BUTTON }`) mapped to one RC channel with linear calibration; `int toMicros(double normalized)` — `AXIS` maps `[-1,0]`/`[0,1]` piecewise-linearly through `centerMicros`; `BUTTON` maps `[0,1]` straight onto `[minMicros,maxMicros]` — `centerMicros` plays no part in a button's own mapping (see Gotchas)
- `record FlightCapability(boolean commandable, boolean armSupported, boolean modeSelectSupported, List<String> selectableModes)` (docs/plans/active/DRONE-INFRA-PLAN.md I-e Stage 2) — a best-effort snapshot of what flight commands a device's aircraft accepts; `armSupported`/`modeSelectSupported` never `true` when `commandable` is `false`; `static notCommandable()` = all-false + empty list
- `record GeofenceZone(ZoneId id, String name, ZoneKind kind, List<GeoPosition> polygon, Double maxAltitudeMeters, boolean enabled)` (docs/plans/done/OPS-CORE-PLAN.md §G) — polygon ≥3 vertices, implicitly closed; `maxAltitudeMeters` nullable, non-negative if present; zones are global (no per-asset/per-group scoping). `boolean contains(GeoPosition)` — ray-casting point-in-polygon treating lat/lon as planar Cartesian (see Gotchas for the accuracy caveat). `withEnabled(boolean)`, `withDetails(...)` return copies
- `record RcChannels(List<Integer> microsByChannel)` — one 1-based microsecond value per RC channel, the payload `ManualControlPort` relays as a MAVLink `RC_CHANNELS_OVERRIDE` (#70) frame; constants `RELEASE=0`, `IGNORE=0xFFFF`, `MIN_MICROS=1000`, `MAX_MICROS=2000`; `static released(int channelCount)` — `RELEASE` for channels 1..count
- `record ZoneId(UUID value)` — `static random()`, `static of(String)`
- `enum ZoneKind` — `KEEP_IN | KEEP_OUT`, read by `GeofenceMonitor` to decide what "inside"/"outside" a zone's polygon means for breach purposes

**O3 additions** (docs/plans/active/DRONE-ONBOARDING-PLAN.md — vehicle onboarding: probe, readiness, remediation):
- `enum FlightPhase` — `PREFLIGHT | IN_FLIGHT | LINK_LOST | POSTFLIGHT | ABANDONED | CLOSED`, the frozen §8.1 wire spelling (the enum name **is** the wire string); `IDLE` deliberately absent — that is "no `AssetUsage` exists yet", not a phase to stamp on one
- `final class FlightPhaseRule(Duration silenceWindow, Duration abandonWindow)` — the pure phase-transition function (§2.3); ctor validates both positive and `abandonWindow >= silenceWindow`. `FlightPhase nextPhase(FlightPhase currentPhase, FlightState state, Duration linkAge, int streamCount)` — the sample-driven half; reads `state.armed()` via `Boolean.TRUE/FALSE.equals(...)`, never unboxes (C7 — `armed == null` is never "false"); `streamCount` only ever gates the never-armed `PREFLIGHT`/`POSTFLIGHT` → `CLOSED` transition, never `IN_FLIGHT`/`LINK_LOST`. `FlightPhase onSessionClosed(FlightPhase currentPhase)` — the explicit-close half (`IN_FLIGHT`/`LINK_LOST` → `ABANDONED`, everything else → `CLOSED`); **two entry points, not the plan's literal one function**, because "session closed while armed" fires when the platform stops observing, not on a telemetry sample — see Gotchas
- `record VehicleProfile(String linkKey, Instant observedAt, Integer sysid, String firmware, String firmwareVersion, String vehicleKind, Long capabilityBitmask, List<String> capabilityFlags, List<MessageObservation> messages, List<ParameterReading> parameters, Long linkBytesPerSecond, boolean complete, String incompleteReason)` (§3.1/§5.1) — the PROBE stage's observed snapshot, keyed by `linkKey` (pre-registration identity, e.g. `"udp://0.0.0.0:14550#7"`) rather than `DeviceId`; `complete == false` requires a non-blank `incompleteReason` and vice versa (C7 — "probably fine, didn't check" cannot be represented); `capabilityBitmask` deliberately **not** validated non-negative (a `uint64` high bit is a legitimate negative `long`); null lists normalize to empty rather than throwing
- `record MessageObservation(int messageId, String name, double hz, long count)` — one passively-inventoried message rate; `name` nullable (unresolved dictionary entry, still counted)
- `record ParameterReading(String name, double value, String type)` — one parameter actually read; "only what was actually read" (§5.3) — an unanswered request has no entry, never a fabricated zero
- `enum ParameterTier { A, B, C }` (§4a/D9, ANY-DRONE-PLAN.md §1.3) — `static Optional<ParameterTier> classify(String parameterName)` matches a seeded regex allowlist (representative, not verified-complete — see this type's own javadoc); `boolean everWritable()` — `false` only for `C`. **The allowlist is domain code, not a UI convention** — a screen that forgets to hide a button is still refused here
- `record FeatureRequirement(String featureKey, String label, String firmware, Integer requiredMessageId, String requiredMessageName, Double minimumHz, String requiredParameterName)` (§5.1/D6) — one seeded requirement row; `public static final Set<String> FEATURE_KEYS` is the frozen §8.1 eleven-key set, enforced in the compact constructor (a typo'd key fails fast at construction); `requiredMessageId` present ⇒ `requiredMessageName` non-blank and `minimumHz` non-negative, both required together; a row with neither message nor parameter requirement is valid — it declares "firmware supports this feature" without a concrete telemetry check (e.g. `command-tx`)
- `enum FeatureStatus { READY, DEGRADED, MISSING, UNKNOWN }`, `enum RemedyKind { MESSAGE_INTERVAL, PARAM_WRITE, CLI_SCRIPT, MANUAL }`, `enum ReadinessVerdict { GO, NO_GO, UNKNOWN }` — frozen §8.1 wire spellings, enum name = wire string
- `record FeatureReadiness(String featureKey, String label, FeatureStatus status, String detail, RemedyKind remedy)` — one `ReadinessReport` row; `featureKey` validated against `FeatureRequirement.FEATURE_KEYS`; `detail` never blank (C7 — absent evidence says why); `remedy` nullable
- `record ReadinessReport(AssetId assetId, ReadinessVerdict verdict, Instant evaluatedAt, Instant profileObservedAt, List<FeatureReadiness> features, List<String> blockers)` (§3.1 NEGOTIATE output) — placed in `domain.model`, not `application`, per the plan's own module-placement table (§7); `profileObservedAt` is `null` when never probed (an honest, renderable `UNKNOWN`, not a 404 — the read's own scope gate is `ReadinessService`'s job, not this type's)
- `enum RemediationResultCode { ACCEPTED, DENIED, NO_ACK, UNSUPPORTED }` — frozen §8.1 `RemediationResult.actions[].outcome` spelling; **not named as its own type in the plan's module-placement table** — added to give `VehicleConfigPort`'s write/message-interval methods an honest return type instead of a boolean; flagged as an extension filling a genuine gap
- `record MessageIntervalOutcome(int messageId, Duration interval, RemediationResultCode outcome, String detail)` — Mechanism A's outcome; not a write, nothing persists past the session
- `record ParameterWriteOutcome(String parameterName, RemediationResultCode outcome, Double previousValue, Double newValue, String detail)` — Mechanism B's outcome; a read-back that differs from the requested value is `DENIED` with `previousValue` set for the caller to restore to, never `ACCEPTED`

**O11 additions** (docs/plans/active/DRONE-ONBOARDING-PLAN.md O11 — "the flight passport": a `VehicleProfile` snapshot at `PREFLIGHT` and again at `POSTFLIGHT`, attached to the `AssetUsage`, plus the config-drift diff between consecutive flights):
- `record ParameterDrift(String parameterName, double previousValue, double currentValue, Instant previousObservedAt, Instant currentObservedAt)` — one changed parameter between two `VehicleProfile` snapshots; ctor rejects a blank name, a null timestamp, `currentObservedAt` before `previousObservedAt`, and `previousValue == currentValue` (`Double.compare`) — a `ParameterDrift` cannot represent a non-change, matching `ParameterReading`'s own "only what was actually observed" discipline (§5.3)
- `final class ConfigDriftCalculator` (pure function, private ctor, no state) — `static List<ParameterDrift> diff(VehicleProfile earlier, VehicleProfile later)`: both args `requireNonNull`; throws `IllegalArgumentException` if `later.observedAt()` precedes `earlier.observedAt()`. Compares parameters present **in both** snapshots by name; a parameter present in only one snapshot is never reported as drift (C7 — absence of evidence is not evidence of a removed/added parameter, it may simply not have been read this probe) and an unchanged value produces no row. Result sorted by `parameterName`, immutable (`List.copyOf`)
- `record FlightPassport(UsageId usageId, AssetId assetId, VehicleProfile preflightProfile, VehicleProfile postflightProfile)` — read model, not persisted as its own row (each half is a `VehicleProfile` row tagged by usage+phase); `usageId`/`assetId` reject `null` via `IllegalArgumentException` in the compact constructor, matching every other domain record here; both profiles are nullable — a passport for a flight whose `PREFLIGHT`/`POSTFLIGHT` snapshot was never captured (probe skipped, `VehicleConfigPort` unreachable, still `IN_FLIGHT`, etc.) is still a valid, renderable passport with a `null` half, never a fabricated one

### `com.drones.vision.flight.domain.port` (driven — implemented by adapters)
- `FlightCommandPort` (docs/plans/active/DRONE-INFRA-PLAN.md I-e — guarded command TX; **the one deliberate place the RX-only doctrine, `docs/main/CYCLES-PLAN.md` §0, is broken**): `boolean supports(Device)`; four blocking commands, each sending one MAVLink command and waiting briefly for the aircraft's own ack — `CommandResult setMode(Device, String modeName)`, `CommandResult arm(Device, boolean force)`, `CommandResult disarm(Device, boolean force)`, `CommandResult returnToHome(Device)` — plus one non-blocking, never-throwing `FlightCapability capabilities(Device)`. `arm`/`disarm`'s `force` uses the MAVLink `21196` magic value. Throws `IllegalArgumentException` for an unsupported device/firmware or unknown mode; `IllegalStateException` when the aircraft explicitly refuses. A lost/missing ack is neither (`CommandResult#NO_ACK`). One real implementation: `drone-link/mavlink`'s `MavlinkFlightCommander`
- `GeofenceRepositoryPort`: `GeofenceZone save(GeofenceZone)` upsert; `Optional<GeofenceZone> findById(ZoneId)`; `List<GeofenceZone> findAll()` snapshot, global; `void deleteById(ZoneId)` idempotent
- `ManualControlLink` — opaque, adapter-owned handle to one engaged `ManualControlPort` relay link; `boolean active()`
- `ManualControlPort` (docs/plans/done/RC-CONTROL-PHASE1-PLAN.md §1) — a streaming, ack-less RC-channel-override relay, the fire-and-forget, continuous-stream opposite of `FlightCommandPort`'s request→ack one-shots: `boolean supports(Device)`; `ManualControlLink engage(Device)` — opens a link + starts a fixed-rate sender thread, throws `IllegalArgumentException` if unsupported/unreachable; `void send(ManualControlLink, RcChannels)` — latest-wins mailbox, non-blocking; `void release(ManualControlLink)` — release-sentinel burst then stops the sender. Real implementation: `drone-link/mavlink`'s `MavlinkManualControlSender`
- `TelemetryLiveUpdatePort` (W1.6b, this context's slice of the former god-port `LiveUpdatePublisherPort`): `void publishTelemetryAppended(AssetId, Telemetry)` — announces one sample appended to an asset's open usage; must not throw, must return quickly
- `TelemetryRepositoryPort`: `void save(UsageId, Telemetry)` append-only; `List<Telemetry> findByUsage(UsageId, int limit)` — returns the **earliest** samples, not latest (see events' `DefaultReplayService` Gotchas for the consequence)
- `TelemetrySourcePort`: `boolean supports(Device)`; `Flow.Publisher<Telemetry> open(Device)` — per-open, hot/live, latest-wins backpressure; `void close(DeviceId)` idempotent

**O3 additions** (docs/plans/active/DRONE-ONBOARDING-PLAN.md §3.1/§3.2):
- `VehicleConfigPort` — talks to a vehicle over its own protocol for onboarding; every method takes a `String linkKey` (`"udp://host:port#sysid"`), **not** a `Device` — the pre-registration probe (stage 3) runs before any `DeviceId` exists, mirroring the plan's own sequence diagram. `boolean supports(Device)`; `VehicleProfile probe(String linkKey, Duration window)` — never throws for an incomplete answer; `MessageIntervalOutcome requestMessageInterval(String linkKey, int messageId, Duration interval)` — Mechanism A, not a write; `List<ParameterReading> readParams(String linkKey, List<String> parameterNames)`; `ParameterWriteOutcome writeParam(String linkKey, String parameterName, double value)` — Mechanism B, snapshot-before/read-back-after is the implementation's job, not the caller's. One expected implementation: `adapter-mavlink`'s `MavlinkVehicleConfigurator` (O4), riding the same shared socket `MavlinkHeartbeatScanner` already borrows
- `VehicleProfileRepositoryPort`: `void save(DeviceId, VehicleProfile)` append-only, never overwrites; `Optional<VehicleProfile> findLatest(DeviceId)` — keyed by `DeviceId`, same "key lives in the port call" idiom as `TelemetryRepositoryPort#save(UsageId, Telemetry)`. **O11 additions**: `void save(DeviceId, UsageId, FlightPhase, VehicleProfile)` — the tagged variant `captureSnapshot` uses, still append-only, still never overwrites, just carries two more key fields the untagged overload leaves absent; `Optional<VehicleProfile> findByUsageAndPhase(UsageId, FlightPhase)` — "the newest tagged row for this usage+phase", the lookup `passport`/`driftFromPreviousFlight` are built on
- `FeatureRequirementRepositoryPort`: `List<FeatureRequirement> findByFirmware(String firmware)` — empty for a never-seen firmware, read by `ReadinessService` as "every feature `UNKNOWN`", not an error; `List<FeatureRequirement> findAll()`

### `application` (root package — flight commands + RC relay)
- `FlightCommandService` (interface) → `DefaultFlightCommandService` — guarded flight command TX (docs/plans/active/DRONE-INFRA-PLAN.md I-e Stage 1 "bring it home", then Stage 2 arm/disarm+mode-select), behind `vision-api`'s `FlightCommandController`
  - `DefaultFlightCommandService(AssetService, FlightCommandPort, AuditTrailPort)` — `AssetService` is warehouse's
  - `CommandResult returnToHome(AssetId, UserId actor, VisibilityScope scope)` — `!scope.includes(asset)` → 403 (not the 404 a scoped *read* returns — a command should honestly say "you may not command this") **and the denial is audited**; resolves the asset via `AssetService#details` (404 unknown), picks the first **active** device `FlightCommandPort#supports` claims (zero matches → 409 naming the asset); the port's own `IllegalArgumentException` is caught and rethrown as `IllegalStateException` with the identical message so `vision-api`'s existing 409 mapping applies without a second special case; the port's own `IllegalStateException` propagates unchanged. One `AuditEntry` per actual command attempt — resolving *no* commandable device is not an attempt and is not audited
  - `CommandResult setMode(AssetId, String modeName, UserId, VisibilityScope)` / `arm(..., boolean force, ...)` / `disarm(..., boolean force, ...)` (Stage 2) — each mirrors `returnToHome` exactly via shared private helpers `resolveForCommand`/`sendAndAudit`. **Unknown-mode 400 vs not-commandable 409, the deliberate split**: `setMode` validates the mode against `capabilities(device).selectableModes()` **before** the port is called at all — unknown mode for a `modeSelectSupported()` vehicle → plain `IllegalArgumentException` (400), thrown outside `sendAndAudit`'s try/catch and **not audited** (nothing was sent); a not-commandable vehicle skips the mode check entirely and stays 409
  - `FlightCapability capabilities(AssetId, VisibilityScope scope)` — a **READ**: uses the scoped `AssetService#details(scope, assetId)` so unknown/out-of-scope both surface as 404 (not the commands' 403); an in-scope asset with no commandable device returns `FlightCapability.notCommandable()` rather than throwing; never audited
- `ManualControlService` (interface) → `DefaultManualControlService`, plus `ManualControlSession` (interface, one private `Default*`-style implementation) and `WatchdogListener` (interface) — docs/plans/done/RC-CONTROL-PHASE1-PLAN.md, Wave R2: a guarded, stateful, watchdog-supervised RC-channel-override relay session, the streaming/ack-less opposite of `FlightCommandService`'s request→ack one-shots
  - `ManualControlSession engage(AssetId, UserId actor, VisibilityScope scope, WatchdogListener onWatchdog)` — same scope-gate/device-resolution/audit idiom as `DefaultFlightCommandService`, reused verbatim; resolves the first active device `ManualControlPort#supports` claims; the port rejecting an unreachable device is rethrown as `IllegalStateException`, unaudited (no attempt was actually relayed)
  - **One session per service handle**: a second `engage()` while one is active throws `IllegalStateException` without touching the port. `vision-app` wires exactly one singleton bean, so this in practice serializes manual-control relaying app-wide — a deliberate Phase 1 simplification, not an oversight
  - `ManualControlSession#onChannels(axes, buttons, seq, tSent)` — maps through the session's `ChannelMap` and forwards to `ManualControlPort#send` (latest-wins), resets the watchdog deadline. `#release()` — idempotent, cancels the watchdog, audits `RELEASE`. `#channelMap()`, `#active()`
  - **Watchdog**: a single self-rescheduling `ScheduledFuture` per session, not cancel-and-reschedule-per-`onChannels` — `armWatchdog()` schedules once; each firing re-reads `lastInput` and either releases (audits `WATCHDOG`, calls `WatchdogListener#watchdogTripped()`) or reschedules for the remaining time
  - **Concurrency**: `onChannels`/`release()`/a scheduled watchdog check can each run on a different thread; one `AtomicBoolean released` (`compareAndSet(false,true)`) gates the single `doRelease` exit path; `lastInput` is `volatile` for single-writer/single-reader visibility only
  - **Constructors**: 3-arg production convenience (`Clock.systemUTC()` + a dedicated `"rc-watchdog"` daemon scheduler + `DEFAULT_WATCHDOG_TIMEOUT_MS=300`); 5-arg test seam (explicit `Clock`+`ScheduledExecutorService`); 6-arg canonical additionally takes `long watchdogTimeoutMs` — `vision-app`'s wiring should call this one directly with `vision.rc.watchdog-timeout-ms` for the property to actually take effect
  - **Audit**: mirrors `DefaultFlightCommandService`'s shape — `attrs = {assetId, command:"MANUAL_CONTROL", result}`, `result ∈ {ENGAGE, RELEASE, WATCHDOG, DENIED:out of scope}`. No `REFUSED` variant here (unlike the flight-command flow) — an engage the port rejected is "no attempt was actually relayed", same posture as the no-supports-device guard

**O3 additions** (docs/plans/active/DRONE-ONBOARDING-PLAN.md — vehicle onboarding):
- `VehicleProfileService` (interface) → `DefaultVehicleProfileService(AssetService, VehicleConfigPort, VehicleProfileRepositoryPort, AuditTrailPort)` — the PROBE stage
  - `VehicleProfile probe(AssetId, Duration window, UserId actor, VisibilityScope scope)` — a **command**, not a read: an active probe puts `REQUEST_MESSAGE`/`PARAM_REQUEST_READ` traffic on the aircraft's own link, so it gates on `scope.canManage(asset.ownership())` (the authority predicate), not `scope.includes(...)` — a denial is `AccessDeniedException` (403) **and audited** (`result = "DENIED:out of scope"`). Resolves the asset unscoped first (`AssetService#details(AssetId)` → 404 unknown), then the first **active** device `VehicleConfigPort#supports` claims (zero matches → `IllegalStateException`, 409, not an attempt, not audited). On success, persists via `VehicleProfileRepositoryPort#save` and audits `result = "COMPLETE"` or `"INCOMPLETE:<reason>"` from `profile.incompleteReason()`
  - `VehicleProfile latestProfile(AssetId, VisibilityScope scope)` — a **read**: uses the scoped `AssetService#details(scope, assetId)`, so unknown/out-of-scope/never-probed all collapse to the identical `NoSuchElementException` (404); never audited
  - `VehicleProfile probeCandidate(String linkKey, Duration window, UserId actor)` — the pre-registration probe (stage 3, D7): calls `VehicleConfigPort#probe` directly, no `Asset`/`Device`/scope/audit involved at all, since none exists yet
  - **O11 additions** (docs/plans/active/DRONE-ONBOARDING-PLAN.md O11 — extended, not a new service/interface, per java-clean-code §5: "can an existing service own this method instead of a new type? usually yes" — every collaborator `captureSnapshot`/`passport`/`driftFromPreviousFlight` need already exists on `DefaultVehicleProfileService`):
    - `VehicleProfile captureSnapshot(AssetId, UsageId, FlightPhase, Duration window, UserId actor, VisibilityScope scope)` — same authority/device-resolution/persist/audit shape as `probe`, plus two things `probe` doesn't do: rejects any `phase` other than `PREFLIGHT`/`POSTFLIGHT` with `IllegalArgumentException` (400, unaudited — a request-shape problem, checked before authority, same ordering precedent as `writeParameter`'s Tier-C short-circuit) and persists via the tagged `save(DeviceId, UsageId, FlightPhase, VehicleProfile)` instead of the untagged one. Audited via a dedicated `auditCapture` helper (`command="CAPTURE_SNAPSHOT"`, attrs add `usageId`/`phase` on top of `probe`'s `assetId`/`command`/`result`)
    - `FlightPassport passport(AssetId, UsageId, VisibilityScope scope)` — a **read**: scoped `AssetService#details` (404 unknown/out-of-scope) then `requireUsageBelongsToAsset` (404 if `usageId` isn't one of this asset's recent usages — see Gotchas for the leak this closes and the cap it inherits); looks up `PREFLIGHT`/`POSTFLIGHT` independently via `findByUsageAndPhase`, either or both `null` if not yet captured; never audited
    - `List<ParameterDrift> driftFromPreviousFlight(AssetId, UsageId, VisibilityScope scope)` — a **read**, same scope+membership gate as `passport`. Compares **the previous flight's `POSTFLIGHT` snapshot against the current flight's `PREFLIGHT` snapshot** — a deliberate design choice (see Gotchas, not stated explicitly by the plan): D10's disarmed-only interlock means a parameter write is only physically possible between one flight's landing and the next one's takeoff, so that is the only window a real config change can appear in. "Previous flight" is the nearest `AssetUsage` in `recentUsages()` with `startedAt()` before the current one's; no previous flight, or either endpoint snapshot missing, both return an empty list (never an error) — `ConfigDriftCalculator.diff` does the actual comparison once both are in hand
- `RemediationService` (interface) → `DefaultRemediationService(AssetService, AssetLiveStatePort, VehicleConfigPort, AuditTrailPort)` — the CONFIGURE stage's vehicle-side half (Mechanism A + Tier-A/B `PARAM_SET`)
  - `MessageIntervalOutcome requestMessageInterval(AssetId, int messageId, Duration interval, UserId actor, VisibilityScope scope)` — gate order: resolve asset (404) → `canManage` (403, audited) → disarmed-only (see below) → resolve device (409, not audited) → call port, audit `outcome.outcome().name()`
  - `ParameterWriteOutcome writeParameter(AssetId, String parameterName, double value, boolean explicitConsent, UserId actor, VisibilityScope scope)` — gate order, **Tier first, before the asset is even looked up**: `ParameterTier.classify(parameterName)` empty or `C` → `IllegalArgumentException` (400), unaudited, no asset resolution at all (D9 read literally: "not exposed at any authority level" means no authority check ever runs). Then resolve asset (404) → Tier B needs `scope.canAdminister()` (403, audited) **and** `explicitConsent == true` (else `IllegalArgumentException`, 400, unaudited — a request-shape problem checked only once authority is established); Tier A needs `scope.canManage(...)` (403, audited) → disarmed-only → resolve device (409) → call port, audit
  - **Disarmed-only (D10), both methods**: reads `AssetLiveStatePort#latestTelemetry(assetId).map(Telemetry::flightState).map(FlightState::armed)`; `armed == null` (no telemetry at all, or an unresolved `FlightState`) is refused **exactly like** `armed == true` — audited as `"REFUSED:arming state unknown"` vs `"REFUSED:aircraft is armed"` respectively, both as `IllegalStateException` (409)
  - **Authority divergence from `DefaultFlightCommandService`, flagged**: existing flight-command/manual-control gates use `scope.includes(asset.ownership())` (visibility); these O3 services use `scope.canManage(...)`/`scope.canAdminister()` (authority) per the plan's own §6.1 table — a deliberate, plan-mandated split within the same module, not an inconsistency to fix
- `ReadinessService` (interface) → `DefaultReadinessService(AssetService, VehicleProfileRepositoryPort, FeatureRequirementRepositoryPort)` (+ package-private 4-arg overload taking `Supplier<Instant> clock`, the test seam) — the NEGOTIATE stage
  - `ReadinessReport evaluate(AssetId, VisibilityScope scope)` — a **read**: `AssetService#details(scope, assetId)` (404 unknown/out-of-scope), never audited. Verdict rule ("absence of evidence is not evidence of readiness"): `UNKNOWN` whenever never-probed or the latest `VehicleProfile.complete() == false`; otherwise `NO_GO` iff any feature evaluates `MISSING` (collected into `blockers`), else `GO` — a `DEGRADED` or per-feature `UNKNOWN` (no requirement row for this firmware) is informational and never forces `NO_GO` by itself, matching the frozen §8.1 wire example. Evaluates **only the configuration-derived half** (profile vs. requirement table) — the telemetry-derived half (today's `derivePreflight` video/telemetry/GPS/battery/armable rows) is an intentional gap, flagged in Gotchas

### `application.geofence`
- `GeofenceService` (interface) → `DefaultGeofenceService(GeofenceRepositoryPort, GeofenceMonitor)` (docs/plans/done/OPS-CORE-PLAN.md §G) — CRUD/list over `GeofenceZone`s; zones are global reference data (no ownership, no audit trail), so this is a thin pass-through plus keeping `GeofenceMonitor`'s cache current
  - `List<GeofenceZone> zones()` sorted by name; `Optional<GeofenceZone> find(ZoneId)`; `create`/`update`/`delete` each call `geofenceMonitor.refresh()` afterward (`update`/`delete` 404 for an unknown id, checked before refreshing)
- `GeofenceMonitor` (public, final, no interface) — evaluates live telemetry against the enabled `GeofenceZone` set and raises `GEOFENCE_BREACH` events on edge transitions; reached from perception's `UsageTracker#applySample` **indirectly** — `vision-app` wires `geofenceMonitor::evaluate` into that tracker's `BiConsumer<AssetId, Telemetry>` seam, so perception never names this flight-context type (see Gotchas)
  - `GeofenceMonitor(GeofenceRepositoryPort, EventPublisherPort, EventLiveUpdatePort)` — both publisher params nullable; `EventLiveUpdatePort` (`vision-platform`) is one of five ports the former god-port `LiveUpdatePublisherPort` split into
  - `void refresh()` — reloads the enabled-zone cache from `findAll()` filtered to `enabled()`
  - `void evaluate(AssetId, Telemetry)` — ignores a sample with no lat/lon entirely; self-populates the cache lazily on first use if `refresh()` was never called. Breach rules (frozen): `KEEP_OUT` breaches iff inside the polygon at any altitude; `KEEP_IN` breaches iff at least one enabled `KEEP_IN` zone exists and the position is outside **every** enabled `KEEP_IN` zone (union computed once per sample), or inside this zone but above its own `maxAltitudeMeters`. Per-`(assetId,zoneId)` breach state is in-heap only; only an edge transition raises one `Event(GEOFENCE_BREACH, ...)` via both ports
- `GeofenceZoneSpec(name, kind, polygon, maxAltitudeMeters, enabled)` — one shape for both create and update; duplicates `GeofenceZone`'s own polygon-size/altitude validation for fail-fast

## Conventions
- **Validation**: domain records validate in their compact constructor; the application layer uses `Objects.requireNonNull`.
- **The acting user is a method parameter (`UserId actor`/`VisibilityScope scope`)**, never a constructor dependency.
- **Constructor injection only**, collaborators `Objects.requireNonNull`-wrapped.
- **Every port interface's javadoc documents Contract and Threading**; `TelemetrySourcePort` (backpressure concerns) adds a Backpressure section describing the latest-wins drop policy.
- **N-1-arg convenience constructor idiom** repeated across waves — e.g. `ManualControlSession`'s 6→5→3-arg chain.
- **Audit shape**: `AuditEntry.of(actor, action, targetType, targetId, summary, attrs)` with a short `result` token (`ACCEPTED`/`NO_ACK`/`REFUSED:<msg>`/`DENIED:out of scope`/`ENGAGE`/`RELEASE`/`WATCHDOG`) plus a human `summary` — the same result-vs-summary split every command/session flow here uses.

## Gotchas
- **`GeofenceZone.contains` is a planar approximation, not spherical geometry** (docs/plans/done/OPS-CORE-PLAN.md §G) — accurate at the scale a geofence actually operates at (tens of meters to a few km), but **not** valid near the poles or across the antimeridian (±180°). No attempt is made to detect/reject a pathological polygon spanning either.
- **`ControlBinding#toMicros` ignores `centerMicros` entirely for `Source.BUTTON`** — a button's mapping is a straight 2-point line from `minMicros` (unpressed) to `maxMicros` (pressed); `ChannelMap.defaultMap()`'s button bindings still set `centerMicros=minMicros` purely to satisfy the record's own `minMicros<=centerMicros<=maxMicros` invariant, not because it participates in the math.
- **`ChannelMap#apply` never throws on missing input** — an unreported/`null`/short `axes`/`buttons` list reads as `0.0` for whichever bindings fall outside it (deliberate: a browser gamepad frame that hasn't yet reported every axis/button must not crash the relay).
- **`GeofenceMonitor` used to take perception's `UsageTracker`/its `GeofenceMonitor` field directly — it does not any more, and must not again.** That direct dependency was the whole cause of the `flight`↔`perception` coupling C2 flagged. `UsageTracker` (perception) now declares a plain `BiConsumer<AssetId,Telemetry>` seam and `vision-app` wires `geofenceMonitor::evaluate` into it. Any future "perception needs to react to a flight-context fact" need should reuse this functional-seam pattern, not add a constructor parameter naming the other context's type.
- **`GeofenceMonitor`'s per-`(assetId,zoneId)` breach state is in-heap only and resets on every restart** — an asset already inside a `KEEP_OUT` zone at boot reports a spurious "enter" on the next sample; a zone deleted/disabled mid-breach never gets a synthetic "exit". Documented as an honest limitation, not fixed — persisting breach state was judged out of scope.
- **`GeofenceMonitor`'s enabled-zone cache has two refresh paths, and both matter**: `GeofenceService` calls `refresh()` synchronously after every CRUD write; `evaluate()` also self-populates lazily on its own first call (covers a monitor constructed after zones already exist in storage, or one never wired to a `GeofenceService` at all in a given deployment). Skipping either is a real bug, not redundancy.
- **A `KEEP_IN` breach with 2+ enabled `KEEP_IN` zones can fire one event per zone simultaneously** — the "outside every enabled zone" condition is computed once per sample and shared across every zone's own per-zone state entry. Known, accepted edge case (the frozen breach rule is stated as a single asset-level condition, not a per-zone one); the common single-zone case is unaffected.
- **`maxAltitudeMeters` only has an effect on a `KEEP_IN` zone** — a `KEEP_OUT` zone breaches "at any altitude" per the frozen rule, so a `maxAltitudeMeters` value stored on one is accepted (the record doesn't forbid it) but never consulted by `GeofenceMonitor`.
- **Command-gate exception mapping is deliberately asymmetric between reads and writes**: a scoped *read* (`capabilities`) hides an out-of-scope asset as 404; a *command* (`returnToHome`/`setMode`/`arm`/`disarm`/`engage`) instead 403s and audits the denial — "you may not command this" is judged more honest than pretending the asset doesn't exist, once the actor is attempting an action against it.
- **`DefaultFlightCommandService`'s IAE→ISE translation exists so `vision-api`'s exception handler needs no endpoint-specific carve-out** — `IllegalArgumentException`→400 stays global and unmodified for every other endpoint; only this one call site catches the port's `IllegalArgumentException` and rethrows as `IllegalStateException` (already 409-shaped).
- **`FlightPhaseRule` has two entry points, not the plan's literal one function** — the diagram's `IN_FLIGHT → ABANDONED: session closed while armed` arrow cannot be carried by a 4-argument `(phase, FlightState, linkAge, streamCount) -> phase` signature, because it fires when the platform stops observing (the session itself ends), not on any telemetry sample. `nextPhase` is the sample-driven half; `onSessionClosed` is the explicit-close half, called once by whatever drives the session (perception's `UsageTracker`, O7). Flagged for the plan author/reader rather than silently resolved.
- **`ParameterTier.PATTERNS` is a representative seed, not a verified-complete enumeration** — the exact ArduPilot parameter names are illustrative examples from §4a, not cross-checked against firmware source (the plan makes the identical caveat about Mechanism C's BF/INAV CLI keys). Tightening the list only ever removes writability that was never explicitly granted; it never silently grants new writability.
- **The O3 authority predicate (`canManage`/`canAdminister`) diverges from every pre-O3 command gate in this module (`includes`)** — see the `application` section above. This is the plan's own §6.1 table, not drift; flagged so a future reader does not "fix" it into consistency with the older code.
- **`ReadinessService` evaluates only half of "readiness"** — the configuration-derived half (profile vs. requirement table). The telemetry-derived half (§2.5's five `derivePreflight` rows: video/telemetry/GPS/battery/armable, today computed elsewhere against live `AssetAttention`) is not merged into `ReadinessReport` by this wave — doing so honestly needs a live-telemetry collaborator this wave's scope did not include, and inventing threshold numbers for battery/GPS without a named source would violate the no-magic-numbers rule. A future wave should either extend `DefaultReadinessService` with that collaborator or explicitly own the merge one layer up.
- **`RemediationResultCode`/`MessageIntervalOutcome`/`ParameterWriteOutcome` are not named in the plan's own type list** — added because `VehicleConfigPort`'s write/message-interval methods need an honest return type (the frozen §8.1 wire shape names the fields but not a Java type for them). Naming stayed inside the frozen vocabulary (`ACCEPTED`/`DENIED`/`NO_ACK`/`UNSUPPORTED`) rather than inventing new spellings.
- **`linkKeyOf(Device)` is duplicated, not shared, between `DefaultVehicleProfileService` and `DefaultRemediationService`** — both derive `"udp://host:port#sysid"` from `device.stream().uri()` + `options.get("sysid")`. Left as two small private methods rather than a new shared helper type, in keeping with this wave's file scope; a third caller needing the same derivation should prompt extracting it.
- **The pre-registration `probeCandidate` has no authority/audit model at all** — by design (D7: registration is the last stage, so no `Asset`/ownership exists yet to gate against), but this means *any* caller holding a reference to `VehicleProfileService` can probe an arbitrary `linkKey` with no scope check. `vision-api`/`vision-app` must restrict which endpoint/role can reach this method — this module cannot enforce it, since there is nothing here to enforce it against.
- **`passport`/`driftFromPreviousFlight`'s asset-ownership check for a `usageId` inherits `AssetDetails#recentUsages()`'s 20-item cap** (`DefaultAssetService`, `RECENT_USAGES_LIMIT`) — `requireUsageBelongsToAsset` 404s a `usageId` that genuinely belongs to the asset but has aged out of that window. Same accepted "fetch-then-aggregate" limitation `DefaultAssetStatsService` already lives with; not fixed here, since widening it is a warehouse-context decision (`AssetService#details`), out of this wave's file scope.
- **`driftFromPreviousFlight` compares the *previous* flight's `POSTFLIGHT` snapshot against the *current* flight's `PREFLIGHT` snapshot — not, say, two consecutive `PREFLIGHT`s or two consecutive `POSTFLIGHT`s.** This is a judgment call the plan does not spell out: D10's disarmed-only write interlock means a parameter can only actually change between one flight's landing and the next one's arming, so that is the only pair of snapshots a real drift could show up between. Flagged explicitly rather than silently picked, in case a future reader expects a different pairing.
- **`first_armed_at`/`last_disarmed_at` on `asset_usages` (added by `V19__asset_usage_phase.sql`) are still mapped to no domain field, deliberately, and this wave did not close that gap.** They live on `AssetUsage`, which is `vision-warehouse`'s type — out of this wave's strict `contexts/vision-flight`/`storage/persistence` file scope, and O5's own migration header already documents the same "schema-only on purpose" choice (see `storage/persistence`'s `v19MigrationAddsNullablePhaseColumnsOnTopOfV1ThroughV18` test). This wave's passport/drift design does not need them either way: `FlightPassport`/`ConfigDriftCalculator` key entirely off `VehicleProfile.observedAt()` (when a snapshot was actually captured) plus `AssetUsage.startedAt()` (already mapped), never off arm/disarm timestamps. A future wave adding "time armed" to the passport would need a `vision-warehouse` change (domain field + entity + mapper both directions + round-trip test), not a `vision-flight` one.
