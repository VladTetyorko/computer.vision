# vision-perception

The ingest and CV runtime: resolves a device's stream, decodes/samples/publishes video, runs
detection and tracking against it, burns in overlays, debounces detections into events, and probes
a device before it's trusted. Owns the stream's whole lifecycle from "start" to "stop," including the
asset-level orchestration of starting one (`AssetStreamService`) and the live-state facts warehouse
needs about it (`StreamBackedAssetLiveState`). Deliberately does **not** own asset/device inventory
(`vision-warehouse` — this context reads it, never the reverse), does not own flight-controller
command/telemetry transport itself (`vision-flight` — this context only opens the telemetry ports
`UsageTracker` needs, plus — since docs/plans/active/DRONE-ONBOARDING-PLAN.md Wave O7 — runs flight's
pure `FlightPhaseRule` state machine and translates its verdict into warehouse's `UsagePhase`; see
Status), and does not own replay/history (`vision-events` — a downstream reader of
this context, never a dependency of it). The largest of the eight contexts by a wide margin: 503
tests, 118 source files (345/91 when W1 landed — docs/plans/active/DOMAIN-SEPARATION-W1.md §16) — it
inherited the hot per-frame pipeline, the whole detect/track/overlay/event machinery, (via W1.6b/d/e
below) three features that used to be filed elsewhere by first-mover rather than by owner, and — from
the MEDIA-SOT/CV-RATE-CONTROL merge — the **pull-mode** detection driver plus the rate and latency
read models that explain what the sampler decided.

**Depends on:** `vision-kernel`, `vision-platform` (every context's baseline) · `vision-warehouse`
(a stream resolves its device via `DeviceRepositoryPort`/`DeviceService`; `AssetStreamService`
resolves the asset itself; this context **implements** warehouse's declared
`AssetLiveStatePort` — see Status; `UsageTracker` also reads/writes warehouse's `UsagePhase` enum on
`AssetUsage`, docs/plans/active/DRONE-ONBOARDING-PLAN.md Wave O7) · `vision-flight` (`UsageTracker`
opens `TelemetrySourcePort`/`TelemetryRepositoryPort`/`TelemetryLiveUpdatePort`, all flight-owned,
and — Wave O7 — runs flight's `FlightPhaseRule`/`FlightPhase`, translated to/from warehouse's
`UsagePhase` entirely inside this context; see Status for why that translation had to live here)
**Used by:** `vision-events` (replay reads perception's `DetectionRepositoryPort`), `vision-learning`
(training capture reads `StreamService#latestRawFrame`/`latestDetections`, `ModelRegistryPort`),
`vision-map` (geolocation reads live telemetry via the same seam), `vision-simulation`; most
adapters (`adapter-rtsp`, `adapter-mjpeg`, `adapter-v4l2`, `adapter-overlay`, `adapter-cv-grpc`,
`adapter-mavlink`, `adapter-simulation`, `adapter-persistence`, `adapter-publish-hls`); `vision-api`,
`vision-app`
**Build/test:** `./mvnw -B -pl contexts/vision-perception test`

## Package shape

```
com.drones.vision.perception.domain.model        26 records/enums
com.drones.vision.perception.domain.port         11 driven ports
com.drones.vision.perception.application.stream   stream lifecycle: StreamService, AssetStreamService,
                                                   StreamBackedAssetLiveState, config-patch records
com.drones.vision.perception.application.pipeline the hot path: StreamPipeline + its collaborators,
                                                   UsageTracker, the two registries
com.drones.vision.perception.application.device   ProbeService (moved in from warehouse, W1.6d)
```

No `port.in` package — driving interfaces collapse into one service interface + one `Default*`
implementation; commands/read-models are top-level records (`.claude/skills/java-clean-code/SKILL.md`).

## API surface

### domain.model — `com.drones.vision.perception.domain.model`
- `record AnnotatedFrame(VideoFrame frame, List<Detection> detections, Telemetry telemetry)` — `telemetry` (kernel type) nullable; `detections` defensively copied
- `record CameraAttitude(double yawDegrees, double pitchDegrees, double rollDegrees, double hfovDegrees, double yawRateDegreesPerSecond, Instant at)` (docs/conclusions/CV-RATE-BUDGET.md §2) — where the camera was pointing when a frame was captured, the input ego-motion compensation needs; `at` non-null (compact ctor). `static ofYaw(yaw, hfov, at)` for the heading-only case; `static from(Telemetry, hfovDegrees)` returns **`null`** when the sample is `null` or carries no heading — deliberately not a zeroed attitude, which would be indistinguishable from a genuine reading and would feed the compensator a fabricated delta on every telemetry dropout
- `record Detection(String label, double confidence, BoundingBox box, ModelRef model, TrackRef track)` — confidence [0,1]; `track` (docs/plans/done/TRACKING-PLAN.md §4.B) nullable = untracked — never a sentinel `TrackRef` with `trackId==0`; a 4-arg convenience ctor defaults `track=null`
- `record DetectionEvent(DetectionEventId id, StreamId streamId, AssetId assetId, String label, double peakConfidence, Instant firstSeen, Instant lastSeen, DetectionEventState state, GeoPosition position)` (docs/plans/done/MVP2-PLAN.md §E, E-a; **moved here from `events` in W1.6b** — it stores/shapes detections and only this context's `DetectionEventEngine`/`DefaultStreamService` ever construct it, filed by consumer not owner before that wave) — a debounced "label X was seen for a while" occurrence; `assetId`/`position` nullable (unresolvable device→asset, or no telemetry yet); `peakConfidence` [0,1]; `lastSeen`≥`firstSeen`; `withObservation(Instant,double)` advances `lastSeen`/raises `peakConfidence` (max), `closed()` flips `state`→CLOSED without moving `lastSeen`. `position` is stamped once, at open time, never updated afterward
- `record DetectionEventId(UUID value)` — `static random()`, `static of(String)`
- `enum DetectionEventState` — OPEN, CLOSED
- `record DetectionQuery(StreamId streamId, Instant from, Instant to, String label, int limit)` — all but `limit` nullable = "don't filter on this"; limit must be positive
- `record DetectionResult(StreamId streamId, long frameSequence, Instant capturedAt, List<Detection> detections, Duration inferenceLatency, TrackingTelemetry tracking)` — frameSequence≥0, latency≥0; `tracking` nullable = tracking was off for this result; a 5-arg convenience ctor defaults `tracking=null`
- `enum DetectionSource` — `DETECTOR | TRACKER`; which of the two tracking loops produced a `Detection` on a frame
- `enum DetectionState` — `OFF | IDLE_NO_VIEWERS | RUNNING` (docs/plans/active/CV-DEMAND-PLAN.md §3.6, wave D1) — which of the two independent detection gates explains a stream's current boxes-or-no-boxes state: `OFF` = `detectionEnabled=false` (the operator's own choice); `IDLE_NO_VIEWERS` = enabled but `StreamPipeline#detectionDemand()` is false (not a fault); `RUNNING` = both gates open. `OFF` takes precedence over `IDLE_NO_VIEWERS` when both hold. **Reports gating, never health** — a stalled/unreachable `DetectionPort` still reads `RUNNING` throughout its outage; that is what the pre-existing outage/backoff machinery and its `PIPELINE_ERROR` events are for, and the enum's own javadoc says so explicitly to head off exactly the "wire this to a status light" misuse
- `enum DetectorReason` — `ALWAYS | CADENCE | TRACKER_FAILED | NO_LOCK | BOX_INVALID | COASTED_OUT`; why a detector pass was spent; mirrors `cv.proto`'s enum minus `DETECTOR_REASON_UNSPECIFIED`
- `record EventRuleConfig(Set<String> labels, double confidenceThreshold, int consecutiveToOpen, Duration absenceToClose)` — debounce rule for `DetectionEvent`, referenced by `PipelineConfig#eventRule()`; `labels` empty = "track nothing"; `confidenceThreshold` [0,1]; `consecutiveToOpen`>0; `absenceToClose` positive; `static defaults()` = {person,car} @ 0.5, N=3, 5s absence. Moved here from `events` alongside `DetectionEvent` (it names no other type, but it is `EventRuleConfig`'s only reader that ever moved — the old `perception ↔ events` cycle C4 was this record living in `events` while `PipelineConfig` referenced it)
- `record FeedId(UUID value)` — `static random()`, `static of(String)`; identity for a transmitted feed
- `record FeedSpec(String protocol, URI source, Map<String,String> options)` — `protocol` lower-case-validated like `StreamDescriptor.protocol` (kernel); `source`/`options` non-null, no defaulting ctor; `options` defensively copied
- `record ModelRef(String id, String version)`
- `record PipelineConfig(ModelRef model, double confidenceThreshold, int inferenceFps, int maxInFlightInferences, boolean overlayTelemetry, Set<String> labelFilter, EventRuleConfig eventRule, boolean overlayBurnIn, boolean detectionEnabled, TrackingConfig tracking)` — inferenceFps/maxInFlightInferences>0; `eventRule` non-null; `overlayBurnIn` gates whether burn-in renders at all; `detectionEnabled` (docs/plans/done/CV-CONTROL-PLAN.md §1, Wave B) is the per-stream, **operator-intent** detect-on/off switch — one of two independent gates `StreamPipeline` ANDs together before it runs inference at all, the other being the system-derived `StreamPipeline#detectionDemand()` (docs/plans/active/CV-DEMAND-PLAN.md §1-2, wave D1; see `DetectionDemandPort`); `tracking` non-null. A four-deep chain of N-1-arg convenience ctors (6/7/8/9-arg) each default the field the wave before it added, ending at the 10-arg canonical. `static defaults()` = `yolo26n.pt`/latest, 0.4, 10fps, 2 in-flight, telemetry on, no filter, `EventRuleConfig.defaults()`, burn-in on, detection **off** (`DEFAULT_DETECTION_ENABLED=false` as of CV-DEMAND-PLAN wave D1, which flipped it from `true` — every convenience ctor picks this up too; a new stream is video-only until an operator turns detection on for it, since many concurrent streams must stay affordable by default; a deployment that wants the old always-on behavior back can restore it deployment-wide via `vision.cv.detection-default-enabled=true`, wave D2), tracking **`ASSOCIATE`** (docs/plans/done/TRACKING-PLAN.md Wave T8 — was `TrackingConfig.off()` through T2–T7). **Convenience ctors still default `TrackingConfig.off()`** — deliberate: a convenience ctor means "what you didn't mention keeps its old value," `defaults()` means "what should a new stream be," and conflating them would silently turn tracking on for every pre-T8 call site (`PipelineConfigTest` pins this with `assertNotEquals`). Turning tracking off is now an explicit act: `PATCH /api/streams/{id}/config`, or `vision.tracking.default-mode=OFF`
- `enum PixelFormat` — BGR24, RGB24, YUV420P, JPEG, H264_PACKET, UNKNOWN
- `record PullTelemetry(long decodeMillis, float sourceFps, float achievedFps, long droppedFrames, ...)` (docs/plans/active/MEDIA-SOT-PLAN.md §7) — what a **pulling worker** reports about the half of the loop this JVM can no longer see: it opens the source itself, so its decode cost, the rate it actually achieved, and the frames it dropped are facts only it holds. Rides the pull result stream and feeds `DetectionRateWindow`/`PipelineLatencyWindow` in pull mode
- `record TargetLock(long lockSeq, Long trackId, Double pointX, Double pointY, boolean release)` — which object `FOLLOW` should hold; restated every frame, applied by cv-service only when `lockSeq` is strictly greater than the last applied one (idempotent restatement, invariant P2). Accepts **exactly one** of three forms — `trackId`, `pointX`+`pointY` (normalized [0,1]), or `release=true`; rejects zero/two/three forms and a partial point. `lockSeq` allocated by the application layer's own monotonic counter, never a client
- `record TrackedObject(long trackId, Detection detection, Instant firstSeen, Instant lastSeen)` — trackId≥0, lastSeen≥firstSeen; the application layer's track-book entry (`TrackBook`); deliberately **not** cross-validated against `detection.track().trackId()` — that would break holding an untracked detection
- `record TrackingConfig(TrackingMode mode, String engineId, int verifyEveryMillis, int followFps, int redetectIouPercent, int maxAgeFrames, int minHits, int capabilityLevel, int reupdateMaxGapMillis, TargetLock lock)` — per-stream tracking config, joins `PipelineConfig`; `engineId` empty = server default; `redetectIouPercent` an **int** percent [0,100] (JSON-/PATCH-friendly); `followFps` is Java-side sampler rate only, no cv-service knob; `verifyEveryMillis`/`followFps`/`maxAgeFrames`/`minHits` positive; `capabilityLevel` (docs/plans/active/TRACKING-V3-BAND1-CONTEXT.md §2, E12) [0,5] — a **ceiling, not a demand**: cv-service serves `min(requested, affordable)`, never a refusal; `0` = auto-probe; `reupdateMaxGapMillis`≥0, `0` = server default — longest gap ORU may reconstruct; `lock` nullable. `static off()`/`static defaults()` both leave `capabilityLevel`/`reupdateMaxGapMillis` at `0` — today's behaviour exactly. An **8-arg convenience ctor** (the pre-V3 signature) defaults both new fields to `0`, byte-identical to not setting either wire field (invariant B2) — every call site written before this wave compiles and behaves unchanged. `static off()` — mode OFF, defaults `DEFAULT_VERIFY_EVERY_MILLIS=2000`/`DEFAULT_FOLLOW_FPS=15`/`DEFAULT_REDETECT_IOU_PERCENT=30`/`DEFAULT_MAX_AGE_FRAMES=30`/`DEFAULT_MIN_HITS=3`; `static defaults()` — mode ASSOCIATE, same cadences (what `PipelineConfig.defaults()` ships since T8)
- `record TrackingCapability(int levelServed, String reason)` (docs/plans/active/TRACKING-V3-BAND1-CONTEXT.md §2) — what the capability ladder **actually served**, as opposed to `TrackingConfig#capabilityLevel`'s requested ceiling; `levelServed` [1,5] — a `TrackingCapability` only exists once a level was genuinely reported, never the ladder's own `0` ("auto-probe") sentinel; `reason` never null, `""` = served exactly as requested; `levelServed` is always ≤ requested — nothing on the Java side may raise it (invariant B5), and a reader must render it as what happened, never echo the request as if it were the outcome
- `enum TrackingMode` — `OFF | ASSOCIATE | FOLLOW`; how the two perception loops cooperate for one stream
- `record TrackingTelemetry(boolean detectorRan, DetectorReason reason, Duration trackerLatency, String engineId, long lockedTrackId, Duration detectionLag, Duration reupdateLatency, int reupdatedTracks, TrackingCapability capability)` — per-**frame** tracking facts (vs. `TrackRef`'s per-**detection** facts); joins `DetectionResult`'s nullable `tracking`; `reason` non-null iff `detectorRan`; `trackerLatency` non-null non-negative; `engineId` non-null, empty=none; `lockedTrackId`≥0, 0=none. `detectionLag`/`reupdateLatency` (docs/plans/active/TRACKING-V3-BAND1-CONTEXT.md §2) non-null non-negative `Duration`s — `ZERO`=unknown/none ran; `reupdatedTracks`≥0 — tracks ORU backfilled this frame; `capability` nullable `TrackingCapability` — `null` = cv-service reported no level at all (a pre-V3 server), same "absent means absent" idiom this record already applies to its five pre-V3 fields (invariant B3). A **5-arg convenience ctor** (the pre-V3 signature) defaults `detectionLag`/`reupdateLatency` to `Duration.ZERO`, `reupdatedTracks` to `0`, `capability` to `null`
- `record TrackRef(long trackId, TrackState state, DetectionSource source, double velocityX, double velocityY, int ageFrames, boolean reupdated)` — per-detection track facts, joins `Detection`'s nullable `track`; `trackId`≥1 (0 is the wire's untracked sentinel and must never reach here — an untracked `Detection` carries `track=null`); `velocityX`/`velocityY` finite, normalized frame-widths/heights per second; `ageFrames`≥0; `reupdated` (docs/plans/active/TRACKING-V3-BAND1-CONTEXT.md §2) — this track's gap was reconstructed by ORU on this frame. A **6-arg convenience ctor** (the pre-V3 signature) defaults `reupdated=false`; the pre-existing 3-arg convenience ctor chains through it, so velocity/age/`reupdated` all default together
- `enum TrackState` — `TENTATIVE | CONFIRMED | COASTING | LOST`; lifecycle of the track a `Detection` belongs to
- `record VideoFrame(StreamId streamId, long sequence, Instant capturedAt, int width, int height, PixelFormat format, ByteBuffer data)` — sequence≥0, width/height>0; ctor stores `data.asReadOnlyBuffer()`; `data()` returns `data.duplicate()` fresh each call

### domain.port — `com.drones.vision.perception.domain.port` (driven — implemented by adapters)
- `DetectionEventRepositoryPort` (**moved here from `events` in W1.6b**): `DetectionEvent save(DetectionEvent)` — **upsert** by id (a `DetectionEvent` mutates over its own open lifetime, unlike `DetectionRepositoryPort`'s append-only rows); `List<DetectionEvent> findRecent(Instant sinceInclusive, int limit)` — across every stream, newest-first by `lastSeen`, `sinceInclusive` nullable; `List<DetectionEvent> findByStream(StreamId, int limit)` — empty (not an error) for an unknown/eventless stream
- `DetectionDemandPort` (docs/plans/active/CV-DEMAND-PLAN.md §2-3.1, wave D1) — the **system-derived** half of the two independent gates `StreamPipeline` ANDs together before it runs inference at all (the other, operator intent, is `PipelineConfig#detectionEnabled()`): `boolean detectionWanted(StreamId, AssetId)` — `assetId` nullable (device-only stream, no resolved owning asset); protocol-agnostic on purpose (a live SSE subscription and a recent detections-poll are both legitimate demand) so nothing above it needs to know which driving protocol asked. **Contract**: cheap/non-blocking, no network I/O, must not throw — `DefaultStreamService`'s demand-poll task wraps every call in its own `catch (Throwable)` regardless, so an implementation answering `false` instead of throwing keeps that safety net reserved for genuine bugs. **Threading**: called from one dedicated scheduler thread on a fixed poll interval, never the video/detection hot path; must be safe to call concurrently for different streams even though today's one caller evaluates them sequentially
- `DetectionLiveUpdatePort` (W1.6b — this context's slice of the deleted god-port `LiveUpdatePublisherPort`): `void publishDetections(AssetId, DetectionResult)` — attributed to the stream's *owning asset*; `void publishDetectionEvent(DetectionEvent)` — a debounced event opened/advanced/closed. Both must not throw on ordinary delivery failure and must return quickly
- `DetectionPort`: `CompletionStage<DetectionResult> detect(VideoFrame, PipelineConfig)` — **must not block**; no internal queuing/limiting — caller bounds in-flight count and skips (never queues) once at the bound. A `default detect(VideoFrame, PipelineConfig, CameraAttitude)` adds camera pose **additively** — a `null` attitude is the normal state (no telemetry / no heading / no configured FOV), not a degradation, and every in-memory or test double stays correct without overriding it; only the gRPC adapter does
- `DetectionRepositoryPort` (**moved here from `events` in W1.6b** — only this context ever constructs a `DetectionResult`/`DetectionQuery`): `void save(DetectionResult)` — append-only; `List<DetectionResult> query(DetectionQuery)`
- `FeedTransmitterPort`: `boolean supports(FeedSpec)`; `StreamDescriptor start(FeedId, FeedSpec)` — blocking setup then background transmit, returns the descriptor the RX side ingests from; `void stop(FeedId)` — idempotent. **TX half** of the RX/TX doctrine (`docs/main/CYCLES-PLAN.md` §0) — simulation infrastructure, unrelated to `StreamPublisherPort`
- `OverlayPort`: `VideoFrame render(AnnotatedFrame)` — synchronous, input frame never mutated, returns a distinct instance
- `PulledDetectionPort` (docs/plans/active/MEDIA-SOT-PLAN.md §5.5, wave M5) — the **pull** counterpart of `DetectionPort`: the worker opens the video itself, so this JVM hands it a URL instead of frames and never decodes the stream. `Flow.Publisher<DetectionResult> open(StreamId, URI sourceUrl, PipelineConfig)` — per-open, live; `void reconfigure(StreamId, PipelineConfig)` — restates the hot fields, no-op for an unopened id; `void attitude(StreamId, CameraAttitude)` — pose for whatever frame the worker analyses next, no-op for an unopened id; `void close(StreamId)` — idempotent. Deliberately **not** an overload on `DetectionPort`: "hand me a frame" and "go get your own frames" are two shapes, and the caller honors `maxInFlightInferences` for the first while the worker paces itself for the second
- `RecordingPort`: `void streamStarted(StreamId, Device)`; `void publish(StreamId, VideoFrame)` — cheap, no blocking I/O; `void streamEnded(StreamId)` — idempotent; shape mirrors `StreamPublisherPort` but a distinct port (durable storage vs live egress)
- `StreamPublisherPort`: `void streamStarted(StreamId, Device)`; `void publish(StreamId, VideoFrame)` — adapter owns latest-wins drop policy; `void streamEnded(StreamId)` — idempotent; `default Optional<URI> viewUrl(StreamId)` — HLS; `default Optional<URI> whepUrl(StreamId)` — WebRTC, **never proxied** (a WHEP session is a POST/SDP+ICE exchange, not a byte stream); `default Optional<URI> playbackUrl(StreamId, Instant, Duration)` — recorded-clip window, **never proxied either**
- `VideoSourcePort`: `boolean supports(StreamDescriptor)`; `Flow.Publisher<VideoFrame> open(StreamId, StreamDescriptor)` — per-open, hot/live, latest-wins backpressure, unrecoverable failure → `onError`; `void close(StreamId)` — idempotent

- `ActiveStream(streamId, deviceId, startedAt)`
- `PipelineConfigPatch(confidenceThreshold, inferenceFps, labelFilter, detectionEnabled, modelId, tracking)` — `StreamService#updateConfig`'s partial-patch command; every field nullable, `null`="leave unchanged" (`PipelineConfigPatch.NOTHING` the identity); `labelFilter` a `Set<String>`, defensively copied when present — a present-but-*empty* value means "keep all labels" (unlike `DeviceEdit#capabilities`'s empty-set rejection); `modelId` is the checkpoint id only, never the version; `tracking` is a **`TrackingConfigPatch`** (retyped from `TrackingConfig` — see Status, T3/T6 follow-up)

### application.stream — services
- **`StreamService`** (interface) → **`DefaultStreamService`** — `DefaultStreamService(DeviceRepositoryPort, VideoSourceRegistry, DetectionPort, StreamPublisherPort, DetectionRepositoryPort, EventPublisherPort, ...)` growing through eight N-1-arg convenience ctors to a **13-arg** canonical (+`UsageTracker`, `OverlayPort`, `DetectionEventRepositoryPort`, `DetectionLiveUpdatePort`, `StreamPipelineSettings`, `PullDetectionSettings`, `DetectionDemandPort`, all nullable — passing `null` simply skips that feature; a `null` `PullDetectionSettings` means push mode for every stream this service starts, exactly as before wave M5). `DetectionDemandPort` (docs/plans/active/CV-DEMAND-PLAN.md §3.3, wave D1) — non-null schedules one `pollDetectionDemand` task on the existing `retryScheduler` at `StreamPipelineSettings#detectionDemandPollInterval()`, re-evaluating every running stream's demand each tick; `null` (every prior constructor) means the task is never scheduled at all, so every stream stays fail-open on demand — gated on `detectionEnabled` alone, exactly as before this capability existed. The per-stream evaluation (`void evaluateDetectionDemand(StreamId, Instant now)`, package-private test seam) resolves the owning asset via `usageTracker` (or `null` if absent), asks the port, and if wanted stamps `RunningStream#lastDemandAt` (an `AtomicReference<Instant>`, the one mutable field on that otherwise-immutable record) to `now`; the effective demand handed to `StreamPipeline#updateDetectionDemand` is `Duration.between(lastDemandAt, now).compareTo(detectionDemandGrace) < 0` — so a stream keeps detecting for `detectionDemandGrace` past its last observed demand rather than dropping the instant a poll tick finds nobody watching. **`lastDemandAt` is seeded to `Instant.EPOCH` at `start`, deliberately not `Instant.now()`** — demand must be *observed*, never assumed; seeding to "now" would silently grant every newly started stream a full `detectionDemandGrace` (30s) window of assumed demand it never earned, worst exactly in the scenario this wave exists for (many streams started at once, each burning inference for nobody). The narrower startup window this leaves instead is already covered by `StreamPipeline#detectionDemand()`'s own fail-open `true` default: a just-started stream detects until the *first* poll tick decides otherwise (at most one `detectionDemandPollInterval`, 2s), not a full grace period. `pollDetectionDemand` itself wraps each stream's evaluation in its own `catch (Throwable)` — `scheduleAtFixedRate` silently cancels all future runs the moment its task throws uncaught, so one misbehaving `DetectionDemandPort` must never stop every later tick for every other stream
  - `StreamId start(DeviceId, PipelineConfig)` / `start(DeviceId, PipelineConfig, TrackingConfigPatch)` (docs/plans/done/TRACKING-PLAN.md T3/T6 follow-up) — at most one active stream per device; `IllegalStateException` if already streaming or not `ACTIVE`, `NoSuchElementException` if unknown. Wraps the opened `VideoSourcePort` in a `SupervisedPublisher<VideoFrame>` before handing it to `StreamPipeline`, so a source I/O failure is retried with backoff instead of ending the stream (docs/plans/done/MVP2-PLAN.md §S, S-a). **Tracking fold, three layers**: `requested.foldOnto(seed.foldOnto(config.tracking()))` — per-stream request > deployment env (`StreamPipelineSettings#trackingSeed`) > code default — composed once, here, so every start path (device, asset, simulation, demo fleet) converges on the same answer
  - `void stop(StreamId)` — no-op for unknown/stopped; the **only** path that ever ends a stream. Returns promptly: map removal + `SupervisedPublisher#stop()` + the `STREAM_STOPPED` event happen synchronously, but `StreamPipeline#close()`/port `close()` run on a fire-and-forget virtual thread (the `/live` stop-freeze bug fix — see Gotchas)
  - `List<ActiveStream> streams()`; `Set<DeviceId> activeDeviceIds()`
  - `Optional<VideoFrame> latestFrame(StreamId)` / `latestRawFrame(StreamId)` (docs/plans/done/CV-TRAINING-PLAN.md §2/§D) — post-overlay vs. pre-overlay, one-line delegations to the running pipeline
  - `boolean burnedIn(StreamId)` (docs/plans/active/MEDIA-SOT-PLAN.md §5.4) — whether overlay burn-in is **actually** active for this stream, not merely configured: `false` exactly when nothing burns boxes into the published video (a proxied source, or a pull-transport stream). What `POST /api/streams` and `POST /api/assets/{id}/stream` report as `burnedIn`, so the client never draws its own boxes on top of server-drawn ones

- **`PipelineLatencyWindow`** (package-private, final) → `record PipelineLatency(Duration window, long samples, double roundTripMillisP50, double roundTripMillisP95, double roundTripMillisMax, double updateIntervalMillisP50, double effectiveFps)` — rolling submit→available timings for one stream. A **peer** of `TrackingStatsWindow`, and load-bearing rather than stylistic: that window returns early when tracking is off, while latency has no such exemption — a tracking-`OFF` stream still has a round trip, and is very often exactly the stream whose lagging boxes are under investigation. - **`DetectionRateWindow`** (package-private, final) → `record DetectionRate(Duration window, double sourceFps, double targetFps, double demandFps, double submittedFps, long submitted, long droppedInFlight, long droppedOutage, long missedDeadlines, String transport, double decodeMillisP50)` — what the sampler decided, per deadline. A **peer** of `PipelineLatencyWindow` rather than fields on it: the two halves are written by different threads at opposite moments (a sampler decision on the source's `onNext` thread *before* a request leaves; a latency sample on a completion thread *after* one lands), so folding them would serialize the video path against the completion path and would leave the counters undefined for the very case they exist to explain — the samples **never sent**, which have no round trip at all. Compare `targetFps` with `submittedFps`: exactly one counter is then non-zero and names the loss — `missedDeadlines` (source slower than target), `droppedInFlight` (detector saturated), `droppedOutage` (cv-service down). `transport` is `TRANSPORT_PUSH`/`TRANSPORT_PULL`, and doubles as the reader's cue for which definition the sibling latency figures use (pull mode redefines the round trip as box age at arrival — there is no Java→Python hop to measure). A window is push **or** pull for its whole life, decided once
- **`DetectionRateController`** (docs/plans/active/CV-RATE-CONTROL-PLAN.md §2) — chooses the rate `StreamPipeline` samples at, from how fast the tracked target is about to leave its own association budget. Two observations associate while the box moves less than that budget: for box width `w` and re-anchor threshold `t`, `d = w(1-t)/(1+t)`, so the rate that keeps displacement inside it is `displacement-per-second / d` — "spend resources not to lose it" written as an inequality rather than a constant, which is why a fixed 10 fps is both wasteful when nothing moves and far too slow during a 30°/s yaw. Everything is in **frame widths, never pixels**: box widths and `TrackRef` velocities are already normalized and a yaw rate divides by the horizontal FOV, so the detector's pixel width never enters the arithmetic
- `record AdaptiveRateSettings(boolean enabled, double maxFps, double ewmaAlpha)` — **on by default**, because the failure it closes is silent: a fixed rate loses the target during exactly the manoeuvres an operator is least able to notice. It can only ever **raise** the rate above what was configured, never lower it, so a deployment that set a number still gets at least that number

## Conventions
- No Spring/framework imports anywhere in this module.
- **The acting user is a method parameter (`UserId actor`), never a constructor dependency.**
- Constructor injection; every collaborator `Objects.requireNonNull`'d **except** the deliberately-nullable ones: `DefaultStreamService`'s `usageTracker`/`overlayPort`/`detectionEventRepositoryPort`/`liveUpdatePublisherPort`; `StreamPipeline`'s `overlayPort`/`eventEngine`/`assetId`/`liveUpdatePublisherPort`/`telemetrySupplier`; `UsageTracker`'s own `liveUpdatePublisherPort`/`telemetryObserver`; `DetectionEventEngine`'s `usageTracker`.
- Injected collections defensively copied at construction (`List.copyOf`): `VideoSourceRegistry.sources`, `UsageTracker.telemetrySources`, `FeedTransmitterRegistry.transmitters`.
- `Flow.Subscriber` used identically in two places — `StreamPipeline` (video) and `UsageTracker`'s internal `TelemetrySubscriber` (telemetry) — both request one item at a time and re-request after processing.
- Concurrency primitives: `ConcurrentHashMap` for shared registries (`DefaultStreamService.activeStreams`/`streamByDevice`, `UsageTracker.trackingByAsset`); `AtomicInteger`/`AtomicBoolean` for pipeline counters/close-flags; `volatile` for single-writer/many-reader fields (`StreamPipeline.config`/`latestDetections`/`latestFrame`/`latestRawFrame`). One dedicated daemon `ScheduledExecutorService` per service (`DefaultStreamService`, `UsageTracker`), shared across every stream/subscription it supervises, scheduling `SupervisedPublisher` retries.
- Per-asset mutable state in `UsageTracker` (`Tracking`) is synchronized on the `Tracking` instance itself, not a module-wide lock — different assets' start/stop/telemetry never contend.
- Every port interface's javadoc documents **Contract** and **Threading**; ports with backpressure concerns (`VideoSourcePort`) add a **Backpressure** section describing the latest-wins drop policy.
- Records validate in their compact constructor with manual `if (…) throw new IllegalArgumentException(…)`; `Objects.requireNonNull` is application-layer only.

## Gotchas
- **`StreamPipeline` has two distinct detection surfaces — do not conflate them.** `latestDetections()` is the raw, most-recently-completed result (what REST/audit/persistence should read); overlay burn-in renders `DetectionExtrapolator.at(frame.capturedAt())`, a *smoothed* view whose **positions** can differ (matched detections move toward their predicted position, frozen `MAX_EXTRAPOLATION_MILLIS`=800ms past `L.capturedAt()`) while `latestDetections()` stays exactly as last set. Wiring a new "what's currently detected" consumer onto the wrong one is an easy, silent bug.
- **A detection failure never closes `StreamPipeline`** (docs/plans/done/MVP1-PLAN.md §C7) — only `onError` (source) and a synchronous publish exception are fatal. Get this wrong and a flaky/absent CV service takes the whole video path down with it.
- **One `PIPELINE_ERROR` event per outage, not per failed frame** — fires exactly once on the `inOutage` false→true transition; every failure after that (including every failed retry probe) is silently counted (`outageFailureCount`), never a second event.
- **Only a failed *probe* doubles the backoff** — a detection call already in flight when the outage began can still fail afterward; that failure is counted but must not touch `backoffNanos`/`nextProbeAtNanos`, or a stray straggler could stomp a backoff a probe already advanced.
- **Exactly one probe in flight at a time** — `probeInFlight` and the deadline check are claimed together inside one `synchronized (outageLock)` block; two separate lock-free reads would let a racing thread start a second concurrent probe or skip the first backoff window outright.
- **In-flight inference bound is skip-not-queue** — once `maxInFlightInferences` is reached, a sampled frame is dropped outright, never buffered; a slow `DetectionPort` degrades detection *rate*, never blocks video.
- **`StreamPipeline`'s sampling rate is a *measured* source cadence**, not fixed — trusted only after `WARMUP_FRAMES`=5 frames, seeded directly from the first observed delta (not blended toward the 30fps fallback) so a constant-cadence source converges immediately.
- **The `/live` stop-freeze bug was a real backend bug, not (only) a frontend one.** `DefaultStreamService#stop` used to call `VideoSourcePort#close` **synchronously** on the calling (MVC request) thread; `FfmpegVideoSource`'s close can block up to 20s on a stuck native grab, and one stuck `DELETE` starves a browser's small per-origin connection pool — reading, from the Network panel, exactly like "the whole app froze." Fixed: `stop()`/`UsageTracker#unsubscribeTelemetry` now do only fast in-memory work synchronously and defer the actual `close()` calls to a fire-and-forget virtual thread.
- **Source supervision (docs/plans/done/MVP2-PLAN.md §S, S-a) — what survives a reconnect vs. what re-establishes.** Survives untouched, exactly once per stream: the `StreamPublisherPort` session (`streamStarted`/`streamEnded` fire only at `start()`/`stop()`), the `UsageId`/`AssetUsage`, and the pipeline's own detection-outage/backoff state, `latestDetections()`, `DetectionExtrapolator`/`DetectionEventEngine` instances — none of this is pipeline-instance-changing, a reconnect just resubscribes the *same* pipeline to a freshly-opened publisher. Re-establishes on every reconnect: only the source-side `Flow.Publisher`/`Flow.Subscription` (a fresh `open()` call each time). Backoff 1s→30s doubling (deliberately different from the pipeline's own 1s→10s detection-outage backoff and `MediamtxStreamPublisher`'s 500ms→10s — reconnecting a whole source is more expensive to hammer than either finer-grained retry loop).
- **Frame/sample sequence numbers are not guaranteed monotonic across a reconnect, and this isn't fixed** — the *adapter* generates `VideoFrame#sequence()` fresh on every `open()`; `StreamPipeline`'s sampling modulo still works correctly against the reset sequence, it just restarts its cycle.
- **A brief, bounded, non-leaking race is possible between an explicit `stop()` and an in-flight reopen attempt** in `SupervisedPublisher` — never leaks, since `stop`'s caller always calls the underlying port's own `close(id)` afterward regardless of supervision state.
- **`DetectionExtrapolator.accept`'s out-of-order guard is `frameSequence` ≤, not <** — a duplicate/retried completion for the same sampled frame is ignored exactly like a strictly-older one.
- **`DetectionEventEngine.accept`'s per-label absence check only runs when a new `DetectionResult` completes** — no background timer. During a detection outage, sampled frames are withheld from `DetectionPort` entirely, so an event left open when the outage began stays open, un-evaluated, until detection recovers and the next completed result's timestamp reveals the gap.
- **`DetectionEvent#position` is frozen at open time, not live-tracked** — `DetectionEventEngine.open` calls `usageTracker.latestPosition` exactly once, at the streak→OPEN transition; a long-open event reports where the asset *was* first confidently seen, not where it is now.
- **`PipelineConfig#eventRule`'s labels are independent of `labelFilter`** — two separate label sets with no cross-validation; `labelFilter={"car"}` with `eventRule.labels()` still defaulting to `{"person","car"}` means "person" events can never open, which is not treated as a configuration error.
- **A model-id re-arm does not actually close/reopen any adapter-side detection session — it can't from here, deliberately.** `DetectionPort` exposes only `detect(frame, config)`, no per-stream lifecycle method; the `streamEnded(StreamId)` hook lives only on the concrete `GrpcDetectionPort` class (adapter-cv-grpc), never on the port interface this module is wired against. `updateConfig` clears this pipeline's own model-bound state and lets the volatile config swap carry the new model into the next `detect()` call — whether an adapter's own session genuinely switches models per call (true for cv-service today) is that adapter's concern.
- **`maybeDetect`'s `detectionEnabled` gate does not reset outage/backoff state** — toggling detection off then on leaves `inOutage`/`backoffNanos` exactly where they were; this answers "is the CV service healthy," a question that doesn't reset just because the operator flipped a local switch.
- **`UsageTracker.TelemetrySubscriber.onError` is an empty method by design** — a telemetry source failure is completely silent, not even logged, because best-effort telemetry must never affect stream/usage lifecycle.
- **`UsageTracker` drops a telemetry sample that arrives after its usage has closed** instead of reopening a new usage for it. This is unchanged by Wave O7's `onTelemetryDeviceDiscovered` on purpose — reopening lazily from a straggling sample racing a legitimate close would risk fabricating a phantom usage; a telemetry-only session gets its own explicit open entry point instead (see below), and the drop-on-null-usage behavior in `applySample` was left completely untouched.
- **Nothing in this wave (O7) ever closes a telemetry-only usage on its own — flagged as a real, un-closed gap, not silently deferred.** `deviceStreamStopped` is the only path that ever runs `FlightPhaseRule#onSessionClosed`/reaches terminal `CLOSED`, and it fires only from `onStreamStopped` (an explicit "video stream stopped" signal). No in-scope adapter wave calls anything like "telemetry device stopped reporting," so a telemetry-only asset (opened via `onTelemetryDeviceDiscovered`) can reach `ABANDONED` via `evaluateLinkHealth`'s silence path but has **no path in this reactor to ever reach `CLOSED`**. Building an `onTelemetryDeviceLost`/timeout-driven close counterpart is future work, not something O7's own test suite covers (there is no assertion anywhere claiming a telemetry-only usage closes).
- **`evaluateLinkHealth(AssetId)` is not wired to any scheduler** — it exists purely as a directly-callable, deterministically-testable entry point for the silence-driven `IN_FLIGHT→LINK_LOST→ABANDONED` transitions (docs/plans/active/DRONE-ONBOARDING-PLAN.md §2.3). Production wiring (a periodic call per tracked asset, presumably from `vision-app`) is left for a later wave, matching how O3 left `FlightPhaseRule` itself unwired until this wave gave it a caller. Until something calls it repeatedly, a genuinely silent aircraft's phase only updates the next time a sample happens to arrive (via `applySample`) or `evaluateLinkHealth` is invoked by hand.
- **`Tracking#activeDevices` and `Tracking#activeVideoStreams` count different things and both matter — do not collapse them.** `activeDevices` (pre-existing) drives usage open/close accounting and counts *any* active device, video or telemetry-only; `activeVideoStreams` (Wave O7) counts video streams only and is the sole value fed to `FlightPhaseRule#nextPhase`'s `streamCount` parameter, whose contract requires it read `0` for a telemetry-only asset throughout. Folding telemetry-only devices into `activeVideoStreams` would silently violate that contract and make a pure-telemetry aircraft indistinguishable from one running video, for phase purposes.
- **`AssetUsage#phase` is typed `com.drones.vision.warehouse.domain.model.UsagePhase`, never `com.drones.vision.flight.domain.model.FlightPhase`, despite the two being name-parallel** — this is deliberate, not an oversight (see Status for the architectural conflict it resolves). `UsageTracker#toFlightPhase`/`toUsagePhase` are the only conversion point; nothing else in this module or `vision-warehouse` should ever import the other context's phase enum.
- `storage/persistence`'s `AssetUsageMapper` does **not** yet map `AssetUsage#phase` to/from `AssetUsageEntity` — confirmed by reading it during O7 (`toEntity` never reads `phase()`; `toDomain` calls the pre-phase 8-arg `AssetUsage` constructor, silently defaulting every persisted-and-reloaded usage back to `PREFLIGHT`). Out of this module's scope; belongs to whichever wave (O5) touches `storage/persistence`.
- **A non-immediate `UsageSummaryBatchSettings` bounds, but does not eliminate, how stale `AssetUsage#sampleCount`/positions can read** (docs/plans/active/SCALE-100-PLAN.md S4 item 3) — up to `batchWindowMillis` behind the freshest folded sample, and lost entirely (not just delayed) on a crash before the coalesced write flushes. Safe by construction, not by luck: the summary is a recomputable running counter, not a historical record, so an unflushed fold is never the *only* copy of anything — the durable `telemetryRepository.save` call for the same sample already landed synchronously, on the sample's own thread, regardless of `UsageSummaryBatchSettings`. Every constructor shipped before this wave resolves to `UsageSummaryBatchSettings.immediate()`, so this gotcha only applies to a caller that explicitly opts into batching via the new 8-/10-argument constructors — today, nothing in this reactor does.
- **`UsageTracker.onStreamStarted`'s `streamId` is only ever recorded on the call that opens the usage** — for an asset with several devices, only the first device's stream is ever visible on `AssetUsage#streamId`.
- **`DefaultStreamService` allows only one active stream per device** (Phase 0 scope) — starting a second throws `IllegalStateException` rather than replacing the existing stream.
- **The tracking component of the `PipelineConfig` you pass to `start`/`startStream` is the *bottom* layer of the fold, not the final answer** — the deployment seed and the request patch are applied on top of it inside the service. Pass `PipelineConfig.defaults()` and say what you mean in the patch.
- A present `TrackingConfigPatch` folds mode/engine/cadences **per field** (each nullable component independently), but its `lock` is itself null-means-unchanged — releasing a lock is the explicit `TargetLock{release=true}` form, never an omission. (The whole-`TrackingConfig`-replace T3 originally shipped was a defect: it silently reset every knob the caller didn't restate — see Status.)
- `ProbeService#probe` never registers anything and never touches any repository — a probe's `StreamId` is fresh, transient, and looked up nowhere else.
- **A stream that's `detectionEnabled` but currently undemanded (docs/plans/active/CV-DEMAND-PLAN.md §5, wave D1) stops more than just calling `DetectionPort`.** `maybeDetect`'s early return means no `DetectionResult` is ever produced for an ungated stream, so everything downstream of that result goes quiet too: debounced `DetectionEvent`s stop advancing (`DetectionEventEngine.accept` is only ever called from `onDetectionResult`, same as during a detection outage — see the outage Gotcha above), training-sample capture sees no fresh `latestDetections()`, and `DetectionRepositoryPort#save`/`DetectionLiveUpdatePort#publishDetections` are never called. An event left `OPEN` when demand drops stays open, un-evaluated, exactly like an event left open during a detection outage, until demand (or `detectionEnabled`) returns and the next completed result's timestamp reveals the gap — nothing time-based closes it in between. Video, overlay burn-in of whatever boxes were last extrapolated, and `latestFrame()`/`latestRawFrame()` are unaffected; only the detect/track/event/persist half of the pipeline goes quiet.
- **`DefaultStreamService.evaluateDetectionDemand` calls `detectionDemandPort.detectionWanted(...)` directly, unguarded** — the `catch (Throwable)` protecting a throwing port lives one frame up, in `pollDetectionDemand`'s per-stream loop, not in `evaluateDetectionDemand` itself. Calling `evaluateDetectionDemand` directly (the package-private test seam) with a `null` `detectionDemandPort` NPEs by design; production code only ever reaches it through `pollDetectionDemand`, which is only ever scheduled when the port is non-null.
- **`DetectionState` reports gating, never health — do not wire it to a status light.** `RUNNING` means both gates (`detectionEnabled`, `detectionDemand`) are open; it says nothing about whether `DetectionPort` is actually answering. A stalled or unreachable cv-service reads `RUNNING` throughout its entire outage — the pre-existing outage/backoff machinery and its `PIPELINE_ERROR` events are the only source of truth for detector health, and `DetectionState` was deliberately kept out of that business rather than merged with it.
- **A freshly started stream's `lastDemandAt` starts at `Instant.EPOCH`, not the stream's own start time** — evaluating demand for a brand-new stream before any consumer has ever shown up computes a `sinceLastDemand` on the order of decades, not zero, so a `wanted=false` first evaluation gates off immediately rather than riding out a full `detectionDemandGrace` it never earned. Do not "simplify" this back to `Instant.now()` — that reintroduces exactly the 30s-of-free-inference-per-stream bug the CV-DEMAND-PLAN follow-up fix closed.
- **Pull mode's gate stops the JVM from forwarding a result, not the worker from producing one** (docs/plans/active/CV-DEMAND-PLAN.md §5/§7, wave D4). `PullResultSubscriber#onNext` drops a result outright when `StreamPipeline#detectionGateOpen()` (`detectionEnabled() && detectionDemand()`) is closed, so `detectionState()` is truthful in pull mode exactly as it already was in push mode — but the Python worker behind `PulledDetectionPort` was never told anything: it keeps pulling frames and running inference at full rate the whole time, since `detectionEnabled` isn't on the pull wire (`proto/vision/v1/cv.proto` has no such field). Stopping the worker itself needs a proto/adapter/`cv-service` change — proposed, not built, in CV-DEMAND-PLAN.md §7. A gated-off result's `recordPullTelemetry` is skipped too (not just `onDetectionResult`): recording a healthy `submittedFps` while `detectionState()` reads `OFF`/`IDLE_NO_VIEWERS` would move the same "gate says off, evidence says on" lie into the rate panel instead of fixing it — push mode already sets this precedent, since `maybeDetect`'s own early return means a gated-off push stream never feeds `detectionRate` a sample either.
- **A true→false transition of the detection gate clears every detection-derived read model, in both transports** (docs/plans/active/CV-DEMAND-PLAN.md §5/§7 — corrects this same wave's own first cut, which left `latestDetections()`/extrapolator/track book/rate-and-latency windows frozen at their last value on gate-close). That first cut was wrong: `DetectionsStore` (the SPA) polls `GET /api/streams/{id}/detections` every 2s and only preserves a stale value on an *empty or failed* poll — a frozen-but-successful response is neither, so an un-cleared server kept re-serving the same boxes, every 2 seconds, forever, indistinguishable from live ones to every consumer. That is the reported "turn detection on and off doesn't work" complaint, not a cosmetic gap. The outage precedent (a stalled `DetectionPort` leaves `latestDetections()` alone during backoff) does not generalize here: an outage is still trying and simply has no fresher answer *yet*, so holding the last one is honest; a closed gate will never try again, so holding the last one asserts something false. CLAUDE.md §9 is explicit: "Newest data/telemetry/detections etc should be used, even if previous is still available." `StreamPipeline#handleDetectionGateTransition()` is the single place both gate inputs (`updateConfig`'s `detectionEnabled`, `updateDetectionDemand`'s viewer demand) funnel through — `synchronized` on a dedicated `gateLock`, edge-triggered off a remembered `gateWasOpen` so a demand-poll's repeated `false` doesn't re-clear on every tick — and it reuses the exact clearing block (`clearDetectionDerivedState()`) `updateConfig`'s model-change branch already used, which still deliberately does *not* clear on a tracking-config-only change (that comment stays true). `onDetectionResult` re-checks `detectionGateOpen()` on entry to close the in-flight race: an inference submitted while the gate was open can complete on an arbitrary thread after `updateConfig`/`updateDetectionDemand` has already closed it and cleared state, and without this guard that late completion would silently repopulate `latestDetections()` right after the clear. `PullResultSubscriber` needed no separate clearing logic of its own — it already routes every forwarded result through the same `onDetectionResult`, so the shared transition point and self-guard cover pull mode for free.

*The plan's architectural gap, and how it was resolved.* The plan puts `FlightPhase` in `vision-flight` and wants `AssetUsage.phase` in `vision-warehouse` — but warehouse is the ArchUnit-enforced pure leaf (`docs/plans/active/DOMAIN-SEPARATION-W1.md` §16) that may depend on nothing but `vision-kernel`/`vision-platform`, so `AssetUsage` cannot be typed with flight's enum without creating an illegal `warehouse → flight` edge. **Resolved by giving warehouse its own, wholly independent `UsagePhase` enum** (`contexts/vision-warehouse`'s own MODULE.md/Gotchas) — name-parallel to `FlightPhase` (`PREFLIGHT, IN_FLIGHT, LINK_LOST, POSTFLIGHT, ABANDONED, CLOSED`) but importing nothing from flight. This context — `vision-perception` — is the only place both `vision-warehouse` and `vision-flight` are already legal dependencies, so it is the natural (and only legal) place to run `FlightPhaseRule` and translate its verdict: `UsageTracker#toFlightPhase`/`toUsagePhase` (private static, exhaustive `switch`es) do that translation immediately before every phase-bearing `AssetUsage` write (`applySample`, `deviceStreamStopped`, `evaluateLinkHealth`). Verified with a full 26-module reactor build (`./mvnw -B -DfailIfNoTests=false -Dsurefire.failIfNoSpecifiedTests=false -pl station/vision-app -am -Dtest=ArchitectureTest,ContextArchitectureTest test`) — `ArchitectureTest` 14/14 and `ContextArchitectureTest` 4/4 green, confirming no new illegal dependency edge exists and `vision-warehouse` still imports nothing from `vision-flight`. This resolution matches what the plan's own author flagged as the open question — stated here so a future reader does not "fix" the two enums back into one.
