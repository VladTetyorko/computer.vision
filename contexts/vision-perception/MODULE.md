# vision-perception

The ingest and CV runtime: resolves a device's stream, decodes/samples/publishes video, runs
detection and tracking against it, debounces detections into events, probes a device before it's
trusted, and orchestrates asset-level streaming (`DefaultAssetStreamService`) plus the live-state
facts warehouse needs (`StreamBackedAssetLiveState`). Does **not** own asset/device inventory
(`vision-warehouse` — reads it, never the reverse), flight-controller command/telemetry transport
(`vision-flight` — this context only opens the telemetry ports `UsageTracker` needs, and runs
flight's pure `FlightPhaseRule` state machine, translating its verdict into warehouse's
`UsagePhase`), or replay/history (`vision-events` — a downstream reader, never a dependency). The
largest of the eight contexts by a wide margin (113 main source files, 65 test classes).

**Depends on:** `vision-kernel`, `vision-platform` · `vision-warehouse` (`AssetDirectoryService`
resolves device/asset identity for `DefaultStreamService`/`DefaultAssetStreamService`/
`UsageTracker` — **never** `DeviceRepositoryPort`/`AssetRepositoryPort` directly; devices
`DefaultAssetStreamService` resolves by capability still go through `DeviceService`; this context
**implements** warehouse's `AssetLiveStatePort` via `StreamBackedAssetLiveState`; `UsageTracker`
reads/writes warehouse's `UsagePhase` on `AssetUsage` and the entire `AssetUsage` lifecycle via
`UsageSessionService`, never a repository port; **`DefaultCvProfileService` (wave W2) additionally
depends on `AssetService`** — `assetService.details(scope, assetId)`/`assetService.assets(scope,
false)` are how it resolves an asset's `category()`/`ownership().groupId()` and applies
`VisibilityScope` to `effective`/`coverage`, deliberately reusing `AssetService` rather than
`AssetDirectoryService`, since only `AssetService` carries scope-aware reads; **`UsageTracker`
(ASSET-FLOWS-PLAN S1) additionally reads warehouse's `MaintenanceQuery#openBlockers(AssetId)`
directly** — not routed through `vision-flight`'s `ReadinessService`, since this context already
depends on warehouse and `MaintenanceQuery` is filed in warehouse's `application` package for
exactly this kind of cross-context read, see Gotchas) · `vision-flight`
(`UsageTracker` opens `TelemetrySourcePort`/`TelemetryLiveUpdatePort`, persists telemetry via
`TelemetryService`, and runs flight's `FlightPhaseRule`/`FlightPhase`, translated to/from
`UsagePhase` entirely inside this context — see Gotchas)
**Used by:** `vision-events` (reads `DetectionRepositoryPort`), `vision-learning` (reads
`StreamService#latestRawFrame`/`latestDetections`, `ModelRegistryPort`), `vision-map` (live
telemetry), `vision-simulation`; adapters `adapter-rtsp`/`adapter-mjpeg`/`adapter-v4l2`/
`adapter-cv-grpc`/`adapter-mavlink`/`adapter-simulation`/`adapter-persistence`/
`adapter-publish-hls`; `vision-api`, `vision-app`
**Build/test:** `./mvnw -B -pl contexts/vision-perception test`

## Package shape
```
domain.model        detection/tracking/streaming/geo-ingest records + enums
domain.port          16 driven ports (implemented by adapters)
application.stream   stream lifecycle: StreamService, AssetStreamService, StreamBackedAssetLiveState
application.pipeline the hot path: StreamPipeline + collaborators, WorldModel, UsageTracker, two registries
application.device   ProbeService (test-before-save connection probe)
application.geo      ReferenceRegionService / GeolocationSessionService — visual-geolocation seam
application.profile  CvProfileService — CRUD/fork/bind, CvProfileResolver (org→category→asset fold,
                     W2.6), CvProfileCache, Intent/IntentPolicyResolver (platform-tier intent, W2.6)
```
No `port.in` package — driving interfaces collapse into one service interface + one `Default*`
implementation; commands/read-models are top-level records (`.claude/skills/java-clean-code/SKILL.md`).

## API surface

### domain.model
- `BindingScope` enum — `ORGANIZATION | CATEGORY | ASSET` — which kind of thing a `CvProfileBinding` attaches a `CvProfile` to (docs/plans/active/CV-SETTINGS-PLAN.md §3.1); ordered least→most specific — since wave W2.6 this is also literally the order `CvProfileResolver#resolve` folds tiers in (organization, then category, then asset, each superseding the last); the platform tier (no binding at any level) is not a member of this enum, represented instead by `ProfileSource.PLATFORM`
- `CameraAttitude(yawDegrees, pitchDegrees, rollDegrees, hfovDegrees, yawRateDegreesPerSecond, Instant at)` — camera pose at frame capture, for ego-motion compensation (docs/conclusions/CV-RATE-BUDGET.md §2); `at` non-null. `ofYaw(yaw,hfov,at)`; `from(Telemetry,hfovDegrees)` → `null` when the sample is null/has no heading — never a zeroed attitude
- `CvProfile(CvProfileId id, String name, String description, boolean builtIn, GroupId groupId, ModelRef model, double confidenceThreshold, int inferenceFps, List<String> labelFilter, List<String> labelDenyFilter, boolean detectionEnabled, TrackingConfig tracking, EventRuleConfig eventRule, Instant createdAt, Instant updatedAt)` — a named, persisted CV configuration a `CvProfileBinding` attaches to organization/category/asset (docs/plans/active/CV-SETTINGS-PLAN.md §3.1); `groupId` is **`null` if and only if `builtIn` is `true`** — a built-in (one of the four migration-seeded templates) is a global template with no owner, every other profile belongs to exactly one group; `confidenceThreshold`/`inferenceFps` share `PipelineConfig`'s own range checks (reused, not new constants); `labelFilter`/`labelDenyFilter` are **`List`, not `Set`** — unlike `PipelineConfig`'s corresponding fields, order here is a display concern worth preserving; `eventRule` is start-time only (the debounce engine is built once at `StreamService#start`, never re-armed by a live PATCH); `updatedAt`≥`createdAt`. `toPipelineConfig(PipelineConfig defaults)` — pure fold: every `PipelineConfig` field comes from the profile **except `maxInFlightInferences` and `trace`**, always `defaults.maxInFlightInferences()`/`defaults.trace()` (host capacity and per-session inspector demand respectively, neither a profile concern — docs/plans/active/CV-SETTINGS-PLAN.md §5.1, docs/plans/active/CV-ORCHESTRATION-PLAN.md §4.4); `labelFilter`/`labelDenyFilter` convert list→set. A profile whose fields mirror `PipelineConfig.defaults()`'s own components folds to a byte-identical `PipelineConfig.defaults()`
- `CvProfileBinding(BindingScope scopeKind, String scopeId, CvProfileId profileId, Instant createdAt)` — attaches a profile to one scope; `scopeId` is a **plain string**, not a typed sealed union, so it mirrors the wire contract exactly (`{"scopeKind":"ASSET|CATEGORY|ORGANIZATION","scopeId":"…"}`, docs/plans/active/CV-SETTINGS-PLAN.md §5.2) — a UUID string for `ORGANIZATION`/`ASSET`, a kebab-case slug for `CATEGORY` (since `CategoryId` isn't UUID-shaped); parsing/validating `scopeId` against the concrete kernel id type for its `scopeKind` is the resolver's job, not this record's (it imports no kernel id types). At most one binding per `(scopeKind, scopeId)`, enforced by storage's composite primary key, not here
- `CvProfileId(UUID value)` — `random()`/`of(String)`
- `Detection(String label, double confidence, BoundingBox box, ModelRef model, TrackRef track)` — confidence [0,1]; `track` nullable = untracked; 4-arg ctor defaults `track=null`
- `DetectionEvent(DetectionEventId id, StreamId streamId, AssetId assetId, String label, double peakConfidence, Instant firstSeen, Instant lastSeen, DetectionEventState state, GeoPosition position)` — a debounced "label X seen for a while" occurrence; `assetId`/`position` nullable; `peakConfidence` [0,1]; `lastSeen`≥`firstSeen`; `withObservation(Instant,double)` advances `lastSeen`/raises `peakConfidence`; `closed()` flips `state`; `position` stamped once at open, never updated after
- `DetectionEventId(UUID value)` — `random()`/`of(String)`
- `DetectionEventState` enum — `OPEN | CLOSED`
- `DetectionQuery(StreamId streamId, Instant from, Instant to, String label, int limit)` — all but `limit` nullable = "don't filter"; `limit` positive
- `DetectionResult(StreamId streamId, long frameSequence, Instant capturedAt, List<Detection> detections, Duration inferenceLatency, TrackingTelemetry tracking, PullTelemetry pullTelemetry, List<ObjectState> objects, Optional<FrameLedger> ledger)` — **9-arg canonical** (CV-ORCHESTRATION wave W2 step A1 appended `ledger`, the last component), **no convenience constructors** (CLAUDE.md rule 10 — every call site is explicit, ~62 sites across 20 files all updated to pass `Optional.empty()` when this wave landed); `frameSequence`≥0, `inferenceLatency`≥0; `tracking`/`pullTelemetry` nullable (tracking off / push-mode stream respectively); `objects` **never** `null` — empty means "no per-identity mirror computed for this frame" (a path predating this wave: legacy replay, devsupport, persistence round-trips), not a disabled feature. `detections` is per-frame/per-box; `objects` is per-identity across frames — `StreamPipeline#applyLabelFilters` (CV-ORCHESTRATION wave W1 step 5) filters both by the same allow/deny rule rather than filtering one and letting the other carry a denied label through under a new JSON key, matching `objects[i].identity().label()` — an object whose `identity` is `null` is always **kept** (nothing to match against; dropping it would invent an answer), see Gotchas. `ledger` is `Optional`, not a nullable component — deliberately, since `null` here would read as "the trace feature is off" for the whole type (CLAUDE.md rule 10 forbids that); `Optional.empty()` = this frame was not traced (`PipelineConfig#trace()` was off for it), a per-frame fact. **Wired end-to-end as of wave W2.5** — `cv/grpc`'s `DetectionFrameCodec#decode` decodes the wire's own `FrameLedger` into this component whenever cv-service attaches one (i.e. whenever `PipelineConfig#trace()` requested it for that frame); `StreamPipeline#onDetectionResult` feeds every present ledger into its own `FrameLedgerRing` (see `application.pipeline` below), and `GET /api/streams/{id}/cv/trace` (`station/vision-api`) is the read side
- `DetectionSource` enum — `DETECTOR | TRACKER`
- `DetectionPolicy` enum — `ON_VIEW | ALWAYS` (docs/plans/active/ALWAYS-ON-FLOW-PLAN.md wave D1) — a per-asset opt-in to inference regardless of viewer demand, stored under `Asset#attributes`' `ATTRIBUTE_KEY = "cv.detection-policy"` (`vision-warehouse`, plain `Map<String,String>`, no Flyway migration). `fromAttributeValue(String)` fail-closed: `null`/blank/unrecognized text all parse to `ON_VIEW` (today's behavior), exact case-insensitive-trimmed `"always"` parses to `ALWAYS`; `toAttributeValue()` round-trips (`"on-view"`/`"always"`, the frozen CV-SCALE-PLAN.md §S2 vocabulary). Parsing lives here, at the domain edge, rather than in `vision-app`'s cache, so the fail-closed contract is a domain fact, not a wiring accident
- `DetectionState` enum — `OFF | IDLE_NO_VIEWERS | RUNNING_UNWATCHED | RUNNING` — which of the **three** independent gate questions (wave D2, see `StreamPipeline#detectionGateOpen()`/`#liveGateOpen()`) explains a stream's boxes-or-no-boxes state; `OFF` = operator's own `detectionEnabled=false`, `IDLE_NO_VIEWERS` = enabled but neither viewer demand nor `DetectionPolicy.ALWAYS`, `RUNNING_UNWATCHED` (new, wave D1/D2) = the wider inference/durable gate is open (`ALWAYS` opt-in) but the narrower live gate is not (no viewer), `RUNNING` = the live gate itself is open. Purely additive — no existing branch on this enum needed to change to keep working, since `RUNNING_UNWATCHED` is a genuinely new state no pre-D1 code path could ever reach. **Reports gating, never health** — a stalled `DetectionPort` still reads `RUNNING`/`RUNNING_UNWATCHED` throughout its outage
- `StreamState` enum — `STARTING | LIVE | STALLED | RECONNECTING | UNOBSERVED` — the video-flow axis only (see `DetectionState` for CV gating, `AssetUsage` for session lifecycle); no `STOPPED` member (a stopped stream is simply absent from `streams()`); `UNOBSERVED` = a proxied stream, this JVM opens no `VideoSourcePort`. `static resolve(sourceObservable, reconnecting, framesObserved, nanosSinceLastFrame, staleAfterNanos)` pure/total; `RECONNECTING` outranks `STARTING`/`STALLED`
- `StopReason` enum — `OPERATOR | IDLE_NO_VIEWERS` — carried as the `STREAM_STOPPED` event's `reason` attribute
- `DetectorReason` enum — `ALWAYS | CADENCE | TRACKER_FAILED | NO_LOCK | BOX_INVALID | COASTED_OUT` — mirrors `cv.proto`'s enum minus `UNSPECIFIED`
- `EventRuleConfig(Set<String> labels, double confidenceThreshold, int consecutiveToOpen, Duration absenceToClose)` — debounce rule for `DetectionEvent`, referenced by `PipelineConfig#eventRule()`; `labels` empty = "track nothing"; `confidenceThreshold` [0,1]; `consecutiveToOpen`>0; `absenceToClose` positive; `defaults()` = {person,car}@0.5, N=3, 5s
- `FeedId(UUID value)` — `random()`/`of(String)`
- `FeedSpec(String protocol, URI source, Map<String,String> options)` — `protocol` lower-case-validated; `source`/`options` non-null, no defaulting ctor
- `FollowState` enum — `REQUESTING | HOLDING | COASTING | LOST | RELEASED` (docs/plans/active/TRACK-FOLLOW-PLAN.md §3.1, wave W2) — `REQUESTING` = a lock was just issued, `lockedTrackId` still `0`; `HOLDING`/`COASTING` = bound, newest `TrackRef.source()` is `DETECTOR`/`TRACKER` respectively; `LOST` = `lockedTrackId` fell back to `0` after having been bound for this lock's generation; `RELEASED` = the operator's own release patch was applied — after which `FollowTracker#status()` reads empty, not a `RELEASED` value at rest
- `FollowStatus(FollowState state, long trackId, String label, Instant since, Instant lastSeenAt, BoundingBox lastBox, boolean reacquirable, long recoveredAfterMillis, double recoveryConfidence)` — `FollowTracker`'s read model (wave W2); `since` is when the **current state** began, restamped on every transition (e.g. HOLDING→COASTING), not just on a fresh bind; `trackId`/`label` stay at their last-bound value through `LOST` (the re-acquire affordance), `lastSeenAt`/`lastBox` freeze at the moment `LOST` began (compact ctor enforces both null together or neither); `recoveredAfterMillis`/`recoveryConfidence` are non-zero **only on the recovery frame itself** (a `TrackRef.identityConfidence()>0` bind), not an ongoing property — a fresh acquisition leaves both `0`/`0.0`; `recoveryConfidence` range-checked `[0,1]`. **No `lastSeenAgeMillis` field** — that is a DTO-only derived value the wire layer computes from a request instant, deliberately not domain state
- `FrameLedger(StreamId streamId, long sequence, Instant capturedAt, int levelServed, String detectorReason, List<String> eligible, List<LedgerEntry> entries, Map<Long,List<ObjectEvidence>> objects, int dropsSinceLast, double gateWaitMillis, double totalMillis, boolean halted, List<DetectorBox> detections, int frameWidth, int frameHeight)` (docs/plans/active/CV-ORCHESTRATION-PLAN.md §4.4, wave W2 step A1; `detections`/`frameWidth`/`frameHeight` added wave W5b, decision E23) — one frame's complete debug evidence, mirroring `cv.proto`'s `FrameLedger`/`LedgerEntry`/`ObjectEvidence` field for field; the **warm** debug tier — present only on a frame cv-service was asked to trace (`PipelineConfig#trace()`), never persisted, never on the durable path. `detectorReason` is the wire's `DetectorReason` enum value carried as a **plain string, not the domain enum** — deliberately, so the ledger survives a cv-service reporting a reason this Java build does not know; empty allowed. All four collection components (`eligible`, `entries`, `objects` and each of its value lists) defensively, deeply copied to immutable collections. `LedgerEntry(String contributorId, LedgerOutcome outcome, String reason, double costMillis, Map<String,String> summary)` — one contributor's row; `contributorId` non-blank; `reason` non-null, empty means "no reason given"; `costMillis` finite ≥0, the contributor's **own** measurement when it has one, never summed into `totalMillis`; `summary` defensively copied. `LedgerOutcome` enum — `RAN | SKIPPED | FAILED`, mirrors `cv.proto`'s enum minus `LEDGER_OUTCOME_UNSPECIFIED` (same posture as `DetectorReason`). `ObjectEvidence(String contributorId, Map<String,String> claim)` — one contributor's claim about one object, kept attributed rather than merged (algorithm-shaped facts live here, never on `ObjectState` — the mirror describes the object, the ledger describes the algorithm); `contributorId` non-blank, `claim` defensively copied. `DetectorBox(String label, double confidence, BoundingBox box)` (wave W5b) — the detector's own raw boxes for a traced frame, validated like `Detection` (label non-blank, confidence [0,1], box non-null) but deliberately **not** `Detection`: a detector has no identity, so this carries no `TrackRef` at all, never a permanently-null one; `detections` is `List.of()` and `frameWidth`/`frameHeight` are `0` on every untraced frame, or a pre-W5b cv-service — "not carried", not an error; both ints validated ≥0. Test-only `com.drones.vision.perception.domain.model.FrameLedgerFixtures#everyFieldDistinct()` (src/test/java), mirroring `ObjectStateFixtures`'s own convention — treat its signature as a stable cross-wave API, reused by a later proto round-trip test; extended wave W5b with two distinct `DetectorBox`es and a distinct frame size, still every numeric leaf pairwise distinct
- `GeoPrior(double latitude, double longitude, double radiusMeters)` — `radiusMeters` positive, lat/lon range-checked
- `GeoSessionConfig(String regionId, float targetFps, GeoPrior prior)` — `regionId` non-blank, `targetFps` positive, `prior` nullable = "search the whole reference index"
- `IngestProgress(String regionId, String phase, int done, int total, IngestState state, String message, ReferenceIndexSummary summary)` — one tick of `ReferenceIndexPort#build`'s progress stream; `summary` non-null iff `state==SUCCEEDED`
- `IngestState` enum — `RUNNING | SUCCEEDED | FAILED` — deliberately mirrors, not shares, `vision-learning`'s `JobState` (this module must not depend on `vision-learning`)
- `ModelRef(String id, String version)`
- `ObjectState(long id, ObjectLifecycle lifecycle, StreamId streamId, Identity identity, Kinematics kinematics, Belief belief, Provenance provenance, MemoryFacts memory, LockFacts lock, Timing timing)` (CV-ORCHESTRATION wave W1 step 3, docs/plans/active/CV-ORCHESTRATION-PLAN.md §4) — the per-identity "wire mirror" of cv-service's own object-tracking state, one instance per tracked identity per frame (as opposed to `Detection`, which is per-box); `id`≥1, `lifecycle`/`streamId` non-null. Every nested group (`identity`/`kinematics`/`belief`/`provenance`/`memory`/`lock`/`timing`) is **individually nullable = "not computed at this level this frame"** (e.g. a stream running `TrackingMode.ASSOCIATE` never computes `lock`) — deliberately **not** the forbidden "null means the feature is off" (CLAUDE.md rule 10): a group's presence is a per-frame computation fact, not a static capability flag. Nested records, each with its own compact-ctor range checks: `LabelCandidate(String label, double weight)` (`weight` must be FINITE, deliberately not [0,1] — it is a decayed confidence-weighted tally, comparable only against its siblings in the same frame, so a normalized range would be a lie); `Identity(String label, String labelRaw, List<LabelCandidate> candidates, int stability)`; `Kinematics(BoundingBox box, BoundingBox detectorBox, BoundingBox trackerBox, BoundingBox predictedBox, long horizonMillis, double velocityX, double velocityY, double displacementX, double displacementY, boolean motionCompensated)` (`horizonMillis`≥0, boxes reuse kernel's `BoundingBox`); `Belief(double confidenceRaw, double confidenceSmoothed, double existence, long sinceConfirmedMillis)` (`confidenceRaw`/`confidenceSmoothed`/`existence` [0,1], `sinceConfirmedMillis`≥0); `Provenance(EvidenceSource source, List<String> contributors, double assocCost, boolean reupdated)`; `MemoryFacts(boolean recovered, double identityConfidence, long dormantMillis, int galleryMatches, double matchDistance)` (`identityConfidence`/`matchDistance` [0,1], `dormantMillis`/`galleryMatches`≥0 — proto's `Memory` renamed to avoid shadowing `java.lang` concepts); `LockFacts(boolean locked, long lockSeqApplied)` (proto's `Lock` renamed for the same reason; `lockSeqApplied`≥0); `Timing(long firstSeenMillis, long lastSeenMillis, long lastConfirmedMillis, int ageFrames, int hits, int misses)` (`ageFrames`/`hits`/`misses`≥0). All `List` components defensively copied. Test-only `com.drones.vision.perception.domain.model.ObjectStateFixtures#everyFieldDistinct()` (src/test/java) builds one instance with every numeric leaf in the whole tree pairwise distinct — reused by a later CV-ORCHESTRATION step for proto→Java→JSON→TS round-trip testing; treat its class/method signature as a stable cross-wave API, not just test scaffolding. - `PipelineConfig(ModelRef model, double confidenceThreshold, int inferenceFps, int maxInFlightInferences, Set<String> labelFilter, EventRuleConfig eventRule, boolean detectionEnabled, TrackingConfig tracking, Set<String> labelDenyFilter, boolean trace)` — **10-arg canonical** (CV-ORCHESTRATION wave W1 step 3 added `trace`, the last component), with 5/6/7/8-arg convenience ctors kept from before that wave — each now passes `trace=false` explicitly (transitively, through the chain) and says so in its javadoc; no new overload was added for `trace` itself (CLAUDE.md rule 10 — every 9-arg call site from before this wave was updated instead). `trace` is per-stream warm-trace-tier demand (docs/plans/active/CV-ORCHESTRATION-PLAN.md §4.4) — a later wave's `TraceDemand` is what actually flips it per-stream; every call site this wave passes `false` (or folds an existing config's own `trace()`, e.g. `CvProfile#toPipelineConfig`/`DefaultStreamService#mergeConfig`/`#withTracking`/`StartStreamRequest#mergeOnto`/`CvWiring#streamDefaultConfig` — same "not a profile/patch/request concern, always the platform default's own value" treatment as `maxInFlightInferences`). `labelDenyFilter` drops labels even when `labelFilter` would keep them, applied at the single drop site in `StreamPipeline#onDetectionResult`; `detectionEnabled` is the per-stream **operator-intent** gate, ANDed with the system-derived `StreamPipeline#detectionDemand()`/`#detectionPolicyAlwaysOn` (wave D1/D2 split the result into three separately-read gates — see `StreamPipeline#detectionGateOpen()`/`#liveGateOpen()` below; this field's own meaning is unchanged). `defaults()` = `yolo26n.pt`/latest, 0.4, 10fps, 2 in-flight, no filter, no deny, `EventRuleConfig.defaults()`, detection **off** by default (`vision.cv.detection-default-enabled=true` flips deployment-wide), tracking `ASSOCIATE`, trace **off**.   - **Ordering inside `onDetectionResult` is load-bearing: the live plane runs BEFORE the durable plane.** Both gates are read once, together, at the top, so the order between the two planes is otherwise free — and it must stay this way. `detectionRepositoryPort#save` is synchronous I/O; running it between a detection completing and the live read models (`latestDetections`/`trackBook`/`trackingStats`/…) makes every read model a polling client observes lag by one database round trip. ## Conventions
- No Spring/framework imports anywhere in this module.
- **The acting user is a method parameter (`UserId actor`), never a constructor dependency.**
- Constructor injection; every collaborator `Objects.requireNonNull`'d **except** the deliberately-nullable ones: `DefaultStreamService`'s `usageTracker`/`detectionEventRepositoryPort`/`liveUpdatePublisherPort`; `StreamPipeline`'s `eventEngine`/`assetId`/`liveUpdatePublisherPort`/`telemetrySupplier`; `UsageTracker`'s `liveUpdatePublisherPort`/`telemetryObserver`; `DetectionEventEngine`'s `usageTracker`.
- Injected collections defensively copied at construction (`List.copyOf`): `VideoSourceRegistry.sources`, `UsageTracker.telemetrySources`, `FeedTransmitterRegistry.transmitters`.
- `Flow.Subscriber` used identically in two places — `StreamPipeline` (video) and `UsageTracker`'s internal `TelemetrySubscriber` (telemetry) — both request one item at a time and re-request after processing.
- Concurrency: `ConcurrentHashMap` for shared registries; `AtomicInteger`/`AtomicBoolean` for pipeline counters/close-flags; `volatile` for single-writer/many-reader fields (`StreamPipeline.config`/`latestDetections`/`latestFrame`/`latestRawFrame`). One dedicated daemon `ScheduledExecutorService` per service (`DefaultStreamService`, `UsageTracker`), scheduling `SupervisedPublisher` retries.
- Per-asset mutable state in `UsageTracker` (`Tracking`) is synchronized on the `Tracking` instance itself, not a module-wide lock — different assets never contend.
- Every port interface's javadoc documents **Contract** and **Threading**; ports with backpressure concerns (`VideoSourcePort`) add **Backpressure**.
- Records validate in the compact constructor with manual `if (…) throw new IllegalArgumentException(…)`; `Objects.requireNonNull` is application-layer only.

## Gotchas
- **`DetectionExtrapolator` no longer exists** — wave W2.2 deleted it outright (plan §7 defect D4) rather than port it into `WorldModel`, since `.at()` (its only query method) had no production caller since server-side burn-in was removed. If a future "what's currently detected, extrapolated between inferences" need arises, it needs a fresh design, not a resurrection of this class — `WorldModel#objects()`/`#latestDetections()` are the current answer to "what's currently detected," un-extrapolated.
- **A detection failure never closes `StreamPipeline`** — only `onError` (source) and a synchronous publish exception are fatal. One `PIPELINE_ERROR` fires per outage (false→true transition), not per failed frame; every failure after that is silently counted.
- **Only a failed *probe* doubles the backoff** — an in-flight call that fails after the outage began is counted but must not touch `backoffNanos`/`nextProbeAtNanos`.
- **Exactly one probe in flight at a time** — `probeInFlight` and the deadline check are claimed together inside one `synchronized (outageLock)` block.
- **In-flight inference bound is skip-not-queue** — a slow `DetectionPort` degrades detection *rate*, never blocks video.
- **`StreamPipeline`'s sampling rate is measured**, not fixed — trusted only after 5 warmup frames, seeded from the first observed delta.
- **The `/live` stop-freeze bug was a real backend bug**: `DefaultStreamService#stop` used to call `VideoSourcePort#close` synchronously on the request thread; a stuck native grab (up to 20s) starved a browser's connection pool. Fixed: `stop()`/`UsageTracker#unsubscribeTelemetry` do fast in-memory work synchronously and defer `close()` to a fire-and-forget virtual thread.
- **What survives a reconnect vs. re-establishes**: the `StreamPublisherPort` session, `UsageId`/`AssetUsage`, and the pipeline's own outage/backoff state survive untouched — a reconnect resubscribes the *same* pipeline to a freshly-opened publisher. Only the source-side `Flow.Publisher`/`Subscription` re-establishes. Source backoff is 1s→30s doubling, deliberately different from the pipeline's 1s→10s detection-outage backoff.
- **`VideoFrame#sequence()` is not guaranteed monotonic across a reconnect** — the adapter regenerates it fresh on every `open()`; sampling still works, it just restarts its cycle.
- **`DetectionEventEngine.accept`'s per-label absence check only runs when a new `DetectionResult` completes** — no background timer; during a detection outage or gated-off period, an open event stays open, un-evaluated, until the next completed result's timestamp reveals the gap.
- **`DetectionEvent#position` is frozen at open time, not live-tracked.**
- **`PipelineConfig#eventRule`'s labels are independent of `labelFilter`/`labelDenyFilter`** — three sets, no cross-validation; a label excluded by `labelFilter`/`labelDenyFilter` but still named in `eventRule.labels()` silently never opens an event (the deny-list is enforced once, centrally, upstream of the event engine).
- **A model-id re-arm cannot close/reopen any adapter-side detection session from here** — `DetectionPort` exposes only `detect(frame, config)`, no per-stream lifecycle method on the interface; `updateConfig` only clears this pipeline's own model-bound state.
- **Toggling `detectionEnabled` does not reset outage/backoff state** — that answers "is cv-service healthy," independent of the operator's local switch.
- **`UsageTracker.TelemetrySubscriber.onError` is an empty method by design** — best-effort telemetry must never affect stream/usage lifecycle. Unaffected by ASSET-FLOWS S4/BK2b's `LINK_LOST` wiring: `SupervisedPublisher` intercepts `onError`/`onComplete` and never forwards them downstream, so `TelemetrySubscriber` (the downstream `Flow.Subscriber`) never sees a source failure at all — the new `reportLinkLost` call sits entirely inside `subscribeTelemetry`'s `SupervisedPublisher` construction, one level up.
- **`EventType.LINK_LOST` (platform bell event, ASSET-FLOWS S4) and `FlightPhase.LINK_LOST` (`vision-flight`'s domain phase enum, DRONE-ONBOARDING-era) are unrelated types that happen to share a name.** The former is a one-shot notification raised from `subscribeTelemetry`'s outage callback; the latter is a `UsagePhase`/`FlightPhase`-translated session *state* this module's own `applySample`/`evaluateLinkHealth` compute from wall-clock silence (see `toFlightPhase`/`toUsagePhase` above). A silent aircraft can sit in `FlightPhase.LINK_LOST` for minutes without a fresh `EventType.LINK_LOST` firing (the event only fires on a genuine `TelemetrySourcePort` outage, not on "no sample recently" alone — see `evaluateLinkHealth`'s own Gotchas entry), and a `TelemetrySourcePort` outage that reconnects within `phaseSettings`'s silence window raises the event without the phase ever transitioning. Do not conflate the two when reading either code path.
- **`UsageTracker` never opens a usage from a sample arriving** — reopening from a straggler racing a legitimate close would fabricate a phantom flight. A session's opening stays explicit (`engage`) or stream-triggered, never an implicit side effect of telemetry. **ALWAYS-ON-FLOW wave A2 narrowed what "drops" means, and this is a deliberate doctrine change, not a bug fix.** A sample with no open usage used to be discarded outright; it now still writes no durable record and still opens nothing, but it *does* update `#latestTelemetry`, publish to `liveUpdatePublisherPort`, and run the `telemetryObserver` geofence evaluation. The rule being preserved is "a flight is a session, and a session is opened deliberately"; the conflation being ended is "a live link needs permission to be true." Read the two halves of `#applySample` as answering different questions — *is this aircraft up, and where?* (always) vs. *what belongs on this flight's record?* (only with a usage).
- **`evaluateLinkHealth(AssetId)` is not wired to any scheduler** — a directly-callable, deterministically-testable entry point; production periodic wiring is left to `vision-app`. Until something calls it repeatedly, a silent aircraft's phase only updates when a sample happens to arrive or `evaluateLinkHealth` is invoked by hand.
- **No code path in this module ever closes a usage on a source/pipeline failure alone** — confirmed for both video (`DefaultStreamService#stop`'s own javadoc: "a source failure alone never does") and telemetry (`UsageTracker.TelemetrySubscriber.onError` is deliberately empty, `SupervisedPublisher` retries forever and never signals a stop). `docs/plans/active/OPERATOR-UX-5-PLAN.md` finding U1's idle-usage-close sweep (`UsageIdleCloseService`, `vision-warehouse`) is therefore the **only** recovery for a usage orphaned by a crashed process, a killed station, or a lost MAVLink link — it closes such a usage from the outside, on a coarse timer (default 10 minutes), not by fixing this gap; it does not replace `evaluateLinkHealth`'s finer-grained `LINK_LOST` phase transition, and no code in this module changed for it. **ASSET-FLOWS S4/BK2b changed the "silent" half of this fact, not the "no auto-close" half**: a telemetry-source outage now raises one `EventType.LINK_LOST` notification (see the `SupervisedPublisher`/Gotchas entries above) the moment it begins, well before the 10-minute idle-close sweep would ever fire — an operator learns of the loss immediately even though the usage itself stays open exactly as before, unchanged.
- **`Tracking#activeDevices` and `Tracking#activeVideoStreams` count different things — do not collapse them.** `activeDevices` drives usage open/close for *any* device (video or telemetry-only); `activeVideoStreams` is video-only and is the sole `streamCount` `FlightPhaseRule` sees (must read `0` for a telemetry-only asset).
- **Telemetry teardown is gated on `AssetUsage#origin()`, not on `Tracking#activeDevices` alone** (wave Z1) — `#deviceStreamStopped` only calls `#unsubscribeTelemetry` when the usage is *not* `OPERATOR`-origin at that instant (read **after** the same synchronized block's own open/close branch may have changed it). An `OPERATOR`-origin usage's telemetry only ever closes via `#disengage`. **ALWAYS-ON-FLOW wave A3 added a third, independent reason to keep it: `Tracking#telemetryPinned`.** The guard now reads `allDevicesStopped && !telemetryPinned && !(usage != null && origin == OPERATOR)`, so with the policy runner on, stopping the last stream — by hand, or via `IdleStreamReaper`'s automatic 10-minute idle sweep, which is the far commoner case — no longer ends the aircraft's telemetry. Do not "simplify" this back to "tear down whenever `activeDevices` hits zero": that is both the B4-adjacent regression Z1 fixes (a stream stopping would silently kill an engaged aircraft's commandability) and the exact defect wave A exists to close.
- **`Tracking#telemetryDeviceIds` is a claim set, not just a subscribed-device index** — `#subscribeTelemetry` adds a `DeviceId` to it *before* opening anything, so `#engage` and `#deviceStreamStarted` racing for the same asset never both open the same device's `TelemetrySourcePort`. A device that gets claimed but turns out to have no owning `Device`/no `TELEMETRY` capability/no supporting source stays claimed until the next `#unsubscribeTelemetry` — harmless (nothing was ever open for it), but do not read "claimed" as "genuinely subscribed."
- **`Tracking#telemetryPinned` is policy, not a refcount** — it is a single boolean per asset, set by `#pinTelemetry` and cleared by `#unpinTelemetry`, and it deliberately does not count callers. There is exactly one production pinner (`station/vision-app`'s `TelemetryPinRunner`, one sweep, one pin per asset), so a count would model a contention that does not exist. A second, independent pinner is the thing this cannot express — give it a real refcount before adding one, rather than assuming the flag composes.
- **`#unpinTelemetry` is not the inverse of `#pinTelemetry`** — it clears the flag unconditionally, but only tears subscriptions down when nothing else still needs them. Unpinning an asset that is mid-flight (active devices, or an `OPERATOR`-origin usage) leaves its telemetry running, exactly as `#deviceStreamStopped` would. This is what lets a policy sweep unpin a just-deactivated asset without cutting the link out from under the operator flying it.
- **Nothing in this module schedules pinning** — `#pinTelemetry`/`#unpinTelemetry` are directly-callable, deterministically-testable entry points, and the periodic reconciliation lives in `station/vision-app` (`TelemetryPinRunner`, `vision.telemetry.always-on.*`, **default off**). Same split as `#evaluateLinkHealth` above. With the property off, this module behaves exactly as it did before wave A: nothing is ever pinned, and telemetry opens only via a video stream or `engage`.
- **`AssetUsage#phase` is typed `com.drones.vision.warehouse.domain.model.UsagePhase`, never `com.drones.vision.flight.domain.model.FlightPhase`**, despite the two being name-parallel — deliberate: warehouse is the ArchUnit-enforced pure leaf and may not depend on flight. `UsageTracker#toFlightPhase`/`toUsagePhase` are the only conversion point; nothing else in this module or warehouse should import the other context's phase enum.
- **`UsageTracker` must never import a `*RepositoryPort` from `vision-warehouse` or `vision-flight`** — a new asset/device/usage need belongs on warehouse's `AssetDirectoryService`/`UsageSessionService`; a new telemetry-persistence need belongs on flight's `TelemetryService`. The phase translation is the one thing that legitimately crosses as a bare type (`FlightPhaseRule`/`FlightPhase`), run only here since warehouse may never depend on flight. `MaintenanceQuery` (ASSET-FLOWS-PLAN S1) is the one further exception to the "no cross-context type" spirit, and it is deliberate: it is warehouse's `application` package, not a repository port, filed there specifically so a cross-context caller need not import `domain.port`.
- **`UsageTracker#engage`'s maintenance-grounding refusal only gates the explicit operator verb, never the stream-triggered session-open path** (ASSET-FLOWS-PLAN S1, wave BK1) — `onStreamStarted`/`deviceStreamStarted` still open a usage for a grounded asset. This is deliberate, not an oversight: `DefaultStreamService#startStream` already starts the pipeline and publishes `STREAM_STARTED` before ever calling `onStreamStarted`, and its exception-handling `catch` block never calls `pipeline.close()` — refusing at that point would leak a running pipeline with nothing left to stop it, not prevent a flight. If a future wave wants a stream-side gate too, it must first give `DefaultStreamService#startStream` a rollback path (`pipeline.close()` on refusal) — this is not a `UsageTracker`-only change.
- **`AssetDirectoryService` deliberately wraps warehouse's repository ports directly rather than reusing `AssetService`/`DeviceService`** — those two already depend on `AssetLiveStatePort`, whose only implementation (`StreamBackedAssetLiveState`, here) depends on `UsageTracker`, so routing `UsageTracker` through `AssetService` would close a Spring bean cycle (`UsageTracker → AssetService → AssetLiveStatePort → UsageTracker`). Anyone "cleaning that up" by folding `AssetDirectoryService` into `AssetService` reintroduces the cycle.
- `storage/persistence`'s `AssetUsageMapper` **does** round-trip `AssetUsage#phase`; its `PREFLIGHT` fallback on read fires only for rows written before `V19__asset_usage_phase.sql`, whose column is null. A usage saved today reloads with the phase the tracker computed.
- **A non-immediate `UsageSummaryBatchSettings` bounds, but does not eliminate, how stale `AssetUsage#sampleCount`/positions can read** — up to `batchWindowMillis` behind the freshest fold, lost (not delayed) on a crash before flush. Safe by construction: the durable `telemetryService.record` write for the same sample already landed synchronously regardless of batching.
- **`UsageTracker.onStreamStarted`'s `streamId` is only ever recorded on the call that opens the usage** — for a multi-device asset, only the first device's stream is visible on `AssetUsage#streamId`.
- **`DefaultStreamService` allows only one active stream per device** — starting a second throws `IllegalStateException` rather than replacing it.
- **The tracking component of the `PipelineConfig` passed to `start`/`startStream` is the *bottom* layer of the fold, not the final answer** — the deployment seed and request patch apply on top inside the service.
- **A `TrackingConfigPatch`'s `lock` is null-means-unchanged** — releasing a lock is the explicit `TargetLock{release=true}` form, never an omission.
- `ProbeService#probe` never registers anything — a probe's `StreamId` is fresh, transient, looked up nowhere else.
- **A `detectionEnabled` but currently-undemanded stream produces no `DetectionResult` at all** — `DetectionEventEngine`, training-sample capture, `DetectionRepositoryPort#save`, and `DetectionLiveUpdatePort#publishDetections` all go quiet; video and `latestFrame()`/`latestRawFrame()` are unaffected.
- **A freshly started stream's `lastDemandAt` starts at `Instant.EPOCH`, not the stream's own start time** — do not "simplify" this back to `Instant.now()`; that reopens a 30s-of-free-inference-per-stream bug.
- **Pull mode's gate stops the JVM from forwarding a result, not the worker from producing one** — `PullResultSubscriber#onNext` drops a gated-off result, but the Python worker behind `PulledDetectionPort` keeps pulling/inferring at full rate regardless (`detectionEnabled`/policy isn't on the pull wire). **Wave D2 closed the "Finding 6" half of this** for an `ALWAYS` asset specifically: before D2, an `ALWAYS`-policy pull stream with no viewer paid for the worker's continuous inference and then discarded every result here (`detectionGateOpen()` used to be exactly `liveGateOpen()`); now that `detectionGateOpen()` also ORs in the policy opt-in, such a stream's results are forwarded and kept durably. The underlying fact this gotcha describes — the worker's own loop has no demand/policy signal on its wire and always runs — is unchanged and is exactly what makes the D2 fix possible (the work was already being done, D2 just stopped throwing it away for `ALWAYS` streams).
- **`DetectionPolicyPort` is deliberately a separate port, not a fourth OR-term in `DetectionDemandPort`/`LiveAndPollDetectionDemand`** (wave D1, a reasoned deviation from that wave's literal wording) — folding the policy opt-in into `detectionWanted`'s own boolean would make it impossible for wave D2 to close the live gate independently of the inference/durable gate for an `ALWAYS` asset, since live would then be reading the same merged signal durable does. `LiveAndPollDetectionDemand` (`vision-api`) is untouched by this wave.
- **`maxInFlightInferences` stays a fixed `2`/stream constant (`PipelineConfig.defaults()`), not a property key, and there is still no fleet-wide inference budget** — deliberately deferred (docs/plans/active/ALWAYS-ON-FLOW-PLAN.md D3, out of wave D1/D2's scope). An operator opting several assets into `DetectionPolicy.ALWAYS` can drive concurrent inference well past the ~3-4 streams/10fps ceiling one `cv-service` instance can sustain, with nothing in this module or `vision-app` to warn or throttle across streams — `ALWAYS` is opt-in per asset but **not** capacity-aware. Treat this as a known, load-bearing limitation of the current wave, not an oversight to quietly patch; D3 is the place a fleet-wide budget belongs.
- **The detection gate is three questions, not one (wave D2, docs/plans/active/ALWAYS-ON-FLOW-PLAN.md §4)** — `StreamPipeline` used to AND `detectionEnabled` with a single `detectionDemand`; it now separately answers **inference** (`detectionEnabled && (viewerDemand || DetectionPolicy.ALWAYS)`), **durable** (follows inference — persistence/`DETECTION` event/`DetectionEventEngine`), and **live** (`detectionEnabled && viewerDemand` alone, unchanged, narrower than inference). Do not read "durable follows policy, live follows demand" as meaning durable stops for an `ON_VIEW` asset someone is actively watching — durable follows the *wider* inference gate, which viewer demand alone still satisfies exactly as before D2; only an `ALWAYS` asset can ever pull the durable/live gates apart. A true→false transition clears state, but **which** state depends on **which** gate closed: the inference gate's own edge does the full clear (`clearDetectionDerivedState()` — every detection-derived read model, `latestDetections()`/extrapolator/track book/rate-and-latency windows, not just future detections); the live gate's edge — reachable only for an `ALWAYS` asset losing its last viewer while inference keeps running — does a narrower live-only clear (`clearLiveDerivedState()`, everything the full clear does except `pipelineLatency`/`detectionRate`, since those windows are still being meaningfully written to by ongoing durable-only inference). An outage leaves the last value alone regardless (still trying, no fresher answer *yet*); a closed gate never tries again on that plane, so holding the last value would assert something false (CLAUDE.md §9). `StreamPipeline#handleDetectionGateTransition()` is the single funnel point for both gate inputs, `synchronized` and edge-triggered against each gate's own last-observed value; `onDetectionResult` re-checks **both** gates independently on entry/exit to close the late-completion race for each — a late result can still be saved durably (inference gate still open) even though live never sees it (live gate already closed). A non-`ALWAYS` asset can only ever take the inference-gate edge, so its behavior is byte-identical to pre-D2.
- **`DetectionState` reports gating, never health** — a stalled cv-service reads `RUNNING` throughout its entire outage; the outage/backoff machinery and `PIPELINE_ERROR` events are the only source of truth for detector health.
- **`CvProfileRepositoryPort` is implemented** — `storage/persistence`'s `JpaCvProfileRepository`, backed by `V29__cv_profiles.sql`, landed by the separate CV-SETTINGS wave W3 (commit `49e84edc`) and is wired into `vision-app`'s Spring context; profiles/bindings persist across a restart. A prior revision of this doc (written during this wave's own W2.1 documentation pass) claimed "zero implementations… nothing persists until wave W3 lands, `vision-app` does not yet construct a bean" — that was already false when written (W3 had already merged before this wave's baseline), not a regression introduced by this wave; corrected here.
- **`DefaultCvProfileService#effective`/`#coverage` take `platformDefault` as an explicit parameter, not a wire field** — this module's application layer cannot read `@ConfigurationProperties`; the caller (controller/wiring layer) must assemble it exactly as `StreamDetectionSupport` does for `start` today. A W5 controller that forgets this will NPE on `Objects.requireNonNull`, not silently invent a default.
- **`CvProfileService#fork` has no dedicated endpoint in the frozen §5.2 wire contract** — built because the W2 task brief asked for it explicitly as a service method; W5 must decide whether to add `POST /api/cv/profiles/fork` or have the client do a plain copy-then-`POST /api/cv/profiles`.
- **`CvProfile#groupId` is `null` if and only if `builtIn` is `true`** — the compact constructor enforces both directions. A future "seed a built-in scoped to one group" feature is not representable with this record as-is; it would need a deliberate model change, not a validation relaxation.
- **`TrackRef#identityConfidence`/`#dormantMillis` (docs/plans/active/TRACK-FOLLOW-PLAN.md §3.1) now have exactly one reader: `WorldModel`'s follow-state machine (formerly `FollowTracker`, wave W2, folded into `WorldModel` unchanged by wave W2.2)** — `WorldModel`'s track-booking (formerly `TrackBook`) and `TrackingStatsWindow` still only read the fields they read before W1/W2 landed; a bind with `identityConfidence>0` is what turns "reacquired," not "freshly acquired," into `FollowStatus.recoveredAfterMillis()`/`recoveryConfidence()`, and the state machine deliberately does not treat it as a loss (same `trackId`, same `label`, straight back to `HOLDING`/`COASTING`).
- **`WorldModel.DEFAULT_MEMORY_TTL` (30s, the former `FollowTracker`'s own constant, ported unchanged) is a documented class constant, not read off `TrackingConfig`** — the plan's literal instruction was "`reacquirable` reads the pipeline's resolved `TrackingConfig` memory TTL, never a constant in this module," but `TrackingConfig` (10-component record) has no `memoryTtlMillis` field yet even though the wire proto (`cv.proto` field 10) defines one; no Java code anywhere decodes it. `StreamPipeline` constructs `new WorldModel(settings.trackRetention(), WorldModel.DEFAULT_MEMORY_TTL, settings.renderTier(), ...)` — still a constant, not settings-threaded, unchanged by the W2.2 fold. A future wave adding `TrackingConfig#memoryTtlMillis` (domain-modeler territory) need only update this one construction call site.
- **A lock already present in a pipeline's `PipelineConfig` at construction time is seeded into `WorldModel` from the `StreamPipeline` constructor itself, not left for `updateConfig`** — `DefaultStreamService#start(DeviceId, PipelineConfig, TrackingConfigPatch)` folds the requested `TrackingConfigPatch` (which may itself carry a lock) into the very first `PipelineConfig` handed to `new StreamPipeline(...)`, before `updateConfig` is ever called for that pipeline. Without the constructor seed, that lock's first generation would silently never reach `REQUESTING`/`HOLDING` and `reacquirable` would default false for it. (Ported unchanged from the former `FollowTracker`'s own behavior by wave W2.2.)
- **CV-ORCHESTRATION wave W2 is now fully wired through W2.6 — `FrameLedger`/`WorldObject`/`GateDecision` (and their families) ARE constructed by production code paths.** `StreamPipeline#maybeDetect` records a `GateDecision` into `FrameGateLedger` for every branch that ends without sending a frame (wave W2.3); `DetectionResult#ledger()` is populated by `cv/grpc`'s `DetectionFrameCodec#decode` whenever cv-service attaches a `FrameLedger` (wave W2.5), fed into `FrameLedgerRing`; `WorldModel` (wave W2.2) replaces `TrackBook`/`FollowTracker`/`DetectionExtrapolator` and constructs a `WorldObject` per tracked identity every accepted frame. A prior revision of this doc (written during this wave's own W2.1 step, before any of the above landed) said none of this was reachable yet — that was accurate for W2.1 alone but is stale now; corrected here. **As of wave W2.8, `WorldObject` also has a dedicated read-model accessor (`StreamService#worldObjects(StreamId)`) and wire DTO (`station/vision-api`'s `WorldObjectResponse`)** — see the `WorldObject`/`DetectionLiveUpdatePort` bullets above; what remains open is only `IntentPolicy#detectFloor`/`#rateCeiling`, computed but unconsumed (wave W2.6, see `IntentPolicy`'s own bullet).
