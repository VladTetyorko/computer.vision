# vision-identity

Users, groups, roles, authentication, and the pilot→asset assignment roster.

**What it deliberately does not do**: resolve *what* a user may see — `VisibilityScope`/`AccessDeniedException` live in `vision-platform` (every context filters by them, not just this one). This context turns a `User` into a `VisibilityScope` (`ScopeResolver`) and manages the roster a scope is computed from — memberships, group tree, pilot→asset assignments. It does not decide whether a command may proceed against a specific asset/device — that is each consuming context's own gate (e.g. flight's `DefaultFlightCommandService`).

**Depends on:** `vision-kernel` (`UserId`, `GroupId`, `AssetId`…) · `vision-platform` (`VisibilityScope`, `AccessDeniedException`, `AuditTrailPort`/`AuditEntry`) · `vision-warehouse` — `DefaultAssignmentService` reaches `AssetService#details(AssetId)` for the one fact it needs (asset exists, its group) to run the grant check
**Used by:** `vision-map` (viewer resolution), `vision-app`, `vision-api`, `adapter-persistence`
**Build/test:** `./mvnw -B -pl contexts/vision-identity test`

## API surface

### `com.drones.vision.identity.domain.model`
- `record Group(GroupId id, String name, GroupId parentGroupId)` — org-chart node a `User` holds a `Membership` in; `parentGroupId` nullable (`null` = root); `name` non-blank; subtree scoping is `ScopeResolver`'s job
- `record Membership(GroupId groupId, Role role)` — a `User`'s role within one group; rides on the `User` aggregate, no separate membership repository
- `enum Role` — `VIEWER`, `PILOT`, `MANAGER`, `ADMIN` (docs/plans/active/AUTH-ROLES-PLAN.md §3.2, wave B1 prepended `VIEWER`), declared least→most privileged; ordinal ordering is load-bearing (`User#topRole()` picks the highest role by ordinal). **Read the ordering as authority, not visibility** — `VIEWER` sits at the bottom of what a caller may *do* (holds no `Capability`) while being *deliberately* handed one of the *widest* visibility scopes once wave B6 lands (a group-wide read, matching a `MANAGER`'s shape) — see the enum's own javadoc and `RoleTest`/`UserTest#topRolePicksPilotOverViewerRegardlessOfInsertionOrder` for the pinned prepend-is-not-a-reorder proof
- `enum AssignmentRole` (docs/plans/active/AUTH-ROLES-PLAN.md §3.4, wave B1) — `PILOT` (flight seat + camera seat), `CREW` (camera seat only) — the CREW-CONTROL-PLAN.md IC-2 answer, held per (pilot, asset) link rather than on `Role`, because the same person is routinely `PILOT` on one asset and `CREW` on another and a global role could never express that. **No ordinal semantics** — unlike `Role`, declaration order here means nothing
- `record Assignment(UserId pilot, AssetId asset, AssignmentRole role)` (wave B1) — one roster row, as returned by `AssignmentRepositoryPort#assignmentsForAsset(AssetId)`; not a separate aggregate, just a read shape over the assignment link
- `record User(UserId id, String username, String displayName, String email, String passwordHash, boolean enabled, boolean mustChangePassword, List<Membership> memberships)` — `username` non-blank, normalized lower-case in the compact ctor; `email` shape-checked only (non-blank, contains `@`), not RFC-validated; `passwordHash` opaque to the domain (BCrypt lives behind `PasswordHasherPort`); `memberships` defensively copied; 6-arg convenience ctor defaults **both** new fields, `mustChangePassword=false, memberships=List.of()`; `topRole()` → `Optional<Role>`; `toString()` renders `passwordHash=***`. `mustChangePassword` (docs/plans/active/AUTH-ROLES-PLAN.md §3.5/D13, wave B2, NEW) — set `true` by `UserService#create` (admin-created user, unknown password to the admin) and `UserService#setPassword` (admin reset), cleared to `false` by `AuthService#changePassword` (self-service) and `UserService#createFirstAdmin` (bootstrap, self-chosen password); purely a UI/flow signal — nothing in this module enforces it (no gate refuses a stale-flag session), enforcement is the API layer's job (B3)

### `com.drones.vision.identity.domain.port` (driven — implemented by adapters)
- `AssignmentRepositoryPort` — the pilot→asset join, independent of both `User` and `Asset`: `void assign(UserId, AssetId, AssignmentRole)` idempotent upsert **(docs/plans/active/AUTH-ROLES-PLAN.md §3.4, wave B1 replaced the 2-arg form — re-assigning an existing link with a different `AssignmentRole` changes the seat rather than creating a second link)**; `void unassign(UserId, AssetId)` idempotent; `Set<AssetId> assetsForPilot(UserId)`; `Set<UserId> pilotsForAsset(AssetId)`; `boolean isAssigned(UserId, AssetId)`; `Optional<AssignmentRole> roleFor(UserId, AssetId)` (wave B1, NEW — the IC-2 seat lookup); `List<Assignment> assignmentsForAsset(AssetId)` (wave B1, NEW — the roster, with roles). Empty set/list (never `null`) means "no links"; `assetsForPilot`/`pilotsForAsset` include a link regardless of its `AssignmentRole` — visibility follows from being assigned at all, only the verb a seat grants differs. **Gotcha for adapter authors** (found wave B2): an in-memory `Map`-of-`Map` implementation of `unassign` must not write `byPilot.getOrDefault(pilot, Map.of()).remove(asset)` — `Map.of()` is immutable, so unassigning a pilot with zero existing links throws `UnsupportedOperationException`; `DefaultAssignmentServiceTest`/`DefaultScopeResolverTest`'s fakes both had this latent bug (fixed in wave B2, see Status)
- `GroupRepositoryPort` — `Optional<Group> findById(GroupId)`; `List<Group> findAll()` snapshot; `Group save(Group)` upsert
- `PasswordHasherPort` — `String hash(String rawPassword)`; `boolean verify(String rawPassword, String hash)`; implemented outside domain/application (BCrypt, `vision-app`)
- `UserRepositoryPort` — `Optional<User> findByUsername(String)` case-insensitive; `Optional<User> findById(UserId)`; `User save(User)` upsert; `List<User> findAll()` snapshot

### `application` (root package)
- `AuthService` (interface) → `DefaultAuthService(UserRepositoryPort, PasswordHasherPort, AuditTrailPort)` (wave B2 widened from 2 to 3 args) — login checks + principal reload + self-service password change + bootstrap probe
  - `Optional<User> authenticate(String username, String rawPassword)` — `null`/blank input short-circuits to empty **with no audit write** (no known actor id to attribute a blank attempt to); returns the user only if **both** `enabled()` and `passwordHasher.verify(...)` hold. Unknown username, disabled user, wrong password are **all** `Optional.empty()` alike — never throws, deliberately, to avoid an information leak. **Wave B2**: looks the user up by username *first*; an unknown username still audits nothing (same "no actor id" reason), but once a real user is found, every attempt is audited — `AuditAction.LOGIN`/`AuditTargetType.USER` on success, `AuditAction.LOGIN_FAILED`/`AuditTargetType.USER` on a wrong password or a disabled account — always attributed to that user's own id
  - `Optional<User> find(UserId)` — reload the current session's principal fresh on every request
  - `Optional<User> loadByUsername(String)` — for Spring Security's `UserDetailsService` bridge. Both are kept — two different callers, neither subsumes the other
  - `Optional<User> changePassword(UserId id, String currentPassword, String newPassword)` (wave B2, NEW, D15) — **self-service**, unlike `authenticate` may safely reveal less by returning `Optional.empty()` uniformly (caller is already authenticated as themself), since the only failure paths are: unknown id, disabled account, wrong `currentPassword`. Rejects a blank `newPassword` with `IllegalArgumentException` (a caller bug, not an auth outcome). On success: replaces the hash, clears `mustChangePassword` to `false`, saves, records one `AuditAction.UPDATED`/`AuditTargetType.USER` entry attributed to `id` itself. **No audit entry on any failure path** (nothing changed)
  - `boolean adminExists()` (wave B2, NEW, D14 bootstrap gate) — `true` iff some user is both `enabled()` and has `Role.ADMIN` as `topRole()`. The one-way latch a first-run "create the admin" flow polls before offering itself; a disabled admin does not count (matches `DefaultUserService#createFirstAdmin`'s own independent check — see Gotchas, the two are deliberately not shared)
- `UserService` (interface) → `DefaultUserService(UserRepositoryPort, PasswordHasherPort, AuditTrailPort)` (wave B2 widened from 2 to 3 args) — every scope-gated method takes the acting `VisibilityScope` **and, wave B2, a separate `UserId actor`** to attribute its audit entry to (see Gotchas — deliberately not bundled with `VisibilityScope`); `unbounded()` (ADMIN/auth-off) passes every gate
  - `User create(UserSpec, UserId actor, VisibilityScope acting)` (wave B2 added `actor`) — `!acting.canManageOrg()` → 403; no-memberships spec allowed only for `unbounded()`; per membership, `!acting.includesGroup(m.groupId())` → 403, a role above `maxGrantableRole(acting)` → 403; duplicate username (case-insensitive) → 409. **Always** sets `mustChangePassword=true` on the created user (D13 — an admin-created account starts with a password the admin, not the new user, chose). Records one `AuditAction.CREATED`/`AuditTargetType.USER` entry attributed to `actor` after save
  - `private static Optional<Role> maxGrantableRole(VisibilityScope)` — `UNBOUNDED`→`ADMIN`, `GROUPS`→`MANAGER`, `ASSIGNED_ASSETS`→empty (unreachable, `canManageOrg()` already excludes it)
  - `List<User> list(VisibilityScope acting)` — `unbounded()`→every user; `GROUPS`→users with ≥1 membership `acting.includesGroup(...)`; any other scope→empty
  - `User setEnabled(UserId, boolean, UserId actor, VisibilityScope acting)` (wave B2 added `actor`) — `!acting.canManageOrg()` → 403; non-unbounded acting scope must include one of the target's membership groups → 403; idempotent; preserves the target's existing `mustChangePassword`. Records one `AuditAction.ACTIVATED`/`DEACTIVATED` (`AuditTargetType.USER`) entry attributed to `actor`, **only if** the enabled flag actually changes — re-disabling an already-disabled user audits nothing
  - `User setMemberships(UserId id, List<Membership> memberships, UserId actor, VisibilityScope acting)` (wave B2, NEW) — same management gate shape as `create`/`setEnabled` (checked against the **union** of the target's old and new membership groups, so a manager can both add a group they administer and remove one they no longer can see); replaces the target's whole membership list. Diffs old vs. new and records one `AuditAction.GRANTED`/`AuditTargetType.GROUP` entry per group added and one `REVOKED`/`GROUP` per group removed (both attributed to `actor`) — an unchanged set audits nothing
  - `User setPassword(UserId id, String rawPassword, UserId actor, VisibilityScope acting)` (wave B2, NEW, D15 admin reset) — same management gate as `setEnabled`; rejects a blank `rawPassword` with `IllegalArgumentException`; **always** sets `mustChangePassword=true` (D13 — the target didn't choose this password). Records one `AuditAction.UPDATED`/`AuditTargetType.USER` entry **unconditionally** (no way to detect a no-op reset — `PasswordHasherPort#hash` never produces comparable output for the same input twice, e.g. BCrypt's salt)
  - `User createFirstAdmin(FirstAdminSpec)` (wave B2, NEW, D14 bootstrap) — **no scope, no actor parameter**: by definition there is no acting user yet. Refuses with `IllegalStateException` if an enabled admin already exists (own `hasEnabledAdmin()` check — see Gotchas) or the username is taken. Creates a user with `enabled=true`, `mustChangePassword=false` (self-chosen password), exactly one `Membership(spec.groupId(), Role.ADMIN)`. Records one `AuditAction.CREATED`/`AuditTargetType.USER` entry attributed to **the new admin's own id** (the only sensible actor — nobody else exists yet)
- `GroupService` (interface) → `DefaultGroupService(GroupRepositoryPort)` — both methods take the acting `VisibilityScope`
  - `Group create(GroupSpec, VisibilityScope acting)` — `!acting.canManageOrg()` → 403; a **root** group (`null` `parentGroupId`) only by `unbounded()`; a parent must be `acting.includesGroup(parent)` (403) before the existence check (404)
  - `List<Group> list(VisibilityScope acting)` — name-sorted; `unbounded()`→every group; `GROUPS`→groups `acting.includesGroup(id)`; any other scope→empty. **No `tree()` read model** — a manager UI wanting a nested view builds it client-side from the flat list's `parentGroupId` links
- Records: `UserSpec(username, displayName, email, rawPassword, memberships, enabled)` — only `rawPassword` non-blank is validated here, `User`'s own compact ctor validates the rest; `GroupSpec(name, parentGroupId)` — `name` non-blank, `parentGroupId` nullable (root); `FirstAdminSpec(username, displayName, email, rawPassword, GroupId groupId)` (wave B2, NEW) — `rawPassword` non-blank, `groupId` non-null (the bootstrap admin's one membership needs a home group); no `enabled`/`memberships` fields, `createFirstAdmin` fixes both

### `application.scope`
- `ScopeResolver` (interface) → `DefaultScopeResolver(GroupRepositoryPort, AssignmentRepositoryPort)` — turns a `User` into a `VisibilityScope`, and (wave B1) a `User` into an `Authority`
  - `VisibilityScope scopeFor(User)` — precedence: any **ADMIN** membership → `unbounded()`; else any **MANAGER** membership → `groups(union of each manager group's subtree)`; else (**PILOT**-only, **VIEWER**-only, or no membership) → `assignedAssets(assignmentRepo.assetsForPilot(user.id()))` (empty for an unassigned user). Subtree = self + descendants via `Group.parentGroupId`, walked BFS per manager root; a `visited` set both dedupes overlapping subtrees and breaks any malformed cycle in the stored tree. **`VIEWER` deliberately falls into the same branch as `PILOT`-only for now** (docs/plans/active/AUTH-ROLES-PLAN.md §3.2/§4 wave B1's "staging rule" — see `ScopeResolver#authorityFor`'s javadoc) — a `VIEWER` is meant to eventually get a group-wide *read*, but that reclassification is wave B6's job, gated on the API/wiring layer being ready to hand out a wider read scope safely; until then a bare `VIEWER` sees only what an unassigned pilot sees
  - `Authority authorityFor(User)` (wave B1, NEW) — `new Authority(scopeFor(user), RoleAuthority.capabilitiesOf(user.topRole()))` (empty capability set for no membership); pairs the existing visibility scope with the new authority axis without changing `scopeFor`'s own behavior at all — see `com.drones.vision.platform.Authority`/`Capability` (vision-platform) and `RoleAuthority` below
- `RoleAuthority` (wave B1, NEW, `application.scope`, final class + private ctor, not an interface — no second implementation exists or is expected) — `static Set<Capability> capabilitiesOf(Role)`, the frozen table from docs/plans/active/AUTH-ROLES-PLAN.md §3.3: `VIEWER`→`Set.of()`, `PILOT`→`{OPERATE_PAYLOAD, COMMAND_FLIGHT}`, `MANAGER`/`ADMIN`→all four `Capability` constants
- `AssignmentService` (interface) → `DefaultAssignmentService(AssignmentRepositoryPort, AssetService, AuditTrailPort)` (wave B2 widened from 2 to 3 args) — the pilot→asset roster
  - `void assign(UserId pilot, AssetId asset, AssignmentRole role, UserId actor, VisibilityScope granterScope)` (wave B2 added `role` and `actor` — B1 had shipped this 3-arg with a temporary hardcoded `AssignmentRole.PILOT` literal, now gone) — validates the asset exists (404) then `granterScope.canManage(asset.ownership())` or 403 (an authority check, not a visibility one — a PILOT may not grant/revoke even their own assignment). Idempotent; `unbounded()` may assign anything, `groups()` (MANAGER) within their own subtree. Records one `AuditAction.GRANTED`/`AuditTargetType.ASSIGNMENT` entry attributed to `actor` for a **new** link or a **seat change** (previous `AssignmentRole` differs from the new one) — a true no-op (identical re-assign) audits nothing; `targetId` is the composite string `"<pilotId>:<assetId>"` since a link has no typed id of its own
  - `void unassign(UserId pilot, AssetId asset, UserId actor, VisibilityScope granterScope)` (wave B2 added `actor`) — same grant check as `assign`; records one `AuditAction.REVOKED`/`AuditTargetType.ASSIGNMENT` entry (same composite `targetId` shape) attributed to `actor`, only if a link actually existed — unassigning a pilot who was never assigned that asset audits nothing
  - `Set<AssetId> assignmentsFor(UserId pilot)` — thin pass-through, not scope-checked (a pilot reading their own roster)
  - `Optional<AssignmentRole> roleFor(UserId pilot, AssetId asset)` (wave B2, NEW) — thin pass-through to the port's own `roleFor`; the IC-2 seat lookup exposed at the application layer
- `ActivityService` (interface) → `DefaultActivityService(AuditTrailPort)`
  - `List<AuditEntry> myActivity(UserId actor, int limit)` — thin pass-through over `AuditTrailPort.findByActor`; scoping is just "your own actor id" (a manager-sees-team view is deferred)

## Conventions
- Domain records validate in their compact constructor (`if (…) throw new IllegalArgumentException(…)`); the application layer uses `Objects.requireNonNull`.
- The acting user is a method parameter (`UserId actor`/`VisibilityScope acting`), never a constructor dependency. **Wave B2**: `actor` (who to attribute an audit entry to) and `acting`/`granterScope` (what the caller may see/manage) are passed as **two separate plain parameters**, never bundled into one type — see Gotchas.
- Constructor injection only, every collaborator `Objects.requireNonNull`-wrapped.
- Management gates repeat the same shape across `UserService`/`GroupService`/`AssignmentService`: "unbounded passes, else check `includesGroup`/`canManageOrg`" — a reviewer checking one understands the other two.
- `Role`'s ordinal ordering is load-bearing — reordering the enum constants silently changes what "top role" and "max grantable role" mean.
- **D15 audit idiom (wave B2)**: audit only on an actual state change (`setEnabled` only if the flag differs, `setMemberships`/`assign`/`unassign` only for links actually added/changed/removed), following the precedent set by `DefaultCameraPoseService#delete` in `vision-map`. The one deliberate exception: `setPassword`/`changePassword` always audit, since a hash-replacement has no cheap way to detect a no-op.

## Gotchas
- `VisibilityScope`/`AccessDeniedException`/the `AuditEntry` family live in `vision-platform`, not here — it is the authorization *value*, not this context's aggregate. Do not add a field to `VisibilityScope` here.
- `maxGrantableRole` lives on `DefaultUserService` (its only caller), not on `VisibilityScope` — granting a role is user-administration policy, not a fact about what a scope can see.
- `ScopeResolver`'s cycle guard is a real safety net: nothing in `GroupRepositoryPort`/`Group` prevents a cyclic group tree from being stored; `DefaultScopeResolverTest` proves it still terminates.
- `DefaultAssignmentService` reaches warehouse's `AssetService#details(AssetId)`, not its `AssetRepositoryPort` — a cross-context read goes through the published service, even though `details` assembles more than this call needs (devices, recent usages too). If a narrower read (e.g. `AssetService#ownershipOf(AssetId)`) is added for another caller, reconsider swapping this one onto it.
- `AuthService#authenticate`'s "never distinguish the failure reason" behavior is a security requirement — do not add a more specific exception/return type to help a caller show a friendlier error message. `changePassword` is different on purpose (own API-surface entry above) — it is self-service, the caller already proved who they are, so its `Optional.empty()` collapsing wrong-current-password/unknown-id/disabled is a simpler uniform contract, not an anti-leak one.
- `Role`'s frozen four-value order (`VIEWER, PILOT, MANAGER, ADMIN`) backs two independent axes that must not be conflated: ordinal order is *authority* (what `topRole()`/`maxGrantableRole` compare), while `RoleAuthority.capabilitiesOf` and `ScopeResolver` each look up a role by identity, not position — adding a fifth role later must update `RoleAuthority`'s switch explicitly (it does not fall through) or it silently grants zero capabilities.
- **`UserId actor` vs. `VisibilityScope acting`/`granterScope` (wave B2, D15)**: `VisibilityScope` (in `vision-platform`) carries **no identity at all** — only `Kind`, `groups`, `assignedAssets` — so once every gated mutation needed to write an `AuditEntry` (whose `actor`/`targetId` are both mandatory, non-null/non-blank), there was no identity already in scope to attribute the entry to. Considered and rejected: a bundled `ActingUser(UserId, VisibilityScope)` type — rejected because `AssetService` (warehouse) never bundles the two either (its write methods take a plain `UserId actor` with no scope; its read methods take a plain `VisibilityScope` with no actor), and introducing a new bundling type here would be unannounced scope-creep the plan's terse B2 line didn't ask for. If a *third* wave adds a *third* per-call parameter to these same methods, revisit this decision — three parameters repeated across five methods is the point a settings/context record starts paying for itself (java-clean-code §3).
- **`AuditTargetType.GROUP`, not `USER`, for membership grant/revoke** (wave B2): chosen by re-reading the two enum constants' own wave-B1 javadoc — `USER`'s is a closed list (created/enabled-disabled/password/authenticated) that doesn't mention memberships, `GROUP`'s reads as "an org-chart node users hold memberships in," the better semantic fit for "user X was granted/revoked membership in group Y."
- **`hasEnabledAdmin()` is duplicated, not shared, between `DefaultUserService#createFirstAdmin` and `DefaultAuthService#adminExists`** (wave B2) — both are a 3-line predicate over `UserRepositoryPort#findAll()`; sharing it would mean `DefaultUserService` taking a constructor dependency on `AuthService` (or vice versa) for one predicate, which this module's services deliberately never do (each depends only on ports, never on a sibling application service). If the check ever grows non-trivial, extract it to a small package-private helper both constructors can take instead of doing it as `AuthService`.
- **Incidental bug found and fixed, wave B2**: both `DefaultAssignmentServiceTest` and `DefaultScopeResolverTest`'s hand-fake `AssignmentRepositoryPort.unassign()` used to read `byPilot.getOrDefault(pilot, Map.of()).remove(asset)` — `Map.of()` is immutable, so unassigning a pilot with **zero** existing assignment links threw `UnsupportedOperationException`. Pre-existing in both files before B2; nothing exercised the path until B2 added `unassigningANonExistentLinkIsANoOpAndAuditsNothing`. Fixed in both (null-check the per-pilot map before removing) — not a production-code bug, but flagged here in case another test fake was copied from the same original.
