# adapter-discovery

ONVIF WS-Discovery, mDNS/DNS-SD, V4L2 local enumeration, and mediamtx push-registry polling scanners for finding candidate devices.

**Depends on:** vision-domain, org.jmdns:jmdns · **Used by:** vision-app
**Build/test:** `./mvnw -B -pl device-discovery/onvif-mdns-v4l2 test` — 64 tests, verified via a live run: 0 failures, 0 skipped.

## API surface
### `com.drones.vision.adapter.discovery.mdns`
- `final class MdnsScanner implements DeviceDiscoveryPort` — `method()` → `"mdns"`. Four constructors, all chaining to one canonical `MdnsScanner(InetAddress bindAddress, ScanBudget budget)`: `MdnsScanner()` (default interface + `ScanBudget.defaults()`), `MdnsScanner(InetAddress bindAddress)` test seam (default budget), `MdnsScanner(ScanBudget budget)` config seam (default interface), `MdnsScanner(InetAddress bindAddress, ScanBudget budget)` full seam. `scan(Duration timeout): List<DiscoveredDevice>` — browses `_rtsp._tcp.local.` and `_http._tcp.local.` concurrently (one virtual thread each).
  - `_rtsp` hits → category `"ip-camera"`, `suggestedStream` protocol `"rtsp"`, URI `rtsp://host:port/`.
  - `_http` hits hinting ESP32 (name/host matches regex `esp32|espressif|esp-cam`, case-insensitive) → category `"esp32-cam"`, `suggestedStream` protocol `"mjpeg"`, `suggestedStream`'s URI is now `http://host:81/stream` — ESP32-CAM's actual conventional MJPEG path — not the advertised `_http._tcp` port (**SOURCE-ONBOARDING-2 U9, fixed** — see Gotchas below); `address()` still carries the advertised port (the camera's plain control page); `details` is empty (no note needed — the URI itself is now correct, not merely explained).
  - Other `_http` hits → returned with `suggestedCategory`/`suggestedStream` both `null` (still surfaced for manual registration).
  - package-private pure mapping methods (unit-testable without jmdns): `static DiscoveredDevice mapRtspHit(String name, String host, int port)`, `static DiscoveredDevice mapHttpHit(String name, String host, int port)`.
- `record ScanBudget(Duration joinGrace, Duration safetyMargin, Duration minListWindow)` (docs/plans/active/LAYERING-REFACTOR-PLAN.md §1.3/§2.2, wave E4) — the timeout-budget cushions `MdnsScanner.listWindowMillis` carves out of the requested timeout; framework-free, compact-ctor-validated (all three non-null, non-negative), `static defaults()` = `150ms`/`50ms`/`50ms` — **byte-identical to the `JOIN_GRACE_MILLIS`/`SAFETY_MARGIN_MILLIS`/`MIN_LIST_WINDOW_MILLIS` constants it replaces**. Package-private `joinGraceMillis()`/`safetyMarginMillis()`/`minListWindowMillis()` accessors keep `MdnsScanner`'s arithmetic terse. Backs the future `vision.discovery.mdns.*` property keys (`join-grace`, `safety-margin`, `min-list-window`) — binding them into an instance of this record and passing it to the `ScanBudget`-taking constructor is `vision-app`'s job in a later wave, not done here.
### `com.drones.vision.adapter.discovery.onvif`
- `final class OnvifWsDiscoveryScanner implements DeviceDiscoveryPort` — `method()` → `"onvif"`. `OnvifWsDiscoveryScanner()` (multicast `239.255.255.250:3702`), `OnvifWsDiscoveryScanner(InetSocketAddress probeTarget)` test seam. `scan(Duration timeout)` runs two phases against one shared budget: (1) sends one WS-Discovery SOAP `Probe` UDP datagram and collects `ProbeMatch` replies for `PROBE_COLLECTION_SHARE` (50%) of `timeout`, hand-rolled regex/string XML extraction (no SOAP/XML stack — deliberate KISS); (2) every candidate found is then run through `OnvifDeviceClient`'s `GetCapabilities`→`GetProfiles`→`GetStreamUri` chain **concurrently** (one virtual thread per candidate, mirroring `DefaultDiscoveryService`'s own fan-out/bounded-wait pattern), bounded by the *same overall* `scan(Duration)` deadline — not phase (1)'s window plus a fresh budget on top. Category is always `"ip-camera"`.
  - **Success**: `suggestedStream = ("rtsp", <uri>, {})`; `details` unchanged from the probe phase.
  - **Auth required** (device answers HTTP 401 or a SOAP auth fault at any step of the chain): `suggestedStream` stays `null`, `details["note"] = "credentials required — stream URL cannot be suggested"` — never a guessed URL.
  - **Anything else** (timeout, connection refused, malformed/incomplete response, no Media capability, no profiles): `suggestedStream` stays `null`, no note — identical to this scanner's pre-Z4 behavior. Never throws, never fails the scan.
  - package-private `static Optional<DiscoveredDevice> parseProbeMatch(String xml)` — pure parser, unit-testable on canned XML; never throws, returns empty on malformed/unusable input.
  - The multicast address, receive-buffer size and SOAP boilerplate are protocol/spec constants (docs/plans/active/LAYERING-REFACTOR-PLAN.md §1.3's explicit out-of-scope list) — deliberately **not** externalized; the only test-facing knob is the existing `probeTarget` constructor seam. `PROBE_COLLECTION_SHARE` (the 50/50 probe-vs-follow-up split) is the same kind of out-of-scope constant, not yet a `vision.discovery.onvif.*` property.
- `final class OnvifDeviceClient` (package-private) — one collaborator per `OnvifWsDiscoveryScanner` instance, not a `*Port` (single implementation, single caller — java-clean-code §1). Runs the anonymous/unauthenticated ONVIF Profile-S media chain over `java.net.http.HttpClient` (JDK stdlib, no new dependency): `GetCapabilities` (`Category=Media`) against the ProbeMatch `XAddrs` → scoped extraction of the **Media** capability's `XAddr` (not the first `XAddr` in the document, which is usually Device's own address) → `GetProfiles` against that address → first profile's `token` attribute → `GetStreamUri` (`StreamSetup` = RTP-Unicast/RTSP) for that token → the response's `MediaUri/Uri`. `GetServices` is **not** implemented as a fallback to `GetCapabilities`.
  - `StreamProbeOutcome probeStream(URI deviceServiceAddress, Duration budget)` — never throws; `budget` bounds the **whole chain**, not each call: the deadline is computed once and each of the (up to three) sequential POSTs gets only its remaining share, so a slow first call cannot also claim a full budget's worth of time on the second and third.
  - package-private static parsers, each unit-testable on canned XML without a socket: `parseMediaXAddr(String)`, `parseFirstProfileToken(String)`, `parseStreamUri(String)`, `isAuthRefused(int statusCode, String body)`.
  - No credentials, no WS-Security header, ever — every request is anonymous by construction.
- `sealed interface StreamProbeOutcome` (package-private) — `Found(URI uri)` / `AuthRequired()` / `Unavailable()`; a plain algebraic result type, not a driven port.
### `com.drones.vision.adapter.discovery.v4l2`
- `final class V4l2Scanner implements DeviceDiscoveryPort` — `method()` → `"v4l2"`. `V4l2Scanner()` (real `/dev`, `/sys`), `V4l2Scanner(Path devBase, Path sysBase)` — both a test seam and, per docs/plans/active/LAYERING-REFACTOR-PLAN.md §1.3 rule 4 (≤2 tunables ⇒ plain constructor params, no settings record needed), **already** the config-extraction seam for the future `vision.discovery.v4l2.dev-base`/`vision.discovery.v4l2.sys-base` properties — `vision-app` wiring in a later wave passes the configured `Path`s here directly; no change needed in this module. `scan(Duration)` lists `videoN` entries directly under `devBase`; friendly name read from `<sysBase>/class/video4linux/videoN/name` if readable, else the node name. Every candidate → category `"usb-camera"`, `suggestedStream` protocol `"v4l2"`, URI **always** `file:/dev/videoN` — the real path, regardless of `devBase` (that parameter only redirects *where the scanner looks*, e.g. in tests). **(SOURCE-ONBOARDING-2 U8, new)** `@Override public SourceStatus lastStatus()` — a `volatile SourceStatus`, defaulting to `OK`. All three local-mechanism scanners override it since 2026-09-05 (`MdnsScanner`/`OnvifWsDiscoveryScanner` gained the same volatile-field idiom — see the reversed U8 Gotchas entry below for why leaving them on the port default 400'd `/api/discovery/status`).
### `com.drones.vision.adapter.discovery.mediamtx`
docs/plans/active/ZERO-CONFIG-ONBOARDING-CONTEXT.md §3 P3, §11 "Z3 amendment (2026-08-31) — poll, not hook": mediamtx's official image is scratch-based (no shell), so a `runOnAvailable` hook cannot run there — this scanner instead **polls** the same Control API `adapter-publish-hls`'s `MediamtxControlApi` already reads, on the ordinary `DeviceDiscoveryPort.scan(Duration)` cadence `DiscoveryInboxRunner` already drives for every other scanner. No new REST endpoint, no hook.
- `record MediamtxScannerSettings(URI apiBase, URI rtspBase, String pathPrefix)` — the module's one collaborator record for this scanner (java-clean-code §3: >2 tunables/no sane single-constructor shape ⇒ settings record, not N-arg overloads). Compact constructor: `Objects.requireNonNull` on `apiBase`/`rtspBase`, `IllegalArgumentException` on a blank `pathPrefix`. `apiBase`/`rtspBase` are deliberately **not** module-local properties — `vision-app` wiring sources both from the existing `VisionPublishProperties.Mediamtx.apiBase()`/`.rtspBase()` (the same values `adapter-publish-hls`/MEDIA-SOT already use to reach this exact mediamtx instance), so the docker-compose-vs-localhost distinction is solved once, not duplicated as a parallel `vision.discovery.mediamtx.api-url` property. `pathPrefix` (default `"ingest/"`) is this module's own concern — it names the push-registry convention, not a mediamtx connection detail.
- `final class MediamtxPathScanner implements DeviceDiscoveryPort` — `method()` → `"mediamtx"`. One public constructor, `MediamtxPathScanner(MediamtxScannerSettings settings)`; builds and caches its `HttpClient` (`Redirect.NEVER`) and the precomputed `{apiBase}/v3/paths/list` URI once, at construction. `scan(Duration timeout)`:
  1. Guards `timeout.isZero() || timeout.isNegative()` → returns `List.of()` immediately (mirrors `OnvifDeviceClient.postWithinBudget`'s guard) — never issues a request against a non-positive budget, and leaves `lastStatus()` at whatever it last genuinely observed (see below).
  2. Issues exactly **one** bounded `HttpRequest` (`GET {apiBase}/v3/paths/list`, `.timeout(timeout)`) — `HttpRequest.Builder.timeout` bounds connection establishment through full response body in one call (the same JDK idiom `OnvifDeviceClient` already relies on), so this satisfies "respect the timeout" with no separate connect-timeout bookkeeping.
  3. A non-200 response, an `IOException` (API down, connection refused, timed out), or a parse failure from `MediamtxPathListParser` are each caught, turned into `List.of()` after a `System.Logger.WARNING` log, and set `lastStatus()` to `SourceStatus.UNREACHABLE` — though the parse-failure branch is dead code against that parser's current tolerant implementation (see Gotchas). An `InterruptedException` is caught separately: no WARNING log, `Thread.currentThread().interrupt()` to re-assert the flag, `List.of()` returned, and `lastStatus()` left **untouched** (the thread was told to stop, not told mediamtx is down) — **scan() never throws differently than "nothing found" for any of these**, matching the task contract and this module's existing "empty list on recoverable miss" idiom (unlike `OnvifWsDiscoveryScanner`/`MdnsScanner`, there is no separate "genuine setup failure" phase to distinguish: the one HTTP call **is** the whole scan).
  4. Every parsed `PathItem` that is **not** `ready`, or whose `name` does not start with `settings.pathPrefix()`, is silently dropped (javadoc explains why: everything outside the prefix is vision's own MEDIA-SOT publish output — `MediamtxStreamPublisher`'s republished HLS/WHEP paths — and reporting those back as "found devices" would have vision discover its own video output as if it were a new camera).
  5. Each surviving item becomes one `DiscoveredDevice(method="mediamtx", name=<path name with the prefix stripped>, address=<rtsp uri>, suggestedCategory=null, suggestedStream=("rtsp", rtsp://<rtspBase host:port>/<full path name>, {}), details={"path": <full name>, "sourceType": <mediamtx's own source.type field, or "" if absent>, "readers": <reader count as a string>})` — `suggestedCategory` is deliberately `null` (unlike onvif/mdns/v4l2, a pushed RTSP path carries no protocol-level hint about what kind of device it is; a human names the category on registration).
  6. On any successful 200 response (empty or not), `lastStatus()` is set to `SourceStatus.OK` right before returning — a reachable-but-empty response is `OK`, not `UNREACHABLE` (ASSET-FLOWS-PLAN §2, A3; see Gotchas).
- `SourceStatus lastStatus()` (override, ASSET-FLOWS-PLAN §2, A3) — a `volatile SourceStatus` field, defaulting to `OK` before any scan has run, updated only by step 3 (→ `UNREACHABLE`) and step 6 (→ `OK`) of `scan` above; a zero/negative-timeout guard call or an interrupted call leaves the previously-observed status untouched rather than resetting to `OK`. This is the fix for the module's former "mediamtx down reads the same as mediamtx empty" gap — see the corrected Gotchas entry below.
- `final class MediamtxPathListParser` (package-private, no instances) — hand-rolled minimal JSON parsing, consistent with this module's existing "no JSON/XML library, JDK stdlib + regex" style (`OnvifDeviceClient`'s parsers, `MdnsScanner`'s mapping methods); confirmed via `pom.xml` that no JSON dependency exists in this module, and adding one for a single endpoint shape would be disproportionate. `record PathItem(String name, boolean ready, String sourceType, int readerCount)`; `static List<PathItem> parseItems(String body)` splits the top-level `items` array into individual object substrings via a **depth- and string-literal-aware** bracket/brace matcher (`extractBracketedValue`, `splitTopLevelObjects`) before running per-field regexes (`NAME_FIELD`, `READY_FIELD`, `SOURCE_TYPE_FIELD` — scoped inside the nested `source` object so a same-named sibling field can't false-match) on each substring — this avoids the desync a single whole-body regex would suffer once a path's own JSON contains nested braces (e.g. `source: {...}`). Modeled on `adapter-publish-hls`'s `MediamtxControlApi` regex style for the same API (read for precedent only — cross-adapter imports are ArchUnit-forbidden, so nothing is shared at the code level). Malformed JSON (missing `items` array, unparseable body) throws from `parseItems`, which `MediamtxPathScanner.scan()` catches into the same empty-list-plus-WARNING path as a network failure.

## Conventions
- Plain classes, no Spring — instantiated directly by `vision-app`'s wiring config.
- Every `scan(Duration)` budgets against `deadlineNanos = System.nanoTime() + timeout` and returns an empty list rather than throwing on "nothing found" or a filesystem/parse hiccup; genuine failures (socket bind, jmdns setup) still propagate per `DeviceDiscoveryPort`'s contract.
- `System.Logger` used for best-effort diagnostic logging in `OnvifWsDiscoveryScanner`/`V4l2Scanner` (`DEBUG` level only — never surfaces as a scan failure).
- Config-extraction (docs/plans/active/LAYERING-REFACTOR-PLAN.md §1.3): the module's tunables are either a small framework-free settings record (`mdns.ScanBudget`, 3 fields > the rule's 2-tunable threshold) or plain constructor params (`V4l2Scanner`'s `devBase`/`sysBase`, ≤2 tunables) — never a bare literal baked into a class. No `Vision*Properties` type is imported here; that stays `vision-app`-only.

## Gotchas
- **(SOURCE-ONBOARDING-2 U8, REVERSED 2026-09-05) Every scanner in this module now overrides
  `lastStatus()` — the U8-era decision to leave `MdnsScanner`/`OnvifWsDiscoveryScanner` on the port
  default was itself a live defect.** The original reasoning ("a mechanism whose genuine setup
  failure is thrown has nothing ambiguous to report") held only while the port default was `OK`;
  once B1/U8 flipped the default to `NEVER_SCANNED`, a scanner without an override answered
  `NEVER_SCANNED` *forever, even after being scanned* — and `DefaultDiscoveryService#health()`
  paired that with a real `lastScanAt`, a combination `SourceHealth`'s compact constructor rejects,
  turning the whole `/api/discovery/status` endpoint into a permanent 400 after the first sweep
  (found live). Both scanners now track a `volatile SourceStatus` (`OK` on a successful scan,
  `UNREACHABLE` when the genuine-setup-failure throw fires), same idiom as `V4l2Scanner`/
  `MediamtxPathScanner`; `health()` also degrades a contract-breaking port to the never-scanned
  shape rather than throwing, as a backstop. Rule of thumb: **every `DeviceDiscoveryPort`
  implementation that scans must override `lastStatus()`** — the interface default exists only for
  ports that have never been asked.
- **`V4l2Scanner.lastStatus()` distinguishes "devBase genuinely cannot be listed" from "devBase simply
  does not exist".** The latter (`NoSuchFileException`) is the normal, expected state for any non-Linux
  host or a container with no `/dev` passthrough — the class's own javadoc has always called this "not
  Linux, nothing to enumerate", never a failure — so it deliberately leaves `lastStatus()` untouched
  (stays at whatever it last genuinely was, default `OK`) rather than flagging every such host as
  `UNREACHABLE`. Only a `devBase` that exists but genuinely cannot be listed (permission denied, not a
  directory — any other `IOException`/`RuntimeException`) sets `UNREACHABLE`. Getting this distinction
  backwards would violate the "never invent 'your link is broken'" principle the diagnostic exists to
  serve (SOURCE-ONBOARDING-2's own D4) — a dev laptop with no V4L2 subsystem at all is not "down".
  Self-heals on the very next successful scan, exactly like `MediamtxPathScanner`'s own idiom.
- **`MdnsScanner` timeout budget math.** `DiscoveryService` (caller, in `vision-application`) hard-bounds its wait at `timeout + 200ms` grace. `JmDNS.create()` setup and `JmDNS.close()` teardown both cost real wall-clock time on top of the two concurrent `list()` calls: `listWindowMillis()` computes the `list()` window as `timeoutMillis - setupElapsedMillis - budget.joinGraceMillis()(150) - budget.safetyMarginMillis()(50)`, clamped to a floor `budget.minListWindowMillis()`=50 — that cushion is carved *out of* the timeout, not added on top (the pre-fix bug). These three numbers now live in `ScanBudget` (default values unchanged, wave E4) rather than `private static final long` constants — see `MdnsScannerLoopbackTest.scanReturnsWithinTimeoutPlusCallerGrace` for the regression test that pins the arithmetic. **Do not change `ScanBudget.defaults()`** without re-verifying that test and `DefaultDiscoveryService`'s coupled 200ms grace (vision-application) — retuning is a deliberate, separately reviewed decision, not incidental to a refactor.
- **`JmDNS.close()` cost, and `closeWithinBudget`.** jmdns 3.5.9 hard-codes its internal cancellation state machine to allow itself up to `DNSConstants.CLOSE_TIMEOUT` (5s), entirely unaware of this scanner's own timeout. `closeWithinBudget()` starts `close()` on its own virtual thread and joins it only up to the scan's remaining deadline (`remainingMillis`); if the budget runs out first, `scan()` returns anyway and the close finishes (releasing the multicast socket) in the background — an accepted "leaked but harmless daemon-ish virtual thread" tradeoff, the same one `DiscoveryService` already accepts for a hanging adapter.
- **`Onvif` deadline is enforced per receive**, not once at the top of the loop: `collectResponses` sets `socket.setSoTimeout` to the exact remaining budget before *every* `receive()` call, so a scan fielding many small/garbage responses still terminates on time.
- All three scanners key `DiscoveredDevice` identity differently: mdns/v4l2 return a fresh list per call with no dedup; onvif dedupes by `address()` within one scan (`LinkedHashMap<URI, DiscoveredDevice>`, `putIfAbsent`) since multiple `ProbeMatch` datagrams can arrive for the same device. The `GetStreamUri` follow-up chain runs *after* this dedupe, on the already-deduplicated set, and never changes `address()` — so the dedupe key is unaffected by wave Z4.
- **`OnvifWsDiscoveryScanner`'s probe/follow-up split is a hard two-phase budget, not "timeout for probing, then however long the chain takes".** `collectResponses` (phase 1) always spends its *entire* allotted window even after receiving a reply (it keeps listening for stragglers until its own sub-deadline) — mirroring the pre-Z4 behavior — so shrinking phase 1 to `PROBE_COLLECTION_SHARE` (50%) of `timeout`, rather than the full `timeout`, is what actually reserves phase 2's budget. Do not "simplify" phase 1 back to using the whole `timeout` without also reworking how phase 2 gets its time.
- **`OnvifDeviceClient`'s regex helpers deliberately avoid a substring trap.** A naive `<...Uri>` pattern (the style `XADDRS_PATTERN`/`SCOPES_PATTERN` use in the Probe parser) would false-match `<MediaUri>` as if it were `<Uri>` when the tag carries no namespace prefix, because the loose `[^:>]*:?` prefix group can consume mid-local-name. `OnvifDeviceClient.elementPattern(String)` instead uses `(?:[A-Za-z0-9]+:)?` — an all-or-nothing prefix group that can only end on a literal colon — so it cannot partially match `MediaUri` as `Uri`, nor `Media2` as `Media`. `parseMediaXAddr` additionally scopes its `XAddr` search to inside the `Media` capability block specifically, not the first `XAddr` in the whole `GetCapabilitiesResponse` (which is normally Device's own address, listed first) — see `OnvifDeviceClientTest.parseMediaXAddrPicksTheMediaCapabilityAddressNotDevice`/`parseStreamUriExtractsTheInnerUriNotTheMediaUriWrapper` for the regression coverage.
- **`isAuthRefused` requires two signals together for the fault-body path** (a SOAP `Fault` element *and* an auth-hinting word in the body — `notauthorized`/`unauthorized`/`authentication`, case-insensitive) so an unrelated fault (e.g. `ActionNotSupported`) is never misreported as "needs credentials". A bare HTTP 401 is sufficient on its own regardless of body content.
- **Per-device follow-up timeout is a real `HttpClient` request timeout**, not a best-effort/advisory one: `OnvifDeviceClient.postWithinBudget` sets `HttpRequest.Builder.timeout(remaining)` per call, which JDK's `HttpClient` enforces by throwing `HttpTimeoutException` at that bound even against a server that accepted the connection and then never writes a response — proven by `OnvifDeviceClientTest.probeStreamReturnsUnavailableWhenTheDeviceIsSlowerThanItsBudget` (200ms budget vs. a 2s-sleeping handler) and `OnvifWsDiscoveryScannerTest.scanReturnsWithinTimeoutPlusCallerGraceEvenWhenTheDeviceNeverResponds` (full-scan regression, mirrors `MdnsScannerLoopbackTest`'s pattern).
- **FIXED (ASSET-FLOWS-PLAN §2, A3) — `MediamtxPathScanner` used to never distinguish "mediamtx is down" from "mediamtx has no ingest paths right now"**: both surfaced as `List.of()`, with a `WARNING` log the only signal, in the former case only. `lastStatus()` (see `com.drones.vision.adapter.discovery.mediamtx` above) now answers this directly — `SourceStatus.UNREACHABLE` vs `SourceStatus.OK` — read by `vision-warehouse`'s `DiscoveryService#health()` and surfaced through `vision-api`'s `GET /api/discovery/inbox` as `sources: [{id:"mediamtx", status}]`, independent of `scan()`'s own return value. The `WARNING` log itself is unchanged: there is still no warn-once idiom anywhere in this module (or `drone-link`) to reuse, so it still logs on **every** failed scan, not just the first — accepted rather than invented here, since `DiscoveryInboxRunner`'s sweep interval (default 30s) already keeps the log rate low, and `lastStatus()` (not the log) is now the honest machine-readable signal.
- **`MediamtxPathListParser.parseItems`'s `RuntimeException` catch in `scan()` is currently dead code** — the parser is deliberately tolerant of a body with no `items` array (its own javadoc: "empty ... if ... has no items array at all"), so a 200 response with a malformed/non-JSON body still returns `List.of()` from the parser itself rather than throwing, and `scan()` reports `SourceStatus.OK` for it (mediamtx *did* answer 200) — proven by `MediamtxPathScannerTest.malformedJsonReturnsEmptyListRatherThanThrowing`. The `catch (RuntimeException)` block around `parseItems` (and its `UNREACHABLE` stamp) is kept as a defensive net against a future parser change, not because today's parser can trigger it.
- **(SOURCE-ONBOARDING-2 U9, fixed) `MdnsScanner`'s ESP32-CAM candidate used to merely *note* its real
  MJPEG path rather than apply it.** Before this wave, `mapHttpHit`'s ESP32 branch set `suggestedStream`'s
  URI to the advertised `_http._tcp` port (the camera's plain control page) and stuffed the actual
  `:81/stream` convention into `details["note"]` for a human to read before registering — a candidate
  accepted as-is (or auto-added by a future zero-config flow with nobody reading the note) would fail to
  stream. `mapHttpHit` now builds the suggested stream URI directly at `http://host:81/stream`
  (`ESP32_CAM_MJPEG_PORT`/`ESP32_CAM_MJPEG_PATH` constants); `address()` is unchanged (still the
  advertised port, for identity/dedup purposes), and `details` is empty for this case now that the URI
  itself is correct rather than merely explained.
- **The `ingest/` prefix match is a literal `String.startsWith`, not a mediamtx path-name/regex concept** — mediamtx grants every path under its `all_others` catch-all identically (see `mediamtx.yml`'s comment block); the prefix is purely this scanner's own filter for "which of mediamtx's paths came from a pushed device vs. vision's own MEDIA-SOT republish output". Renaming the convention means changing `vision.discovery.mediamtx.path-prefix` (and re-pointing whatever pushes to `ingest/…` today), not touching mediamtx's config.
