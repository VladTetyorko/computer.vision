# cv-service

Python gRPC CV inference & training service — real Ultralytics YOLO inference behind `Inference.DetectStream`, with an echo fallback when the model backend is unavailable. `DetectStream` runs each stream's frame receipt and inference concurrently (V-d), bounded by a process-wide inference gate.

**Depends on:** grpcio, grpcio-tools, protobuf (Python); `cv` extra: ultralytics (pulls in torch, opencv-python transitively); shared contract `proto/vision/v1/cv.proto` · **Used by:** adapter-cv-grpc (Phase 2, not wired yet)
**Build/test:** `python -m cv_service.server` (run). `scripts/test.sh` or `python -m pytest` (test; needs `pip install -e '.[dev]'` at minimum, `-e '.[cv,dev]'` for the mock+real-model suites — see Status). Codegen: `scripts/gen_proto.sh` (regenerates `cv_service/gen/`, not committed).

## API surface
### `cv_service/concurrency.py`
Pure-stdlib (`threading` only — no `cv_pb2`, no cv2/numpy/ultralytics), protobuf-agnostic by the same convention as `inference.py`. Two independent primitives, wired to `FrameRequest`/`DetectStream` by `server.py`:
- `class LatestOnlyMailbox[T]` — single-slot, latest-wins handoff between one producer thread and one consumer thread. `put(value)` never blocks/queues: if a value is already waiting unconsumed, it's silently replaced (`.dropped` counts replacements). `get() -> T | None` blocks until a value is available or the mailbox is `close()`d and drained (`None` sentinel — don't use this for a value where `None` is itself meaningful; `FrameRequest`s never are). `close()` unblocks every pending/future `get()` with `None` once any already-pending value has been delivered once.
- `class InferenceGate(max_concurrent: int)` — a plain `threading.Semaphore(max_concurrent)` wrapped as a context manager (`gate.acquire()`), not a thread pool: it gates how many *existing* stream-consumer threads may be inside `detect()` at once, it never creates threads of its own. Raises `ValueError` if `max_concurrent < 1`.
- `DEFAULT_MAX_CONCURRENT_INFERENCES: int` — resolved once at import time from `CV_MAX_CONCURRENT_INFERENCES` (same forgiving-parse idiom as `CV_IMGSZ`: unset/non-numeric/non-positive all fall back), default `min(2, cpu_count // 2)` floored at 1 — see `_default_max_concurrent_inferences`'s own docstring and "V-d: cross-stream concurrency bound" below for the reasoning.
- `process_gate() -> InferenceGate` — the shared, process-wide gate every `InferenceServicer` uses by default; tests construct their own differently-sized `InferenceGate` and inject it instead (`InferenceServicer(detector=..., inference_gate=...)`).

### `cv_service/inference.py`
Independent of the generated protobuf stubs (importable/testable without codegen) — only `cv2`/`numpy`/optionally `ultralytics`.
- `ENCODING_JPEG`, `ENCODING_BGR24: str` — match `ImageEncoding` enum names one-for-one (get via `cv_pb2.ImageEncoding.Name(request.encoding)`).
- `DEFAULT_MODEL = "yolo11n.pt"`, `DEFAULT_CONFIDENCE = 0.25`.
- `class ModelUnavailableError(RuntimeError)` — raised by `YoloDetector.__init__` when `ultralytics` isn't installed, or the model/weights can't be loaded.
- `@dataclass(frozen=True) class Detection(label: str, confidence: float, x: float, y: float, width: float, height: float)` — mirrors proto `Detection`/`BoundingBox`: `x`/`y` top-left corner, `width`/`height` extend right/down, all normalized to `[0, 1]`.
- `def decode_frame(width: int, height: int, encoding: str, data: bytes) -> np.ndarray` — JPEG via `cv2.imdecode`; BGR24 via `np.frombuffer(...).reshape((height, width, 3))`. Raises `ValueError` on bad length/bytes/encoding.
- `def map_detections(result: Any, frame_width: int, frame_height: int) -> list[Detection]` — maps one Ultralytics `Results` (duck-typed: `.boxes.xyxy`/`.conf`/`.cls`, `.names`) to normalized `Detection`s (Ultralytics already rescales `xyxy` to the original frame, so no letterbox un-padding needed); clamps to `[0, 1]`; `[]` if `boxes` is `None`/empty.
- `DEFAULT_IMGSZ = 416` — inference input size (pixels, square), overridable via `CV_IMGSZ`.
- `class YoloDetector(model_name: str | None = None, *, model: Any = None)` — loads `ultralytics.YOLO(model_name or $CV_MODEL or DEFAULT_MODEL)` once; `model=` injects a test double, bypassing `ultralytics` entirely. `.model_name -> str`. `.imgsz -> int` — parsed from `$CV_IMGSZ` (default `DEFAULT_IMGSZ`; unset/non-numeric/non-positive all fall back to the default, never raise). After the model is loaded (real or injected), construction runs one warmup `predict()` on a black `np.zeros((imgsz, imgsz, 3), uint8)` frame; a warmup failure raises `ModelUnavailableError` same as a load failure. `.detect(*, width, height, encoding, data, confidence_threshold: float | None = None) -> tuple[list[Detection], int]` — decode → `model.predict(frame, conf=conf, imgsz=self.imgsz, verbose=False)` → map; returns `(detections, inference_millis)`. Falsy/`None` `confidence_threshold` uses `DEFAULT_CONFIDENCE`.

### `cv_service/server.py`
- `class InferenceServicer(cv_pb2_grpc.InferenceServicer)` — `__init__(detector: YoloDetector | None = None, *, inference_gate: InferenceGate | None = None)`: uses the given detector, or calls `_build_default_detector()` (constructs the default `YoloDetector`, catching `ImportError`/`ModelUnavailableError` and logging one clear warning); `inference_gate` defaults to `concurrency.process_gate()` (shared process-wide) — tests inject a smaller/differently-sized one. `DetectStream(request_iterator, context)`: runs real inference per frame when a detector is loaded, mapping `Detection`s to `cv_pb2.Detection`/`BoundingBox`; both "no detector" and any per-frame exception degrade to the original Phase 0 echo response (stream_id/sequence/timestamp_millis/model_id/model_version copied, empty detections, `inference_millis=0`) — a bad frame or missing model never kills the bidi stream. An unknown `request.model_id` (≠ the loaded model's name) logs one INFO per distinct id seen, then serves the default — model registry is Phase 3. **When a detector is loaded, frame receipt and inference run concurrently within the stream, and every `detect()` call is gated across streams** — see "V-d: parallel per-stream inference" below for the full design; the echo-only path (no detector) is unchanged, plain synchronous `for request in request_iterator: yield echo(request)`.
- `class _StreamReader` — package-private; one instance per active `DetectStream` call with a detector loaded. Spawns a daemon thread (`cv-detectstream-reader`) that drains the *rest* of `request_iterator` (everything after the first frame — see below) into a `LatestOnlyMailbox`. `.next()` blocks for the next (latest) frame, `None` at end of stream, re-raises whatever the iterator itself raised. `.stop()` closes the mailbox (best-effort — see Gotchas for what it can't do).
- `class TrainingServicer(cv_pb2_grpc.TrainingServicer)` — unchanged, all three RPCs `UNIMPLEMENTED` (Phase 3).
- `def serve(port: int = DEFAULT_PORT) -> grpc.Server`, `def main() -> None` — unchanged.

## Conventions
- Generated stubs live under `cv_service/gen/` and are **never committed** — run `scripts/gen_proto.sh` after cloning and whenever `proto/vision/v1/cv.proto` changes.
- `inference.py` never imports `cv_pb2` — `server.py` is the sole translation point between wire types (`cv_pb2.FrameRequest`, `encoding` as an enum int) and `inference.py`'s plain types (`width`/`height`/`encoding: str`/`data: bytes`, `Detection`). This keeps `inference.py` unit-testable without running codegen first.
- `cv_service/inference.py` imports `cv2`/`numpy` at module scope, so importing it at all requires the `cv` extra. `server.py` only imports it lazily inside `_build_default_detector()` — `cv_service.server`, and hence `python -m cv_service.server`, stays importable/runnable without the `cv` extra (echo mode).
- Tests live in `tests/` (not under `cv_service/`), plain `pytest`, fixtures in `tests/conftest.py` (a tiny synthetic frame, no fixture image files on disk).

## V-d: parallel per-stream inference (`docs/MVP2-PLAN.md` §V-d)

**Problem this closes:** pre-V-d, `DetectStream` was `for request in request_iterator: infer(request); yield response` — receiving the next frame off the network only started *after* the current frame's inference finished and its response had been handed back to gRPC, so inference and network transfer never overlapped within one stream; and every stream's `detect()` calls ran fully unbounded/uncoordinated against every other stream's, with nothing protecting the CPU as more streams were added.

**Design chosen — a background reader thread + a 1-slot latest-wins mailbox, per stream, plus a small process-wide semaphore across streams:**

- **Within a stream** (`_StreamReader` + `LatestOnlyMailbox`, both above): `DetectStream` claims the stream's **first** frame directly and synchronously (there's nothing to overlap with before the first frame's own inference even begins), *then* spawns a `_StreamReader` background thread to drain the rest of `request_iterator` into a `LatestOnlyMailbox` while the consumer (the thread gRPC itself drives as the `DetectStream` generator) is inside `detect()`. If a second frame arrives in the mailbox before the consumer has taken the first, it silently replaces it (`.dropped` counts this) — **never a growing backlog**, always the newest available frame. **Response ordering per stream is still always increasing/in-order** (frames are only ever consumed and yielded one at a time, in the order the reader thread received them, minus whichever got overwritten) — this was a deliberate simplicity choice, not a requirement: `adapter-cv-grpc/MODULE.md`'s "Correlation design" section was read first and confirms the Java side matches responses back to pending futures **by their own `sequence` field**, independently per response (`ConcurrentHashMap<Long, CompletableFuture<DetectionResult>>` keyed by sequence, proven under out-of-order server replies by its own `detectCorrelatesInterleavedResponsesBySequence` test) — so mild reordering would have been tolerated too, but keeping this side in-order is simpler to reason about and costs nothing.
  - **Why the first frame is claimed synchronously rather than also going through the reader thread:** confirmed empirically (not assumed) while building this — spawning the reader thread immediately and letting *it* claim frame 0 too creates a real, reproducible race between the reader thread racing ahead through an already-available burst of frames and the consumer's very first `mailbox.get()` call; with a zero-latency in-memory iterator (exactly what this module's own tests use, and plausible for a very bursty real sender too) the reader can legitimately win that race and have already overwritten frame 0 with a later frame before the consumer ever asks for anything. Claiming frame 0 directly removes the possibility entirely, and matches reality: there's no earlier frame to be overlapping the first one's *reception* with anyway.
  - **Why drops are expected to be rare in production, not just "possible in theory":** the mailbox only drops when a *second* new frame arrives while a *first* one is still unconsumed — i.e. only when the sender is at least two frames ahead of what's been inferred+responded-to. `adapter-cv-grpc` (the only real caller) allows at most a small, bounded number of frames in flight per stream at once (see its own MODULE.md "Failure semantics"/correlation design) rather than sending unboundedly far ahead of received responses, so in practice the reader is rarely more than one frame ahead of the consumer. This module's own tests deliberately *do* trigger drops (with instantaneous/fast fake iterators and a gated fake detector) specifically because proving the drop behavior needs to force that "sender got ahead" condition on demand — that's a test-engineering choice, not evidence it's common in production.
- **Across streams** (`InferenceGate`, in `concurrency.py`): every `detect()` call, regardless of which stream it's for, acquires the same process-wide `InferenceGate` (default size `min(2, cpu_count // 2)`, floored at 1, overridable via `CV_MAX_CONCURRENT_INFERENCES`) before running and releases it after — bounding how many inferences may run *concurrently* across the whole process, independent of how many streams happen to be open. This is a plain semaphore around each stream's own existing consumer thread, not a new thread pool — inference was already running on a per-stream thread (gRPC's own `ThreadPoolExecutor`, see `serve()`), this only caps concurrent admission into `detect()`.
  - **Why 2, not `cpu_count`, and the honest OpenVINO/torch interplay:** a single Ultralytics/PyTorch `detect()` call is already internally multi-threaded (intra-op parallelism) — verified in this task's own dev environment, `torch.get_num_threads()` reported `6` on a 12-logical-core box, entirely PyTorch's own default heuristic, nothing this module configures or was asked to configure. So even 2 *concurrent* `detect()` calls can already ask for `2 x 6 = 12` threads' worth of work on that same 12-thread box — deliberately in the right ballpark rather than under- or wildly over-subscribing it, and it's capped at 2 regardless of core count because the realistic demo load (1-3 simultaneous streams) never needs more concurrency than that anyway. **What was NOT independently re-verified**: OpenVINO's own CPU-plugin thread auto-configuration (the Docker image's actual inference backend, see CP-a) — OpenVINO isn't installed in this dev environment (it's `pip install`ed only inside the Dockerfile, deliberately kept out of the `cv` extra), so this reasoning is carried over from the verified PyTorch behavior on the assumption OpenVINO's own default thread auto-tuning is comparably core-proportional (documented OpenVINO CPU plugin behavior, not measured here) — a real difference here would only change the *justification's* precision, not the gate's correctness, since `CV_MAX_CONCURRENT_INFERENCES` is an env var precisely so this number can be tuned without a code change once it's run against the real Docker image under load.
- **Sync `grpc.server`, not `grpc.aio`:** the existing synchronous gRPC server (`futures.ThreadPoolExecutor`-backed, see `serve()`) was kept rather than switching to `grpc.aio`. The concurrency this task needed — overlap within a stream, a bound across streams — is fully expressible with plain `threading` primitives (`LatestOnlyMailbox`, `InferenceGate`) layered onto the existing per-call-gets-its-own-thread model; a switch to `grpc.aio` would have meant rewriting `DetectStream` as an `async def`, `detect()`'s blocking `model.predict()` call would need `run_in_executor`-wrapping to avoid blocking the event loop anyway (it's not async-native), and the Dockerfile/test setup would gain a second async runtime to reason about for no behavioral gain this task needed. Kept simple; revisit only if a future task needs `grpc.aio`-specific features (e.g. true async model backends).
- **Echo mode (no model loaded) is untouched**: `DetectStream` special-cases `self._detector is None` to the original plain `for request in request_iterator: yield echo(request)` loop — no reader thread, no gate, nothing to overlap or bound without a model in the loop.
- **Graceful teardown (client cancel):** verified empirically against this grpc version (not assumed) — cancelling a call unblocks a **background** thread's `next(request_iterator)` within milliseconds, the exact same as it would the main thread; `_StreamReader`'s reader thread is therefore reliably unblocked and exits on its own once a stream ends for any reason, and `DetectStream`'s `finally: reader.stop()` (closing the mailbox) handles the rest. Covered by `test_reader_thread_does_not_leak_on_client_cancel` (real `grpc.server` + `grpc.insecure_channel`, not a fake) and `test_reader_thread_does_not_leak_on_normal_stream_completion`.

**Measured/estimated effect on detection rate:**
- *Per-stream overlap (goal 1), deterministic (fake-clock, immune to real CPU-inference noise — controlled `time.sleep`s standing in for network transit and inference)*: when simulated network transit is comparable to or larger than simulated inference (the case this task's goal targets — hiding real gRPC network latency behind compute), overlap measured **1.3-1.7x faster than the naive receive-then-infer bound** with zero frames dropped (`transit=50ms/infer=50ms/n=5`: 301ms measured vs 500ms naive-serial, 1.66x; `transit=100ms/infer=50ms/n=10`: 1102ms vs 1500ms, 1.36x) — the naive-serial bound is exactly what the pre-V-d `for request in iterator: infer(); yield` loop's wall time equals by construction (each frame pays `transit + infer` in strict sequence), so this is a direct, honest A/B, not just a measurement of the new code in isolation.
- *Cross-stream (goal 2), real Ultralytics `.pt` CPU inference at `imgsz=416`, illustrative only*: 1 stream alone sustained **~10-14 detections/sec** and 3 concurrent streams sustained **~9-10 detections/sec in aggregate** (~3/sec each) on this task's dev machine — **caveat, stated honestly**: this box was under real, visible, concurrent load from other agents' own builds/IDE for the whole task (`uptime` load average 4.7-7.9 on a 12-thread box, several `java`/Maven processes and an IDE running at the same time — confirmed via `ps`), so the absolute numbers vary run-to-run by 30%+ and are **not** a clean isolated benchmark; presented for directional insight, not a performance SLA. The qualitative, more load-independent finding is the one that matters for the goal: 3 streams' *aggregate* throughput does not collapse to a fraction of 1 stream's (it stays in the same ballpark), and each stream gets a fair, bounded share (~1/3 each) rather than any one stream starving the others or all three uncoordinatedly thrashing the CPU against each other — which is exactly what `InferenceGate` is for. The gate's own admission-control correctness (distinct from real-inference throughput) is verified deterministically and without any real-model noise by `test_inference_gate_caps_concurrent_detects_across_four_streams` (4 contending fake streams, gate size 2 → observed peak concurrency is exactly 2, never more).

## Gotchas
- **`sys.path` gotcha** (unchanged): `protoc`'s Python codegen emits imports rooted at the proto package path (`from vision.v1 import cv_pb2`) — the generated tree's *root* (`cv_service/gen`) must be on `sys.path`. `gen_proto.sh` touches `__init__.py` everywhere so the tree imports as regular packages.
- **protobuf version-scheme note** (unchanged): `protobuf>=5.26.1,<6` vs Java's `protobuf-java` 3.25.5 is not a real mismatch — don't "fix" it.
- **Dockerfile build context** (unchanged): must build from the **repository root** — `docker build -f cv-service/Dockerfile -t cv-service .`.
- **`opencv-python` vs `opencv-python-headless`**: do NOT add `opencv-python-headless` to the `cv` extra even though it would be preferable for Docker. `ultralytics` hard-depends on plain `opencv-python` (the GUI-enabled build), and pip has no notion that the two packages both provide `cv2` and conflict — installing both leaves whichever installs last silently overwriting the other's files on disk (confirmed locally: uninstalling one after both were present broke `cv2` entirely, `ImportError`). Instead the Dockerfile installs `libgl1`/`libglib2.0-0` at the OS level so plain `opencv-python` imports cleanly in the `python:3.12-slim` image.
- **`CV_MODEL` / weights location**: `YOLO("yolo11n.pt")` (a relative/known-alias name) downloads into the **current working directory** if not already present there — not a global cache dir. Locally this drops `yolo11n.pt` under `cv-service/` when running the server/tests from there; it's gitignored (`*.pt`/`*.onnx`/`*.engine`) — never commit it. The Dockerfile pre-downloads the `.pt` weights the same way at build time from `WORKDIR /app/cv-service`, then (CP-a) exports them to an OpenVINO IR directory (`yolo11n_openvino_model/`, also gitignored via `*_openvino_model/`) and points `CV_MODEL` at that directory instead — both the `.pt` source and the exported IR end up baked into the image so the container needs no network at runtime. If the export step ever proves unbuildable (network/size), drop the `yolo export` line and leave `CV_MODEL=yolo11n.pt` — the server falls back to plain PyTorch inference, just slower (documented inline in the Dockerfile).
- **`confidence_threshold` ambiguity**: proto3 `float` means an unset `FrameRequest.confidence_threshold` reads as `0.0`, indistinguishable from "explicitly zero". Both `server.py` and `YoloDetector.detect()` treat falsy/`None` as "use `DEFAULT_CONFIDENCE` (0.25)" — a caller wanting threshold `0.0` (accept everything) isn't representable on the wire today; not expected to matter for the demo.
- **First-request latency**: model construction + first `predict()` call include Ultralytics warmup (~1s observed locally even with cached weights); `inference_millis` only measures the `predict()` call itself, not model construction. As of CP-a, `YoloDetector.__init__` pays this cost itself (a dedicated warmup `predict()` on a black frame, at `self.imgsz`) so the *first real* `detect()` call no longer does — this is what protects adapter-cv-grpc's 2s response timeout from tripping into outage backoff right at stream start. The warmup call runs for injected `model=` doubles too, not just the real model.
- **`imgsz`/OpenVINO export coupling (CP-a)**: `CV_IMGSZ` (default `416`, must be a multiple of 32 by Ultralytics convention — not enforced in code) is passed as `imgsz=` to every `predict()` call, including warmup. The Dockerfile exports the model to OpenVINO IR at build time with a **fixed** input size baked in (`yolo export model=yolo11n.pt format=openvino imgsz=416`) — that export `imgsz` MUST equal the runtime `CV_IMGSZ`, or inference silently runs against the wrong size. If you change one, change both (Dockerfile `ENV CV_IMGSZ=416` and `DEFAULT_IMGSZ` in `inference.py` are the two places). Local/dev (non-Docker) runs plain `.pt` weights via `ultralytics.YOLO`, which has no such fixed-size constraint — `openvino` is intentionally NOT in the `cv` extra in `pyproject.toml`, only `pip install`ed directly in the Dockerfile.
- **Warmup failure semantics**: a warmup `predict()` exception (bad model state, OpenVINO backend mismatch, etc.) raises `ModelUnavailableError` from `YoloDetector.__init__`, exactly like a load failure — `server.py`'s `_build_default_detector()` catches it and degrades to the echo fallback rather than crash-looping.
- **`LatestOnlyMailbox` drops a frame with no response at all, ever, for that frame's `sequence`** (V-d): a dropped frame never reaches `detect()`, so no `DetectionResponse` is ever produced for it. On the Java side this means that specific pending future simply times out (`adapter-cv-grpc`'s own `RESPONSE_TIMEOUT_SECONDS=2s`, see its MODULE.md) rather than being answered quickly — expected and harmless given how rare drops are meant to be in practice (see "V-d" above), but worth knowing if a dropped-frame's timeout ever shows up in logs: it is not a bug, it's the latest-wins design working as intended.
- **`CV_MAX_CONCURRENT_INFERENCES` is a startup-time knob, not a live one** (V-d): `concurrency.py` resolves it once at **import time** into `DEFAULT_MAX_CONCURRENT_INFERENCES`/`process_gate()`'s module-level singleton — changing the env var after the process has started has no effect (matches `CV_MODEL`/`CV_IMGSZ`'s own existing "read once at construction" precedent, just at import time instead of `YoloDetector` construction time since the gate has no natural "construction" event of its own to hook).
- **Test-only nuance if you add more `DetectStream` tests with multiple frames**: any test iterator delivering 2+ frames with no artificial per-item delay races `_StreamReader`'s background thread against however fast the test happens to get scheduled — the reader can (and, empirically, sometimes does) put and overwrite several items before the consumer's first `get()` call, which is `LatestOnlyMailbox` correctly doing its job against a producer that (in the test) is unrealistically instantaneous, not a bug. Tests asserting an exact multi-frame response count/order use a small artificial per-item delay (`_PacedIterator`/`_DelayedIterator` in the test files) to avoid this — a real network is never actually instantaneous, so this is purely a test-engineering concern, not a production one.

## Status
Real inference (Ultralytics YOLO11n, CPU by default) implements `Inference.DetectStream` per `docs/MVP1-PLAN.md` §C7 bullet 1; falls back to the Phase 0 echo stub when the `cv` extra is absent or the model can't load, so the service never crash-loops for lack of a model. `Training` is still stubbed `UNIMPLEMENTED` (Phase 3); model registry / `model_id` selection is still Phase 3 (log-and-serve-default). **`docs/MVP2-PLAN.md` §V-d done**: `DetectStream` decouples per-stream frame receipt from inference (background reader thread + `LatestOnlyMailbox`) and bounds cross-stream concurrent inference (`InferenceGate`) — see "V-d: parallel per-stream inference" above for the full design, what was verified against `adapter-cv-grpc`'s correlator, and measured/estimated numbers. Test suite (`tests/`): `test_inference.py` + `test_server.py` + `test_server_concurrency.py` are mock-based (need `cv2`/`numpy`, i.e. the `cv` extra's transitive opencv-python, but not `ultralytics`/`torch` — they inject fake model/detector doubles); `test_concurrency.py` is pure-stdlib (no `cv` extra needed at all); `test_real_model.py` is a real-weights integration test, auto-skipped unless `ultralytics` is importable and its default weights load. Verified locally end-to-end: full `pip install -e '.[cv,dev]' --extra-index-url https://download.pytorch.org/whl/cpu` + `scripts/gen_proto.sh` + `scripts/test.sh` all green (57/57, real-model test included, run repeatedly with no flakes observed — 15 consecutive runs of the new concurrency-specific suites, 5 of the full suite); `python -m cv_service.server` confirmed to start and serve echo cleanly with the `cv` extra absent, and to load the real model and detect on a real JPEG frame end-to-end through `InferenceServicer.DetectStream` with the extra present (unchanged by V-d). `docker build -f cv-service/Dockerfile .` was not re-verified in this task — see §V-d's own done-note in `docs/MVP2-PLAN.md` for why (disk headroom at task time).
