# cv-service

Python gRPC CV inference & training service — real Ultralytics YOLO inference behind `Inference.DetectStream`, with an echo fallback when the model backend is unavailable. `DetectStream` runs each stream's frame receipt and inference concurrently (V-d), bounded by a process-wide inference gate. A `ModelRegistry` (`cv_service/inference/registry.py`, CP-b/`docs/CV-MODELS-PLAN.md`) lazily loads whichever local model(s) `model_id` names — including a comma-separated composite list that runs more than one model per frame — falling back to today's single default model for anything unrecognized. A per-stream `StreamTrackingSession` (`cv_service/tracking/`, T1/`docs/TRACKING-PLAN.md`) adds stable track ids and a **detect-then-track duty cycle**: in `FOLLOW` a sub-millisecond visual tracker holds the locked target every frame while the detector drops to a ~2 s verify pass, measured 30× fewer detector passes per second. Tracking is **off by default** and byte-identical to the pre-tracking service when a client does not ask for it.

**Package shape** (`docs/LAYERING-REFACTOR-PLAN.md` §5.2, wave G): the former 1031-line `server.py` monolith (gRPC servicing + training orchestration + zip IO + process bootstrap all in one file) is split into four packages by role:

```
cv_service/
  config.py          frozen Settings dataclass + Settings.from_env() -- the ONE place every
                      CV_* env var is read, resolved once at startup and passed down explicitly.
  grpc/
    servicers.py      InferenceServicer + TrainingServicer -- wire<->domain translation ONLY;
                       the sole place that touches generated cv_pb2 types.
    server.py         serve()/main(), signal handling, composition root (builds Settings,
                       wires servicers, starts the gRPC server).
  inference/
    detector.py        YoloDetector + Detection + decode_frame/map_detections (was inference.py)
    registry.py         ModelRegistry + discover_roster + detect_composite + build_default_registry
    concurrency.py      LatestOnlyMailbox + InferenceGate + process_gate()
  training/
    dataset.py          exported-YOLO dataset layout, path-safety guards, sanitize_dataset_id,
                         zip landing for UploadDataset (the ONE definition -- was duplicated
                         between server.py and trainer.py)
    trainer.py           the ultralytics fine-tune core (TrainingSpec, build_spec,
                          ultralytics_train, output_model_id)
    marker.py             active_model.json read/write (renamed from the misleading training.py)
    orchestrator.py        the StartTraining job-lifecycle/queue-poll state machine, lifted out
                            of the servicer method; yields plain JobEvents, never touches cv_pb2
  tracking/            the detect-then-track duty cycle (docs/TRACKING-PLAN.md wave T1)
    params.py           TrackingParams + resolve() -- the ONLY place a `<=0` wire sentinel
                         becomes a number; resolved on config CHANGE, never per frame
    scheduler.py        DutyCycleScheduler.decide(now, state) -> Decision(run_detector, reason)
                         -- PURE policy, TRACKING-PLAN §3.1's table and nothing else
    track.py            Track + TrackBook: TENTATIVE->CONFIRMED->COASTING->LOST->expired,
                         and the per-stream track-id allocator
    lock.py             LockArbiter (lock_seq monotonicity) + target selection (click point,
                         best-IoU re-anchor)
    registry.py         TrackerRegistry: TWO rosters of FACTORIES, startup constructibility
                         probe, roster logged once at INFO
    engines/
      base.py            the TWO protocols (Associator, SingleObjectTracker) + Box/Observation/
                          TrackerUpdate -- stdlib only
      bytetrack.py       ByteTrackEngine  -- ultralytics BYTETracker          (Associator)
      lk.py              LkFlowEngine     -- Lucas-Kanade optical flow        (SingleObjectTracker)
      ncc.py             NccEngine        -- matchTemplate NCC                (SingleObjectTracker)
    session.py          StreamTrackingSession: COMPOSITION ONLY, one instance per stream,
                         created inside DetectStream exactly where `_StreamReader` is
```

Tests mirror this exactly: `tests/{inference,training,grpc,tracking}/` + `tests/test_config.py`.

**Depends on:** grpcio, grpcio-tools, protobuf (Python); `cv` extra: ultralytics (pulls in torch transitively) + explicit `opencv-python>=5.0,<6` and `lap>=0.5.12` pins (T1 — see pyproject.toml's comment for why each is pinned rather than floated, and for invariant **P1**: nothing x86- or CUDA-only may ever enter this extra); shared contract `proto/vision/v1/cv.proto` · **Used by:** adapter-cv-grpc, wired end-to-end (`PipelineConfig.model` → `FrameRequest.model_id` — see "Java plumb verification" under CP-b below)
**Build/test:** `python -m cv_service.grpc.server` (run). `scripts/test.sh` or `python -m pytest` (test; needs `pip install -e '.[dev]'` at minimum, `-e '.[cv,dev]'` for the mock+real-model suites — see Status). Codegen: `scripts/gen_proto.sh` (regenerates `cv_service/gen/`, not committed). The local checkpoints this repo ships (`yolo11n.pt`, `yolo26n.pt`, `orion12l.pt`, `yoloe-26s-seg-pf.pt`, all gitignored, provenance: `docs/CV-MODELS-PLAN.md`) exercise the registry/composite tests in `tests/inference/test_registry.py`/`test_real_model.py` when present. Deploying this service on a separate CUDA machine (offloading inference off the laptop): `cv-service/DEPLOY-GPU.md`.

## API surface

### `cv_service/config.py`
The **one place** every `CV_*` environment variable is read. Before this module existed, five vars were read piecemeal across `server.py`/`inference.py`/`trainer.py`/`concurrency.py` (three of them -- `CV_DEVICE`, `CV_MAX_CONCURRENT_INFERENCES`, `CV_DATASET_DIR` -- resolved once at *import* time, so a value could never change without a process restart even though nothing required that).
- `@dataclass(frozen=True) class Settings` — every configurable knob, resolved once: `port` (`CV_PORT`, default `50051` — new, previously unreachable via env), `model` (`CV_MODEL`, default `"yolo26n.pt"`), `imgsz` (`CV_IMGSZ`, default `416`), `device` (`CV_DEVICE`, default `None` = ultralytics auto), `max_concurrent_inferences` (`CV_MAX_CONCURRENT_INFERENCES`, default `min(2, cpu_count // 2)` floored at 1), `dataset_dir` (`CV_DATASET_DIR`, default `<cv-service>/datasets`), `model_dir` (`CV_MODEL_DIR` — new, default `<cv-service>/`), `max_upload_bytes` (`CV_MAX_UPLOAD_BYTES`, default 2 GiB), `grpc_workers` (`CV_GRPC_WORKERS`, default `10`), `shutdown_grace_seconds` (`CV_SHUTDOWN_GRACE`, default `5`). Every default is byte-identical to the literal it replaces.
- `Settings.from_env() -> Settings` — reads `os.environ` fresh (no caching) and resolves one `Settings`. `cv_service/grpc/server.py`'s `main()` calls this exactly once at process startup and threads the result down explicitly (`serve(settings)` → `InferenceServicer(registry=..., inference_gate=...)`/`TrainingServicer(model_dir=..., dataset_dir=..., max_upload_bytes=...)`). Nothing downstream reads `os.environ` directly anymore — modules that can be constructed standalone (`YoloDetector`, `ultralytics_train`) call `Settings.from_env()` themselves when a value isn't explicitly supplied, which re-parses fresh every call, exactly matching the pre-`config.py` per-construction-refresh behavior for `CV_MODEL`/`CV_IMGSZ` (and, deliberately, *changing* `CV_DEVICE`/`CV_MAX_CONCURRENT_INFERENCES` from "frozen at first import" to "fresh at each resolution" — see Gotchas).
- **Tracking knobs (T1)**, backing the wire's `<=0 = server default` sentinels on `TrackingConfig` — `cv_service/tracking/params.py`'s `resolve()` is their only consumer: `track_associate_engine` (`CV_TRACK_ASSOCIATE_ENGINE`, default `"bytetrack"`), `track_follow_engine` (`CV_TRACK_FOLLOW_ENGINE`, default `"lk"`), `track_verify_millis` (`CV_TRACK_VERIFY_MS`, default `2000`), `track_iou` (`CV_TRACK_IOU`, default `0.3`), `track_max_age_frames` (`CV_TRACK_MAX_AGE`, default `30`), `track_min_hits` (`CV_TRACK_MIN_HITS`, default `3`). Two engine knobs, not one, because the two modes are served by two *protocols* that share no method — a single "default tracker" would be meaningless (see "Tracking engine" below).
- Forgiving-parse helpers (unset/garbage → default, never raise): `_parse_imgsz`, `_parse_device`, `_resolve_max_concurrent_inferences`/`_default_max_concurrent_inferences`, `_parse_positive_int` (the last backs the newer `CV_PORT`/`CV_MAX_UPLOAD_BYTES`/`CV_GRPC_WORKERS`/`CV_SHUTDOWN_GRACE` knobs plus `CV_TRACK_VERIFY_MS`/`CV_TRACK_MAX_AGE`/`CV_TRACK_MIN_HITS`), `_parse_engine_id` (blank → default; deliberately does **not** validate against the engine roster — that is `TrackerRegistry`'s startup probe's job, and validating here would make a typo a startup crash instead of a logged degradation), `_parse_unit_fraction` (backs `CV_TRACK_IOU`; rejects anything outside `(0, 1]` **with a fallback rather than a clamp**, because the likeliest mistake is writing the REST layer's percent `30` into the wire layer's fraction, and clamping `30` to `1.0` would silently produce a tracker that never re-anchors). These used to be duplicated across `inference.py`/`trainer.py`/`concurrency.py`; this is the one definition.

### `cv_service/inference/concurrency.py`
Pure-stdlib (`threading` only — no `cv_pb2`, no cv2/numpy/ultralytics), protobuf-agnostic by the same convention as `detector.py`. Two independent primitives, wired to `FrameRequest`/`DetectStream` by `cv_service/grpc/servicers.py`:
- `class LatestOnlyMailbox[T]` — single-slot, latest-wins handoff between one producer thread and one consumer thread. `put(value)` never blocks/queues: if a value is already waiting unconsumed, it's silently replaced (`.dropped` counts replacements). `get() -> T | None` blocks until a value is available or the mailbox is `close()`d and drained (`None` sentinel — don't use this for a value where `None` is itself meaningful; `FrameRequest`s never are). `close()` unblocks every pending/future `get()` with `None` once any already-pending value has been delivered once.
- `class InferenceGate(max_concurrent: int)` — a plain `threading.Semaphore(max_concurrent)` wrapped as a context manager (`gate.acquire()`), not a thread pool: it gates how many *existing* stream-consumer threads may be inside `detect()` at once, it never creates threads of its own. Raises `ValueError` if `max_concurrent < 1`.
- `process_gate() -> InferenceGate` — the shared, process-wide gate a bare `InferenceServicer()` falls back to when no `inference_gate=` is given. Lazily built (and cached) from `cv_service.config.Settings.from_env()` on first call rather than at import time (see `cv_service/config.py`) — the production composition root, `cv_service.grpc.server.serve()`, always builds and passes a gate explicitly instead, so this lazy singleton is only reached via direct/test construction. Tests construct their own differently-sized `InferenceGate` and inject it instead (`InferenceServicer(detector=..., inference_gate=...)`).

### `cv_service/inference/detector.py`
Independent of the generated protobuf stubs (importable/testable without codegen) — only `cv2`/`numpy`/optionally `ultralytics`.
- `ENCODING_JPEG`, `ENCODING_BGR24: str` — match `ImageEncoding` enum names one-for-one (get via `cv_pb2.ImageEncoding.Name(request.encoding)`).
- `DEFAULT_MODEL = "yolo26n.pt"`, `DEFAULT_IMGSZ = 416` — re-exported from `cv_service.config` (the canonical home for `CV_*` defaults) for backward-compatible imports. `DEFAULT_CONFIDENCE = 0.25` — an inference-behavior default, not a `CV_*` env knob, so it stays local to this module.
- `class ModelUnavailableError(RuntimeError)` — raised by `YoloDetector.__init__` when `ultralytics` isn't installed, or the model/weights can't be loaded.
- `@dataclass(frozen=True) class Detection(label: str, confidence: float, x: float, y: float, width: float, height: float)` — mirrors proto `Detection`/`BoundingBox`: `x`/`y` top-left corner, `width`/`height` extend right/down, all normalized to `[0, 1]`.
- `def decode_frame(width: int, height: int, encoding: str, data: bytes) -> np.ndarray` — JPEG via `cv2.imdecode`; BGR24 via `np.frombuffer(...).reshape((height, width, 3))`. Raises `ValueError` on bad length/bytes/encoding.
- `def map_detections(result: Any, frame_width: int, frame_height: int) -> list[Detection]` — maps one Ultralytics `Results` (duck-typed: `.boxes.xyxy`/`.conf`/`.cls`, `.names`) to normalized `Detection`s (Ultralytics already rescales `xyxy` to the original frame, so no letterbox un-padding needed); clamps to `[0, 1]`; `[]` if `boxes` is `None`/empty.
- `class YoloDetector(model_name: str | None = None, *, model: Any = None, device: str | None = None)` — loads `ultralytics.YOLO(model_name or Settings.from_env().model)` once; `model=` injects a test double, bypassing `ultralytics` entirely. `.model_name -> str`. `.imgsz -> int` — from `Settings.from_env().imgsz` (default `DEFAULT_IMGSZ`; unset/non-numeric/non-positive all fall back to the default, never raise). `.device -> str | None` — the constructor `device` kwarg if given (falsy falls through), else `Settings.from_env().device`; logged once at INFO at construction (`"cv-service inference device=%s (model=%r)"`, `"auto"` when `None`) alongside the model-load log. `Settings.from_env()` is called fresh at every construction (no caching) — this is one of the few places outside `config.py` itself that calls `from_env()` directly rather than receiving an already-resolved value, because `YoloDetector` is constructed from more than one call site (the model registry, tests, real-model smoke tests) that don't all have a `Settings` handy; the *parsing* still lives in exactly one place either way. After the model is loaded (real or injected), construction runs one warmup `predict()` on a black `np.zeros((imgsz, imgsz, 3), uint8)` frame; a warmup failure (including an invalid/unavailable `device`, e.g. `"cuda:0"` with no GPU — ultralytics raises inside `predict()`) raises `ModelUnavailableError` same as a load failure, no special-casing needed. `.detect(*, width, height, encoding, data, confidence_threshold: float | None = None) -> tuple[list[Detection], int]` — decode → `model.predict(frame, conf=conf, imgsz=self.imgsz, verbose=False, **({"device": self.device} if self.device is not None else {}))` → map; returns `(detections, inference_millis)`. `device=` is passed to *every* `predict()` call (warmup and `detect()`) only when resolved — omitted entirely (not passed as `None`) when unset, keeping behavior byte-identical to before this knob existed. Falsy/`None` `confidence_threshold` uses `DEFAULT_CONFIDENCE`.

### `cv_service/inference/registry.py` (CP-b, `docs/CV-MODELS-PLAN.md`)
Same "no `cv_pb2`" convention as `detector.py` — importable/testable without codegen, but importing it (it imports `cv_service.inference.detector`) requires the `cv` extra. See "Model registry & composite mode" below for the full design/rationale.
- `def discover_roster(base_dir: Path, default_model: str) -> dict[str, str]` — scans `base_dir` for `*.pt` files and `*_openvino_model` directories (one level, non-recursive); always includes `default_model` even if not found there (a not-yet-downloaded alias, or a `CV_MODEL` path elsewhere). Returns `{model_id -> loadable name/path}`.
- `def short_name(model_id: str) -> str` — strips `.pt`/`_openvino_model` for use as a composite-mode label prefix (`"yolo11n.pt"`/`"yolo11n_openvino_model"` → `"yolo11n"`).
- `class ModelRegistry(roster: dict[str, str], default_id: str, *, detector_factory: Callable = YoloDetector)` — lazy `{model_id -> YoloDetector}`; `default_id` must be a `roster` key (raises `ValueError` otherwise — always true when `roster` came from `discover_roster`). `.roster -> dict[str, str]` (a copy). `.default_detector() -> YoloDetector | None` — lazily builds/caches the default; `None` if even it fails to load. `.resolve(requested_model_id: str) -> list[tuple[str, YoloDetector]]` — splits on `,` (composite mode), drops unknown ids (logs once per distinct unknown id, INFO) and ids that fail to load (logs once per id, WARNING) from that specific request, keeping any other known/loadable members; falls back to `[(default_id, default_detector())]` only when *nothing* in the request resolved (empty/unknown/all-failed), and to `[]` if even the default itself is unavailable (caller echoes that frame). `.loaded_ids() -> list[str]` — diagnostics/tests.
- `def detect_composite(resolved: list[tuple[str, YoloDetector]], *, gate: InferenceGate, width, height, encoding, data, confidence_threshold=None) -> tuple[list[Detection], int]` — runs every resolved member's `detect()` (each individually through `gate.acquire()`, same as a lone model), concatenates detections, sums `inference_millis`. When `len(resolved) > 1`, prefixes every label `"{short_name}:{label}"` (e.g. `"orion12l:tank"`) — a single-model call is untouched. Logs each member's own `inference_millis` at DEBUG (not INFO — see Gotchas, this runs every frame).
- `def build_default_registry(settings: Settings) -> ModelRegistry | None` — builds the production registry: `discover_roster(settings.model_dir, settings.model)`, applies a persisted promotion from `cv_service.training.marker.read_active_model` if one names a current roster id, constructs the `ModelRegistry`, eagerly forces the default detector to load (a broken default degrades the whole servicer to echo mode). Assumes the `cv` extra is already available (this module's own import already requires it); callers that don't yet know whether the extra is installed (`cv_service/grpc/server.py`'s `serve()`, `InferenceServicer`'s omitted-`registry` default path) import this module itself inside a `try/except ImportError`, mirroring the pre-split `_build_default_detector()`/`_build_default_registry()` contract.

### `cv_service/training/dataset.py`
Stdlib-only (`os`, `shutil`, `zipfile`, `uuid`, `pathlib`) — importable without the `cv` extra. Never imports `cv_pb2` — `cv_service/grpc/servicers.py` is the sole translation point, turning this module's plain `UploadOutcome` into a `cv_pb2.UploadAck` itself.
- `DATASET_DIRNAME = "datasets"`, `DATA_YAML_NAME`/`IMAGES_DIRNAME`/`LABELS_DIRNAME` — the exported-YOLO layout a dataset dir must carry (Phase 1's `FilesystemDatasetExport`). Format contract shared with another process, so these stay plain constants (not env-configurable — `docs/LAYERING-REFACTOR-PLAN.md` §1.3's explicit out-of-scope list).
- `class DatasetNotFoundError(Exception)` — missing/malformed dataset (a *reported* `FAILED`, never a gRPC abort).
- `def resolve_dataset_dir(datasets_root, dataset_id) -> Path` — validates `<root>/<id>/` carries `data.yaml`+`images/`+`labels/`, else raises `DatasetNotFoundError`. Re-exported by `cv_service.training.trainer` (which calls it from `build_spec`) so existing callers importing it via `trainer.resolve_dataset_dir` keep working.
- `def sanitize_dataset_id(dataset_id: str) -> str` — filesystem-safe basename. **The one definition** — previously duplicated between `server.py`'s own sanitize step and an inline copy inside `trainer.output_model_id`; `trainer.output_model_id` now imports this instead.
- `def is_safe_dataset_id(dataset_id: str) -> bool` — `UploadDataset`'s accept test: anything `sanitize_dataset_id` would rewrite (blank, a path separator, `..`, ...) is rejected outright rather than silently accepted under a different name.
- `def is_safe_zip_entry(name: str) -> bool` — zip-slip protection for one archive member's path: accepts only `data.yaml`, `images/<name>`, `labels/<stem>.txt`; rejects an absolute path, a `..` segment, or any other top-level prefix.
- `@dataclass(frozen=True) class UploadOutcome(ok: bool, message: str, dataset_id="", bytes_received=0, file_count=0)` — plain (wire-agnostic) result of landing an archive.
- `def land_dataset(zip_path, datasets_root, dataset_id, bytes_received) -> UploadOutcome` — validates + extracts into a sibling temp dir, validates the extracted tree with `resolve_dataset_dir`, then atomically replaces `<datasets_root>/<dataset_id>/` (remove-then-`os.replace`). Every failure past the streaming/size-cap stage is a *reported* `ok=False`, never raised.

### `cv_service/training/trainer.py` (CV-TRAINING Phase 2, `StartTraining` core)
Stdlib-only at import scope (no `ultralytics`/`torch`/`cv2` at module top — same discipline as `cv_service/grpc/server.py`); the heavyweight `ultralytics` import is **lazy**, inside `ultralytics_train`, so the server stays importable/runnable without the `cv` extra. Re-exports `DATA_YAML_NAME`/`IMAGES_DIRNAME`/`LABELS_DIRNAME`/`DatasetNotFoundError`/`resolve_dataset_dir` from `cv_service.training.dataset` (its own `build_spec` calls `resolve_dataset_dir` directly).
- `DEFAULT_EPOCHS = 50` (fallback when `TrainingJobSpec.epochs` is unset/≤0), `DEFAULT_BASE_MODEL = "yolo26n.pt"`.
- `@dataclass(frozen=True) TrainingSpec(job_id, base_model, dataset_id, epochs, dataset_dir, data_yaml, output_dir)` — everything `ultralytics_train` needs. `@dataclass(frozen=True) EpochProgress(epoch, total_epochs, loss, map50)` — one epoch's reported metrics, mapped 1:1 to `TrainingProgress` fields (via `cv_service.training.orchestrator.JobEvent`, see below).
- `class TrainingCancelled(Exception)` — raised out of a `train_fn` on caller cancel.
- `build_spec(*, job_id, base_model, dataset_id, epochs, datasets_root, output_dir) -> TrainingSpec` — resolves the dataset (`cv_service.training.dataset.resolve_dataset_dir`) + defaults epochs/base_model.
- `output_model_id(dataset_id, epochs) -> str` — the produced artifact's id/filename: **`<dataset_id>-<epochs>e.pt`** (deterministic; `dataset_id` sanitized via `cv_service.training.dataset.sanitize_dataset_id` so a path separator can't escape the model dir).
- `TrainFn = Callable[..., Path]` — the injectable trainer contract: `train_fn(spec, *, on_epoch: Callable[[EpochProgress],None], is_cancelled: Callable[[],bool]) -> Path` returning the produced `best.pt`; raises `TrainingCancelled` if cancelled, any `Exception` on failure. Default is `ultralytics_train`; tests inject a fast fake.
- `ultralytics_train(spec, *, on_epoch, is_cancelled) -> Path` — lazily imports `ultralytics`, resolves `device`/`imgsz` via `cv_service.config.Settings.from_env()` (device auto if unset — **never hard-pins CPU**), hooks `on_fit_epoch_end` for per-epoch progress (suppressing Ultralytics' one **trailing** post-training-validation callback where `trainer.epoch==trainer.epochs`, so callers see exactly one update per epoch), sets `trainer.stop=True` on cancel, and returns the run's `best.pt` (`<output_dir>/runs/<job_id>/weights/best.pt`). `loss` is read from `trainer.loss` (scalar; falls back to summing the `trainer.tloss` dict); `map50` from `metrics["metrics/mAP50(B)"]`. `_warn_cpu_once` logs the one-time "training on CPU — this is slow" note when no CUDA is available.

### `cv_service/training/marker.py` (renamed from `cv_service/training.py`)
Stdlib-only (`json`), importable without the `cv` extra — the misleading old name (`training.py`) suggested it owned the whole training feature; it only ever read/wrote `active_model.json`, so it's named for that now.
- `ACTIVE_MODEL_MARKER = "active_model.json"` (written under `Settings.model_dir`, gitignored — runtime state); `read_active_model(model_dir) -> str | None` (forgiving — missing/corrupt/empty marker reads as `None`, never raises); `write_active_model(model_dir, model_id, version="")`. `build_default_registry()` (`cv_service/inference/registry.py`) reads the marker at startup and, if it names a **current roster id**, seeds the registry's `default_id` from it (a marker naming an absent id, or no marker, falls back to `settings.model`) — this is what makes a promotion survive the rsync-deploy restart.

### `cv_service/training/orchestrator.py`
The job-lifecycle/queue-poll state machine lifted out of the (formerly ~120-line) `StartTraining` gRPC handler, so it can be read/tested independent of wire translation. **Never imports `cv_pb2` or `grpc`** — `cv_service/grpc/servicers.py` is the sole place that turns its output into wire messages.
- `@dataclass(frozen=True) class JobEvent(kind: str, epoch=0, total_epochs=0, loss=0.0, map50=0.0, message="", model_id="")` — the plain, wire-agnostic counterpart of `cv_pb2.TrainingProgress`. `kind` is `"running"` (one per epoch) or a terminal `"succeeded"`/`"failed"`; a job ending via cancellation yields no event at all (the generator just stops), same as before extraction.
- `run_training_job(spec, *, job_id, train_fn, is_context_active, register_cancel_callback, publish_artifact) -> Iterator[JobEvent]` — runs `train_fn` on a background worker thread (mirrors `DetectStream`'s `_StreamReader` "keep long-lived work off the calling thread" shape); this generator only polls a `queue.Queue` for progress + yields, so it stays responsive to cancellation. `is_context_active`/`register_cancel_callback` are plain callables `cv_service/grpc/servicers.py` wires to `context.is_active()`/`context.add_callback()` — this function itself never touches `grpc.ServicerContext`. `publish_artifact` is the servicer's own callback (it needs `self._registry`/`self._model_dir`) for landing a successful run's `best.pt`.

### `cv_service/tracking/` (T1, `docs/TRACKING-PLAN.md` + `docs/TRACKING-ORCHESTRATION.md`)
Same "no `cv_pb2`" convention as `inference/`/`training/`. **Everything except `engines/{bytetrack,lk,ncc}.py` is pure stdlib** — no `cv2`/`numpy`/`ultralytics` at module scope, including `engines/base.py` (its `np.ndarray` annotations are `TYPE_CHECKING`-only). That is what keeps `python -m cv_service.grpc.server` runnable with no `cv` extra even though `grpc/servicers.py` imports the session at module scope, and what makes the duty cycle testable against a fake clock with no frames. Both properties have their own tests (`tests/tracking/test_registry.py`). Full design: "Tracking engine" below.

- **`params.py`** — `MODE_OFF`/`MODE_ASSOCIATE`/`MODE_FOLLOW`/`MODE_UNSPECIFIED: str` (match `cv_pb2.TrackingMode`'s enum **value names** one-for-one, the same convention `detector.py`'s `ENCODING_*` uses, so the servicer maps with `Name()`/`Value()` and keeps no lookup table). `@dataclass(frozen=True) TrackingRequest` / `LockRequest` — the protobuf-free counterparts of `cv_pb2.TrackingConfig`/`TargetLock`, **sentinels intact**. `@dataclass(frozen=True) TrackingParams(mode, engine_id, verify_every_millis, redetect_iou_threshold, max_age_frames, min_hits)` + `.active`. `normalize_mode(str) -> str` (an unknown mode from a newer client → OFF). `resolve(request, settings) -> TrackingParams` — **the only place a `<=0` sentinel becomes a number**; the engine default is per mode.
- **`scheduler.py`** — `REASON_*: str` (match `cv_pb2.DetectorReason` value names). `@dataclass(frozen=True) Decision(run_detector, reason)`; `reason` is `UNSPECIFIED` exactly when `run_detector` is False. `@dataclass(frozen=True) SchedulerState(mode, has_lock, last_detector_millis, tracker_failed, box_invalid, coasting_frames)` — everything `decide()` may look at, as a value. `DutyCycleScheduler(params)` with `.decide(now_millis, state) -> Decision` and `.retune(params)`. In FOLLOW the triggers are evaluated most-specific-first, so a frame that is both past cadence and holding no lock reports `NO_LOCK`. **No cadence/threshold/count literal appears in this file.**
- **`track.py`** — `STATE_*: str` (match `cv_pb2.TrackState`). `@dataclass Track(track_id, key, box, label, confidence, first_seen, last_seen, state, source, velocity_x, velocity_y, age_frames, hits, misses)`. `TrackBook(params)`: `.apply(observations, now, *, detector_ran) -> list[Track]` (books in order, ages the untouched, settles every state, expires), `.tracks`, `.get(track_id)`, `.retune(params)`, `.forget_keys()`. **The book allocates track ids, not the engine** — see the Gotcha on ByteTrack's global counter. `observation_for(detection, key, *, det_index, source, authoritative)` adapts a duck-typed `Detection`. Velocities are normalized units/second; `age_frames` is 0 on the birth frame.
- **`lock.py`** — `@dataclass(frozen=True) LockTarget(track_id, point, box)`. `LockArbiter`: `.apply(LockRequest|None) -> bool` (**strictly-greater `lock_seq` only**, so restating the same lock every frame is a no-op), `.bind(track_id)`/`.unbind()`/`.drop()`, `.target`, `.bound_track_id`, `.generation`, `.applied_seq`. Plus two pure selectors used by the session: `select_by_point(boxes, x, y)` (smallest containing box, else nearest centre) and `best_iou_match(box, candidates, min_iou)` (the §3.1 re-anchor test).
- **`engines/base.py`** — `SOURCE_DETECTOR`/`SOURCE_TRACKER: str`. `@dataclass(frozen=True) Box(x, y, width, height)` normalized, with `.center`, `.valid` (threshold-free: non-positive extent, or zero overlap with the unit square), `.iou(other)`, `.contains(x, y)`. `@dataclass(frozen=True) Observation(key, box, label, confidence, source, det_index, authoritative)`. `@dataclass(frozen=True) TrackerUpdate(box, confidence)`. `class Associator(Protocol)`: `engine_id`, `associate(detections, now) -> list[Observation]`, `reset()`. `class SingleObjectTracker(Protocol)`: `engine_id`, `init(frame, box) -> bool`, `update(frame) -> TrackerUpdate | None`, `reset()`.
- **`engines/bytetrack.py`** — `ENGINE_ID = "bytetrack"`; `ByteTrackEngine(max_age_frames=...)` (an `Associator`) and `create(*, max_age_frames)`. Adapts plain normalized `Detection`s to the minimal `Results`-like view `BYTETracker.update` consumes.
- **`engines/lk.py` / `engines/ncc.py`** — `ENGINE_ID`; `LkFlowEngine()` / `NccEngine()` (both `SingleObjectTracker`) and `create()`. `init()` returns **False**, never raises, for a target the engine cannot hold (featureless patch, sub-2px box).
- **`registry.py`** — `BUILTIN_ASSOCIATORS`/`BUILTIN_FOLLOWERS: dict[str, factory]` (lazy imports inside the factories). `TrackerRegistry(*, associators, followers, default_associate_id, default_follow_id)`: `.probe() -> dict[str, list[str]]` (constructs each engine once, drops what raises, logs the surviving roster **once at INFO**; idempotent, never raises), `.roster()`, `.associator(engine_id, *, max_age_frames)` / `.follower(...)` → `(serving_engine_id, engine) | None` — **a NEW instance per call**, unknown id logged once and served the default. `build_default_registry(settings, *, probe=True) -> TrackerRegistry` — never `None` (an empty roster is a usable object that degrades every stream, and returning `None` would move the same branch into every caller).
- **`session.py`** — `@dataclass(frozen=True) TrackedBox(label, confidence, box, track)` (`track is None` is the one spelling of untracked). `@dataclass(frozen=True) FrameOutcome(boxes, inference_millis, detector_ran, detector_reason, tracker_millis, engine_id, locked_track_id)` (`boxes is None` → echo this frame). `StreamTrackingSession(*, settings, registry_provider)`: `.active`, `.params`, `.tracks`, `.applied_wire_config` (opaque, compared by the servicer), `.apply_config(TrackingRequest, wire_token)` (**on change only**), `.process(*, now_millis, detect, frame) -> FrameOutcome`. `detect` and `frame` are callables the servicer supplies — which is exactly why this file **holds no reference to an `InferenceGate` and structurally cannot acquire one**.

### `cv_service/grpc/servicers.py`
The **sole place** that touches generated `cv_pb2` message types — every other cv-service module works with plain Python values/dataclasses. Owns the `sys.path`/`cv_service/gen` bootstrap (`cv_service/grpc/server.py` re-imports `cv_pb2`/`cv_pb2_grpc` from here rather than duplicating it).
- `class InferenceServicer(cv_pb2_grpc.InferenceServicer)` — `__init__(detector: YoloDetector | None = None, *, inference_gate: InferenceGate | None = None, registry: ModelRegistry | None = None)`. Two mutually-exclusive ways to give it a model:
  - **`detector=`** (explicit injection — every pre-registry test still uses this): exactly one detector serves every frame regardless of `model_id`; an unrecognized `model_id` logs once (`_warn_once_on_unknown_model`, unchanged) and serves this same detector anyway. No registry, no composite mode.
  - **omitted** (the default/production path): builds a `ModelRegistry` via the module-local `_build_default_registry()` (a thin wrapper resolving `Settings.from_env()` and lazily importing `cv_service.inference.registry.build_default_registry`) — or takes `registry=` directly, for tests — `request.model_id` (comma-separated for composite) is routed through `registry.resolve()` + `registry.detect_composite()` in `_detect_via_registry()`.
  `inference_gate` defaults to `cv_service.inference.concurrency.process_gate()` (shared process-wide) — tests inject a smaller/differently-sized one; production (`serve()`) always builds and passes one explicitly from `Settings`. `DetectStream(request_iterator, context)`: runs real inference per frame when a model is loaded (either path), mapping `Detection`s to `cv_pb2.Detection`/`BoundingBox`; "no model at all" and any per-frame exception degrade to the original Phase 0 echo response — a bad frame or missing model never kills the bidi stream. **When a model is loaded, frame receipt and inference run concurrently within the stream, and every `detect()` call is gated across streams** — see "V-d: parallel per-stream inference" below.
  Two more constructor kwargs land with T1: **`settings=`** (a resolved `Settings`; falls back to `Settings.from_env()`, the same per-construction-refresh idiom `YoloDetector` uses) supplies the `CV_TRACK_*` defaults `params.resolve()` falls back to, and **`tracker_registry=`** injects the shared `TrackerRegistry`. Omitting `tracker_registry` builds one **lazily**, on the first frame that actually requests an active tracking mode, so neither the OFF path nor a test that never tracks pays for constructing and probing engines; `serve()` passes an already-probed one instead, which is what makes the roster get logged at *startup* rather than on first use.
  `DetectStream` creates one **`StreamTrackingSession`** per call, in the same place and for the same reason `_StreamReader` is created (state that belongs to one bidi call, not to the servicer every stream shares), and threads it into `_handle_request(request, session)`.
- Tracking wire translation lives here and nowhere else (module-level, T1): `_tracking_request_from_wire` / `_lock_request_from_wire` (`cv_pb2.TrackingConfig`/`TargetLock` → the plain `TrackingRequest`/`LockRequest`), `_tracking_mode_name` (an unknown mode number from a *newer* client → `UNSPECIFIED` → OFF, never a raise), `_tracked_detection` (a `TrackedBox` → `cv_pb2.Detection`; an untracked box sets **no** track field at all), `_tracked_response` (a `FrameOutcome` → `DetectionResponse`, including `detector_ran`/`detector_reason`/`tracker_millis`/`tracker_engine_id`/`locked_track_id`), and `_frame_loader` (a **memoized, lazy** `decode_frame` closure for the FOLLOW path — lazy because `ASSOCIATE` never needs pixels and importing `detector.py` at module scope would break echo mode without the `cv` extra; memoized because a FOLLOW verify frame touches the pixels twice).
- `InferenceServicer._run_detector(request)` is the **one place `InferenceGate` is acquired** — both model paths (explicit `detector=` and registry-routed) fold into it precisely so the tracking session can spend a detector pass through a single callable without knowing which one the servicer was built with, and so the gate acquisition stays a single greppable location. `_sync_tracking(session, request)` folds in this frame's restated `TrackingConfig` (one protobuf `==` per frame; `resolve()` and any engine rebuild only on a real change) and reports whether tracking is active.
- `class _StreamReader` — package-private; one instance per active `DetectStream` call with a model loaded. Spawns a daemon thread (`cv-detectstream-reader`) that drains the *rest* of `request_iterator` into a `LatestOnlyMailbox`. `.next()` blocks for the next (latest) frame, `None` at end of stream, re-raises whatever the iterator itself raised. `.stop()` closes the mailbox (best-effort).
- `class TrainingServicer(cv_pb2_grpc.TrainingServicer)` — model-registry control plane + dataset fine-tune (CV-TRAINING Phase 2; `docs/CV-TRAINING-PLAN.md` §6). `__init__(*, registry=None, model_dir: Path | None = None, dataset_dir: Path | None = None, train_fn: trainer.TrainFn | None = None, max_upload_bytes: int = DEFAULT_MAX_UPLOAD_BYTES)` — holds the **same** `ModelRegistry` instance the inference path routes against. `model_dir`/`dataset_dir` are resolved lazily (`_resolved_model_dir()`/`_resolved_dataset_dir()`, falling back to `Settings.from_env()` when omitted) at each method that actually needs a concrete directory (`StartTraining`, `_publish_artifact`, `UploadDataset`) — **except** `PromoteModel`'s marker persistence, which keeps its own unresolved `self._model_dir is not None` check: a `None` there means "don't persist a marker" (a test-only affordance), not "use the default directory". `registry` is typed loosely (not `ModelRegistry`) to keep this servicer importable without the `cv` extra.
  - **`ListModels(Empty) -> ModelList`** — one `ModelInfo{id, version="", stage}` per roster id (`sorted`), `stage="active"` for the current default, `"available"` for the rest. Returns an **empty** `ModelList` (never aborts) when `registry is None` (echo mode / no model loaded).
  - **`PromoteModel(ModelRefMsg) -> Ack`** — re-points the shared registry default via `registry.promote(id)` **and** persists the choice to the active-model marker (`cv_service.training.marker`) for restart-survival. `Ack{ok:true}` on success. A bad id is a **normal reported outcome, never an abort**: unknown id, empty id, or `registry is None` all return `Ack{ok:false, message}`.
  - **`StartTraining(TrainingJobSpec) -> stream TrainingProgress`** — resolves the dataset (`trainer.build_spec`, catching `dataset.DatasetNotFoundError` as a terminal reported `FAILED`), then delegates the actual job-lifecycle state machine to `cv_service.training.orchestrator.run_training_job`, translating each plain `JobEvent` it yields into a `cv_pb2.TrainingProgress` (one `RUNNING` per epoch, then exactly one terminal `SUCCEEDED`/`FAILED`). Cancellation is wired via `context.is_active()`/`context.add_callback()`. **Never auto-promotes** — the operator promotes deliberately via `PromoteModel`. Device-agnostic (CUDA if present, else CPU — slow on this Intel box, logged once).
  - **`UploadDataset(stream DatasetChunk) -> UploadAck`** — client-streaming: buffers incoming bytes to a temp file under the datasets root (checking `dataset.is_safe_dataset_id` and the byte cap per-chunk, `context.abort()`ing `INVALID_ARGUMENT`/`RESOURCE_EXHAUSTED` for protocol-level problems), then delegates zip validation/extraction/atomic-replace to `cv_service.training.dataset.land_dataset`, translating its plain `UploadOutcome` into a `cv_pb2.UploadAck`. Content problems (corrupt zip, zip-slip entry, malformed tree, zero chunks) are **reported** (`ok:false`), never aborted. `trainer.py`/`StartTraining` are **not** touched by this RPC.
  - `_publish_artifact(best_weights, spec) -> str` — copies the produced `best.pt` into the model dir under `trainer.output_model_id(...)` and `registry.register()`s it so `ListModels`/`PromoteModel` see it immediately, without a restart. Passed into `orchestrator.run_training_job` as its `publish_artifact` callback.

### `cv_service/grpc/server.py`
`def serve(settings: Settings | None = None) -> grpc.Server` — resolves `Settings.from_env()` if none given, builds `grpc.server(futures.ThreadPoolExecutor(max_workers=settings.grpc_workers), options=_KEEPALIVE_SERVER_OPTIONS)`, builds the `ModelRegistry` **once** (`_build_default_registry(settings)`, may be `None`) and one `InferenceGate(settings.max_concurrent_inferences)`, builds and **probes** the `TrackerRegistry` once (`_build_tracker_registry(settings)`, T1 — probing at startup rather than on first frame is the whole point, so the roster an operator sees is the one that actually constructs on this box; a failure here degrades trackers, never blocks startup), passes the same registry to both `InferenceServicer(registry=..., inference_gate=..., settings=..., tracker_registry=...)` and `TrainingServicer(registry=..., model_dir=settings.model_dir, dataset_dir=settings.dataset_dir, max_upload_bytes=settings.max_upload_bytes)` so `PromoteModel` re-points the very registry inference routes against (one source of truth), binds `[::]:{settings.port}`, starts, returns. `def main() -> None` — resolves `Settings` once, calls `serve(settings)`, installs `SIGTERM`/`SIGINT` handlers that call `server.stop(grace=settings.shutdown_grace_seconds)`. `_KEEPALIVE_SERVER_OPTIONS: list[tuple[str, int]]` — module-level constant, HTTP/2 keepalive server options (docs/REMOTE-CV-PLAN.md "Transport decisions" P1): `grpc.keepalive_permit_without_calls=1`, `grpc.http2.min_ping_interval_without_data_ms=10000`, `grpc.keepalive_time_ms=30000`, `grpc.keepalive_timeout_ms=10000`.

## Conventions
- Generated stubs live under `cv_service/gen/` and are **never committed** — run `scripts/gen_proto.sh` after cloning and whenever `proto/vision/v1/cv.proto` changes.
- `cv_service/grpc/servicers.py` is the sole translation point between wire types (`cv_pb2.FrameRequest`, `encoding` as an enum int, `cv_pb2.TrackingConfig`/`TargetLock`, `cv_pb2.TrainingProgress`, `cv_pb2.UploadAck`) and every other module's plain types (`width`/`height`/`encoding: str`/`data: bytes`, `Detection`, `TrackingRequest`/`LockRequest`/`FrameOutcome`, `JobEvent`, `UploadOutcome`). `cv_service/inference/detector.py`, `registry.py`, `cv_service/training/dataset.py`, `trainer.py`, `orchestrator.py` and **every module under `cv_service/tracking/`** follow the same rule (none of them import `cv_pb2`). This keeps all of them unit-testable without running codegen first.
- **Proto enum values cross that boundary as their own value-name strings** — `"TRACK_STATE_CONFIRMED"`, `"DETECTOR_REASON_CADENCE"`, `"TRACKING_MODE_FOLLOW"`, `"DETECTION_SOURCE_TRACKER"` — the same convention `detector.py`'s `ENCODING_JPEG`/`ENCODING_BGR24` already used for `ImageEncoding`. The servicer maps them with `cv_pb2.X.Name()`/`.Value()` and keeps **no lookup table**, so there is nothing to drift when the proto grows a value.
- **`cv_service/tracking/` is pure stdlib except `engines/{bytetrack,lk,ncc}.py`.** `engines/base.py` is stdlib too (its `np.ndarray`/`Detection` annotations are `TYPE_CHECKING`-only), which is what lets `track.py`/`lock.py`/`session.py` share its `Box`/`Observation` vocabulary. Two things depend on this: `python -m cv_service.grpc.server` stays runnable with no `cv` extra even though `servicers.py` imports the session at module scope, and the scheduler/lifecycle/lock/session tests run against a fake clock with no frames and no OpenCV. Both are pinned by tests in `tests/tracking/test_registry.py`.
- `cv_service/inference/detector.py` (and, transitively, `cv_service/inference/registry.py`) imports `cv2`/`numpy` at module scope, so importing either at all requires the `cv` extra. `cv_service/grpc/servicers.py`/`server.py` only import them lazily inside their own `_build_default_registry()` functions — so `cv_service.grpc.server`, and hence `python -m cv_service.grpc.server`, stays importable/runnable without the `cv` extra (echo mode).
- `cv_service/config.py` is the one place every `CV_*` env var is read (see its API surface entry above) — no other module calls `os.environ.get` directly.
- Tests live in `tests/` (not under `cv_service/`), mirroring the package layout (`tests/inference/`, `tests/training/`, `tests/grpc/`, `tests/tracking/`, plus `tests/test_config.py`), plain `pytest`, fixtures in `tests/conftest.py` (a tiny synthetic frame, no fixture image files on disk).

## V-d: parallel per-stream inference (`docs/MVP2-PLAN.md` §V-d)

**Problem this closes:** pre-V-d, `DetectStream` was `for request in request_iterator: infer(request); yield response` — receiving the next frame off the network only started *after* the current frame's inference finished and its response had been handed back to gRPC, so inference and network transfer never overlapped within one stream; and every stream's `detect()` calls ran fully unbounded/uncoordinated against every other stream's, with nothing protecting the CPU as more streams were added.

**Design chosen — a background reader thread + a 1-slot latest-wins mailbox, per stream, plus a small process-wide semaphore across streams:**

- **Within a stream** (`_StreamReader` + `LatestOnlyMailbox`, both in `cv_service/grpc/servicers.py`/`cv_service/inference/concurrency.py`): `DetectStream` claims the stream's **first** frame directly and synchronously (there's nothing to overlap with before the first frame's own inference even begins), *then* spawns a `_StreamReader` background thread to drain the rest of `request_iterator` into a `LatestOnlyMailbox` while the consumer (the thread gRPC itself drives as the `DetectStream` generator) is inside `detect()`. If a second frame arrives in the mailbox before the consumer has taken the first, it silently replaces it (`.dropped` counts this) — **never a growing backlog**, always the newest available frame. **Response ordering per stream is still always increasing/in-order** (frames are only ever consumed and yielded one at a time, in the order the reader thread received them, minus whichever got overwritten) — this was a deliberate simplicity choice, not a requirement: `adapter-cv-grpc/MODULE.md`'s "Correlation design" section was read first and confirms the Java side matches responses back to pending futures **by their own `sequence` field**, independently per response (`ConcurrentHashMap<Long, CompletableFuture<DetectionResult>>` keyed by sequence, proven under out-of-order server replies by its own `detectCorrelatesInterleavedResponsesBySequence` test) — so mild reordering would have been tolerated too, but keeping this side in-order is simpler to reason about and costs nothing.
  - **Why the first frame is claimed synchronously rather than also going through the reader thread:** confirmed empirically (not assumed) while building this — spawning the reader thread immediately and letting *it* claim frame 0 too creates a real, reproducible race between the reader thread racing ahead through an already-available burst of frames and the consumer's very first `mailbox.get()` call; with a zero-latency in-memory iterator (exactly what this module's own tests use, and plausible for a very bursty real sender too) the reader can legitimately win that race and have already overwritten frame 0 with a later frame before the consumer ever asks for anything. Claiming frame 0 directly removes the possibility entirely, and matches reality: there's no earlier frame to be overlapping the first one's *reception* with anyway.
  - **Why drops are expected to be rare in production, not just "possible in theory":** the mailbox only drops when a *second* new frame arrives while a *first* one is still unconsumed — i.e. only when the sender is at least two frames ahead of what's been inferred+responded-to. `adapter-cv-grpc` (the only real caller) allows at most a small, bounded number of frames in flight per stream at once (see its own MODULE.md "Failure semantics"/correlation design) rather than sending unboundedly far ahead of received responses, so in practice the reader is rarely more than one frame ahead of the consumer. This module's own tests deliberately *do* trigger drops (with instantaneous/fast fake iterators and a gated fake detector) specifically because proving the drop behavior needs to force that "sender got ahead" condition on demand — that's a test-engineering choice, not evidence it's common in production.
- **Across streams** (`InferenceGate`, in `cv_service/inference/concurrency.py`): every `detect()` call, regardless of which stream it's for, acquires the same process-wide `InferenceGate` (default size `min(2, cpu_count // 2)`, floored at 1, overridable via `CV_MAX_CONCURRENT_INFERENCES`) before running and releases it after — bounding how many inferences may run *concurrently* across the whole process, independent of how many streams happen to be open. This is a plain semaphore around each stream's own existing consumer thread, not a new thread pool — inference was already running on a per-stream thread (gRPC's own `ThreadPoolExecutor`, see `serve()`), this only caps concurrent admission into `detect()`.
  - **Why 2, not `cpu_count`, and the honest OpenVINO/torch interplay:** a single Ultralytics/PyTorch `detect()` call is already internally multi-threaded (intra-op parallelism) — verified in this task's own dev environment, `torch.get_num_threads()` reported `6` on a 12-logical-core box, entirely PyTorch's own default heuristic, nothing this module configures or was asked to configure. So even 2 *concurrent* `detect()` calls can already ask for `2 x 6 = 12` threads' worth of work on that same 12-thread box — deliberately in the right ballpark rather than under- or wildly over-subscribing it, and it's capped at 2 regardless of core count because the realistic demo load (1-3 simultaneous streams) never needs more concurrency than that anyway. **What was NOT independently re-verified**: OpenVINO's own CPU-plugin thread auto-configuration (the Docker image's actual inference backend, see CP-a) — OpenVINO isn't installed in this dev environment (it's `pip install`ed only inside the Dockerfile, deliberately kept out of the `cv` extra), so this reasoning is carried over from the verified PyTorch behavior on the assumption OpenVINO's own default thread auto-tuning is comparably core-proportional (documented OpenVINO CPU plugin behavior, not measured here) — a real difference here would only change the *justification's* precision, not the gate's correctness, since `CV_MAX_CONCURRENT_INFERENCES` is an env var precisely so this number can be tuned without a code change once it's run against the real Docker image under load.
- **Sync `grpc.server`, not `grpc.aio`:** the existing synchronous gRPC server (`futures.ThreadPoolExecutor`-backed, see `serve()`) was kept rather than switching to `grpc.aio`. The concurrency this task needed — overlap within a stream, a bound across streams — is fully expressible with plain `threading` primitives (`LatestOnlyMailbox`, `InferenceGate`) layered onto the existing per-call-gets-its-own-thread model; a switch to `grpc.aio` would have meant rewriting `DetectStream` as an `async def`, `detect()`'s blocking `model.predict()` call would need `run_in_executor`-wrapping to avoid blocking the event loop anyway (it's not async-native), and the Dockerfile/test setup would gain a second async runtime to reason about for no behavioral gain this task needed. Kept simple; revisit only if a future task needs `grpc.aio`-specific features (e.g. true async model backends).
- **Echo mode (no model loaded) is untouched**: `DetectStream` special-cases `self._detector is None` to the original plain `for request in request_iterator: yield echo(request)` loop — no reader thread, no gate, nothing to overlap or bound without a model in the loop.
- **Graceful teardown (client cancel):** verified empirically against this grpc version (not assumed) — cancelling a call unblocks a **background** thread's `next(request_iterator)` within milliseconds, the exact same as it would the main thread; `_StreamReader`'s reader thread is therefore reliably unblocked and exits on its own once a stream ends for any reason, and `DetectStream`'s `finally: reader.stop()` (closing the mailbox) handles the rest. Covered by `test_reader_thread_does_not_leak_on_client_cancel` (real `grpc.server` + `grpc.insecure_channel`, not a fake) and `test_reader_thread_does_not_leak_on_normal_stream_completion` (`tests/grpc/test_detect_stream_concurrency.py`).

**Measured/estimated effect on detection rate:**
- *Per-stream overlap (goal 1), deterministic (fake-clock, immune to real CPU-inference noise — controlled `time.sleep`s standing in for network transit and inference)*: when simulated network transit is comparable to or larger than simulated inference (the case this task's goal targets — hiding real gRPC network latency behind compute), overlap measured **1.3-1.7x faster than the naive receive-then-infer bound** with zero frames dropped (`transit=50ms/infer=50ms/n=5`: 301ms measured vs 500ms naive-serial, 1.66x; `transit=100ms/infer=50ms/n=10`: 1102ms vs 1500ms, 1.36x) — the naive-serial bound is exactly what the pre-V-d `for request in iterator: infer(); yield` loop's wall time equals by construction (each frame pays `transit + infer` in strict sequence), so this is a direct, honest A/B, not just a measurement of the new code in isolation.
- *Cross-stream (goal 2), real Ultralytics `.pt` CPU inference at `imgsz=416`, illustrative only*: 1 stream alone sustained **~10-14 detections/sec** and 3 concurrent streams sustained **~9-10 detections/sec in aggregate** (~3/sec each) on this task's dev machine — **caveat, stated honestly**: this box was under real, visible, concurrent load from other agents' own builds/IDE for the whole task (`uptime` load average 4.7-7.9 on a 12-thread box, several `java`/Maven processes and an IDE running at the same time — confirmed via `ps`), so the absolute numbers vary run-to-run by 30%+ and are **not** a clean isolated benchmark; presented for directional insight, not a performance SLA. The qualitative, more load-independent finding is the one that matters for the goal: 3 streams' *aggregate* throughput does not collapse to a fraction of 1 stream's (it stays in the same ballpark), and each stream gets a fair, bounded share (~1/3 each) rather than any one stream starving the others or all three uncoordinatedly thrashing the CPU against each other — which is exactly what `InferenceGate` is for. The gate's own admission-control correctness (distinct from real-inference throughput) is verified deterministically and without any real-model noise by `test_inference_gate_caps_concurrent_detects_across_four_streams` (4 contending fake streams, gate size 2 → observed peak concurrency is exactly 2, never more).

## Model registry & composite mode (CP-b, `docs/CV-MODELS-PLAN.md`)

**Problem this closes:** before CP-b, `DetectStream` hard-loaded exactly one `YoloDetector` at construction time; any other `request.model_id` was logged once and silently served the same default — there was no way for a client to actually pick between the two local checkpoints this repo ships (`yolo11n.pt`, a general COCO model, and `orion12l.pt`, a user-provided 53MB YOLO12-L military-vehicle model), let alone run both on the same frame.

**Design chosen — a lazy `{model_id -> YoloDetector}` registry, keyed by what's actually on disk, plus a comma-separated composite mode:**

- **Roster discovery** (`registry.discover_roster`, called once by `build_default_registry()` at servicer construction): scans `cv-service/` (`Settings.model_dir`'s default — the same directory `YOLO("x.pt")`'s own cwd-relative download/cache behavior already uses — see "`CV_MODEL` / weights location" below, and where the Dockerfile's `WORKDIR` puts things too) for every `*.pt` file and `*_openvino_model` export directory, plus always includes the resolved default (`settings.model`) even if discovery didn't find it there. On this repo's checkout that roster is `{"yolo11n.pt": ..., "yolo26n.pt": ..., "orion12l.pt": ..., "yoloe-26s-seg-pf.pt": ...}` (or, inside the Docker image, with `yolo11n_openvino_model` added — see the Docker gotcha below) — **logged once at INFO at startup** (`"cv-service model registry roster: [...] (default=...)"`), so an operator can see exactly which ids are routable without reading code.
- **Lazy loading**: no model is constructed (no ultralytics weights load, no warmup `predict()`) until first requested. Each is cached for the process's lifetime after that.
- **Routing** (`ModelRegistry.resolve`): `request.model_id` may be one id or a comma-separated list. Every requested id not in the roster is dropped with a once-per-distinct-id INFO log (same log-and-serve-default contract as before CP-b — old clients that never set `model_id`, or clients naming a genuinely unknown model, see zero behavior change). If *nothing* in the request resolved (empty, all-unknown, or a roster id that itself failed to load), falls back to the default model. A **partially**-unknown composite list (e.g. `"orion12l.pt,typo"`) keeps its known member(s) rather than discarding the whole request, since at least one requested model *was* real.
- **Composite mode** (`registry.detect_composite`): every resolved model runs `detect()` on the *same* frame, gated individually through the existing process-wide `InferenceGate` (no separate bound for composite), and detections are concatenated. `inference_millis` returned is the **sum** of every member's own `inference_millis` — composite work is strictly more compute run sequentially on one stream's consumer thread, never overlapped (V-d's overlap is about *network receipt* vs. *inference*, not about running two models at once). Confidence filtering already happens per-model inside each `YoloDetector.detect()` call; composite mode adds no second filtering pass.

**Composite mode: no free proto field, so labels get prefixed instead.** `Detection` (`proto/vision/v1/cv.proto`) has no spare field to carry which model produced a detection (`label`/`confidence`/`box` are the only three fields); adding one is a wire-format change out of scope for this module. Instead, when more than one model actually ran, every detection's `label` gets prefixed `"{short_name}:{label}"` (e.g. `"orion12l:tank"`, `"yolo11n:person"`) — verified safe: `adapter-overlay`'s `Java2DOverlayRenderer` treats `Detection.label()` as a fully opaque string (only ever hashed to pick a stable box color and drawn as literal text). A useful side effect: because the hash includes the prefix, `"yolo11n:person"` and a hypothetical `"orion12l:person"` get *different* colors automatically. **Single-model requests are completely unaffected**.

**Java plumb verification (read-only — vision-application/adapter-cv-grpc/vision-proto were NOT modified by this task):**
`PipelineConfig.model` (a `ModelRef(id, version)`, `vision-domain/src/main/java/com/drones/vision/domain/model/PipelineConfig.java:43`) reaches the wire intact:
- `adapters/adapter-cv-grpc/src/main/java/com/drones/vision/adapter/cvgrpc/GrpcDetectionPort.java:263` — `.setModelId(config.model().id())` (and `:264` `.setModelVersion(config.model().version())`) inside `buildRequest()`, building the `FrameRequest` sent to this service.
- `proto/vision/v1/cv.proto:30` — `FrameRequest.model_id` (`string model_id = 8;`) is exactly the field `ModelRegistry.resolve` reads (`request.model_id`).
- **Verdict: the plumb is intact, zero Java changes needed for registry/composite routing to work today.** The only gap is on the *default value* side, not the plumbing: `PipelineConfig.defaults()` (`PipelineConfig.java:107`) ships `new ModelRef("yolo", "latest")` — `"yolo"` isn't (and was never) a roster id either before or after this task, so it already hit the pre-existing "unknown id, log once, serve default" path and continues to after CP-b unchanged. Wiring an actual model picker into `PipelineConfig.model` is a UI/settings-surface task, out of this module's scope.

**Measured per-model latency and memory (this dev machine, 12 logical cores, `torch.get_num_threads()`=6, `imgsz=416`, plain PyTorch `.pt` weights — not the Docker image's OpenVINO IR; numbers are directional not a clean isolated benchmark):**

## Tracking engine (T1, `docs/TRACKING-PLAN.md` + `docs/TRACKING-ORCHESTRATION.md`)

**Problem this closes:** `DetectStream` ran one full detector pass per received frame, and detections carried no identity across frames — a box was a fresh anonymous rectangle every time, so nothing downstream could say "that is the same car". Two consequences: the CPU cost of watching one target was the full detector cost, forever; and `trackId` did not exist for the UI, for geolocation trails, or for click-to-follow.

**Design chosen — two perception loops on the same stream, running at very different rates:**

| Mode | Every frame | Detector pass when |
|---|---|---|
| `OFF` (default) | — | every received frame. **Byte-identical to pre-T1 behavior** |
| `ASSOCIATE` | associate the detector's boxes to existing tracks | every received frame — cv-service only ever receives *sampled* frames, so there is nothing left to duty-cycle |
| `FOLLOW` | `engine.update(frame)` on the locked target | any of: cadence elapsed · tracker reported lost · no lock held · predicted box collapsed/left frame · coasted past `max_age_frames` |

### Measured on this box (12 logical cores, load avg ~0.7, `opencv-python 5.0.0.93`, `ultralytics 8.4.104`, 640×360 frames)

Directional, not a clean isolated benchmark — same caveat every other number in this file carries.

| What | mean | p95 |
|---|---|---|
| `lk` `update()` — 40 corners, incl. full-frame BGR→grey | **0.525 ms** | 0.619 ms |
| `ncc` `update()` — 80×60 template in a 2× window | **0.243 ms** | 0.283 ms |
| `bytetrack` `associate()` — 10 detections | **0.780 ms** | 0.857 ms |
| **session per tracker-only frame, end to end** (`lk`, incl. JPEG decode) | **2.40 ms** | 2.79 ms |
| **session per tracker-only frame, end to end** (`ncc`, incl. JPEG decode) | **1.83 ms** | 1.94 ms |
| — of which `decode_frame`, 154 KB pure-noise JPEG (worst case) | 2.14 ms | 3.18 ms |
| — of which `decode_frame`, 27 KB realistic-content JPEG | 0.61 ms | 0.82 ms |
| `yolo26n.pt` `detect()` on the same 640×360 JPEG, `imgsz=416`, for contrast | **22.8 ms** | 23.7 ms |

**The two numbers that matter.** The engine itself costs **0.24–0.53 ms/frame**, i.e. **43×–95× cheaper** than a `yolo26n` pass on the same frame (and 650×–1400× cheaper than an `orion12l` pass at ~343 ms). End to end through the session the tracker-only frame costs **1.8–2.4 ms on a pathological all-noise JPEG**, of which the **frame decode is the dominant term, not the tracker** — on realistic content the same path is ~0.9–1.1 ms. Recorded explicitly because it says where the next optimization is if one is ever needed (a BGR24 feed or a smaller frame, not a faster tracker).

**`FOLLOW` duty ratio, measured over 300 frames at 15 fps with the default 2000 ms cadence: 10 detector passes / 300 frames = exactly 1 in 30 (3.3%), i.e. 0.50 detector passes per second instead of 15.** The detector pass rate drops **30×**; the mean per-frame server cost drops from ~23.6 ms (`ASSOCIATE`: a detector pass plus an association every frame) to ~3.2 ms (`FOLLOW`: one pass in thirty plus a tracker update), a **~7×** reduction per stream. Both figures come from `tests/grpc/test_detect_stream_tracking.py`'s fake-clock harness plus the measured per-call costs above. The end-to-end before/after is wave T8's, below — run against real photographic content and a real detector, but **not against a camera**, for the reason T8's section states.

### Engine roster (§5.B) — dictated by what is actually installed

| `engine_id` | Protocol | Mechanism | Assets |
|---|---|---|---|
| **`bytetrack`** | `Associator` (ASSOCIATE default) | ultralytics `BYTETracker` — IoU + Kalman, two-stage high/low-confidence association | none (already a dependency; needs `lap`, now pinned) |
| **`lk`** | `SingleObjectTracker` (FOLLOW default) | `cv2.calcOpticalFlowPyrLK` over ≤40 `goodFeaturesToTrack` corners; median translation + median radial scale | none — core OpenCV `video`, build-info confirmed present |
| **`ncc`** | `SingleObjectTracker` | `cv2.matchTemplate(TM_CCOEFF_NORMED)` in a 2× search window | none — core OpenCV |

`lk` and `ncc` fail in *different* places, which is why both ship: `lk` needs corners and refuses a feature-poor target (returns `False` from `init`, never raises), while `ncc` needs only that the patch keep looking like itself but drifts under rotation/scale, which `lk` handles. **KCF/CSRT/MOSSE are not options here** — OpenCV 5 removed them and `cv2.legacy` is gone; the only `Tracker*` symbols present are `TrackerMIL` (24 ms/frame, ~50× the budget, rejected) and `TrackerNano`/`TrackerVit`/`TrackerDaSiamRPN`, each of which raises on construction because opencv-python ships no ONNX weights for them. Those three are a deferred, documented seam: a file drop (the Dockerfile carries a commented, ready-to-uncomment `curl`) plus a registry entry, not a redesign.

### Six decisions worth knowing before you change this

1. **`TrackerRegistry` hands out factories; `ModelRegistry` caches singletons.** A YOLO model is stateless across streams and expensive to load, so it is cached per id. A tracker is the exact reverse — cheap to build, inherently stateful — so **every call constructs a new engine, and engines are never shared between streams**. Getting this backwards corrupts every stream at once, so it has its own test.
2. **Two protocols, not one.** `bytetrack` can never implement `update(frame)` and `lk` can never implement `associate(detections)`; one protocol would force every engine to stub half of itself on the seam the whole extensibility story rests on. An engine that legitimately served both would implement both.
3. **The tracker path never acquires `InferenceGate`** — the gate bounds concurrent *YOLO* passes, and a 0.5 ms tracker update queueing behind a 343 ms `orion12l` pass on another stream would destroy the design. This is structural, not a convention: `session.py` holds no gate reference and can only reach the detector through the `detect` callable the servicer passes in, which is `_run_detector`, the single acquisition site. Tested with a recording fake gate asserting **zero** acquisitions across 59 consecutive tracker-only frames.
4. **The config is restated on every frame and resolved on change.** `TrackingConfig` rides every `FrameRequest` deliberately (`LatestOnlyMailbox` can silently drop a frame, so a one-shot control message could vanish with no error and no retry; a restated desired state is self-healing). The per-frame cost of that is exactly one protobuf `==` in `_sync_tracking`; `params.resolve()` runs only on a real change. A `TargetLock` applies only on a **strictly greater** `lock_seq`, so restating the same lock 15×/second is a no-op.
5. **`session.py` is ~300 code lines, not the "~80" TRACKING-ORCHESTRATION §2.1 budgeted.** The charter held — no scheduling policy, lifecycle rule or geometry lives there, and the two blocks that did (target selection, the degradation ladder's parameter copy) moved to `lock.py` and `params.py`. What the estimate missed is that FOLLOW alone has five distinct per-frame outcomes (re-anchor, coast, tracker-lost, box-invalid, lost-past-max-age), each sequencing engine + book + lock, on top of the degradation ladder and the engine lifecycle. Recorded rather than quietly split across a ninth file, which would move the seam without moving a responsibility.
6. **In `FOLLOW`, `CONFIRMED` and `COASTING` alternate, and that is the visible signature of the duty cycle.** A verify pass that re-anchors makes the box `CONFIRMED` with `source = DETECTOR`; every frame in between is `COASTING` with `source = TRACKER` — literally "tracker-predicted; the detector has not re-confirmed it on the most recent pass". A locked target is `CONFIRMED` immediately on acquisition rather than serving `min_hits` verify passes (six seconds at the default cadence) first: `min_hits` is an anti-flicker gate against *false positives*, and an operator clicking a box is not one. Carried as `Observation.authoritative`, which engines never set.

### `yoloe-26s-seg-pf.pt` — prompt-free open-vocabulary YOLOE (opt-in, CV-MODELS-PLAN follow-up)

Satisfies the "one model covering people **+** vehicles **+** buildings" need, controllable via model selection without disturbing the fast default.

- **Zero code change to route it.** It loads via the *plain* `ultralytics.YOLO(name)` class `YoloDetector` already uses — there is **no `YOLOE` class and no `set_classes()` call**; prompt-free mode auto-loads a built-in ~1200-class-scale LVIS+Objects365 vocabulary (the loaded checkpoint reports **4585** class names). `discover_roster` already globs `*.pt`, so dropping the file into `cv-service/` makes it a routable `model_id` immediately. Verified end-to-end (discovery → `resolve` → `detect` → `map_detections`) against the real weights.
- **It is instance-segmentation, but boxes work identically.** The `*-seg-pf` checkpoints are the only prompt-free variant (there is **no detection-only prompt-free YOLOE**). Their Ultralytics `Results` carry a non-None `.masks` **in addition to** the usual `.boxes` (`.xyxy`/`.conf`/`.cls`) and `.names`. `map_detections` is already mask-agnostic — it reads only `.boxes`/`.names` and never touches `.masks` — so segmentation and detection checkpoints flow through the same box-mapping path. Confirmed on real weights: a `bus.jpg` predict returned a `Results` with `.masks is not None` and `map_detections` still produced well-formed boxes (e.g. `person` @ conf 0.88). No mask handling was added; masks are simply dropped.
- **Real emitted labels (measured, this box, imgsz=416):**
  - *people* → `person` (vocabulary also has `man`/`woman`).
  - *vehicles* → `bus` (on `bus.jpg`); vocabulary also has `car`, `truck`, `van`, `motorcycle`, `bicycle`, `motor vehicle`, `land vehicle`.
  - *buildings* → the literal labels **`building`, `skyscraper`, `office building`, `house`, `brick building`, `glass building`** are all in the vocabulary, **but** the model — being a ~4585-class LVIS+scene vocabulary — is quite scene-descriptive and often emits a *more specific* label than the bare `building`: on real city photos it produced `downtown`, `city nightview`, `sky tower`, `apartment`, `roof`, `Prague Castle`, `auto factory`, `fishing village`. **Open item / caveat:** don't assume a stable literal `"building"` string — the exact building-ish label is image-dependent; a UI that wants to bucket "buildings" should match a *set* of these labels, not one string.
- **Latency:** ~69ms/frame on a synthetic 64×48 frame, ~85–100ms on real imagery (`bus.jpg`) at imgsz=416 on this 12-thread CPU — i.e. **~1.7–2.5× slower than `yolo26n`**, still well under `orion12l`'s ~343ms. Directional only (shared dev box under load), same caveat as the tables above.
- **One-time acquisition** (the file is gitignored via `*.pt`, so a clean checkout won't have it and the real test skips): from `cv-service/`, with the `cv` extra installed, run
  `python -c "from ultralytics import YOLO; YOLO('yoloe-26s-seg-pf.pt')"`
  — Ultralytics auto-downloads the official asset (~31MB, `github.com/ultralytics/assets` release `v8.4.0`) into the cwd. No network fetch is ever done by the test suite itself; this is a manual one-off. (Other sizes exist: `yoloe-26n/26m/…-seg-pf.pt`, `yoloe-11s/11m/11l-seg-pf.pt`, `yoloe-v8*-seg-pf.pt`.)
- **OpenVINO export — OPEN ITEM, not verified.** `openvino` is deliberately not in the `cv` extra (only installed inside the Dockerfile), so export feasibility for this checkpoint was **not** verified in this task. Expectation (unconfirmed): `yolo export model=yoloe-26s-seg-pf.pt format=openvino imgsz=416` should produce a `yoloe-26s-seg-pf_openvino_model/` IR that the registry would auto-discover (it globs `*_openvino_model`), and the **same imgsz-coupling caveat applies verbatim** — the export `imgsz` MUST equal runtime `CV_IMGSZ` or inference silently runs at the wrong size. A segmentation export also carries mask outputs the box path ignores, same as the `.pt`. **Do not assume this works until someone runs it in the Docker/openvino environment** and confirms the IR loads and `.boxes` still populate. The default `yolo11n`/`yolo26n` OpenVINO export in the Dockerfile is unchanged; this model would run plain-PyTorch inside the container today (same as `orion12l`, see the Docker gotcha below).
- **`short_name("yoloe-26s-seg-pf.pt")` → `"yoloe-26s-seg-pf"`** (only the trailing `.pt` is stripped; `-seg-pf` is part of the model's own name, not a known export suffix). This is correct, not a bug — the prefix only ever labels detections in composite mode (`yoloe-26s-seg-pf:building`), where the full name disambiguates it from other yoloe variants.

## Running on ARM64 / a companion computer

cv-service is the deployable unit and it is **placement-blind**: `Settings`, the registries and the servicers have no notion of where they run, which is why the third placement below costs no redesign. The same package, the same `Inference.DetectStream` contract, the same `CV_*` env vars run in all three:

| Placement | Frames arrive by | Status |
|---|---|---|
| Co-located (laptop/server, beside vision-app) | localhost gRPC | works today |
| LAN inference box (GB4005, `vision.cv.endpoint`) | LAN gRPC, rsync deploys | works today |
| **Onboard companion computer** (Raspberry Pi 4/5, ARM64) | localhost gRPC from an onboard frame-feeder | dependency-verified; **no runtime numbers, no hardware** |

**Install path — plain pip + rsync, deliberately not a multi-arch image.** From `cv-service/` on the ARM host:

```bash
pip install -e '.[cv]'          # NOTE: no --extra-index-url on ARM
./scripts/gen_proto.sh
python -m cv_service.grpc.server
```

**The `--extra-index-url https://download.pytorch.org/whl/cpu` line is x86-only.** PyPI's plain `torch` wheel for aarch64 *is* the CPU build — there are no generic-ARM CUDA wheels — so the extra index buys nothing there and only risks resolution surprises. Deploy by rsync, the same pattern GB4005 already uses (`cv-service/DEPLOY-GPU.md`). There is deliberately **no buildx multi-arch target**: the amd64 image's defining feature is its baked OpenVINO IR export, an Intel-CPU optimization that does not apply to ARM, so a second architecture of a ~1.5 GB image would be cost with no payoff.

**Invariant P1 — nothing x86-only or CUDA-only may ever enter the `cv` extra.** It is free to hold and expensive to recover: one CUDA-gated dependency, or `openvino` promoted out of the Dockerfile into `pyproject.toml`, silently ends the onboard story. This is why the shipped tracker engines are pure core-OpenCV (`lk`, `ncc`) and pure Python over numpy (`bytetrack`), and why `openvino` stays a Docker-image-only install.

**aarch64 wheel availability — verified by downloading the wheels, not by reading a table.** This is
TRACKING-PLAN wave T8's **portability acceptance check**, and it is a *resolution* check, nothing
more: **it does not promise a green ARM build.** There is no ARM CI in this repo and no Pi. What it
establishes is that every pinned member of the `cv` extra has a real aarch64/cp312 wheel that pip
will actually select — which is the honest bound available without hardware. Re-run verbatim on
**2026-08-11 (wave T8)**, exit code 0:

**No Pi number in this document is measured — there is no companion-computer hardware yet.** Everything below is a **designed-for budget**, explicitly labelled as such, and stays that way until someone runs it on real silicon:

- **Budget, not measurement:** a YOLO nano `.pt` at `CV_IMGSZ=320` rather than 416 is the realistic onboard detector, and continuous detection on a Pi is not viable at any size. The duty cycle is what makes onboard perception plausible at all: a verify pass every ~2 s against a sub-millisecond tracker, rather than a detector pass every frame. `CV_TRACK_VERIFY_MS` is already the operator knob that trades re-anchor freshness for CPU with no code change.
- **Budget, not measurement:** ~1.5 GB of installed footprint (torch dominates) and thermal throttling in a sealed airframe bay are both real risks that only real hardware can size.
- **Documented escape hatch, not built:** a torch-free onboard profile (`onnxruntime`/NCNN for the detector plus an in-repo ~200-line IoU+Kalman associator registered under the same `engine_id`) — build it if and when a *measured* Pi says 407 MB of torch is the blocker, not before. `TrackerRegistry` is what keeps that a one-file change.
- **Deferred deliverable with a frozen interface:** the onboard frame-feeder — a small Python process capturing from the Pi/UVC camera and speaking the existing `Inference.DetectStream` contract to `localhost:50051`, forwarding only `DetectionResponse`s up the radio link (KB/s of tracks instead of MB/s of video). It needs no change to anything in this module; it is not built because the hardware does not exist.

## Gotchas
- **`ultralytics`' `BYTETracker` resets a PROCESS-GLOBAL track-id counter in its constructor** (T1, verified against ultralytics 8.4.104, not assumed): `BYTETracker.__init__` calls `self.reset_id()` → `BaseTrack._count = 0`, a **class attribute shared by every tracker instance in the process**. Measured consequence with two concurrent streams: stream A allocates id 1, stream B is constructed and allocates id **1** as well, and A's next new object then re-uses an id it has already issued. `ByteTrackEngine._new_tracker` restores `BaseTrack._count` after construction (guarded with `getattr`, so a future ultralytics that drops the attribute degrades silently rather than raising), which makes engine keys unique process-wide — measured A/B/A′ = 1/2/3 with the guard, 1/1/2 without. Belt and braces: `TrackBook` never publishes an engine's key anyway, it maps keys to its own per-stream ids, so even a regression here cannot leak an id across streams. Note the subtlety that bit during this work: assigning `STrack._count` does **not** work — it shadows the attribute on the subclass while `next_id()` keeps incrementing `BaseTrack._count`.
- **In `FOLLOW`, scheduler triggers (b) `TRACKER_FAILED` and (d) `BOX_INVALID` are raised only on tracker-only frames** (T1). They exist to *bring forward* the next verify pass; re-raising them on the verify frame that had already been brought forward asks for a pass that has just happened, and the detector then runs on **every single frame** for as long as the tracker stays unhappy — the duty cycle collapsing back into continuous detection, silently, exactly when the target is hardest. Found while building this (75 detector passes in 149 frames), fixed, and pinned by `test_an_unhappy_tracker_never_collapses_the_duty_cycle_into_every_frame`. The follow-on case — a tracker that reports lost *and* a verify pass that then cannot re-anchor — sets `_tracker_stalled`, after which the session stops calling the engine at all and coasts on the miss schedule until `LOST`.
- **`tracker_millis` on the response is the whole tracker path, including the frame decode, not just the engine call** (T1). That is the honest number for a duty-cycle claim (it is what a tracker-only frame actually costs the server) but it is 3–5× the engine's own cost on a JPEG feed — do not read it as "`lk` costs 2.4 ms". It is also an `int64` of milliseconds on the frozen wire, so a sub-half-millisecond frame reports **0**; on small frames that is the common case, not a bug.
- **`OFF` emits no tracking fields at all, including `detector_ran`** (T1). The frozen contract calls `detector_ran` "the honesty field", but a stream that never asked for tracking has no duty cycle to be honest about, and the acceptance criterion for proto3 additivity here is that an absent `tracking` on the request produces a **byte-identical** response to the pre-T1 service. So `OFF` takes the untouched pre-tracking response path and sets none of fields 8–12; `detector_ran`/`detector_reason` are populated on every `ASSOCIATE`/`FOLLOW` response. Tested by serializing both and comparing bytes.
- **A `FOLLOW` verify pass costs one extra frame decode** (T1): the session decodes the frame to re-anchor the tracker, and `YoloDetector.detect()` decodes it again internally for the model. `_frame_loader` memoizes the session's side so it happens at most once per frame there, but the detector's own decode is that module's contract and is not shared. It affects ~1 frame in 30 in `FOLLOW`, so it was not worth widening `detect()`'s signature to plumb a decoded frame through.
- **`sys.path` gotcha** (unchanged): `protoc`'s Python codegen emits imports rooted at the proto package path (`from vision.v1 import cv_pb2`) — the generated tree's *root* (`cv_service/gen`) must be on `sys.path`. `gen_proto.sh` touches `__init__.py` everywhere so the tree imports as regular packages. Resolved in `cv_service/grpc/servicers.py` (`Path(__file__).resolve().parent.parent / "gen"` — two `.parent`s now that this file lives at `cv_service/grpc/`, not `cv_service/`).
- **protobuf version-scheme note** (unchanged): `protobuf>=5.26.1,<6` vs Java's `protobuf-java` 3.25.5 is not a real mismatch — don't "fix" it.
- **Dockerfile build context** (unchanged): must build from the **repository root** — `docker build -f cv-service/Dockerfile -t cv-service .`. The Dockerfile's `CMD` runs `python -m cv_service.grpc.server` (moved from `cv_service.server`).
- **`opencv-python` vs `opencv-python-headless`**: do NOT add `opencv-python-headless` to the `cv` extra even though it would be preferable for Docker. `ultralytics` hard-depends on plain `opencv-python` (the GUI-enabled build), and pip has no notion that the two packages both provide `cv2` and conflict — installing both leaves whichever installs last silently overwriting the other's files on disk (confirmed locally: uninstalling one after both were present broke `cv2` entirely, `ImportError`). Instead the Dockerfile installs `libgl1`/`libglib2.0-0` at the OS level so plain `opencv-python` imports cleanly in the `python:3.12-slim` image.
- **`CV_MODEL` / weights location**: `YOLO("yolo11n.pt")` (a relative/known-alias name) downloads into the **current working directory** if not already present there — not a global cache dir. Locally this drops `yolo11n.pt` under `cv-service/` when running the server/tests from there; it's gitignored (`*.pt`/`*.onnx`/`*.engine`) — never commit it. The Dockerfile pre-downloads the `.pt` weights the same way at build time from `WORKDIR /app/cv-service`, then (CP-a) exports them to an OpenVINO IR directory (`yolo11n_openvino_model/`, also gitignored via `*_openvino_model/`) and points `CV_MODEL` at that directory instead — both the `.pt` source and the exported IR end up baked into the image so the container needs no network at runtime. Note the Dockerfile's baked default (`yolo11n.pt`) is intentionally independent of `cv_service/config.py`'s `DEFAULT_MODEL` (`yolo26n.pt`, unrelated to what the image bakes) — a docker-only choice, not doc drift. If the export step ever proves unbuildable (network/size), drop the `yolo export` line and leave `CV_MODEL=yolo11n.pt` — the server falls back to plain PyTorch inference, just slower (documented inline in the Dockerfile).
- **`confidence_threshold` ambiguity**: proto3 `float` means an unset `FrameRequest.confidence_threshold` reads as `0.0`, indistinguishable from "explicitly zero". Both `cv_service/grpc/servicers.py` and `YoloDetector.detect()` treat falsy/`None` as "use `DEFAULT_CONFIDENCE` (0.25)" — a caller wanting threshold `0.0` (accept everything) isn't representable on the wire today; not expected to matter for the demo.
- **First-request latency**: model construction + first `predict()` call include Ultralytics warmup (~1s observed locally even with cached weights); `inference_millis` only measures the `predict()` call itself, not model construction. `YoloDetector.__init__` pays this cost itself (a dedicated warmup `predict()` on a black frame, at `self.imgsz`) so the *first real* `detect()` call no longer does — this is what protects adapter-cv-grpc's 2s response timeout from tripping into outage backoff right at stream start. The warmup call runs for injected `model=` doubles too, not just the real model.
- **`imgsz`/OpenVINO export coupling (CP-a)**: `CV_IMGSZ` (default `416`, must be a multiple of 32 by Ultralytics convention — not enforced in code) is passed as `imgsz=` to every `predict()` call, including warmup. The Dockerfile exports the model to OpenVINO IR at build time with a **fixed** input size baked in (`yolo export model=yolo11n.pt format=openvino imgsz=416`) — that export `imgsz` MUST equal the runtime `CV_IMGSZ`, or inference silently runs against the wrong size. If you change one, change both (Dockerfile `ENV CV_IMGSZ=416` and `cv_service/config.py`'s `DEFAULT_IMGSZ` are the two places). Local/dev (non-Docker) runs plain `.pt` weights via `ultralytics.YOLO`, which has no such fixed-size constraint.
- **Warmup failure semantics**: a warmup `predict()` exception (bad model state, OpenVINO backend mismatch, etc.) raises `ModelUnavailableError` from `YoloDetector.__init__`, exactly like a load failure — the registry's `build_default_registry()` catches it and degrades to the echo fallback rather than crash-looping.
- **`LatestOnlyMailbox` drops a frame with no response at all, ever, for that frame's `sequence`** (V-d): a dropped frame never reaches `detect()`, so no `DetectionResponse` is ever produced for it. On the Java side this means that specific pending future simply times out (`adapter-cv-grpc`'s own `RESPONSE_TIMEOUT_SECONDS=2s`, see its MODULE.md) rather than being answered quickly — expected and harmless given how rare drops are meant to be in practice (see "V-d" above), but worth knowing if a dropped-frame's timeout ever shows up in logs: it is not a bug, it's the latest-wins design working as intended.
- **`CV_MAX_CONCURRENT_INFERENCES`/`CV_DEVICE` are no longer import-time-cached** (post-layering-refactor change): before `cv_service/config.py` existed, both were resolved once at *import* time (`concurrency.py`'s `DEFAULT_MAX_CONCURRENT_INFERENCES`, `inference.py`'s `DEFAULT_DEVICE`), so changing the env var after the process started never affected anything already imported. Now `Settings.from_env()` is called fresh each time a value is actually needed (`YoloDetector.__init__`, `ultralytics_train`, `process_gate()`'s first-call lazy build) — still effectively "resolved once per process" for the production path (nothing calls `Settings.from_env()` mid-request), but no longer accidentally frozen at the moment a *module* first happened to be imported, which was never a deliberate design goal, just an artifact of where the old constants lived. Tests that used to monkeypatch `inference_module.DEFAULT_DEVICE`/`concurrency_module.DEFAULT_MAX_CONCURRENT_INFERENCES` directly now `monkeypatch.setenv(...)` instead (see `tests/inference/test_detector.py`/`tests/test_config.py`).
- **`CV_DEVICE`**: `YoloDetector.__init__` reads it fresh per-instance via `Settings.from_env().device` (`device or settings.device`), so a *new* `YoloDetector`/`ModelRegistry` entry constructed later in the same process picks up whatever `CV_DEVICE` currently resolves to. A bad/unavailable device (e.g. `"cuda:0"` with no GPU present) is not special-cased: it surfaces as a normal warmup-`predict()` exception, which `YoloDetector._warmup` already converts to `ModelUnavailableError` like any other load/warmup failure — the servicer degrades to echo mode exactly as it would for a bad `CV_MODEL`.
- **Test-only nuance if you add more `DetectStream` tests with multiple frames**: any test iterator delivering 2+ frames with no artificial per-item delay races `_StreamReader`'s background thread against however fast the test happens to get scheduled — the reader can (and, empirically, sometimes does) put and overwrite several items before the consumer's first `get()` call, which is `LatestOnlyMailbox` correctly doing its job against a producer that (in the test) is unrealistically instantaneous, not a bug. Tests asserting an exact multi-frame response count/order use a small artificial per-item delay (`_PacedIterator`/`_DelayedIterator` in the test files) to avoid this — a real network is never actually instantaneous, so this is purely a test-engineering concern, not a production one.
- **Registry base dir is resolved from `Settings.model_dir`, not `os.getcwd()`** (CP-b, unchanged by the layering refactor): `Settings.model_dir` defaults to `Path(__file__).resolve().parent.parent` computed **from `cv_service/config.py`** (i.e. always `cv-service/` regardless of the directory the process happens to be launched from — `cv_service/config.py` sits at the same depth under `cv-service/` that `cv_service/server.py` used to, so the computed default is unchanged) — deliberately more robust than the cwd-relative behavior `ultralytics.YOLO("x.pt")` itself uses for *downloading* a not-yet-cached alias (see "`CV_MODEL` / weights location" above), which is still cwd-dependent and unchanged; discovery just needs to reliably *find* whatever's already sitting in the checkout, not decide where a fresh download lands.
- **Docker image bakes an OpenVINO export only for the default model (`yolo11n`)** (unchanged): the Dockerfile's `yolo export ... format=openvino` step (CP-a) only runs for `yolo11n.pt`; `orion12l.pt` is present in the image (the `COPY cv-service/ ./cv-service/` step copies it, same as any other checked-in file) but the registry would load it via plain PyTorch inside the container too, same as locally — functional, just without OpenVINO's ~2-3x CPU speedup.
- **`detect_composite` logs each member's `inference_millis` at DEBUG, not INFO** (CP-b): this runs once per resolved model per *frame* (so up to 10+/sec per stream at the sampling rate `PipelineConfig.inferenceFps` targets) — INFO would spam logs at anything above a trivial frame rate. DEBUG keeps it available (`logging.getLogger("cv_service.inference.registry").setLevel(logging.DEBUG)`) without being on by default; contrast with the once-per-distinct-id unknown-model/load-failure warnings elsewhere in this module, which stay at INFO/WARNING because they're bounded (once per id, not once per frame).
- **`test_real_model.py`'s per-local-model and composite smoke tests skip (not fail) if a weights file is absent** (CP-b): `orion12l.pt` is a large (53MB), user-provided, gitignored file (see docs/CV-MODELS-PLAN.md's provenance note — **never fetched from the network**, only ever the checked-out local file) — a clone without it present still gets a green (skipped, not failed) test suite, same contract `tests/inference/test_real_model.py`'s original `real_detector` fixture already established for "ultralytics not installed at all".
- **grpc Python servers GOAWAY ("too_many_pings") a client that pings with no active calls, by default** (docs/REMOTE-CV-PLAN.md "Transport decisions" P1): `adapter-cv-grpc`'s `GrpcDetectionPort` pings every `KEEPALIVE_TIME_SECONDS` (20s) *including while idle* (`keepAliveWithoutCalls`, needed because a stream mid-`StreamPipeline`-outage-backoff has no in-flight RPC to piggyback a ping on) — without `grpc.keepalive_permit_without_calls=1` in `_KEEPALIVE_SERVER_OPTIONS`, this server would tear down that exact connection as abusive, defeating the client-side tuning entirely rather than helping it. `grpc.http2.min_ping_interval_without_data_ms=10000` is deliberately half the client's 20s interval (jitter headroom), not equal to it.
- **`StartTraining` on this host trains on CPU — it is genuinely SLOW** (CV-TRAINING Phase 2): the production deploy box (GB4005) is Intel-only / no CUDA (MEMORY: gb4005-inference-box), an inference appliance. A real multi-epoch fine-tune there can take a very long time; the trainer logs a one-time `"training on CPU — this is slow"` warning (`trainer._warn_cpu_once`). Device is **never hard-pinned to CPU** — `CV_DEVICE` (auto if unset) lets a GPU training-host build run on CUDA with zero code change. The honest operational path stays *train on a GPU box → rsync the artifact in → `PromoteModel`* (the `StartTraining` CPU path is buildable/correct, just slow).
- **Datasets must be rsync'd or uploaded onto the training host first** (CV-TRAINING Phase 2 / CV-TRAINING-V2): `StartTraining` does **not** receive dataset bytes over gRPC itself — `TrainingJobSpec.dataset_id` resolves to an already-present exported-YOLO dir at `<CV_DATASET_DIR>/<dataset_id>/` (`data.yaml`+`images/`+`labels/`), landed either by manual rsync or by `Training.UploadDataset`. A dataset that hasn't been copied in yet is a **normal reported outcome** — one `TrainingProgress{state:FAILED, message:"dataset <id> isn't on the training host — export it and copy it in first"}` then end-of-stream, **not** a gRPC abort. `datasets/` + `runs/` are gitignored (runtime data).
- **Produced training artifact naming + non-promotion** (CV-TRAINING Phase 2): a successful `StartTraining` copies `best.pt` into the model dir as **`<dataset_id>-<epochs>e.pt`** (deterministic; re-training the same dataset+epochs overwrites) and `ModelRegistry.register()`s it so `ListModels` shows it (`stage="available"`) immediately, no restart. It is **NOT** auto-promoted — the operator calls `PromoteModel` deliberately. If `registry is None` (echo mode), the artifact is still written and gets picked up by `discover_roster` on the next restart.
- **`StartTraining`'s `.train()` runs off the gRPC stream thread** (CV-TRAINING Phase 2): the blocking multi-minute training runs on a **background worker thread** managed by `cv_service.training.orchestrator.run_training_job`; the RPC generator only polls a `queue.Queue` for progress + yields, so a long train never wedges the server's `ThreadPoolExecutor` worker into an unresponsive state and client/`context` cancellation is honored promptly.
- **Ultralytics fires `on_fit_epoch_end` once extra** (CV-TRAINING Phase 2): after the last training epoch it runs a final validation and fires `on_fit_epoch_end` again with `trainer.epoch == trainer.epochs` (0-indexed), re-reporting the last epoch's metrics. `ultralytics_train` **suppresses** that trailing call so the stream carries exactly one `RUNNING` per epoch (never `epoch > total_epochs`). Verified against ultralytics 8.4.x via a throwaway 1-/2-epoch real train (not in the suite — CI never runs a real train).
- **`test_serve_passes_keepalive_options_to_grpc_server` fakes every collaborator `serve()` touches except `grpc.server` itself** (monkeypatches `InferenceServicer`/`TrainingServicer`/`add_*Servicer_to_server`/`_build_default_registry` to no-ops): calling the real `InferenceServicer()` default constructor would eagerly load whatever model the registry finds on disk, which is slow and environment-dependent — irrelevant to what this test actually checks (the `options=` kwarg reaching `grpc.server`).
