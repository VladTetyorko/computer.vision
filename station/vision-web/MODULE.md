# vision-web

Angular 21 SPA (driving adapter): the whole product UI — operator cockpit, manager dashboard, tactical map, asset/device management, replay, CV training — talking only to vision-api's REST/SSE surface, built into vision-app's jar.

**Depends on:** nothing internal (HTTP only) · Angular 21 (`core|common|forms|router|cdk`), **NgRx 21** (`store|effects|entity|router-store|operators` — the state engine, see [`core/state/`](#corestate--the-state-engine)), `hls.js`, `leaflet` (lazy, and see Gotchas), `rxjs` (effects, WS, preload) · dev/test: `@angular/cli|build`, `@ngrx/store-devtools`, `vitest`, `jsdom`
**Used by:** vision-app (packages `dist/` into `META-INF/resources`; vision-api ships no static resources)
**Build/test:** `./mvnw -B -pl station/vision-web clean install` · `-DskipWeb=true` skips Node+Angular entirely · tests `npm run test:ci` (**never** raw `npx vitest`, see Gotchas) · dev `npm start` (proxies `/api`, `/actuator`, `/legacy`, `/hls` → `:8080`)

## API surface

### `core/api/` — the only place wire shapes live
- `models.ts` (~3000 lines) — every DTO, mirroring Java 1:1. Change a Java DTO → fix here first, then `grep -rn` the field.
- `VisionApi` (~123 methods) — thin `firstValueFrom` wrappers over `HttpClient`; no component calls `fetch`/`HttpClient` directly.
- `api-error.ts#describeHttpError(err)` — the one place an HTTP failure becomes user text.
- **`ControlProfile` gained required `stickMode`/`forwardIsUp`; `UpdateControlProfileRequest` gained
  the same pair as optional** (docs/plans/active/CONTROLLER-SETUP-CONTEXT.md wave C15, reconciled here
  as part of merging `feat/controller-setup-c15`) — the owner's transmitter arrangement (mode 1-4,
  which way a vertical axis reads), stored per layout rather than per browser. An older/omitting
  caller of `UpdateControlProfileRequest` gets the platform default read back on the next fetch. See
  `TransmitterView`/`WizardStep` below for where the setup UI reads/writes this.
- **`BatteryThresholds`/`OpsThresholdsResponse` (S3, docs/plans/active/ASSET-FLOWS-PLAN.md §2)** — the
  wire mirror of `GET /api/ops/thresholds`, `VisionApi#opsThresholds()`. **`DiscoveryInboxResponse` now
  wraps `DiscoveryCandidate[]` in `{candidates, sources}`; `DiscoverySource` (`{id, status: 'OK' |
  'UNREACHABLE'}`) is new (A3, same plan §2)** — `listDiscoveryInboxCandidates()`'s return type changed
  accordingly; see `core/ops/`/`core/discovery/` below for the consumers. `AssetUsage`/`UsageSummary`
  both gained an optional `pilotId` mirroring the backend's own addition (no frontend consumer yet).
- **`FollowState`/`FollowStatus` (new) + `StreamTracksResponse.follow?: FollowStatus`** (docs/plans/active/
  TRACK-FOLLOW-PLAN.md §3.1, wave W4) — the follow lock's own lifecycle, orthogonal to the sibling
  `lockedTrackId` sentinel on the same response (which reads `0` in `LOST` while `follow.trackId`
  stays bound). `FollowState = 'REQUESTING'|'HOLDING'|'COASTING'|'LOST'|'RELEASED'`. Omitted entirely
  (not `null`) when no lock was ever issued or after one `RELEASED` read. See `shared/player/`'s
  `follow-hud/` bullet below for the one reader.
- **`SeatKind`/`SeatHolderResponse`/`SeatsResponse`/`TakeSeatRequest` (new)** (docs/plans/active/
  CREW-CONTROL-PLAN.md §3.6, wave W3) — `GET /api/assets/{id}/seats`/`POST .../seats/{kind}`'s wire
  shape, byte-exact: explicit-null holder fields (`holderUserId`/`holderDisplayName`/`acquiredAt`/
  `expiresAt`, all `null` on a free seat, `mine` included) and three `may*` authority booleans that
  are purely server-derived — the frontend never re-derives authority from role/capability. `{kind}`
  is `flight`|`camera`, lowercase exactly (`VisionApi#takeAssetSeat`/`releaseAssetSeat` lowercase the
  `SeatKind` union on the way out). See `core/seat/`/`features/crew/` below for the one consumer.
- **`ObjectState` family (new, type mirror only — no endpoint serves it yet)** (docs/plans/active/
  CV-ORCHESTRATION-PLAN.md §4.5, wave W1 "wire mirror") — `ObjectState`/`ObjectIdentity`/
  `ObjectLabelCandidate`/`ObjectKinematics`/`ObjectBelief`/`ObjectProvenance`/`ObjectMemoryFacts`/
  `ObjectLockFacts`/`ObjectTiming`, plus `OBJECT_LIFECYCLES`/`ObjectLifecycle` and
  `EVIDENCE_SOURCES`/`EvidenceSource` (`as const` tuple + derived union, same idiom as
  `DETECTION_STATES`/`DetectionState`, each pinned by its own `*.contract.spec.ts`). Every nested
  group (`identity`/`kinematics`/`belief`/`provenance`/`memory`/`lock`/`timing`) is **optional**, not
  nullable — the DTO layer serializes `NON_NULL`, so a Java `null` group is a missing key, meaning
  "this configuration does not compute these facts," never a zeroed default; same rule for
  `kinematics.detectorBox`/`trackerBox`/`predictedBox` (`kinematics.box` alone is always present).
  `streamId` is a plain string on the wire. Nested TS interfaces are named `Object*` rather than the
  Java records' own bare names (`Identity`, `Belief`, `Timing`, …) because TS has no per-record
  nesting scope the way Java does — collapsing them to the Java names would collide with (or shadow)
  unrelated concepts elsewhere in this 4000-line file. **Nothing constructs, fetches, or renders an
  `ObjectState` yet** — no store, no component, no route; rendering is wave W3's job. See
  `core/api/models.ts`'s own doc comment on `ObjectState` and the two contract specs for detail.
- **`LinkCarrierKind`/`LinkSerialRole`/`LinkQualityView`/`LinkView`/`LinkGroupResponse`/`CarrierSummaryResponse` (new, docs/plans/active/LINK-PAIRING-PLAN.md §3.4, wave L4)** — the body of `GET /api/assets/{id}/links` and the `links:<assetId>` SSE topic's payload (`LinkGroupResponse`, whole-list-snapshot not a diff). `GET`/`PUT .../links/{linkId}/pin`/`DELETE .../links/pin` are now confirmed **mounted and working** (`AssetLinksController`, live-walked via direct curl §8, 2026-09-18) — the earlier "no server-side controller exists yet" note is stale; field names here were not independently re-diffed against the Java DTO this wave (LF2 was web-only), so still treat a mismatch as the first thing to check if a link row ever renders emptily where the curl check didn't. `CarrierSummaryResponse` (station-wide `GET /api/carriers`) remains unconsumed by any store. See `core/pairing/`/`asset-detail/`'s Links-panel bullets below for the one consumer.
- **`SystemNetworkResponse.simulationEnabled?: boolean` (new, docs/plans/active/LINK-PAIRING-PLAN.md §4 row L4)** — **assumed for L2, not yet a real field**; no dedicated capability endpoint exists anywhere in this app, so this reuses the one deploy-time config response the onboarding wizard already reads. `features/playground/playground-facade.ts` defaults to `true` (enabled) both pre-fetch and when the field is absent — an un-upgraded backend or a failed fetch keeps today's "simulate creation is unconditionally available" behavior rather than silently losing the feature.

### `core/state/` — the state engine

**NgRx 21.1.1** (`store`, `effects`, `entity`, `router-store`, `operators`; `store-devtools` in dev)
is the app's state engine. The migration off the 32 hand-rolled store classes runs wave by wave —
docs/plans/active/NGRX-MIGRATION-PLAN.md is the spec, its §9 the status. **Both shapes are live right
now**: the table below still lists the hand-rolled stores that have not moved yet.

| Piece | Where | Rule |
|---|---|---|
| root registration | `core/state/app-state.ts#provideAppState()` | every app-wide slice + its effects + its hydrators, used verbatim by `app.config.ts` **and** by specs, so a test can never register a subset that drifts from what ships |
| persistence | `core/state/hydration.ts` | a meta-reducer is the *only* way a persisted value enters state (`INIT` **and** `UPDATE`, so lazily-provided slices hydrate too); writes go the other way, through effects |
| a slice | `core/<domain>/state/<domain>.{model,actions,reducer,effects,hydration}.ts` | `createActionGroup` per event source · `createFeature` for selectors · functional effects · reducers pure |
| its boundary | `core/<domain>/<domain>-facade.ts` | the only type that injects `Store` besides effects; exposes `Signal<T>` and dispatch methods, named `<Domain>Facade` — a settled rename, not the old store class's own name |
| page-scoped slices | `features/<feature>/state/…`, provided in that feature's `*.routes.ts` | loaded and torn down with the page — **not** the same thing as a page-scoped *facade* over an app-wide slice (`SeatFacade`, `core/seat/` above): the slice/effects still register once in `provideAppState()`, only the facade class itself is `@Injectable()`/component-provided |

`SidebarStore`, wave N0); **`overlay`** (`core/ui/state/`, replacing `GlobalOverlayStore`, wave N1);
**`settings`**, **`org`**, **`seat`** and **`auth`** (`core/<domain>/state/`, replacing
`SettingsStore`/`OrgStore`/`SeatStore`/`AuthStore`, wave N2); **`live`** (`core/live/state/`,
replacing `LiveStore`, wave N3 — see the dedicated paragraph below for its non-serializable
`LiveGateway` seam); **`telemetry`**, **`detections`** and **`cv-trace`** (`core/<domain>/state/`,
replacing `TelemetryStore`/`DetectionsStore`/`CvTraceStore`, wave N5 — see the stores table below for
each slice's own poll-vs-live shape, and cv-trace's deliberate lack of one); **`training`,
`thresholds`, `controlProfile`, `weather`, `geo`, `links`, `discoveryInbox` and `events`**
(`core/<domain>/state/`, replacing `TrainingStore`/`ThresholdsStore`/`ControlProfileStore`/
`WeatherStore`/`GeoStore`/`LinksStore`/`DiscoveryInboxStore`/`EventsStore`, wave N7 — eight
independently-sized stores (69–319 lines) converted together as one wave; see the `core/**` stores
table below for each slice's own shape); and **`map`**, **`marks`**, **`layers`**, **`drawings`**,
**`tracks`**, **`route`** and **`geofence`** (`core/map/state/`, `core/map-data/state/`,
`core/geofence/state/`, replacing `FleetMapStore`/`MarksStore`/`LayersStore`/`DrawingsStore`/
`TracksStore`/`RouteStore`/`GeofenceStore`, wave N6 — `@ngrx/entity` backs the four collections, and
`FleetMapStore`'s "construction is demand" contract needed an explicit `activeConsumers` ref-count to
survive being registered app-wide; see that wave's own paragraph below); and **`fleet`** and
**`systemStatus`** (`core/fleet/state/`, `core/system-status/state/`, replacing `FleetStore`/
`SystemStatusStore`, wave N4b — both root-registered, since `app.ts`/`AppSidebar`/`NotificationBell`
inject one or both before any lazy route loads, so neither is N-split-eligible; `fleet`'s
`devices`/`streams` are `@ngrx/entity` collections. **`systemEvents` converts to a plain renamed
facade with no NgRx slice at all** — see the dedicated paragraph below for why, and for the
correction that makes to NGRX-MIGRATION-PLAN.md §4's "N4 fleet: 3 (fleet = entity)" row); and
**`onboardingWizard`** (`features/onboarding/state/`, replacing the 1656-line `OnboardingStore`, wave
N8b — page-scoped, registered on `onboarding.page-routes.ts` beside `provideDiscoveryState()`, never
in `provideAppState()`; see the dedicated paragraph below for its `OnboardingPhotoBuffer` split); and
**`grounding`** (`features/fly/state/`, replacing `GroundingStore`, wave N8a — page-scoped on
`fly.page-routes.ts`, and the smallest slice in the app: one asset id, one `ReadinessReport`, one
one-shot read, no poll and no live axis).

Wave N7 settled two demand-gate idioms later slices can reuse: **`byHostId`/`byAssetId`-keyed, page-provided facades that own their own live-bridging
constructor `effect()`** (`WeatherFacade`/`GeoFacade`/`LinksFacade` — mirrors the session slices' own
`seat` idiom above, just with a live projection added), and **root-singleton facades whose ref-count
lives in NgRx state itself**, with the poll-vs-live *phase* computed inside the effects file via
cross-slice `store.select()` — never by injecting another slice's facade into an *effect* (a facade
injecting another facade is fine; an effects class must only ever cross-select) —
`DiscoveryInboxFacade`/`EventsFacade`, see their own rows below for the full `combineLatest`+
`distinctUntilChanged`+`switchMap` shape. Runtime checks are all four on. Router state is mirrored
with `MinimalRouterStateSerializer` — the full serializer holds component classes and would trip
`strictStateSerializability`.

**Nothing is hand-rolled any more — wave N8 was the last one.** Two classes survive that migration by
explicit decision, and neither is an oversight:
- `core/ui/ui-store.ts#UiStore` — NGRX-MIGRATION-PLAN.md §8: a deliberately plain class with no DI
  token, instantiated 27 times as a host-owned field, one per independent overlay *group*. NgRx
  feature state is global by name and cannot express 27 independent instances. **Must not become a
  slice.**
- `features/inventory/inventory-view-storage.ts#InventoryViewStorage` — renamed from
  `InventoryViewStore` in wave N8a, because it is a `localStorage` adapter, not a store: two methods,
  no signals, no fetch, no timer. The state it guards is one enum among ~20 plain page signals on
  `InventoryFacade`; promoting exactly that one to a feature slice would be arbitrary, and whatever
  remained would still be this wrapper, since `core/state/hydration.ts#StateHydrator.read()` would
  have to call something just like it. Same "decline the ceremony, write down why" call as
  `systemEvents` in N4b — see the class's own doc comment.

Note for whoever adds the first persisted page-scoped preference: `hydrationMetaReducer`'s `UPDATE`
branch already exists so a lazily-registered feature slice can hydrate, and **nothing exercises it
yet** — all three current hydrators (`theme`, `sidebar`, `settings`) are root slices hydrated at
`INIT`.

**`onboardingWizard` (wave N8b) is the biggest single-file store this migration has converted** — 1656
lines, 66 signals, 13 computeds, ~60 methods, 21 direct `VisionApi` calls — and the second slice
(after `overlay`) to need a non-serializable split. Three things stay out of
`features/onboarding/state/onboarding.model.ts#OnboardingWizardState` rather than the slice:
`OnboardingPhotoBuffer` (`features/onboarding/onboarding-photo-buffer.ts`, a plain page-provided class,
same posture as `OverlayHostRegistry`/`LiveGateway`) owns the photo `File`/`Blob`/object-URL —
`uploadAssetImage$` reads its `currentBlob` directly, degrading to a no-op success when none is
buffered, since a `Blob` can never be an action payload under `strictActionSerializability`;
`preProvenRoles` is a plain `readonly FitOutRole[]` rather than the old class's `ReadonlySet` (Sets
are not serializable either — every `.has()` call site became `.includes()`); and the discovery-status
poll is `state/onboarding.effects.ts#discoveryStatusPoll$`, gated on `store.select` of
`step === 'source'`, rather than a `PollScheduler` handle the old class held as a field. **One
subtlety worth knowing before copying this pattern**: `OnboardingPhotoBuffer` is bundled into
`state/onboarding.providers.ts#provideOnboardingState()` itself, *not* `OnboardingPage`'s own
component `providers:`, even though only the page (via its facade) reads it — an `@ngrx/effects`
class's `inject()` calls resolve against the *environment* injector its `provideEffects()` was
registered on, never a component's element injector, so a service only an effect needs must be
registered at the same environment-injector level as the slice, not the component. The new
`OnboardingWizardFacade` (not folded into the pre-existing `OnboardingFacade`, which keeps its `store`
field name but now injects this class instead) reproduces `OnboardingStore`'s full public surface
field-for-field; the one break is structural, not behavioural — a handful of templates called a
writable `store.someSignal.set(value)` directly, which an NgRx facade's read-only `Signal<T>` can
never expose (§3 rule 8), so each became a `setXxx(value)` dispatch method on the facade instead. Cost
folded into the measurement below (route-scoped, so negligible — see that paragraph's own note).

**`overlay` is the first slice with real DOM behaviour** (docs/plans/active/NGRX-MIGRATION-PLAN.md
§8), so it splits across more than one file: `core/ui/state/overlay.{model,actions,reducer,effects}.ts`
hold only the serializable half — the open `GlobalOverlayId | null` — while
`core/ui/overlay-host-registry.ts#OverlayHostRegistry` (a plain `providedIn: 'root'` class, **not** a
slice) holds the live `HTMLElement` `{root, trigger}` pairs a `register()` call needs; either one going
into state would trip `strictStateSerializability` on the first `register()`. `overlay.effects.ts` owns
the three lifecycle rules `UiStore` alone never had to: close-on-navigation (listens for
`@ngrx/router-store`'s `ROUTER_NAVIGATED` action rather than injecting `Router` — every spec that calls
`provideAppState()` without a `Router`, `theme-facade.spec.ts`/`sidebar-facade.spec.ts` included, must
still construct cleanly), close-on-`Escape` (returns focus to the registered trigger), and
close-on-outside-click (never fighting the trigger's own `(click)`). `core/ui/overlay-facade.ts#OverlayFacade`
is the one consumer-facing surface — same `active`/`isOpen`/`open`/`close`/`toggle`/`register` names
`GlobalOverlayStore` had. **The reducer does not compose `UiStore`** (the old class did, for
exclusivity) — "opening any id replaces whichever was open" is now a plain assignment, simpler than
reaching for a second primitive for behaviour `createReducer` already gives for free. **`UiStore`
itself stays unmigrated** (see its own row below) — host-owned, DI-less, instantiated per overlay
*group* across 27 call sites; NgRx feature state is global by name and cannot express that.

**The session slices** (wave N2) carry two idioms later waves reuse. `seat` is **page-provided but
app-wide-stored**: `SeatFacade` stays `@Injectable()` in its host's `providers:` exactly as
`SeatStore` was, while the slice itself is keyed by `assetId` and its effects `groupBy(assetId)` +
`mergeMap`, so two hosts tracking two assets get independent, non-cancelling poll/renewal pipelines
— isolation lives in the data shape, not the injector tree. And `core/state/dispatch-bridge.ts#dispatchAndAwait`
lets a facade keep returning `Promise<T>` for callers that branch on the result (org's 5 mutations,
auth's `login`/`changePassword`/`bootstrap`); `logout`/`bootstrapRequired` await their one success
action directly, having no natural failure counterpart to pair with. `AuthFacade`'s constructor
dispatches its own `bootRequested()` rather than waiting on `ROOT_EFFECTS_INIT`, which is what makes
its `ready: Promise<void>` race-free — see that class's doc comment for the `ENVIRONMENT_INITIALIZER`
ordering argument.

**Cost, measured on the merged tree after N6+N7+N-split+N4a+N4b:** **512.34 kB raw / 146.06 kB
transfer**, against a pre-NgRx baseline of 442.45 kB / 123.81 kB. The engine itself was 45 kB of
that at N0; the slice waves added the rest. **Wave N-split gave back 46.05 kB** (587.42 → 541.37)
by registering page-scoped slices on their own routes instead of at the root injector, and **wave
N4a gave back a further 43.61 kB** (541.37 → 497.76, 52.24 kB of headroom — briefly *under* the
500 kB warning line for the first time since N2 — by moving six more facades off the root
injector: `MarksFacade`, `LayersFacade`, `DrawingsFacade`, `TracksFacade`, `GeofenceFacade`,
`OrgFacade`). **Wave N4b then cost +14.58 kB raw / +3.03 kB transfer back** (497.76 → 512.34) for
its two new root slices, `fleet` and `systemStatus` — neither is N-split-eligible, since
`app.ts`/`AppSidebar`/`NotificationBell` inject one or both before any lazy route loads (the
eligibility test is "does every class injecting this facade already sit behind a lazy route", not
consumer count). `ng build --configuration production` is **green** (exit 0) with 37.66 kB of
headroom under `angular.json`'s 550 kB error budget; it is back over the 500 kB *warning* line by
12.34 kB, which is a warning by design and was already true before N4a's split. **`angular.json`
was not touched** — raising a failing budget is an owner's policy decision, not a wave's. This
number is re-measured on the merged tree after every wave; the per-wave deltas above are *not*
additive. **Wave N8 (N8a + N8b) measured 512.34 kB raw / 146.04 kB transfer** — raw unchanged, transfer
0.02 kB *down* — confirming `onboardingWizard` stayed correctly page-scoped (`onboarding.page-routes.ts`
alongside `provideDiscoveryState()`, never `provideAppState()`): the whole slice, its effects, and
`OnboardingPhotoBuffer` ship only in the `onboarding` lazy chunk (100.16 kB raw / 21.14 kB transfer),
never the initial bundle this paragraph measures.

**What N-split actually moved, and the rule it followed.** 13 of the 26 slices remain root-registered
in `core/state/app-state.ts`; the other 13 are registered by the route of the page that reads them,
through a `core/<domain>/state/<domain>.providers.ts#provide<Domain>State()` each. The rule is not
"few consumers" but **"every class that injects the facade already sits behind a lazy route"** — a
`providedIn: 'root'` facade outlives the route that registered its slice and would then select a
feature NgRx has removed. Four facades (`ThresholdsFacade`, `ControlProfileFacade`, `TrainingFacade`,
`DiscoveryInboxFacade`) were converted from `providedIn: 'root'` to page-provided in this wave to
make their slices eligible; **each carries in its own doc comment the one behaviour that changed** —
state loaded per page visit rather than per session, so two pages that used to share one fetch now
each fetch. `OrgFacade` is the one that failed the test and stayed root: `shared/map/map-controls/
layer-manager.ts` injects it, and that control renders on several map surfaces.

**The constraint that made it a wave rather than an edit:** `app.routes.ts` imports every feature's
route file **statically**, so a `providers:` array there drags the slice it names back into the
initial bundle. Twelve features are therefore now `loadChildren` boundaries, with the real routes and
their providers in a sibling `<feature>.page-routes.ts`. Two consequences worth knowing before
touching routes: a boundary **prefix-matches** where a plain `loadComponent` route had to consume the
whole URL, so the `/assets` and `/manage/training` families are ordered longest-path-first in
`app.routes.ts` and `app.routes.spec.ts` asserts that order by index; and the static `children` walk
in `features/hubs/route-audit-logic.ts` cannot see past a boundary, which is why `flattenRoutesDeep`
(async, resolves `loadChildren`) exists and is what `app.routes.spec.ts` uses.

**The migration is a net bundle cost, not a wash — say so rather than hoping.** Every wave so far
added bytes *despite* deleting the store it replaced (N1 +0.89, N2 +12.47, N3 +5.04, N5 +9.96, N7
+24.62, N6 +47.21 kB raw, the last two for eight and seven slices at once): a slice — model, actions, reducer, effects,
facade, plus `createFeature`/`@ngrx/entity` machinery — ships more code than the hand-rolled class it
replaces. What is bought with it is one state engine instead of 32 re-implementations, and that is
the trade to judge. Re-measure per wave; never add two waves' separately-measured deltas together.

**`live` is the first slice to isolate a genuinely non-serializable resource** (docs/plans/active/
NGRX-MIGRATION-PLAN.md §8) — the browser's own `EventSource`. `core/live/live-gateway.ts#LiveGateway`
(a plain `providedIn: 'root'` class, **not** a slice, same posture as `OverlayHostRegistry`) owns it
exclusively: `isAvailable()` degrades honestly when `EventSource` doesn't exist at all (jsdom, every
spec), `open(topics)` returns a cold `Observable<LiveGatewayEvent>` wrapping the real connection —
`live.effects.ts#connection$` is the only subscriber, turning each `LiveGatewayEvent` into a
`LiveSocketActions` dispatch and owning the manual `SSE_RETRY_INTERVAL_MS`-spaced retry loop on a
`'fatal'` open (non-2xx/wrong-content-type; a transient drop is the browser's *own* native reconnect,
reported as `'retrying'` — unchanged from `LiveStore`, **including its one accepted gap**: a topic
ref-count change during a native auto-retry is missed until the next full reconnect, since the browser
silently re-fetches the *previous* URL). Every `trackX`/`untrackX` ref-count lives in the slice itself
(`topicRefs: Record<string, number>`) — the reducer increments/decrements synchronously (NgRx
guarantees a dispatched action's reducer runs before any effect observes the same action), so
`patchOnTrack$`/`patchOnUntrack$` reading `topicRefs[topic] === 1` (or absent, after decrementing)
right after the reducer ran reliably means "first subscriber"/"last unsubscriber" — the only two
moments that PATCH `/api/live/{connectionId}/topics`. `core/live/live-facade.ts#LiveFacade` is the
read/dispatch boundary, keeping every one of `LiveStore`'s own signal and method names — so all 25
consumer files changed only their `inject(LiveStore)` line to `inject(LiveFacade)` — plus the same
per-asset `Signal` identity cache (`Map<assetId, Signal<T>>`) the old class kept, since a derived,
cached `Signal` is local bookkeeping, never itself state. **Fourteen topics now** (`fleet`, `event`,
`telemetry`, `detections`, `devices`, `detection-events`, `map`, `geo`, `discovery`, `zones`,
`system`, `tracks`, `cv-trace`, `links`) — see `LiveFacade`'s own class doc for the full per-topic
framing, corrected from a stale "twelve" this wave found.

**A production defect this wave found and fixed, not a test artifact**: `auth.effects.ts`'s
`reconnectLiveOnSession$`/`logoutSideEffects$` used to `inject(LiveFacade)` as an eager `createEffect`
factory default parameter. `@ngrx/effects`' own `EffectsRootModule` constructor calls `runner.start()`
(subscribing the merged action stream) **before** looping over `provideEffects(...)`'s groups to
`addEffects()` each one, in that call's own array order — and `app-state.ts` registers `authEffects`
ahead of `liveEffects`. Resolving `authEffects`'s factories eagerly constructed the `LiveFacade`
singleton, running its constructor-time `reconnect()` dispatch, **before** `liveEffects.connection$`
had even been created to receive it — silently dropping the boot-time reconnect every time, masked in
practice only because `AuthFacade`'s own later `bootstrapSucceeded` dispatch re-triggers
`reconnectLiveOnSession$` well after every effect is live. `live-facade.spec.ts`'s "degrades to closed
shortly after construction" case is what caught it (deterministic, not flaky — confirmed by bisecting
against a byte-for-byte copy of `live-facade.ts` under a different class name, which passed). Fixed by
injecting a plain `Injector` and resolving `Injector.get(LiveFacade)` **inside** each effect's own
callback instead of as a factory parameter, deferring construction until the action genuinely fires —
see `auth.effects.ts#reconnectLiveOnSession$`'s own doc comment for the full mechanism.

**Wave N6 converted all seven map/geofence stores in one pass** (`FleetMapStore`→`MapFacade`,
`MarksStore`/`LayersStore`/`DrawingsStore`/`TracksStore`/`RouteStore`/`GeofenceStore` → their
`*Facade` siblings) — the largest wave by line count, but mechanical: every consumer changed only its
one `inject(XStore)` line. `@ngrx/entity` (`createEntityAdapter<T>({selectId})`) fits all four
collections (`marks`, `layers`, `drawings`, `tracks`) cleanly with the same shape each time — no
`sortComparer` (display order is a pure derivation, not storage order), a live/REST envelope folds
through the domain's existing pure `apply*Events` function first and the *result* goes into
`adapter.setAll([...], state)`, never a per-field entity mutation. One adapter quirk worth knowing:
**`setAll` always returns a new state object, even when the resulting array is unchanged** — a reducer
spec asserting a true no-op must use `.toEqual`, not `.toBe`, for a "map" envelope that doesn't match
this slice's entity (the *other-topic* branch, which returns the literal unchanged `state` with no
`setAll` call, is correctly still `.toBe`). Domain semantics carried over exactly: a mark or drawing
event with `action: 'cleared'` **removes** the entity outright (a status transition the fold treats as
a removal, same as `'deleted'` — it does not linger with `status: 'CLEARED'`), and a layer arriving
over SSE with no `grants` field keeps the previously-known grants rather than clobbering them to
`undefined` (`layers.reducer.ts`'s `adoptLayer`).

**`MapFacade` and `RouteFacade` are page-provided (`@Injectable()`, not `providedIn: 'root'`)**,
`CommandPage`'s own `providers:` — same posture as the stores they replace. This exposed the one real
plan-shaped defect the wave found: `FleetMapStore` had **no ref-count at all** — its own construction
*was* its demand signal, since a page-provided class's lifetime already matched the page's. An NgRx
slice can't express that (it's registered once, root-scoped, in `provideAppState()`, and stays
subscribed for the app's lifetime) so `map.effects.ts#assetGate$` needed a **new** `activeConsumers`
ref-count on the `map` slice itself, bumped/dropped from `MapPageActions.activated()`/`released()` in
the facade's constructor/`DestroyRef.onDestroy` — the same idiom every other ref-counted row in the
table below already used, just newly applied here. `RouteFacade`'s constructor dispatches `hide()` on
every mount for the same reason in miniature: the `route` slice is app-wide storage for a page-scoped
concept, so a fresh page visit must not render the previous visit's stale span before its own `show()`
call lands.

## Conventions

- Standalone components, `OnPush`, signals for all state, **zoneless** (no `zone.js`).
- **Three files per component** — `.ts`/`.html`/`.css`. Never inline `template`/`styles`; split any component you touch.
- **Component → Facade → Store → Service.** Every *routed* feature has a `<feature>-facade.ts` (`@Injectable()`, in the page's own `providers`) owning all injection, `computed()` read-models (incl. every `canX`/disabled predicate) and HTTP commands. The page injects **only its facade** (+ host-owned `UiStore`) — enforced by `core/ui/architecture.spec.ts`, which globs `features/**` only. Non-routed presentational children may inject a shared store directly. "Store" here means an **NgRx slice** for anything already migrated (docs/plans/active/NGRX-MIGRATION-PLAN.md) and a hand-rolled store class for the rest; no component injects NgRx's `Store`, only a `*-facade.ts` or a `*.effects.ts` may — the same spec's NgRx layering guard, which additionally asserts reducers stay pure (no `inject`/clock/random/`localStorage`/DOM) and that every `*.reducer.ts` has a sibling `*.actions.ts` and spec.
- Mutually-exclusive overlays go through `UiStore`, never independent booleans.
- HTTP errors are reported **once**, by the layer that knows what the user attempted — never an interceptor: a hand-rolled store's own toast-wrapper method (the old `FleetStore.run()`'s shape, before wave N4b), one `notify$`/`notifyFailure$`-style effect per slice mapping `*Failure` in a migrated one. Background polls degrade silently (no toast).
- **Pure logic in `*-logic.ts`, unit-tested; components are not.** No *page* facade has a spec — those are covered through their logic + `tsc` + the architecture guard. The exception is a **core facade over an NgRx slice** (`core/shell/theme-facade.spec.ts`/`sidebar-facade.spec.ts`, `core/settings/settings-facade.spec.ts`, `core/org/org-facade.spec.ts`, `core/seat/seat-facade.spec.ts`), which is specced end to end over the real `provideAppState()` — facade → action → reducer → effect → `localStorage`/DOM/HTTP — because that is where the replaced store's behaviour now lives and a `provideMockStore` version would assert nothing real; each slice's `*.reducer.spec.ts`/`*.effects.spec.ts` cover the RxJS-timing-specific cases (cadence, `groupBy` isolation, `distinctUntilChanged` dedup) directly, so the facade spec itself stays a consumer-level read of the observable behaviour. Component `TestBed` specs only for wiring bugs a pure spec cannot reach.
- Single-consumer logic stays feature-local; it moves to `core/` **only when a second consumer needs it** (re-exported from the old home for existing imports).
- **Never paraphrase a server-supplied failure reason** — render it verbatim (calibration `solved:false`, geo `NO_FIX`, onboarding verify).
- **Absent ≠ empty.** A disabled feature renders *nothing*; an enabled one with no data renders a distinct empty/dim state. Prefer enforcing it in the type (`GeoChipTone` has no `danger` member, so "never red for PROBABLE" is structural).
- Never optimistic about a *claim*: "Following #N" comes only from the server's `lockedTrackId` poll. A segmented control echoing the operator's own click is ordinary feedback, not a claim — and is still re-synced from the server after.
- **Marks are not draggable.** A mark records where something *was observed*; a drag would silently rewrite it. No `(markMoved)`, no `MarksFacade.moveTo`. `PATCH /api/map/marks/{id}` still accepts coordinates (generic patch machinery) — nothing here sends them. Flight-plan waypoints and geofence vertices *do* drag; they run their own Leaflet maps.
- Styling: two-tier tokens only, raw hex confined to TIER 1 in `styles.css` (exception: canvas/Leaflet draw colors, which can't read `var()`). Light default; `.surface-dark` marks video enclaves. Selection language everywhere: 2px `--color-info` left bar + `--color-info-soft` fill. Classification → muted text, state → one chip. See `.claude/skills/frontend-style`.
- Diagnostic logging: plain `console.*` with a per-file `LOG_PREFIX` (`[player]`, `[fleet]`, `[fly]`) — no logging service. One line per state transition, never per tick. `Player`'s reducer dispatches log `[action] <event> → phase X→Y` only when state actually changed.

## Gotchas

- **`ng test` ≠ `vitest run`.** Specs need the Angular CLI's zoneless `TestBed` bootstrap; raw `npx vitest run` fails hundreds of specs with `TestBed.initTestEnvironment()`/`localStorage is not defined`. Use `npm run test:ci`.
- **A bare `ng` on `PATH` is not necessarily the Angular CLI, on at least one build box in this fleet.** `/usr/bin/ng` is Debian's own `ng` (a `nethack`-family game launcher wrapper, unrelated to Angular) and can shadow `node_modules/.bin/ng` when a shell invokes `ng build`/`ng serve` directly rather than through `npm run <script>` (`npm run` prepends `node_modules/.bin` to `PATH` first, so `package.json`'s own `"build": "ng build"`/`"test:ci": "ng test --watch=false"` scripts are unaffected). The failure mode is not a missing-command error — the wrong binary launches, tries to init a terminal UI with no real tty attached, and aborts with `panic: aborting due to terminal initialize failure` (`SIGABRT`, exit 134), which reads like a native toolchain crash and is not one. Fix: `npx ng build …`/`npx ng test …` (npx always resolves the local package binary first), or run the `npm run` script instead of the bare command. **A second collision confirmed 2026-09-03 (WALL-FLOW-PLAN.md wave W5)**: wrapping the bare command in `script -qec "ng build --configuration production --no-progress" /dev/null` (a workaround tried for the panic above, before its root cause was re-diagnosed) did not panic — it silently resolved to yet a *third*, unrelated binary, `/usr/bin/ng-latin` (confirmed via `ps -ef --forest`: the process tree showed `/usr/bin/ng-latin build --configuration production --no-progress` as the actual running command), which hangs indefinitely on those arguments — zero output, zero CPU time, no panic, easy to mistake for "still compiling" for 10+ minutes. `npx ng`/`npm run build` avoid this the same way they avoid the nethack wrapper; if a manual invocation is ever unavoidable, resolve the binary explicitly instead of trusting a bare `ng` in *any* wrapper shell: `node node_modules/@angular/cli/bin/ng.js build --configuration production` (confirmed correct — 181/181 spec files pass through the identical `npm run test:ci` path, and this direct invocation produced a real `Application bundle generation complete` in under 10s once used).
- **A route-scoped (non-`providedIn: 'root'`) facade's own signals restart at their initial value on every mount, even when a root-provided store it also reads is already warm.** `WallFacade` is instantiated fresh on every navigation to `/wall` (§3.4), so its own `summarySignal` starts `undefined` there while `FleetFacade.streams()`/`devices()` (root-provided, possibly SSE-warm from a prior page) can already be populated — a real window where a matching `streamId` exists on both `/api/streams` and `/api/fleet/summary`, yet the join has genuinely not run yet. `buildWallTiles` used to treat that the same as a confirmed non-match, rendering `unlinked: true` and a device-name title — an honest-*looking* but factually wrong "Not linked to an asset," caught only by live verification (every unit test built inputs as already-loaded, so none caught it). Fix: a request-scoped facade must gate any "confirmed absent" verdict it hands a pure function on an explicit `xLoaded` boolean the facade itself flips once its own first fetch settles, success or failure — see `wall-logic.ts#BuildWallTilesInput.summaryLoaded` / `WallFacade#summaryLoadedSignal`. `command-facade.ts`'s near-identical polling shape has the same latent gap, just less visible (root-provided, so its cold-start window is once per app boot rather than once per navigation) — not fixed here (out of scope), worth an audit if Command ever shows the same symptom.
- **Signals compare with `Object.is`, and a poll hands you a fresh object every tick.** Any `effect()` whose job is "call a store method when an id changes" must derive that id as a **primitive** and compare it against the last id *it itself* acted on. Ignoring this produced a 50–90×/sec `TelemetryStore.track()` loop (a real PATCH storm: 721 requests in 11.5s) and a tab-freezing reattach loop in `Player`. Guards: `telemetry-logic#trackingIdChanged`, `Player#lastAttachKey`, `TelemetryFacade/DetectionsFacade#lastTrackKey`.
- **A `linkedSignal` that re-seeds off a whole object destroys in-progress user input.** Stores replace their whole list on every SSE fold and 30s poll, so an operator mid-typing lost keystrokes. Use the `{source, computation}` form keyed on a primitive id: `(id, previous) => previous?.source === id ? previous.value : fresh()`. Both closures are tracked reactively (verified against Angular's runtime, not the typings).
- **A `localStorage` read inside a `computed()`/`effect()` is invisible to reactivity** — dependency tracking sees signal reads only. A helper that looks pure (two exported functions, no class) is exactly the shape that forgets this; it needs a module-level `signal` seeded from storage at load, written *before* the persist call. See `leaflet-loader#explicitMapLayer`.
- **`inject()` inside an `afterNextRender` callback throws NG0203** on every route. Inject in the constructor's context, capture the instance, use it in the callback.
- **A route param name must match the page's `input()` name exactly.** `assets/:id` + `input.required<string>('assetId')` made `withComponentInputBinding()` set `undefined`, which `HttpClient` cheerfully serialized to `GET /api/assets/undefined` — the page was fully broken, not degraded. Path is `assets/:assetId`.
- **Never assume an `await`ed WebRTC promise's continuation runs before a related event.** `pc.ontrack` fires *during* `setRemoteDescription`, so a no-track timeout armed after the `await` fired unconditionally 6s later against healthy streams — every attach. Re-check observable state (`whepTrackArrived`) at both arm and fire.
- **`navigator.sendBeacon` cannot send a WHEP `DELETE`** (it only ever POSTs; mediamtx's session resource requires the real verb). Teardown uses `fetch(url, {method:'DELETE', keepalive:true})`.
- **`webrtc-ice-restart.ts` was derived from mediamtx's Go source at tag `v1.19.2`, not the IETF drafts.** mediamtx's own bundled reference client doesn't implement ICE-restart-via-PATCH at all, so there's nothing upstream to diff against — re-verify against the server's request handling on any tag bump.
- **The WHEP→HLS fallback is load-bearing, not an edge case.** Dockerized mediamtx advertises `127.0.0.1` ICE candidates unless `VISION_WEBRTC_HOST` is set, so every LAN viewer silently lands on HLS. Don't "fix" an HLS transport chip before checking that env var. **As of fix/stream-start-latency, landing on HLS this way is no longer a page-session-long sentence** — `Player` re-probes WHEP on a cooldown for as long as it stays on HLS with a `whepUrl` configured (see the `player/` bullet above), so a `VISION_WEBRTC_HOST` fixed mid-session (or a mediamtx restart that finally opens the path) is picked up without a page reload.
- **`proxy.conf.json` must carry `/hls`** — without it `ng serve` answers the playlist request with `index.html` (HTTP 200, `text/html`), which looks exactly like a broken player. `Player` now detects this shape and says so. **Restart `ng serve` after editing the proxy** — it's read once at startup.
- **Snap-to-live never triggers for WHEP** (`Player#behindLive` is pinned `0` — there's no seekable buffer). Overlay/detection sync uses `overlaySyncLatencySeconds` (which substitutes the measured WHEP latency) instead. The behind-live chip uses two-threshold hysteresis (show ≥4s, hide <2s) so a jittering per-second measurement doesn't flicker it.
- **`stopped` is absorbing and checked first in `reattach()`** — once true nothing attaches, whatever `src`/`whepUrl` say. This is what makes an explicit Stop hold regardless of backend flapping (the `/live` "stop freezes the app" bug was the frontend amplifying a backend problem, not merely suffering it).
- **The detection overlay resolves a model key from `Detection.label`'s prefix, never `Detection.modelId`** — every detection in a composite batch carries the same comma-joined composite id, so `modelId` cannot distinguish members even though it's on the wire.
- **HiDPI:** `canvasBackingSize` + `ctx.setTransform(dpr,…)` scale the *backing store* only; the CSS box stays `clientWidth/Height` so all hit-testing stays in CSS-pixel space. Redraw is driven by `requestVideoFrameCallback` where available, a 200ms interval otherwise, plus a `ResizeObserver` on the `<video>`.
- **`Number('') === 0`, not `NaN`.** Every numeric draft form must parse via `Number(raw.trim() === '' ? NaN : raw)` or a blank field silently validates as zero.
- **Re-entrancy flag idiom**: set a flag immediately before a programmatic write, check-and-clear it in the listener that write would otherwise re-trigger (`replay#videoDrivenUpdate`, `TacticalMap`'s auto-fit suppression). Used wherever a control and its subject drive each other.
- **`GeoFacade.disabled` is sticky within a `track()` session** and clears only on `track()`/`reset()` — a transient network blip must never read as "the feature is off".
- **Leaflet:** its CSS is a hand-maintained copy at `public/leaflet/leaflet.css` injected as a runtime `<link>` (importing it would trip the 8/10 kB `anyComponentStyle` budget); `::ng-deep` is required for Leaflet-owned DOM (Angular never stamped `_ngcontent-*` on it); `allowedCommonJsDependencies: ["leaflet"]` silences UMD warnings. **`leaflet` sits in `devDependencies` despite being imported at runtime** — fine for the bundled build, fatal for `npm ci --omit=dev`.
- **Tile-cache `fetch()` reads need CORS**; all four current providers send `Access-Control-Allow-Origin: *`. A fifth layer whose host doesn't still renders (falls back to plain `<img src>`) but silently never caches.
- **`PollScheduler`'s heartbeat is 1s** — register only multiples of 1000 ms (all current callers use 1s/2s/5s).
- **`JpaTelemetryRepository#findByUsage` returns the *first* `limit` samples, not the latest** (deliberately mirroring the old in-memory semantics). At 1 Hz a usage older than ~200s makes `?limit=200` return a frozen earliest window forever — the OSD's staleness indicator is telling the truth. Backend behavior, not a frontend bug.
- **Dev-parity trap:** with `vision.auth.enabled=false` the synthetic principal's `Root` group id (`UUID(0,1)`) does not match seeded users' real random-UUID Root group, so a pilot picker legitimately finds zero matches. That's an honest empty state, not a bug.
- **`shared/player/sample-box-editor-logic.ts` deliberately forks `player.ts`'s letterbox math** rather than importing it — the live player's hot render path is read-only and stays simple.
- **`flight-state-logic.ts#derivePreflight`'s GPS-fix/Battery rows are vehicle-kind-aware** (FLEET-RADIO-PLAN.md F14/R4c): `vehicleKind === 'ROVER'` is the *only* carve-out (a rover/boat drives with no GPS fix at all; its low-battery bar is a separate, lower, named-table entry — `BATTERY_LOW_PERCENT_BY_KIND`). Every other kind, **and `undefined`** (capabilities not loaded yet, or the fetch failed), falls through to the original copter-shaped rule — an unresolved kind never silently inherits the rover's laxer treatment. `cockpit-facade.ts` threads `this.capabilities()?.vehicleKind` through; no other call site of `derivePreflight` exists.
- **Preflight thresholds are a per-kind table in the logic layer, not a client-config read** — FLEET-RADIO-PLAN.md's D7 wants server-sourced UI thresholds, but no client-config endpoint exists anywhere in this codebase (nothing serves UI thresholds from `application.yaml`); building one is properties + a controller + a client store across three modules, deferred as its own wave. The rover's 25% battery bar is a reasoned placeholder (documented in `flight-state-logic.ts`'s own comment), not a measured constant.
- **`core/rc/controller-setup-logic.ts`'s channel ceiling is 16, not 18** (FLEET-RADIO-PLAN.md R3/F17, web half closed 2026-08-27) — ArduPilot reads only channels 1–16 out of an `RC_CHANNELS_OVERRIDE`, so `ControlBinding` (vision-flight) now **throws** on 17/18. `nextFreeChannel`/`blankControlDraft` clamp to 16, which means a fully-bound layout re-offers 16 rather than inventing a 17th the server would reject. The two ceilings must move together: this page offering a channel the domain refuses is a 400 the operator cannot act on.
- **`core/rc/control-action-logic.ts#actionLabel` takes an optional third `vehicleKind`** (FLEET-RADIO-PLAN.md R4b, shipped in R2's task) — the only case it changes is `EMERGENCY_STOP`, which reads `'Emergency stop (Hold)'` on a `ROVER` (the backend now holds/brakes a rover instead of force-disarming it) and keeps the historical `'Emergency stop'` for every other kind, including `undefined`/`UNKNOWN` — same "unresolved kind never inherits the rover-specific treatment" rule `derivePreflight` follows two bullets up. Both call sites in `control-action-dispatcher.ts` (`send()`'s toast/log text, the dangerous-hold "Hold … to …" message) and `features/fly/rc-monitor.html`'s bound-switch chip list thread `profile.kind`/`capabilities()?.vehicleKind` through. **The `denied`-state refusal text needed no frontend change at all** — `rc-monitor.html` already renders `ManualControlClient#deniedReason()` verbatim, and that client already forwards any `denied` frame's free-text `reason` regardless of `code`, so a new backend refusal (FLEET-RADIO R2's `VEHICLE_UNIDENTIFIED`) reaches the operator's screen unchanged the moment the backend sends it.
- **The onboarding wizard's `sysid` step** (FLEET-RADIO-PLAN.md R5/F0, shipped 2026-08-27; copy rework LINK-PAIRING wave LF2, 2026-09-18) — `VisionApi#writeAssetParameter` (`POST /api/assets/{id}/parameters`) and `features/onboarding/sysid-collision-logic.ts` (`detectSysidCollision`, `sysidParameterName`, `describeSysidStep`, `heardSysidFor`, `SYSID_RANGE_MIN`/`SYSID_RANGE_MAX`); see the `onboarding/` bullet above for the full flow and LF2's three-kind classification. Server-side, this degrades honestly to `409` whenever `vision.onboarding.probe.enabled` is at its default `false` (no client-side flag check needed — the write button's own error banner renders that `409` verbatim, like every other error here).
- **`RcSource#keyboard` is injected `{ optional: true }`, not a hard dependency** (CONTROLLER-UX-PLAN.md §5 wave K) — two specs build a narrower `RcSource` harness by hand and never select `'keyboard'` (`manual-control-client.spec.ts`'s own `createEnvironmentInjector([ManualControlClient, RcSource, VirtualRcInputService, …])`, and `control-action-dispatcher.spec.ts` via the same chain), so a hard `inject(KeyboardRcInputService)` field initializer threw `NG0201` for both the moment `RcSource` started depending on it — neither spec's provider list, by design, mirrors the real page's own (they predate the keyboard source and test a narrower slice on purpose). `{ optional: true }` isn't a "null means the feature is off" contract (CLAUDE.md §10) — every read of `this.keyboard` only executes once `_kind() === 'keyboard'`, which is unreachable without the real service present. **As of wave WEB1 below, the "real page's own `providers` array" that always lists all three siblings is `fly-hud.ts`, not `rc-monitor.ts`** — the whole RC provider stack moved host, see that wave's own entry.

- **Keyboard action keys (Space e-stop, `Shift`+`Enter` arm, `1`-`4` mode) route through `ControlActionDispatcher`, never a second command path** (MAVLINK-COMMANDS-PLAN.md D2d/D3, wave W1) — `keyboard-rc-input.service.ts` only tracks *which* action keys are physically down (`actionKeysDown: Signal<ReadonlySet<ActionKeyId>>`, edge-triggered on `keydown`/`keyup`, cleared on `blur`/`visibilitychange(hidden)`/`setEnabled(false)` exactly like the axis keys); all chord parsing, catalogue-driven danger resolution, and edge/hold decisions live in the new pure `keyboard-action-logic.ts`, and `ControlActionDispatcher` is the only place that turns a resolved key into a `send()` call. A bound switch's hold (`holdKey`/`holdPosition`/`holdSince`) and the keyboard's own hold (`keyHoldId`/`keyHoldSince`) are two **separate** field groups — they are genuinely independent physical inputs that can be mid-hold at once — but both share the same `DANGEROUS_HOLD_MS` constant and the same frame-driven "has enough time passed since `Date.now()`" check inside one `onFrame`, never a second `setTimeout`; both funnel into the one `send()`, which is what actually enforces one-command-in-flight.
  - **`ControlActionDispatcher` fetches `FlightCapability` itself** (`VisionApi.flightCapabilities(assetId)`, reactive on `assetId`, race-guarded by `capabilitiesRequestId`) rather than requiring a caller to thread `selectableModes` in — the file-scope for this wave was `keyboard-rc-input.service.ts`/`control-action-dispatcher.ts`/`keyboard-action-logic.ts` only, and `rc-monitor.ts`'s own facade wiring was concurrently-owned by another wave. This is a deliberate, self-contained trade: a small amount of duplicate network I/O (the cockpit facade already fetches the same endpoint for other reasons) in exchange for the digit keys never shipping "green but inert" behind a call site nobody wired up. A failed/missing read degrades to `[]`/`undefined` (`console.warn`s once) — a mode digit past what the vehicle actually reports does nothing, never a fabricated mode name.
  - **The settled-first-frame sentinel that protects a bound switch does NOT translate directly to keyboard state, and copying it verbatim is a real bug, not a style choice.** A gamepad polls continuously, so "the next frame after `bind()`" is always background noise, safe to treat as already-settled. A keyboard `onFrame` only runs off an actual DOM key event — no idle heartbeat — so "the next frame after `bind()`" is frequently the operator's own first genuine keypress; a sentinel that swallows it silently eats a real command. Fix: `keyboardPrev` is never `undefined` — `bind()` seeds it *synchronously* from `KeyboardRcInputService#actionKeysDown()`'s live value the instant `assetId`/`enabled` changes, giving the same "already-held-at-activation doesn't fire" guarantee without swallowing the operator's next real press.

- **A root-registered NgRx effect auto-starts the moment the environment injector realizes — independent of whether anything ever injects the facade over it.** Found in NGRX-MIGRATION-PLAN.md wave N4b: the old `providedIn: 'root'` `FleetStore`/`SystemStatusStore` classes were lazily *constructed* only on first injection anywhere, so a spec that never touched them never triggered their HTTP calls.
