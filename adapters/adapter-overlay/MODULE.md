# adapter-overlay

Frame annotation adapter: burns detection boxes/labels and a telemetry OSD onto video frames, pure Java2D.

**Depends on:** vision-domain · **Used by:** vision-app (`WiringConfiguration#overlayRenderer`, threaded into `StreamPipeline` via `DefaultStreamService`, docs/MVP1-PLAN.md §C8 bullet 2)
**Build/test:** `./mvnw -B -pl adapters/adapter-overlay test` — 24 tests (`Java2DOverlayRendererTest` 14, `DetectionBoxPainterTest` 5, `OverlaySettingsTest` 5), no docker/network needed.

## API surface
### `com.drones.vision.adapter.overlay`
- `final class Java2DOverlayRenderer implements OverlayPort` — plain class, no Spring. Thin dispatch/orchestration only; codec and painting are delegated to package-private collaborators (docs/LAYERING-REFACTOR-PLAN.md §5.1, wave E3).
  - `Java2DOverlayRenderer()` — no-arg, renders with `OverlaySettings.defaults()`. Kept so today's callers (`vision-app`'s wiring, this module's own tests) keep compiling unchanged; this is the "public constructors unchanged" half of the E-phase contract.
  - `Java2DOverlayRenderer(OverlaySettings settings)` — the injectable constructor a later wiring wave (docs/LAYERING-REFACTOR-PLAN.md F3) will use to pass real `vision.overlay.*` configuration. Not wired to Spring yet — no `@ConfigurationProperties`/`Vision*Properties` type exists in this module, by design (§1.3 rule 5: adapters never import one).
  - `VideoFrame render(AnnotatedFrame annotated)` — the `OverlayPort` method. Zero-cost path: if `detections` is empty and `telemetry` is `null`, returns `annotated.frame()` itself (same instance, no copy). Otherwise dispatches on `frame.format()`:
    - `BGR24` — via `FrameImageCodec.decodeBgr24`/`encodeBgr24`.
    - `JPEG` — via `FrameImageCodec.decodeJpeg`/`encodeJpeg`, quality from `OverlaySettings#jpegQuality`.
    - Anything else (`RGB24`/`YUV420P`/`H264_PACKET`/`UNKNOWN`), or a JPEG payload the codec can't decode/re-encode — **passed through unchanged, never throws**. Overlay is a cosmetic add-on; it must never be the reason a stream breaks.
  - `static Color colorForLabel(String label)` — package-private, hashes `label` (via `String.hashCode()`, JDK-specified formula, stable across JVM runs) into the **`LABEL_PALETTE`** fixed 8-color array (`Math.floorMod(label.hashCode(), 8)`). Stays on this class deliberately (docs/LAYERING-REFACTOR-PLAN.md §1.3 explicitly excludes it from the split/config-extraction) — its length is baked into the hash formula and the pixel-probe tests assert the stable label→color mapping; `DetectionBoxPainter` calls back into this method rather than owning its own copy. **Untouched by wave T5** — its palette length and hash formula are still the pinned contract; the tracking wave added a sibling method instead of modifying this one.
  - `static Color colorForTrack(long trackId)` — package-private, added in wave T5 (docs/TRACKING-PLAN.md §7). Same `LABEL_PALETTE` array, `Math.floorMod(trackId, 8)` instead of hashing a label — so a tracked detection keeps **one color for the life of its track** even when its label flips between frames (composite-mode detectors can relabel the same physical object across frames, docs/TRACKING-PLAN.md §9 risk R9). `DetectionBoxPainter.draw` picks this over `colorForLabel` whenever `detection.track() != null`.
- `record OverlaySettings(float jpegQuality, int minStrokeWidth, int strokeDivisor, int minFontSize, int fontDivisor, int osdBackgroundAlpha, int osdMargin)` — public, framework-free, compact-ctor validated (`jpegQuality` in `(0,1]`; the two divisors and `minStrokeWidth`/`minFontSize` positive; `osdBackgroundAlpha` in `[0,255]`; `osdMargin` non-negative). `static defaults()` reproduces the exact literals this record replaced (`0.8f, 2, 200, 12, 45, 160, 4`) — every value under the `vision.overlay` property prefix (docs/LAYERING-REFACTOR-PLAN.md §2.2).
- `final class FrameImageCodec` (package-private) — pixel/byte ↔ `BufferedImage` conversion only: `decodeBgr24`/`encodeBgr24` (packed-BGR bulk copy, no per-pixel loop), `decodeJpeg`/`encodeJpeg` (`ImageIO`, quality from the constructor). Logs a `WARNING` (via `System.Logger`) on a decode/encode failure before falling back to pass-through — the failure itself is still swallowed by the caller, never thrown further; this only makes it observable instead of silent.
- `final class DetectionBoxPainter` (package-private) — one detection's box border (`drawInsetBorder` solid / `drawDashedBorder` for a `COASTING` track, docs/TRACKING-PLAN.md §7 wave T5) + label bar (`drawLabel`), normalized-box→pixel clamping (`clampToDimension`), and text-contrast pick (`readableTextColor`). Constructor takes `(minStrokeWidth, strokeDivisor, minFontSize, fontDivisor)`.
  - `static String labelText(Detection detection)` — package-private, `"#<trackId> <label> <confidence>"` when `detection.track()` is non-null, unchanged `"<label> <confidence>"` when it is `null`. Exposed directly (not only through rendered pixels) so its exact text can be asserted without going through `FontMetrics`-dependent label-bar geometry.
- `final class TelemetryOsdPainter` (package-private) — the telemetry OSD block (`draw`): builds the lat/lon/alt/batt line list, sizes/positions the semi-transparent background, draws white text. Constructor takes `(minFontSize, fontDivisor, osdBackgroundAlpha, osdMargin)`. `TEXT_PADDING = 6` (inter-line/text padding inside the OSD block) stays a private literal — it is not one of the seven `vision.overlay` keys in §2.2, so it was not extracted.

## Conventions
- **Never mutates the input frame.** `BGR24`: `FrameImageCodec.decodeBgr24`'s `BufferedImage` backing array is freshly allocated and only ever `.get()`-copied from `frame.data()` (a read-only duplicate per `VideoFrame`'s own contract), so drawing on it can't reach back into the caller's buffer. `JPEG`: `ImageIO.read` always returns a fresh `BufferedImage` decoded from a copy of the bytes, never aliasing anything.
- **Box → pixel conversion:** each `BoundingBox` component is independent (`x`,`y`,`width`,`height` all `[0,1]` on their own axis; the domain does not guarantee `x+width <= 1`). Pixel `x`/`y` are clamped to `[0, dimension]`; pixel `w`/`h` are `Math.min(round(component * dimension), dimension - pixelCoordinate)` so a box is silently clipped to the frame, never thrown on, even sitting exactly on the `1.0` edge (a zero-size clipped box is simply not drawn — `w <= 0 || h <= 0` short-circuits).
- **Box border is drawn as four filled strips (`DetectionBoxPainter.drawInsetBorder`), not a `java.awt.Stroke`.** A centered `BasicStroke` straddles the path and its exact rasterized pixels depend on anti-aliasing/line-join rules; an inset border (`fillRect` on each of the four edges, entirely inside `[x,x+w) x [y,y+h)`) is byte-exact and independent of any rendering hint — this is what makes the box-corner pixel-probe tests deterministic. Stroke thickness: `max(minStrokeWidth, min(frameWidth, frameHeight) / strokeDivisor)` — defaults `max(2, .../200)`, byte-identical to before.
- **Label text** (`"person 0.87"`, `%.2f` confidence) is drawn on a filled bar in the label's own color, positioned above the box; if there's no room above (`boxY - barHeight < 0`, i.e. the box touches/is near the frame top), the bar falls back to the box's own top-left corner instead of going negative. Font: `SansSerif BOLD`, size `max(minFontSize, frameHeight / fontDivisor)` (defaults `max(12, frameHeight/45)`, 16px at 720p), `KEY_TEXT_ANTIALIASING` on. Text color is black or white, whichever contrasts more with the label color (luminance threshold 140, standard `0.299r+0.587g+0.114b`).
- **Telemetry OSD** is a small monospaced block anchored at `(osdMargin, osdMargin)` (default `(4,4)`) with a semi-transparent dark background (`rgba(0,0,0,osdBackgroundAlpha/255)`, default `160/255`, alpha-blended so it also works over non-black frames). One line per present field, each independently skippable: `lat`/`lon` (5 decimals, combined on one line when both present), `alt …m` (1 decimal), `batt …%` (0 decimals). No lines → nothing drawn (distinct from the top-level "no detections and no telemetry" fast path — this covers "telemetry object present but every field is `null`"). **Font now scales with resolution** (`max(minFontSize, frameHeight / fontDivisor)`, same formula the detection label already used) — see Gotchas for why this is a behavior-preserving fix, not a retune.
- Rendering hints: `KEY_ANTIALIASING` intentionally left unset (shapes are axis-aligned `fillRect`s, always crisp regardless); only `KEY_TEXT_ANTIALIASING` is turned on, for readable label/OSD text.
- **Track rendering (docs/TRACKING-PLAN.md §7, wave T5).** `DetectionBoxPainter.draw` branches on `detection.track()`:
  - **Label** — `#7 person 0.87` (`DetectionBoxPainter.labelText`) when tracked, unchanged `person 0.87` when not. Prefix only; confidence formatting (`%.2f`) is unchanged.
  - **Color** — `Java2DOverlayRenderer.colorForTrack(track.trackId())` instead of `colorForLabel(detection.label())` when tracked. This is the point of coloring by id rather than by label: one physical object keeps one box color across a composite-mode label flip.
  - **Border** — `TrackState.COASTING` draws a **dashed** border (`DetectionBoxPainter.drawDashedBorder`) instead of the solid four-strip `drawInsetBorder`, so an operator can see the system is extrapolating rather than seeing (docs/TRACKING-PLAN.md §3.2). Every other state (`TENTATIVE`/`CONFIRMED`/`LOST`) and every untracked detection draws the solid border, unchanged.
  - An **untracked** detection (`track() == null` — tracking off for the stream, or not yet associated) is unaffected by any of the above: same color, same label text, same solid border as before this wave. Verified as a **byte-identical render**, not just "no visible difference" (`Java2DOverlayRendererTest#untrackedDetectionRendersByteIdenticalWhetherTrackIsExplicitOrDefaultedNull`).
- **No trails.** This renderer is stateless and `render()` has no stream identity in its signature (`AnnotatedFrame` is single-frame) — deliberately not built here (docs/TRACKING-PLAN.md §6, decision D6). A burned trail would need either a domain change or per-stream renderer state; trails are a client-side vector-overlay concern (wave T7, `vision-web`). The burned overlay's contribution to "visible flow" stops at `#id` + the dashed `COASTING` box.

## Gotchas
- **The dashed `COASTING` border is asserted structurally, never pixel-probed** (docs/TRACKING-PLAN.md §7 wave T5, following this module's own determinism convention below). `drawDashedBorder` goes through a real `java.awt.Stroke`/`Graphics2D#draw(Shape)` instead of `fillRect` strips, so — unlike the solid border — its rasterized pixels are not guaranteed byte-identical across JDK/fontconfig versions. `DetectionBoxPainterTest` instead uses a hand-written `RecordingGraphics2D` (a `Graphics2D` test double, `src/test/.../RecordingGraphics2D.java`) that wraps a real `Graphics2D` from a `BufferedImage` — so rendering still actually happens and can't NPE/throw — and records every `fillRect`/`draw(Shape)` call plus the `Stroke` in effect at each `draw`. Tests assert *which method fired* (`COASTING` → exactly one `draw(Shape)` call with a dashed `BasicStroke`, zero border `fillRect` calls; `CONFIRMED`/untracked → the same 4-strip-plus-label-bar `fillRect` count as before, zero `draw` calls), never the resulting pixels. `RecordingGraphics2D` is otherwise pure delegation — generated from `Graphics2D`'s ~70-method abstract surface via reflection, not hand-maintained — so it is not a general-purpose mock and should not grow scope beyond what a future structural (non-pixel) assertion in this package needs.
- **OSD font-scaling fix (docs/LAYERING-REFACTOR-PLAN.md §5.1, wave E3).** Before this wave, `drawTelemetry` built its `Font` with the raw `MIN_FONT_SIZE` literal (`12`) directly, instead of running it through the same `max(MIN_FONT_SIZE, frameHeight / 45)` formula the detection-label font already used — so the OSD was pinned at a fixed 12px at *any* resolution, unreadable at 4K. `TelemetryOsdPainter.draw` now calls the same `fontSize(frameHeight)` formula (parameterized by `OverlaySettings#minFontSize`/`#fontDivisor`). **This is confirmed behavior-preserving at today's actual default resolution**: the platform's simulation/pipeline default frame size is 640×480 (`vision.simulation.video.width/height`, docs/LAYERING-REFACTOR-PLAN.md §2.2) — `max(12, 480/45) = max(12, 10) = 12`, byte-identical to the old hardcoded `12`. Both this module's tests and `Java2DOverlayRendererTest`'s telemetry tests render at 640×480 and stayed green unchanged, confirming no observable difference at that resolution. Only a frame taller than 540px (`frameHeight/fontDivisor >= minFontSize`, i.e. `>= 45*12`) will actually render a larger OSD font than before — which is the intended fix, not a side effect.
- **`OverlaySettings` covers all seven `vision.overlay` keys from docs/LAYERING-REFACTOR-PLAN.md §2.2** (`jpeg-quality`, `min-stroke-width`, `stroke-divisor`, `min-font-size`, `font-divisor`, `osd-background-alpha`, `osd-margin`). Note the plan's own §1.3 rule 4 lists `adapter-overlay` among the "≤2 tunables, skip the settings record" modules, but §2.2's table gives it 7 keys — clearly more than 2. This wave resolved the discrepancy in favor of §2.2 (the frozen, more specific contract) and built a settings record per §1.3 rule 2/3, since 7 raw constructor parameters would blow past the house style's 5-parameter ceiling. Flagging this here rather than silently picking one reading.
- `BufferedImage.TYPE_3BYTE_BGR`'s raster backing array is genuinely byte-for-byte `PixelFormat.BGR24` (B,G,R per pixel, packed, no stride padding) — this is what lets `FrameImageCodec`'s BGR24 path skip any per-pixel conversion loop and just bulk-copy into `((DataBufferByte) image.getRaster().getDataBuffer()).getData()`. This assumption is shared with `adapter-publish-hls`'s `FrameConverter` (see its Javadoc) — if that platform-wide convention ever changes, both adapters need to change together.
- A decoded JPEG `BufferedImage` is assumed opaque (no alpha) for re-encoding; `FrameImageCodec.encodeJpeg` defensively flattens onto `TYPE_INT_RGB` first if `getColorModel().hasAlpha()` is ever true, since JPEG writers throw `IIOException` on an alpha-bearing image type — belt-and-braces, not expected to trigger in practice (JPEG has no alpha channel).
- Label bar / OSD block *pixel positions* are not asserted exactly in tests (only their fill color at deterministic, geometry-only-dependent probe points is) — their width/height depend on `FontMetrics`, which can vary slightly by JDK/fontconfig; only the box border (pure integer geometry, no font involved) is probed at exact pixel coordinates.
- `FrameImageCodec` now logs at `WARNING` (via `System.Logger`) when a JPEG frame can't be decoded or re-encoded, before falling back to pass-through — previously silent. This is an observability addition only; the returned `VideoFrame` is unchanged either way.

## Status
`Java2DOverlayRenderer` implements `docs/MVP1-PLAN.md` §C8 bullet 1 in full (box burn-in, per-label palette, telemetry OSD, pass-through-never-throws for unsupported formats), wired into `StreamPipeline` as of §C8 bullet 2 (`vision-app`'s `WiringConfiguration#overlayRenderer` bean, threaded through `DefaultStreamService`'s `OverlayPort` parameter) — see vision-application/MODULE.md's `StreamPipeline` entry for the burn-in/failure-handling behavior this adapter is driven by.

**docs/LAYERING-REFACTOR-PLAN.md wave E3 (this wave, done):** internal split into `FrameImageCodec`/`DetectionBoxPainter`/`TelemetryOsdPainter`, `OverlaySettings` record with an injectable constructor, and the OSD font-scaling bug fix. `Java2DOverlayRenderer`'s public no-arg constructor is unchanged (still renders with today's exact literal defaults) — **wave F3 is not done**: nothing binds `vision.overlay.*` yet, and `vision-app`'s `WiringConfiguration#overlayRenderer` still calls the no-arg constructor. A later wave adds `VisionOverlayProperties` in `vision-app`, maps it to `OverlaySettings`, and switches that bean to the settings-taking constructor.

`PipelineConfig.overlayTelemetry`'s OSD gate is still not reachable in practice: `StreamPipeline` has no telemetry input yet, so it always passes `telemetry=null` into `AnnotatedFrame` regardless of that flag — this renderer itself still always draws the OSD when `telemetry != null` is passed to it, but nothing upstream does that yet. Plumbing a telemetry input into `StreamPipeline` remains a later task.

**docs/TRACKING-PLAN.md wave T5 (this wave, done):** `#id`/track-color/dashed-`COASTING` rendering per §7's acceptance list — see "Track rendering" under Conventions and the dashed-border gotcha above. Depends only on wave T2's already-committed domain types (`Detection#track()`, `TrackRef`, `TrackState`); no other module in this plan's dependency graph (T3 application, T4 adapter-cv-grpc, T6 api/persistence, T7 web-ui) is touched or required for this wave to be complete. **No trails** — deliberately out of scope, §6 decision D6 (see Conventions). Byte-identical rendering for untracked detections is a first-class regression test (`Java2DOverlayRendererTest#untrackedDetectionRendersByteIdenticalWhetherTrackIsExplicitOrDefaultedNull`), not an assumption.
