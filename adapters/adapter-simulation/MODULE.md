# adapter-simulation

Synthetic video + telemetry sources so every phase is testable/demoable without real hardware.

**Depends on:** vision-domain · **Used by:** vision-app
**Build/test:** `./mvnw -B -pl adapters/adapter-simulation test` (30 tests, verified via a live run)

## API surface
### `com.drones.vision.adapter.simulation`
- `final class SimulatedVideoSource implements VideoSourcePort` — `supports(StreamDescriptor)`, `open(StreamId, StreamDescriptor): Flow.Publisher<VideoFrame>`, `close(StreamId)`. Supports protocol `"sim"`. Public no-arg constructor uses `VideoSettings.defaults()`; public `SimulatedVideoSource(VideoSettings)` overload takes explicit defaults (for a later wiring wave). Per-`open()` options `width`/`height`/`fps` (int) override the instance's configured defaults when present; malformed/blank/absent falls back to the default.
  - nested `private static final class StreamRuntime` — one per `open()` call: single-thread `ScheduledExecutorService` (`scheduleAtFixedRate`, period `max(1, 1000/fps)` ms) rendering via `FrameRenderer` and submitting to a per-stream `SubmissionPublisher<VideoFrame>`.
- `record VideoSettings(int width, int height, int fps)` — framework-free, compact-constructor-validated (all three must be positive) tunables for `SimulatedVideoSource`; `static defaults()` = 640x480 @15fps (package-visible `DEFAULT_WIDTH`/`DEFAULT_HEIGHT`/`DEFAULT_FPS` constants, readable from tests), byte-identical to the pre-extraction literals. Public record — a later wave binds `vision.simulation.video.*` in `vision-app` and constructs this there (this module never imports a `@ConfigurationProperties` type).
- `final class SimulatedTelemetrySource implements TelemetrySourcePort` — public no-arg constructor uses `TelemetrySettings.defaults()` (1 Hz); public `SimulatedTelemetrySource(TelemetrySettings)` overload; package-private `SimulatedTelemetrySource(long periodMillis)` test seam (must be > 0, applies to `TelemetrySettings.defaults()` via `withPeriodMillis`). `supports(Device)`, `open(Device): Flow.Publisher<Telemetry>`, `close(DeviceId)`. Requires `Capability.TELEMETRY` **and** `"sim"` protocol. Options (all lenient, see Conventions):
  | Option | Meaning | Default |
  |---|---|---|
  | `lat`/`lon` | circular-track center (double) | `TelemetrySettings.centerLatitude()`/`centerLongitude()` = 50.45/30.52; ignored once a valid `route` is given |
  | `route` | `lat,lon[,altM];lat,lon[,altM];…`, ≥2 points (docs/main/CYCLES-PLAN.md §7, CT-a) | absent/malformed → no route, circular track applies (back-compat) |
  | `speedMps` | cruise speed along `route` (double, must be positive) | `RoutePlan.DEFAULT_SPEED_MPS`=12.0 |
  | `routeMode` | `loop`/`bounce`/`once`, case-insensitive, only meaningful with `route` | `RoutePlan.DEFAULT_MODE`=`LOOP` |
  | `batteryDrainPerSecond` | drain rate, whether flying the circle or a route | `TelemetrySettings.batteryDrainPercentPerSecond()`=0.05%/s from 100% |

  Circular track (back-compat default, unchanged since before CT-a): radius = `TelemetrySettings.trackRadiusMeters()` (200.0, not exposed as a per-device option), one lap per `TICKS_PER_LAP`=60 samples.
  Every sample also carries a synthetic `FlightState` (docs/plans/done/FC-INTEGRATIONS-PLAN.md F-c), no new options: for the first `SyntheticFlightState.STARTUP_DISARMED_TICKS`=5 samples of a subscription, `armed=false` + one arming blocker (`STARTUP_ARMING_BLOCKER`="PreArm: GPS: waiting for home") + `gpsFixType` ramping 1→3; after that, nominal (`firmware="ardupilot"`, `mode="Loiter"`, armed, no failsafe, 3D fix, `satellites`≈`NOMINAL_SATELLITES`=12 ±1, `hdop`≈`NOMINAL_HDOP`=0.8, `rssiPercent`≈`NOMINAL_RSSI_PERCENT`=90) — unless the same drained `batteryPercent` this class already computes has crossed a threshold: `< RTL_BATTERY_PERCENT_THRESHOLD`=20 → `mode="RTL"` + `failsafe=true`; `< LAND_BATTERY_PERCENT_THRESHOLD`=8 → `mode="Land"` (failsafe stays true) — battery-driven RTH/failsafe drama for dev demos, gated behind having armed (an aircraft can't RTL while disarmed on the ground).
  - nested `private static final class DeviceRuntime` — same scheduled-executor-per-`SubmissionPublisher` shape as `StreamRuntime`; each tick either computes the next circular-track point (no valid `route`) or advances a cumulative `distanceMeters` by `speedMps * tickSeconds` and asks the parsed `RoutePlan` for the position there. Also computes that tick's `FlightState` via its own `SyntheticFlightState.forDevice(deviceId)` instance's `at(tick, batteryPercent)` — deterministic per device id, so re-opening the same device id reproduces an identical `FlightState` sequence tick-for-tick.
- `record TelemetrySettings(double centerLatitude, double centerLongitude, double trackRadiusMeters, long periodMillis, double batteryDrainPercentPerSecond)` — framework-free, compact-constructor-validated (`trackRadiusMeters` and `periodMillis` must be positive) tunables for `SimulatedTelemetrySource`; `static defaults()` = 50.45/30.52 center, 200m radius, 1000ms period, 0.05%/s drain (package-visible `DEFAULT_*` constants, readable from tests), byte-identical to the pre-extraction literals. Package-private `withPeriodMillis(long)` is the test-seam plumbing. Public record — a later wave binds `vision.simulation.telemetry.*` in `vision-app` and constructs this there.
- `final class SyntheticFlightState` (package-private, docs/plans/done/FC-INTEGRATIONS-PLAN.md F-c) — a pure, framework-free, scheduler-free synthetic `FlightState` generator, extracted from `SimulatedTelemetrySource.DeviceRuntime` mirroring the `RoutePlan` precedent:
  - `static SyntheticFlightState forDevice(DeviceId deviceId)` — seeds a fresh generator deterministically from a hash of the device id (`getMostSignificantBits() ^ getLeastSignificantBits()`)
  - `FlightState at(long tick, double batteryPercent)` — the startup-ramp/nominal-cruise/battery-driven-RTL-Land logic (unchanged from before the extraction) plus the deterministic (seeded `java.util.Random`) satellites/hdop/rssi jitter; same draw order as before, so seeded sequences are unchanged
  - Owns the constants `STARTUP_DISARMED_TICKS`, `RTL_BATTERY_PERCENT_THRESHOLD`, `LAND_BATTERY_PERCENT_THRESHOLD`, `FLIGHT_STATE_FIRMWARE`, `FLIGHT_MODE_LOITER`/`FLIGHT_MODE_RTL`/`FLIGHT_MODE_LAND`, `STARTUP_ARMING_BLOCKER`, `NOMINAL_SATELLITES`, `NOMINAL_HDOP`, `NOMINAL_RSSI_PERCENT` (package-visible, readable from tests) — these are scripted-demo-behavior constants, not `vision.simulation.*` tunables, so they stayed put rather than moving into `TelemetrySettings`
- `final class RoutePlan` (package-private, docs/main/CYCLES-PLAN.md §7, CT-a) — a pure, framework-free, scheduler-free flight-route engine, fully unit-tested without any thread:
  - `static RoutePlan parse(String routeOption, String modeOption)` — parses the `route`/`routeMode` option strings; returns `null` (never throws) when `routeOption` is absent or malformed (fewer than 2 points, unparseable number, wrong field count per point) — signals the caller to fall back to the circular track; an unrecognized `modeOption` falls back to `DEFAULT_MODE` (`LOOP`), also without throwing
  - `Position positionAt(double metersAlongRoute)` — returns `record Position(latitude, longitude, altitudeMeters, headingDegrees)` interpolated along the route at that cumulative distance, folded per `RouteMode`
  - nested `enum RouteMode { LOOP, BOUNCE, ONCE }` and `record Waypoint(latitude, longitude, altitudeMeters)` — both adapter-local; deliberately **not** shared with vision-application's own `RouteMode`/`Waypoint` types of the same name, since this module depends only on vision-domain (see Gotchas)
  - Distance/bearing between waypoints use a local equirectangular approximation (adequate at flight-plan scale, same technique the circular track already uses); bearing is geographic (0=north, 90=east, clockwise)
  - `LOOP` traverses the path plus a closing end→start leg, wrapping via `distance % lapLength`; `BOUNCE` folds into a "there and back" period and mirrors the second half onto the same forward segments with a 180°-reversed heading; `ONCE` clamps distance to the path length and holds at the end
  - Altitude interpolates linearly only when **both** a segment's endpoints give one; otherwise `null`
- `final class FrameRenderer` (package-private) — `static byte[] renderJpeg(int width, int height, long sequence) throws IOException`: Java2D-rendered moving filled circle + frame counter + wall-clock time, JPEG-encoded via `ImageIO`.

## Conventions
- Plain classes, no Spring — instantiated directly by `vision-app`'s wiring config.
- Config extraction (docs/plans/active/LAYERING-REFACTOR-PLAN.md §1.3/§7 E4): every literal `vision.simulation.*` value hardcoded as a `static final` constant now lives in `VideoSettings`/`TelemetrySettings` instead — both framework-free records with a `static defaults()` factory, byte-identical to what they replace. `vision-app` still constructs both sources with their public no-arg constructors today; a later wave (F4) binds `vision.simulation.video.*`/`vision.simulation.telemetry.*` onto `VisionSimulationProperties` and switches the wiring to the `(VideoSettings)`/`(TelemetrySettings)` constructors added here. Neither settings record nor either source imports a `@ConfigurationProperties` type — that stays `vision-app`-only.
- Each `open()` call creates an independent runtime keyed by `StreamId`/`DeviceId` in a `ConcurrentHashMap`; a stale runtime already present under the same id is defensively closed before the new one starts.
- `close()` is idempotent via `AtomicBoolean closed` CAS; daemon threads named `sim-video-<id>` / `sim-telemetry-<id>`.
- Malformed/blank numeric options silently fall back to the default (no exception) — see `intOption`/`doubleOption`/`positiveDoubleOption` (the last also rejects a parsed non-positive value, used for `speedMps`). A malformed/absent `route` string is the same lenient idiom at a larger grain: `RoutePlan.parse` returns `null` instead of throwing, and the adapter falls back to the circular track — strict validation of user-supplied route data lives one layer up, in vision-application/vision-api (`TelemetryPlan`/`Waypoint`/`StartSimulationRequest#toSpec()`), where the option strings this module parses are themselves produced from already-validated input.

## Gotchas
- `SimulatedTelemetrySource`'s package-private `(long periodMillis)` constructor is a deliberate test seam (`SimulatedTelemetrySourceTest.fastSource`) — same-package tests drop the period to tens of ms to observe several samples without waiting real seconds; production always uses the public no-arg 1 Hz constructor (or the explicit `(TelemetrySettings)` overload once a later wave wires it).
- A render/sample failure (`IOException`/`RuntimeException`) closes the publisher exceptionally and self-closes the runtime rather than crash the scheduler thread.
- `FrameRenderer` uses pure in-memory `BufferedImage`/`Graphics2D` (no AWT display/toolkit) — safe headless (CI/containers).
- `RoutePlan`'s tick math is purely a function of tick *count*, not wall-clock time: `DeviceRuntime` advances `distanceMeters` by `speedMps * (periodMillis / 1000.0)` once per scheduled tick regardless of how much real time actually elapsed between ticks, so `positionAt` results are deterministic given the tick index — useful for tests (see `SimulatedTelemetrySourceTest`'s route tests, which assert step distances precisely) but means a caller relying on wall-clock elapsed time to predict "how far along the route" would be wrong if the scheduler ever falls behind (it won't meaningfully at 1Hz in practice).
- This module has no dependency on vision-application (see the module table above), so `RoutePlan.RouteMode`/`RoutePlan.Waypoint` (adapter-local, string-driven) are intentionally distinct types from vision-application's `RouteMode`/`Waypoint` (domain-shaped, used by `TelemetryPlan`) even though the names and (for `Waypoint`) shape match — the two layers communicate only through `StreamDescriptor.options()` strings, never a shared Java type, per the hexagonal dependency rule.
- `FlightState` seeding: because `sampleAndPublish()` runs unconditionally on the scheduler's own schedule (ticks are generated even with zero subscribers — `SubmissionPublisher` never buffers pre-subscription items for a late subscriber), a test's `subscribe()` call can race the very first tick(s) and silently miss them; two independent runs against the *same* device id can therefore observe different starting tick offsets even though the underlying per-tick sequence is identical. `SimulatedTelemetrySourceTest.flightStateSequenceIsDeterministicForTheSameDeviceId` handles this by aligning both runs on the sample where `armed` first flips to `true` (always real tick `SyntheticFlightState.STARTUP_DISARMED_TICKS`, by construction) rather than comparing from index 0 — a pattern worth reusing for any future test that needs to compare two live runs tick-for-tick.
- `SyntheticFlightState`/`TelemetrySettings`/`VideoSettings` are a pure code-structure and config-extraction split, not a behavior change: `SyntheticFlightState.at()` draws from its seeded `Random` in the exact same order `DeviceRuntime.flightStateFor()` used to (satellites → hdop → rssi), so the deterministic-per-device-id sequence tests assert against is unchanged.

## Status
Fully implemented (Task T5), no placeholders. All video frames are `PixelFormat.JPEG`; every telemetry sample always populates lat/lon/heading/battery (never null) and, since F-c, a non-null `flightState`. docs/main/CYCLES-PLAN.md §7 (CT-a) added configurable flight plans (`route`/`speedMps`/`routeMode`/`batteryDrainPerSecond` options, the `RoutePlan` engine) on top of the pre-existing circular-track behavior, which stays the unmodified back-compat default — `RoutePlanTest` (13 tests) plus 5 `SimulatedTelemetrySourceTest` cases cover it. docs/plans/done/FC-INTEGRATIONS-PLAN.md F-c (2026-07-28) added the synthetic `FlightState` on every sample (startup disarmed→armed ramp, nominal Loiter, battery-driven RTL/Land) with no new `StreamDescriptor` options — 4 more `SimulatedTelemetrySourceTest` cases cover it (nominal state, the startup ramp, the RTL/Land battery transition, cross-run determinism for the same device id), bringing this module to 30 tests total. docs/plans/active/LAYERING-REFACTOR-PLAN.md §7 E4 (2026-08-01) extracted `SyntheticFlightState` (pure `FlightState` engine, mirroring `RoutePlan`) out of `DeviceRuntime`, and moved every `vision.simulation.*` hardcoded default (video width/height/fps; telemetry center lat/lon, track radius, period, battery drain) into new `VideoSettings`/`TelemetrySettings` framework-free records with `static defaults()` — all defaults byte-identical, no test deleted, tests updated in place to reference the new constant homes; still 30 tests. `vision-app`'s wiring is untouched (still uses the no-arg constructors); binding `vision.simulation.video.*`/`vision.simulation.telemetry.*` onto `VisionSimulationProperties` and switching wiring to the new `(VideoSettings)`/`(TelemetrySettings)` constructors is deferred to wave F4.
