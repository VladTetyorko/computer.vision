# adapter-cv-grpc

gRPC client to the Python CV service: `GrpcDetectionPort implements DetectionPort` over the generated `Inference/DetectStream` bidi stub (`proto/vision/v1/cv.proto`).

**Depends on:** vision-domain, vision-proto (which brings io.grpc:grpc-{netty-shaded,protobuf,stub}, com.google.protobuf:protobuf-java) · **Used by:** vision-app (`WiringConfiguration#detectionPort`, gated by `vision.cv.enabled` per `docs/MVP1-PLAN.md` §C7.4)
**Build/test:** `./mvnw -B -pl adapters/adapter-cv-grpc test` — 25 tests, `GrpcDetectionPortTest`, in-process gRPC server for most cases plus a handful of real-TCP-loopback cases (no Python/docker needed either way). Four cover the payload-shrinking path added in CP-b: wide-`BGR24`→downscaled-JPEG (captured request decodes to the scaled dimensions via `ImageIO`), narrow-`BGR24` byte-identical passthrough, `JPEG` byte-identical passthrough, and a conversion failure (malformed too-short `BGR24` data) failing only that one frame's stage while a subsequent good frame on the same `StreamId` still succeeds. Seven more (docs/REMOTE-CV-PLAN.md P1 item 5) cover the constructor-configurable wire-tuning knobs: a custom `detectWidth` actually drives the downscale threshold/target width, `detectWidth`/`jpegQuality` boundary validation (`< MIN_DETECT_WIDTH` / `<= 0` / `> 1` rejected, the respective boundary values accepted), and the `(host, port, detectWidth, jpegQuality)` constructor delegating validation to the canonical one. One more (docs/REMOTE-CV-PLAN.md P0 item 1) is the real dead-endpoint-then-server-starts recovery test — see Gotchas. One more (docs/REMOTE-CV-PLAN.md "Transport decisions" P1) asserts the keepalive constants are sane (positive, timeout well under the ping interval, both well under a minute) rather than timing a real ping/GOAWAY, which would be flaky at unit-test level — the pre-existing real-TCP-loopback tests already exercise the host/port constructor these values are applied on, so a broken `ManagedChannelBuilder` call would fail the whole suite, not just this one test.

## API surface
### `com.drones.vision.adapter.cvgrpc`
- `final class GrpcDetectionPort implements DetectionPort, AutoCloseable` — plain class, no Spring.
  - `GrpcDetectionPort(String host, int port)` — convenience ctor; builds a plaintext `ManagedChannel` (the CV service is reached over a private/internal network — docker-compose, or a Wi-Fi/VPN link to a remote GPU box, see `docs/REMOTE-CV-PLAN.md` — so plaintext is deliberate) with the default wire-tuning knobs (`detectWidth=640`, `jpegQuality=0.8`) and HTTP/2 keepalive tuning (below).
  - `GrpcDetectionPort(String host, int port, int detectWidth, float jpegQuality)` — same, with explicit wire-tuning knobs (docs/REMOTE-CV-PLAN.md P1 item 5; e.g. `vision.cv.detect-width`/`vision.cv.jpeg-quality`, vision-app); delegates validation to the canonical constructor below. **This is the only constructor that configures HTTP/2 keepalive** (`.keepAliveTime`/`.keepAliveTimeout`/`.keepAliveWithoutCalls` on the `ManagedChannelBuilder`, docs/REMOTE-CV-PLAN.md "Transport decisions" P1) — real-TCP concern, not applied on the bring-your-own-channel constructors below (tests inject in-process channels).
  - `GrpcDetectionPort(ManagedChannel channel)` — bring-your-own-channel seam (tests use an in-process channel) with the default wire-tuning knobs; `close()` shuts this channel down too, regardless of who built it.
  - `GrpcDetectionPort(ManagedChannel channel, int detectWidth, float jpegQuality)` — **canonical constructor**; every other constructor delegates here. Validates `detectWidth >= MIN_DETECT_WIDTH` (64) and `jpegQuality` in `(0, 1]`, throwing `IllegalArgumentException` otherwise. Four public constructors total (2 channel sources × default-vs-explicit tuning) rather than a builder — `.claude/skills/java-clean-code/SKILL.md`'s "smallest clean shape" call: each pair is one level of "explicit tuning args added to the with-defaults form," not open-ended telescoping.
  - `CompletionStage<DetectionResult> detect(VideoFrame, PipelineConfig)` — the `DetectionPort` method; never blocks. See **Correlation design** and **Failure semantics** below.
  - `void streamEnded(StreamId)` — optional lifecycle hook (see **Stream lifecycle**); idempotent.
  - `void close()` — idempotent; ends every open stream, then shuts down the channel (awaits termination 5s, then `shutdownNow()`).

## Correlation design
`DetectStream` is bidirectional streaming, so there is one open call per `StreamId`, not per frame:
- A private `StreamSession` (one per `StreamId`, held in a `ConcurrentHashMap<StreamId, StreamSession>`) owns the request `StreamObserver<FrameRequest>`, lazily opened on the first `detect()` for that stream.
- Each frame is sent as one `FrameRequest`, keyed in a `ConcurrentHashMap<Long, CompletableFuture<DetectionResult>>` by `sequence` (`VideoFrame.sequence()`, per-stream-monotonic). The matching `DetectionResponse` (matched back by its own `sequence` field) completes that specific future — proven under out-of-order server replies (`detectCorrelatesInterleavedResponsesBySequence`).
- **The mapped `DetectionResult.streamId()` is the session's own (domain) `StreamId`, not a re-parse of the response's wire `stream_id` string.** Correlation never depends on the server echoing that field correctly, and this avoids a `StreamId.of(...)` parse failure on a malformed echo turning into a crash instead of a clean per-frame failure.
- gRPC stream observers are not thread-safe: every write to a session's request observer (including the lazy open) is serialized through that session's own monitor (`synchronized` block). Concurrent `detect()` calls for the *same* stream from multiple threads are safe (`concurrentDetectCallsForSameStreamCompleteWithoutCorruption`); different streams never contend on the same lock.
- **`StreamSession.send(long sequence, FrameRequest request)` takes an already-built `FrameRequest`**, not a `VideoFrame`/`PipelineConfig` pair — `detect()` builds the wire request first (`buildRequest`, see **Payload shrinking** below) and only then does `sessions.computeIfAbsent(...)`/`session.send(...)`. This is deliberate: it keeps request *construction* (which can fail per-frame, e.g. a bad downscale) entirely decoupled from session *lifecycle* — a conversion failure never creates or touches a `StreamSession`.

## Payload shrinking for large `BGR24` frames (CP-b, `docs/CYCLES-PLAN.md` §CP-b)
The RTSP/file RX path produces full-resolution raw `BGR24` frames (e.g. 1280×720 ≈ 2.7 MB uncompressed) — too large to push over gRPC at a useful detection rate. In `detect()`, before the request is built:
- A `BGR24` frame **wider than the instance's `detectWidth`** (constructor parameter, default `MAX_DETECT_WIDTH=640`px — an adapter-internal wire-payload tuning knob, not a `PipelineConfig` field; independent of `cv-service`'s own `CV_IMGSZ` inference size, see `cv-service/MODULE.md`) is downscaled to exactly `detectWidth` wide (aspect preserved, `Math.round`-ed height) via Java2D bilinear `drawImage`, then JPEG-encoded (`ImageIO`, explicit `ImageWriter`, quality = the instance's `jpegQuality`, default `JPEG_QUALITY=0.8f`) and sent as `IMAGE_ENCODING_JPEG` with the *scaled* width/height. **Promoted from package-private constants to constructor-configurable fields** (docs/REMOTE-CV-PLAN.md P1 item 5) so per-network tuning (e.g. 480px over a slow VPN link) needs no rebuild — see API surface above; vision-app threads `vision.cv.detect-width`/`vision.cv.jpeg-quality` through.
- `wrapBgr24(width, height, ByteBuffer)` turns the source bytes into a `BufferedImage` by allocating a fresh `TYPE_3BYTE_BGR` image and bulk-copying into its backing `DataBufferByte` array (`data.get(pixels)`) — the same idiom `adapter-overlay`'s `Java2DOverlayRenderer.renderBgr24` already uses, chosen over hand-building a `Raster`/`ComponentColorModel` (tried first, worked, but was strictly more code for the same result: `TYPE_3BYTE_BGR`'s own band layout is already byte0=B/byte1=G/byte2=R, i.e. exactly `PixelFormat.BGR24`'s packed-no-padding layout, so no per-pixel reordering is ever needed either way).
- `JPEG` frames and `BGR24` frames already `≤640`px wide pass through byte-identical, exactly as before this existed (only `>`, not `≥`, triggers the downscale — a frame exactly `640`px wide is untouched).
- **No coordinate mapping back to the original resolution is needed or performed.** Detection boxes come back normalized to `[0,1]` and `DetectionResult` never references the source frame's pixel dimensions — the sequence-keyed correlation this class already does is entirely oblivious to whether a given frame was sent raw or downscaled.
- **Runs synchronously on the calling thread**, inside `detect()`, before the request/session machinery is touched — deliberately not offloaded to an executor. It's CPU-bound (no I/O), bounded at roughly 15ms for a 720p frame, and it *replaces* serializing/transmitting several MB of raw pixel data with encoding and sending a couple hundred KB — net caller-thread cost versus the pre-existing fast path is roughly flat, not new added latency, so the class javadoc's "never blocks" framing still holds in practice even though this one step is technically synchronous CPU work.
- A conversion failure (the encoder throwing, or `wrapBgr24`'s bulk `ByteBuffer.get(byte[])` throwing `BufferUnderflowException` on malformed/too-short source data) is caught in `detect()` and fails only that one frame's returned stage — **no `StreamSession` is created or touched**, so an already-open session for that stream (if any) is completely unaffected and the very next `detect()` call for the same `StreamId` proceeds normally (verified: `detectConversionFailureFailsOnlyThatFrameAndSubsequentGoodFrameOnSameStreamSucceeds`).

## Failure semantics
- **Transport failure** (`onError` from the server — e.g. the CV service process restarting): every still-pending future for that stream fails immediately with the transport exception (`StatusRuntimeException`), and the `StreamSession` entry is dropped from the map. The next `detect()` for that `StreamId` transparently opens a fresh call — no explicit reconnect step needed by the caller. This is the recovery mechanism a caller's retry/backoff (`docs/MVP1-PLAN.md` §C7.3 / `StreamPipeline`'s outage-probe policy, see vision-application/MODULE.md §StreamPipeline) depends on.
- **Server ends the stream normally** (`onCompleted` with no error): treated the same as a transport failure — pending futures fail with `IllegalStateException`, session dropped — because a live bidi call is never expected to complete server-side on its own.
- **Hung or unreachable service, and — critically — a session opened while the CV service is down entirely** (no error, just silence): a bidi call has no natural per-call deadline, so every pending future instead gets its own `RESPONSE_TIMEOUT_SECONDS`=2s timeout via `CompletableFuture.orTimeout` (package-private constant, not a Spring property — this is an adapter-internal safety net, not user-tunable config). **The timeout is now terminal for the whole session, exactly like a transport error**: the first pending future to time out cancels the underlying call (`ClientCallStreamObserver.cancel`), fails every other still-pending future for that stream immediately (they don't wait out their own individual timers), and drops the `StreamSession` from the map — so the next `detect()` for that `StreamId` opens a fresh call instead of resending onto a call that may never produce a transport signal at all. **This was a real, verified bug before this fix**: a session opened while cv-service was down could sit half-open forever — no `onError`, no `onCompleted`, ever — because relying solely on transport `onError` assumed the transport always eventually reports failure, which is not guaranteed (see Gotchas below for the concrete mechanism that made this reproducible). A response arriving after a future's own timeout (or after the session was already torn down) is silently ignored (its sequence is no longer in the pending map).
  - **Recovery contract with `StreamPipeline`:** the pipeline's outage/backoff (vision-application/MODULE.md §StreamPipeline) probes at most every `INITIAL_BACKOFF_NANOS`=1s, doubling to `MAX_BACKOFF_NANOS`=10s, and treats every `DetectionPort#detect` failure — including a timeout — as "this probe failed, try again later." This adapter's contract with that policy is: **every probe after a torn-down session gets a fresh call**, so once the CV service is actually reachable again, the very next probe (not some later one) succeeds — the pipeline never needs to know a session ever existed, and never needs its own reconnect logic.
  - **Teardown is idempotent per session** (a package-private `AtomicBoolean torndown` per `StreamSession`, guarding a single `failAllAndDrop`/`endAndClose` path): a timeout and a transport error (or `streamEnded`/`close()`) racing each other — e.g. the server's `onError` and a pending future's own timeout landing on different executor threads at nearly the same instant — resolve to exactly one teardown; whichever trigger wins does the real work (drop from `sessions`, fail every pending future once), every other trigger for the same session is a no-op. Verified under a genuine race in `timeoutRacingTransportErrorTearsDownSessionOnceAndFailsPendingSiblingsFast` (a server thread firing `onError` at ~`RESPONSE_TIMEOUT_SECONDS` while the client's own timeout fires independently).
  - **Design choice: plain fail-fast RPCs (no `withWaitForReady()`) plus fresh-call-per-probe-after-teardown**, not a wait-for-ready call kept alive across the outage. Once the session is unconditionally torn down on any terminal signal (transport error *or* timeout), a wait-for-ready call would add complexity (an RPC that itself never fails, so *only* our own timeout would ever end it — no different in the end, since we already treat every timeout as terminal) without a corresponding benefit; plain fail-fast keeps the two failure paths (`onError`, timeout) symmetric and lets the channel's own connectivity management do the reconnect work, which is all `StreamPipeline`'s probe cadence needs. See Gotchas for a now-fixed dependency version skew that used to prevent the channel itself from ever recognizing a failed connection attempt, independent of anything in this class.
- **Unsupported `PixelFormat`** (only `JPEG`→`IMAGE_ENCODING_JPEG` and `BGR24`→`IMAGE_ENCODING_BGR24` are mapped; `RGB24`/`YUV420P`/`H264_PACKET`/`UNKNOWN` are not): fails fast with `IllegalArgumentException` — no session is opened/touched, no gRPC call is made at all.
- **Malformed response** (e.g. a confidence/box value outside the domain's validated range, causing the `DetectionResult`/`Detection`/`BoundingBox` record constructors to throw): caught per-response and fails just that one future — never crashes the stream or affects other pending futures on the same session.
- **Port already closed**: `detect()` returns an already-failed stage (`IllegalStateException`) without touching any session.

## Stream lifecycle
Chose the **explicit hook** over idle eviction: `streamEnded(StreamId)` fails any still-pending futures for that stream with a `CancellationException`, half-closes the request observer (`onCompleted()`, best-effort), and drops the session. It is optional — an ended stream that's never told so just keeps its call open until `close()`; the next `detect()` for that id would simply keep reusing it. **A future wiring/resilience task should call `streamEnded` when a `StreamPipeline` stops**, so the CV-side call doesn't linger; this class does not (and cannot, from here) know when a stream ends on its own. `streamEnded`/`close()` share the same per-session `torndown` CAS guard as the timeout/transport-error paths (see Failure semantics), so a `streamEnded` racing a concurrent timeout or transport error is also exactly-once — not just idempotent across repeated *external* calls as before, but idempotent against *every* internal trigger too.

Note: `CompletableFuture.get()` reports a future completed via `completeExceptionally(new CancellationException(...))` by throwing that `CancellationException` **directly**, not wrapped in `ExecutionException` (a JDK special case for cancellation-shaped completions) — callers using `.get()`/`.join()` on a `streamEnded`-cancelled future should catch `CancellationException`, not `ExecutionException`.

## Conventions
- Plain class, no Spring, no framework annotations — matches every other adapter in this repo.
- Logging via `System.Logger` (not java.util.logging/SLF4J directly), same idiom as `adapter-publish-hls`'s `MediamtxStreamPublisher`: INFO on opening a stream, WARNING on transport error/unexpected completion/response timeout (with cause where there is one), DEBUG for a best-effort `onCompleted()`/`cancel()` failure during teardown.
- Field-by-field proto↔domain mapping, no shared DTOs: `BoundingBox`/`Detection` both exist as distinct domain and generated-proto types in the same file; proto's `com.drones.vision.proto.v1.Detection`/`BoundingBox` are always referenced fully-qualified (or via `var`) at the two or three call sites that need them, since Java has no import aliasing and the domain names are the ones used everywhere else.
- `ModelRef` for a mapped `Detection` comes from the *response*-level `model_id`/`model_version` fields (the wire `Detection` message itself carries no model info) — the same `ModelRef` instance is reused for every detection in one response.
- **HTTP/2 keepalive on the real-TCP channel (docs/REMOTE-CV-PLAN.md "Transport decisions" P1):** package-private constants, same idiom as `RESPONSE_TIMEOUT_SECONDS` — `KEEPALIVE_TIME_SECONDS=20` (ping interval, including on an idle stream), `KEEPALIVE_TIMEOUT_SECONDS=5` (ack deadline before the channel considers the connection dead), `KEEPALIVE_WITHOUT_CALLS=true` (ping even with no RPC in flight — the case that most needs it, e.g. a stream mid-outage-backoff). Applied only in the `(host, port, detectWidth, jpegQuality)` constructor's `ManagedChannelBuilder` — a real-transport concern, not exposed as `vision.cv.*` properties (the plan: promote to config only if the defaults prove wrong in the field). The matching cv-service server-side permit options live in `cv_service/server.py`'s `_KEEPALIVE_SERVER_OPTIONS` — see `cv-service/MODULE.md`.

## Gotchas
- **FIXED (docs/REMOTE-CV-PLAN.md P0 item 1): the `io.grpc:grpc-core` version skew that used to wedge a real gRPC channel permanently in `CONNECTING` after a genuine TCP connect failure is resolved at the root pom.** Previously, `grpc-core` was not pinned by `${grpc.version}` anywhere in this repo — it came from Spring Boot 4.1's imported `io.grpc:grpc-bom` (`spring-boot-dependencies` pins `grpc-java.version`=1.80.0), since the root pom only overrode `grpc-netty-shaded`/`grpc-protobuf`/`grpc-stub` explicitly; `grpc-netty-shaded:1.64.0`'s compiled bytecode against `grpc-core:1.80.0` threw `NoSuchMethodError: io.grpc.internal.ManagedClientTransport$Listener.transportShutdown(Status)` deep inside Netty's transport-shutdown notification on a real connect failure, silently swallowed by Netty's own listener-dispatch logging, so the channel never learned the attempt failed. **The fix: the root `pom.xml`'s `dependencyManagement` now imports `io.grpc:grpc-bom:${grpc.version}` (scope `import`, type `pom`) *before* the individual `grpc-netty-shaded`/`grpc-protobuf`/`grpc-stub` pins** — Maven's first-declaration-wins rule for imported BOM entries makes this bom import win over `spring-boot-dependencies`' own `grpc-bom` import (declared later, transitively, via the `spring-boot-starter-parent` chain), aligning the *whole* `io.grpc` family (`grpc-core`, `grpc-inprocess`, `grpc-api`, `grpc-context`, `grpc-util`, …) to `${grpc.version}`=1.64.0 in one place — not just the three artifacts previously pinned individually. Pinning `grpc-core` alone inside this module's own `pom.xml` was tried in an earlier task and rejected (it fixed `grpc-netty-shaded`'s connect-failure path but broke `grpc-inprocess:1.80.0`, which needs 1.80.0-only APIs like `io.grpc.internal.DisconnectError` against a downgraded `grpc-core:1.64.0`, throwing `NoClassDefFoundError`) — the root-level bom import avoids that failure mode entirely because it re-aligns every `io.grpc` artifact together, not just one. **Verified** with `mvn -pl adapters/adapter-cv-grpc dependency:tree -Dverbose | grep grpc` and the same for `vision-app`: every `io.grpc:*` line resolves to `1.64.0` with no `(version managed from …)` skew remaining (`grpc-core` and `grpc-inprocess` both included). **The real dead-endpoint-then-server-starts scenario is now a passing test**: `GrpcDetectionPortTest#detectRecoversAfterRealConnectFailureOnceServerStarts` binds nothing to a TCP port, asserts `detect()` fails, then starts a real gRPC server on that exact port and asserts a subsequent `detect()` on the *same* `GrpcDetectionPort`/channel succeeds — stable across repeated runs (recovers in 1-2 reopen attempts, ~1-2s wall time). One nuance worth knowing if this test is ever touched: a fail-fast RPC issued while the channel is in `TRANSIENT_FAILURE` returns near-instantly rather than blocking, so the retry loop needs an explicit `Thread.sleep` between attempts to give the channel's own reconnect-backoff timer (and this class's per-`detect()`-call fresh-session-open, which itself re-attempts the TCP connect) real wall-clock time — a tight retry loop with no sleep observes only fast, repeated `UNAVAILABLE` failures and never recovers within a short bound.
- The `grpc-inprocess` test dependency in this module's `pom.xml` is deliberately left unversioned so it resolves via the same root-level `grpc-bom` import to `1.64.0` — do not add an explicit version pin here, it is redundant now that the BOM already aligns it. See `vision-proto/MODULE.md`'s Gotchas for the analogous (actually harmless) protobuf Java/Python version-line divergence.
- `FrameRequest`/`DetectionResponse` carry `timestamp_millis` (a `long`), so `VideoFrame.capturedAt()`'s sub-millisecond precision (`Instant.now()` often has nanosecond resolution) does not round-trip — expected and harmless in production (millisecond precision is enough), but tests must build frames with a millis-truncated `Instant` or round-trip equality assertions will flake.
- Proto `float` fields (`confidence`, `BoundingBox.x/y/width/height`) widen to `double` on the domain side with normal float-to-double imprecision (e.g. `0.1f` != `0.1d` bit-for-bit) — tests assert those fields with a small delta, not record `.equals()`.
- `pending.values().forEach(future -> future.completeExceptionally(cause))` (used by both the transport-error and `endAndClose` paths) relies on each future's own `whenComplete`-registered self-removal (attached when the future was created in `send()`) to actually drain the `pending` map — there is no separate explicit `pending.clear()`, so if that `whenComplete` registration were ever removed, failed sessions would leak map entries.

## Status
Implements `docs/MVP1-PLAN.md` §C7 bullet 2 in full: correlation, both failure paths (transport error + hung/unreachable service — the latter now including a session opened while the CV service is down entirely, fixed to be terminal-on-timeout rather than silently stuck), unsupported-format fast-fail, and the `streamEnded`/`close()` lifecycle, all sharing one idempotent per-session teardown guard. **`docs/CYCLES-PLAN.md` §CP-b done**: wide-`BGR24` frames are downscaled+JPEG-encoded before sending (see **Payload shrinking** above), shrinking the detection payload for the RTSP/file RX path's full-resolution frames without any coordinate-mapping cost, with the target width/quality now constructor-configurable (see below). Wired into `vision-app` (§C7 bullet 4, `WiringConfiguration#detectionPort`, gated by `vision.cv.enabled`) and exercised against a real (in-test) gRPC server over real TCP (`vision-app`'s `CvDetectionE2ETest`/`CvDetectionResilienceSmokeTest`) as well as this module's own in-process/real-TCP-loopback tests. `PixelFormat.YUV420P` (used by simulation sources) is not sendable to the CV service today; `StreamPipeline`'s frame path would need to convert to `BGR24`/`JPEG` before sampling for detection, or this adapter would need to grow a conversion step. **docs/REMOTE-CV-PLAN.md P0 item 1 done** (see Gotchas): the root-pom `io.grpc:grpc-bom` import fixes the `grpc-core` version skew, verified via `dependency:tree` in both this module and `vision-app`, and the previously-untestable real dead-endpoint-then-recovers scenario now has a passing regression test. **docs/REMOTE-CV-PLAN.md P1 item 5 done**: `MAX_DETECT_WIDTH`/`JPEG_QUALITY` promoted from constants to constructor-configurable `detectWidth`/`jpegQuality` fields (validated, defaults unchanged), threaded from `vision.cv.detect-width`/`vision.cv.jpeg-quality` (vision-app) — see API surface above. **docs/REMOTE-CV-PLAN.md "Transport decisions" P1 done**: the host/port `ManagedChannelBuilder` now sets HTTP/2 keepalive (`KEEPALIVE_TIME_SECONDS`/`KEEPALIVE_TIMEOUT_SECONDS`/`KEEPALIVE_WITHOUT_CALLS`, see Conventions above) so a half-open TCP connection over a flaky Wi-Fi/VPN link to a remote GPU box is detected in roughly 25s worst case instead of relying solely on the OS TCP stack's own (much longer) failure detection; paired with cv-service's server-side permit options so the server doesn't GOAWAY the pinging client.
