# adapter-rtsp

FFmpeg ingest **and** transmit adapter (IP cameras, drone companions, and local-file simulation) via JavaCV/FFmpeg. Despite the module name (kept for historical/build reasons), it covers:
- **RX** (`VideoSourcePort`): `rtsp` (real RTSP/RTP cameras) and `file` (a local video file played back as a simulated live source — drone simulation with zero hardware) protocols, via `FfmpegVideoSource`.
- **TX** (`FeedTransmitterPort`, `docs/CYCLES-PLAN.md` §0/§3): pushes a local video file to a real RTSP target (e.g. mediamtx) so this module's own RX half (or any real RTSP client) ingests it like live hardware — simulation infrastructure, not egress — via `RtspFeedTransmitter`.

**Depends on:** vision-domain, org.bytedeco:javacv, org.bytedeco:ffmpeg-platform-gpl · **Used by:** vision-app
**Build/test:** `./mvnw -B -pl adapters/adapter-rtsp test` — 29 test methods across 5 classes: `FrameConverterTest` 8, `FfmpegVideoSourceTest` 13 (9 pre-existing + 4 new, docs/MVP2-PLAN.md V-c demuxer-tuning tests), `RtspFeedTransmitterTest` 6, `MediamtxDockerIntegrationTest` 1 (docker-gated TX→wire→RX round trip), `FfmpegVideoSourceLiveManualTest` 1 `@Disabled`. Verified via repeated live runs (clean test run twice consecutively): 0 failures, 1 skipped, docker IT included and passing both times.

## API surface
### `com.drones.vision.adapter.rtsp`
- `final class FfmpegVideoSource implements VideoSourcePort` — supports protocol `"rtsp"` (any URI) and `"file"` (URI scheme must itself be `file`). `supports(StreamDescriptor)`, `open(StreamId, StreamDescriptor): Flow.Publisher<VideoFrame>`, `close(StreamId)`.
  - package-private test seam: `Flow.Publisher<VideoFrame> openAny(StreamId id, URI uri, Map<String,String> options)` — runs the exact production grab loop against any URI (skips the protocol check), letting tests exercise the real FFmpeg decode path against a local file.
  - package-private test seam: `static void configureRtspOptions(FFmpegFrameGrabber grabber, Map<String,String> options)` — applies every RTSP-only grabber option (below) without calling `start()`, so a test can assert exactly what a real grabber would be started with, no live camera/RTSP server needed. Mirrors adapter-publish-hls's `MediamtxStreamPublisher.configureRecorder` seam.
  - Options (all optional):
    - `rtsp_transport` (default `DEFAULT_RTSP_TRANSPORT`="tcp") and `timeout` in **microseconds** (default `DEFAULT_TIMEOUT_MICROS`="10000000" = 10s; applied to both the RTSP demuxer's `timeout` option and the generic `rw_timeout` option) — both only set when `uri.getScheme()` is `"rtsp"`.
    - `loop` (`"true"`/`"false"`, default `false`; malformed values fall back to the default, same lenient idiom as every other option here) — on graceful EOF (`grab()` returns `null`) with `loop=true` and no stop requested, the grabber is **restarted** (`FFmpegFrameGrabber.restart()`, i.e. `stop()`+`start()`, which reopens the file from the beginning) instead of completing the publisher; the frame `sequence` keeps climbing monotonically across restarts, it is never reset. Default `false` — a source loops only when explicitly asked (the simulation layer will ask explicitly, see docs/CYCLES-PLAN.md §1b).
    - **docs/MVP2-PLAN.md V-c, RTSP-only low-latency demuxer tuning** (never applied to `file` sources — see "V-c: RTSP demuxer latency tuning" below for the full verified-facts writeup): `probesize` bytes (default `DEFAULT_PROBESIZE_BYTES`="32768", vs. FFmpeg's own 5,000,000-byte default), `analyzeduration` microseconds (default `DEFAULT_ANALYZE_DURATION_MICROS`="1000000" = 1s, vs. FFmpeg's own 5s/up-to-7s-for-mpegts default), `reorder_queue_size` packets (default `DEFAULT_REORDER_QUEUE_SIZE`="0", pinning this module's own TCP-implied default), `max_delay` microseconds (default `DEFAULT_MAX_DELAY_MICROS`="100000" = 100ms — **applied via `FFmpegFrameGrabber.setMaxDelay(int)`, not `setOption`**, see below for why). All four follow the same device-option-override idiom as `rtsp_transport`/`timeout` (`options.getOrDefault(key, default)`), with lenient malformed-value fallback for `max_delay`'s integer parse.
  - **Real-time pacing (`file` URIs only):** a local file decodes as fast as disk I/O allows, but a simulated drone must feed frames at the file's own rate, like a live camera. Whenever `uri.getScheme()` is `"file"`, the grab loop tracks the delta between successive `grabber.getTimestamp()` values (microseconds) and sleeps the difference between that delta and the wall-clock time actually spent since the previous frame (clamped to zero — never a negative sleep). The pacing baseline (`-1` sentinel = "no previous frame yet") resets on every loop restart, so the first frame of each pass is never delayed. `rtsp` URIs are never paced — the network already paces a live camera. No drift compensation beyond this one monotonic baseline (deliberately kept simple per docs/CYCLES-PLAN.md §1a).
  - nested `private static final class StreamRuntime` — one dedicated platform thread (`rtsp-video-<id>`, not virtual — decoding is CPU-bound) per open, running a blocking `FFmpegFrameGrabber` loop; feeds a `SubmissionPublisher<VideoFrame>` built with `PUBLISHER_BUFFER_CAPACITY`=4 and `publisher.offer(frame, (subscriber, dropped) -> true)` for drop-newest backpressure. Computes `loop`/`paced` once per open (constructor) from the descriptor's options/URI scheme.
- `final class FrameConverter` (package-private, stateless) — `static ByteBuffer copyBgr24(Frame frame)`: copies a JavaCV `Frame`'s BGR24 pixel data into a fresh, tightly-packed heap `ByteBuffer` (strips row stride padding). Throws `IllegalArgumentException` for null frame, missing image data, invalid dimensions, non-3-channel data, or a non-byte-backed image buffer.
- `final class RtspFeedTransmitter implements FeedTransmitterPort` — `RtspFeedTransmitter(URI rtspTargetBase)` (e.g. `rtsp://localhost:8554`; constructor-injected by `vision-app`, same pattern as `adapter-publish-hls`'s `MediamtxStreamPublisher`). `supports(FeedSpec)`: protocol `"rtsp"` and `spec.source()` scheme `file`. `start(FeedId, FeedSpec)`: validates the source file exists/is readable (`IllegalArgumentException` otherwise, synchronously — the only blocking part), then starts one dedicated platform thread (`rtsp-feed-<id>`) and returns immediately with `StreamDescriptor("rtsp", <rtspTargetBase>/feed-<id>, Map.of())` — does not wait for the first frame to reach the wire. `stop(FeedId)`: idempotent, CAS-guarded, interrupt + bounded (`CLOSE_JOIN_TIMEOUT_MILLIS`=20s) thread join.
  - Options: `loop` (`"true"`/`"false"`, **default `true`** — the opposite of `FfmpegVideoSource`'s default `false`, because a transmitted simulation feed exists to be watched/rehearsed indefinitely; same lenient malformed-value-falls-back-to-default parsing idiom).
  - Real-time pacing: duplicates `FfmpegVideoSource`'s timestamp-delta grab-loop pacing (deliberately not shared, see that class's Gotchas).
  - Encoder settings deliberately duplicated from `adapter-publish-hls`'s `MediamtxStreamPublisher` (adapters must not depend on each other): format `"rtsp"`, `rtsp_transport=tcp`, `timeout`="5000000" (5s), codec `AV_CODEC_ID_H264`/`"libx264"`, `preset=ultrafast`, `tune=zerolatency`, pixel format `AV_PIX_FMT_YUV420P`. **Deviation:** frame rate/GOP are derived from the source file's own reported frame rate (`grabber.getFrameRate()`, falling back to `FALLBACK_FRAME_RATE_FPS`=15.0 fps if unusable) rather than `MediamtxStreamPublisher`'s fixed 15fps, and no explicit per-frame `setTimestamp` call is made — the recorder's own auto-incrementing per-`record()`-call PTS is collision-free by construction here (unlike `MediamtxStreamPublisher`, which must reconcile an arbitrary/bursty upstream cadence against a fixed nominal rate).
  - GOP = `round(frameRate * GOP_SECONDS)`, `GOP_SECONDS`=2 (same constant as `MediamtxStreamPublisher`) — i.e. one keyframe roughly every 2 real seconds, **regardless of source file loop length**; see Gotchas for why this matters to RX-side test/consumer code.
  - `ensureQuietLogging()` is **not** re-duplicated a third time: the constructor calls `FfmpegVideoSource.ensureQuietLogging()` directly — both classes live in this same module/package, so this is intra-module reuse, not the cross-adapter-module dependency the duplication rule guards against.

## Conventions
- Plain classes, no Spring — instantiated directly by `vision-app`'s wiring config (`WiringConfiguration#ffmpegVideoSource`).
- Grab loop uses **`grabber.grabImage()`, never `grab()`** (both `FfmpegVideoSource` and `RtspFeedTransmitter`; `adapter-mjpeg`'s transmitter does the same): `grab()` also returns audio/data frames, and mp4 muxers interleave audio up to ~0.5s *ahead* of video — pacing on those look-ahead timestamps slept until wall-clock caught up with the audio track, starving a real 30fps AAC-carrying clip down to ~2 emitted fps (regression test: `fileWithAudioTrackIsPacedByVideoTimestampsNotStalledByAudioLookahead`, which muxes a silent AAC track into its fixture). `grabImage()` skips non-video packets, so pacing sees only the video track's monotonic timeline. Loop runs until `stopRequested` or `grabImage()` returns `null` (graceful EOF, unless `loop=true` restarts).
- `close()`: sets `stopRequested`, interrupts the grab thread (best-effort — native `grab()` may not respond, and a paced source may be mid-sleep, resolved on the next loop iteration), joins up to `CLOSE_JOIN_TIMEOUT_MILLIS`=20s, releases the grabber, closes the publisher. Idempotent via `AtomicBoolean closed`.
- **Native FFmpeg log level pinned to ERROR**: `FfmpegVideoSource`'s no-arg constructor calls the idempotent package-private `static void ensureQuietLogging()`, which calls `avutil.av_log_set_level(avutil.AV_LOG_ERROR)` once per JVM (a `synchronized` static-boolean guard makes every call after the first a no-op). This silences FFmpeg's default AV_LOG_INFO chatter (codec/format banners) *and* AV_LOG_WARNING noise — the driver for ERROR over WARNING is swscale's benign per-frame `deprecated pixel format used, make sure you did set range correctly` spam whenever yuvj-tagged media (MJPEG streams, many mp4s) is decoded, which JavaCV's high-level API cannot avoid per-context; native errors still print. Deliberately duplicated in `adapter-publish-hls`'s `MediamtxStreamPublisher` (adapters must not depend on each other) — see that module's MODULE.md Gotchas for the empirical reasoning behind choosing plain `av_log_set_level` over `org.bytedeco.javacv.FFmpegLogCallback.set()`. **Note:** `adapter-publish-hls`'s in-code comment still names this class by its pre-rename name (`RtspVideoSource`) — out of this task's scope (adapter-publish-hls untouched), flagged here so it isn't mistaken for a real second class. `RtspFeedTransmitter` reuses this same guard directly (`FfmpegVideoSource.ensureQuietLogging()`) rather than duplicating it a third time, since both classes live in this one module — see its own entry above.

## Gotchas
- **Mandatory copy**: `FFmpegFrameGrabber` reuses its native image buffers across `grab()` calls. Every grabbed frame's payload MUST be copied via `FrameConverter.copyBgr24` before being wrapped in an immutable `VideoFrame` (whose compact constructor stores the buffer for the record's lifetime) — never hand out the raw `Frame#image` buffer directly.
- Backpressure is drop-**newest**-on-full via `SubmissionPublisher.offer(..., onDrop -> true)` with a buffer capacity of only 4 — a slow subscriber never blocks capture, per `VideoSourcePort`'s latest-wins contract.
- First FFmpeg-touching test in a fresh module pays real cost for native library extraction — `FfmpegVideoSourceTest.AWAIT_SECONDS`=60 is deliberately generous for exactly this reason; once extracted, runs are fast (~2s observed for the whole class in this environment, most of it the pacing test's deliberate real-time waits).
- `resolveFilename(URI)` special-cases the `file:` scheme (via `Paths.get(uri)`) for both the `openAny` test seam and the real `"file"` protocol — the same code path serves both.
- **Pacing and loop both key off `uri.getScheme()`/options, not the descriptor's `protocol()` string** — `openAny` (used by every FFmpeg-path test, and indirectly by `open()`) computes `paced` from `uri.getScheme().equals("file")` directly, so a `"file"`-protocol descriptor and a raw `file:` URI passed through the test seam behave identically.
- `FFmpegFrameGrabber.restart()` (used for `loop=true`) is JavaCV's own `stop()`+`start()`; `stop()` fully releases the native `AVFormatContext` and `start()` reopens from the constructor-set filename, so it naturally reopens a file at position 0 — no manual seek/rewind needed.
- The pacing test (`fileSourceIsPacedToItsNativeFrameRate`) only asserts a generous **lower** bound on wall-clock time (0.5× the frame-rate-implied duration) — deliberately never asserts an upper bound, since CI scheduling jitter must not flake the test.
- **IMPORTANT for the next C3 task (application/api/app wiring): running `RtspFeedTransmitter` (TX) and `FfmpegVideoSource` (RX) concurrently in the *same JVM process* against the *same* mediamtx path triggers a same-process JavaCV/FFmpeg native contention.** Empirically reproduced outside this module's own tests (a standalone harness, not checked in): with `FfmpegVideoSource`'s RX side left at its default RTSP `timeout`/`rw_timeout` (10s, see its own default above), the *transmitter's* grab/record loop would silently stall for ~10s (matching the RX side's configured timeout, not the TX's own 5s) before mediamtx dropped the now-stale publisher connection ("i/o timeout") and the transmitter's next `record()` failed with `av_interleaved_write_frame() error -32` (EPIPE). Confirmed via a from-scratch minimal repro that the RX side alone (no TX in-process) and the TX side alone (no RX in-process) both run cleanly for 12+ seconds; only the *combination*, in one process, stalls — and reducing the RX side's `timeout` option (e.g. to `"2000000"` = 2s) reliably eliminates it (verified clean across multiple repeated runs). `MediamtxDockerIntegrationTest` demonstrates the fix (passes an explicit short `timeout` option on the RX-side `StreamDescriptor`), but **this is a real risk for `vision-app`'s eventual `transport=rtsp` wiring**, which will run both halves in one process by design (`docs/CYCLES-PLAN.md` §3) — that task should budget time to either apply the same short-RX-timeout workaround in production wiring, or investigate further (e.g. file a JavaCV issue; see `FFmpegFrameRecorder hangs when server connection is broken while streaming` (bytedeco/javacv#1063) for a related report of hangs when multiple recorders/grabbers interact under connection trouble).
- **Mid-GOP RX connects are normal, not a bug**: `RtspFeedTransmitter`'s encoder emits a keyframe only once per `GOP_SECONDS`=2 real seconds (see its entry above), regardless of how short the looped source file is. An RX side that connects between keyframes will log transient `decode_slice_header`/"Missing reference picture" warnings until the next keyframe arrives and decoding self-heals — this is expected RTSP-viewer behavior, not a failure. Test/consumer code must **not** react to "no frames yet" by tearing down and reopening the subscription impatiently: doing so restarts the wait against a new, differently-phased mid-GOP landing and can — as observed while writing `MediamtxDockerIntegrationTest` — never happen to land on a keyframe at all if the reconnect cadence and the GOP period fall into a synchronized "beat frequency". Stay on one subscription for the full timeout budget instead; only reopen on a genuine `onError`/`onComplete`.
- **docs/MVP2-PLAN.md V-c: `max_delay` must go through `setMaxDelay(int)`, not `setOption`.** Verified against JavaCV 1.5.10's own source (`FFmpegFrameGrabber#startUnsafe`): `max_delay` is a real, generic FFmpeg AVOption that a `setOption("max_delay", ...)` call *would* apply during `avformat_open_input` — but JavaCV unconditionally overwrites it immediately afterwards with `oc.max_delay(this.maxDelay)`, its own `maxDelay` Java field (default `-1`), silently discarding anything set the `setOption` way. `probesize`/`analyzeduration`/`reorder_queue_size` have no such dedicated setter in JavaCV and no post-open override, so `setOption` is correct (and the only option) for those three. Anyone adding a new demuxer/grabber option to this module should check JavaCV's own source the same way before assuming `setOption` is sufficient — see the "V-c" section below for the full verification trail.

## V-c: RTSP demuxer latency tuning (docs/MVP2-PLAN.md §V-c)

**Scope: `rtsp` protocol only, `file` untouched.** `StreamRuntime.newGrabber()` calls the new `configureRtspOptions` seam only inside its existing `uri.getScheme().equals("rtsp")` branch — the exact same gate the pre-existing `rtsp_transport`/`timeout` options already used, unchanged. `file` sources (paced local-file simulation) get none of this; `fileProtocolNeverReceivesRtspDemuxerTuning` in `FfmpegVideoSourceTest` pins that contract directly against a real `FFmpegFrameGrabber`'s untouched defaults.

**What changed, mechanically**, all four via the same device-option-override idiom as `rtsp_transport`/`timeout` (`options.getOrDefault(key, default)`):

| Option | Old (FFmpeg default) | New default | Applied via |
|---|---|---|---|
| `probesize` | unset → 5,000,000 bytes (5MB) | `32768` (32 KiB) | `setOption` |
| `analyzeduration` | unset → 5,000,000µs (5s), **7,000,000µs (7s) for mpegts payload** | `1000000` (1s) | `setOption` |
| `reorder_queue_size` | unset → adaptive: `0` packets under `tcp`, `500` under `udp` | `0` packets (explicit) | `setOption` |
| `max_delay` | unset (`-1`) → `100000`µs (100ms), RTSP-demuxer's own `DEFAULT_REORDERING_DELAY` | `100000`µs (100ms, explicit) | **`setMaxDelay(int)`** |

Every default above was verified against real FFmpeg 6.1.1 source (`libavformat/options_table.h`, `demux.c`, `rtsp.c`) fetched and read during this task, not assumed from common blog-post folklore — full citations live in each constant's javadoc in `FfmpegVideoSource.java`.

**Two genuine, verified corrections to the task brief's own framing** (honesty rule):

1. **The "several-second RTSP default" is real, but it's `analyzeduration`'s, not `max_delay`'s.** `libavformat/demux.c`'s `avformat_find_stream_info` resolves an unset (`0`) `analyzeduration` to `5*AV_TIME_BASE` (5s) for most formats — **and a full `7*AV_TIME_BASE` (7s) specifically when the payload is detected as `mpeg`/`mpegts`**, a common RTSP payload for many IP cameras and drone companions. This is the actual multi-second RTSP-connect-stall lever; bounding it to 1s here is the single biggest change in this block.
2. **`max_delay`'s own RTSP-specific default is already a modest 100ms, not several seconds.** `libavformat/rtsp.c` resolves an unset `max_delay` to `DEFAULT_REORDERING_DELAY` = 100,000µs — verified by reading the source, not assumed. The task brief's suggested "500ms, down from a 7s default" would have **loosened**, not tightened, this specific value (the real 7s figure belongs to `analyzeduration`'s mpegts branch above). `DEFAULT_MAX_DELAY_MICROS` is therefore set to `100000` — pinning FFmpeg's own already-good default as living documentation against a future version silently changing `DEFAULT_REORDERING_DELAY` (same intent as V-a's `setMaxBFrames(0)`), not tightening it further: `max_delay` is what gives a jittery/far source's late RTP packets a chance to arrive in order before the demuxer force-delivers (logging FFmpeg's own "max delay reached" warning) — shrinking it below FFmpeg's own chosen balance would trade a little latency for materially worse robustness on exactly the non-ideal links this task asked to reason about.

**`reorder_queue_size=0`'s trade-off, stated honestly.** Under this module's actual (and only exercised) `rtsp_transport=tcp` default, FFmpeg's own adaptive logic already resolves an *unset* `reorder_queue_size` to `0` (TCP guarantees in-order delivery at the transport layer, so a reorder queue buys nothing) — so pinning it at `0` explicitly is a no-op for today's behavior, not a change. But it *is* a real behavior change for a hypothetical future device option overriding `rtsp_transport=udp`: without this pin, a `udp` source would silently inherit FFmpeg's own 500-packet (`RTP_REORDER_QUEUE_DEFAULT_SIZE`) default; with it, that source instead gets `0` — favoring latency over reorder tolerance. A `udp` camera on a genuinely lossy/jittery link would want to override `reorder_queue_size` back up via the same device-option map; this module does not attempt to auto-detect that case.

**Expected effect on far/jittery sources.** `probesize`/`analyzeduration` only affect one-time connect-time stream-info probing, not steady-state decode — a far/jittery source connects faster but is not otherwise affected once streaming starts. `max_delay`/`reorder_queue_size` are the two that matter for jitter tolerance, and both were deliberately left at (not below) FFmpeg's own already-conservative built-in behavior for this module's TCP-default path specifically to avoid regressing robustness on exactly that kind of source — see the two corrections above.

**Existing timeout/transport handling: read first, not regressed.** `rtsp_transport` (default `tcp`, a hard-forced transport, not a soft `rtsp_flags=prefer_tcp` preference — this module never sets `rtsp_flags` at all, so there was nothing to preserve there) and `timeout`/`rw_timeout` (10s default, including the documented same-process JavaCV contention workaround above) are untouched by this task, both in value and in the `uri.getScheme().equals("rtsp")` gating that already existed.

**Devices/overrides.** All four new options are overridable per-device the same way `timeout` already is — no new plumbing invented; `intOption`'s lenient integer parsing (malformed → default, mirroring `StreamRuntime.booleanOption`'s existing idiom) backs `max_delay`'s override path specifically, since it must reach an `int`, not a string option.
