# adapter-rtsp

FFmpeg ingest adapter (IP cameras, drone companions, and local-file simulation) via JavaCV/FFmpeg. Despite the module name (kept for historical/build reasons), it now covers two protocols: `rtsp` (real RTSP/RTP cameras) and `file` (a local video file played back as a simulated live source — drone simulation with zero hardware).

**Depends on:** vision-domain, org.bytedeco:javacv, org.bytedeco:ffmpeg-platform-gpl · **Used by:** vision-app
**Build/test:** `./mvnw -B -pl adapters/adapter-rtsp test` — 17 test methods across 3 classes (`FrameConverterTest` 8, `FfmpegVideoSourceTest` 8, `FfmpegVideoSourceLiveManualTest` 1 `@Disabled`), verified via a live run: 0 failures, 1 skipped.

## API surface
### `com.drones.vision.adapter.rtsp`
- `final class FfmpegVideoSource implements VideoSourcePort` — supports protocol `"rtsp"` (any URI) and `"file"` (URI scheme must itself be `file`). `supports(StreamDescriptor)`, `open(StreamId, StreamDescriptor): Flow.Publisher<VideoFrame>`, `close(StreamId)`.
  - package-private test seam: `Flow.Publisher<VideoFrame> openAny(StreamId id, URI uri, Map<String,String> options)` — runs the exact production grab loop against any URI (skips the protocol check), letting tests exercise the real FFmpeg decode path against a local file.
  - Options (all optional):
    - `rtsp_transport` (default `DEFAULT_RTSP_TRANSPORT`="tcp") and `timeout` in **microseconds** (default `DEFAULT_TIMEOUT_MICROS`="10000000" = 10s; applied to both the RTSP demuxer's `timeout` option and the generic `rw_timeout` option) — both only set when `uri.getScheme()` is `"rtsp"`.
    - `loop` (`"true"`/`"false"`, default `false`; malformed values fall back to the default, same lenient idiom as every other option here) — on graceful EOF (`grab()` returns `null`) with `loop=true` and no stop requested, the grabber is **restarted** (`FFmpegFrameGrabber.restart()`, i.e. `stop()`+`start()`, which reopens the file from the beginning) instead of completing the publisher; the frame `sequence` keeps climbing monotonically across restarts, it is never reset. Default `false` — a source loops only when explicitly asked (the simulation layer will ask explicitly, see docs/CYCLES-PLAN.md §1b).
  - **Real-time pacing (`file` URIs only):** a local file decodes as fast as disk I/O allows, but a simulated drone must feed frames at the file's own rate, like a live camera. Whenever `uri.getScheme()` is `"file"`, the grab loop tracks the delta between successive `grabber.getTimestamp()` values (microseconds) and sleeps the difference between that delta and the wall-clock time actually spent since the previous frame (clamped to zero — never a negative sleep). The pacing baseline (`-1` sentinel = "no previous frame yet") resets on every loop restart, so the first frame of each pass is never delayed. `rtsp` URIs are never paced — the network already paces a live camera. No drift compensation beyond this one monotonic baseline (deliberately kept simple per docs/CYCLES-PLAN.md §1a).
  - nested `private static final class StreamRuntime` — one dedicated platform thread (`rtsp-video-<id>`, not virtual — decoding is CPU-bound) per open, running a blocking `FFmpegFrameGrabber` loop; feeds a `SubmissionPublisher<VideoFrame>` built with `PUBLISHER_BUFFER_CAPACITY`=4 and `publisher.offer(frame, (subscriber, dropped) -> true)` for drop-newest backpressure. Computes `loop`/`paced` once per open (constructor) from the descriptor's options/URI scheme.
- `final class FrameConverter` (package-private, stateless) — `static ByteBuffer copyBgr24(Frame frame)`: copies a JavaCV `Frame`'s BGR24 pixel data into a fresh, tightly-packed heap `ByteBuffer` (strips row stride padding). Throws `IllegalArgumentException` for null frame, missing image data, invalid dimensions, non-3-channel data, or a non-byte-backed image buffer.

## Conventions
- Plain classes, no Spring — instantiated directly by `vision-app`'s wiring config (`WiringConfiguration#ffmpegVideoSource`).
- Grab loop runs until `stopRequested` or `grabber.grab()` returns `null` (graceful EOF, e.g. a finite file source, unless `loop=true` restarts it instead); audio/data-only frames (empty/null `frame.image`) are silently skipped — but a paced source still updates its pacing baseline for every grabbed frame (audio or video), not just the ones that get published.
- `close()`: sets `stopRequested`, interrupts the grab thread (best-effort — native `grab()` may not respond, and a paced source may be mid-sleep, resolved on the next loop iteration), joins up to `CLOSE_JOIN_TIMEOUT_MILLIS`=20s, releases the grabber, closes the publisher. Idempotent via `AtomicBoolean closed`.
- **Native FFmpeg log level pinned to WARNING**: `FfmpegVideoSource`'s no-arg constructor calls the idempotent package-private `static void ensureQuietLogging()`, which calls `avutil.av_log_set_level(avutil.AV_LOG_WARNING)` once per JVM (a `synchronized` static-boolean guard makes every call after the first a no-op). This silences FFmpeg's default AV_LOG_INFO chatter (codec/format banners) while leaving warnings/errors on stdout/stderr untouched. Deliberately duplicated in `adapter-publish-hls`'s `MediamtxStreamPublisher` (adapters must not depend on each other) — see that module's MODULE.md Gotchas for the empirical reasoning behind choosing plain `av_log_set_level` over `org.bytedeco.javacv.FFmpegLogCallback.set()`. **Note:** `adapter-publish-hls`'s in-code comment still names this class by its pre-rename name (`RtspVideoSource`) — out of this task's scope (adapter-publish-hls untouched), flagged here so it isn't mistaken for a real second class.

## Gotchas
- **Mandatory copy**: `FFmpegFrameGrabber` reuses its native image buffers across `grab()` calls. Every grabbed frame's payload MUST be copied via `FrameConverter.copyBgr24` before being wrapped in an immutable `VideoFrame` (whose compact constructor stores the buffer for the record's lifetime) — never hand out the raw `Frame#image` buffer directly.
- Backpressure is drop-**newest**-on-full via `SubmissionPublisher.offer(..., onDrop -> true)` with a buffer capacity of only 4 — a slow subscriber never blocks capture, per `VideoSourcePort`'s latest-wins contract.
- First FFmpeg-touching test in a fresh module pays real cost for native library extraction — `FfmpegVideoSourceTest.AWAIT_SECONDS`=60 is deliberately generous for exactly this reason; once extracted, runs are fast (~2s observed for the whole class in this environment, most of it the pacing test's deliberate real-time waits).
- `resolveFilename(URI)` special-cases the `file:` scheme (via `Paths.get(uri)`) for both the `openAny` test seam and the real `"file"` protocol — the same code path serves both.
- **Pacing and loop both key off `uri.getScheme()`/options, not the descriptor's `protocol()` string** — `openAny` (used by every FFmpeg-path test, and indirectly by `open()`) computes `paced` from `uri.getScheme().equals("file")` directly, so a `"file"`-protocol descriptor and a raw `file:` URI passed through the test seam behave identically.
- `FFmpegFrameGrabber.restart()` (used for `loop=true`) is JavaCV's own `stop()`+`start()`; `stop()` fully releases the native `AVFormatContext` and `start()` reopens from the constructor-set filename, so it naturally reopens a file at position 0 — no manual seek/rewind needed.
- The pacing test (`fileSourceIsPacedToItsNativeFrameRate`) only asserts a generous **lower** bound on wall-clock time (0.5× the frame-rate-implied duration) — deliberately never asserts an upper bound, since CI scheduling jitter must not flake the test.
