# adapter-rtsp

FFmpeg ingest **and** transmit adapter (IP cameras, drone companions, and local-file simulation) via JavaCV/FFmpeg. Despite the module name (kept for historical/build reasons), it covers:
- **RX** (`VideoSourcePort`), via `FfmpegVideoSource`: `rtsp` (real RTSP/RTP cameras), `file` (a local video file played back as a simulated live source — drone simulation with zero hardware), and — docs/plans/active/DRONE-INFRA-PLAN.md I-h — `srt` (SRT, low-latency drone video over lossy cellular/long-range links) and `udp` (raw UDP/MPEG-TS, the classic ground-station/encoder output) protocols.
- **TX** (`FeedTransmitterPort`, `docs/main/CYCLES-PLAN.md` §0/§3): pushes a local video file to a real RTSP target (e.g. mediamtx) so this module's own RX half (or any real RTSP client) ingests it like live hardware — simulation infrastructure, not egress — via `RtspFeedTransmitter`.

**Depends on:** vision-domain, org.bytedeco:javacv, org.bytedeco:ffmpeg-platform-gpl · **Used by:** vision-app
**Build/test:** `./mvnw -B -pl adapters/adapter-rtsp test` — 48 test methods across 8 classes: `FrameConverterTest` 8, `FfmpegVideoSourceTest` 12 (real-loopback/end-to-end coverage of `open()`/`openAny()` — the per-protocol option-seam unit tests that used to live here moved to `FfmpegGrabberOptionsTest` below, docs/plans/active/LAYERING-REFACTOR-PLAN.md §5.1), `FfmpegGrabberOptionsTest` 9 (the RTSP V-c + SRT/UDP option-seam unit tests, new home), `FfmpegSettingsTest` 8 (new — the settings record's `defaults()`/compact-ctor validation), `RealtimePacerTest` 3 (new — the shared pacer, previously only exercised indirectly), `RtspFeedTransmitterTest` 6, `MediamtxDockerIntegrationTest` 1 (docker-gated TX→wire→RX round trip), `FfmpegVideoSourceLiveManualTest` 1 `@Disabled`. Verified via repeated live runs (`clean test` run twice consecutively): 0 failures, 1 skipped, docker IT included and passing every time.

**docs/plans/active/LAYERING-REFACTOR-PLAN.md §5.1, wave E1 (internal restructuring only, no behavior change):** the pre-split 912-line `FfmpegVideoSource` was split four ways — `FfmpegSettings` (every environment/tuning literal, a plain validated record), `FfmpegGrabberOptions` (per-protocol grabber option/default config, the RTSP V-c + SRT + UDP tuning surface), `FfmpegGrabLoop` (the promoted former nested `StreamRuntime`, one dedicated grab thread per open), and a narrowed `FfmpegVideoSource` (~130 lines: just `supports`/`open`/`openAny`/`close` plus the native-log-quieting guard both classes in this module share). A new `RealtimePacer` class replaces the identical timestamp-delta pacing logic that used to be duplicated verbatim in both `FfmpegVideoSource`'s grab loop and `RtspFeedTransmitter`'s transmit loop. See "Layering refactor" under Status below for the full before/after mapping.

## API surface
### `com.drones.vision.adapter.rtsp`

Module layout after docs/plans/active/LAYERING-REFACTOR-PLAN.md §5.1's wave E1 split (internal restructuring
only — every public constructor either is unchanged or gained a pure-addition overload; no protocol/
option/default behavior changed):

- `final class FfmpegVideoSource implements VideoSourcePort` (~130 lines — the thin `VideoSourcePort`
  entry point only) — supports protocol `"rtsp"` (any URI) and `"file"`/`"srt"`/`"udp"` (URI scheme
  must itself match the protocol string — `supports()` checks `uri.getScheme()` for these three,
  unlike `rtsp` which accepts any URI). `supports(StreamDescriptor)`, `open(StreamId,
  StreamDescriptor): Flow.Publisher<VideoFrame>`, `close(StreamId)`.
  - `FfmpegVideoSource()` — uses `FfmpegSettings.defaults()`, byte-identical to this class's
    pre-split behavior; still the constructor `vision-app`'s wiring calls.
  - `FfmpegVideoSource(FfmpegSettings settings)` — new, additive overload for constructor-injecting
    tunables; not yet wired by `vision-app` (a later wave, docs/plans/active/LAYERING-REFACTOR-PLAN.md §7 F1,
    adds the Spring `VisionRtspProperties` binding).
  - **Listen vs. dial** (docs/plans/active/DRONE-INFRA-PLAN.md I-h, mirroring adapter-mavlink's own listen-vs-dial
    documentation discipline): `rtsp` always dials out (the app connects to the camera). `file`
    opens a local path (neither). `srt` dials out as `caller` (default) or binds/listens as
    `listener` when `mode=listener` is given or inferred. `udp` always binds/listens — UDP is
    connectionless, so opening `udp://host:port` for reading means "receive datagrams sent to this
    host:port", never "connect to a remote peer".
  - package-private test seam: `Flow.Publisher<VideoFrame> openAny(StreamId id, URI uri,
    Map<String,String> options)` — runs the exact production grab loop (via `FfmpegGrabLoop`)
    against any URI (skips the protocol check), letting tests exercise the real FFmpeg decode path
    against a local file.
  - package-private constants `PROTOCOL_RTSP`/`PROTOCOL_FILE`/`PROTOCOL_SRT`/`PROTOCOL_UDP` and
    `OPTION_LOOP`/`DEFAULT_LOOP` — shared within the module by `FfmpegGrabberOptions`/`FfmpegGrabLoop`
    (registry dispatch keys, out of docs/plans/active/LAYERING-REFACTOR-PLAN.md §1.3's config-extraction scope).
  - `static synchronized void ensureQuietLogging()` — idempotent native-log-quieting guard (unchanged
    from before the split); `RtspFeedTransmitter` calls this directly rather than duplicating it.
- `final class FfmpegGrabberOptions` (package-private, static-methods-only, ~400 lines incl. javadoc)
  — every per-protocol `FFmpegFrameGrabber` option/default seam, promoted out of `FfmpegVideoSource`.
  Every FFmpeg AVOption *name* (`OPTION_RTSP_TRANSPORT`, `OPTION_SRT_MODE`, `SRT_MODE_CALLER`/
  `SRT_MODE_LISTENER`, `OPTION_UDP_FIFO_SIZE`, ...) still lives here as a constant (registry/protocol
  vocabulary, out of config-extraction scope); every tunable **default value** now comes from an
  injected `FfmpegSettings` parameter instead of a `private static final` constant.
  - `static FFmpegFrameGrabber newGrabber(URI uri, Map<String,String> options, FfmpegSettings settings)`
    — the single grabber-construction entry point `FfmpegGrabLoop` uses; dispatches to the three
    `configure*Options` methods below by `uri.getScheme()`, or applies none for `file`.
  - package-private test seam: `static void configureRtspOptions(FFmpegFrameGrabber grabber,
    Map<String,String> options, FfmpegSettings settings)` — applies every RTSP-only grabber option
    without calling `start()`, so a test can assert exactly what a real grabber would be started
    with, no live camera/RTSP server needed. Mirrors adapter-publish-hls's
    `MediamtxStreamPublisher.configureRecorder` seam.
  - package-private test seam: `static void configureSrtOptions(FFmpegFrameGrabber grabber, URI uri,
    Map<String,String> options, FfmpegSettings settings)` — applies every SRT-only grabber option,
    same no-`start()` idiom as `configureRtspOptions`.
  - package-private test seam: `static void configureUdpOptions(FFmpegFrameGrabber grabber,
    Map<String,String> options, FfmpegSettings settings)` — applies every UDP-only grabber option
    plus forces `setFormat("mpegts")`, same no-`start()` idiom.
  - RTSP options (all optional, defaults now sourced from `FfmpegSettings`):
    - `rtsp_transport` (default `FfmpegSettings#transport()`="tcp") and `timeout` in **microseconds**
      (default `FfmpegSettings#openTimeout()`=10s; applied to both the RTSP demuxer's `timeout`
      option and the generic `rw_timeout` option) — both only set when `uri.getScheme()` is `"rtsp"`.
    - `loop` (`"true"`/`"false"`, default `false`, `FfmpegVideoSource.DEFAULT_LOOP` — a business
      default, not a `FfmpegSettings` tunable; malformed values fall back to the default, same
      lenient idiom as every other option here) — on graceful EOF (`grab()` returns `null`) with
      `loop=true` and no stop requested, the grabber is **restarted** (`FFmpegFrameGrabber.restart()`,
      i.e. `stop()`+`start()`, which reopens the file from the beginning) instead of completing the
      publisher; the frame `sequence` keeps climbing monotonically across restarts, it is never
      reset. Default `false` — a source loops only when explicitly asked (the simulation layer will
      ask explicitly, see docs/main/CYCLES-PLAN.md §1b).
    - **docs/plans/done/MVP2-PLAN.md V-c, RTSP-only low-latency demuxer tuning** (never applied to `file`
      sources — see "V-c: RTSP demuxer latency tuning" below for the full verified-facts writeup):
      `probesize` bytes (default `FfmpegSettings#probesizeBytes()`=32768, vs. FFmpeg's own
      5,000,000-byte default), `analyzeduration` microseconds (default
      `FfmpegSettings#analyzeDuration()`=1s, vs. FFmpeg's own 5s/up-to-7s-for-mpegts default),
      `reorder_queue_size` packets (default `FfmpegSettings#reorderQueueSize()`=0, pinning this
      module's own TCP-implied default), `max_delay` microseconds (default
      `FfmpegSettings#maxDelay()`=100ms — **applied via `FFmpegFrameGrabber.setMaxDelay(int)`, not
      `setOption`**, see below for why). All four follow the same device-option-override idiom as
      `rtsp_transport`/`timeout` (`options.getOrDefault(key, default)`), with lenient malformed-value
      fallback for `max_delay`'s integer parse.
  - **SRT options** (docs/plans/active/DRONE-INFRA-PLAN.md I-h, `configureSrtOptions`, only applied when
    `uri.getScheme()` is `"srt"`) — every FFmpeg AVOption name/default below was verified against
    this module's actual pinned `ffmpeg-platform-gpl` 6.1.1-1.5.10 native binary (extracted the
    published jar, grepped `libavformat.so.60`'s strings for
    `SRTO_LATENCY`/`SRTO_PASSPHRASE`/`SRTO_STREAMID`/the `caller`/`listener`/`rendezvous` mode
    constants — all present, confirming `--enable-libsrt`), not assumed from FFmpeg's docs:
    | Option | Maps to | Default | Notes |
    |---|---|---|---|
    | `latency` | FFmpeg `latency` AVOption | `FfmpegSettings#srtLatency()`=120ms | **Unit conversion**: this module's option is milliseconds (docs/plans/active/DRONE-INFRA-PLAN.md I-h's contract unit); FFmpeg's own `latency` AVOption is **microseconds** — `configureSrtOptions` multiplies by 1000 before calling `setOption`. 120ms matches libsrt's own built-in default exactly. |
    | `mode` | FFmpeg `mode` AVOption (`caller`/`listener`) | inferred via `defaultSrtMode(URI)`: `listener` for an any-address host (`0.0.0.0`/`::`/unset), `caller` otherwise | Only `caller`/`listener` exposed (not FFmpeg's third `rendezvous`) per the frozen contract. |
    | `streamid` | FFmpeg `streamid` AVOption | none (absent = unset) | Pure passthrough. |
    | `passphrase` | FFmpeg `passphrase` AVOption | none (absent = no encryption) | Pure passthrough; when set, `configureSrtOptions` also sets FFmpeg's `pbkeylen` AVOption to `DEFAULT_SRT_PBKEYLEN`="16" (a fixed `FfmpegGrabberOptions` constant, **not** promoted into `FfmpegSettings` — see that record's own javadoc for why) — not strictly required (libsrt already defaults an unset `pbkeylen` to 16 bytes when a passphrase is set) but pins the key length as living documentation rather than relying on an unstated library default. |
    - `loop` is accepted but has no useful effect for `srt` (a live source has no bounded content to restart from) — see class javadoc.
    - **Applied via `setOption`, not the `srt://` URL's query string** — both are documented FFmpeg mechanisms; this module chose `setOption` for one idiom across rtsp/srt/udp and to avoid hand-building a query string on top of a caller-supplied URI that may already carry its own. Verified (not assumed) that `setOption` actually reaches the SRT protocol's own private AVOptions in this exact JavaCV/FFmpeg build: a standalone probe that set `mode=listener` via `setOption` measurably reached the SRT listener accept code path (not the caller-connect path) — see the SRT Gotcha below for the full investigation, including why the URL-query-string alternative was also tried and made no difference to the actual (unrelated) connectivity problem found.
  - **UDP/MPEG-TS options** (docs/plans/active/DRONE-INFRA-PLAN.md I-h, `configureUdpOptions`, only applied when `uri.getScheme()` is `"udp"`):
    | Option | Maps to | Default | Notes |
    |---|---|---|---|
    | `fifo_size` | FFmpeg `fifo_size` AVOption (packets of 188 bytes) | `FfmpegSettings#udpFifoSizePackets()`=512 (~96KB) | vs. FFmpeg's own unset default of 7×4096=28,672 packets (~5.4MB) — tightened for latency, same intent as the RTSP V-c tuning above. |
    | `overrun_nonfatal` | FFmpeg `overrun_nonfatal` AVOption | `FfmpegGrabberOptions.DEFAULT_UDP_OVERRUN_NONFATAL`="1" (true; a fixed posture, **not** promoted into `FfmpegSettings` — see that record's own javadoc) | vs. FFmpeg's own default `false` — a full receive ring buffer survives (drops) instead of aborting the whole stream. |
    | `buffer_size` | FFmpeg `buffer_size` AVOption (OS `SO_RCVBUF`, bytes) | none (absent = OS default) | Pure passthrough — a system-level knob this module has no basis to override by default. |
    - **Format always forced to `mpegts`** via `FFmpegFrameGrabber.setFormat("mpegts")` — a raw `udp://` URL carries no container self-description the way `rtsp://`'s SDP `DESCRIBE` does, so an explicit hint removes format auto-detection as a failure mode entirely; docs/plans/active/DRONE-INFRA-PLAN.md I-h's contract already assumes MPEG-TS for `udp` ("MPEG-TS assumed"), so this names the guaranteed container rather than guessing. **Honesty note**: an ad hoc local A/B check found auto-probing just as reliable as an explicit `setFormat` on this module's quiet loopback test (5/5 either way) — kept on contract-correctness grounds, not a measured reliability delta on a real lossier/jitterier link.
    - **An internal `timeout` AVOption (default `FfmpegSettings#udpTimeout()`=5s) is always applied and is *not* one of the three options above** — it is not exposed via `StreamDescriptor#options()` at all, just a safety default. This is a genuine production-robustness fix, not a test convenience — see the Gotcha below ("a udp source can wedge every other video source in the process") for the serious finding that motivated it.
    - `loop` is accepted but has no useful effect for `udp` (same reasoning as `srt`).
- `final class FfmpegGrabLoop` (package-private — one dedicated grab thread per `open`, promoted out
  of `FfmpegVideoSource`'s former nested `private static final class StreamRuntime`; zero references
  back to the `FfmpegVideoSource` instance that created it — every dependency, including
  `FfmpegSettings`, is passed in through its own constructor) — one dedicated platform thread
  (`rtsp-video-<id>`, not virtual — decoding is CPU-bound) per open, running a blocking
  `FFmpegFrameGrabber` loop via `FfmpegGrabberOptions.newGrabber`; feeds a `SubmissionPublisher<VideoFrame>`
  built with `FfmpegSettings#publisherBufferCapacity()`=4 and `publisher.offer(frame, (subscriber,
  dropped) -> true)` for drop-newest backpressure. Computes `loop`/`paced` once per open (constructor)
  from the descriptor's options/URI scheme. Owns its own `System.Logger` (the WARN-on-open-failure log
  described in Gotchas below now logs under `FfmpegGrabLoop`'s own class name, not `FfmpegVideoSource`'s
  — a cosmetic difference from this move, no test asserts on logger identity). `close()` joins its
  grab thread bounded by `FfmpegSettings#closeJoinTimeout()`=20s.
  - **Real-time pacing (`file` URIs only)**, via the shared `RealtimePacer` (below): a local file
    decodes as fast as disk I/O allows, but a simulated drone must feed frames at the file's own
    rate, like a live camera. Whenever `uri.getScheme()` is `"file"`, the grab loop calls
    `pacer.paceTo(grabber.getTimestamp())` every frame; `pacer.reset()` on every loop restart, so the
    first frame of each pass is never delayed. `rtsp`/`srt`/`udp` URIs are never paced — the network
    already paces a live source.
- `final class RealtimePacer` (package-private, stateful, not thread-safe — one instance per grab/
  transmit loop) — the timestamp-delta real-time pacing logic shared between `FfmpegGrabLoop` (`file`
  sources) and `RtspFeedTransmitter`'s transmit loop, previously duplicated verbatim between the two.
  `void paceTo(long timestampMicros)` — sleeps the difference between the media-timestamp delta and
  the wall-clock time actually spent since the previous call, clamped to zero (never a negative
  sleep); the first call after construction or `reset()` never sleeps. `void reset()` — call after a
  loop restart (e.g. `loop=true` on EOF), since the restarted media's timeline starts over too.
- `record FfmpegSettings(...)` (public — every environment/tuning literal this module previously
  scattered across `private static final` constants on `FfmpegVideoSource`/`RtspFeedTransmitter`;
  docs/plans/active/LAYERING-REFACTOR-PLAN.md §2.2's frozen `vision.rtsp` property-key contract) — plain,
  framework-free, compact-constructor validated (non-blank `transport`, positive durations/counts,
  non-null `transmit`). `static FfmpegSettings defaults()` reproduces every one of those old literals
  exactly (a structural move, not a retune): `transport`="tcp", `openTimeout`=10s,
  `probesizeBytes`=32768, `analyzeDuration`=1s, `reorderQueueSize`=0, `maxDelay`=100ms,
  `udpTimeout`=5s, `udpFifoSizePackets`=512, `srtLatency`=120ms, `publisherBufferCapacity`=4,
  `closeJoinTimeout`=20s, and a nested `Transmit` record (`gopSeconds`=2, `preset`="ultrafast",
  `fallbackFps`=15.0, `connectTimeout`=5s, `tune`="zerolatency") for `RtspFeedTransmitter`-only
  tunables. `static String microsOption(Duration)` — converts a duration to the whole-microsecond
  decimal string every microsecond-resolution FFmpeg AVOption in this module expects.
  - **One genuine collapse, not just a move**: `transport` is now a *single* field feeding both
    `FfmpegGrabberOptions.configureRtspOptions`'s RX-side `rtsp_transport` default **and**
    `RtspFeedTransmitter`'s TX-side hardcoded push transport — pre-split, these were two separately
    hardcoded `"tcp"` literals that happened to already agree; same for `closeJoinTimeout`, which
    both `FfmpegGrabLoop` and `RtspFeedTransmitter`'s `FeedRuntime` already used identically (20s)
    before this extraction.
  - **Two module tunables deliberately not promoted here** (a judgment call, flagged for the next
    reader rather than silently decided): `FfmpegGrabberOptions.DEFAULT_UDP_OVERRUN_NONFATAL` (a
    fixed survive-vs-abort posture, not a scalar the frozen §2.2 key table names) and the SRT
    `pbkeylen` pin (living documentation of libsrt's own already-built-in default — a protocol/spec
    constant, not a deployment choice, per docs/plans/active/LAYERING-REFACTOR-PLAN.md §1.3's explicit
    out-of-scope list). Both stay as named constants in `FfmpegGrabberOptions` next to the option
    they configure.
- `final class FrameConverter` (package-private, stateless) — `static ByteBuffer copyBgr24(Frame frame)`: copies a JavaCV `Frame`'s BGR24 pixel data into a fresh, tightly-packed heap `ByteBuffer` (strips row stride padding). Throws `IllegalArgumentException` for null frame, missing image data, invalid dimensions, non-3-channel data, or a non-byte-backed image buffer.
- `final class RtspFeedTransmitter implements FeedTransmitterPort` — `supports(FeedSpec)`: protocol `"rtsp"` and `spec.source()` scheme `file`. `start(FeedId, FeedSpec)`: validates the source file exists/is readable (`IllegalArgumentException` otherwise, synchronously — the only blocking part), then starts one dedicated platform thread (`rtsp-feed-<id>`) and returns immediately with `StreamDescriptor("rtsp", <rtspTargetBase>/feed-<id>, Map.of())` — does not wait for the first frame to reach the wire. `stop(FeedId)`: idempotent, CAS-guarded, interrupt + bounded (`FfmpegSettings#closeJoinTimeout()`=20s) thread join.
  - `RtspFeedTransmitter(URI rtspTargetBase)` — uses `FfmpegSettings.defaults()`; still the constructor `vision-app`'s wiring calls (e.g. `rtsp://localhost:8554`).
  - `RtspFeedTransmitter(URI rtspTargetBase, FfmpegSettings settings)` — new, additive overload for constructor-injecting encoder/timeout tunables; not yet wired by `vision-app` (same later-wave note as `FfmpegVideoSource`'s two-arg constructor above).
  - Options: `loop` (`"true"`/`"false"`, **default `true`** — the opposite of `FfmpegVideoSource`'s default `false`, because a transmitted simulation feed exists to be watched/rehearsed indefinitely; same lenient malformed-value-falls-back-to-default parsing idiom).
  - Real-time pacing: shares `RealtimePacer` with `FfmpegGrabLoop`'s own `file`-source pacing (previously duplicated verbatim, see that class's entry above).
  - Encoder settings deliberately duplicated from `adapter-publish-hls`'s `MediamtxStreamPublisher` (adapters must not depend on each other): format `"rtsp"`, `rtsp_transport`=`FfmpegSettings#transport()`, `timeout`=`FfmpegSettings.Transmit#connectTimeout()`=5s, codec `AV_CODEC_ID_H264`/`"libx264"`, `preset`=`FfmpegSettings.Transmit#preset()`="ultrafast", `tune`=`FfmpegSettings.Transmit#tune()`="zerolatency", pixel format `AV_PIX_FMT_YUV420P`. **Deviation:** frame rate/GOP are derived from the source file's own reported frame rate (`grabber.getFrameRate()`, falling back to `FfmpegSettings.Transmit#fallbackFps()`=15.0 fps if unusable) rather than `MediamtxStreamPublisher`'s fixed 15fps, and no explicit per-frame `setTimestamp` call is made — the recorder's own auto-incrementing per-`record()`-call PTS is collision-free by construction here (unlike `MediamtxStreamPublisher`, which must reconcile an arbitrary/bursty upstream cadence against a fixed nominal rate).
  - GOP = `round(frameRate * transmit.gopSeconds())`, `gopSeconds`=2 (same constant as `MediamtxStreamPublisher`) — i.e. one keyframe roughly every 2 real seconds, **regardless of source file loop length**; see Gotchas for why this matters to RX-side test/consumer code.
  - `ensureQuietLogging()` is **not** re-duplicated a third time: the constructor calls `FfmpegVideoSource.ensureQuietLogging()` directly — both classes live in this same module/package, so this is intra-module reuse, not the cross-adapter-module dependency the duplication rule guards against.

## Conventions
- Plain classes, no Spring — instantiated directly by `vision-app`'s wiring config (`WiringConfiguration#ffmpegVideoSource`).
- **Logging: `System.Logger`, not SLF4J** — `private static final System.Logger LOG = System.getLogger(...)`, matching every other adapter in this codebase (e.g. `adapter-publish-hls`'s `MediamtxStreamPublisher`) and `RtspFeedTransmitter`'s own pre-existing convention in this same module. `FfmpegGrabLoop` owns the RX-side `LOG` field (see "RX-side open-failure visibility" below); pre-E1-split this lived directly on `FfmpegVideoSource`, previously the only class in this module with zero logging of its own.
- Grab loop uses **`grabber.grabImage()`, never `grab()`** (both `FfmpegGrabLoop` and `RtspFeedTransmitter`; `adapter-mjpeg`'s transmitter does the same): `grab()` also returns audio/data frames, and mp4 muxers interleave audio up to ~0.5s *ahead* of video — pacing on those look-ahead timestamps slept until wall-clock caught up with the audio track, starving a real 30fps AAC-carrying clip down to ~2 emitted fps (regression test: `fileWithAudioTrackIsPacedByVideoTimestampsNotStalledByAudioLookahead`, which muxes a silent AAC track into its fixture). `grabImage()` skips non-video packets, so pacing sees only the video track's monotonic timeline. Loop runs until `stopRequested` or `grabImage()` returns `null` (graceful EOF, unless `loop=true` restarts).
- `close()`: sets `stopRequested`, interrupts the grab thread (best-effort — native `grab()` may not respond, and a paced source may be mid-sleep, resolved on the next loop iteration), joins up to `FfmpegSettings#closeJoinTimeout()`=20s, releases the grabber, closes the publisher. Idempotent via `AtomicBoolean closed`.
- **Native FFmpeg log level pinned to ERROR**: `FfmpegVideoSource`'s no-arg constructor calls the idempotent package-private `static void ensureQuietLogging()`, which calls `avutil.av_log_set_level(avutil.AV_LOG_ERROR)` once per JVM (a `synchronized` static-boolean guard makes every call after the first a no-op). This silences FFmpeg's default AV_LOG_INFO chatter (codec/format banners) *and* AV_LOG_WARNING noise — the driver for ERROR over WARNING is swscale's benign per-frame `deprecated pixel format used, make sure you did set range correctly` spam whenever yuvj-tagged media (MJPEG streams, many mp4s) is decoded, which JavaCV's high-level API cannot avoid per-context; native errors still print. Deliberately duplicated in `adapter-publish-hls`'s `MediamtxStreamPublisher` (adapters must not depend on each other) — see that module's MODULE.md Gotchas for the empirical reasoning behind choosing plain `av_log_set_level` over `org.bytedeco.javacv.FFmpegLogCallback.set()`. **Note:** `adapter-publish-hls`'s in-code comment still names this class by its pre-rename name (`RtspVideoSource`) — out of this task's scope (adapter-publish-hls untouched), flagged here so it isn't mistaken for a real second class. `RtspFeedTransmitter` reuses this same guard directly (`FfmpegVideoSource.ensureQuietLogging()`) rather than duplicating it a third time, since both classes live in this one module — see its own entry above.

## Gotchas
- **RX-side open-failure visibility (found investigating a real "frozen video" report, a dead RTSP-loopback simulation feed)**: before this note, `FfmpegVideoSource.StreamRuntime#runGrabLoop`'s catch block (an unrecoverable `grabber.start()`/`grabImage()` failure — e.g. an RTSP `DESCRIBE` 404 against a path nothing is publishing to) only called `publisher.closeExceptionally(e)`, with **zero application-level logging anywhere in this class**. `vision-application`'s `SupervisedPublisher` (the stream supervisor wrapping every `VideoSourcePort#open`, docs/plans/done/MVP2-PLAN.md §S-a) retries such a failure forever with a 1s→30s exponential backoff and logs nothing itself either — so a permanently-dead source (e.g. a TX feed transmitter that never came back after a JVM restart, see `DefaultSimulationService`'s own Gotcha in vision-application/MODULE.md) produced an *endless*, silent retry loop: the only visible symptom was FFmpeg's own native stderr (suppressed to `AV_LOG_ERROR` by this class's own `ensureQuietLogging`) and a repeating 404 nobody could see in application logs. **Fixed**: `FfmpegVideoSource` gained a `LOG` field and now logs one `WARNING` per failed open/grab attempt — `"Video source error for stream <id> at <uri> (consecutive failure <n>); will be retried with backoff by the stream supervisor, dropping frames until it recovers"`, with the causing exception attached — via a small local `Map<StreamId, AtomicInteger> consecutiveOpenFailures` (purely a logging aid, not a supervision mechanism of its own: this class has no idea what backoff delay `SupervisedPublisher` is actually using, it only knows "this stream has now failed to open N times in a row"). Reset to zero the moment `grabber.start()` succeeds (proof the specific "can't even connect" failure mode has cleared, mirroring `MediamtxStreamPublisher.StreamState`'s own reset-on-recovery convention in adapter-publish-hls) and removed entirely on an explicit `close(StreamId)`. This does **not** fix the underlying "nothing re-publishes a dead TX feed" gap — it only makes the resulting endless retry loop observable in application logs instead of silent; see vision-application/MODULE.md's own Gotcha for the actual root cause and a recommended fix. **Post-E1-split note**: this logic (the `LOG` field, the `consecutiveOpenFailures` map's read/increment, the WARN log call) now lives in `FfmpegGrabLoop#runGrabLoop` (promoted out of `FfmpegVideoSource`'s former nested `StreamRuntime`, docs/plans/active/LAYERING-REFACTOR-PLAN.md §5.1) — `FfmpegVideoSource` itself just owns the shared `Map<StreamId, AtomicInteger>` instance and passes it into each `FfmpegGrabLoop` it constructs. Behavior and log message text are unchanged; only the emitting class's name changed (log lines now show `FfmpegGrabLoop`, not `FfmpegVideoSource`).
- **Mandatory copy**: `FFmpegFrameGrabber` reuses its native image buffers across `grab()` calls. Every grabbed frame's payload MUST be copied via `FrameConverter.copyBgr24` before being wrapped in an immutable `VideoFrame` (whose compact constructor stores the buffer for the record's lifetime) — never hand out the raw `Frame#image` buffer directly.
- Backpressure is drop-**newest**-on-full via `SubmissionPublisher.offer(..., onDrop -> true)` with a buffer capacity of only 4 — a slow subscriber never blocks capture, per `VideoSourcePort`'s latest-wins contract.
- First FFmpeg-touching test in a fresh module pays real cost for native library extraction — `FfmpegVideoSourceTest.AWAIT_SECONDS`=60 is deliberately generous for exactly this reason; once extracted, runs are fast (~2s observed for the whole class in this environment, most of it the pacing test's deliberate real-time waits).
- `resolveFilename(URI)` special-cases the `file:` scheme (via `Paths.get(uri)`) for both the `openAny` test seam and the real `"file"` protocol — the same code path serves both.
- **Pacing and loop both key off `uri.getScheme()`/options, not the descriptor's `protocol()` string** — `openAny` (used by every FFmpeg-path test, and indirectly by `open()`) computes `paced` from `uri.getScheme().equals("file")` directly, so a `"file"`-protocol descriptor and a raw `file:` URI passed through the test seam behave identically.
- `FFmpegFrameGrabber.restart()` (used for `loop=true`) is JavaCV's own `stop()`+`start()`; `stop()` fully releases the native `AVFormatContext` and `start()` reopens from the constructor-set filename, so it naturally reopens a file at position 0 — no manual seek/rewind needed.
- The pacing test (`fileSourceIsPacedToItsNativeFrameRate`) only asserts a generous **lower** bound on wall-clock time (0.5× the frame-rate-implied duration) — deliberately never asserts an upper bound, since CI scheduling jitter must not flake the test.
- **IMPORTANT for the next C3 task (application/api/app wiring): running `RtspFeedTransmitter` (TX) and `FfmpegVideoSource` (RX) concurrently in the *same JVM process* against the *same* mediamtx path triggers a same-process JavaCV/FFmpeg native contention.** Empirically reproduced outside this module's own tests (a standalone harness, not checked in): with `FfmpegVideoSource`'s RX side left at its default RTSP `timeout`/`rw_timeout` (10s, see its own default above), the *transmitter's* grab/record loop would silently stall for ~10s (matching the RX side's configured timeout, not the TX's own 5s) before mediamtx dropped the now-stale publisher connection ("i/o timeout") and the transmitter's next `record()` failed with `av_interleaved_write_frame() error -32` (EPIPE). Confirmed via a from-scratch minimal repro that the RX side alone (no TX in-process) and the TX side alone (no RX in-process) both run cleanly for 12+ seconds; only the *combination*, in one process, stalls — and reducing the RX side's `timeout` option (e.g. to `"2000000"` = 2s) reliably eliminates it (verified clean across multiple repeated runs). `MediamtxDockerIntegrationTest` demonstrates the fix (passes an explicit short `timeout` option on the RX-side `StreamDescriptor`), but **this is a real risk for `vision-app`'s eventual `transport=rtsp` wiring**, which will run both halves in one process by design (`docs/main/CYCLES-PLAN.md` §3) — that task should budget time to either apply the same short-RX-timeout workaround in production wiring, or investigate further (e.g. file a JavaCV issue; see `FFmpegFrameRecorder hangs when server connection is broken while streaming` (bytedeco/javacv#1063) for a related report of hangs when multiple recorders/grabbers interact under connection trouble).
- **Mid-GOP RX connects are normal, not a bug**: `RtspFeedTransmitter`'s encoder emits a keyframe only once per `FfmpegSettings.Transmit#gopSeconds()`=2 real seconds (see its entry above), regardless of how short the looped source file is. An RX side that connects between keyframes will log transient `decode_slice_header`/"Missing reference picture" warnings until the next keyframe arrives and decoding self-heals — this is expected RTSP-viewer behavior, not a failure. Test/consumer code must **not** react to "no frames yet" by tearing down and reopening the subscription impatiently: doing so restarts the wait against a new, differently-phased mid-GOP landing and can — as observed while writing `MediamtxDockerIntegrationTest` — never happen to land on a keyframe at all if the reconnect cadence and the GOP period fall into a synchronized "beat frequency". Stay on one subscription for the full timeout budget instead; only reopen on a genuine `onError`/`onComplete`.
- **docs/plans/done/MVP2-PLAN.md V-c: `max_delay` must go through `setMaxDelay(int)`, not `setOption`.** Verified against JavaCV 1.5.10's own source (`FFmpegFrameGrabber#startUnsafe`): `max_delay` is a real, generic FFmpeg AVOption that a `setOption("max_delay", ...)` call *would* apply during `avformat_open_input` — but JavaCV unconditionally overwrites it immediately afterwards with `oc.max_delay(this.maxDelay)`, its own `maxDelay` Java field (default `-1`), silently discarding anything set the `setOption` way. `probesize`/`analyzeduration`/`reorder_queue_size` have no such dedicated setter in JavaCV and no post-open override, so `setOption` is correct (and the only option) for those three. Anyone adding a new demuxer/grabber option to this module should check JavaCV's own source the same way before assuming `setOption` is sufficient — see the "V-c" section below for the full verification trail.
- **docs/plans/active/DRONE-INFRA-PLAN.md I-h, a udp source with nobody ever sending it a packet can wedge every *other* video source in the same JVM process — a genuine production finding, not just a test flake.** This was found in three escalating stages while developing `udpMpegtsLoopbackDeliversAtLeastOneFrame`; each stage's fix is now real production behavior, not test-only scaffolding:
  1. **UDP has no protocol-level EOF.** A first draft sent a fixed 30-frame (~1.5s) burst then closed the sender; this reliably left the receiver's native `avformat_find_stream_info` (inside `FFmpegFrameGrabber#start()`) blocked on a `read()` that would never be satisfied again once the sender stopped — UDP has no FIN/TEARDOWN, so the demuxer has no signal that "no more data is coming". Not a production concern by itself (a real encoder streams continuously regardless of when a viewer connects) — fixed in the test by streaming continuously (bounded by `MAX_LOOPBACK_SENDER_FRAMES`=400 frames at `LOOPBACK_SENDER_FRAME_INTERVAL_MILLIS`=50ms pacing, up to ~20s) until the receiver confirms a frame, rather than a fixed burst — see `streamUntilConfirmedOrTimeout` in `FfmpegVideoSourceTest`.
  2. **The real, severe finding: JavaCV's `FFmpegFrameGrabber`/`FFmpegFrameRecorder#start()` both synchronize on a shared, static, process-wide lock (the `avcodec` class object) for their entire native call — verified via a real thread dump.** With the stage-1 fix alone, a full `mvn test` of this class still occasionally left a **later, completely unrelated test method permanently blocked** (`jstack` showed it waiting on that exact lock, held by a udp receiver thread stuck inside `avformat_open_input` with `bytes read:0`). The application's own stream supervisor retries a failed `open()` indefinitely (1s→30s backoff) — in production, a udp source that never sends a single packet (e.g. misconfigured, or a drone that never powers on) would, without a bound, hold that lock on every retry, silently blocking every *other* video source's own open/reconnect attempts in the same `vision-app` JVM. **Fixed in production code**, not just the test: `configureUdpOptions` now always applies FFmpeg's own `timeout` AVOption (default `FfmpegSettings#udpTimeout()`=5s — `DEFAULT_UDP_TIMEOUT_MICROS`="5000000" pre-docs/plans/active/LAYERING-REFACTOR-PLAN.md §5.1, verified present in this build's binary strings: `"set raise error timeout, in microseconds (only in read mode)"`) — not exposed via `StreamDescriptor#options()`, a safety bound only. This makes a dead/silent udp source fail cleanly within ~5s instead of blocking forever.
  3. **The `timeout` fix has its own sharp edge: it removes the demuxer's patience for a receiver that starts *before* any data has arrived.** Verified via a verbose (`AV_LOG_DEBUG`) standalone reproduction: with `timeout` set, an idle receiver's `avformat_find_stream_info` can return almost immediately with `"Did not find a video or audio stream"` (`bytes read:0`) rather than waiting out its own budget for the sender to start — unlike the old unset/block-forever default, which patiently retried regardless of relative timing. **Fixed in the test** (this is legitimately test-harness sequencing, not a production gap — a real drone/encoder is already running before the app connects to it) by starting the sender first and waiting for a `started` signal (`FFmpegFrameRecorder#start()` succeeded) before opening the receiver — see `attemptUdpLoopback`'s own javadoc. UDP's connectionless nature makes this safe (an unbound destination just silently drops the earliest datagrams). Also retries up to `UDP_LOOPBACK_MAX_ATTEMPTS`=3 times as a further defensive margin, mirroring the supervisor's own real retry behavior.

  **Net effect, verified**: `./mvnw -B -pl adapters/adapter-rtsp clean test`, run three times consecutively — 37/37 green, 0 failures, 1 skipped, ~22-28s total each time (down from single runs occasionally taking 95s+ with a failure, and one early draft that genuinely wedged the whole forked JVM for 10+ minutes, requiring a manual `kill -9`). **Anyone adding a new protocol/option to this module should treat "does a `start()` failure mode exist that can block indefinitely" as a mandatory question** — given the shared JavaCV lock, an unbounded block in *any* one stream's native open call is not a local problem, it is a whole-process one.
- **docs/plans/active/DRONE-INFRA-PLAN.md I-h, verified finding: a JVM-hosted SRT *listener* open via JavaCV does not complete in this development environment, and — critically — a stuck one poisons the same process-wide JavaCV lock as the udp Gotcha above.** (Read that entry first for the shared lock's full mechanics — `FFmpegFrameGrabber`/`FFmpegFrameRecorder#start()` synchronizing on the `avcodec` class object — this entry only covers what's SRT-specific.) A first draft of the SRT test opened a real `srt://0.0.0.0:<port>` listener (mode inferred, see `OPTION_SRT_MODE` above) alongside a continuously-streaming caller sender, mirroring the `udp` loopback test. In this environment that listener open reliably hit libsrt's own defensive native error `"no sockets to check, this would deadlock"` (from its epoll-wait helper) and never returned, holding the shared lock forever — confirmed via `jstack` to cascade into a later, completely unrelated test method stalling indefinitely (the process needed a manual `kill -9` to recover). **Unlike the udp case, this was not fixed with an internal timeout AVOption** — SRT's own `listen_timeout` AVOption exists and could bound a *normal* "nobody has connected yet" wait, but the specific failure observed here is a native defensive error that fires early, not a genuine timeout being exceeded, so a `listen_timeout` would not have prevented it. Given that, the SRT test avoids the listener role entirely (see below) rather than attempting the same class of fix as udp.
  - Investigation establishing this is an environment/library interop issue, not this task's code: (1) `--enable-libsrt` confirmed in the bundled binary's own recorded build config string, and `srt` confirmed as a registered runtime protocol via `avio_enum_protocols`. (2) Both option-application mechanisms the task asked to compare — `FFmpegFrameGrabber.setOption("mode", "listener")` and an equivalent `srt://…?mode=listener` URL query string — hit the identical failure, which is itself informative: it shows `setOption` genuinely reaches the SRT protocol's own private AVOptions in this build (the listener code path is actually reached, not silently falling back to caller) — settling that this module's chosen mechanism (`setOption`, kept for one idiom across rtsp/srt/udp) is not the problem. (3) Explicit `127.0.0.1` vs. `0.0.0.0` listener hosts, and swapping which JavaCV class played the listener role, made no difference. (4) A **completely independent, non-JVM `ffmpeg` CLI process pair** (the Ubuntu system package, not this module's bundled dependency) on the same machine completed a full `srt://` listener+caller round trip successfully, ruling out a machine-wide network/firewall/epoll restriction (this machine also has full capabilities/no sandboxing, confirmed via `/proc/1/status`). (5) A JVM-hosted grabber-as-**caller** against that same real external listener also failed (`avformat_open_input() error -5`), but — unlike the listener path — failed *fast* (not stuck), and this module's own `udp://` loopback (previous Gotcha) reliably succeeds via the exact same JVM-hosted mechanism, ruling out something generically wrong with JVM-hosted JavaCV networking.
  - **Given the demonstrated severity (a whole-class-wedging risk, not just one flaky test), the SRT test does not attempt a live listener open in this JVM at all.** `srtCallerConnectAttemptReachesRealFfmpegSrtCodeAndFailsCleanlyWhenNobodyIsListening` (`FfmpegVideoSourceTest`) instead only exercises the caller role — verified safe (a caller against a definitely-nothing-listening port fails cleanly with a real FFmpeg/libsrt exception in single-digit seconds, every time it was tried) — proving the real, bundled-FFmpeg SRT caller code path is live and reachable through this class's own `open()`, without the unsafe listener path. This means this module currently has **no automated coverage of a full SRT round trip actually delivering a frame** in this environment; `configureSrtOptions`'s own option-application correctness (including `mode` inference) is still fully covered by the unit tests above, which touch no network at all.
  - **Anyone revisiting this**: a newer JavaCV/bundled-libsrt pairing, or a different host kernel/glibc, may resolve the underlying listener issue — re-verify with the same `jstack`-during-a-full-class-run technique before trusting a live listener test again, since the failure mode (whole-suite wedge) is easy to miss if you only ever run the SRT test in isolation.

## V-c: RTSP demuxer latency tuning (docs/plans/done/MVP2-PLAN.md §V-c)

**Scope: `rtsp` protocol only, `file` untouched.** `newGrabber()` (originally `StreamRuntime.newGrabber()` on `FfmpegVideoSource`; now `FfmpegGrabberOptions.newGrabber`, docs/plans/active/LAYERING-REFACTOR-PLAN.md §5.1) calls the `configureRtspOptions` seam only inside its existing `uri.getScheme().equals("rtsp")` branch — the exact same gate the pre-existing `rtsp_transport`/`timeout` options already used, unchanged. `file` sources (paced local-file simulation) get none of this; `fileProtocolNeverReceivesRtspDemuxerTuning` (now in `FfmpegGrabberOptionsTest`, moved with its production code) pins that contract directly against a real `FFmpegFrameGrabber`'s untouched defaults.

**What changed, mechanically**, all four via the same device-option-override idiom as `rtsp_transport`/`timeout` (`options.getOrDefault(key, default)`):

| Option | Old (FFmpeg default) | New default | Applied via |
|---|---|---|---|
| `probesize` | unset → 5,000,000 bytes (5MB) | `32768` (32 KiB) | `setOption` |
| `analyzeduration` | unset → 5,000,000µs (5s), **7,000,000µs (7s) for mpegts payload** | `1000000` (1s) | `setOption` |
| `reorder_queue_size` | unset → adaptive: `0` packets under `tcp`, `500` under `udp` | `0` packets (explicit) | `setOption` |
| `max_delay` | unset (`-1`) → `100000`µs (100ms), RTSP-demuxer's own `DEFAULT_REORDERING_DELAY` | `100000`µs (100ms, explicit) | **`setMaxDelay(int)`** |

Every default above was verified against real FFmpeg 6.1.1 source (`libavformat/options_table.h`, `demux.c`, `rtsp.c`) fetched and read during this task, not assumed from common blog-post folklore — the full citations, split docs/plans/active/LAYERING-REFACTOR-PLAN.md §5.1: the mechanism/AVOption-name rationale lives in each option's javadoc in `FfmpegGrabberOptions.java`, the actual default *value*'s provenance lives in the corresponding field's javadoc in `FfmpegSettings.java`.

**Two genuine, verified corrections to the task brief's own framing** (honesty rule):

1. **The "several-second RTSP default" is real, but it's `analyzeduration`'s, not `max_delay`'s.** `libavformat/demux.c`'s `avformat_find_stream_info` resolves an unset (`0`) `analyzeduration` to `5*AV_TIME_BASE` (5s) for most formats — **and a full `7*AV_TIME_BASE` (7s) specifically when the payload is detected as `mpeg`/`mpegts`**, a common RTSP payload for many IP cameras and drone companions. This is the actual multi-second RTSP-connect-stall lever; bounding it to 1s here is the single biggest change in this block.
2. **`max_delay`'s own RTSP-specific default is already a modest 100ms, not several seconds.** `libavformat/rtsp.c` resolves an unset `max_delay` to `DEFAULT_REORDERING_DELAY` = 100,000µs — verified by reading the source, not assumed. The task brief's suggested "500ms, down from a 7s default" would have **loosened**, not tightened, this specific value (the real 7s figure belongs to `analyzeduration`'s mpegts branch above). `FfmpegSettings#maxDelay()` is therefore set to 100ms (`DEFAULT_MAX_DELAY_MICROS`="100000" pre-docs/plans/active/LAYERING-REFACTOR-PLAN.md §5.1) — pinning FFmpeg's own already-good default as living documentation against a future version silently changing `DEFAULT_REORDERING_DELAY` (same intent as V-a's `setMaxBFrames(0)`), not tightening it further: `max_delay` is what gives a jittery/far source's late RTP packets a chance to arrive in order before the demuxer force-delivers (logging FFmpeg's own "max delay reached" warning) — shrinking it below FFmpeg's own chosen balance would trade a little latency for materially worse robustness on exactly the non-ideal links this task asked to reason about.

**`reorder_queue_size=0`'s trade-off, stated honestly.** Under this module's actual (and only exercised) `rtsp_transport=tcp` default, FFmpeg's own adaptive logic already resolves an *unset* `reorder_queue_size` to `0` (TCP guarantees in-order delivery at the transport layer, so a reorder queue buys nothing) — so pinning it at `0` explicitly is a no-op for today's behavior, not a change. But it *is* a real behavior change for a hypothetical future device option overriding `rtsp_transport=udp`: without this pin, a `udp` source would silently inherit FFmpeg's own 500-packet (`RTP_REORDER_QUEUE_DEFAULT_SIZE`) default; with it, that source instead gets `0` — favoring latency over reorder tolerance. A `udp` camera on a genuinely lossy/jittery link would want to override `reorder_queue_size` back up via the same device-option map; this module does not attempt to auto-detect that case.

**Expected effect on far/jittery sources.** `probesize`/`analyzeduration` only affect one-time connect-time stream-info probing, not steady-state decode — a far/jittery source connects faster but is not otherwise affected once streaming starts. `max_delay`/`reorder_queue_size` are the two that matter for jitter tolerance, and both were deliberately left at (not below) FFmpeg's own already-conservative built-in behavior for this module's TCP-default path specifically to avoid regressing robustness on exactly that kind of source — see the two corrections above.

**Existing timeout/transport handling: read first, not regressed.** `rtsp_transport` (default `tcp`, a hard-forced transport, not a soft `rtsp_flags=prefer_tcp` preference — this module never sets `rtsp_flags` at all, so there was nothing to preserve there) and `timeout`/`rw_timeout` (10s default, including the documented same-process JavaCV contention workaround above) are untouched by this task, both in value and in the `uri.getScheme().equals("rtsp")` gating that already existed.

**Devices/overrides.** All four new options are overridable per-device the same way `timeout` already is — no new plumbing invented; `FfmpegGrabberOptions.intOption`'s lenient integer parsing (malformed → default, mirroring `FfmpegGrabLoop.booleanOption`'s existing idiom) backs `max_delay`'s override path specifically, since it must reach an `int`, not a string option.

- `FfmpegGrabLoop` — new package-private class, the promoted former nested `StreamRuntime` (zero references back to the `FfmpegVideoSource` instance that created it — it was already `static`, so this is a physical file move, not a behavior change); owns its own `System.Logger` (log lines now show `FfmpegGrabLoop`, not `FfmpegVideoSource` — the only observable, non-test-asserted difference from this move).
- `RealtimePacer` — new package-private class, the timestamp-delta real-time pacing logic that was duplicated verbatim between `FfmpegVideoSource`'s grab loop and `RtspFeedTransmitter`'s transmit loop; both now share one instance-per-loop implementation (intra-module sharing, not a cross-adapter dependency).
- `FfmpegVideoSource` — narrowed to ~130 lines: `supports`/`open`/`openAny`/`close` plus the shared `ensureQuietLogging()` guard. Gained an additive `FfmpegVideoSource(FfmpegSettings)` constructor; the pre-existing no-arg constructor is unchanged (`this(FfmpegSettings.defaults())`).
- `RtspFeedTransmitter` gained an additive `RtspFeedTransmitter(URI, FfmpegSettings)` constructor (the pre-existing one-arg constructor is unchanged, `this(rtspTargetBase, FfmpegSettings.defaults())`); its encoder settings and thread-join timeout now read from `FfmpegSettings`/`FfmpegSettings.Transmit` instead of five separate `private static final` constants, and its transmit loop now uses the shared `RealtimePacer` instead of a duplicated inline pacing block. `vision-app`'s two call sites (`new FfmpegVideoSource()`, `new RtspFeedTransmitter(properties.mediamtx().rtspBase())`) were not touched and still compile — neither constructor overload was removed.

Two module tunables were deliberately **not** promoted into `FfmpegSettings`, flagged rather than silently decided: `FfmpegGrabberOptions.DEFAULT_UDP_OVERRUN_NONFATAL` (a fixed survive-vs-abort posture, not a scalar the frozen `vision.rtsp` key table names) and the SRT `pbkeylen` pin (living documentation of libsrt's own already-built-in default — a protocol/spec constant per docs/plans/active/LAYERING-REFACTOR-PLAN.md §1.3, not a deployment choice). One genuine literal *collapse* happened alongside the moves: `FfmpegSettings#transport()` now feeds both the RX side's `rtsp_transport` default and the TX side's previously separately-hardcoded `"tcp"` push transport, and `FfmpegSettings#closeJoinTimeout()` now feeds both halves' previously-identical-but-separate 20s thread-join bound.

A later wave (docs/plans/active/LAYERING-REFACTOR-PLAN.md §7, F1) adds a Spring `VisionRtspProperties` record in `vision-app` and binds it to `FfmpegSettings` — out of scope for this wave, and this module gained no Spring dependency doing this work.
