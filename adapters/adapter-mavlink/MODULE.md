## Library choice

**`io.dronefleet.mavlink:mavlink` 1.1.11** (Maven Central, latest as of this task — checked 2026-07-23; last released 2023-02-27, dependency-free at runtime: its own `mavlink-protocol` sub-artifact declares zero non-test dependencies, and the combined jars are ~1.8 MB, mostly generated per-dialect message classes). Chosen over hand-rolling frame decode because:
- It already CRC-validates and auto-resyncs past malformed/unparseable frames inside `MavlinkConnection#next()` (skips bad frames and keeps scanning for the next valid one, never throws for that case) — exactly the "unparseable datagrams skipped, never fatal" requirement, for free.
- Typed, code-generated message classes (`GlobalPositionInt`, `Heartbeat`, `SysStatus`, ...) with builders — no manual bit-twiddling for the messages this task needs, and headroom for more (`BATTERY_STATUS`, attitude, etc.) without touching the wire-format layer later.
- No transitive baggage to justify avoiding it (see size/deps above) — the "hand-roll if it drags baggage" escape hatch in this task's brief doesn't apply.

Version pinned via root `pom.xml`'s `<dronefleet-mavlink.version>` property, same pattern as `javacv.version`/`jmdns.version`.

## API surface

### `com.drones.vision.adapter.mavlink`
- `final class MavlinkTelemetrySource implements TelemetrySourcePort` — RX. Supports protocol `"mavlink"` with a `udp://host:port` `StreamDescriptor.uri()` and `Capability.TELEMETRY`. `supports(Device)`, `open(Device): Flow.Publisher<Telemetry>`, `close(DeviceId)`.
  - **`udp://host:port` means listen, not connect** — see Gotchas. `host` blank/absent → binds the wildcard `0.0.0.0` (all interfaces).
  - **docs/DRONE-INFRA-PLAN.md I-a — fleet gateway.** `open()` no longer binds its own socket: it registers with a shared `MavlinkSocketHub` keyed by bind address (`bindKey(host, port)` = `"host:port"`, package-private static), reference-counted across every device sharing that address. `StreamDescriptor.options["sysid"]` — a positive int 1-255, lenient parse (missing/blank/malformed/out-of-range → unpinned, same idiom as every other option in this module) — pins the device to exactly that MAVLink system id; omitted/invalid means unpinned (claims the first unclaimed sysid heard, re-electable — see `MavlinkSocketHub` and the Gotchas below for the full claim/re-election rules this replaces the old single-device behavior with). `close(id)` releases this device's registration; the hub's socket/thread only actually shut down once the last registration on that bind address releases. Package-private `unclaimedVehicles(bindKey)` exposes vehicles heard-but-claimed-by-nobody on that address; **docs/DRONE-INFRA-PLAN.md I-b** added two more package-private methods consumed by `MavlinkHeartbeatScanner` (below): `hasActiveHub(bindKey)` (whether some device currently has that address open — the hub-borrow-vs-self-bind decision point) and `claimedVehicles(bindKey)` (delegates to `MavlinkSocketHub#claimedVehicles()`, see next bullet). A package-private constructor `MavlinkTelemetrySource(long silenceWindowMillis)` overrides the 30s production re-election silence window for tests; the public no-arg constructor (used by `vision-app`'s wiring, unchanged) defaults to it.
  - **docs/DRONE-INFRA-PLAN.md I-e Stage 1 — command-TX pass-throughs**, consumed by `MavlinkFlightCommander` (below), mirroring the `unclaimedVehicles`/`hasActiveHub`/`claimedVehicles` shape: package-private `bindKeyFor(Device)` (the same host-defaulting + `bindKey` logic `open()` uses internally, exposed so a caller that already validated `supports(device)` can address the same hub without duplicating that logic); `commandTarget(bindKey, deviceId)` (delegates to `MavlinkSocketHub#commandTarget`); `socket(bindKey)` (the hub's shared `DatagramSocket`, for sending a command back through it); `awaitAck(bindKey, sysid, commandId)`/`cancelAckWait(bindKey, sysid, commandId)` (delegate to the hub's own ack-waiter registry, see below — `awaitAck` returns an already-failed future, never `null`, when no hub is active for that address).
- `final class MavlinkSocketHub` (package-private, docs/DRONE-INFRA-PLAN.md I-a) — one shared `DatagramSocket` + one dedicated read thread (`mavlink-telemetry-hub-<host>-<port>`) per distinct bind address, owned entirely by `MavlinkTelemetrySource`. Demultiplexes every decoded `MavlinkMessage` by system id (never source address for *routing* — see Gotchas) to the registered device that claims it, creating a **fresh** `MavlinkTelemetryDecoder` per claim/re-election (a decoder's accumulated fields belong to one physical vehicle; reusing one across a claim change would leak stale values). `register`/`unregister` are called from whatever thread calls `open`/`close`; all claim/routing state is guarded by one monitor, touched by both those callers and the hub's own read thread. `unregister` returns whether the hub is now empty (0 registrations), so `MavlinkTelemetrySource` knows to evict it from its hub map and let the next `open()` for that address build a fresh one. `unclaimedVehicles()` returns a bounded (max 32, oldest-evicted-first) list of `UnclaimedVehicle(sysid, firmware, mavType, lastHeard)` records for vehicles nobody currently claims. **docs/DRONE-INFRA-PLAN.md I-b** added `claimedVehicles()`, returning one `ClaimedVehicle(sysid, deviceId, firmware, mavType, lastHeard)` per currently-claimed registration — `VehicleRegistration` gained its own `firmware`/`mavType` fields (mutated under the same lock, refreshed from every `HEARTBEAT` a claimed vehicle sends, via the new `captureHeartbeatInfo` — the claimed-side mirror of the pre-existing `recordUnclaimed`) so a claimed vehicle can be labeled the same way an unclaimed one already was.
  - **docs/DRONE-INFRA-PLAN.md I-e Stage 1 — command-TX seam.** `VehicleRegistration` gained `lastSourceAddress` (an `InetSocketAddress`, mutated under the same lock, refreshed on every message from that claim — sourced from the new `MavlinkUdpInputStream#lastSourceAddress()`, see below): this hub was previously receive-only and had never needed to remember *where* a vehicle's datagrams came from, only *which sysid* they carried (routing itself still never uses the source address — see Gotchas, unchanged). Package-private `commandTarget(DeviceId)` returns a new `CommandTarget(sysid, firmware, mavType, sourceAddress)` record for a device's current claim, or `null` if it holds none; `socket()` exposes the current shared `DatagramSocket` so a command sender can push a reply through it instead of opening a second one. `awaitAck(sysid, commandId)` registers a one-shot `CompletableFuture<CommandAck>` in a small `ackWaiters` map (keyed by a private `AckKey(sysid, commandId)` record, guarded by the same lock) and returns it immediately; `routeMessage` — already the one place every inbound message is dispatched — now also recognizes a `CommandAck` payload, looks up (and removes) any matching waiter, and completes it *outside* the lock, right alongside its existing telemetry-submission step. `cancelAckWait(sysid, commandId)` releases a waiter, idempotent. This is a deliberately narrow seam: no second socket reader, no new thread — `MavlinkFlightCommander` (below) is the one caller.
- `final class MavlinkHeartbeatScanner implements DeviceDiscoveryPort` (**new**, docs/DRONE-INFRA-PLAN.md I-b) — plug-and-fly heartbeat discovery. `method()` = `"mavlink"`. Constructor takes the `MavlinkTelemetrySource` instance to borrow from (`vision-app` wires the same singleton bean used for real telemetry ingest) and the port to scan (port-agnostic; `vision-app` wires the well-known default, 14550); the bind host is always the wildcard (`MavlinkTelemetrySource.DEFAULT_BIND_HOST`), matching how an omitted/blank device URI host already defaults. `scan(timeout)` picks one of two paths per call, based on `telemetrySource.hasActiveHub(bindKey)`:
  - **Hub already active** — no bind of its own. Polls `claimedVehicles`/`unclaimedVehicles` a handful of times (`ACTIVE_HUB_POLL_COUNT` = 5, spaced across the timeout, floor `ACTIVE_HUB_MIN_POLL_INTERVAL_MILLIS` = 20ms — no busy-spin) so a vehicle whose first `HEARTBEAT` lands partway through the scan still gets a real firmware/vehicle-kind label by the last poll. A claimed vehicle is reported with `details["claimed"]="true"` + `details["claimedBy"]=<device id>` (poka-yoke against a duplicate asset); an unclaimed one is reported plain.
  - **No active hub** — binds the port itself for the scan's duration (`DatagramSocket` + `setReuseAddress(true)`), reusing `MavlinkConnection`/`MavlinkUdpInputStream` exactly like `MavlinkSocketHub`'s own read loop, with `SO_TIMEOUT` (20-200ms, clamped from the requested timeout) so the blocking read loop can re-check its deadline without busy-spinning; releases the socket in a `finally`. A bind failure (`IOException`, e.g. the port is held by something other than this app's own gateway) is caught, logged at WARNING, and returns an empty list — **never thrown** (discovery must never break the scan-all flow over one mechanism's bind conflict).
  - Naming: `"<Firmware> <vehicle kind> (sysid <n>)"`, e.g. `"ArduPilot quadcopter (sysid 7)"` — firmware from `HEARTBEAT.autopilot` (reuses `MavlinkTelemetryDecoder.firmwareLabel`, mapped to a display name: ardupilot→ArduPilot, px4→PX4, generic→Generic, unknown/null→MAVLink) and vehicle kind from `HEARTBEAT.type` (own local `MAV_TYPE_*` constants, duplicated from upstream rather than reused from `FlightModes`, whose own constants are private and exist there only to pick a mode table — not to label a vehicle kind): quadcopter/hexacopter/octocopter/tricopter/helicopter/fixed-wing/rover/boat, or `"vehicle"` if unknown/not yet heard. `suggestedCategory` is `CategoryId("drone")` only for an airborne kind (quadcopter/hexacopter/octocopter/tricopter/helicopter/fixed-wing); rover/boat/unknown gets no suggested category. `suggestedStream` is `StreamDescriptor("mavlink", udp://0.0.0.0:<port>, {"sysid": "<n>"})`. `details` always carries `firmware` (raw label or `"unknown"`), `mavType` (the vehicle-kind label, not the raw int), `sysid`; `claimed`/`claimedBy` only when already registered.
  - Blocking, self-time-boxed to ~`timeout` on both paths; an empty list ("nothing heard") is never an error, per `DeviceDiscoveryPort`'s contract.
- `final class MavlinkFeedTransmitter implements FeedTransmitterPort` — TX. Supports `FeedSpec.protocol()` `"mavlink"` with a `source()` whose scheme is `udp` and which carries a non-blank host **and** a positive port. `supports(FeedSpec)`, `start(FeedId, FeedSpec): StreamDescriptor`, `stop(FeedId)`.
  - **`FeedSpec.source()` is repurposed as a destination**, not a file — see Gotchas.
  - Options: `route` (**required**, `lat,lon[,altM];lat,lon[,altM];...`, ≥2 points — missing/malformed → `IllegalArgumentException` at `start()`, no lenient fallback); `speedMps` (default 12.0); `batteryDrainPerSecond` (default 0.05 %/s); `positionRateHz` (default 5.0); `failsafeBatteryPercent` (docs/FC-INTEGRATIONS-PLAN.md F-a, default 15.0 — battery percent below which `HEARTBEAT` switches to the failsafe custom_mode/system_status described below; lenient like `batteryDrainPerSecond`, i.e. a non-positive value is accepted as-is, `0` meaning "never"); `sysid` (docs/DRONE-INFRA-PLAN.md I-a, default `DEFAULT_MAV_SYSTEM_ID` = 1 — the MAVLink system id every message from this feed carries; lenient, missing/blank/unparseable/out of 1-255 → default). The other numeric options: non-positive/unparseable → default (same lenient idiom as every other adapter, except `route` itself).
  - nested `private static final class FeedRuntime` — one dedicated platform thread (`mavlink-feed-<id>`) per `start()`: owns an ephemeral `DatagramSocket`, sends `HEARTBEAT`+`SYS_STATUS`+`GPS_RAW_INT` once a second and `GLOBAL_POSITION_INT` at `positionRateHz`, as system id `sysid` (default 1) / component id 1, paced by a 50ms tick loop comparing wall-clock deadlines (not a `ScheduledExecutorService` — one thread, two cadences, simplest thing that works). `close()`: same CAS/interrupt/bounded-join (5s) shape as RX.
  - docs/FC-INTEGRATIONS-PLAN.md F-a: `HEARTBEAT` now reports `autopilot` ARDUPILOTMEGA, `type` QUADROTOR, `base_mode` armed+custom-mode-enabled, and `custom_mode`/`system_status` that flip together once the simulated battery drains below `failsafeBatteryPercent` — nominal: `custom_mode` `CUSTOM_MODE_LOITER` (5, "Loiter") + `system_status` ACTIVE; failsafe-triggered: `custom_mode` `CUSTOM_MODE_RTL` (6, "RTL") + `system_status` CRITICAL. `GPS_RAW_INT` is a fixed 3D fix, 12 satellites, eph 90 (hdop 0.9), lat/lon taken from the same route position `GLOBAL_POSITION_INT` uses.
  - docs/DRONE-INFRA-PLAN.md I-a: the `sysid` option exists specifically so a single test (or a real multi-vehicle rehearsal) can run two or more feeds with distinct system ids at one destination, matching how `MavlinkTelemetrySource`/`MavlinkSocketHub` demultiplex real multi-vehicle traffic.
- `final class MavlinkFlightCommander implements FlightCommandPort` (**new**, docs/DRONE-INFRA-PLAN.md I-e Stage 1 — "bring it home") — the one deliberate break in the RX-only doctrine. Constructor takes the same `MavlinkTelemetrySource` instance used for real telemetry ingest (identical borrowing pattern to `MavlinkHeartbeatScanner`). `supports(Device)` delegates straight to `telemetrySource.supports(device)` — no duplicated logic, the two can never disagree. `returnToHome(Device)`:
  - Resolves the device's bind key (`telemetrySource.bindKeyFor(device)`) and current claim (`telemetrySource.commandTarget(bindKey, device.id())`); `null`, or a claim with no `sourceAddress` yet, throws `IllegalArgumentException` — the Stage-1 reachability rule ("you cannot command what you cannot hear"): a command can only be sent to an address this platform has actually received a datagram from.
  - Resolves the RTL `custom_mode` via `FlightModes.customModeFor`: `firmware == null` (no `HEARTBEAT` yet) → `IllegalArgumentException`; `firmware.equals("generic")` (Betaflight) → `IllegalArgumentException` naming Betaflight explicitly, checked *before* ever consulting `FlightModes` (whose own table would happily resolve an RTL number for it — see that class's own Gotchas-adjacent javadoc note); any other non-`"ardupilot"` firmware (e.g. `"px4"`) → `IllegalArgumentException`; `"ardupilot"` (covers INAV too, which masquerades as ArduPilot) resolves via `FlightModes.customModeFor(FlightModes.AUTOPILOT_ARDUPILOTMEGA, mavType, "RTL")`, `null` (an ArduPilot `mavType` outside copter/plane/rover) → `IllegalArgumentException`.
  - Sends a `COMMAND_LONG` (`MAV_CMD_DO_SET_MODE`, param1 = `MAV_MODE_FLAG_CUSTOM_MODE_ENABLED` = `1.0f`, param2 = the resolved custom mode) from this platform's own sysid/compid (`COMMANDER_SYSTEM_ID` = 255, MAVLink's conventional GCS system id; `COMMANDER_COMPONENT_ID` = 190, `MAV_COMP_ID_MISSIONPLANNER`) to the vehicle's autopilot component (`TARGET_COMPONENT_AUTOPILOT` = 1, `MAV_COMP_ID_AUTOPILOT1`), via a fresh `MavlinkConnection` wrapping `InputStream.nullInputStream()` + a `MavlinkUdpOutputStream` targeting the claim's `sourceAddress` over the hub's own shared `socket()` — the same "one connection per send, reuse the shared socket" shape `MavlinkFeedTransmitter` already uses for TX, just pointed at a vehicle's dynamic address instead of a fixed configured one.
  - Registers `telemetrySource.awaitAck(bindKey, sysid, MAV_CMD_DO_SET_MODE)` **before** sending (so a very fast reply can never race the wait), then blocks up to `ACK_TIMEOUT_MILLIS` (2000, package-private) for the matching `COMMAND_ACK`: `MAV_RESULT_ACCEPTED` (compared by enum identity, same idiom as `MavlinkTelemetryDecoder`'s `MAV_STATE_CRITICAL` check) → `CommandResult.ACCEPTED`; any other result → `IllegalStateException` naming it; a timeout → `CommandResult.NO_ACK`. Always releases the waiter in a `finally` (`cancelAckWait`).
  - Logging: `System.Logger`, INFO on send (sysid/mode/target address), WARNING on denial or timeout — module idiom.
  - **docs/DRONE-INFRA-PLAN.md I-e Stage 2** generalized the DO_SET_MODE send into a private `send(...)` helper shared by every command: `setMode(Device, String)` resolves the requested mode via `FlightModes.customModeFor(AUTOPILOT_ARDUPILOTMEGA, mavType, modeName)` (unknown mode → `IllegalArgumentException`) and `returnToHome` now just calls `setMode(device, "RTL")`; `arm(Device, boolean)`/`disarm(Device, boolean)` send `COMMAND_LONG` `MAV_CMD_COMPONENT_ARM_DISARM` (wire id **400**, a named literal beside `MAV_CMD_DO_SET_MODE`=176 for the ack-key; the enum `MavCmd.MAV_CMD_COMPONENT_ARM_DISARM` is used to *build* the command — the library exposes both) with param1 1.0 (arm)/0.0 (disarm), param2 21196.0f when `force` else 0.0f. All await `COMMAND_ACK` the same ~2s way and map ACCEPTED→`ACCEPTED` / explicit denial→`IllegalStateException` / timeout→`NO_ACK`. Firmware commandability (`null`/unheard, Betaflight `"generic"`, non-ArduPilot) is checked in one shared `requireCommandableFirmware` *before* `FlightModes` is consulted — Betaflight is rejected for setMode/arm/disarm exactly as Stage-1 rejected it for RTL (message names Betaflight). `capabilities(Device)` never throws: resolves the vehicle via the hub's `commandTarget`; no claim / not-ArduPilot firmware / Betaflight / unheard → `FlightCapability.notCommandable()`; ArduPilot-family → `commandable=armSupported=modeSelectSupported=true` with `selectableModes` from `FlightModes.selectableModes(...)`. **INAV is indistinguishable from ArduPilot on the wire** so it reports commandable=true; its commands are honestly *attempted* and simply return `NO_ACK` if the INAV RX ignores them — same known Stage-1 limitation, documented not hidden.
- `final class MavlinkManualControlSender implements ManualControlPort` (**new**, docs/RC-CONTROL-PHASE1-PLAN.md R3) — the streaming, ack-less sibling to `MavlinkFlightCommander`'s request→ack one-shots: a persistent, fixed-rate MAVLink 2 `RC_CHANNELS_OVERRIDE` (#70) relay. Single field `private final MavlinkTelemetrySource telemetrySource` — borrows the RX instance's shared hub socket and target registry exactly like `MavlinkFlightCommander`; opens **no socket of its own** (the one new hard requirement this port adds over `MavlinkFeedTransmitter`'s own ephemeral-socket precedent — see Gotchas).
  - `supports(Device)` delegates straight to `telemetrySource.supports(device)`, same as every other class that borrows this instance.
  - `engage(Device)` resolves the device's bind key and current claim exactly like `MavlinkFlightCommander.resolveReachableTarget` (`telemetrySource.bindKeyFor(device)` then `telemetrySource.commandTarget(bindKey, device.id())`); a `null` claim or a claim with no `sourceAddress()` yet throws `IllegalArgumentException` naming the same "you cannot command what you cannot hear" rule — **and starts no thread**. On success it constructs and starts a per-link `RcLinkRuntime` (private static nested class, modeled on `MavlinkFeedTransmitter.FeedRuntime`) and returns it as the opaque `ManualControlLink`.
  - **Sender thread** (`"mavlink-rc-<deviceId>"`, daemon): a nanoTime-deadline fixed-rate loop (`nextTickNanos += tickPeriodNanos`, self-correcting rather than drifting, unlike `FeedRuntime`'s coarser 50ms-tick-comparing-two-cadences shape — this class only ever has one cadence to keep) that, every tick, **re-resolves the device's current claim** (`commandTarget`/`socket`, both live off `MavlinkSocketHub`'s own always-current registry) rather than caching it once at `engage`-time, builds an `RcChannelsOverride` from the mailbox's latest `RcChannels`, and sends it via a throwaway `MavlinkConnection` wrapping `telemetrySource.socket(bindKey)` in a fresh `MavlinkUdpOutputStream` targeting the claim's `sourceAddress` — connection-per-tick, exactly `MavlinkFlightCommander.send()`'s own shape, just looped. GCS `sysid`/`compid` (255/190) and the autopilot target component (1) are **reused directly from `MavlinkFlightCommander`**'s own package-private constants (`COMMANDER_SYSTEM_ID`/`COMMANDER_COMPONENT_ID`/`TARGET_COMPONENT_AUTOPILOT`) rather than re-declared, so the one GCS-identity convention has a single source of truth. If the claim is lost mid-link (vehicle gone quiet, hub torn down) the tick is skipped, not fatal — one WARNING on the reachable→unreachable transition, one INFO on the reverse, never a flood, never a wedged thread.
  - **Latest-wins mailbox**: a single `volatile RcChannels` field on `RcLinkRuntime`, written only inside a small `synchronized` block shared with `release()`'s own release-sentinel write (closes a narrow race where a late in-flight `send()` could otherwise clobber a release burst that already started — see Gotchas), read lock-free by the tick loop. Before the first real `send()` the slot holds an all-`IGNORE` 8-channel frame — ticks still go out every cycle (the fixed cadence never pauses), they simply tell the aircraft "leave every channel alone" until the caller sends something real.
  - `send(link, channels)` just overwrites that slot (`Objects.requireNonNull` on `channels`, `IllegalArgumentException` if `link` was not created by this port's own `engage`) — non-blocking, never touches the wire itself, and is a silent no-op once the link has begun releasing.
  - `release(link)` writes `RcChannels.released(8)` into the mailbox (all 8 v1 channels back to `RELEASE=0`), sleeps `releaseFrameCount * tickPeriodMillis` on the **caller's** thread to let the still-running sender thread actually transmit that burst, then interrupts and bounded-joins (5s) the thread — same CAS/interrupt/join shape as every other runtime in this module. Idempotent via one `AtomicBoolean` CAS (`beginRelease()`); a second `release()` is an immediate, side-effect-free no-op — no sleep, no interrupt, no re-join.
  - **v1 scope, channels 1..8 only**: every frame sets `chan1Raw`..`chan8Raw` from the mailbox (a shorter-than-8 `RcChannels` fills the remainder with `IGNORE`) and `chan9Raw`..`chan18Raw` to `IGNORE` unconditionally — matches `ChannelMap.defaultMap()`'s own ch1..8 scope and sidesteps the ambiguous MAVLink #70 extension release sentinel for channels 9..18 (docs/RC-CONTROL-PHASE1-PLAN.md's own Open Questions §4).
  - **Env knobs** (system property, falling back to the identically-named env var; defaulted, clamped/validated — same lenient-with-bounds idiom this module already uses for `sysid`): `VISION_RC_OVERRIDE_HZ` (default **33**, clamped to **10–50**) sets the fixed tick rate; `VISION_RC_RELEASE_FRAMES` (default **3**, any positive value accepted) sets the release-burst tick count. Read once, at construction, via the public single-arg constructor; a package-private test-seam constructor (`MavlinkManualControlSender(MavlinkTelemetrySource, long tickPeriodMillis, int releaseFrameCount)`) injects both directly for deterministic, fast tests — same "package-private test-seam constructor" idiom as `MavlinkTelemetrySource(long silenceWindowMillis)`.
- `final class MavlinkTelemetryDecoder` (package-private) — stateful message→`Telemetry` merger; one instance per claim (fresh on every RX `open()` and on every hub-level claim/re-election, see `MavlinkSocketHub`). See "Message → field mapping" below and its own javadoc for the full unit-conversion table. docs/FC-INTEGRATIONS-PLAN.md F-a: also merges a `FlightState` (armed/mode/failsafe/GPS/RSSI/arming-blockers), carried as `Telemetry#flightState()`, `null` until at least one `FlightState` field has actually become known (see Gotchas). Its own system-id lock (first sysid observed wins, no re-election) is unchanged and still exercised directly by this class's own unit tests, but as of I-a is no longer reachable in practice through `MavlinkTelemetrySource`: `MavlinkSocketHub` demultiplexes by sysid *before* a message reaches a decoder. `static String firmwareLabel(int autopilot)` is package-private (not `private`) specifically so `MavlinkSocketHub` can reuse it to label unclaimed vehicles.
- `final class FlightModes` (package-private, docs/FC-INTEGRATIONS-PLAN.md F-a) — `static String name(int autopilot, int mavType, long customMode)`: ArduPilot copter/plane/rover + Betaflight mode-number→name tables, table selected by `autopilot` (3=ArduPilot/INAV, further split by `mavType` into copter/plane/rover; 0=Betaflight; 12=PX4 and anything else → no table). Any lookup miss (unrecognized autopilot/mavType/table entry) falls back to `"Mode <n>"` — never a fabricated name. No dependency on `MavlinkTelemetryDecoder` or vice versa beyond this one static call. **docs/DRONE-INFRA-PLAN.md I-e Stage 1** added the reverse lookup, `static Integer customModeFor(int autopilot, int mavType, String modeName)` — the numeric `custom_mode` for a named mode within the same table selection (e.g. `customModeFor(AUTOPILOT_ARDUPILOTMEGA, MAV_TYPE_QUADROTOR, "RTL")` → `6`), `null` when no table is selected or the table has no entry with that exact name. Pure name↔number lookup, no opinion on which firmwares are actually commandable — it happily resolves Betaflight's own `"RTL"`-named entry too (to `6`); deciding Betaflight isn't commandable is `MavlinkFlightCommander`'s job, checked before this method is ever called for that firmware — see this method's own javadoc. **docs/DRONE-INFRA-PLAN.md I-e Stage 2** added `static List<String> selectableModes(int autopilot, int mavType)` — the distinct mode names of the resolved ArduPilot copter/plane/rover table, returned **sorted alphabetically** for a stable/testable order (`Map.ofEntries` has no meaningful iteration order); deliberately ArduPilot-only — Betaflight, PX4, an unrecognized autopilot, and an ArduPilot mavType outside every family all return an **empty** list (Betaflight has a table but its RC link processes no commands, so surfacing its modes as "selectable" would be dishonest). Feeds `MavlinkFlightCommander#capabilities`'s `FlightCapability.selectableModes`.
- `final class MavlinkRoute` (package-private) — minimal `LOOP`-only flight-route engine for TX (parse + `positionAt(metersAlongRoute)`); deliberately duplicates `adapter-simulation`'s `RoutePlan` *technique* (equirectangular approximation), not its code — see Gotchas.
- `final class MavlinkUdpInputStream` / `final class MavlinkUdpOutputStream` (package-private) — bridge a `DatagramSocket` to the `InputStream`/`OutputStream` `MavlinkConnection` expects; one datagram in, one datagram out per MAVLink message. **docs/DRONE-INFRA-PLAN.md I-e Stage 1** added `MavlinkUdpInputStream#lastSourceAddress()` — the source address (`InetSocketAddress`) of the most recently received datagram, `null` before the first one; `MavlinkSocketHub`'s read loop reads it immediately after each `connection.next()` and attributes it to whichever vehicle owned that message, relying on the one-datagram-per-message correspondence this module's TX sides already guarantee (see the class's own javadoc for the exact reasoning and its limits around the pre-existing malformed-frame resync case).

## Conventions
- Plain classes, no Spring — instantiated directly by `vision-app`'s wiring config.
- Lenient numeric option parsing (RX's `sysid`; TX's `speedMps`/`batteryDrainPerSecond`/`positionRateHz`/`failsafeBatteryPercent`/`sysid`) matches every other adapter's idiom: missing/blank/malformed → default (RX: unpinned). `route` is the one deliberate exception (fails fast) — see Gotchas.
- Idempotent close/stop via `AtomicBoolean` CAS, dedicated named threads (`mavlink-telemetry-hub-<host>-<port>` — one per shared bind address, docs/DRONE-INFRA-PLAN.md I-a; `mavlink-feed-<id>`; `mavlink-rc-<deviceId>` — one per engaged manual-control link, docs/RC-CONTROL-PHASE1-PLAN.md R3), close-the-socket-to-unblock-the-read-thread — all identical in shape to `adapter-mjpeg`'s RX/TX runtimes, this module's closest precedent.

## Gotchas
- **`udp://host:port` means listen, not connect (RX).** A telemetry radio or SITL instance *pushes* datagrams to this app; `MavlinkTelemetrySource` never dials out. `host` is the local bind address (wildcard when blank), `port` the local bind port. The sender's own address is never checked — any datagram arriving on the bound port is read, which is also how multiple systems can end up sharing one port (see next point).
- **Multiple systems on one port (docs/DRONE-INFRA-PLAN.md I-a): claim/re-election, not first-wins-forever.** Superseded gotcha, kept for history: before I-a, `MavlinkTelemetryDecoder` locked onto the first system id it ever saw and silently dropped every other system for its whole lifetime, with no re-adoption if that system went silent. As of I-a, `MavlinkSocketHub` owns this instead, per bind address: a **pinned** device (`StreamDescriptor.options["sysid"]` set) claims exactly that sysid, permanently, the first time it's heard, and never re-elects. An **unpinned** device claims the first sysid heard that nothing else already claims (today's old behavior, generalized per socket instead of per device); if its claimed vehicle then falls silent for 30s, it may re-elect to a different, still-unclaimed sysid — but only *lazily*, checked only when a message from some other still-unclaimed sysid next arrives (no timer, no thread beyond the one read loop — see `MavlinkSocketHub#claim`). A sysid nothing claims is not dropped: it lands in the hub's bounded (32) unclaimed-vehicle registry (see below) instead.
- **Source-address demux was descoped for *routing* — sysid is still the only demultiplexing key.** `MavlinkMessage#getOriginSystemId()` only exists on a decoded message, not the raw `DatagramPacket` — a datagram is attributable to a vehicle only *after* parsing. `MavlinkUdpInputStream` (unchanged by I-a) already concatenates every datagram arriving on a socket into one continuous byte stream for `MavlinkConnection` to read frames off of, and does not preserve which source address any given byte came from; teaching it to do so would be real surgery on a component whose whole job is "look like a continuous stream" to a library with no concept of datagram boundaries — out of scope for what I-a needed. `MavlinkSocketHub` therefore demultiplexes by sysid alone, which is also the more correct signal in the field anyway: a companion computer or radio relaying several vehicles is itself the one source address for every one of them, so source-address demux would have been *less* useful, not more. **docs/DRONE-INFRA-PLAN.md I-e Stage 1** later needed a source address after all, but for a completely different reason — *sending a reply*, not routing an inbound message — and got it far more cheaply: `MavlinkUdpInputStream#lastSourceAddress()` (a small, natural addition, since `fill()` already calls `DatagramSocket#receive` into a `DatagramPacket` that carries the sender's address for free) exposes the source of the most recently received datagram, and `MavlinkSocketHub#routeMessage` just remembers it per claim. This did not need the "real surgery" this bullet describes above precisely because it only needs *one* address at a time (the last one), not a per-byte or per-frame history threaded through the continuous-stream abstraction.
- **Unclaimed-vehicle registry (docs/DRONE-INFRA-PLAN.md I-a, consumed by I-b's `MavlinkHeartbeatScanner`).** `MavlinkSocketHub.unclaimedVehicles()` (reachable from `MavlinkTelemetrySource#unclaimedVehicles(bindKey)`, package-private) returns every sysid heard on that socket that no device currently claims: `sysid`, `firmware` (from the most recent `HEARTBEAT`'s `autopilot` field, via `MavlinkTelemetryDecoder.firmwareLabel`, `null` until one arrives), `mavType` (`HEARTBEAT.type`, same caveat), `lastHeard`. Bounded at 32 entries, oldest-by-recency evicted first. I-b added the claimed-side mirror, `claimedVehicles()` (see the `MavlinkSocketHub` API-surface entry above) — together, still the *entire* surface this module exposes for provisioning: no domain/port change, no new public API outside `MavlinkHeartbeatScanner` itself (which does implement the public `DeviceDiscoveryPort`).
- **A discovery scan on an already-open socket only sees what the hub has heard *since it opened*, not the port's full history.** `MavlinkHeartbeatScanner`'s hub-borrow path reads `MavlinkSocketHub`'s live claimed/unclaimed registries — it does not replay anything from before the hub started, and the unclaimed registry itself is bounded (32 entries, oldest-evicted-first) and only ever contains the currently-live view, not a durable log. A vehicle that transmitted for a while, then went silent long before the hub's silence window (30s, production default) elapsed and a *different* still-unclaimed sysid arrived to trigger re-election, is simply gone from both registries — same "no fake reads" honesty as everywhere else in this module, but worth knowing before assuming a scan is a complete history of every aircraft that was ever on the air.
- **Malformed/garbage datagrams need no special handling here.** `io.dronefleet.mavlink.MavlinkConnection#next()` already scans for the next valid frame-start marker and silently drops anything that fails to parse or fails CRC, internally, before ever returning — confirmed by reading `MavlinkPacketReader`/`MavlinkFrameReader`'s own source and proven by `MavlinkRoundTripIntegrationTest`'s noise-interleaved test. `MavlinkUdpInputStream#read()` never returns `-1` (a live listening socket has no natural EOF), which is what lets the library's internal resync loop keep working across datagram boundaries exactly like it would over a continuous serial/TCP stream. The only exception that ever reaches `MavlinkSocketHub`'s own `catch` (docs/DRONE-INFRA-PLAN.md I-a moved this loop from `MavlinkTelemetrySource` into the shared hub) is a genuine `IOException` from the socket itself (almost always its own shutdown unblocking the read thread).
- **`FeedSpec.source()` is repurposed as a destination for TX, not a file.** Every other `FeedTransmitterPort` in this codebase (`RtspFeedTransmitter`, `MjpegFeedTransmitter`) reads a local video *file* named by `source()` and either pushes to its own constructor-injected base or serves its own ephemeral port. MAVLink has no such thing to read — the transmitted content is a synthesized flight plan — and no path-based multiplexing the way RTSP/mediamtx has, so what actually varies per feed is *where to send it*. `MavlinkFeedTransmitter.start()` therefore treats `spec.source()` as the `udp://host:port` **destination** to push datagrams to, and returns it back verbatim as the `StreamDescriptor` — which is also exactly the address a `MavlinkTelemetrySource` should bind/listen on to receive it, since MAVLink UDP push has one shared address for both ends. Documented here because it's the one place this adapter's use of `FeedSpec`/`FeedTransmitterPort` deviates from every other implementation's convention.
- **TX's `route` option has no lenient fallback**, unlike everything else in this codebase (`adapter-simulation`'s `lat`/`lon` circular-track default, this module's own `speedMps`/etc.). A missing/malformed route throws `IllegalArgumentException` at `start()` instead of falling back to a circular track, because reimplementing that fallback would duplicate more of `adapter-simulation`'s `RoutePlan` than this task's "minimal reimplementation" brief called for — see `MavlinkRoute`'s own javadoc.
- **`MavlinkRoute` only implements `LOOP`** (retrace via a closing end→start leg, repeat indefinitely) — no `BOUNCE`/`ONCE` — because a transmitted simulation feed exists to be watched/rehearsed indefinitely, the same reasoning behind `RtspFeedTransmitter`/`MjpegFeedTransmitter`'s own `loop=true` TX default. `adapter-simulation`'s `RoutePlan` (three modes, altitude/bounce folding) is the fuller reference if a future task needs more.
- **`MavlinkFeedTransmitter` and `MavlinkTelemetrySource` are not yet wired into `SimulationService`/`SimulationTransport`** (vision-application) — `SimulationTransport` has no `MAVLINK` variant, and adding one is out of X-a's scope (vision-application wasn't in this task's file scope). Both beans are still fully usable today via the plain device/asset APIs (`POST /api/devices` + `POST /api/assets`, or a future task's `SimulationTransport.MAVLINK`), exactly like `adapter-mjpeg`'s pair was before its own follow-up wiring task landed.
- **`MAV_STATE_CRITICAL`'s wire value is compared by enum identity, never a hardcoded ordinal** (docs/FC-INTEGRATIONS-PLAN.md F-a). The plan's own research-facts prose parenthetically says "`MAV_STATE_CRITICAL (6)`", but the actual `io.dronefleet.mavlink.minimal.MavState` enum (and the upstream MAVLink common.xml spec) defines `MAV_STATE_CRITICAL = 5` and `MAV_STATE_EMERGENCY = 6` — the parenthetical is simply wrong. `MavlinkTelemetryDecoder` sidesteps the discrepancy entirely by comparing `heartbeat.systemStatus().entry() == MavState.MAV_STATE_CRITICAL` (symbolic, not `.value() == 6`), so the correct message decodes as failsafe regardless of anyone's memory of the ordinal. Do not "fix" this comparison to a raw `6` — that would introduce the bug the symbolic form avoids.
- **`base_mode` is read via `.value()` (raw bitmask int), never `.entry()`.** `HEARTBEAT.base_mode` is a genuine bitmask (`MavModeFlag` entries are power-of-two flags: 128 armed, 64 manual-input, ..., 1 custom-mode-enabled) — a real value like `armed + custom-mode-enabled` (`128 | 1 = 129`) does not match any single `MavModeFlag` constant, so `EnumValue#entry()` resolves to `null` for it (the dronefleet deserializer always calls `getEntryByValue`, which only succeeds for values matching exactly one defined constant). `MavlinkTelemetryDecoder`/`MavlinkFeedTransmitter` therefore always work with `.value()` and raw bit tests (`& 128`, `& 1`) for this one field, unlike `autopilot`/`type`/`system_status`, which are genuine single-value enums where `.entry()` (or the builder's semantic `MavAutopilot`/`MavType`/`MavState` overloads) is used and works as expected.
- **`Telemetry#flightState()` materializes only once a `FlightState`-mapped field has actually fired** — see the "Message → field mapping" table's closing note. A device that only ever sends `GLOBAL_POSITION_INT`/`VFR_HUD`/`SYS_STATUS`/`BATTERY_STATUS` (no `HEARTBEAT`/`GPS_RAW_INT`/`RC_CHANNELS`/matching `STATUSTEXT`) never gets a `FlightState` at all — honest, not a bug: this decoder only speaks for what a message actually told it, the same "no fake reads" discipline as every sentinel-to-`null` conversion elsewhere in this class.
- **`FlightModes` is deliberately its own package-private class, not folded into `MavlinkTelemetryDecoder`.** It is pure data (four static tables) plus pure selection logic with zero MAVLink-message/wire-format awareness — a natural, independently-testable unit (see `FlightModesTest`, which exercises it with plain ints, no golden bytes at all) that `MavlinkTelemetryDecoder` calls exactly once per `HEARTBEAT`.
- **ardupilotmega dialect selection is automatic, confirmed against the library's own source (docs/FC-INTEGRATIONS-PLAN.md F-e)** — no fix was needed anywhere in this module to decode `WIND`/`EKF_STATUS_REPORT`/`RANGEFINDER` (ardupilotmega-only messages). Read directly from `~/.m2/.../mavlink-1.1.11-sources.jar`: `io.dronefleet.mavlink.MavlinkConnection.Builder`'s constructor unconditionally registers `MAV_AUTOPILOT_ARDUPILOTMEGA` (and `MAV_AUTOPILOT_PX4`) against `new ArdupilotmegaDialect()`, and every other `MavAutopilot` value against `new CommonDialect()`, *before* any caller-supplied `.dialect(...)`/`.defaultDialect(...)` override — so every `MavlinkConnection.create(in, out)` call in this module (the only construction style used here; none override the dialect map) already has the full ardupilotmega dialect wired in. `MavlinkConnection#next()` resolves and caches the per-system dialect (in its own `systemDialects` map, keyed by system id, scoped to that one connection instance) the moment it decodes that system's first `HEARTBEAT`, then uses it for every later message from that system — meaning a real ArduPilot vehicle's own unsolicited ~1Hz `HEARTBEAT` (autopilot `ARDUPILOTMEGA`, already relied on for `FlightState.firmware`/`mode`) is what silently unlocks these three messages on the one long-lived `MavlinkConnection` each of `MavlinkSocketHub`'s read loop and `MavlinkHeartbeatScanner`'s self-bind path keeps open. Confirmed against the real socket/thread path (not just golden bytes) by `MavlinkRoundTripIntegrationTest`'s new `anArdupilotmegaWindMessageSurvivesTheRealUdpPathIntoATelemetrySample` — a raw `WIND` datagram sent directly to the port `MavlinkFeedTransmitter` is already feeding decodes correctly once the transmitter's own `HEARTBEAT` traffic has taught the shared connection the dialect. **The one real gotcha this implies**: a *brand-new* `MavlinkConnection` that has not yet decoded a `HEARTBEAT` for a given system id falls back to `CommonDialect` for that system and cannot resolve an ardupilotmega-only message id — irrelevant in production (the hub's connection is long-lived and every real ArduPilot vehicle heartbeats constantly) but very relevant for golden-bytes unit tests: `MavlinkTelemetryDecoderTest`'s per-message `encodeThenDecode` helper builds a fresh connection per call, so the three ardupilotmega-only messages needed a second helper, `encodeThenDecodeAsArdupilotmega`, that sends a priming ArduPilot `HEARTBEAT` first on the *same* sender/receiver connection pair before the real payload.
- **The commander's own sysid/compid (255/190) are a convention, not something read off the wire** (docs/DRONE-INFRA-PLAN.md I-e Stage 1). MAVLink has no formal registry binding "255" to "ground control station", but it is the de-facto value QGroundControl/Mission Planner/every common GCS uses, and no real vehicle is expected to claim it (this module's own `MavlinkSocketHub` would happily let a *device* pin sysid 255 too, but nothing stops a human operator from choosing a saner one — Stage 1 does not defend against that self-inflicted collision, matching the plan's own scope). `190` (`MAV_COMP_ID_MISSIONPLANNER`) was picked as the closest standard component id whose own MAVLink description ("a component that can generate/supply a flight plan") fits what this platform is; any other unclaimed component id would have worked equally well for correctness — a real vehicle's `COMMAND_ACK` handling does not inspect the sender's component id, only its `targetSystem`/`targetComponent` *if present at all* (see next bullet).
- **`COMMAND_ACK` matching is by `(sysid, command id)` only — this module never inspects `CommandAck.targetSystem()`/`targetComponent()`.** Those two fields are `extension` fields on the wire (added later to the MAVLink common dialect) and are not guaranteed to be populated by every firmware/dialect version; `MavlinkSocketHub#routeMessage` matches a pending `awaitAck` waiter purely by the ack's `getOriginSystemId()` (the vehicle that sent it) and `command().value()` (which command it's acknowledging) — both of which every `COMMAND_ACK`, old or new, reliably carries. This is also why `MavlinkFlightCommander` never sets `targetSystem`/`targetComponent` when building its own reply-side expectations — there is nothing to set; matching happens entirely on the hub's existing per-sysid claim plus the command id.
- **A one-shot `awaitAck` future must always be paired with `cancelAckWait` in a `finally` block**, exactly as `MavlinkFlightCommander#sendReturnToHome` does. `MavlinkSocketHub#ackWaiters` is a plain `HashMap` guarded by the hub's own lock, not a cache with eviction — a waiter that is registered but never explicitly removed (a caller that forgets the `finally`, or throws between `awaitAck` and the matching `cancelAckWait`) stays in that map forever, both leaking memory and permanently shadowing any *future* ack for the same `(sysid, commandId)` pair (a second `returnToHome` call to the same vehicle would silently register a second waiter under the same key, clobbering the first in the map — `Map#put` semantics — rather than either erroring or coexisting). Stage 1 has exactly one caller and one command id, so this has not yet been exercised by a real leak, but it is a sharp edge worth knowing before Stage 2 adds more commands/callers onto the same map. **docs/DRONE-INFRA-PLAN.md I-e Stage 2** did add more command ids (`400` for arm/disarm) and callers (setMode/arm/disarm), but every one routes through `MavlinkFlightCommander`'s single shared `send()` helper whose `finally` always pairs the `awaitAck` with `cancelAckWait` under the same `(sysid, commandId)` key — the discipline is preserved by construction, not re-litigated per command.
- **`MavlinkFlightCommanderTest`'s fake vehicle heartbeats continuously (~5Hz), not once.** The first draft sent exactly one `HEARTBEAT` on construction, mirroring how little wire traffic the test actually needs — and flaked, because that single heartbeat could arrive before `MavlinkSocketHub`'s read thread had finished binding its socket (a `register()` call starts the thread asynchronously; there is no synchronous "socket is now listening" signal back to the caller) and was simply lost, exactly like a real vehicle's heartbeat would be if the gateway wasn't listening yet. A real feed transmitter or SITL instance never has this problem because it heartbeats forever, so eventually one lands after the socket is up; the fake vehicle now does the same, and the write path (heartbeat thread + the vehicle-under-test-control thread's own ack reply) is guarded by a private lock since both share one `MavlinkUdpOutputStream`'s non-thread-safe internal buffer.
- **`MavlinkSitlSmokeIntegrationTest` uses `--network host`, not `up.sh`'s bridge-network + `host.docker.internal` combination**, because a test only needs one ephemeral localhost port for one run, not a stable well-known port multiple real operators might share — host networking lets `MAVLINK_TARGET_HOST=127.0.0.1` mean exactly the JVM's own loopback with no extra indirection, and avoids needing `--add-host=host.docker.internal:host-gateway` at all. This is a test-only convenience; it does not change anything about `infra/sitl/entrypoint.sh` itself (still just reads `MAVLINK_TARGET_HOST`/`MAVLINK_TARGET_PORT`, oblivious to which networking mode picked their values). Observed live on this task's own dev machine: with the image already built and cached, the whole test (container start → first `HEARTBEAT`/`GPS_RAW_INT` decoding into a `Telemetry` with a non-null `FlightState`) completed in under 2 seconds — ArduPilot's `HEARTBEAT` needs no GPS/EKF convergence, unlike the ~45-70s "boot-to-flying" figure in `infra/sitl/README.md`, which times arm+takeoff, a much later milestone this test deliberately never waits for (see its own javadoc for why it doesn't attempt command TX against SITL at all).
- **`MavlinkManualControlSender` sends on the hub's shared socket, deliberately, not an ephemeral one of its own** (docs/RC-CONTROL-PHASE1-PLAN.md R3) — the one hard requirement this port adds over `MavlinkFeedTransmitter`'s own long-standing "own ephemeral socket per feed" precedent. The RC-override stream must appear to come from the same `host:port` the platform's telemetry gateway already listens on so the flight controller sees one consistent GCS endpoint; sending from a second, different local port would still technically reach the vehicle (MAVLink itself doesn't care), but would be a needless deviation from "one platform, one address" with no upside. `DatagramSocket#send` is thread-safe (confirmed by this class coexisting with `MavlinkSocketHub`'s own read thread and any concurrent `MavlinkFlightCommander` write on the exact same socket, at up to 50Hz in this class's own test suite, with zero observed contention issues across three consecutive full-module runs), so sharing costs nothing.
- **Every tick re-resolves the claim; nothing is cached at `engage()`-time.** A device's sysid can (rarely) re-elect and its `sourceAddress` refreshes on every inbound datagram (see `MavlinkSocketHub`'s own claim-semantics Gotchas above) — caching either at `engage()` would let the sender silently keep transmitting to a stale address after a re-election, or with the wrong `targetSystem` after one. Paying a `commandTarget`/`socket` lookup (both simple map reads under the hub's lock) on every tick, up to 50Hz, is cheap enough not to matter and keeps the link honest about where the vehicle actually is *right now*.
- **A lost claim mid-link pauses, it does not fail.** If `commandTarget` returns `null` (or a claim with no `sourceAddress` yet) on some tick after `engage()` already succeeded, the tick is skipped — no exception, no thread death, no busy-spin — because a vehicle going briefly quiet (a re-election window, a flaky radio) is an expected field condition, not a bug; the thread keeps ticking and resumes real sends the instant the vehicle is heard again. Logged once on each transition (WARNING losing reachability, INFO regaining it) rather than either silently or once per tick at up to 50Hz.
- **The mailbox write is `synchronized`, not bare-volatile, specifically to close one release-ordering race.** `send()` and `release()`'s own release-sentinel write both go through one monitor (`send()` re-checks `closed` *inside* the lock before writing); without it, a `send()` call already in flight when `release()` starts could theoretically land its "real" channel values *after* `release()`'s all-`RELEASE` write, defeating the "release truly means release" guarantee. The tick loop still reads the mailbox lock-free (a single `volatile` read), since only the *last* writer before a given tick matters and torn reads are not possible for an object reference — no reader-side lock needed.
- **`RcLinkRuntime`'s send loop does not check `closed` to decide whether to keep running.** `release()` deliberately leaves the loop ticking (on `!Thread.currentThread().isInterrupted()` alone) for `releaseFrameCount` ticks *after* `closed` has already flipped true, specifically so the release burst it just queued actually gets a chance to go out over the wire before the thread is told to stop — checking `closed` in the loop condition would race the burst against the flag flip and could suppress it entirely.
- **`release()` blocks the *caller's* thread for `releaseFrameCount * tickPeriodMillis`**, deliberately — that sleep is what gives the still-running sender thread time to emit the burst before `release()` goes on to interrupt+join it. `ManualControlLink`'s own javadoc already documents that `release` "may block briefly to join" the sender thread; this is the same contract, just with a bounded sleep in front of the join rather than only the join itself. At the production default (33Hz, 3 frames) that's ~90ms; test-seam-injected fast ticks (this module's own suite uses ~20ms) keep it well under a second.
- **`COMMANDER_SYSTEM_ID`/`COMMANDER_COMPONENT_ID`/`TARGET_COMPONENT_AUTOPILOT` are reused directly from `MavlinkFlightCommander`**, not re-declared on this class — both classes share the exact same GCS-identity convention (255/190 → autopilot comp 1, see the dedicated Gotchas entry above for why those specific numbers), and package-private visibility already makes them reachable from any class in this package. Duplicating the constants would have meant two places that must agree forever; referencing them keeps that a compile-time-enforced single source of truth.

## Try it with a real SITL instance

ArduPilot's SITL can push straight at this adapter without needing `MavlinkFeedTransmitter` at all — register a `mavlink` telemetry device with `uri = udp://0.0.0.0:14550` (or any free port) and point SITL at it:

```
sim_vehicle.py -v ArduCopter --out=udp:127.0.0.1:14550
```

(`--out` tells SITL to *push* MAVLink to that address — matches this adapter's listen-not-connect model exactly.)
