# adapter-mavlink

MAVLink 2 UDP telemetry ingest (RX) and flight-plan transmit simulator (TX) — docs/MVP2-PLAN.md X-a, the first *real drone* protocol under the RX/TX doctrine (`docs/CYCLES-PLAN.md` §0). docs/FC-INTEGRATIONS-PLAN.md F-a added flight-controller-aware decoding: armed/mode/failsafe/GPS/RSSI/arming-blockers, surfaced as `Telemetry#flightState()`. docs/DRONE-INFRA-PLAN.md I-a turned RX into a genuine **fleet gateway**: N vehicles now coexist on one shared UDP port instead of needing one port each. docs/DRONE-INFRA-PLAN.md I-b added **plug-and-fly heartbeat discovery** (`MavlinkHeartbeatScanner`): every distinct sysid heard on the gateway's port becomes a `DiscoveredDevice`, no manual sysid/URI entry. docs/FC-INTEGRATIONS-PLAN.md F-e added five more ArduPilot-only messages (`WIND`/`VIBRATION`/`EKF_STATUS_REPORT`/`MISSION_CURRENT`/`RANGEFINDER`) into `Telemetry.extra`, riding the ardupilotmega dialect the library already auto-selects — no wiring change.

## Library choice

**`io.dronefleet.mavlink:mavlink` 1.1.11** (Maven Central, latest as of this task — checked 2026-07-23; last released 2023-02-27, dependency-free at runtime: its own `mavlink-protocol` sub-artifact declares zero non-test dependencies, and the combined jars are ~1.8 MB, mostly generated per-dialect message classes). Chosen over hand-rolling frame decode because:
- It already CRC-validates and auto-resyncs past malformed/unparseable frames inside `MavlinkConnection#next()` (skips bad frames and keeps scanning for the next valid one, never throws for that case) — exactly the "unparseable datagrams skipped, never fatal" requirement, for free.
- Typed, code-generated message classes (`GlobalPositionInt`, `Heartbeat`, `SysStatus`, ...) with builders — no manual bit-twiddling for the messages this task needs, and headroom for more (`BATTERY_STATUS`, attitude, etc.) without touching the wire-format layer later.
- No transitive baggage to justify avoiding it (see size/deps above) — the "hand-roll if it drags baggage" escape hatch in this task's brief doesn't apply.

Version pinned via root `pom.xml`'s `<dronefleet-mavlink.version>` property, same pattern as `javacv.version`/`jmdns.version`.

## API surface

### `com.drones.vision.adapter.mavlink`
- `final class MavlinkTelemetrySource implements TelemetrySourcePort` — RX. Supports protocol `"mavlink"` with a `udp://host:port` `StreamDescriptor.uri()` and `Capability.TELEMETRY`. `supports(Device)`, `open(Device): Flow.Publisher<Telemetry>`, `close(DeviceId)`.
  - **`udp://host:port` means listen, not connect** — see Gotchas. `host` blank/absent → binds the wildcard `0.0.0.0` (all interfaces).
  - **docs/DRONE-INFRA-PLAN.md I-a — fleet gateway.** `open()` no longer binds its own socket: it registers with a shared `MavlinkSocketHub` keyed by bind address (`bindKey(host, port)` = `"host:port"`, package-private static), reference-counted across every device sharing that address. `StreamDescriptor.options["sysid"]` — a positive int 1-255, lenient parse (missing/blank/malformed/out-of-range → unpinned, same idiom as every other option in this module) — pins the device to exactly that MAVLink system id; omitted/invalid means unpinned (claims the first unclaimed sysid heard, re-electable — see `MavlinkSocketHub` and the Gotchas below for the full claim/re-election rules this replaces the old single-device behavior with). `close(id)` releases this device's registration; the hub's socket/thread only actually shut down once the last registration on that bind address releases. Package-private `unclaimedVehicles(bindKey)` exposes vehicles heard-but-claimed-by-nobody on that address; **docs/DRONE-INFRA-PLAN.md I-b** added two more package-private methods consumed by `MavlinkHeartbeatScanner` (below): `hasActiveHub(bindKey)` (whether some device currently has that address open — the hub-borrow-vs-self-bind decision point) and `claimedVehicles(bindKey)` (delegates to `MavlinkSocketHub#claimedVehicles()`, see next bullet). A package-private constructor `MavlinkTelemetrySource(long silenceWindowMillis)` overrides the 30s production re-election silence window for tests; the public no-arg constructor (used by `vision-app`'s wiring, unchanged) defaults to it.
- `final class MavlinkSocketHub` (package-private, docs/DRONE-INFRA-PLAN.md I-a) — one shared `DatagramSocket` + one dedicated read thread (`mavlink-telemetry-hub-<host>-<port>`) per distinct bind address, owned entirely by `MavlinkTelemetrySource`. Demultiplexes every decoded `MavlinkMessage` by system id (never source address — see Gotchas) to the registered device that claims it, creating a **fresh** `MavlinkTelemetryDecoder` per claim/re-election (a decoder's accumulated fields belong to one physical vehicle; reusing one across a claim change would leak stale values). `register`/`unregister` are called from whatever thread calls `open`/`close`; all claim/routing state is guarded by one monitor, touched by both those callers and the hub's own read thread. `unregister` returns whether the hub is now empty (0 registrations), so `MavlinkTelemetrySource` knows to evict it from its hub map and let the next `open()` for that address build a fresh one. `unclaimedVehicles()` returns a bounded (max 32, oldest-evicted-first) list of `UnclaimedVehicle(sysid, firmware, mavType, lastHeard)` records for vehicles nobody currently claims. **docs/DRONE-INFRA-PLAN.md I-b** added `claimedVehicles()`, returning one `ClaimedVehicle(sysid, deviceId, firmware, mavType, lastHeard)` per currently-claimed registration — `VehicleRegistration` gained its own `firmware`/`mavType` fields (mutated under the same lock, refreshed from every `HEARTBEAT` a claimed vehicle sends, via the new `captureHeartbeatInfo` — the claimed-side mirror of the pre-existing `recordUnclaimed`) so a claimed vehicle can be labeled the same way an unclaimed one already was.
- `final class MavlinkHeartbeatScanner implements DeviceDiscoveryPort` (**new**, docs/DRONE-INFRA-PLAN.md I-b) — plug-and-fly heartbeat discovery. `method()` = `"mavlink"`. Constructor takes the `MavlinkTelemetrySource` instance to borrow from (`vision-app` wires the same singleton bean used for real telemetry ingest) and the port to scan (port-agnostic; `vision-app` wires the well-known default, 14550); the bind host is always the wildcard (`MavlinkTelemetrySource.DEFAULT_BIND_HOST`), matching how an omitted/blank device URI host already defaults. `scan(timeout)` picks one of two paths per call, based on `telemetrySource.hasActiveHub(bindKey)`:
  - **Hub already active** — no bind of its own. Polls `claimedVehicles`/`unclaimedVehicles` a handful of times (`ACTIVE_HUB_POLL_COUNT` = 5, spaced across the timeout, floor `ACTIVE_HUB_MIN_POLL_INTERVAL_MILLIS` = 20ms — no busy-spin) so a vehicle whose first `HEARTBEAT` lands partway through the scan still gets a real firmware/vehicle-kind label by the last poll. A claimed vehicle is reported with `details["claimed"]="true"` + `details["claimedBy"]=<device id>` (poka-yoke against a duplicate asset); an unclaimed one is reported plain.
  - **No active hub** — binds the port itself for the scan's duration (`DatagramSocket` + `setReuseAddress(true)`), reusing `MavlinkConnection`/`MavlinkUdpInputStream` exactly like `MavlinkSocketHub`'s own read loop, with `SO_TIMEOUT` (20-200ms, clamped from the requested timeout) so the blocking read loop can re-check its deadline without busy-spinning; releases the socket in a `finally`. A bind failure (`IOException`, e.g. the port is held by something other than this app's own gateway) is caught, logged at WARNING, and returns an empty list — **never thrown** (discovery must never break the scan-all flow over one mechanism's bind conflict).
  - Naming: `"<Firmware> <vehicle kind> (sysid <n>)"`, e.g. `"ArduPilot quadcopter (sysid 7)"` — firmware from `HEARTBEAT.autopilot` (reuses `MavlinkTelemetryDecoder.firmwareLabel`, mapped to a display name: ardupilot→ArduPilot, px4→PX4, generic→Generic, unknown/null→MAVLink) and vehicle kind from `HEARTBEAT.type` (own local `MAV_TYPE_*` constants, duplicated from upstream rather than reused from `FlightModes`, whose own constants are private and exist there only to pick a mode table — not to label a vehicle kind): quadcopter/hexacopter/octocopter/tricopter/helicopter/fixed-wing/rover/boat, or `"vehicle"` if unknown/not yet heard. `suggestedCategory` is `CategoryId("drone")` only for an airborne kind (quadcopter/hexacopter/octocopter/tricopter/helicopter/fixed-wing); rover/boat/unknown gets no suggested category. `suggestedStream` is `StreamDescriptor("mavlink", udp://0.0.0.0:<port>, {"sysid": "<n>"})`. `details` always carries `firmware` (raw label or `"unknown"`), `mavType` (the vehicle-kind label, not the raw int), `sysid`; `claimed`/`claimedBy` only when already registered.
  - Blocking, self-time-boxed to ~`timeout` on both paths; an empty list ("nothing heard") is never an error, per `DeviceDiscoveryPort`'s contract.
- `final class MavlinkFeedTransmitter implements FeedTransmitterPort` — TX. Supports `FeedSpec.protocol()` `"mavlink"` with a `source()` whose scheme is `udp` and which carries a non-blank host **and** a positive port. `supports(FeedSpec)`, `start(FeedId, FeedSpec): StreamDescriptor`, `stop(FeedId)`.
  - **`FeedSpec.source()` is repurposed as a destination**, not a file — see Gotchas.
  - Options: `route` (**required**, `lat,lon[,altM];lat,lon[,altM];...`, ≥2 points — missing/malformed → `IllegalArgumentException` at `start()`, no lenient fallback); `speedMps` (default 12.0); `batteryDrainPerSecond` (default 0.05 %/s); `positionRateHz` (default 5.0); `failsafeBatteryPercent` (docs/FC-INTEGRATIONS-PLAN.md F-a, default 15.0 — battery percent below which `HEARTBEAT` switches to the failsafe custom_mode/system_status described below; lenient like `batteryDrainPerSecond`, i.e. a non-positive value is accepted as-is, `0` meaning "never"); `sysid` (docs/DRONE-INFRA-PLAN.md I-a, default `DEFAULT_MAV_SYSTEM_ID` = 1 — the MAVLink system id every message from this feed carries; lenient, missing/blank/unparseable/out of 1-255 → default). The other numeric options: non-positive/unparseable → default (same lenient idiom as every other adapter, except `route` itself).
  - nested `private static final class FeedRuntime` — one dedicated platform thread (`mavlink-feed-<id>`) per `start()`: owns an ephemeral `DatagramSocket`, sends `HEARTBEAT`+`SYS_STATUS`+`GPS_RAW_INT` once a second and `GLOBAL_POSITION_INT` at `positionRateHz`, as system id `sysid` (default 1) / component id 1, paced by a 50ms tick loop comparing wall-clock deadlines (not a `ScheduledExecutorService` — one thread, two cadences, simplest thing that works). `close()`: same CAS/interrupt/bounded-join (5s) shape as RX.
  - docs/FC-INTEGRATIONS-PLAN.md F-a: `HEARTBEAT` now reports `autopilot` ARDUPILOTMEGA, `type` QUADROTOR, `base_mode` armed+custom-mode-enabled, and `custom_mode`/`system_status` that flip together once the simulated battery drains below `failsafeBatteryPercent` — nominal: `custom_mode` `CUSTOM_MODE_LOITER` (5, "Loiter") + `system_status` ACTIVE; failsafe-triggered: `custom_mode` `CUSTOM_MODE_RTL` (6, "RTL") + `system_status` CRITICAL. `GPS_RAW_INT` is a fixed 3D fix, 12 satellites, eph 90 (hdop 0.9), lat/lon taken from the same route position `GLOBAL_POSITION_INT` uses.
  - docs/DRONE-INFRA-PLAN.md I-a: the `sysid` option exists specifically so a single test (or a real multi-vehicle rehearsal) can run two or more feeds with distinct system ids at one destination, matching how `MavlinkTelemetrySource`/`MavlinkSocketHub` demultiplex real multi-vehicle traffic.
- `final class MavlinkTelemetryDecoder` (package-private) — stateful message→`Telemetry` merger; one instance per claim (fresh on every RX `open()` and on every hub-level claim/re-election, see `MavlinkSocketHub`). See "Message → field mapping" below and its own javadoc for the full unit-conversion table. docs/FC-INTEGRATIONS-PLAN.md F-a: also merges a `FlightState` (armed/mode/failsafe/GPS/RSSI/arming-blockers), carried as `Telemetry#flightState()`, `null` until at least one `FlightState` field has actually become known (see Gotchas). Its own system-id lock (first sysid observed wins, no re-election) is unchanged and still exercised directly by this class's own unit tests, but as of I-a is no longer reachable in practice through `MavlinkTelemetrySource`: `MavlinkSocketHub` demultiplexes by sysid *before* a message reaches a decoder. `static String firmwareLabel(int autopilot)` is package-private (not `private`) specifically so `MavlinkSocketHub` can reuse it to label unclaimed vehicles.
- `final class FlightModes` (package-private, docs/FC-INTEGRATIONS-PLAN.md F-a) — `static String name(int autopilot, int mavType, long customMode)`: ArduPilot copter/plane/rover + Betaflight mode-number→name tables, table selected by `autopilot` (3=ArduPilot/INAV, further split by `mavType` into copter/plane/rover; 0=Betaflight; 12=PX4 and anything else → no table). Any lookup miss (unrecognized autopilot/mavType/table entry) falls back to `"Mode <n>"` — never a fabricated name. No dependency on `MavlinkTelemetryDecoder` or vice versa beyond this one static call.
- `final class MavlinkRoute` (package-private) — minimal `LOOP`-only flight-route engine for TX (parse + `positionAt(metersAlongRoute)`); deliberately duplicates `adapter-simulation`'s `RoutePlan` *technique* (equirectangular approximation), not its code — see Gotchas.
- `final class MavlinkUdpInputStream` / `final class MavlinkUdpOutputStream` (package-private) — bridge a `DatagramSocket` to the `InputStream`/`OutputStream` `MavlinkConnection` expects; one datagram in, one datagram out per MAVLink message.

Every other message type (hundreds in the common dialect) is ignored. `Telemetry#flightState()` stays `null` until at least one row above *through `STATUSTEXT`* has actually fired at least once for the decoder's lifetime (`SYS_STATUS`'s `batteryVoltage` alone never counts — it lives in `extra`, not `FlightState`; none of the five F-e rows below `STATUSTEXT` touch `FlightState` either — they are `extra`-only, same as `batteryVoltage`). None of the five F-e keys have a documented "unknown" sentinel in the ArduPilot source for these messages (unlike GPS/RSSI/battery above) — last-message-wins, no sentinel-to-`null` conversion.

## Conventions
- Plain classes, no Spring — instantiated directly by `vision-app`'s wiring config.
- Lenient numeric option parsing (RX's `sysid`; TX's `speedMps`/`batteryDrainPerSecond`/`positionRateHz`/`failsafeBatteryPercent`/`sysid`) matches every other adapter's idiom: missing/blank/malformed → default (RX: unpinned). `route` is the one deliberate exception (fails fast) — see Gotchas.
- Idempotent close/stop via `AtomicBoolean` CAS, dedicated named threads (`mavlink-telemetry-hub-<host>-<port>` — one per shared bind address, docs/DRONE-INFRA-PLAN.md I-a; `mavlink-feed-<id>`), close-the-socket-to-unblock-the-read-thread — all identical in shape to `adapter-mjpeg`'s RX/TX runtimes, this module's closest precedent.

## Gotchas
- **`udp://host:port` means listen, not connect (RX).** A telemetry radio or SITL instance *pushes* datagrams to this app; `MavlinkTelemetrySource` never dials out. `host` is the local bind address (wildcard when blank), `port` the local bind port. The sender's own address is never checked — any datagram arriving on the bound port is read, which is also how multiple systems can end up sharing one port (see next point).
- **Multiple systems on one port (docs/DRONE-INFRA-PLAN.md I-a): claim/re-election, not first-wins-forever.** Superseded gotcha, kept for history: before I-a, `MavlinkTelemetryDecoder` locked onto the first system id it ever saw and silently dropped every other system for its whole lifetime, with no re-adoption if that system went silent. As of I-a, `MavlinkSocketHub` owns this instead, per bind address: a **pinned** device (`StreamDescriptor.options["sysid"]` set) claims exactly that sysid, permanently, the first time it's heard, and never re-elects. An **unpinned** device claims the first sysid heard that nothing else already claims (today's old behavior, generalized per socket instead of per device); if its claimed vehicle then falls silent for 30s, it may re-elect to a different, still-unclaimed sysid — but only *lazily*, checked only when a message from some other still-unclaimed sysid next arrives (no timer, no thread beyond the one read loop — see `MavlinkSocketHub#claim`). A sysid nothing claims is not dropped: it lands in the hub's bounded (32) unclaimed-vehicle registry (see below) instead.
- **Source-address demux was descoped — sysid is the only demultiplexing key.** `MavlinkMessage#getOriginSystemId()` only exists on a decoded message, not the raw `DatagramPacket` — a datagram is attributable to a vehicle only *after* parsing. `MavlinkUdpInputStream` (unchanged by I-a) already concatenates every datagram arriving on a socket into one continuous byte stream for `MavlinkConnection` to read frames off of, and does not preserve which source address any given byte came from; teaching it to do so would be real surgery on a component whose whole job is "look like a continuous stream" to a library with no concept of datagram boundaries — out of scope for what I-a needed. `MavlinkSocketHub` therefore demultiplexes by sysid alone, which is also the more correct signal in the field anyway: a companion computer or radio relaying several vehicles is itself the one source address for every one of them, so source-address demux would have been *less* useful, not more.
- **Unclaimed-vehicle registry (docs/DRONE-INFRA-PLAN.md I-a, consumed by I-b's `MavlinkHeartbeatScanner`).** `MavlinkSocketHub.unclaimedVehicles()` (reachable from `MavlinkTelemetrySource#unclaimedVehicles(bindKey)`, package-private) returns every sysid heard on that socket that no device currently claims: `sysid`, `firmware` (from the most recent `HEARTBEAT`'s `autopilot` field, via `MavlinkTelemetryDecoder.firmwareLabel`, `null` until one arrives), `mavType` (`HEARTBEAT.type`, same caveat), `lastHeard`. Bounded at 32 entries, oldest-by-recency evicted first. I-b added the claimed-side mirror, `claimedVehicles()` (see the `MavlinkSocketHub` API-surface entry above) — together, still the *entire* surface this module exposes for provisioning: no domain/port change, no new public API outside `MavlinkHeartbeatScanner` itself (which does implement the public `DeviceDiscoveryPort`).
- **A discovery scan on an already-open socket only sees what the hub has heard *since it opened*, not the port's full history.** `MavlinkHeartbeatScanner`'s hub-borrow path reads `MavlinkSocketHub`'s live claimed/unclaimed registries — it does not replay anything from before the hub started, and the unclaimed registry itself is bounded (32 entries, oldest-evicted-first) and only ever contains the currently-live view, not a durable log. A vehicle that transmitted for a while, then went silent long before the hub's silence window (30s, production default) elapsed and a *different* still-unclaimed sysid arrived to trigger re-election, is simply gone from both registries — same "no fake reads" honesty as everywhere else in this module, but worth knowing before assuming a scan is a complete history of every aircraft that was ever on the air.
- **Malformed/garbage datagrams need no special handling here.** `io.dronefleet.mavlink.MavlinkConnection#next()` already scans for the next valid frame-start marker and silently drops anything that fails to parse or fails CRC, internally, before ever returning — confirmed by reading `MavlinkPacketReader`/`MavlinkFrameReader`'s own source and proven by `MavlinkRoundTripIntegrationTest`'s noise-interleaved test. `MavlinkUdpInputStream#read()` never returns `-1` (a live listening socket has no natural EOF), which is what lets the library's internal resync loop keep working across datagram boundaries exactly like it would over a continuous serial/TCP stream. The only exception that ever reaches `MavlinkSocketHub`'s own `catch` (docs/DRONE-INFRA-PLAN.md I-a moved this loop from `MavlinkTelemetrySource` into the shared hub) is a genuine `IOException` from the socket itself (almost always its own shutdown unblocking the read thread).
- **`FeedSpec.source()` is repurposed as a destination for TX, not a file.** Every other `FeedTransmitterPort` in this codebase (`RtspFeedTransmitter`, `MjpegFeedTransmitter`) reads a local video *file* named by `source()` and either pushes to its own constructor-injected base or serves its own ephemeral port. MAVLink has no such thing to read — the transmitted content is a synthesized flight plan — and no path-based multiplexing the way RTSP/mediamtx has, so what actually varies per feed is *where to send it*. `MavlinkFeedTransmitter.start()` therefore treats `spec.source()` as the `udp://host:port` **destination** to push datagrams to, and returns it back verbatim as the `StreamDescriptor` — which is also exactly the address a `MavlinkTelemetrySource` should bind/listen on to receive it, since MAVLink UDP push has one shared address for both ends. Documented here because it's the one place this adapter's use of `FeedSpec`/`FeedTransmitterPort` deviates from every other implementation's convention.
- **TX's `route` option has no lenient fallback**, unlike everything else in this codebase (`adapter-simulation`'s `lat`/`lon` circular-track default, this module's own `speedMps`/etc.). A missing/malformed route throws `IllegalArgumentException` at `start()` instead of falling back to a circular track, because reimplementing that fallback would duplicate more of `adapter-simulation`'s `RoutePlan` than this task's "minimal reimplementation" brief called for — see `MavlinkRoute`'s own javadoc.
- **`MavlinkRoute` only implements `LOOP`** (retrace via a closing end→start leg, repeat indefinitely) — no `BOUNCE`/`ONCE` — because a transmitted simulation feed exists to be watched/rehearsed indefinitely, the same reasoning behind `RtspFeedTransmitter`/`MjpegFeedTransmitter`'s own `loop=true` TX default. `adapter-simulation`'s `RoutePlan` (three modes, altitude/bounce folding) is the fuller reference if a future task needs more.
- **`MavlinkFeedTransmitter` and `MavlinkTelemetrySource` are not yet wired into `SimulationService`/`SimulationTransport`** (vision-application) — `SimulationTransport` has no `MAVLINK` variant, and adding one is out of X-a's scope (vision-application wasn't in this task's file scope). Both beans are still fully usable today via the plain device/asset APIs (`POST /api/devices` + `POST /api/assets`, or a future task's `SimulationTransport.MAVLINK`), exactly like `adapter-mjpeg`'s pair was before its own follow-up wiring task landed.
- **`MAV_STATE_CRITICAL`'s wire value is compared by enum identity, never a hardcoded ordinal** (docs/FC-INTEGRATIONS-PLAN.md F-a). The plan's own research-facts prose parenthetically says "`MAV_STATE_CRITICAL (6)`", but the actual `io.dronefleet.mavlink.minimal.MavState` enum (and the upstream MAVLink common.xml spec) defines `MAV_STATE_CRITICAL = 5` and `MAV_STATE_EMERGENCY = 6` — the parenthetical is simply wrong. `MavlinkTelemetryDecoder` sidesteps the discrepancy entirely by comparing `heartbeat.systemStatus().entry() == MavState.MAV_STATE_CRITICAL` (symbolic, not `.value() == 6`), so the correct message decodes as failsafe regardless of anyone's memory of the ordinal. Do not "fix" this comparison to a raw `6` — that would introduce the bug the symbolic form avoids.
- **`base_mode` is read via `.value()` (raw bitmask int), never `.entry()`.** `HEARTBEAT.base_mode` is a genuine bitmask (`MavModeFlag` entries are power-of-two flags: 128 armed, 64 manual-input, ..., 1 custom-mode-enabled) — a real value like `armed + custom-mode-enabled` (`128 | 1 = 129`) does not match any single `MavModeFlag` constant, so `EnumValue#entry()` resolves to `null` for it (the dronefleet deserializer always calls `getEntryByValue`, which only succeeds for values matching exactly one defined constant). `MavlinkTelemetryDecoder`/`MavlinkFeedTransmitter` therefore always work with `.value()` and raw bit tests (`& 128`, `& 1`) for this one field, unlike `autopilot`/`type`/`system_status`, which are genuine single-value enums where `.entry()` (or the builder's semantic `MavAutopilot`/`MavType`/`MavState` overloads) is used and works as expected.
- **`Telemetry#flightState()` materializes only once a `FlightState`-mapped field has actually fired** — see the "Message → field mapping" table's closing note. A device that only ever sends `GLOBAL_POSITION_INT`/`VFR_HUD`/`SYS_STATUS`/`BATTERY_STATUS` (no `HEARTBEAT`/`GPS_RAW_INT`/`RC_CHANNELS`/matching `STATUSTEXT`) never gets a `FlightState` at all — honest, not a bug: this decoder only speaks for what a message actually told it, the same "no fake reads" discipline as every sentinel-to-`null` conversion elsewhere in this class.
- **`FlightModes` is deliberately its own package-private class, not folded into `MavlinkTelemetryDecoder`.** It is pure data (four static tables) plus pure selection logic with zero MAVLink-message/wire-format awareness — a natural, independently-testable unit (see `FlightModesTest`, which exercises it with plain ints, no golden bytes at all) that `MavlinkTelemetryDecoder` calls exactly once per `HEARTBEAT`.
- **ardupilotmega dialect selection is automatic, confirmed against the library's own source (docs/FC-INTEGRATIONS-PLAN.md F-e)** — no fix was needed anywhere in this module to decode `WIND`/`EKF_STATUS_REPORT`/`RANGEFINDER` (ardupilotmega-only messages). Read directly from `~/.m2/.../mavlink-1.1.11-sources.jar`: `io.dronefleet.mavlink.MavlinkConnection.Builder`'s constructor unconditionally registers `MAV_AUTOPILOT_ARDUPILOTMEGA` (and `MAV_AUTOPILOT_PX4`) against `new ArdupilotmegaDialect()`, and every other `MavAutopilot` value against `new CommonDialect()`, *before* any caller-supplied `.dialect(...)`/`.defaultDialect(...)` override — so every `MavlinkConnection.create(in, out)` call in this module (the only construction style used here; none override the dialect map) already has the full ardupilotmega dialect wired in. `MavlinkConnection#next()` resolves and caches the per-system dialect (in its own `systemDialects` map, keyed by system id, scoped to that one connection instance) the moment it decodes that system's first `HEARTBEAT`, then uses it for every later message from that system — meaning a real ArduPilot vehicle's own unsolicited ~1Hz `HEARTBEAT` (autopilot `ARDUPILOTMEGA`, already relied on for `FlightState.firmware`/`mode`) is what silently unlocks these three messages on the one long-lived `MavlinkConnection` each of `MavlinkSocketHub`'s read loop and `MavlinkHeartbeatScanner`'s self-bind path keeps open. Confirmed against the real socket/thread path (not just golden bytes) by `MavlinkRoundTripIntegrationTest`'s new `anArdupilotmegaWindMessageSurvivesTheRealUdpPathIntoATelemetrySample` — a raw `WIND` datagram sent directly to the port `MavlinkFeedTransmitter` is already feeding decodes correctly once the transmitter's own `HEARTBEAT` traffic has taught the shared connection the dialect. **The one real gotcha this implies**: a *brand-new* `MavlinkConnection` that has not yet decoded a `HEARTBEAT` for a given system id falls back to `CommonDialect` for that system and cannot resolve an ardupilotmega-only message id — irrelevant in production (the hub's connection is long-lived and every real ArduPilot vehicle heartbeats constantly) but very relevant for golden-bytes unit tests: `MavlinkTelemetryDecoderTest`'s per-message `encodeThenDecode` helper builds a fresh connection per call, so the three ardupilotmega-only messages needed a second helper, `encodeThenDecodeAsArdupilotmega`, that sends a priming ArduPilot `HEARTBEAT` first on the *same* sender/receiver connection pair before the real payload.

## Try it with a real SITL instance

ArduPilot's SITL can push straight at this adapter without needing `MavlinkFeedTransmitter` at all — register a `mavlink` telemetry device with `uri = udp://0.0.0.0:14550` (or any free port) and point SITL at it:

```
sim_vehicle.py -v ArduCopter --out=udp:127.0.0.1:14550
```

(`--out` tells SITL to *push* MAVLink to that address — matches this adapter's listen-not-connect model exactly.)
