# adapter-mjpeg

MJPEG HTTP ingest (RX) and file-loop transmit simulator (TX) — `docs/CYCLES-PLAN.md` §5, the second protocol under the RX/TX doctrine (§0).

**Depends on:** vision-domain, org.bytedeco:javacv, org.bytedeco:ffmpeg-platform-gpl (TX decode only — RX is pure JDK `java.net.http`/`com.sun.net.httpserver`, no native library) · **Used by:** *(none yet — vision-app wiring lands in the follow-up C5 transport/wiring task)*
**Build/test:** `./mvnw -B -pl adapters/adapter-mjpeg test` — 38 tests across 5 classes: `MjpegStreamParserTest` 14, `JpegDimensionsTest` 7, `MjpegVideoSourceTest` 6, `MjpegFeedTransmitterTest` 10, `MjpegRoundTripIntegrationTest` 1 (no docker — TX and RX round-trip against each other in-process). Verified via repeated live runs: 0 failures.

## API surface
### `com.drones.vision.adapter.mjpeg`
- `final class MjpegVideoSource implements VideoSourcePort` — RX. Supports protocol `"mjpeg"` with an `http`/`https` `StreamDescriptor.uri()`. `supports(StreamDescriptor)`, `open(StreamId, StreamDescriptor): Flow.Publisher<VideoFrame>`, `close(StreamId)`.
  - Option: `timeout` — connect timeout in **milliseconds**, default `DEFAULT_TIMEOUT_MILLIS`=5000 (lenient parse: missing/blank/malformed falls back to the default). Only bounds the initial TCP connect; once streaming, the connection is expected to stay open indefinitely (no request-wide timeout — see Gotchas).
  - nested `private static final class StreamRuntime` — one dedicated platform thread (`mjpeg-video-<id>`) per `open()`, running a blocking `java.net.http.HttpClient` synchronous GET + `MjpegStreamParser` read loop; feeds a `SubmissionPublisher<VideoFrame>` (`PUBLISHER_BUFFER_CAPACITY`=4, drop-newest `offer`). Every extracted JPEG part is emitted as `PixelFormat.JPEG` **passthrough** (no decode) with `width`/`height` from `JpegDimensions.parse`; a part whose dimensions can't be determined is silently skipped (never fatal). A non-2xx HTTP status, connect failure, or malformed multipart framing surfaces once via `onError` and ends the loop (the port's "unrecoverable failure" contract — this loop simply ending *is* this adapter's self-close). `close()`: CAS-guarded idempotent, closes the live response body (unblocks a pending socket read) before interrupting + bounded-joining (`CLOSE_JOIN_TIMEOUT_MILLIS`=20s) the read thread.
- `final class MjpegFeedTransmitter implements FeedTransmitterPort, java.io.Closeable` — TX. `MjpegFeedTransmitter()` (no-arg; no target base to inject, unlike `adapter-rtsp`'s `RtspFeedTransmitter` — it serves its own ephemeral HTTP port). Supports `FeedSpec.protocol()` `"mjpeg"` with a `source()` whose URI scheme is `file`. `supports(FeedSpec)`, `start(FeedId, FeedSpec): StreamDescriptor`, `stop(FeedId)`, `close()`.
  - Option: `loop` — `"true"`/`"false"`, default **`true`** (opposite of `MjpegVideoSource`, same rationale as `RtspFeedTransmitter`: a transmitted simulation feed exists to be watched indefinitely).
  - **One `com.sun.net.httpserver.HttpServer` per transmitter *instance*** (`127.0.0.1`, ephemeral port), lazily started on the first `start()` call — not one server per feed. Each feed gets its own `/feed-<id>` context on that shared server. `start()` returns `StreamDescriptor("mjpeg", http://127.0.0.1:<port>/feed-<id>, Map.of())`.
  - `stop(id)`: idempotent; closes that feed's in-flight viewer exchanges + interrupts/bounded-joins (`VIEWER_JOIN_TIMEOUT_MILLIS`=5s each) their grab-loop threads, removes the context — **does not** stop the shared server (a later `start()` may reuse it).
  - `close()`: stops every active feed, then actually shuts the shared `HttpServer` down (`stop(0)`) and its dispatch `ExecutorService` (`shutdownNow()`), releasing the port. Idempotent, safe with zero feeds ever started.
  - **Concurrent viewers, KISS**: every accepted HTTP connection to a feed's context opens its **own** fresh `FFmpegFrameGrabber` against the source file and runs its own decode→`Java2DFrameConverter`→`ImageIO` JPEG-encode→pace loop for that one response's lifetime — no shared decode state across viewers.
  - nested `private static final class FeedRegistration` — per-feed bookkeeping (`activeExchanges`, `activeThreads`, both `ConcurrentHashMap.newKeySet()`). Each viewer's handling thread is **temporarily renamed** `mjpeg-feed-<feedId>-<n>` for the duration of its request (restored to the HTTP dispatch pool's own name in a `finally` block once the connection ends) — see Gotchas.
- `final class MjpegStreamParser` (package-private, pure) — hand-rolled `multipart/x-mixed-replace` parser operating on any `InputStream`, no HTTP/network dependency, unit-testable with a plain `ByteArrayInputStream`. `MjpegStreamParser(String boundaryToken)`; `static MjpegStreamParser forContentType(String contentTypeHeaderValue)`; `static String extractBoundaryToken(String contentTypeHeaderValue)`; `static String normalizeBoundaryToken(String raw)` (strips quotes and any leading `--` a non-conformant server may already have embedded); `byte[] nextPart(InputStream in)` — returns the next part's raw JPEG bytes, or `null` at a clean end (EOF or an explicit `--boundary--` marker). Uses `Content-Length` when a part declares it (exact read via `InputStream.readNBytes`, correctly looping over short/fragmented reads); scans forward for the next boundary when absent. Does no internal buffering — callers should wrap their raw stream in a `BufferedInputStream` for efficiency.
- `final class JpegDimensions` (package-private, pure) — `static int[] parse(byte[] jpeg)`: walks the JPEG marker chain to find the `SOF0`(`0xC0`)/`SOF2`(`0xC2`) start-of-frame marker and reads its declared width/height directly (big-endian, 1-byte precision then 2-byte height then 2-byte width) **without decoding any pixel data**. Returns `null` for anything not a well-formed/complete-enough JPEG (missing SOI, truncated before SOF, entropy-coded data (`SOS`, `0xDA`) reached with no SOF seen first).

## Conventions
- Plain classes, no Spring — instantiated directly by `vision-app`'s wiring configuration (a later task; not wired anywhere yet).
- RX has **no FFmpeg/native dependency at all** — it is pure `java.net.http` + the hand-rolled parser, matching `docs/CYCLES-PLAN.md` §5's "transparent, dependency-free" requirement for the read path. TX is the only half that touches JavaCV/FFmpeg (file decode), hence the module still needs the `javacv`/`ffmpeg-platform-gpl` dependencies.
- `MjpegFeedTransmitter`'s real-time pacing (timestamp-delta sleep) and `ensureQuietLogging()` guard are **deliberately duplicated** (not shared) from `adapter-rtsp`'s `FfmpegVideoSource`/`RtspFeedTransmitter` and `adapter-publish-hls`'s `MediamtxStreamPublisher` — per `CLAUDE.md`'s rule that adapters never depend on each other.
- Lenient option parsing throughout (`timeout`, `loop`): missing/blank/malformed values silently fall back to the default, same idiom as every other adapter in this codebase.
- Idempotent close/stop via `AtomicBoolean` CAS everywhere (`MjpegVideoSource.StreamRuntime`, `MjpegFeedTransmitter.FeedRegistration`, and `MjpegFeedTransmitter` itself via its `feeds`/`server` bookkeeping).

## Gotchas
- **RX sets no request-wide HTTP timeout, only a connect timeout.** `HttpRequest.Builder.timeout(Duration)` bounds the *entire* exchange including body reads — setting it would kill a legitimately infinite MJPEG stream after that duration. Only `HttpClient.Builder.connectTimeout` is used; a server that accepts the TCP connection but then never sends headers can still hang past `timeout`'s nominal budget (mitigated only by `close()`'s explicit stream-close + thread interrupt).
- **Testing "connection refused" is racy against a just-stopped `com.sun.net.httpserver.HttpServer`** in this environment: binding an `HttpServer`, calling `stop(0)`, and immediately connecting to that same port was empirically observed to still succeed at the TCP level (the OS accept backlog appears to outlive `stop(0)`'s return by a few ms), leaving the client waiting forever for HTTP headers that never arrive. `MjpegVideoSourceTest` instead connects to `192.0.2.1` (TEST-NET-1, RFC 5737, guaranteed unroutable) to reliably exercise the connect-timeout/`onError` path — do not reintroduce the stop-and-reuse-the-port pattern for this kind of test.
- **TX's per-viewer thread rename is deliberate and load-bearing for thread-leak tests.** The shared `HttpServer`'s dispatch pool uses the **default**, unprefixed `ThreadFactory` (`Executors.newCachedThreadPool()`) specifically so its pool threads never start with `mjpeg-`; only the temporary rename inside `FeedRegistration#handle` (restored in `finally`) uses that prefix. This means a thread dump (or a test asserting no `mjpeg-`-prefixed thread remains) reflects genuinely active per-feed/per-stream work, never idle HTTP infrastructure threads that `stop(id)` intentionally leaves alive (see below).
- **`stop(FeedId)` never shuts down the shared `HttpServer`** — only `close()` does. A transmitter instance that has stopped every one of its feeds still holds its ephemeral port and dispatch thread pool open, ready for a future `start()`. Callers that want the port fully released (e.g. end of a test, or JVM shutdown wiring in the later task) must call `close()`.
- **`MjpegFeedTransmitter` decodes without an explicit `grabber.setPixelFormat(...)`** (unlike `adapter-rtsp`'s `FfmpegVideoSource`/`RtspFeedTransmitter`, which force `AV_PIX_FMT_BGR24` for their own manual buffer copy). `Java2DFrameConverter` handles the grabber's default decoded format directly into a `BufferedImage` — this is the standard JavaCV idiom for that converter and was verified working against this module's own generated test videos; forcing a pixel format here would be needless.
- **JPEG dimension parsing intentionally covers only `SOF0`/`SOF2`** (baseline and progressive), per the task spec, not the full `SOF0`–`SOF15` family. `ImageIO`'s built-in JPEG writer (used by both `adapter-simulation` and this module's TX side) always emits baseline (`SOF0`), so this covers every JPEG this platform itself produces; a real ESP32-CAM's JPEGs are also baseline in practice.
- `MjpegStreamParser` is stateful per connection (tracks whether the stream position is already parked right after a just-scanned boundary token) — a single instance must only ever be driven by one `InputStream` for one connection's lifetime, exactly like `adapter-rtsp`'s per-open `StreamRuntime`/`FeedRuntime` are never shared across opens.
