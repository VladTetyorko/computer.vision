# mavlink-core

A reusable, framework-free MAVLink library. Zero project dependencies — it does not know what a
`Device` or `Telemetry` is, and must never learn (docs/plans/active/MAVLINK-CORE-PLAN.md D2). One
third-party dependency: `io.dronefleet.mavlink:mavlink`. Frozen seam contract: `API.md`.
docs/plans/active/MAVLINK-CORE-PLAN.md **W1 done** (L0 kernel, L1 transport, L2 codec, config, ArchUnit),
**W2 done** (L3 session: peers, dispatch, correlation, link health, TX scheduling), **W3 done**
(L4 services: heartbeat, command, manual control, message interval; L4½ the broker-seam `api` package),
**W4 done** — `adapter-mavlink` was rebuilt on this library (its own MODULE.md carries that wave's notes;
`MavlinkSocketHub`/`CommandAckRegistry`/`MavlinkUdpInputStream`/`MavlinkUdpOutputStream` deleted there).
docs/plans/active/FLEET-RADIO-PLAN.md **R3 done** — every channel 1..16 an operator binds now reaches
the wire (F3), the extension-channel release sentinel is correctly encoded (F4), and the accepted
range is narrowed to `[1,16]` (F17); see the FLEET-RADIO R3 Gotchas below.
**R1 done** — the one `MAV_TYPE` → family table (`VehicleClass`) all three `adapter-mavlink` naming
call sites now delegate to; see the FLEET-RADIO R1 Gotchas below.
**R4 done** — F7 ("the silent death": a genuine `poll()` `IOException` was logged WARNING and the
reader thread just returned, telling nobody) and D4 ("lost identity": `LinkHealth.Health` carried no
`PeerId`, so per-vehicle health could only ever be averaged, not named) are fixed at this layer; see
the FLEET-RADIO R4 Gotchas below.

**Depends on:** nothing internal · `io.dronefleet.mavlink:mavlink` · **Used by:** `adapter-mavlink` (`drone-link/mavlink`, since W4 — implements `LinkRegistry`), `adapter-carrier-udp`/`adapter-carrier-serial` (`drone-link/carrier-udp`/`carrier-serial`, since LINK-PAIRING L1 — each depends on `LinkRegistry`/`LinkDescriptor`/`CarrierKind`/`SerialRole`/`SerialLink` only, never on `adapter-mavlink`)
**Build/test:** `./mvnw -B -pl drone-link/mavlink-core test` — **172 tests** (2 cleanly skipped — `SerialLinkSocatIntegrationTest`, gated on the external `socat` binary), all green (re-measured 2026-09-18 after LINK-PAIRING L1; see Status for the breakdown).

## API surface

### `com.drones.mavlink` (L0 — universal, depended on by anything)
- `record SysId(int value)` — 1..255, validated
- `record CompId(int value)` — 1..255, validated
- `record PeerId(SysId system, CompId component)` — identity is always `(sysid, compid)`, never a transport address
- `enum VehicleClass { COPTER, PLANE, ROVER, SUBMARINE, UNSUPPORTED_VEHICLE, NOT_A_VEHICLE, UNKNOWN }` (**FLEET-RADIO R1**) — the one `HEARTBEAT.type` (`MAV_TYPE`) → family table for the whole project; `static VehicleClass of(int mavType)` (never `null`, `UNKNOWN` for an unmapped number) · `static String label(int mavType)` (a shared display string, `null` only for `UNKNOWN`). Distinguishes four outcomes, not two: a supported family (copter/plane/rover — submarine has a slot but deliberately maps to no `VehicleKind`, operator instruction), a recognized-but-uncontrollable airframe (`UNSUPPORTED_VEHICLE` — airship, balloon, rocket, ...), a non-vehicle instrument heartbeating on the same link (`NOT_A_VEHICLE` — gimbal, GCS, ADS-B, ...), and a genuinely unrecognized number (`UNKNOWN`). Zero project dependencies, same as everything else in this package — the context-level `VehicleKind` translation happens at the adapter boundary (`drone-link/mavlink`'s `FlightModes.vehicleKind`), never here (D2).

### `com.drones.mavlink.transport` (L1)
- `record LinkId(String value)` · `record LinkPeer(String host, int port)` (+ `LinkPeer.NONE` sentinel) · `record ByteChunk(byte[] data, int length, LinkPeer source, Instant receivedAt)`
- `interface MavlinkLink extends AutoCloseable` — `LinkId id()` · `boolean preservesMessageBoundaries()` · `ByteChunk poll(Duration timeout) throws IOException` (null on timeout **or** close, never throws for either) · `void send(byte[], int, int, LinkPeer) throws IOException` · `LinkPeer defaultTarget()` · `void close()` (idempotent, no throws)
- `final class UdpListenLink implements MavlinkLink` — **listens**: `UdpListenLink(String bindHost, int bindPort)`, binds immediately. `defaultTarget()` = most recently learned sender, `LinkPeer.NONE` before anything heard. **(SOURCE-ONBOARDING-2 A1, new)** `public LinkIntake intake()` — pre-parse datagram/byte counters + last-arrival timestamp off this link's socket; safe from any thread. See `LinkIntake` below.
- `record LinkIntake(long datagramsReceived, long bytesReceived, Instant lastDatagramAt)` **(SOURCE-ONBOARDING-2 A1, new)** — `lastDatagramAt` is `null` until the first datagram; both counters are monotonic, never reset. Counted in package-private `UdpSocketIo` (shared by `UdpListenLink`/`UdpTargetLink`) on every successful `socket.receive`, **before** anything above L1 (resync, framing, decode) ever sees the bytes — this is the honest "did anything reach the socket at all" signal a dead port cannot otherwise produce (see Gotchas). Only `UdpListenLink` exposes it publicly; `UdpTargetLink`/`TcpClientLink` gained no new method.
- `final class UdpTargetLink implements MavlinkLink` — **dials**: `UdpTargetLink(String destinationHost, int destinationPort)`, ephemeral local socket, `defaultTarget()` = the fixed configured destination. Still fully bidirectional (can `poll()` replies).
- `final class TcpClientLink implements MavlinkLink` — **dials**: `TcpClientLink(String host, int port, Duration connectTimeout)`. `preservesMessageBoundaries()` = `false`. `send`'s `target` param is accepted but unused (one connected peer only).
- package-private helpers (not part of the seam): `UdpSocketIo` (shared UDP poll/send plumbing for the two UDP links), `LinkPeers` (send-target validation), `Timeouts` (`Duration`→millis, clamped ≥1 so `Duration.ZERO`/negative never becomes `setSoTimeout(0)`'s "block forever")
- **(LINK-PAIRING-PLAN.md §3.1/§3.2, new)** `enum CarrierKind { UDP, SERIAL }` — additive, a new carrier is a new constant + a new adapter module, never a `LinkRegistry`/`LinkDescriptor` rework. `enum SerialRole { NONE, GROUND_RADIO, BENCH }` — `NONE` is the sentinel every `CarrierKind.UDP` descriptor carries (never `null`); `BENCH` always registers at priority 0 and is never auto-elected regardless of that number; role is decided by the registering carrier's own allow/deny/bench config, never guessed from a USB vendor/product id. `record LinkDescriptor(CarrierKind carrier, SerialRole serialRole, String label, int priority)` — compact-constructor validated (`label` non-blank, `priority >= 0`). `interface LinkRegistry { LinkId register(MavlinkLink, LinkDescriptor); void unregister(LinkId); }` — `register` never mints a new id (always `link.id()`) and never opens/binds anything; `unregister` is idempotent and never closes the link (registry does not own it). `final class SerialLink implements MavlinkLink` — **dials** an already-open serial device (no listen/bind semantics apply to serial): `static SerialLink open(String portDescriptor, int baudRate) throws IOException` is the production path (jSerialComm-backed via package-private `JSerialCommChannel`); package-private `SerialLink(SerialChannel)` is the test seam (`SerialLinkTest` uses a fake `SerialChannel`, `SerialLinkSocatIntegrationTest` feeds a real `socat` pty pair through the same constructor). `preservesMessageBoundaries()` is honestly `false` (stream semantics, like `TcpClientLink`); `defaultTarget()` is always `LinkPeer.NONE` (a serial wire has no addressable peer); `send`'s `target` param is accepted but unused.

- `final class FrameWriter` — `FrameWriter(SysId ourSystem, CompId ourComponent)` · `void addLink(MavlinkLink)` · `void removeLink(LinkId)` · `void send(Object payload, PeerId target)` (still requires exactly one registered link — throws `IllegalStateException` otherwise) · `void broadcast(Object payload, LinkId link)`. The only class in the module allowed to construct a `MavlinkConnection`. **No longer `implements FrameSink`** (W2) — see Gotchas.

### `com.drones.mavlink.session` (L3 — depends on L0, L1, L2; may depend on `io.dronefleet.mavlink` for message-type extraction, e.g. `Heartbeat`, `CommandAck`)
- `record HeartbeatInfo(int autopilot, int mavType, int baseMode, long customMode, int systemStatus)` — raw wire values, no firmware-name translation (that's adapter policy)
- `record Peer(PeerId id, LinkId link, LinkPeer address, Instant firstHeard, Instant lastHeard, HeartbeatInfo heartbeat)` — `heartbeat` nullable until the first `HEARTBEAT`
- `interface PeerDirectory` — `Collection<Peer> peers()` · `Peer peer(PeerId)` (null if unheard) · `List<Peer> peersOnLink(LinkId)`. `final class DefaultPeerDirectory` (package-private) is the impl; its extra `void recordFrame(MavFrame)` is package-private, called only by `MavlinkSession`.
- `interface MessageFilter` — `boolean test(MavFrame)`; statics `any()`, `messageId(int)`, `type(Class<?>)`, `fromSystem(SysId)`, `and(MessageFilter...)`
- `interface Dispatcher` — `Subscription subscribe(MessageFilter, Consumer<MavFrame>)`. `final class DefaultDispatcher` (package-private) is the impl, backed by `CopyOnWriteArrayList`; its extra `void dispatch(MavFrame)` is package-private, called only by `MavlinkSession`. Subscriber identity is by reference, not by `(filter, handler)` equality, so two subscriptions registered with an equals-identical pair close independently.
- `interface Subscription` — `void close()` (idempotent)
- `final class BoundedSubscriber implements Consumer<MavFrame>` — `BoundedSubscriber(String name, int capacity, Duration closeJoinTimeout, Consumer<MavFrame> downstream)` · `long droppedCount()` · `void close()`. Wraps a slow downstream consumer for a `Dispatcher` subscription: `accept` only ever enqueues (never blocks), a dedicated named drain thread (`mavlink-bounded-subscriber-<name>`) calls `downstream`, drop-oldest when at `capacity`.
- `record MatchKey(SysId system, int messageId, long discriminator)`
- `interface Correlator` — `CompletableFuture<MavFrame> await(MatchKey, Duration)` (throws `IllegalStateException` on a live-key repeat) · `void cancel(MatchKey)` (idempotent). `final class DefaultCorrelator` is the impl; its extra `void offer(MavFrame)` (package-private) is called only by `MavlinkSession`. **`DefaultCorrelator` is closed for modification** as of ONBOARDING O2 (MISSIONS **D6**): it owns registry mechanics only and delegates every key extraction to `CorrelationKeys`.
- `final class CorrelationKeys` — the one place a correlated reply's key is defined, **for both directions**. Request side (public): `MatchKey forCommandAck(SysId, int commandId)` · `MatchKey forParamValue(SysId, String paramId)` · `MatchKey forAutopilotVersion(SysId)` · `String normalizeParamId(String)` · `long paramDiscriminator(String)` · constants `COMMAND_ACK_MESSAGE_ID` (77), `PARAM_VALUE_MESSAGE_ID` (22), `AUTOPILOT_VERSION_MESSAGE_ID` (148), `MISSION_REQUEST_MESSAGE_ID` (40), `MISSION_COUNT_MESSAGE_ID` (44), `MISSION_ACK_MESSAGE_ID` (47), `MISSION_REQUEST_INT_MESSAGE_ID` (51), `NO_DISCRIMINATOR` (0). Reply side (package-private): `static MatchKey keyFor(MavFrame)`, backed by a compiled-in `Map<Class<?>, Function<MavFrame, MatchKey>>` — exact-class lookup (every payload type is `final`), `null` for anything uncorrelated. **Adding a correlated message type is a row in this table plus a factory here — never an edit to `DefaultCorrelator`.** The four MISSION rows are landed here in full per **D14** so MISSIONS' `MissionService` consumes the table unchanged; they are covered by `CorrelationKeysTest`.
- `interface TxScheduler` — `Handle repeat(String name, Duration period, Runnable)` · **`void submit(String name, Runnable)`** (RC-LATENCY W L1, **new** — a one-shot on the same pool, same catch-and-log contract, and a submission racing shutdown is *dropped, not thrown*; no `Handle`, since an already-queued one-shot cannot usefully be cancelled); nested `interface Handle { void close(); }` (idempotent). `final class DefaultTxScheduler implements TxScheduler` — `DefaultTxScheduler(MavlinkCoreSettings)` or `DefaultTxScheduler(Duration closeJoinTimeout)` · extra `void close()` (not part of the `TxScheduler` seam) shuts down the shared 2-thread `ScheduledExecutorService`. **Not owned by `MavlinkSession`** — construct one independently (see Gotchas).
- `interface LinkHealth` — `Health of(PeerId)`; nested `record Health(PeerId peerId, boolean connected, Instant lastHeard, long received, long lost, double dropRate)` (**FLEET-RADIO R4/D4** — gained `peerId` as its first field so a consumer aggregating several peers' `Health` records can still name which one is which; see the FLEET-RADIO R4 Gotchas below). `final class DefaultLinkHealth implements LinkHealth` — `DefaultLinkHealth(Duration peerTimeout)`; extra `void recordFrame(MavFrame)` (package-private) called only by `MavlinkSession`.
- `final class RoutingFrameSink implements FrameSink` — `RoutingFrameSink(PeerDirectory, FrameWriter)`. Resolves a `PeerId`'s link via `PeerDirectory.peer(target)`, delegates to `FrameWriter.broadcast(payload, peer.link())`; throws `IllegalArgumentException` naming the "you cannot send to a peer you have not heard from" rule for an unknown/unheard peer.
- `record MavlinkNode(SysId system, CompId component)` — `static groundStation()` → 255/190
- `final class MavlinkSession implements AutoCloseable` — `MavlinkSession(MavlinkNode, MavlinkCoreSettings)` · `void addLink(MavlinkLink)` (throws if already registered or session closed) · `void removeLink(LinkId)` (idempotent) · `PeerDirectory peers()` · `Dispatcher dispatcher()` · `Correlator correlator()` · `FrameSink sink()` · `LinkHealth health()` · **`void onLinkFailure(BiConsumer<LinkId, IOException> listener)`** (**FLEET-RADIO R4/F7**, new) · `void close()` (idempotent). The composition root: one reader thread per link (`mavlink-rx-<linkId>`), fixed per-frame order `PeerDirectory` + `LinkHealth` → `Correlator` → `Dispatcher`. See the FLEET-RADIO R4 Gotchas below for `onLinkFailure`'s full contract (fires synchronously from the dying reader thread, must not block/throw; a shutdown-triggered `IOException` never fires it; `RuntimeException` from a frame handler never fires it either).
- **(LINK-PAIRING-PLAN.md §3.1, new)** `interface LinkQuality { Quality of(LinkId); }` — a deliberate **separate** port from `LinkHealth`, keyed by `LinkId` not `PeerId`: answers "how good is this *link* right now" (per-link RADIO_STATUS telemetry) rather than `LinkHealth`'s "is this *peer* connected," which already collapses to whichever link a peer was most recently heard on. Nested `record Quality(LinkId linkId, Instant lastRadioStatusAt, Integer rssi, Integer remoteRssi, Integer noise, Integer rxErrors, Boolean fixed)` — every numeric field nullable-boxed so "never heard" (`of` returns `null`) stays distinguishable from "heard a genuine zero." `final class DefaultLinkQuality implements LinkQuality` — `DefaultLinkQuality(Dispatcher)`, subscribes once in the constructor (no `MavlinkSession` change needed — `dispatcher()`/`Dispatcher#subscribe` were already public) to inbound `RADIO_STATUS` (#109) frames whose source component id is 68/110/111/112 (the well-known telemetry-radio component ids, distinct from the autopilot's own).

### `com.drones.mavlink.config` (universal, like L0)
- `record MavlinkCoreSettings(Duration heartbeatPeriod, Duration peerTimeout, Duration commandTimeout, int commandRetries, Duration commandDedupeWindow, Rc rc, Duration closeJoinTimeout, int maxResyncBuffers, int dispatchQueueCapacity, Mission mission, Ftp ftp, Parameter parameter)` — `static defaults()`, one `with*` per top-level field, compact-constructor validated. Nested `Rc(int overrideHz, int minOverrideHz, int maxOverrideHz, int releaseFrames)` (+ `clampedOverrideHz()`), `Mission(Duration timeout, Duration itemTimeout, int retries)`, `Ftp(Duration timeout, int retries)`, `Parameter(Duration timeout, int retries)` (1 s / 3 — the MAVLink parameter-protocol page states its own retry policy). Only `maxResyncBuffers` (64) is consumed in W1; the rest exist now so W2/W3 don't need a contract change to reach them. Every default is byte-identical to `API.md`'s table.

### `com.drones.mavlink.service` (L4 — depends on L0, L3; one class per MAVLink microservice, ISP-scoped role interfaces only, never `MavlinkSession`)
- `final class RequestResponse` — the shared Family-A machine (plan §2.2), constructed from a bare `Correlator` + `FrameSink` — genuinely standalone, not folded into `CommandService`. `RequestResponse(Correlator, FrameSink)` · `CompletableFuture<MavFrame> exchange(PeerId target, MatchKey key, Duration timeout, int maxRetries, AttemptPayload payload, ReplyClassifier classifier)`. `AttemptPayload.forAttempt(int attempt)` builds the payload for a 0-based attempt; `ReplyClassifier.extensionFor(MavFrame reply)` returns `null` for a terminal reply (the exchange completes with it) or a `Duration` to keep waiting on the same key without resending. Continuation-based throughout (`thenCompose`/`exceptionallyCompose`, never a blocked thread) — see its own javadoc for why, and for the one subtle bug this wave found and fixed (next Gotchas entry).
- `final class CommandService` — `COMMAND_LONG` and `COMMAND_INT`, `COMMAND_ACK` awaited via `RequestResponse`, matched on `(origin sysid, command id)` only (inherited from `Correlator`/`DefaultCorrelator` unchanged). `CommandService(FrameSink, Correlator, Duration timeout, int retries)` and a `MavlinkCoreSettings`-based overload. `CompletableFuture<CommandOutcome> sendLong(PeerId target, MavCmd command, float param1..param7)` · `CompletableFuture<CommandOutcome> sendInt(PeerId target, io.dronefleet.mavlink.common.MavFrame frame, MavCmd command, float param1..param4, int x, int y, float z)` — the parameter is the *coordinate-frame* enum, spelled fully-qualified in both the API and this doc because it shares a simple name with this module's own `MavFrame` envelope (see Gotchas). `confirmation` = the 0-based attempt number on every `COMMAND_LONG` retry (not sent at all on `COMMAND_INT`, which has no such field). `record CommandOutcome(Status status, MavResult mavResult, int resultCode, CommandAck ack)`, nested `enum Status { ACCEPTED, TEMPORARILY_REJECTED, DENIED, UNSUPPORTED, FAILED, CANCELLED, IN_PROGRESS, NO_ACK }` — a protocol-level, 8-value status distinct from `com.drones.mavlink.api.CommandOutcome.Status`'s frozen 7-value one (see Gotchas for the mapping). `IN_PROGRESS` replies extend the deadline (bounded at 20 extensions, `MAX_IN_PROGRESS_EXTENSIONS`, not spec/config — see Gotchas) rather than terminating; exhausting that bound still completes the exchange, with `Status.IN_PROGRESS`, not a bare timeout.
- `final class HeartbeatService` — `HeartbeatService(FrameSink, TxScheduler, PeerDirectory, MavlinkCoreSettings)`, a `+ HeartbeatContent` overload for a non-default identity, package-private `(FrameSink, TxScheduler, PeerDirectory, Duration heartbeatPeriod, Duration peerTimeout, HeartbeatContent)` test seam. `void start()` / `void stop()` (both idempotent) · `boolean isConnected(PeerId)` (reflects the most recent tick, `false` for an unknown peer). Every tick both emits `content.toMessage()` (a `Heartbeat`) via `FrameSink#broadcast` on every distinct `LinkId` currently known through `PeerDirectory#peers()`, and recomputes its own connected/disconnected view from `Peer#lastHeard()` vs. `peerTimeout` (see Gotchas — this is deliberately not `LinkHealth`).
- `record HeartbeatContent(MavType type, MavAutopilot autopilot, int baseMode, long customMode, MavState systemStatus)` — raw wire values for our own outgoing `HEARTBEAT`, `static groundStation()` default (`MAV_TYPE_GCS` / `MAV_AUTOPILOT_INVALID` / `MAV_STATE_ACTIVE`, matching `MavlinkNode.groundStation()`'s own convention).
- `final class ManualControlService` — `RC_CHANNELS_OVERRIDE` (#70) relay, ported from `adapter-mavlink`'s `MavlinkManualControlSender` onto this module's `TxScheduler` instead of a hand-rolled thread. **No longer a single fixed rate** (docs/plans/done/RC-LATENCY-PLAN.md §2 A): it runs on a *ceiling* (`1/maxOverrideHz`, the scheduler period — never transmit faster) and a *floor* (`1/clampedOverrideHz` — an unchanged mailbox still transmits this often, so an aircraft never sees a gap that expires its override timeout). A `send` arriving at least a ceiling-period after the last transmit is pushed to the wire immediately via `TxScheduler#submit`, so the periodic task is the keepalive rather than the send loop; both paths share one under-lock decision, so the combined wire rate is bounded by the ceiling, not their sum. `ManualControlService(FrameSink, TxScheduler, PeerDirectory, MavlinkCoreSettings.Rc)` and package-private `(FrameSink, TxScheduler, PeerDirectory, Duration tickPeriod, int releaseFrames)` / `(…, Duration tickPeriod, int releaseFrames, LongSupplier nanoClock)` test seams (one period serving as both ceiling and floor; the clock seam lets a manually driven scheduler step past either without real sleeps) — **no `Correlator` parameter at all**, by design (ISP: this class must not be able to express an ack wait). `ManualControlLink engage(PeerId target)` (throws `IllegalArgumentException` — "cannot command what you cannot hear" — and starts no task if `target` is unknown to `PeerDirectory`) · `void send(ManualControlLink, RcChannels)` (latest-wins mailbox write, silent no-op once releasing) · `void release(ManualControlLink)` (writes the release sentinel, blocks the caller `releaseFrames * coalescePeriod` for the burst to actually go out, then closes the scheduled task; idempotent). `interface ManualControlLink { boolean active(); }` — an opaque handle (core's own; distinct from `vision-flight`'s port type of the same name, which additionally carries `rateHz()`), `send`/`release` throw `IllegalArgumentException` for a link this service did not itself create. Every tick re-resolves `PeerDirectory#peer(target)` fresh (never cached at `engage`-time); a currently-unknown target pauses the tick (no send, logged once on the transition) rather than failing. **FLEET-RADIO R3**: `buildFrame` populates every channel 1..16 the caller's `RcChannels` carries (previously hardcoded chan9..18 to `IGNORE` unconditionally — F3); channels 17/18 stay hardcoded `IGNORE` since `RcChannels` itself now refuses to carry a value past 16 (F17).
- `record RcChannels(List<Integer> microsByChannel)` — this module's own RC-override value type (`RELEASE=0`, `IGNORE=0xFFFF`, `EXTENSION_RELEASE=0xFFFE`, `MIN_MICROS=1000`, `MAX_MICROS=2000`, `MAX_CHANNELS=16`, `BASE_CHANNEL_COUNT=8`, `wireValue(int)`, `static allIgnore(int)`/`released(int)`) — a deliberate, small duplication of `vision-flight`'s identically-shaped `RcChannels` (see Gotchas: D2 forbids importing it). **FLEET-RADIO R3**: accepts 1..16 channels, not 1..18 (F17 — ArduPilot reads no higher); `wireValue(int)` (renamed from `channelOrIgnore`) is the one place a domain `RELEASE` is re-encoded as `EXTENSION_RELEASE` for channel 9 and above (F4 — see Gotchas).
- `final class MessageIntervalService` — `MAV_CMD_SET_MESSAGE_INTERVAL` / `MAV_CMD_REQUEST_MESSAGE`, both plain `COMMAND_LONG`s over `CommandService` ("do not reimplement the ack cycle"). `MessageIntervalService(CommandService)`. `setMessageInterval(PeerId, int messageId, Duration interval)` (converts to **microseconds** — the one easy-to-get-wrong number; throws for a negative `Duration`) · `disableMessage(PeerId, int messageId)` (`param2 = DISABLE_STREAM = -1`, the spec's own sentinel) · `requestMessage(PeerId, int messageId)`.
- `final class ParameterService` — the parameter microservice, over `RequestResponse`. `ParameterService(FrameSink, Correlator, Duration timeout, int retries)` and a `MavlinkCoreSettings`-based overload (uses `settings.parameter()`). `CompletableFuture<ParameterOutcome> read(PeerId, String name)` · `CompletableFuture<Map<String, ParameterOutcome>> readAll(PeerId, List<String> names)` (all in flight at once — distinct `MatchKey`s never collide; duplicates in `names` are collapsed, since two live waiters on one key is an `IllegalStateException` by `Correlator`'s contract) · `CompletableFuture<ParameterOutcome> write(PeerId, String name, float value, MavParamType type)`. Reads always address the parameter **by name**, with `param_index = READ_BY_NAME = -1` — an index is a property of one firmware build's table and shifts across versions. A write is **always** a read-back (see Gotchas); there is no fire-and-forget variant. A blank name, or one longer than the wire's 16-char `param_id`, throws `IllegalArgumentException` before anything is sent or any waiter is registered.
- `record ParameterValue(String name, float value, MavParamType type, int index, int count)` — `boolean isNamed(String)`. `name` is normalised; `index` is informational and must never be used to correlate.
- `record ParameterOutcome(Status status, ParameterValue value, String detail)`, nested `enum Status { OK, MISMATCH, NO_REPLY }`, `boolean ok()`. `value` is non-null except for `NO_REPLY`; compact-constructor enforced.
- `final class CapabilityService` — `MAV_CMD_REQUEST_MESSAGE(AUTOPILOT_VERSION)`, awaiting the **message itself**, not its `COMMAND_ACK` (which is why this is not a `MessageIntervalService.requestMessage` call — that awaits the ack, which only says the request was accepted). `CapabilityService(FrameSink, Correlator, Duration timeout, int retries)` and a `MavlinkCoreSettings`-based overload that reuses `commandTimeout`/`commandRetries`, since what goes on the wire is a `COMMAND_LONG`. `CompletableFuture<CapabilityReport> requestAutopilotVersion(PeerId)`. The `COMMAND_ACK` the vehicle also sends finds no waiter and is dropped, as an uncorrelated frame should be.
- `record CapabilityReport(Status status, String firmwareVersion, Maturity maturity, Set<MavProtocolCapability> capabilities, long boardVersion, int vendorId, int productId, AutopilotVersion raw)`, nested `enum Status { OK, NO_REPLY }` and `enum Maturity { DEV, ALPHA, BETA, RC, OFFICIAL, UNKNOWN }`, `boolean ok()` · `boolean supports(MavProtocolCapability)`. Decodes the packed `flight_sw_version` uint32 into `"major.minor.patch"` + maturity, and expands the `capabilities` bitmask into the flags it sets — both are protocol knowledge that belongs here rather than in every caller; what those flags *mean* for a feature is domain policy and deliberately stays out.

- `record CommandOutcome(String correlationId, Status status, int resultCode, String detail, Instant at)`, nested `enum Status { ACCEPTED, IN_PROGRESS, DENIED, NO_ACK, UNSUPPORTED, DUPLICATE, UNREACHABLE }` — frozen per API.md, L0-only imports.
- `interface VehicleKeyResolver { PeerId resolve(String vehicleKey); }` — `null` for unknown; L0-only.
- `interface CommandGateway { CompletionStage<CommandOutcome> submit(CommandRequest); }` — L0-only.
- `final class DefaultCommandGateway implements CommandGateway` — the **one** class in this package that imports L3/L4 (`CommandService`; see Gotchas for the API.md table-vs-deliverables tension this resolves). `DefaultCommandGateway(CommandService, VehicleKeyResolver, Duration dedupeWindow)` and a `MavlinkCoreSettings`-based overload. `submit`: parses `kind` and builds the `COMMAND_LONG` params synchronously first (**throws** `IllegalArgumentException` here, before any dedupe bookkeeping, for an unknown `kind` or a `kind` missing a required positional `param`) — this is the *only* way `submit` throws. Dedupe reservation is one atomic `ConcurrentHashMap#compute` keyed by `correlationId`: a live (not-yet-done, not-expired) entry is returned as-is (same `CompletionStage`, no second dispatch); a completed-but-fresh entry yields `Status.DUPLICATE`; anything else (new or expired) reserves a fresh, not-yet-complete stage and this caller becomes the one dispatcher. `resolver.resolve(vehicleKey) == null`, or a resolved-but-never-heard peer (surfaces as an exception from `CommandService`/`FrameSink#send`, caught via `.exceptionally`), both complete `Status.UNREACHABLE` — never thrown. Expired dedupe entries are pruned lazily/opportunistically on every `submit()` call (no background thread). The kind→command mapping (`ARM`, `DISARM`, `SET_MODE`, `RTL`, `SET_MESSAGE_INTERVAL`, `REQUEST_MESSAGE`) lives in one private `CommandSpec.forRequest`/`Kind` pair — see Gotchas for `SET_MODE`'s and `RTL`'s own design notes.

## Conventions
- Plain classes, `System.Logger` (WARNING on recoverable decode/discard events), no framework annotations.
- Idempotent `close()` via `AtomicBoolean` CAS + close-the-socket-to-unblock-a-pending-poll, ported from `adapter-mavlink`'s `MavlinkSocketHub`/`MavlinkUdpInputStream` idiom.
- `poll(Duration)` is driven by exactly one reader thread per link (no internal threads in L1/L2); `send` is thread-safe on every link so several services can share one link concurrently.
- Records validate in compact constructors, `IllegalArgumentException` naming the bad value.

## Gotchas
- **(SOURCE-ONBOARDING-2 A1) `LinkIntake` counts are deliberately pre-parse and deliberately dumb.**
  A UDP port nothing is transmitting to blocks forever in `DatagramSocket#receive` with no error, no
  timeout distinct from "nothing yet," and no log — this is the actual mechanism behind
  `SOURCE-ONBOARDING-2` §2.4 S1 ("a MAVLink device pointed at a dead port never errors"), and this
  module cannot fix it at the socket, only report around it honestly. `LinkIntake` is that report:
  `datagramsReceived`/`bytesReceived` increment on every successful `receive`, before `FrameReader`
  attempts any resync — a garbage datagram (wrong protocol, MAVLink 1, random bytes) counts exactly
  like a valid frame does. This is intentional, not a gap: the diagnostic value is entirely in the
  *comparison* between this count and a higher layer's `framesDecoded` — zero datagrams means nothing
  is reaching the socket; datagrams arriving with nothing decoding means the wrong thing is. Neither
  number alone can tell those apart, and this module has no framesDecoded of its own to compare
  against (that lives one layer up, at the codec/session boundary — `adapter-mavlink`'s own
  `intakeStatus`, SOURCE-ONBOARDING-2 A2).
- **`FrameReader` never re-implements CRC/resync/dialect layout** — every parse attempt hands the current pending buffer to a fresh `io.dronefleet.mavlink.MavlinkConnection` over a `ByteArrayInputStream`. This is deliberate, not an oversight: `MavlinkConnection#next()` is built around a *genuinely blocking* `InputStream` (real end-of-stream only), and reusing one persistent connection while feeding it bytes incrementally corrupts its internal `TransactionalInputStream` bookkeeping the moment a read attempt fails mid-frame — a retried `next()` would misread the tail of an unfinished frame as a fresh version-marker search. A `CountingInputStream` wrapper tracks exactly how many bytes (resync-skipped garbage included) a successful attempt consumed, so the pending buffer trims correctly; a failed attempt (`EOFException`, not a real error) trims nothing and retries the *whole* buffer once more bytes arrive — cheap, since frames are ≤280 bytes.
- **Dialect persistence is a per-buffer approximation, not the library's own per-sysid map.** Rebuilding the connection per attempt loses `MavlinkConnection`'s internal `systemDialects` cache, so `ResyncBuffer` asks the about-to-be-discarded connection for `getDialect(originSystemId)` after every successful decode and primes the next attempt's connection with it as the default dialect — reusing the library's own resolution rather than re-declaring an autopilot→dialect table. This is last-heartbeat-wins per resync buffer, not truly per-sysid: one physical source relaying two vehicles of *different* firmware families (rare, but the plan explicitly allows for a companion computer relaying several) could see the wrong default briefly applied to the second vehicle's ardupilotmega-only messages until its own heartbeat arrives. Full per-sysid tracking belongs to L3 (`PeerDirectory`, W2), not this layer.
- **One resync buffer per source, LRU-evicted at `maxResyncBuffers`.** Boundary-preserving links (UDP) key by `LinkPeer`; stream links (TCP) use one fixed sentinel key regardless of `ByteChunk.source()`. This is the fix for `adapter-mavlink`'s `MavlinkUdpInputStream`, which concatenates every sender into one byte stream — proven by `PerSourceResyncIsolationTest`.
- **A single resync buffer is bounded (4096 bytes) against a source that never produces a valid frame**, checked *after* each drain attempt, not before — checking before would (and in an early draft, did) discard a single large-but-entirely-valid chunk containing many back-to-back frames just because its raw length briefly exceeded the cap.
- **`FrameWriter` keeps one persistent `MavlinkConnection` per registered link, reused for every send.** This is what makes "sequence allocation per `(link, sysid, compid)`, wrapping at 255" work for free: `MavlinkConnection`'s own sequence counter already increments and wire-wraps correctly (8-bit truncation on serialize) as long as the *same* connection instance is reused — constructing a fresh one per send (the pattern `FrameWriter` replaces) would reset the sequence to 0 on every call.
- **(W1, resolved in W2) `FrameSink.send(Object, PeerId)` had a real routing gap.** The signature takes a `PeerId` (sysid/compid) but no link, and resolving which link a peer is reachable on needs an L3 `PeerDirectory`, which W1 didn't have. W1 shipped the honest subset (worked for exactly one registered link, threw `IllegalStateException` for more rather than guess). **W2's `RoutingFrameSink` closes this** by resolving the link through `PeerDirectory` — see the W2 bullets below for what's still open (the address-level part of routing).
- **`Object payload` on `MavFrame`/`FrameSink` is a known, investigated wart (kept).** `io.dronefleet.mavlink`'s generated message classes (`Heartbeat`, `CommandLong`, ...) are plain `public final class`, no common interface or superclass — confirmed by reading the sources jar. The only shared marker is the class-level `@MavlinkMessageInfo` runtime annotation (carries `id`/`crc`), which cannot replace `Object` in a type position since annotations aren't types. `FrameWriter` does use it defensively: a payload missing the annotation is rejected with a clear `IllegalArgumentException` before it would otherwise hit a confusing NPE inside `MavlinkConnection.send2`.
- **`Duration.ZERO`/negative never means "block forever."** `DatagramSocket#setSoTimeout(0)` and `Socket#setSoTimeout(0)` both mean "wait indefinitely" — the opposite of what a caller passing a non-positive `poll(Duration)` timeout almost certainly means. `Timeouts.clampMillis` floors at 1ms.
- **`FrameWriter` no longer implements `FrameSink` (W2).** It did in W1, as an honest-but-limited stopgap (single-link-only `send`, per its own now-updated javadoc). `com.drones.mavlink.session.RoutingFrameSink` is the real `FrameSink` implementation now — it resolves a peer's link via `PeerDirectory` and delegates to `FrameWriter.broadcast`. `FrameWriter.send`/`broadcast` are unchanged otherwise (same bodies, just no `@Override`), kept as plain public methods for a caller that only ever has one link and doesn't want to build a `PeerDirectory` (a TX simulator, a test).
- **`RoutingFrameSink` closes the *link* routing gap, not the *address* one.** `FrameWriter.broadcast` always sends via that link's own `defaultTarget()` — for `UdpListenLink` that's "the most recently learned sender," not necessarily the specific peer `RoutingFrameSink.send` was asked to reach. With one peer per link this is correct by construction; with several peers sharing one listen link (exactly the scenario `MultiPeerLoopbackTest` exercises on the *receive* side), a `send` to a peer that is not the most-recently-heard one on that link can still physically reach the wrong address, even though it resolves the right *link*. Closing this needs `FrameWriter` (or a lower primitive) to accept an explicit `LinkPeer` target instead of trusting `defaultTarget()` — out of W2's minimal-codec-touch mandate (only un-implementing `FrameSink` was in scope). Flagged for W3/W4.
  **Update from W3:** already closed by the time this wave started reading the source — `FrameWriter` gained `sendTo(Object, LinkId, LinkPeer)` (an explicit-address send, bypassing `defaultTarget()`) and `RoutingFrameSink.send` already calls it with `peer.address()`. `CommandService`/`ManualControlService` both send correctly to a specific peer's own last-known address on a shared listen link as a result — proven incidentally by every real-loopback test in this wave. This paragraph is left in place, unedited above, only because fixing it was out of this wave's own file scope (`codec`/`session` are frozen for W3); flagging here so a future reader doesn't go looking for a gap that is not there.
- **`Correlator.offer`'s extraction is a compiled-in table, not an `instanceof` chain and not a plugin registry.** *(Superseded W3's single-case note; ONBOARDING O2 / MISSIONS **D6**.)* W3's entry here predicted "revisit if/when a second case arrives" — it arrived as seven at once (parameters, capability, and MISSIONS' four transfer types), so `extractKey` moved into `CorrelationKeys` as a `Map<Class<?>, Function<MavFrame, MatchKey>>`. `DefaultCorrelator` is now closed for modification and the API.md-frozen `Correlator` seam is byte-identical. Deliberately *not* a runtime registry: nothing needs to register an extractor at runtime, and one would trade a compile-time guarantee for a startup-ordering bug.
- **`TxScheduler` is not owned or exposed by `MavlinkSession`.** API.md's `MavlinkSession` accessor list has no `txScheduler()` — TX scheduling is orthogonal to the RX-driven state `MavlinkSession` manages (peers/health/correlation/dispatch), so W3's `HeartbeatService`/`ManualControlService` construct their own `DefaultTxScheduler` (or share one) rather than pulling it from a session.
- **`DefaultTxScheduler`'s pool size (2) is an internal implementation choice, not a config value.** `MavlinkCoreSettings` (out of W2's file scope) has no scheduler-pool-size field; 2 is a small, documented, arbitrary safety margin so one slow/blocked TX task cannot delay every other periodic task sharing the scheduler, while staying "one shared pool, not one thread per feature" per plan §3.3. Revisit if W3's real services reveal contention.
- **`MavlinkSession.LinkRuntime.stop()` guards against a self-join.** A `Dispatcher` handler runs on the RX thread that decoded the frame, and may itself call `removeLink`/`close` on its own link synchronously (e.g. reacting to a link-error message). `Thread#join` from a thread on itself doesn't deadlock forever (a bounded `join(millis)` always returns once the timeout elapses) but would needlessly stall that thread for up to `closeJoinTimeout` — `stop()` checks `thread == Thread.currentThread()` and skips the join in that case, mirroring `MavlinkSocketHub#shutdown`'s own identical guard (the exact idiom this class was ported from). Proven by `MavlinkSessionSelfRemovalTest` with a 10s `closeJoinTimeout` so a regression would show up as an obvious stall, not a subtle timing flake.
- **(LINK-PAIRING-PLAN.md §3.1/§3.2) `SerialLink.poll` treats a negative read as a genuine `IOException`, unlike `TcpClientLink`'s silent-close-on-FIN.** A TCP `read() == -1` is the remote peer's own orderly shutdown — an intentional signal. A serial file descriptor has no peer to send one; end-of-stream there means the underlying device disappeared out from under an open link (a USB radio unplugged, a bridge process killed) while nobody asked this link to close — exactly the "genuine failure" `MavlinkSession#onLinkFailure` (FLEET-RADIO F7) exists to report. Get this backwards (treat it as a silent close, `TcpClientLink`-style) and an unplugged radio looks identical to an intentional `removeLink()` — no WARNING, no failure notification, nothing.
- **`LinkRegistry.register`/`unregister` never own the link's lifecycle — this mirrors `MavlinkSession.addLink`/`removeLink` exactly, one layer up.** A carrier adapter (carrier-udp, carrier-serial) that calls `unregister` on a link it is retiring (a hotplug removal, a lost bench cable) is still responsible for calling that link's own `close()` — the registry only stops routing frames through it. Getting this backwards leaks a still-open socket/port every time a link disappears.
- **`LinkHealth`'s per-`(PeerId, LinkId)` accounting is exposed through a `PeerId`-only query (`of(PeerId)`).** API.md pins `LinkHealth.of(PeerId)` with no `LinkId` parameter even though the plan's own drop-rate note says accounting is per `(PeerId, LinkId)`. `DefaultLinkHealth` resolves this by tracking one window per peer and resetting it whenever that peer is next heard on a *different* link than the one the running window belongs to (latest-link-wins, mirroring `Peer`'s own single `link` field) — correct for the common case (one peer, one link) and for W2's own acceptance test, but `of(PeerId)` cannot disambiguate two links a peer is genuinely active on *simultaneously*. Flagged as an API.md tension, not fixed here (not in scope, not exercised by any required test).

### W3 Gotchas

- **A real `CompletableFuture` ordering hazard, found and fixed inside `RequestResponse`.** `Correlator#await`'s own self-cleanup (`future.whenComplete(...)` removing the map entry) and `RequestResponse`'s own retry-on-timeout continuation (`waiter.exceptionallyCompose(...)`) are two independent dependents registered on the *same* future — and `CompletableFuture` gives no ordering guarantee between two independently-registered dependents of one future's completion. The first draft's retry path called `correlator.await(key, ...)` again immediately on a timeout and intermittently (in practice, reliably, once retries actually exercised the path) hit `IllegalStateException: A live await is already registered`, because the self-cleanup dependent had not necessarily run yet. Fixed by calling `correlator.cancel(key)` defensively, deterministically, right before every retry's re-registration (idempotent either way — a no-op if cleanup already ran, a real release if not). **This is worth remembering for W6's Mission/FTP if they ever re-register the same key without going through `RequestResponse` itself** — reuse this class rather than re-deriving the same race.
- **A second, related bug the same fix session found: extension-phase timeouts were being mis-routed into the retry path.** The first draft attached `.exceptionallyCompose(retryOrFail)` to the *combined* result of `waiter.thenCompose(continueOrComplete)` — so a timeout inside `continueOrComplete`'s own recursive extension chain (which must be terminal, never a resend, per plan §2.2) was being caught by the *same* handler as the initial await's timeout (which *should* retry), and got a spurious resend. Fixed by attaching the retry-on-timeout handling to the initial `waiter` alone, before `continueOrComplete` is chained on to it — see `RequestResponse.sendAttempt`'s own comment. Both bugs were caught by `RequestResponseTest`'s hand-fake-`Correlator` unit tests before any real-socket test ever ran; the real-socket `CommandServiceTest` would very likely have caught the first (a genuine retry needs this to work) but plausibly not the second (it needs a *reply-driven* timeout specifically, which fewer scenarios exercise) — worth noting as an argument for keeping fast, deterministic fakes alongside the real-loopback tests, not instead of them.
- **`ManualControlService`'s and `CommandService`'s "lost target" branch (`PeerDirectory#peer(target) == null`) is unreachable in production once `engage`/a send has already succeeded once.** `PeerDirectory`/`DefaultPeerDirectory` never evicts a once-known peer (see its own contract) — there is no protocol-level "this peer is gone" signal at L4 without `LinkHealth` (deliberately not an L4 role interface) or adapter-level claim/re-election policy (deliberately out of scope, plan D5). A vehicle that goes silent forever after being heard once still returns a non-null, increasingly stale `Peer`. `ManualControlServiceTest.lostTargetPausesWithoutKillingTheTask` therefore proves the pause logic itself is correct using a hand-fake `PeerDirectory` that — unlike the real one — can be told to "forget" a peer; it does **not** prove the real production wiring can ever reach that branch today. Flagged for W4: if "pause when a vehicle goes quiet" is a real product requirement, `adapter-mavlink` needs a claim-aware `PeerDirectory` wrapper (or an equivalent), since core's own `PeerDirectory` cannot and should not grow eviction (it would have to invent a policy — how stale is "gone" — that plan §2.3/D6 explicitly leaves to configuration/policy, not a protocol fact).
- **`HeartbeatService` can only broadcast our `HEARTBEAT` on links `PeerDirectory` already knows about a peer on** (`peers().stream().map(Peer::link)`), because there is no "every registered link" role interface at L4 (only `FrameSink`/`Correlator`/`PeerDirectory`/`TxScheduler` — plan §3.3). A dial-out `UdpTargetLink` whose destination has never sent us anything is unreachable by this service until it does. For a `UdpListenLink` this is not a regression — `MavlinkLink#send` cannot address an unlearned target at all, so nothing was reachable there either — but for a pure dial-out gateway that wants to announce itself *before* ever hearing from the other end, this is a real, documented gap. Closing it would need a link-registry role interface this wave deliberately did not invent (not asked for, no test needs it).
- **`CommandService.CommandOutcome.Status` (8 values, protocol-level) and `com.drones.mavlink.api.CommandOutcome.Status` (7 values, frozen by API.md) are deliberately different enums**, not a naming accident. `DefaultCommandGateway.toApiOutcome` folds `TEMPORARILY_REJECTED`/`FAILED`/`CANCELLED` all into the api-level `DENIED` bucket — the frozen enum has no room for the finer distinction — while `CommandOutcome.detail` still carries the raw `MavResult` name, so nothing is silently lost, only coarsened at the broker-facing boundary.
- **`RcChannels` is duplicated, on purpose.** `com.drones.mavlink.service.RcChannels` and `vision-flight`'s own `com.drones.vision.flight.domain.model.RcChannels` are structurally identical (same sentinels, same validation) but this module cannot import the latter (D2: zero project dependencies) and must not invent a shared jar just for one record. W4's `adapter-mavlink` is expected to translate between the two at the L4/L5 boundary when it wires `MavlinkManualControlSender` onto `ManualControlService`.
- **`com.drones.mavlink.codec.MavFrame` (this module's own envelope: header + payload + link) and `io.dronefleet.mavlink.common.MavFrame` (the wire coordinate-frame enum, e.g. `MAV_FRAME_GLOBAL_INT`) share a simple name.** `CommandService.sendInt`'s `frame` parameter and `MessageIntervalService`/`DefaultCommandGateway`'s own call sites that touch it spell the library type out fully-qualified (`io.dronefleet.mavlink.common.MavFrame`) rather than importing it, specifically so the unqualified `MavFrame` symbol everywhere else in this module unambiguously means the codec envelope. A real, unavoidable collision given both names come from outside this module's control (one from us, one from the wire spec) — not a design flaw to fix.
- **`SET_MODE`/`RTL` in `DefaultCommandGateway`'s kind table carry zero firmware-mode-name knowledge, by design.** `SET_MODE` expects the caller to supply an *already-resolved* numeric `custom_mode` as `params[0]` — this module has no ArduPilot/Betaflight mode-name table (that stays `adapter-mavlink`'s `FlightModes`, project policy per D5) and must not grow one. `RTL` sends the spec's own dedicated, firmware-agnostic `MAV_CMD_NAV_RETURN_TO_LAUNCH` rather than resolving a firmware-specific `custom_mode` number the way `adapter-mavlink`'s current `MavlinkFlightCommander.returnToHome` does via `DO_SET_MODE` — a deliberate, non-breaking difference (nothing consumes this gateway yet). **Flagged for W4**: whether `adapter-mavlink`'s own RTL should switch to this gateway's approach, or whether `NAV_RETURN_TO_LAUNCH` support is inconsistent enough across real firmwares that the `DO_SET_MODE`-based approach should stay the adapter's own, is a product decision this wave does not make.
- **`ManualControlService`'s release burst is guaranteed by the tick body itself, not by `TxScheduler.Handle#close()`'s timing.** `TxScheduler`'s own contract only promises `close()` "stops this task from firing again" — no synchronous "no more executions after this call returns" guarantee (`DefaultTxScheduler`'s `Handle#close` is `future.cancel(false)`, which does not interrupt an already-running/already-queued execution). `release()` therefore tracks its own release-frame budget inside the tick body (decrementing under the same lock the mailbox write uses) so the *exact* release-frame count is enforced regardless of exactly when the scheduler's own cancellation takes effect; `handle.close()` afterward is cleanup, not the correctness mechanism.

### FLEET-RADIO R3 Gotchas

- **`RC_CHANNELS_OVERRIDE`'s extension channels (9..16) do not share base channels (1..8)'s release sentinel — this is a MAVLink wire fact, not a choice this module made, and getting it wrong latches a channel forever.** On channels 1..8, `0` means "release this channel back to the RC transmitter" and `65535` means "leave it alone, I'm not touching it." On channels 9..16, **both `0` and `65535` mean "ignore"**, and only `65534` (`UINT16_MAX - 1`) means "release." Before this wave, `RcChannels` modeled one uniform `RELEASE=0` for every channel — harmless while `ManualControlService.buildFrame` hardcoded chan9..18 to `IGNORE` unconditionally (F3, below), because a domain value that's never encoded onto the wire can't be encoded wrong. The moment F3 is fixed and channel 9+ values start reaching `buildFrame`, a naive `RELEASE=0` sent on channel 9 reads to the autopilot as "ignore, keep whatever you last had" — not "give this channel back" — so `release()`'s own release burst would have silently failed to release an extension channel while looking, from the domain's side, exactly like a correct release. **Fixed by resolving the sentinel at the one point it actually matters — the wire encode — via `RcChannels#wireValue(int oneBased)`:** the domain still stores one `RELEASE` constant everywhere (nothing upstream of the wire needs to know two channels-ranges disagree), and `wireValue` is the single place that re-encodes a domain `RELEASE` into `EXTENSION_RELEASE` (65534) when `oneBased > BASE_CHANNEL_COUNT`. Do not scatter this branch across call sites — a second sentinel-aware call site is exactly how this class of bug reappears.
- **F3 — chan9..18 were hardcoded `IGNORE` regardless of what the caller bound.** `ManualControlService.buildFrame` populated chan1..8 from the caller's `RcChannels` but never even looked at index 9+ before this wave — an operator's CH9 binding (a rover mode switch, a gimbal trigger, anything past the base 8) was accepted by every layer above this one and then silently dropped exactly at the wire boundary. Fixed: `buildFrame` now calls `channels.wireValue(n)` for every `n` in `1..MAX_CHANNELS` (16); the caller's actual list drives every one of those calls, not a hardcoded constant.
- **F17 — the accepted channel range is `[1,16]`, not `[1,18]`.** MAVLink #70 itself has 18 channel fields on the wire, but ArduPilot's own `RC_Channels`/override handling only reads channels 1..16 — 17/18 exist in the message and are accepted by this module's own `chan17Raw`/`chan18Raw` builder fields (still sent, always `IGNORE`, since some other autopilot family might one day read them) but `RcChannels` itself now refuses to *carry* a 17th or 18th value at all (`MAX_CHANNELS = 16` in the compact constructor), and `ManualControlService` never asks for anything past channel 16. This is enforced at the value-object boundary specifically so a caller cannot construct a channel set that looks valid but is silently truncated at the wire — it fails at construction instead, in the caller's own module (see `vision-flight`'s `MODULE.md` for the `ControlBinding`/domain-level half of this same rule, and how a persisted binding on 17/18 is made to fail loudly rather than silently degrade).

### FLEET-RADIO R1 Gotchas

- **`VehicleClass` distinguishes four outcomes, not the two `VehicleKind` has room for — this matters most for R2, the very next wave.** Before this wave, an unidentified vehicle and a non-vehicle instrument on the same link (a gimbal, a GCS, an ADS-B transponder) both fell through to the exact same fallback everywhere (`"vehicle"` in discovery, `UNKNOWN` in `FlightModes`/`VehicleKind`) — indistinguishable from each other by anything downstream. R2 makes `ControlProfile.forKind(UNKNOWN)` refuse to hand out a flyable stick map; if a gimbal heartbeating on a shared link still read as `UNKNOWN`, R2's refusal is correct by accident, and a firmware fix (or a table gap closing) that later reclassifies the gimbal into something with a real `VehicleKind` risks silently changing behaviour no one asked to change. `VehicleClass.NOT_A_VEHICLE` is the fix: it is a *different* enum constant from `UNKNOWN`, verified distinctly reachable by `VehicleTaxonomyAgreementTest.aGimbalOnTheLinkIsClassifiedDistinctlyFromAnUnrecognizedNumber`. `FlightModes.vehicleKind` still folds both into `VehicleKind.UNKNOWN` today (that enum has nowhere else to put them) — the point of keeping the finer distinction in `VehicleClass` itself is so a later wave has something to fold *from*. **R2 has since landed and confirms this was the right call**: it added `drone-link/mavlink`'s `FlightModes.unidentifiedReason(int)`, which switches on this module's own `VehicleClass.of(mavType)` (not on `VehicleKind`) to recover exactly the `NOT_A_VEHICLE`/`UNSUPPORTED_VEHICLE`/genuinely-`UNKNOWN` distinction this bullet predicted would be needed — `VehicleClass` itself required no change to support it. See `contexts/vision-flight/MODULE.md`'s `UnidentifiedReason` entry and `drone-link/mavlink/MODULE.md`'s FLEET-RADIO R2 section for what was built on top of this table.
- **`VehicleClass` gains no `SUBMARINE` constant on `VehicleKind`, by operator instruction, not by omission.** The table has a `SUBMARINE` slot (`MAV_TYPE` 12) so a later wave adding submarine support is a new `VehicleKind` row plus one already-correct `VehicleClass.of` mapping, not a fourth hand-maintained table. `FlightModes.vehicleKind(12)` returns `VehicleKind.UNKNOWN` today, same as before this wave — nothing about submarine *handling* changed, only the taxonomy's ability to name it (`VehicleClass.label(12) == "submarine"`, used by discovery and the onboarding probe, both of which already knew this vehicle before R1).
- **Package-private, not public, delegating wrappers at all three call sites.** `FlightModes.vehicleKind(int)`, `MavlinkHeartbeatScanner.vehicleKind(Integer)` and `MavlinkVehicleConfigurator.vehicleKind(int)` each kept a thin one-line method — rather than inlining `VehicleClass.of`/`.label` calls directly at every use site — specifically so `VehicleTaxonomyAgreementTest` (same package as all three) can call all three independently and assert they agree, without widening any of the three classes' public API. None of the three methods contains a `MAV_TYPE` literal any more; the mechanical check for "no local table survived" is `grep -rn "MAV_TYPE_QUADROTOR\|case 13 ->\|case 11 ->" drone-link/mavlink/src/main/java`, which returns nothing except one unrelated hit in `SimulatedVehicleMessages.java` (a synthetic outgoing `HEARTBEAT` builder that declares itself `MAV_TYPE_QUADROTOR` — an emission, not a classification table).
- **One vocabulary, chosen deliberately, not just alphabetically first.** `MavlinkHeartbeatScanner` (discovery) and `MavlinkVehicleConfigurator` (the onboarding probe) disagreed on the very same vehicles before this wave: `"fixed-wing"`/`"fixed wing"`, `"rover"`/`"ground rover"`, `"boat"`/`"surface boat"`. `VehicleClass.label` keeps the scanner's `"fixed-wing"` and `"rover"`, keeps the configurator's finer `"surface boat"` (over the scanner's plain `"boat"`, since "surface boat" is the more specific and already-persisted spelling — see `OnboardingWireContractTest`, which asserts only non-nullness of `VehicleProfile.vehicleKind`, never an exact string, so this choice does not break a frozen wire contract) and its `"coaxial helicopter"`/`"helicopter"` split, and adds new labels neither table had (`"dodecacopter"`, `"decacopter"`, `"multirotor"`, one label per VTOL subtype, `"submarine"`, a label per unsupported airframe, a label per not-a-vehicle instrument). A UI or log line that previously read `"boat"` (from discovery) now reads `"surface boat"` — the only user-visible spelling change this wave makes.
- **The ArduRover mode table's `Dock` (8) is intentionally never hidden from the reverse lookup (`customModeFor`), even though it is compiled in behind `#if MODE_DOCK_ENABLED` on real ArduPilot and therefore absent from some builds.** The forward lookup (`name(autopilot, mavType, customMode)`) is safe regardless — a build without Dock compiled in simply never reports `custom_mode == 8`, so the table entry is inert. The reverse lookup (`customModeFor`, used to *command* a mode by name) is the real risk: it would resolve `"Dock"` to `8` and let an operator command a mode number a given firmware build may not have. This wave does not hide it, because there is no live per-vehicle capability signal for an optional compiled-in mode to gate on, and hiding it would make Dock permanently uncommandable even on builds that *do* have it. The actual safety net is upstream and already exists: `MavlinkFlightCommander.send` throws for an explicit non-`ACCEPTED` `COMMAND_ACK`, so a build without Dock that honestly rejects the mode-change surfaces that rejection normally. The one residual gap — a build that ACKs `ACCEPTED` for a mode change it does not actually honor — is a firmware-honesty problem no client-side table edit can fix.

### FLEET-RADIO R4 Gotchas

- **F7, "the silent death": before this wave, a genuine `poll()` `IOException` was a dead end.** `LinkRuntime.runLoop`'s `catch (IOException e)` logged a WARNING and `return`ed — the reader thread quietly stopped, and nothing downstream (the gateway, the platform's subsystem-status page, an operator) was ever told the link had actually failed, as opposed to the vehicle simply having gone quiet. Fixed by `MavlinkSession.onLinkFailure(BiConsumer<LinkId, IOException> listener)`: the `catch (IOException e)` block now calls the listener (via a small `notifyLinkFailure` helper that itself try/catches a `RuntimeException` from the listener and logs a WARNING rather than letting it propagate) before returning. The default listener is a no-op (`(id, cause) -> { }`), not `null` — per java-clean-code §3, "a parameter may not mean 'off' by being `null`."
- **The listener fires synchronously, on the dying reader thread itself, and must not block or throw.** This is a direct extension of `MavlinkSession`'s own existing threading contract (one reader thread per link, `Dispatcher` handlers already run on it) rather than a new one — a caller that needs to do slow work (closing a `SubmissionPublisher`, tearing down a gateway) should do it inline if it is fast and non-blocking, or hand off to another thread/executor itself if it is not. `MavlinkSession` makes no attempt to time-box or isolate the listener beyond the try/catch already described; a listener that blocks indefinitely would stall that one link's reader thread's own teardown, exactly as a slow `Dispatcher` handler already could before this wave (see `BoundedSubscriber`'s existence as the answer for that case — the same discipline applies here, by the caller's own choice, not a new guarantee this method makes).
- **A shutdown must never masquerade as a link failure — this reuses the pre-existing `running` `AtomicBoolean`, not a new signal.** `LinkRuntime` already has a `running` flag flipped to `false` by `stop()` *before* it joins the reader thread; `runLoop`'s `catch (IOException e)` now checks `if (running.get())` before notifying. A poll that was parked when `removeLink`/`close` ran, and unblocks with a genuine `IOException` only because the underlying socket was closed out from under it, therefore reports nothing — indistinguishable, from the listener's point of view, from an ordinary intentional close (which never reaches this catch block at all, since `poll()`'s own contract returns `null`, not throws, for a conforming link's intentional close). Deliberately **not** a new dedicated "we are shutting down" boolean: `running` already means exactly this, and a second flag would be two sources of truth for one fact. Proven by `MavlinkSessionLinkFailureTest.aPollFailureRacingWithShutdownDoesNotFireTheListener`, which starts `removeLink()` on its own thread, waits long enough that `running` has almost certainly already flipped, then releases a parked `poll()` to throw — a regression here would show up as the listener firing during an entirely ordinary teardown.
- **The `RuntimeException` branch (unexpected error decoding/dispatching one frame) deliberately does *not* notify `onLinkFailure`, unlike the `IOException` branch.** The two branches are answering different questions. `IOException` from `poll()` means the *transport* is gone — the reader thread is `return`ing, no more frames will ever arrive on this link, and that is exactly the fact `onLinkFailure` exists to report. A `RuntimeException` while processing one already-received frame (a downstream `Dispatcher` handler misbehaving, a decode bug) is caught, logged at WARNING, and the loop *continues* to the next `poll()` — the link itself is still alive and may well deliver a perfectly good next frame. Calling `onLinkFailure` here would misreport a link that is not failing at all, which is the exact class of dishonest signal this wave exists to remove (compare F7 itself: reporting nothing when something failed is one kind of lie; reporting a failure when nothing failed is the opposite one). If a future wave wants "N consecutive frame-processing errors" to also count as a link-level failure, that is a new, separate signal to design deliberately — not a reuse of this listener as-is.
- **`LinkHealth.Health` gaining `PeerId` (D4) is the identity half of this wave; `MavlinkSession`/`DefaultLinkHealth` needed exactly one change each.** `Health` already existed *per peer* — `LinkHealth.of(PeerId)` was always keyed correctly — the bug was that the returned record threw the key away, so a caller holding several `Health` records in a collection (`adapter-mavlink`'s `MavlinkGateway.claimedVehicleHealth()`, see that module's own MODULE.md) had no way to say which one belonged to which vehicle without separately threading the `PeerId` alongside every record by hand. `DefaultLinkHealth.of(PeerId id)`'s two `new Health(...)` construction sites now pass `id` as the new first argument; no other production code in this module reads or constructs a `Health` directly, so this was the entire fix at this layer.

### O2 Gotchas (parameters + capability)

- **A 16-character `param_id` does not fit in a 64-bit `discriminator`, so the key *routes* and the service *verifies*.** `CorrelationKeys.paramDiscriminator` is FNV-1a 64 over the normalised name; `ParameterService` then compares `ParamValue.paramId()` to the requested name exactly, and a foreign name extends the wait (bounded, `MAX_FOREIGN_REPLIES = 8`) instead of being accepted. **The two halves are a pair — neither is optional.** Hashing alone would silently hand back a colliding parameter's value; verification alone has nothing to match on. FNV-1a specifically because its two constants can never drift, unlike `String#hashCode` (32-bit) or `Objects#hash` (explicitly no stability contract) — the value is a wire-matching convention shared between the requester and the RX path, so a JDK upgrade changing it would be a silent, fleet-wide hang.
- **The verification half is structurally unreachable from a loopback test.** Over a real link a wrong-named `PARAM_VALUE` hashes to a *different* key and never lands on our waiter at all, so no amount of `FakeVehicle` testing exercises the exact-name compare — only a genuine FNV-1a 64 collision would. `ParameterNameVerificationTest` therefore substitutes a scripted `Correlator` that hands the service a reply on the key it asked for whatever that reply is named, which is exactly what a collision looks like from the service's side. Without that test the safety claim would be argued rather than asserted.
- **`normalizeParamId` must be applied on both sides.** The wire field is `char[16]`, un-terminated at exactly 16 characters and NUL-padded below that, so `"SR2_EXTRA2"` and the `"SR2_EXTRA2\0\0…"` that comes back are the same name only after normalisation. Both the table and the service call the same function; a name longer than 16 chars is rejected at the API rather than silently truncated into a *different* parameter.
- **A `PARAM_SET` is never fire-and-forget, and the read-back compares floats exactly.** An autopilot clamps an out-of-range value and truncates a float into the parameter's real integer width **without refusing the write** — the echoed `PARAM_VALUE` is the only evidence of what it now holds. An epsilon here would hide precisely the small clamps that matter (a `0.1` stored as `0.0999`), so the compare is `==` on the two IEEE float32s off the same wire field; `MISMATCH` still carries what the vehicle actually holds.
- **`NO_REPLY` also means "I have no such parameter", and that conflation is the protocol's, not ours.** MAVLink gives an autopilot no way to refuse a `PARAM_REQUEST_READ` for a name it does not recognise — it simply says nothing. Unsupported, unreachable, and lost-on-the-link are one observation at this layer and are deliberately not guessed apart; the onboarding flow's `incompleteReason` is where that becomes a human-readable answer.
- **The full parameter download (`PARAM_REQUEST_LIST`) is a non-goal, not an omission.** Everything the platform needs names its parameters in advance; the stream-me-all-~1200 protocol, with its own missing-index gap detection and re-request loop, costs minutes of airtime on a 2.4 kB/s link.
- **No `api.ParameterGateway` was added.** `CommandGateway` exists because commands genuinely arrive from a broker (plan §5.1); parameters reach this service in-process through `adapter-mavlink`'s `VehicleConfigPort` implementation. Adding broker records now would be an untested seam with no caller — recorded here as a decision so a later wave adds it deliberately rather than assuming it was forgotten.
