# mavlink-core

A reusable, framework-free MAVLink library. Zero project dependencies — it does not know what a
`Device` or `Telemetry` is, and must never learn (docs/plans/active/MAVLINK-CORE-PLAN.md D2). One
third-party dependency: `io.dronefleet.mavlink:mavlink`. Frozen seam contract: `API.md`.

**Depends on:** nothing internal · `io.dronefleet.mavlink:mavlink`
**Used by:** `adapter-mavlink` (`drone-link/mavlink` — implements `LinkRegistry`), `adapter-carrier-udp`/`adapter-carrier-serial` (`drone-link/carrier-udp`/`carrier-serial` — each depends on `LinkRegistry`/`LinkDescriptor`/`CarrierKind`/`SerialRole`/`SerialLink` only, never on `adapter-mavlink`)
**Build/test:** `./mvnw -B -pl drone-link/mavlink-core test` — **172 tests** (2 cleanly skipped — `SerialLinkSocatIntegrationTest`, gated on the external `socat` binary), all green.

## API surface

### `com.drones.mavlink` (L0 — universal, depended on by anything)
- `record SysId(int value)` — 1..255, validated
- `record CompId(int value)` — 1..255, validated
- `record PeerId(SysId system, CompId component)` — identity is always `(sysid, compid)`, never a transport address
- `enum VehicleClass { COPTER, PLANE, ROVER, SUBMARINE, UNSUPPORTED_VEHICLE, NOT_A_VEHICLE, UNKNOWN }` — the one `HEARTBEAT.type` (`MAV_TYPE`) → family table for the whole project; `static VehicleClass of(int mavType)` (never `null`, `UNKNOWN` for an unmapped number) · `static String label(int mavType)` (a shared display string, `null` only for `UNKNOWN`). Distinguishes four outcomes, not two: a supported family (copter/plane/rover — submarine has a slot but deliberately maps to no `VehicleKind`, operator instruction), a recognized-but-uncontrollable airframe (`UNSUPPORTED_VEHICLE` — airship, balloon, rocket, ...), a non-vehicle instrument heartbeating on the same link (`NOT_A_VEHICLE` — gimbal, GCS, ADS-B, ...), and a genuinely unrecognized number (`UNKNOWN`). Zero project dependencies, same as everything else in this package — the context-level `VehicleKind` translation happens at the adapter boundary (`drone-link/mavlink`'s `FlightModes.vehicleKind`), never here (D2).

### `com.drones.mavlink.transport` (L1)
- `record LinkId(String value)` · `record LinkPeer(String host, int port)` (+ `LinkPeer.NONE` sentinel) · `record ByteChunk(byte[] data, int length, LinkPeer source, Instant receivedAt)`
- `interface MavlinkLink extends AutoCloseable` — `LinkId id()` · `boolean preservesMessageBoundaries()` · `ByteChunk poll(Duration timeout) throws IOException` (null on timeout **or** close, never throws for either) · `void send(byte[], int, int, LinkPeer) throws IOException` · `LinkPeer defaultTarget()` · `void close()` (idempotent, no throws)
- `final class UdpListenLink implements MavlinkLink` — **listens**: `UdpListenLink(String bindHost, int bindPort)`, binds immediately. `defaultTarget()` = most recently learned sender, `LinkPeer.NONE` before anything heard. `public LinkIntake intake()` — pre-parse datagram/byte counters + last-arrival timestamp off this link's socket; safe from any thread. See `LinkIntake` below.
- `record LinkIntake(long datagramsReceived, long bytesReceived, Instant lastDatagramAt)` — `lastDatagramAt` is `null` until the first datagram; both counters are monotonic, never reset. Counted in package-private `UdpSocketIo` (shared by `UdpListenLink`/`UdpTargetLink`) on every successful `socket.receive`, **before** anything above L1 (resync, framing, decode) ever sees the bytes — this is the honest "did anything reach the socket at all" signal a dead port cannot otherwise produce (see Gotchas). Only `UdpListenLink` exposes it publicly; `UdpTargetLink`/`TcpClientLink` gained no new method.
- `final class UdpTargetLink implements MavlinkLink` — **dials**: `UdpTargetLink(String destinationHost, int destinationPort)`, ephemeral local socket, `defaultTarget()` = the fixed configured destination. Still fully bidirectional (can `poll()` replies).
- `final class TcpClientLink implements MavlinkLink` — **dials**: `TcpClientLink(String host, int port, Duration connectTimeout)`. `preservesMessageBoundaries()` = `false`. `send`'s `target` param is accepted but unused (one connected peer only).
- package-private helpers (not part of the seam): `UdpSocketIo` (shared UDP poll/send plumbing for the two UDP links), `LinkPeers` (send-target validation), `Timeouts` (`Duration`→millis, clamped ≥1 so `Duration.ZERO`/negative never becomes `setSoTimeout(0)`'s "block forever")
- **(LINK-PAIRING-PLAN.md §3.1/§3.2, new)** `enum CarrierKind { UDP, SERIAL }` — additive, a new carrier is a new constant + a new adapter module, never a `LinkRegistry`/`LinkDescriptor` rework. `enum SerialRole { NONE, GROUND_RADIO, BENCH }` — `NONE` is the sentinel every `CarrierKind.UDP` descriptor carries (never `null`); `BENCH` always registers at priority 0 and is never auto-elected regardless of that number; role is decided by the registering carrier's own allow/deny/bench config, never guessed from a USB vendor/product id. `record LinkDescriptor(CarrierKind carrier, SerialRole serialRole, String label, int priority)` — compact-constructor validated (`label` non-blank, `priority >= 0`). `interface LinkRegistry { LinkId register(MavlinkLink, LinkDescriptor); void unregister(LinkId); }` — `register` never mints a new id (always `link.id()`) and never opens/binds anything; `unregister` is idempotent and never closes the link (registry does not own it). `final class SerialLink implements MavlinkLink` — **dials** an already-open serial device (no listen/bind semantics apply to serial): `static SerialLink open(String portDescriptor, int baudRate) throws IOException` is the production path (jSerialComm-backed via package-private `JSerialCommChannel`); package-private `SerialLink(SerialChannel)` is the test seam (`SerialLinkTest` uses a fake `SerialChannel`, `SerialLinkSocatIntegrationTest` feeds a real `socat` pty pair through the same constructor). `preservesMessageBoundaries()` is honestly `false` (stream semantics, like `TcpClientLink`); `defaultTarget()` is always `LinkPeer.NONE` (a serial wire has no addressable peer); `send`'s `target` param is accepted but unused.

### `com.drones.mavlink.codec` (L2 — the only package that may depend on `io.dronefleet.mavlink`)
- `record MavHeader(int version, int sequence, SysId system, CompId component, int messageId, int incompatFlags, int compatFlags, boolean signed)` — `version` is 1 or 2 (not the raw magic byte)
- `record MavFrame(MavHeader header, Object payload, LinkId link, LinkPeer source, Instant receivedAt)` + `boolean is(Class<?>)` / `<T> T as(Class<T>)`
- `final class FrameReader` — `FrameReader(MavlinkLink link, MavlinkCoreSettings settings)` (+ `FrameReader(MavlinkLink link)` defaulting settings) · `void offer(ByteChunk, Consumer<MavFrame> out)`
- `interface FrameSink` — `void send(Object payload, PeerId target)` · `void broadcast(Object payload, LinkId link)`. Implemented by `com.drones.mavlink.session.RoutingFrameSink` — not `FrameWriter` (see below).
- `final class FrameWriter` — `FrameWriter(SysId ourSystem, CompId ourComponent)` · `void addLink(MavlinkLink)` · `void removeLink(LinkId)` · `void send(Object payload, PeerId target)` (still requires exactly one registered link — throws `IllegalStateException` otherwise) · `void broadcast(Object payload, LinkId link)` · `void sendTo(Object payload, LinkId link, LinkPeer address)` (explicit-address send, bypassing that link's `defaultTarget()`). The only class in the module allowed to construct a `MavlinkConnection`. Does not implement `FrameSink` — see Gotchas for why, and `RoutingFrameSink` below for the real implementation.
- package-private: `ResyncBuffer` (one per source, see Gotchas)

### `com.drones.mavlink.session` (L3 — depends on L0, L1, L2; may depend on `io.dronefleet.mavlink` for message-type extraction, e.g. `Heartbeat`, `CommandAck`)
- `record HeartbeatInfo(int autopilot, int mavType, int baseMode, long customMode, int systemStatus)` — raw wire values, no firmware-name translation (that's adapter policy)
- `record Peer(PeerId id, LinkId link, LinkPeer address, Instant firstHeard, Instant lastHeard, HeartbeatInfo heartbeat)` — `heartbeat` nullable until the first `HEARTBEAT`
- `interface PeerDirectory` — `Collection<Peer> peers()` · `Peer peer(PeerId)` (null if unheard) · `List<Peer> peersOnLink(LinkId)`. `final class DefaultPeerDirectory` (package-private) is the impl; its extra `void recordFrame(MavFrame)` is package-private, called only by `MavlinkSession`.
- `interface MessageFilter` — `boolean test(MavFrame)`; statics `any()`, `messageId(int)`, `type(Class<?>)`, `fromSystem(SysId)`, `and(MessageFilter...)`
- `interface Dispatcher` — `Subscription subscribe(MessageFilter, Consumer<MavFrame>)`. `final class DefaultDispatcher` (package-private) is the impl, backed by `CopyOnWriteArrayList`; its extra `void dispatch(MavFrame)` is package-private, called only by `MavlinkSession`. Subscriber identity is by reference, not by `(filter, handler)` equality, so two subscriptions registered with an equals-identical pair close independently.
- `interface Subscription` — `void close()` (idempotent)
- `final class BoundedSubscriber implements Consumer<MavFrame>` — `BoundedSubscriber(String name, int capacity, Duration closeJoinTimeout, Consumer<MavFrame> downstream)` · `long droppedCount()` · `void close()`. Wraps a slow downstream consumer for a `Dispatcher` subscription: `accept` only ever enqueues (never blocks), a dedicated named drain thread (`mavlink-bounded-subscriber-<name>`) calls `downstream`, drop-oldest when at `capacity`.
- `record MatchKey(SysId system, int messageId, long discriminator)`
- `interface Correlator` — `CompletableFuture<MavFrame> await(MatchKey, Duration)` (throws `IllegalStateException` on a live-key repeat) · `void cancel(MatchKey)` (idempotent). `final class DefaultCorrelator` is the impl; its extra `void offer(MavFrame)` (package-private) is called only by `MavlinkSession`. **`DefaultCorrelator` is closed for modification** (MISSIONS D6): it owns registry mechanics only and delegates every key extraction to `CorrelationKeys`.
- `final class CorrelationKeys` — the one place a correlated reply's key is defined, **for both directions**. Request side (public): `MatchKey forCommandAck(SysId, int commandId)` · `MatchKey forParamValue(SysId, String paramId)` · `MatchKey forAutopilotVersion(SysId)` · `String normalizeParamId(String)` · `long paramDiscriminator(String)` · constants `COMMAND_ACK_MESSAGE_ID` (77), `PARAM_VALUE_MESSAGE_ID` (22), `AUTOPILOT_VERSION_MESSAGE_ID` (148), `MISSION_REQUEST_MESSAGE_ID` (40), `MISSION_COUNT_MESSAGE_ID` (44), `MISSION_ACK_MESSAGE_ID` (47), `MISSION_REQUEST_INT_MESSAGE_ID` (51), `NO_DISCRIMINATOR` (0). Reply side (package-private): `static MatchKey keyFor(MavFrame)`, backed by a compiled-in `Map<Class<?>, Function<MavFrame, MatchKey>>` — exact-class lookup (every payload type is `final`), `null` for anything uncorrelated. **Adding a correlated message type is a row in this table plus a factory here — never an edit to `DefaultCorrelator`.** The four MISSION rows are landed here in full per **D14** so MISSIONS' `MissionService` consumes the table unchanged; they are covered by `CorrelationKeysTest`.
- `interface TxScheduler` — `Handle repeat(String name, Duration period, Runnable)` · `void submit(String name, Runnable)` — a one-shot on the same pool, same catch-and-log contract; a submission racing shutdown is *dropped, not thrown*; no `Handle`, since an already-queued one-shot cannot usefully be cancelled; nested `interface Handle { void close(); }` (idempotent). `final class DefaultTxScheduler implements TxScheduler` — `DefaultTxScheduler(MavlinkCoreSettings)` or `DefaultTxScheduler(Duration closeJoinTimeout)` · extra `void close()` (not part of the `TxScheduler` seam) shuts down the shared 2-thread `ScheduledExecutorService`. **Not owned by `MavlinkSession`** — construct one independently (see Gotchas).
- `interface LinkHealth` — `Health of(PeerId)`; nested `record Health(PeerId peerId, boolean connected, Instant lastHeard, long received, long lost, double dropRate)` (carries `peerId` as its first field so a consumer holding several `Health` records — e.g. a fleet health aggregator — can tell them apart). `final class DefaultLinkHealth implements LinkHealth` — `DefaultLinkHealth(Duration peerTimeout)`; extra `void recordFrame(MavFrame)` (package-private) called only by `MavlinkSession`.
- `final class RoutingFrameSink implements FrameSink` — `RoutingFrameSink(PeerDirectory, FrameWriter)`. Resolves a `PeerId`'s link **and address** via `PeerDirectory.peer(target)`, then calls `FrameWriter.sendTo(payload, peer.link(), peer.address())` — an explicit-address send, not `broadcast` — so a `send` reaches that specific peer even when several peers share one listen link (`UdpListenLink#defaultTarget()` only ever reports the most recently learned sender). Throws `IllegalArgumentException` naming the "you cannot send to a peer you have not heard from" rule for an unknown/unheard peer.
- `record MavlinkNode(SysId system, CompId component)` — `static groundStation()` → 255/190
- `final class MavlinkSession implements AutoCloseable` — `MavlinkSession(MavlinkNode, MavlinkCoreSettings)` · `void addLink(MavlinkLink)` (throws if already registered or session closed) · `void removeLink(LinkId)` (idempotent) · `PeerDirectory peers()` · `Dispatcher dispatcher()` · `Correlator correlator()` · `FrameSink sink()` · `LinkHealth health()` · `void onLinkFailure(BiConsumer<LinkId, IOException> listener)` · `void close()` (idempotent). The composition root: one reader thread per link (`mavlink-rx-<linkId>`), fixed per-frame order `PeerDirectory` + `LinkHealth` → `Correlator` → `Dispatcher`. See Gotchas for `onLinkFailure`'s full contract (fires synchronously from the dying reader thread and must not block/throw; a shutdown-triggered `IOException` never fires it; a `RuntimeException` from a frame handler never fires it either).
- **(LINK-PAIRING-PLAN.md §3.1, new)** `interface LinkQuality { Quality of(LinkId); }` — a deliberate **separate** port from `LinkHealth`, keyed by `LinkId` not `PeerId`: answers "how good is this *link* right now" (per-link RADIO_STATUS telemetry) rather than `LinkHealth`'s "is this *peer* connected," which already collapses to whichever link a peer was most recently heard on. Nested `record Quality(LinkId linkId, Instant lastRadioStatusAt, Integer rssi, Integer remoteRssi, Integer noise, Integer rxErrors, Boolean fixed)` — every numeric field nullable-boxed so "never heard" (`of` returns `null`) stays distinguishable from "heard a genuine zero." `final class DefaultLinkQuality implements LinkQuality` — `DefaultLinkQuality(Dispatcher)`, subscribes once in the constructor (no `MavlinkSession` change needed — `dispatcher()`/`Dispatcher#subscribe` were already public) to inbound `RADIO_STATUS` (#109) frames whose source component id is 68/110/111/112 (the well-known telemetry-radio component ids, distinct from the autopilot's own).

### `com.drones.mavlink.config` (universal, like L0)
- `record MavlinkCoreSettings(Duration heartbeatPeriod, Duration peerTimeout, Duration commandTimeout, int commandRetries, Duration commandDedupeWindow, Rc rc, Duration closeJoinTimeout, int maxResyncBuffers, int dispatchQueueCapacity, Mission mission, Ftp ftp, Parameter parameter)` — `static defaults()`, one `with*` per top-level field, compact-constructor validated. Nested `Rc(int overrideHz, int minOverrideHz, int maxOverrideHz, int releaseFrames)` (+ `clampedOverrideHz()`), `Mission(Duration timeout, Duration itemTimeout, int retries)`, `Ftp(Duration timeout, int retries)`, `Parameter(Duration timeout, int retries)` (1 s / 3 — the MAVLink parameter-protocol page states its own retry policy). Every default is byte-identical to `API.md`'s table.

### `com.drones.mavlink.service` (L4 — depends on L0, L3; one class per MAVLink microservice, ISP-scoped role interfaces only, never `MavlinkSession`)
- `final class RequestResponse` — the shared Family-A machine (plan §2.2), constructed from a bare `Correlator` + `FrameSink` — genuinely standalone, not folded into `CommandService`. `RequestResponse(Correlator, FrameSink)` · `CompletableFuture<MavFrame> exchange(PeerId target, MatchKey key, Duration timeout, int maxRetries, AttemptPayload payload, ReplyClassifier classifier)`. `AttemptPayload.forAttempt(int attempt)` builds the payload for a 0-based attempt; `ReplyClassifier.extensionFor(MavFrame reply)` returns `null` for a terminal reply (the exchange completes with it) or a `Duration` to keep waiting on the same key without resending. Continuation-based throughout (`thenCompose`/`exceptionallyCompose`, never a blocked thread) — see its own javadoc for why, and see Gotchas for a `CompletableFuture` ordering hazard worth knowing before touching this class.
- `final class CommandService` — `COMMAND_LONG` and `COMMAND_INT`, `COMMAND_ACK` awaited via `RequestResponse`, matched on `(origin sysid, command id)` only (inherited from `Correlator`/`DefaultCorrelator` unchanged). `CommandService(FrameSink, Correlator, Duration timeout, int retries)` and a `MavlinkCoreSettings`-based overload. `CompletableFuture<CommandOutcome> sendLong(PeerId target, MavCmd command, float param1..param7)` · `CompletableFuture<CommandOutcome> sendInt(PeerId target, io.dronefleet.mavlink.common.MavFrame frame, MavCmd command, float param1..param4, int x, int y, float z)` — the parameter is the *coordinate-frame* enum, spelled fully-qualified in both the API and this doc because it shares a simple name with this module's own `MavFrame` envelope (see Gotchas). `confirmation` = the 0-based attempt number on every `COMMAND_LONG` retry (not sent at all on `COMMAND_INT`, which has no such field). `record CommandOutcome(Status status, MavResult mavResult, int resultCode, CommandAck ack)`, nested `enum Status { ACCEPTED, TEMPORARILY_REJECTED, DENIED, UNSUPPORTED, FAILED, CANCELLED, IN_PROGRESS, NO_ACK }` — a protocol-level, 8-value status distinct from `com.drones.mavlink.api.CommandOutcome.Status`'s frozen 7-value one (see Gotchas for the mapping). `IN_PROGRESS` replies extend the deadline (bounded at 20 extensions, `MAX_IN_PROGRESS_EXTENSIONS`, not spec/config — see Gotchas) rather than terminating; exhausting that bound still completes the exchange, with `Status.IN_PROGRESS`, not a bare timeout.
- `final class HeartbeatService` — `HeartbeatService(FrameSink, TxScheduler, PeerDirectory, MavlinkCoreSettings)`, a `+ HeartbeatContent` overload for a non-default identity, package-private `(FrameSink, TxScheduler, PeerDirectory, Duration heartbeatPeriod, Duration peerTimeout, HeartbeatContent)` test seam. `void start()` / `void stop()` (both idempotent) · `boolean isConnected(PeerId)` (reflects the most recent tick, `false` for an unknown peer). Every tick both emits `content.toMessage()` (a `Heartbeat`) via `FrameSink#broadcast` on every distinct `LinkId` currently known through `PeerDirectory#peers()`, and recomputes its own connected/disconnected view from `Peer#lastHeard()` vs. `peerTimeout` (see Gotchas — this is deliberately not `LinkHealth`).
- `record HeartbeatContent(MavType type, MavAutopilot autopilot, int baseMode, long customMode, MavState systemStatus)` — raw wire values for our own outgoing `HEARTBEAT`, `static groundStation()` default (`MAV_TYPE_GCS` / `MAV_AUTOPILOT_INVALID` / `MAV_STATE_ACTIVE`, matching `MavlinkNode.groundStation()`'s own convention).
- `final class ManualControlService` — `RC_CHANNELS_OVERRIDE` (#70) relay, driven by this module's own `TxScheduler`. Runs on a ceiling/floor pair, not a single fixed rate (docs/plans/done/RC-LATENCY-PLAN.md §2 A): a *ceiling* (`1/maxOverrideHz`, the scheduler period — never transmit faster) and a *floor* (`1/clampedOverrideHz` — an unchanged mailbox still transmits this often, so an aircraft never sees a gap that expires its override timeout). A `send` arriving at least a ceiling-period after the last transmit is pushed to the wire immediately via `TxScheduler#submit`, so the periodic task is the keepalive rather than the send loop; both paths share one under-lock decision, so the combined wire rate is bounded by the ceiling, not their sum. `ManualControlService(FrameSink, TxScheduler, PeerDirectory, MavlinkCoreSettings.Rc)` and package-private `(FrameSink, TxScheduler, PeerDirectory, Duration tickPeriod, int releaseFrames)` / `(…, Duration tickPeriod, int releaseFrames, LongSupplier nanoClock)` test seams (one period serving as both ceiling and floor; the clock seam lets a manually driven scheduler step past either without real sleeps) — **no `Correlator` parameter at all**, by design (ISP: this class must not be able to express an ack wait). `ManualControlLink engage(PeerId target)` (throws `IllegalArgumentException` — "cannot command what you cannot hear" — and starts no task if `target` is unknown to `PeerDirectory`) · `void send(ManualControlLink, RcChannels)` (latest-wins mailbox write, silent no-op once releasing) · `void release(ManualControlLink)` (writes the release sentinel, blocks the caller `releaseFrames * coalescePeriod` for the burst to actually go out, then closes the scheduled task; idempotent). `interface ManualControlLink { boolean active(); }` — an opaque handle (core's own; distinct from `vision-flight`'s port type of the same name, which additionally carries `rateHz()`), `send`/`release` throw `IllegalArgumentException` for a link this service did not itself create. Every tick re-resolves `PeerDirectory#peer(target)` fresh (never cached at `engage`-time); a currently-unknown target pauses the tick (no send, logged once on the transition) rather than failing. `buildFrame` populates every channel 1..16 from the caller's `RcChannels`; channels 17/18 stay hardcoded `IGNORE` since `RcChannels` itself refuses to carry a value past 16 (see Gotchas for why).
- `record RcChannels(List<Integer> microsByChannel)` — this module's own RC-override value type (`RELEASE=0`, `IGNORE=0xFFFF`, `EXTENSION_RELEASE=0xFFFE`, `MIN_MICROS=1000`, `MAX_MICROS=2000`, `MAX_CHANNELS=16`, `BASE_CHANNEL_COUNT=8`, `wireValue(int)`, `static allIgnore(int)`/`released(int)`) — a deliberate, small duplication of `vision-flight`'s identically-shaped `RcChannels` (see Gotchas: zero project dependencies forbids importing it). Accepts 1..16 channels, not 1..18 — ArduPilot reads no higher (see Gotchas); `wireValue(int)` is the one place a domain `RELEASE` is re-encoded as `EXTENSION_RELEASE` for channel 9 and above (see Gotchas).
- `final class MessageIntervalService` — `MAV_CMD_SET_MESSAGE_INTERVAL` / `MAV_CMD_REQUEST_MESSAGE`, both plain `COMMAND_LONG`s over `CommandService` ("do not reimplement the ack cycle"). `MessageIntervalService(CommandService)`. `setMessageInterval(PeerId, int messageId, Duration interval)` (converts to **microseconds** — the one easy-to-get-wrong number; throws for a negative `Duration`) · `disableMessage(PeerId, int messageId)` (`param2 = DISABLE_STREAM = -1`, the spec's own sentinel) · `requestMessage(PeerId, int messageId)`.
- `final class ParameterService` — the parameter microservice, over `RequestResponse`. `ParameterService(FrameSink, Correlator, Duration timeout, int retries)` and a `MavlinkCoreSettings`-based overload (uses `settings.parameter()`). `CompletableFuture<ParameterOutcome> read(PeerId, String name)` · `CompletableFuture<Map<String, ParameterOutcome>> readAll(PeerId, List<String> names)` (all in flight at once — distinct `MatchKey`s never collide; duplicates in `names` are collapsed, since two live waiters on one key is an `IllegalStateException` by `Correlator`'s contract) · `CompletableFuture<ParameterOutcome> write(PeerId, String name, float value, MavParamType type)`. Reads always address the parameter **by name**, with `param_index = READ_BY_NAME = -1` — an index is a property of one firmware build's table and shifts across versions. A write is **always** a read-back (see Gotchas); there is no fire-and-forget variant. A blank name, or one longer than the wire's 16-char `param_id`, throws `IllegalArgumentException` before anything is sent or any waiter is registered.
- `record ParameterValue(String name, float value, MavParamType type, int index, int count)` — `boolean isNamed(String)`. `name` is normalised; `index` is informational and must never be used to correlate.
- `record ParameterOutcome(Status status, ParameterValue value, String detail)`, nested `enum Status { OK, MISMATCH, NO_REPLY }`, `boolean ok()`. `value` is non-null except for `NO_REPLY`; compact-constructor enforced.
- `final class CapabilityService` — `MAV_CMD_REQUEST_MESSAGE(AUTOPILOT_VERSION)`, awaiting the **message itself**, not its `COMMAND_ACK` (which is why this is not a `MessageIntervalService.requestMessage` call — that awaits the ack, which only says the request was accepted). `CapabilityService(FrameSink, Correlator, Duration timeout, int retries)` and a `MavlinkCoreSettings`-based overload that reuses `commandTimeout`/`commandRetries`, since what goes on the wire is a `COMMAND_LONG`. `CompletableFuture<CapabilityReport> requestAutopilotVersion(PeerId)`. The `COMMAND_ACK` the vehicle also sends finds no waiter and is dropped, as an uncorrelated frame should be.
- `record CapabilityReport(Status status, String firmwareVersion, Maturity maturity, Set<MavProtocolCapability> capabilities, long boardVersion, int vendorId, int productId, BigInteger uid, AutopilotVersion raw)` (`uid` added LINK-PAIRING-PLAN.md §3.6, wave L2), nested `enum Status { OK, NO_REPLY }` and `enum Maturity { DEV, ALPHA, BETA, RC, OFFICIAL, UNKNOWN }`, `boolean ok()` · `boolean supports(MavProtocolCapability)`. Decodes the packed `flight_sw_version` uint32 into `"major.minor.patch"` + maturity, and expands the `capabilities` bitmask into the flags it sets — both are protocol knowledge that belongs here rather than in every caller; what those flags *mean* for a feature is domain policy and deliberately stays out. `uid` is `AUTOPILOT_VERSION.uid` verbatim — the flight-controller hardware uid `PairingService` uses to detect a board swap (§3.6); `null` for `Status#NO_REPLY`, same as every other OK-only field on this record.

### `com.drones.mavlink.api` (L4½ — the broker seam)
- `record CommandRequest(String vehicleKey, String kind, List<Double> params, String correlationId, Duration deadline, boolean force)` — compact-constructor validated (`vehicleKey`/`kind`/`correlationId` non-blank, `params.size() <= 7`, `deadline` positive). L0-only imports.
- `record CommandOutcome(String correlationId, Status status, int resultCode, String detail, Instant at)`, nested `enum Status { ACCEPTED, IN_PROGRESS, DENIED, NO_ACK, UNSUPPORTED, DUPLICATE, UNREACHABLE }` — frozen per API.md, L0-only imports.
- `interface VehicleKeyResolver { PeerId resolve(String vehicleKey); }` — `null` for unknown; L0-only.
- `interface CommandGateway { CompletionStage<CommandOutcome> submit(CommandRequest); }` — L0-only.
- `final class DefaultCommandGateway implements CommandGateway` — the **one** class in this package that imports L3/L4 (`CommandService`; the frozen seam types above import nothing beyond L0). `DefaultCommandGateway(CommandService, VehicleKeyResolver, Duration dedupeWindow)` and a `MavlinkCoreSettings`-based overload. `submit`: parses `kind` and builds the `COMMAND_LONG` params synchronously first (**throws** `IllegalArgumentException` here, before any dedupe bookkeeping, for an unknown `kind` or a `kind` missing a required positional `param`) — this is the *only* way `submit` throws. Dedupe reservation is one atomic `ConcurrentHashMap#compute` keyed by `correlationId`: a live (not-yet-done, not-expired) entry is returned as-is (same `CompletionStage`, no second dispatch); a completed-but-fresh entry yields `Status.DUPLICATE`; anything else (new or expired) reserves a fresh, not-yet-complete stage and this caller becomes the one dispatcher. `resolver.resolve(vehicleKey) == null`, or a resolved-but-never-heard peer (surfaces as an exception from `CommandService`/`FrameSink#send`, caught via `.exceptionally`), both complete `Status.UNREACHABLE` — never thrown. Expired dedupe entries are pruned lazily/opportunistically on every `submit()` call (no background thread). The kind→command mapping (`ARM`, `DISARM`, `SET_MODE`, `RTL`, `SET_MESSAGE_INTERVAL`, `REQUEST_MESSAGE`) lives in one private `CommandSpec.forRequest`/`Kind` pair — see Gotchas for `SET_MODE`'s and `RTL`'s own design notes.

## Conventions
- Plain classes, `System.Logger` (WARNING on recoverable decode/discard events), no framework annotations.
- Idempotent `close()` via `AtomicBoolean` CAS + close-the-socket-to-unblock-a-pending-poll, ported from `adapter-mavlink`'s `MavlinkSocketHub`/`MavlinkUdpInputStream` idiom.
- `poll(Duration)` is driven by exactly one reader thread per link (no internal threads in L1/L2); `send` is thread-safe on every link so several services can share one link concurrently.
- Records validate in compact constructors, `IllegalArgumentException` naming the bad value.
- An L3 role interface (`Correlator`, `PeerDirectory`, `Dispatcher`, `LinkHealth`) stays read-only/fire-and-forget in its public shape; the one `Default*` class implementing it carries one extra package-private mutation method (`offer`/`recordFrame`/`dispatch`), callable only by `MavlinkSession` in the same package. This keeps the frozen `API.md` seam exactly as published while still giving the composition root what it needs.

## Gotchas
- **`LinkIntake` counts are deliberately pre-parse and deliberately dumb.** A UDP port nothing is transmitting to blocks forever in `DatagramSocket#receive` with no error, no timeout distinct from "nothing yet," and no log. `LinkIntake` is the report a caller can use instead: `datagramsReceived`/`bytesReceived` increment on every successful `receive`, before `FrameReader` attempts any resync — a garbage datagram (wrong protocol, MAVLink 1, random bytes) counts exactly like a valid frame does. This is intentional: the diagnostic value is entirely in the *comparison* between this count and a higher layer's own decoded-frame count — zero datagrams means nothing is reaching the socket; datagrams arriving with nothing decoding means the wrong thing is. Neither number alone can tell those apart, and this module has no frames-decoded counter of its own to compare against (that lives one layer up, at the adapter's own intake-status endpoint).
- **`FrameReader` never re-implements CRC/resync/dialect layout** — every parse attempt hands the current pending buffer to a fresh `io.dronefleet.mavlink.MavlinkConnection` over a `ByteArrayInputStream`. Deliberate: `MavlinkConnection#next()` is built around a *genuinely blocking* `InputStream` (real end-of-stream only), and reusing one persistent connection while feeding it bytes incrementally corrupts its internal `TransactionalInputStream` bookkeeping the moment a read attempt fails mid-frame — a retried `next()` would misread the tail of an unfinished frame as a fresh version-marker search. A `CountingInputStream` wrapper tracks exactly how many bytes (resync-skipped garbage included) a successful attempt consumed, so the pending buffer trims correctly; a failed attempt (`EOFException`, not a real error) trims nothing and retries the *whole* buffer once more bytes arrive — cheap, since frames are ≤280 bytes.
- **Dialect persistence is a per-buffer approximation, not the library's own per-sysid map.** Rebuilding the connection per attempt loses `MavlinkConnection`'s internal `systemDialects` cache, so `ResyncBuffer` asks the about-to-be-discarded connection for `getDialect(originSystemId)` after every successful decode and primes the next attempt's connection with it as the default dialect — reusing the library's own resolution rather than re-declaring an autopilot→dialect table. This is last-heartbeat-wins per resync buffer, not truly per-sysid: one physical source relaying two vehicles of *different* firmware families could see the wrong default briefly applied to the second vehicle's ardupilotmega-only messages until its own heartbeat arrives. Full per-sysid tracking belongs to L3 (`PeerDirectory`), not this layer.
- **One resync buffer per source, LRU-evicted at `maxResyncBuffers`.** Boundary-preserving links (UDP) key by `LinkPeer`; stream links (TCP) use one fixed sentinel key regardless of `ByteChunk.source()`. Proven by `PerSourceResyncIsolationTest` — a source that concatenates every sender into one byte stream corrupts resync across multiple senders on one link, which is exactly what per-source buffers prevent.
- **A single resync buffer is bounded (4096 bytes) against a source that never produces a valid frame**, checked *after* each drain attempt, not before — checking before would discard a single large-but-entirely-valid chunk containing many back-to-back frames just because its raw length briefly exceeded the cap.
- **`FrameWriter` keeps one persistent `MavlinkConnection` per registered link, reused for every send.** This is what makes "sequence allocation per `(link, sysid, compid)`, wrapping at 255" work for free: `MavlinkConnection`'s own sequence counter already increments and wire-wraps correctly (8-bit truncation on serialize) as long as the *same* connection instance is reused — constructing a fresh one per send would reset the sequence to 0 on every call.
- **`Object payload` on `MavFrame`/`FrameSink` is a known, investigated wart (kept).** `io.dronefleet.mavlink`'s generated message classes (`Heartbeat`, `CommandLong`, ...) are plain `public final class`, no common interface or superclass — confirmed by reading the sources jar. The only shared marker is the class-level `@MavlinkMessageInfo` runtime annotation (carries `id`/`crc`), which cannot replace `Object` in a type position since annotations aren't types. `FrameWriter` does use it defensively: a payload missing the annotation is rejected with a clear `IllegalArgumentException` before it would otherwise hit a confusing NPE inside `MavlinkConnection.send2`.
- **`Duration.ZERO`/negative never means "block forever."** `DatagramSocket#setSoTimeout(0)` and `Socket#setSoTimeout(0)` both mean "wait indefinitely" — the opposite of what a caller passing a non-positive `poll(Duration)` timeout almost certainly means. `Timeouts.clampMillis` floors at 1ms.
- **`FrameWriter` does not implement `FrameSink`; `RoutingFrameSink` (in `session`) is the real implementation, and it must route by address, not just by link.** `UdpListenLink#defaultTarget()` reports only "the most recently learned sender" on that link — with several peers sharing one listen link (see `MultiPeerLoopbackTest`), sending via `broadcast`/`defaultTarget()` alone can reach the wrong peer even after resolving the right link. `RoutingFrameSink.send` therefore calls `FrameWriter.sendTo(payload, peer.link(), peer.address())`, an explicit-address send that bypasses `defaultTarget()` entirely. `FrameWriter.send`/`broadcast` remain plain public methods (not `@Override`s of anything) for a caller with only one link that doesn't want to build a `PeerDirectory` (a TX simulator, a test).
- **`Correlator.offer`'s extraction is a compiled-in table (`CorrelationKeys`), not an `instanceof` chain and not a plugin registry.** `DefaultCorrelator` is closed for modification: it owns registry mechanics only and delegates every key extraction to `CorrelationKeys`'s `Map<Class<?>, Function<MavFrame, MatchKey>>` (exact-class lookup, since every payload type is `final`). Adding a correlated message type is a new row in `CorrelationKeys` plus a factory method — never an edit to `DefaultCorrelator`. Deliberately not a runtime registry: nothing needs to register an extractor at runtime, and a registry would trade a compile-time guarantee for a startup-ordering bug.
- **`TxScheduler` is not owned or exposed by `MavlinkSession`.** `API.md`'s `MavlinkSession` accessor list has no `txScheduler()` — TX scheduling is orthogonal to the RX-driven state `MavlinkSession` manages (peers/health/correlation/dispatch); `HeartbeatService`/`ManualControlService` each take a `TxScheduler` as a constructor argument, and whether they share one instance or each get their own is the caller's choice.
- **`DefaultTxScheduler`'s pool size (2) is an internal implementation choice, not a config value.** `MavlinkCoreSettings` has no scheduler-pool-size field; 2 is a small, documented, arbitrary safety margin so one slow/blocked TX task cannot delay every other periodic task sharing the scheduler, while staying "one shared pool, not one thread per feature."
- **`MavlinkSession.LinkRuntime.stop()` guards against a self-join.** A `Dispatcher` handler runs on the RX thread that decoded the frame, and may itself call `removeLink`/`close` on its own link synchronously (e.g. reacting to a link-error message). `Thread#join` from a thread on itself doesn't deadlock forever (a bounded `join(millis)` always returns once the timeout elapses) but would needlessly stall that thread for up to `closeJoinTimeout` — `stop()` checks `thread == Thread.currentThread()` and skips the join in that case. Proven by `MavlinkSessionSelfRemovalTest` with a 10s `closeJoinTimeout` so a regression shows up as an obvious stall, not a subtle timing flake.
- **(LINK-PAIRING-PLAN.md §3.1/§3.2) `SerialLink.poll` treats a negative read as a genuine `IOException`, unlike `TcpClientLink`'s silent-close-on-FIN.** A TCP `read() == -1` is the remote peer's own orderly shutdown — an intentional signal. A serial file descriptor has no peer to send one; end-of-stream there means the underlying device disappeared out from under an open link (a USB radio unplugged, a bridge process killed) while nobody asked this link to close — exactly the "genuine failure" `MavlinkSession#onLinkFailure` exists to report. Get this backwards (treat it as a silent close, `TcpClientLink`-style) and an unplugged radio looks identical to an intentional `removeLink()` — no WARNING, no failure notification, nothing.
- **`LinkRegistry.register`/`unregister` never own the link's lifecycle — this mirrors `MavlinkSession.addLink`/`removeLink` exactly, one layer up.** A carrier adapter (carrier-udp, carrier-serial) that calls `unregister` on a link it is retiring (a hotplug removal, a lost bench cable) is still responsible for calling that link's own `close()` — the registry only stops routing frames through it. Getting this backwards leaks a still-open socket/port every time a link disappears.
- **`LinkHealth`'s per-`(PeerId, LinkId)` accounting is exposed through a `PeerId`-only query (`of(PeerId)`).** Accounting is genuinely per `(PeerId, LinkId)`, but the frozen `LinkHealth.of` signature takes no `LinkId`. `DefaultLinkHealth` resolves this by tracking one window per peer and resetting it whenever that peer is next heard on a *different* link than the one the running window belongs to (latest-link-wins, mirroring `Peer`'s own single `link` field) — correct for the common case (one peer, one link), but `of(PeerId)` cannot disambiguate two links a peer is genuinely active on *simultaneously*.
- **A genuine `poll()` `IOException` notifies `onLinkFailure`; the reader thread does not just stop silently.** `LinkRuntime.runLoop`'s `catch (IOException e)` calls the registered listener (via a `notifyLinkFailure` helper that itself catches a `RuntimeException` from the listener and logs WARNING rather than letting it propagate) before returning. The default listener is a no-op (`(id, cause) -> {}`), not `null` — per java-clean-code §3, a parameter never means "off" by being `null`.
- **The `onLinkFailure` listener fires synchronously, on the dying reader thread itself, and must not block or throw.** This extends `MavlinkSession`'s existing threading contract (one reader thread per link, `Dispatcher` handlers already run on it) rather than inventing a new one — a caller needing slow work should do it inline only if fast/non-blocking, or hand off to its own executor otherwise. `MavlinkSession` does not time-box or isolate the listener beyond the try/catch described above (the same discipline `BoundedSubscriber` exists to provide for a slow `Dispatcher` handler applies here, by the caller's own choice).
- **A shutdown must never masquerade as a link failure.** `LinkRuntime` already has a `running` `AtomicBoolean` flipped to `false` by `stop()` *before* it joins the reader thread; `runLoop`'s `catch (IOException e)` checks `if (running.get())` before notifying. A poll parked when `removeLink`/`close` ran, unblocking with a genuine `IOException` only because the underlying socket was closed out from under it, therefore reports nothing — indistinguishable from an ordinary intentional close. Deliberately reuses `running` rather than adding a second "we are shutting down" flag — that would be two sources of truth for one fact. Proven by `MavlinkSessionLinkFailureTest.aPollFailureRacingWithShutdownDoesNotFireTheListener`.
- **A `RuntimeException` while processing one already-received frame does *not* fire `onLinkFailure`, unlike an `IOException` from `poll()`.** The two answer different questions: an `IOException` from `poll()` means the *transport* is gone (the reader thread is returning, nothing more will ever arrive); a `RuntimeException` from a `Dispatcher` handler or a decode bug is caught, logged WARNING, and the loop *continues* — the link itself is still alive. Calling `onLinkFailure` here would misreport a link that is not failing. "N consecutive frame-processing errors should also count as a link failure" would be a new, deliberately-designed signal, not a reuse of this listener.
- **`RequestResponse` defensively cancels the correlator key before every retry.** `Correlator#await`'s own self-cleanup (`future.whenComplete(...)` removing the map entry) and `RequestResponse`'s own retry-on-timeout continuation are two independent dependents registered on the *same* future, and `CompletableFuture` gives no ordering guarantee between two independently-registered dependents of one future's completion — re-registering the same key immediately on a timeout can otherwise hit `Correlator`'s `IllegalStateException: A live await is already registered` before the self-cleanup dependent has run. `RequestResponse` calls `correlator.cancel(key)` (idempotent either way) immediately before every retry's re-registration. Any future code that re-registers the same key outside `RequestResponse` (e.g. a Mission/FTP service) should reuse this discipline rather than re-derive it.
- **A timeout inside `RequestResponse`'s extension phase is terminal, never a retry.** The retry-on-timeout handling attaches to the *initial* `waiter` alone, before `continueOrComplete` (the recursive extension chain) is chained onto it — attaching it to the *combined* result would catch an extension-phase timeout with the same handler as the initial await's timeout and issue a spurious resend, corrupting a protocol exchange that must not resend mid-extension (see `RequestResponse.sendAttempt`'s own comment).
- **`ManualControlService`'s and `CommandService`'s "lost target" branch (`PeerDirectory#peer(target) == null`) is unreachable in production once a send has already succeeded once.** `PeerDirectory`/`DefaultPeerDirectory` never evicts a once-known peer — there is no protocol-level "this peer is gone" signal at L4 without `LinkHealth` (deliberately not an L4 role interface) or an adapter-level claim/re-election policy (deliberately out of scope for this module). A vehicle that goes silent forever after being heard once still returns a non-null, increasingly stale `Peer`. Tests exercising the "lost target" pause logic use a hand-fake `PeerDirectory` that — unlike the real one — can be told to forget a peer; that proves the pause logic itself, not that production wiring can reach the branch today.
- **`HeartbeatService` can only broadcast our `HEARTBEAT` on links `PeerDirectory` already knows a peer on** (`peers().stream().map(Peer::link)`) — there is no "every registered link" role interface at L4 (only `FrameSink`/`Correlator`/`PeerDirectory`/`TxScheduler`). A dial-out `UdpTargetLink` whose destination has never sent us anything is unreachable by this service until it does; a `UdpListenLink` has the same limitation for a structural reason (`MavlinkLink#send` cannot address an unlearned target at all).
- **`CommandService.CommandOutcome.Status` (8 values, protocol-level) and `com.drones.mavlink.api.CommandOutcome.Status` (7 values, frozen by `API.md`) are deliberately different enums**, not a naming accident. `DefaultCommandGateway.toApiOutcome` folds `TEMPORARILY_REJECTED`/`FAILED`/`CANCELLED` all into the api-level `DENIED` bucket — the frozen enum has no room for the finer distinction — while `CommandOutcome.detail` still carries the raw `MavResult` name, so nothing is silently lost, only coarsened at the broker-facing boundary.
- **`RcChannels` is duplicated, on purpose.** `com.drones.mavlink.service.RcChannels` and `vision-flight`'s own `com.drones.vision.flight.domain.model.RcChannels` are structurally identical (same sentinels, same validation) but this module cannot import the latter (zero project dependencies) and must not invent a shared jar just for one record; `adapter-mavlink` translates between the two at the L4/L5 boundary.
- **`com.drones.mavlink.codec.MavFrame` (this module's own envelope: header + payload + link) and `io.dronefleet.mavlink.common.MavFrame` (the wire coordinate-frame enum, e.g. `MAV_FRAME_GLOBAL_INT`) share a simple name.** `CommandService.sendInt`'s `frame` parameter and every call site that touches it spell the library type out fully-qualified (`io.dronefleet.mavlink.common.MavFrame`) rather than importing it, specifically so the unqualified `MavFrame` symbol everywhere else in this module unambiguously means the codec envelope.
- **`SET_MODE`/`RTL` in `DefaultCommandGateway`'s kind table carry zero firmware-mode-name knowledge, by design.** `SET_MODE` expects the caller to supply an *already-resolved* numeric `custom_mode` as `params[0]` — this module has no ArduPilot/Betaflight mode-name table (that stays `adapter-mavlink`'s `FlightModes`) and must not grow one. `RTL` sends the spec's own dedicated, firmware-agnostic `MAV_CMD_NAV_RETURN_TO_LAUNCH` rather than resolving a firmware-specific `custom_mode` number.
- **`ManualControlService`'s release burst is guaranteed by the tick body itself, not by `TxScheduler.Handle#close()`'s timing.** `TxScheduler`'s contract only promises `close()` "stops this task from firing again" — no synchronous "no more executions after this call returns" guarantee (`DefaultTxScheduler`'s `Handle#close` is `future.cancel(false)`, which does not interrupt an already-running/already-queued execution). `release()` therefore tracks its own release-frame budget inside the tick body (decrementing under the same lock the mailbox write uses) so the *exact* release-frame count is enforced regardless of exactly when the scheduler's own cancellation takes effect; `handle.close()` afterward is cleanup, not the correctness mechanism.
- **`RC_CHANNELS_OVERRIDE`'s extension channels (9..16) do not share base channels' (1..8) release sentinel — a MAVLink wire fact, not a choice this module made, and getting it wrong latches a channel forever.** On channels 1..8, `0` means "release this channel back to the RC transmitter" and `65535` means "leave it alone, I'm not touching it." On channels 9..16, **both `0` and `65535` mean "ignore,"** and only `65534` (`EXTENSION_RELEASE`, `UINT16_MAX - 1`) means "release." The domain (`RcChannels`) stores one `RELEASE` constant everywhere; `RcChannels#wireValue(int oneBased)` is the single place that re-encodes a domain `RELEASE` into `EXTENSION_RELEASE` when `oneBased > BASE_CHANNEL_COUNT` (8). Do not scatter this branch across call sites — a second sentinel-aware call site is exactly how this class of bug reappears.
- **The accepted RC channel range is `[1,16]`, not `[1,18]`.** MAVLink message #70 (`RC_CHANNELS_OVERRIDE`) has 18 channel fields on the wire, but ArduPilot's own `RC_Channels`/override handling only reads channels 1..16 — 17/18 exist in the message (`ManualControlService` still sends them, always `IGNORE`, since some other autopilot family might read them) but `RcChannels` itself refuses to *carry* a 17th/18th value at all (`MAX_CHANNELS = 16` in the compact constructor). Enforced at the value-object boundary so a caller cannot construct a channel set that looks valid but is silently truncated at the wire — it fails at construction instead, in the caller's own module (see `vision-flight`'s `MODULE.md` for the domain-level half of this rule).
- **`VehicleClass` has a `SUBMARINE` slot (`MAV_TYPE` 12) that deliberately maps to no `VehicleKind`** (operator instruction, not an omission) — a later wave adding submarine support only needs a new `VehicleKind` row plus the already-correct `VehicleClass.of` mapping, not a fourth hand-maintained table.
- **A 16-character `param_id` does not fit in a 64-bit `discriminator`, so the correlation key *routes* and the service *verifies*.** `CorrelationKeys.paramDiscriminator` is FNV-1a 64 over the normalised name; `ParameterService` then compares `ParamValue.paramId()` to the requested name exactly, and a foreign name extends the wait (bounded, `MAX_FOREIGN_REPLIES = 8`) instead of being accepted. **The two halves are a pair — neither is optional.** Hashing alone would silently hand back a colliding parameter's value; verification alone has nothing to match on. FNV-1a specifically because its two constants can never drift, unlike `String#hashCode` (32-bit) or `Objects#hash` (explicitly no stability contract) — this value is a wire-matching convention shared between the requester and the RX path, so a JDK upgrade changing it would be a silent, fleet-wide hang.
- **The exact-name verification half is structurally unreachable from a loopback test.** Over a real link a wrong-named `PARAM_VALUE` hashes to a *different* key and never lands on our waiter at all, so no amount of `FakeVehicle` testing exercises the exact-name compare — only a genuine FNV-1a 64 collision would. `ParameterNameVerificationTest` substitutes a scripted `Correlator` that hands the service a reply on the key it asked for regardless of what that reply is named, which is exactly what a collision looks like from the service's side. Without that test the safety claim would be argued rather than asserted.
- **`normalizeParamId` must be applied on both sides.** The wire field is `char[16]`, un-terminated at exactly 16 characters and NUL-padded below that, so `"SR2_EXTRA2"` and the `"SR2_EXTRA2\0\0…"` that comes back are the same name only after normalisation. Both the `CorrelationKeys` table and `ParameterService` call the same function; a name longer than 16 chars is rejected at the API rather than silently truncated into a *different* parameter.
- **A `PARAM_SET` is never fire-and-forget, and the read-back compares floats exactly.** An autopilot clamps an out-of-range value and truncates a float into the parameter's real integer width **without refusing the write** — the echoed `PARAM_VALUE` is the only evidence of what it now holds. An epsilon here would hide precisely the small clamps that matter (a `0.1` stored as `0.0999`), so the compare is `==` on the two IEEE float32s off the same wire field; `MISMATCH` still carries what the vehicle actually holds.
- **`NO_REPLY` also means "I have no such parameter," and that conflation is the protocol's, not ours.** MAVLink gives an autopilot no way to refuse a `PARAM_REQUEST_READ` for a name it does not recognise — it simply says nothing. Unsupported, unreachable, and lost-on-the-link are one observation at this layer and are deliberately not guessed apart; a human-readable answer is a higher layer's job.
- **The full parameter download (`PARAM_REQUEST_LIST`) is a non-goal, not an omission.** Everything the platform needs names its parameters in advance; the stream-me-all-~1200 protocol, with its own missing-index gap detection and re-request loop, costs minutes of airtime on a 2.4 kB/s link.
- **No `api.ParameterGateway` was added.** `CommandGateway` exists because commands genuinely arrive from a broker; parameters reach `ParameterService` in-process through `adapter-mavlink`'s `VehicleConfigPort` implementation. Adding broker records now would be an untested seam with no caller.

## Status
- **L0** (`com.drones.mavlink`) — complete: `SysId`, `CompId`, `PeerId`, `VehicleClass`.
- **L1** (`transport`) — complete: `UdpListenLink`, `UdpTargetLink`, `TcpClientLink`, shared `UdpSocketIo`/`LinkPeers`/`Timeouts`, `LinkIntake`.
- **L2** (`codec`) — complete: `FrameReader`, `FrameWriter` (+ `sendTo`), `MavFrame`, `FrameSink` (implemented by `session.RoutingFrameSink`, not `FrameWriter`).
- **L3** (`session`) — complete: `MavlinkSession` (composition root), `PeerDirectory`, `Dispatcher` + `BoundedSubscriber`, `Correlator` + `CorrelationKeys`, `LinkHealth`, `TxScheduler`, `RoutingFrameSink`.
- **L4** (`service`) — real and tested: `RequestResponse` (shared retry/extension machine), `CommandService`, `HeartbeatService`, `ManualControlService`, `MessageIntervalService`, `ParameterService`, `CapabilityService`.
- **L4½** (`api`, broker seam) — real: `CommandGateway`/`DefaultCommandGateway`, dedupe-by-`correlationId`.
- **Mission and FTP protocols are provisioned but not implemented.** `MavlinkCoreSettings` carries `Mission`/`Ftp` config records and `CorrelationKeys` already has the four MISSION-message correlation rows landed (`MISSION_REQUEST`/`MISSION_COUNT`/`MISSION_ACK`/`MISSION_REQUEST_INT`), but no `MissionService` or `FtpService` class exists in this module yet.
- No RX-only restriction at this layer: every `MavlinkLink` implementation is bidirectional (`send` + `poll`); RX-only is a policy an adapter chooses to apply on top, not a constraint this module imposes.
- `vision-app`'s `ArchitectureTest` carries rules scoped to this module's `transport`/`codec` packages; they skip cleanly via `Assumptions` when `drone-link/mavlink-core` isn't on the classpath (no Maven dependency wires it onto `vision-app` by design).
