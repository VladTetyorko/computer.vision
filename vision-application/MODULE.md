# vision-application

Control-plane services orchestrating `vision-domain` ports: asset/device/stream management, the per-stream pipeline runtime, and usage/telemetry tracking.

**One interface + one `Default*` implementation per service area** — there is no inbound-port package and no `*UseCase` type. Commands and read models are top-level records in this package, not types nested in interfaces. See `.claude/skills/java-clean-code/SKILL.md`.

**Depends on:** vision-domain (only) · **Used by:** adapters (adapter-simulation, adapter-rtsp, adapter-publish-hls, adapter-discovery, adapter-cv-grpc, adapter-overlay, adapter-persistence), vision-app, vision-api
**Build/test:** `./mvnw -B -pl vision-application test`

## API surface

All types in the single package `com.drones.vision.application`.

- **Records (commands + read models):** `DeviceRegistration(name, capabilities, stream)`, `DeviceEdit(name, capabilities, stream)` (all-nullable partial edit, `DeviceEdit.NOTHING`), `AssetSpec(displayName, category, attributes, devices)`, `AssetEdit(displayName, category, attributes)` (partial, `AssetEdit.NOTHING`), `AssetSummary(asset, categoryName, status, lastUsedAt, lastKnownPosition)`, `AssetStatus` enum `{OFFLINE, STREAMING}`, `AssetDetails(summary, devices, recentUsages)`, `AssetDeletion(id, displayName, devicesDeleted, usagesRetained, streamsStopped)`, `ActiveStream(streamId, deviceId, startedAt)`, `ScanRequest(timeout, methods)` + `ScanRequest.defaults()`, `ScanResult(devices, failedMethods)`, `SimulationSpec(displayName, videoPath, latitude, longitude, autoStart, transport, plan)` (docs/CYCLES-PLAN.md §1b, §3, §7, §9; `transport` is a `SimulationTransport` — non-null-validated in the canonical 7-arg compact ctor, same idiom as `AssetSpec`/`DeviceRegistration`/`PipelineConfig`/`ScanRequest`'s creation-command records; a 6-arg convenience ctor defaults the newly-added `plan` to `null`, and a 5-arg convenience ctor defaults both `transport` to `SimulationTransport.DIRECT` and `plan` to `null` — mirroring `Asset`/`Device`'s (vision-domain) N-1-arg convenience constructors — **not** `AssetEdit`/`DeviceEdit`'s null-means-"leave unchanged" idiom, which only fits partial-*edit* records, not this creation command. **`videoPath` is nullable** (docs/CYCLES-PLAN.md §9, CU-a): `null` means a fully synthetic simulation with no video file at all — the compact ctor still rejects a genuinely *blank* (non-null, all-whitespace) string as distinct from absent, but only further validates a non-`null` path for blank/null shape, leaving filesystem checks (existence, regular file, readable) to `SimulationService`. The compact ctor also cross-validates `videoPath`×`transport`: a `null` `videoPath` is only valid with `transport=DIRECT` — `RTSP`/`MJPEG` throw `IllegalArgumentException("SimulationSpec transport " + transport + " requires a videoPath")` (→ 400), since a wired transport has no in-process renderer output to push over the wire), `SimulationTransport` enum `{DIRECT, RTSP, MJPEG}` (top-level, docs/CYCLES-PLAN.md §3, §5), `SimulatedAsset(assetId, streamId)` (`streamId` nullable when `!autoStart`), `TelemetryPlan(speedMps, mode, route)` (docs/CYCLES-PLAN.md §7, CT-a — a configurable flight plan for the synthetic telemetry track, converted by `DefaultSimulationService` into `SimulatedTelemetrySource`'s (adapter-simulation) `route`/`speedMps`/`routeMode` device options once `SimulationSpec#plan()` is non-null, in place of the bare `lat`/`lon` home-point options; validated: `speedMps` positive when given, `route` null-or-≥2 waypoints, defensively copied), `RouteMode` enum `{LOOP, BOUNCE, ONCE}` (top-level, docs/CYCLES-PLAN.md §7, mirrors `SimulationTransport`'s top-level-enum convention; **not** the same type as adapter-simulation's own `RoutePlan.RouteMode` — see that module's Gotchas for why), `Waypoint(latitude, longitude, altitudeMeters)` (docs/CYCLES-PLAN.md §7 — one route checkpoint; range-validated exactly like `GeoPosition` [vision-domain] despite the shape match, since it's deliberately a distinct type: `GeoPosition` is a derived "where is it now" reading, `Waypoint` is ordered route input), `UsageTimeline(usage, from, to, telemetry, detections)` (docs/MVP2-PLAN.md §R, R-a — `ReplayService`'s read model; `from`/`to` are the *resolved* window bounds, never `null` even when the caller passed `null`; `telemetry`/`detections` defensively copied), `FleetSummary(categories, assets, totalAssets)` (docs/MVP3-PLAN.md C-a — `FleetSummaryService`'s read model, `categories`/`assets` defensively copied), `CategoryCounts(categoryId, categoryName, total, active, deactivated, deleted, streaming)` (docs/MVP3-PLAN.md C-a — one `FleetSummary#categories()` row; all six counts non-negative, `streaming` ≤ `active`), `AssetAttention(assetId, displayName, categoryId, categoryName, lifecycle, streaming, streamId, batteryPercent, telemetryAgeMs, openEventCount)` (docs/MVP3-PLAN.md C-a — one `FleetSummary#assets()` row; `streamId`/`batteryPercent`/`telemetryAgeMs` nullable, `batteryPercent` range-validated [0,100] when present, `openEventCount` non-negative; deliberately **no `sourceState` field** — see `AssetAttention`'s own javadoc and this file's C-a paragraph below for why)

- **`AssetService`** (interface) → **`DefaultAssetService`**
  - `DefaultAssetService(AssetRepositoryPort, CategoryRepositoryPort, AssetUsageRepositoryPort, AuditTrailPort, DeviceService, StreamService)` — reaches devices through `DeviceService`, never the device repository, so a source's rules (stop its stream, write an audit line) live in one place
  - `Asset create(AssetSpec, Ownership, UserId actor)` — validates the category, registers each device, audits `CREATED`
  - `List<AssetSummary> assets()` / `assets(boolean includeDeleted)` — soft-deleted excluded by default; status from `streamService.activeDeviceIds()`
  - `AssetDetails details(AssetId)` — `NoSuchElementException` if unknown; up to 20 (`RECENT_USAGES_LIMIT`) most-recent usages
  - `Asset update(AssetId, AssetEdit, UserId)` — partial; audits `UPDATED` with changed fields only, and writes nothing when nothing changed
  - `Asset setState(AssetId, LifecycleState, UserId)` — idempotent; stops streams when leaving service; `DELETED → ACTIVE` throws `IllegalStateException` (restore first)
  - `AssetDeletion delete(AssetId, UserId)` — **soft**: marks the asset and its devices `DELETED`, keeps usages/telemetry; idempotent
  - `StreamId startStream(AssetId, DeviceId, PipelineConfig)` — `device` nullable: resolves the asset's single **active** `VIDEO`-capable device, `IllegalArgumentException` (naming candidates) if zero or >1; `IllegalStateException` if the asset is not in service
  - `void stopStream(AssetId)` — stops every active stream on the asset's devices; unknown asset is a no-op
  - `Asset assignDevice(AssetId, DeviceId, UserId actor)` (docs/CYCLES-PLAN.md §8's pinned contract) — the device must exist (`NoSuchElementException` otherwise) and not be soft-deleted (`IllegalArgumentException` otherwise: restore it first); `AssetRepositoryPort.findByDeviceId` must be empty — a device already owned by *any* asset (including this one) is refused with `IllegalStateException` naming the owning asset (→409); adds the device via `Asset.withDevices`, audits `UPDATED`
  - `Asset unassignDevice(AssetId, DeviceId, UserId actor)` (docs/CYCLES-PLAN.md §8's pinned contract) — the device must currently belong to this asset (`IllegalArgumentException` otherwise); removing it must leave at least one device, or `IllegalStateException` (the reduced set is built *before* the `Asset.withDevices` call, since the record's own compact ctor is what actually enforces non-empty); audits `UPDATED`. The device itself is untouched (not soft-deleted) — unassigning just breaks the asset↔device link, mirroring how `DeviceService#delete` never needs an asset-side special case

- **`CategoryService`** (interface) → **`DefaultCategoryService`**
  - `DefaultCategoryService(CategoryRepositoryPort)`
  - `List<DeviceCategory> categories()` — thin pass-through over `CategoryRepositoryPort.findAll()`, sorted by `CategoryId.slug()` for a stable UI order

- **`DeviceService`** (interface) → **`DefaultDeviceService`**
  - `DefaultDeviceService(DeviceRepositoryPort, StreamService, AuditTrailPort, EventPublisherPort)`
  - `Device register(DeviceRegistration, UserId actor)` — assigns `DeviceId.random()`, saves, publishes `DEVICE_ONLINE`, audits `CREATED`
  - `List<Device> devices()` / `devices(boolean includeDeleted)`; `Optional<Device> find(DeviceId)`
  - `Device update(DeviceId, DeviceEdit, UserId)` — partial; a running stream keeps its settings until the next start
  - `Device setState(DeviceId, LifecycleState, UserId)` — idempotent; stops the device's stream when leaving service; `DELETED → ACTIVE` throws `IllegalStateException`
  - `Device delete(DeviceId, UserId)` — **soft**; the device stays a member of its asset, so removing an asset's last source is never refused

- **`ReplayService`** (interface) → **`DefaultReplayService`** — flight replay (docs/MVP2-PLAN.md §R, R-a/R-a2): the read side behind `GET /api/usages/{usageId}/timeline` (vision-api)
  - `DefaultReplayService(AssetUsageRepositoryPort, TelemetryRepositoryPort, DetectionRepositoryPort)` (docs/MVP2-PLAN.md R-a2 — up from 2 args; the wiring bean lives in `vision-app`'s `WiringConfiguration#replayService`)
  - `UsageTimeline timeline(UsageId, Instant from, Instant to, int maxPoints)` — `NoSuchElementException` for an unknown usage; `IllegalArgumentException` for non-positive `maxPoints` or a resolved `to` before `from`. `from`/`to` are each independently nullable, defaulting to the usage's own `startedAt`/`endedAt` — `to` defaults to `Instant.now()` when the usage is still open (no `endedAt`). `maxPoints` is silently clamped to `MAX_POINTS_CEILING` (2,000; package-private) if the caller asks for more — never an error, just a cap
  - **Telemetry**: fetched via `TelemetryRepositoryPort.findByUsage(usageId, TELEMETRY_FETCH_LIMIT)` (package-private, 20,000) — see Gotchas for why this is a fetch-then-filter workaround, not a real time-bounded query — then filtered to `[from, to]` inclusive both ends, sorted by `Telemetry#at()`, and thinned to `maxPoints` (see below)
  - **Detections** (docs/MVP2-PLAN.md R-a2 — real now, was always empty under R-a): when `usage.streamId()` is non-`null`, queried directly via `DetectionRepositoryPort.query(new DetectionQuery(streamId, windowFrom, windowTo, null, DETECTION_FETCH_LIMIT))` (package-private, 20,000) — a genuinely time-bounded query, unlike telemetry's fetch-then-filter workaround — then re-sorted ascending by `DetectionResult#capturedAt()` (the port's real implementations return newest-first) and thinned exactly like telemetry. A `null` `streamId()` (legacy/streamless usage) short-circuits to `List.of()` without touching the port at all — see Gotchas for both series' truncation-direction caveats
  - `static <T> List<T> thin(List<T> items, int maxPoints)` (package-private, generic, used for both series) — equidistant-index thinning: if `items.size() <= maxPoints`, returns `items` unchanged (no thinning needed, exact identity — this is how "fewer points than max" and "exactly max" both come out lossless); otherwise selects `maxPoints` indices via `round(i * (n-1) / (maxPoints-1))` for `i` in `0..maxPoints-1`, which always lands exactly on index `0` and index `n-1` — the algorithm's "always keeps first and last" guarantee — and is deterministic (same input + `maxPoints` always produces the same output, no time-based tie-breaking). `maxPoints <= 1` is a degenerate case with no room for both a first and last point: returns a single-element list holding just the first item
- **`FleetSummaryService`** (interface) → **`DefaultFleetSummaryService`** — the manager dashboard's single aggregated read (docs/MVP3-PLAN.md C-a): the read side behind `GET /api/fleet/summary` (vision-api)
  - `DefaultFleetSummaryService(AssetService, StreamService, UsageTracker, DetectionEventRepositoryPort)` — composes existing services/ports rather than reaching past them to repositories directly, so every rule they already enforce (soft-delete visibility via `AssetService#assets`, streaming derivation) applies here without duplication
  - `FleetSummary summary(boolean includeArchived)` — `includeArchived` passed straight through as `AssetService#assets`'s `includeDeleted`
    - **Category counts**: folded over *every* in-scope asset (never capped), one `CategoryCounts` row per category actually present, sorted by `CategoryId#slug()`
    - **Per-asset attention rows**: sorted by `displayName` (case-insensitive) and capped at `MAX_ASSETS_IN_SUMMARY` (package-private, 500) — `FleetSummary#totalAssets()` always reports the true, uncapped count, so a caller can detect truncation (`assets().size() < totalAssets()`). True pagination (offset/cursor) was judged unnecessary for this cycle's "capped/paged for 100+" done-criterion
    - `streaming`/`streamId` come from `AssetSummary#status()` (already `STREAMING`/`OFFLINE`) plus a `StreamService#streams()`-derived `DeviceId → StreamId` map (first of the asset's own `devices()` that matches, order unspecified — today's flows never have more than one simultaneously-streaming device per asset anyway)
    - `batteryPercent`/`telemetryAgeMs` come from `UsageTracker#latestTelemetry(AssetId)` (new for this task — see that class's own entry below); both `null` when the asset has never reported telemetry
    - `openEventCount` scans `DetectionEventRepositoryPort#findRecent(null, OPEN_EVENTS_SCAN_LIMIT)` (package-private, 2,000 — across every stream, newest-first by `lastSeen`) and counts `state()==OPEN` events per `assetId()`; honestly bounded, not exhaustive — see the constant's own javadoc for the edge case this leaves
    - **No `sourceState` field** (docs/MVP3-PLAN.md C-a's own instruction: omit and document rather than fake) — `EventPublisherPort` is write-only (no read/query side, see vision-api/MODULE.md's Gotchas) and `SupervisedPublisher`'s outage/backoff state is private to `DefaultStreamService`'s per-stream bookkeeping, never exposed through `StreamService`; there is no honest "reconnecting" signal to read today
- **`DiscoveryService`** (interface) → **`DefaultDiscoveryService`**
  - `DefaultDiscoveryService(List<DeviceDiscoveryPort> ports)` — indexed by `port.method()` into an immutable map
  - `ScanResult scan(ScanRequest request)` — one virtual thread per requested port; overall deadline = `timeout` + a package-private 200ms grace period (`GRACE_PERIOD`); per-adapter exception/timeout isolated into `failedMethods`, not thrown; throws `IllegalArgumentException` only for an unknown requested method key
  - Dedup is two-pass: (1) exact `(method, address)` match within one scan, then (2) cross-method merge — candidates are grouped by network identity (`URI.getHost()`, case-insensitive, when present; exact address when the host is null, e.g. `v4l2` `file:` URIs) and a group is merged into one `DiscoveredDevice` only if it spans **2+ distinct methods** (a same-method group, even sharing a host, passes through unmerged). Merged fields: `method` = distinct methods sorted alphabetically and joined with `"+"` (e.g. `"mdns+onvif"`, deterministic regardless of discovery order); `name` = the first candidate, in priority order (`onvif` > `mdns` > others), whose name isn't just the address/host literal, else the top-priority candidate's name; `suggestedStream`/`address` = the first candidate (priority order) with an `rtsp`-protocol stream, else the first with any non-null stream (`address` follows whichever candidate supplied the stream, else the top-priority candidate's own address); `suggestedCategory` = first non-null (priority order); `details` = union of all candidates' maps, with a key contributed by 2+ distinct methods namespaced `"<method>.<key>"` for every contributing candidate (symmetric, not just the losing side). See `DefaultDiscoveryService.mergeGroup`/`mergeDetails` javadoc for the full rule set.

- **`SimulationService`** (interface) → **`DefaultSimulationService`** — the one-call, zero-hardware simulation entry point (docs/CYCLES-PLAN.md §1b, §3, §5, §9)
  - `DefaultSimulationService(AssetService, CategoryRepositoryPort, FeedTransmitterRegistry)` — builds one `AssetSpec` and delegates creation/streaming to `AssetService`, so every rule it already enforces (category validation, audit, device registration) applies here without duplication; `FeedTransmitterRegistry` backs `SimulationTransport.RTSP`/`MJPEG` (docs/CYCLES-PLAN.md §5 generalized the original single `FeedTransmitterPort` dependency once a second transmit protocol existed — see `FeedTransmitterRegistry` below)
  - `SimulatedAsset simulate(SimulationSpec, Ownership, UserId actor)`:
    - Validates `spec.videoPath()` via `java.nio.file` — must exist, be a regular file, and be readable — else `IllegalArgumentException` naming the resolved absolute path; **skipped entirely when `spec.videoPath()` is `null`** (docs/CYCLES-PLAN.md §9, CU-a — a fully synthetic simulation), which `spec`'s own compact ctor guarantees only happens with `transport=DIRECT`
    - Requires category `simulated` to exist in `CategoryRepositoryPort` (seeded by devsupport in vision-app) — else `IllegalStateException("category 'simulated' is not seeded")`
    - Derives the display name from the video file's name (extension stripped) when `spec.displayName()` is null/blank — or, for a `null`-`videoPath` spec, the constant `SYNTHETIC_DISPLAY_NAME` ("Synthetic drone"), since there is no file name to derive one from (docs/CYCLES-PLAN.md §9, CU-a)
    - Registers exactly two devices: a video device and a telemetry device (`"<name> · telemetry"`, protocol `"sim"`, a descriptive (never looked up) `sim://<slug>-telemetry` URI, `Capability.TELEMETRY` — the telemetry device is what `SimulatedTelemetrySource` (adapter-simulation) opens). Telemetry device options (built by the private `telemetryDevice` helper, docs/CYCLES-PLAN.md §7, CT-a): when `spec.plan()` is non-null **and** carries a route, the plan wins over the bare `lat`/`lon` fields entirely — the route's first waypoint doubles as the `lat`/`lon` start position (so even a hypothetically-malformed route string would make the adapter's circular fallback center on the intended start, not its own unrelated default), the route itself is serialized `lat,lon[,altM];…` (`Locale.ROOT`-formatted, since the format's own field separators are `,`/`;`), and `speedMps`/`routeMode` (the latter lower-cased) are set only when the plan gives them (letting the adapter's own defaults apply otherwise). Without a route-carrying plan, behavior is unchanged from before CT-a: bare `lat`/`lon` options are set only when `spec` provides them. The video device depends on `spec.transport()` and, for `DIRECT`, on whether `spec.videoPath()` is `null`:
      - `DIRECT` with a path: `"<name> · video"`, protocol `"file"`, `uri = videoPath.toUri()`, options `{"loop":"true"}`, `Capability.VIDEO` — unchanged from docs/CYCLES-PLAN.md §1b.
      - `DIRECT` with **no** path (docs/CYCLES-PLAN.md §9, CU-a — the private `syntheticVideoDevice` helper): `"<name> · video"`, protocol `"sim"` (same `SIM_PROTOCOL` constant/renderer the telemetry device already uses — `SimulatedVideoSource`, adapter-simulation), `uri = "sim://<slug>"` (no `-telemetry` suffix, `slug` shared with the telemetry device's own URI derivation), **no `loop` option** (the synthetic renderer runs forever on its own, nothing to loop), `Capability.VIDEO`. `AssetSpec#attributes` gets no `source` key in this case (there is no file path to record).
      - `RTSP`/`MJPEG` (docs/CYCLES-PLAN.md §3, §5, always a non-`null` `videoPath` — `spec`'s compact ctor forbids the combination otherwise): a fresh `FeedId.random()`; `FeedSpec(protocol, videoPath.toUri(), Map.of("loop","true"))` (`protocol` = `"rtsp"`/`"mjpeg"`); `feedTransmitters.transmitterFor(feedSpec)` selects the adapter (`IllegalArgumentException` naming the protocol if none supports it — see `FeedTransmitterRegistry`), then `transmitter.start(feedId, feedSpec)` and the video device is registered against the *returned* `StreamDescriptor` — for `RTSP` only, augmented with `options.put("timeout","2000000")` (`StreamDescriptor` is immutable, so a new one is built) — the RX-side contention fix, see Gotchas; `MJPEG`'s descriptor is registered as-is, no augmentation (the mjpeg pair has no such contention, see adapter-mjpeg/MODULE.md).
    - `attributes` on the created `AssetSpec` includes `source` = the resolved absolute video path, or is empty when `spec.videoPath()` is `null` (docs/CYCLES-PLAN.md §9, CU-a)
    - `autoStart` → (for `RTSP` only) a short fixed delay (see Gotchas), then `assetService.startStream(assetId, null, PipelineConfig.defaults())`; `SimulatedAsset.streamId()` is `null` otherwise
    - Tracks `AssetId -> (FeedTransmitterPort, FeedId)` (private `TrackedFeed` record) in a `ConcurrentHashMap` for every wired-transport asset (untracked for `DIRECT`) — the transmitter is remembered per asset (not just the id) so `stop` calls it back on the *same* adapter that started it, now that more than one transmitter can be registered; if `assetService.create`/`startStream` throws after a feed was started, the feed is stopped (and any partial tracking removed) before rethrowing — no orphaned transmitters
  - `void stop(AssetId)` (docs/CYCLES-PLAN.md §3): `assetService.stopStream(assetId)` always, then — if a feed is tracked for the asset — its `TrackedFeed.transmitter().stop(feedId)` and untrack. Idempotent; unknown/untracked/already-stopped asset is a no-op, mirroring `AssetService#stopStream`'s semantics

- **`FeedTransmitterRegistry`** (docs/CYCLES-PLAN.md §5) — TX-side mirror of `VideoSourceRegistry`
  - `FeedTransmitterRegistry(List<FeedTransmitterPort> transmitters)` — defensively copied to an immutable list
  - `FeedTransmitterPort transmitterFor(FeedSpec)` — first adapter whose `supports()` is true; throws `IllegalArgumentException` naming the unsupported protocol otherwise (not `UnsupportedProtocolException` — that type's message is `VideoSourcePort`-specific)

- **`DetectionEventEngine`** (package-private, final, no interface — docs/MVP2-PLAN.md §E, E-a) — per-stream debounce rule engine: collapses a tracked label's consecutive-qualifying-`DetectionResult` streak into an open/close `DetectionEvent` lifecycle
  - `DetectionEventEngine(StreamId, DeviceId, EventRuleConfig, UsageTracker, DetectionEventRepositoryPort)` — `UsageTracker` nullable (no geolocation/asset resolution when absent, same convention as `DefaultStreamService`'s own field of the same name); `DetectionEventRepositoryPort` required
  - `void accept(DetectionResult)` (`synchronized`, mirrors `DetectionExtrapolator`'s threading note) — for every label in `EventRuleConfig#labels()`: a result whose peak confidence for that label is ≥ `confidenceThreshold` counts toward a consecutive streak; reaching `consecutiveToOpen` opens an event (`firstSeen` = the streak's first qualifying result, not the opening one); while already open, each further qualifying result advances `lastSeen`/raises `peakConfidence` (`DetectionEvent#withObservation`); a non-qualifying result resets the streak count to 0 and, if an event is open, checks the gap since its `lastSeen` against `absenceToClose` — reaching it closes the event (`DetectionEvent#closed()`, `lastSeen` left exactly as the last real observation, not moved forward). Every timestamp comes from `DetectionResult#capturedAt()`, never wall-clock time — no clock injection needed for tests. `assetId`/`position` are resolved **once, at open time only**, via `usageTracker.resolveAsset(deviceId)`/`usageTracker.latestPosition(assetId)` — frozen on the event thereafter even while it stays open and the asset keeps moving. Each tracked label is fully independent (its own streak/open-event state); labels outside `EventRuleConfig#labels()` are never touched at all.
- **`SupervisedPublisher<T>`** (package-private, final, generic, no interface — docs/MVP2-PLAN.md §S, S-a) — the source-supervision mechanism behind "a started stream survives source failures; only an explicit Stop ends it." A `Flow.Publisher<T>` decorator wrapping a re-openable source (`VideoSourcePort`/`TelemetrySourcePort`), used by both `DefaultStreamService#start` (video) and `UsageTracker#subscribeTelemetry` (telemetry) — one shared class rather than two near-identical ones, since the backoff/retry/stop machinery is identical in shape between them
  - `SupervisedPublisher(Supplier<Flow.Publisher<T>> opener, Consumer<Throwable> onOutageBegan, ScheduledExecutorService scheduler)` — production ctor, uses `INITIAL_BACKOFF_NANOS`(1s)/`MAX_BACKOFF_NANOS`(30s); a package-private 5-arg ctor takes explicit backoff bounds instead (test seam, mirrors `StreamPipeline`'s own `LongSupplier`-taking test ctor) — both `DefaultStreamService`/`UsageTracker` gained their own matching package-private test-seam constructors purely to thread smaller bounds through for fast tests, production always uses the defaults
  - `subscribe(Flow.Subscriber<? super T> subscriber)` — opens the source (`opener.get()`) and forwards `onSubscribe`/`onNext` straight through to `subscriber`, untouched; `onError`/`onComplete` are intercepted, **never forwarded downstream** — the wrapped subscriber (`StreamPipeline`/`UsageTracker`'s `TelemetrySubscriber`) never sees a source ending at all, only the normal traffic. On interception: `onOutageBegan` runs **exactly once per outage** (not once per failed retry — mirrors `StreamPipeline`'s own detection-outage and `MediamtxStreamPublisher`'s own publish-outage "one log/event per outage" convention, chosen for consistency with those two pre-existing precedents), then a retry is scheduled after the current backoff, which then doubles (capped). The outage ends — and backoff resets to `initialBackoffNanos` — the moment an item actually flows again (`onNext`), not merely once a reopen attempt starts (a source can fail again immediately after a superficially successful resubscribe)
  - `stop()` — cancels any pending scheduled retry (`ScheduledFuture#cancel(false)`) and permanently disables further retries via an `AtomicBoolean`; idempotent; does **not** close whatever source/subscription is currently open — that stays the caller's own responsibility, unchanged from the unsupervised case
  - A synchronous exception from `opener.get()` itself (not just an async `onError`) is caught and funneled through the exact same `ended(...)` path — otherwise a `ScheduledExecutorService` silently swallows an uncaught exception from a fire-and-forget scheduled `Runnable`, permanently and invisibly ending retries
  - **What it deliberately doesn't do:** publish any event itself — `onOutageBegan` is the caller's own callback (`DefaultStreamService` publishes `PIPELINE_ERROR`; `UsageTracker` passes a no-op, see its own entry below for why)
- **`DetectionExtrapolator`** (package-private, final, no interface — docs/CYCLES-PLAN.md §12, CP-c) — internal collaborator of `StreamPipeline`, one instance per pipeline; smooths burned-in boxes between completed inferences instead of freezing them at the latest result until the next one lands
  - `void accept(DetectionResult result)` — keeps only the two most recent results (previous `P`, latest `L`); a `result.frameSequence()` &le; the current `L`'s is ignored (detection completions can land out of order relative to sampling order)
  - `List<Detection> at(Instant t)` — no result yet: `List.of()`. Only `L` (or `L`'s detections are empty): `L.detections()` unchanged. Both `P` and `L`, non-empty `L`: greedy nearest-box-center matching of `L`'s detections to `P`'s (same `label`, gated at **0.15** normalized center distance, each side matches at most once); a matched detection's center is extrapolated along `Δcenter/Δt` (velocity) to `min(t, L.capturedAt()+800ms)` (`MAX_EXTRAPOLATION_MILLIS`, package-private) — `L`'s width/height are kept, `x`/`y` clamped to `BoundingBox`'s `[0,1]` per-component range; a zero/negative `Δt` between `P` and `L` (degenerate/duplicate timestamps) skips extrapolation entirely (returns `L.detections()`). Unmatched `L` detections pass through as-is; `P`-only detections are dropped. Never throws, never returns `null`.
  - Both methods `synchronized` — called at most once per sampled/published frame by `StreamPipeline`, never on a hot loop.

  - **Overlay burn-in** (docs/MVP1-PLAN.md §C8 bullet 2, smoothed per docs/CYCLES-PLAN.md §12 CP-c, optional per docs/MVP2-PLAN.md §V, V-e, `overlayIfNeeded`): every completed detection result feeds a private `DetectionExtrapolator` (`extrapolator.accept(result)`, same call site as the `latestDetections` update) — this happens **unconditionally**, regardless of `overlayBurnIn`, since it's cheap bookkeeping over at most two results, not the cost the flag exists to avoid (see below). Before every `streamPublisherPort.publish`, if `overlayPort != null` **and** `config.overlayBurnIn()` is `true` **and** `extrapolator.at(frame.capturedAt())` is non-empty, the frame is rendered via `overlayPort.render(new AnnotatedFrame(frame, extrapolator.at(frame.capturedAt()), null))` and the renderer's returned instance is published instead of the raw frame; otherwise (no `overlayPort`, burn-in disabled, or nothing to draw yet) the raw frame is published unchanged. Detection sampling always runs against the **raw** frame, never the rendered one. Telemetry is always passed as `null` here — this pipeline has no telemetry input yet, so `PipelineConfig#overlayTelemetry()`'s OSD gate cannot activate until a later task plumbs one in; detections-only burn-in is what §C8 ships, and `overlayBurnIn` is the single decision point that will gate OSD burn-in identically once that lands, since both share the same `overlayIfNeeded` call site. A renderer exception is swallowed (never a pipeline failure): the raw frame publishes instead, and a plain boolean latch (`overlayFailureLogged`, reset on the next successful render) limits the `WARNING` log to once per failure run rather than once per frame — rendering itself is still retried on every frame (unlike detection's outage/backoff skip policy), only the logging is throttled. **What `overlayBurnIn=false` actually skips** (V-e, verified by reading `overlayIfNeeded` rather than assumed): the `extrapolator.at(...)` lookup itself (box matching/velocity-extrapolation math), `OverlayPort#render`'s Java2D work (decode/allocate a fresh `BufferedImage`, draw boxes/OSD, re-encode), and the extra `VideoFrame` instance `render` returns — every publish instead falls straight through to the already-decoded raw frame from the source. It does **not** skip `extrapolator.accept` (still runs, per above) or detection sampling/persistence/event-engine feeding, all of which are independent of burn-in.
  - **Debounced detection events** (docs/MVP2-PLAN.md §E, E-a): every completed result — empty or not — also feeds `eventEngine.accept(result)` when one is configured, right alongside `extrapolator.accept(result)` in `onDetectionResult`. Empty results matter here (unlike the `DETECTION` event/persistence path below, which only fires for non-empty ones) because an empty result is exactly what "absent" looks like to `DetectionEventEngine`'s debounce rule. This is a read-only observer — the engine never influences what gets published or returned from this class.
  - **Two distinct failure policies** (docs/MVP1-PLAN.md §C7 bullet 3 — a failing/absent CV service can never kill or degrade the video path):
    - **Source errors** (`onError`) and any `RuntimeException` thrown synchronously while publishing are fatal, unchanged from before: one `PIPELINE_ERROR` event, then `close()` (cancels the subscription, signals `streamEnded`).
    - **Detection failures** (an exceptionally-completed `CompletionStage` from `DetectionPort#detect`, including timeouts) never close the pipeline and never touch the video path — a failed frame's detections are simply absent. The first failure enters a detection **outage**: exactly one `PIPELINE_ERROR` event (message names the cause), and until recovery, sampled frames are withheld from `DetectionPort` entirely — skipped as an in-flight-bound skip is, and likewise never counted against `maxInFlightInferences` or queued — while an exponential backoff counts down: `INITIAL_BACKOFF_NANOS`=1s, doubling on each failed probe, capped at `MAX_BACKOFF_NANOS`=10s (both package-private). Once the backoff deadline passes, **exactly one probe inference** is attempted (an internal `probeInFlight` flag, guarded together with the deadline check under one `synchronized` block, prevents a second concurrent probe even if several sampled frames land inside the same window): success ends the outage (logged via `System.Logger` at `INFO`, no second event) and detection resumes normally; failure doubles the backoff and the outage continues under the single original event. Subsequent failures during an outage — whether the probe's or from a call already in flight when the outage began — are counted (`outageFailureCount`, surfaced in the recovery log line) but never raise a second event; only a failed **probe** doubles the backoff, so a stray already-in-flight failure can't perturb a backoff a probe has already advanced. Any successful detection, in or out of an outage, resets the backoff to its initial interval. A later, independent outage raises its own new single event.
    - All outage/backoff state (`inOutage`, `probeInFlight`, `backoffNanos`, `nextProbeAtNanos`, `outageFailureCount`) is plain (non-volatile/non-atomic) fields guarded by one dedicated lock object (`outageLock`), not volatile/`Atomic*` like the frame-cadence fields — unlike `onNext`'s per-signal serialization, outage-entry/probe decisions and detect() completion callbacks race genuinely (completions can land on an arbitrary executor thread), and the relevant checks (e.g. "claim the probe slot AND read the deadline") must be one atomic step; a `synchronized` block was chosen over hand-rolled volatile-publish ordering for reviewability, and contention is a non-issue since it's only entered around sampled-frame decisions and (in/out of) outage transitions, never on the hot per-frame publish path. All backoff timing runs off the same injectable `LongSupplier nanoTimeSource` seam as the frame-cadence measurement, so tests drive it synthetically (see Gotchas).

## Conventions
- No Spring/framework imports anywhere in this module (Spring only appears in adapters/vision-app/vision-api).
- **The acting user is a method parameter (`UserId actor`), never a constructor dependency** — it varies per request; the API edge resolves it from the token and passes it down.
- Constructor injection only; every collaborator is wrapped in `Objects.requireNonNull(x, "x must not be null")` **except** `DefaultStreamService`'s `usageTracker`/`overlayPort`/`detectionEventRepositoryPort`/`liveUpdatePublisherPort`, `StreamPipeline`'s `overlayPort`/`eventEngine`/`assetId`/`liveUpdatePublisherPort`, `UsageTracker`'s own `liveUpdatePublisherPort`, and `DetectionEventEngine`'s own `usageTracker`, all deliberately left nullable so the classes stay trivially testable/usable without those collaborators.
- Injected collections are defensively copied at construction (`List.copyOf`/`Map.copyOf`): `VideoSourceRegistry.sources`, `DefaultDiscoveryService.portsByMethod`, `UsageTracker.telemetrySources`.
- Virtual threads: `DefaultDiscoveryService.scanAsync` starts one `Thread.ofVirtual()` per requested discovery port per scan call; a hung adapter's thread is never tracked or interrupted (cheap + daemon, so it never blocks JVM shutdown). Same idiom, docs/MVP2-PLAN.md §S, S-a: `DefaultStreamService#stop`/`UsageTracker#unsubscribeTelemetry` each fire one `Thread.ofVirtual()` to run the actual (possibly slow) `close()` calls off the caller's thread.
- Concurrency primitives: `ConcurrentHashMap` for shared registries (`DefaultStreamService.activeStreams`/`streamByDevice`, `UsageTracker.trackingByAsset`); `AtomicInteger`/`AtomicBoolean` for pipeline counters/close-flags; `volatile` for single-writer/many-reader fields (`StreamPipeline.latestDetections`/`subscription`). docs/MVP2-PLAN.md §S, S-a added this module's first `ScheduledExecutorService` usage (previously only in adapters, e.g. `adapter-simulation`'s per-instance schedulers) — `DefaultStreamService`/`UsageTracker` each own **one** dedicated daemon-thread `Executors.newSingleThreadScheduledExecutor`, shared across every stream/subscription that class supervises, scheduling `SupervisedPublisher`'s reopen retries; see that class's own Gotcha entry for why one shared thread per service is judged sufficient rather than per-stream.
- `Flow.Subscriber` pattern used identically in two places — `StreamPipeline` (video) and `UsageTracker.TelemetrySubscriber` (telemetry) — both request exactly one item at a time and re-request after processing.
- Per-asset mutable state in `UsageTracker` (`Tracking`) is synchronized on the `Tracking` instance itself, not a module-wide lock — different assets' start/stop/telemetry never contend.

## Gotchas
- `StreamPipeline`'s sampling rate is driven by a *measured* source cadence (EWMA of inter-frame-arrival deltas), not a fixed assumption — but the measurement only starts being trusted after `WARMUP_FRAMES`=5 frames, and the EWMA is seeded directly from the first observed delta (not blended toward the 30fps fallback) so a constant-cadence source converges immediately once warmup ends, rather than drifting in slowly. A source whose rate changes *during* a stream still tracks (recomputed every frame), but a source that starts, drifts wildly, then stabilizes will have a skewed effective inference FPS for its first 5 frames.
- In-flight inference bound is **skip-not-queue**: once `maxInFlightInferences` in-flight calls are outstanding, `StreamPipeline` drops the sampled frame outright rather than buffering it — a slow `DetectionPort` degrades detection *rate*, never blocks the video path. Frames skipped because of an in-flight detection outage's backoff window are likewise never counted as in-flight — they never reach `inFlightInferences` at all, only the separate `probeInFlight` flag applies to them.
- `StreamPipeline.close()`/source-error handling both funnel through one `AtomicBoolean` CAS; a detection completing *after* close is a silent no-op regardless of outage state (`closed.get()` re-checked inside the `whenComplete` callback, before any outage/backoff bookkeeping runs).
- **A detection failure never closes `StreamPipeline`** (docs/MVP1-PLAN.md §C7 — changed from the pre-C7 behavior where any detection failure closed the pipeline exactly like a source error). Only `onError` (source) and a synchronous `RuntimeException` from `publish()`/the sampling call are still fatal. Get this wrong and a flaky/absent CV service takes the whole video path down with it, defeating the point of the outage/backoff machinery.
- **One `PIPELINE_ERROR` event per outage, not per failed frame.** The event fires exactly once, on the transition into outage (`inOutage` false→true); every failure after that — including every failed retry probe — is silently counted (`outageFailureCount`) and never raises a second event. Don't be tempted to move the event into the probe-failure branch "for visibility" — that reintroduces per-frame spam under a sustained outage, exactly what this design avoids.
- **Only a failed *probe* doubles the backoff** — a detection call that was already in flight (not gated by the outage) when the outage began can still complete with a failure afterward, and that failure must be counted silently *without* touching `backoffNanos`/`nextProbeAtNanos`, or a slow straggler could stomp a backoff a probe already advanced.
- **Exactly one probe in flight at a time.** `probeInFlight` and the deadline check (`nextProbeAtNanos`) are read/claimed together inside one `synchronized (outageLock)` block in `outageDecision()` — checking them as two separate lock-free reads would let a racing thread observe `inOutage` freshly `true` before its paired backoff fields are visible, either starting a second concurrent probe or skipping the very first backoff window outright.
- `DefaultStreamService` allows only one active stream per device (Phase 0 scope) — starting a second throws `IllegalStateException` rather than replacing the existing stream.
- `UsageTracker` drops a telemetry sample that arrives after its usage has closed (`tracking.usage == null`) instead of reopening a new usage for it.
- **`UsageTracker.onStreamStarted`'s `streamId` param is only ever recorded on the call that opens the usage** (docs/MVP2-PLAN.md R-a2) — for an asset with several devices, only the **first** device's stream is ever visible on `AssetUsage#streamId`; a second/third device starting later (while the usage is already open) passes its own `streamId` in, but that argument is simply discarded on that path. This mirrors the pre-existing "first currently-active device opens the usage" rule exactly — no new asymmetry, just extended to a new field.
- **Overlay rendering is now wired in** (docs/MVP1-PLAN.md §C8 bullet 2 — supersedes the earlier "not wired in yet" note): `StreamPipeline`'s `overlayPort` is nullable, so a caller that never passes one (or explicitly passes `null`, `DefaultStreamService`'s own default) sees zero behavior change. Telemetry burn-in specifically is **still not reachable** — `StreamPipeline` has no telemetry input, so `AnnotatedFrame`'s `telemetry` component is always `null` here regardless of `PipelineConfig#overlayTelemetry()`; only detections-only burn-in is live. Adding a telemetry input to `StreamPipeline` (and gating on `overlayTelemetry()`) remains a later task.
- **`StreamPipeline` now has two distinct detection surfaces — do not conflate them** (docs/CYCLES-PLAN.md §12, CP-c): `latestDetections()` is the raw, most-recently-completed result (unchanged since C7/C8, and what REST/audit/persistence consumers should read), while overlay burn-in renders `DetectionExtrapolator.at(frame.capturedAt())` — a *smoothed* view with the same element count as `latestDetections()` (every `L` detection yields exactly one output, matched-and-extrapolated or unmatched-as-is; `P`-only detections are simply never in `L`'s list to begin with) but whose **positions** can differ (a matched detection's box is moved toward its predicted position, frozen once `MAX_EXTRAPOLATION_MILLIS` past `L.capturedAt()` elapses) while `latestDetections()` stays exactly as last set either way. Wiring a new consumer of "what's currently detected" onto the wrong one of these two is an easy, silent bug — only the overlay renderer wants the extrapolator's output.
- **`DetectionExtrapolator.accept`'s out-of-order guard is `frameSequence` &le;, not `<`** — a detection completion whose `frameSequence` equals the current latest's (e.g. a duplicate/retried completion for the same sampled frame) is ignored exactly like a strictly-older one, not treated as a legitimate update. This mirrors `StreamPipeline`'s own tolerance for inference completions racing/landing out of order (see the detection-outage Gotchas above) — sampling order and completion order are not guaranteed to match once more than one inference can be in flight (`PipelineConfig#maxInFlightInferences`).
- `DefaultDiscoveryService` cross-method merge only triggers for a group spanning 2+ *distinct* methods — two candidates from the *same* method that happen to land in the same network-identity group (e.g. two mDNS services on one host) are intentionally left unmerged, passed through exactly as the exact-`(method,address)` dedup pass would have produced them.
- `DiscoveredDevice.method`'s compact constructor only rejects blank/null — no single-token or lower-case pattern (unlike `StreamDescriptor.protocol` or `CategoryId.slug`) — so a merged, `"+"`-joined value like `"mdns+onvif"` is valid without any `vision-domain` change. `DeviceDiscoveryPort.method()`'s own javadoc ("stable lower-case key") still applies to each *individual* port's method key, not to this merged/derived field.
- `UsageTracker.TelemetrySubscriber.onError` is an empty method (comment-only) by design — a telemetry source failure is completely silent, not even logged, because best-effort telemetry must never affect stream/usage lifecycle.
- **`DefaultSimulationService`'s RX-side timeout augmentation is not optional, and is RTSP-only.** `FfmpegVideoSource`'s default RTSP `timeout`/`rw_timeout` is 10s; running it (RX) in the same JVM as `RtspFeedTransmitter` (TX) against the same mediamtx path — exactly what `transport=RTSP` creates — causes the transmitter's own grab/record loop to stall for ~10s before mediamtx drops the connection and the transmitter's next write fails with EPIPE. `DefaultSimulationService.RTSP_RX_TIMEOUT_MICROS` ("2000000" = 2s) is added to the transmitter-returned `StreamDescriptor`'s options for exactly this reason — see adapter-rtsp/MODULE.md Gotchas for the full empirical writeup this fix is based on. `transport=MJPEG` never gets this augmentation: the mjpeg TX/RX pair has no same-JVM contention (proven by adapter-mjpeg's own in-process round-trip IT and by `MjpegSimulationSmokeTest` in vision-app), so its `StreamDescriptor` is registered exactly as the transmitter returned it.
- **`DefaultSimulationService.RTSP_FEED_ESTABLISH_DELAY_MILLIS` (1000ms) is an empirically-required fixed delay, also RTSP-only**, paid only when `transport=RTSP` and `autoStart=true`, between `feedTransmitter.start()` returning and `assetService.startStream()` opening the RX side: `RtspFeedTransmitter`'s transmit thread takes on the order of tens of milliseconds to reach mediamtx's ANNOUNCE/SETUP/RECORD handshake, and mediamtx answers an RX `DESCRIBE` for a not-yet-published path with a bare 404 — not a "retry me" signal. `FfmpegVideoSource` has no reconnect logic (a single failed connect permanently kills that `StreamPipeline`, emitting one `PIPELINE_ERROR` event), so without this delay `startStream` reliably raced ahead of the transmitter and the simulated stream died before a single frame flowed (reproduced while writing `RtspSimulationDockerE2ETest` in vision-app: the RX side logged `avformat_open_input()` failing with a 404 within ~15ms of `STREAM_STARTED`, while the transmitter's own "Transmitting..." log line didn't appear until ~50-80ms later). This is exactly the caller-side responsibility `FeedTransmitterPort#start`'s own javadoc calls out ("callers that need frames to actually be flowing before opening the RX side must poll or retry rather than assume readiness"); a fixed delay matching the margin adapter-rtsp's own `MediamtxDockerIntegrationTest` already validated empirically is the simplest thing that could work, given `vision-application` must stay framework/dependency-free (so no FFmpeg-based readiness probe belongs here). A manually-started stream (`autoStart=false`, started later via a separate call) never pays this delay and doesn't need to — by then the feed has long since been established. `MjpegFeedTransmitter#start` only returns once its HTTP context is registered on an already-listening server, so `transport=MJPEG` never needs (or pays) an equivalent delay — its very first RX connection attempt already succeeds.
- **`FeedTransmitterRegistry.transmitterFor` probes every candidate's `supports()` in order until one matches**, exactly like `VideoSourceRegistry` — an earlier-registered transmitter that doesn't support the requested protocol still has `supports()` called on it (a real interaction, visible to a strict mock verification) even though it is never `start()`ed/`stop()`ped.
- **`DefaultSimulationService.feedByAsset` is pure in-memory bookkeeping — a `transport=RTSP`/`MJPEG` simulation's TX feed is never re-published after a JVM restart, even with `vision.persistence.enabled=true`.** Found investigating a real "frozen video" report: an RTSP-loopback simulated asset (category `simulated`, video device `protocol="rtsp"`, `uri=rtsp://<rtsp-push-base>/feed-<uuid>`) survived a backend restart in Postgres exactly as designed (docs/MVP2-PLAN.md P-a/P-b), but its `RtspFeedTransmitter` push to mediamtx did not — mediamtx showed nothing publishing that path, and `adapter-rtsp`'s RX side (whatever re-requested the stream after the restart — a user action or the frontend's own reconnect logic) retried `DESCRIBE` against it forever, 404 every time (see adapter-rtsp/MODULE.md's own Gotcha for the RX-side silent-endless-retry half of this, now fixed to at least log it). **Root cause, by file:line**: `feedByAsset` (`private final Map<AssetId, TrackedFeed> feedByAsset = new ConcurrentHashMap<>()`, this class, populated only in `simulate()` and read/removed only in `stop()`) is the *only* record of "this asset's video device is backed by a live TX transmitter, started from this file, with this `FeedId`" — and it lives purely in this service instance's JVM heap. A restart starts with an empty map. There is no boot-time hook anywhere in this codebase (searched the whole tree: no `ApplicationReadyEvent`/`CommandLineRunner`/`ApplicationRunner`/`@PostConstruct`/`InitializingBean` exists) that re-scans persisted assets and calls `feedTransmitters.transmitterFor(...).start(...)` again for ones that need it — this was never built, in any cycle's plan (docs/CYCLES-PLAN.md §3/§5/§9, the only places `transport=RTSP`/`MJPEG` simulation is specified, describe only the initial `simulate()`/`stop()` lifecycle, never a restart/restore path), so this is a genuine, previously-undocumented gap, not a regression.
  - **Why it can't be trivially bolted on**: nothing persisted today distinguishes "this RTSP-protocol device is one of our own TX-fed simulation feeds" from "this is a real external RTSP camera" — both are just `Device(protocol="rtsp", uri=<something>)` once written to `AssetRepositoryPort`/`DeviceRepositoryPort`. `AssetSpec#attributes`' `source` key (the resolved video file path, set for *any* non-null-`videoPath` transport including plain `DIRECT`/`file`) isn't transport-specific either. The one honestly-reliable signal is structural, not stored: an RTSP device whose `uri` host:port matches the app's own configured mediamtx push target (`VisionPublishProperties.Mediamtx#rtspBase()`, vision-app) is *always* one of this app's own feed-transmitted assets — this architecture never registers a real external camera against mediamtx's own RTSP ingest port, only ever pushes *to* it — and the `feed-<uuid>` path segment already round-trips a valid `FeedId.of(String)` (vision-domain).
  - **Recommended fix (not implemented here — no docs/*-PLAN.md spec covers it, so this is a recommendation, not a "clearly within existing design" change)**: a boot-time (or `SimulationController`-triggered) `SimulationService` method — e.g. `resume(AssetId)`/`resumeAll()` — that, for each persisted, non-deleted `simulated`-category asset whose video device's `uri` matches the mediamtx push-base heuristic above: parses `FeedId.of(...)` back out of the URI's `feed-` segment, rebuilds a `FeedSpec` from `attributes.source` (the video file path) + the device's existing `protocol`, and calls `feedTransmitters.transmitterFor(feedSpec).start(feedId, feedSpec)` — deliberately *not* going through `simulate()` (which always creates a brand-new asset+devices) or a fresh `FeedId.random()` (which would orphan the persisted device's own already-stored URL). This would need a small new wiring hook in `vision-app` (e.g. an `ApplicationRunner` bean, gated on `vision.persistence.enabled` — the in-memory profile has nothing to restore after a restart anyway, its `feedByAsset`/repositories are both wiped together) to actually invoke it once the context is up. Out of scope to build speculatively here — flagged for a real cycle plan to pick up.
- **`DefaultReplayService.timeline`'s detections are real as of docs/MVP2-PLAN.md R-a2** — `AssetUsage#streamId` (vision-domain) is the join key, recorded once at open time by `UsageTracker`; a `null` `streamId()` (a usage opened before R-a2, or by an asset with no video device) still yields an honestly empty detections list rather than a guessed join — there remains no reliable fallback for those. Unlike telemetry's fetch-then-filter workaround, the detections query *is* genuinely time-bounded (`DetectionRepositoryPort#query` takes `from`/`to` directly), so it doesn't share telemetry's "silently drops whatever's past the fetch cutoff" failure mode — but it has the mirror-image one: the port's real implementations return newest-first with `limit` already applied, so a stream with more than `DETECTION_FETCH_LIMIT` (20,000) results *inside* the requested window loses its **earliest** ones, not its latest. `DetectionQuery#to()`'s own javadoc calls it exclusive, but `DefaultReplayService` passes the resolved window's `to` straight through as-is, relying on every real `DetectionRepositoryPort` implementation actually treating it as inclusive (see `adapter-persistence`'s `JpaDetectionRepository` javadoc/MODULE.md) — exactly the same inclusive-both-ends semantics this class already uses for telemetry, so the two series stay consistent at the window edges.
- **`DefaultReplayService`'s telemetry fetch is a workaround, not a real time-bounded query** — `TelemetryRepositoryPort#findByUsage(usageId, limit)` has no `from`/`to` parameters at all, and its `limit` selects the usage's **earliest** samples (see the port's javadoc and `adapter-persistence`'s `JpaTelemetryRepository`, which deliberately preserves this exact semantic). `DefaultReplayService` fetches up to `TELEMETRY_FETCH_LIMIT` (20,000) samples and filters/thins the requested window out of that fetch in memory. For a usage with more than 20,000 total telemetry samples (at 1Hz, ~5.5 hours of continuous flight), any window whose data falls after that cutoff is silently missing from the response, **even if the caller's `to` explicitly asks for it** — there is no way to detect or signal this truncation from inside this method, since the port gives no total-count or "more available" signal either. The real fix is a time-bounded query added to `TelemetryRepositoryPort` (`adapter-persistence/MODULE.md` already flags the `findByUsage` ordering oddity as a future contract-cleanup item for exactly this reason) — not attempted here, per this task's explicit instruction not to change the port.
- **`ReplayService#timeline`'s `to` default for an open usage is resolved eagerly, once, at call time** (`Instant.now()`) — there is no clock/`Supplier<Instant>` injection seam (unlike `StreamPipeline`'s `nanoTimeSource`), since a single wall-clock read per request has no meaningful test-flakiness risk here; tests bracket the call with `Instant.now()` calls before/after instead of injecting a fake clock.
- **`DetectionEventEngine.accept`'s per-label absence check only ever runs when a new `DetectionResult` completes** (docs/MVP2-PLAN.md §E, E-a) — there is no background timer independently ticking `absenceToClose` forward. Under normal operation this is a non-issue (completed results keep arriving at roughly `inferenceFps`, so a genuine absence is detected within about one sampling interval of the configured window), but during an actual `StreamPipeline` detection **outage** (see that class's own outage/backoff Gotchas), sampled frames are withheld from `DetectionPort` entirely and no results complete at all — an event left open when the outage began stays open, un-evaluated, until detection recovers and the next completed result's timestamp reveals the gap. This mirrors the deliberate "no extra threads for a soft/cosmetic concern" posture already established for overlay rendering, rather than adding scheduler machinery to this module (which must stay framework-free).
- **`DetectionEvent#position` is frozen at open time, not live-tracked** (docs/MVP2-PLAN.md §E, E-a) — `DetectionEventEngine.open` calls `usageTracker.latestPosition` exactly once, when the event transitions from candidate-streak to `OPEN`; every subsequent `withObservation` call (while the event stays open) only touches `lastSeen`/`peakConfidence`, never `position`. An event open for a long-moving asset therefore reports where it *was* when first confidently seen, not where it *is now* — judged an acceptable first-cut tradeoff (the map can separately show "where is it now" from the asset's own live position), not an oversight; live-tracking the position would mean re-querying `usageTracker` on every still-open update, which is easy to add later if a real need shows up.
- **`PipelineConfig#eventRule`'s labels are independent of `labelFilter`** — `labelFilter` (existing, gates what `DetectionPort` even returns) and `EventRuleConfig#labels` (new, gates what `DetectionEventEngine` debounces into events) are two separate label sets with no cross-validation between them. Configuring `labelFilter={"car"}` while `eventRule.labels()` still defaults to `{"person","car"}` is valid but means "person" events can never actually open (the label never reaches the engine in the first place) — this is not treated as a configuration error, since a filtered-out label silently having no events is the same "no data, not a failure" shape every other empty-result path in this class already has.

- **docs/MVP2-PLAN.md §S, S-a — source supervision, what survives a reconnect vs. what re-establishes.** The whole mechanism is one `Flow.Publisher` decorator (`SupervisedPublisher<T>`, see its own API-surface entry) interposed **before** the pipeline/subscriber is ever constructed, not a change to `StreamPipeline`/`TelemetrySubscriber` themselves — `StreamPipeline.java` has **zero** lines changed by this task. Concretely, per reconnect:
  - **Survives untouched, exactly once per stream (never repeated by a reconnect):** the `StreamPublisherPort` session — `streamStarted`/`streamEnded` fire only at `DefaultStreamService#start`/`#stop`, since `StreamPipeline.start()` (which calls `streamStarted`) is invoked exactly once and a reconnect never calls it again, it just resubscribes the *same* still-running pipeline instance to a freshly-opened publisher. This was explicitly called out as "even better" if achievable, and it falls out for free from the decorator design rather than needing special-casing — confirmed by reading `MediamtxStreamPublisher`, which would otherwise reset its cadence-measurement/GOP state on every `streamStarted` (see that adapter's own `StreamState`). Also surviving untouched: the `UsageId`/`AssetUsage`/`streamId` (`UsageTracker#onStreamStarted`/`#onStreamStopped` likewise fire only once per stream, never on a reconnect — a device's "active" count in `UsageTracker.Tracking` never changes during supervised retries, so the usage-open/close accounting has nothing to react to); `StreamPipeline`'s own detection-outage/backoff state, `latestDetections()`, and the `DetectionExtrapolator`/`DetectionEventEngine` instances (all pipeline-instance state, and the pipeline instance itself never changes).
  - **Re-establishes on every reconnect:** only the actual source-side `Flow.Publisher`/`Flow.Subscription` — a fresh `VideoSourcePort#open`/`TelemetrySourcePort#open` call each time, each producing whatever fresh per-open state the *adapter* itself resets (see the frame-sequence Gotcha below).
  - **`PIPELINE_ERROR` policy: once per outage, not once per failed attempt** — the same choice `StreamPipeline`'s own detection-outage machinery and `MediamtxStreamPublisher`'s own publish-outage machinery already made, for consistency with two pre-existing precedents in this exact codebase rather than inventing a third convention. Telemetry supervision (`UsageTracker`) does **not** publish `PIPELINE_ERROR` at all, even though the video path does — `UsageTracker` has no `EventPublisherPort` dependency and no `StreamId` to publish an event against (telemetry is tracked per-device/asset, not per-stream), and `TelemetrySubscriber#onError` was already, deliberately, a silent no-op *before* this task (see below) — adding a brand-new constructor dependency purely to emit an event for a class whose failures were always silent by design was judged out of scope; reconnection with backoff is the actual resilience requirement and is fully delivered either way.
  - **Backoff: 1s→30s, doubling, uncapped in count** (`SupervisedPublisher.INITIAL_BACKOFF_NANOS`/`MAX_BACKOFF_NANOS`) — a deliberately different magnitude from `StreamPipeline`'s own detection-outage backoff (1s→10s) and `MediamtxStreamPublisher`'s own publish backoff (500ms→10s): reconnecting a whole video/telemetry *source* (a real network/USB/process-level operation) is more expensive to hammer than either of those two finer-grained, in-process retry loops, and 30s matches this row's own plan text verbatim.
  - **Frame/sample sequence numbers are *not* guaranteed monotonic across a reconnect, and this task does not fix that** — `StreamPipeline` never generates `VideoFrame#sequence()` itself, the *adapter* does (e.g. `adapter-rtsp`'s `FfmpegVideoSource` keeps a per-`StreamRuntime` `AtomicLong` that starts fresh at 0 on every `open()` call), and `SupervisedPublisher` calls `open()` again on every retry, creating a brand-new adapter-side runtime each time. Fixing this would mean either renumbering frames in the wrapper (extra allocation/complexity on the hot per-frame path, for a cosmetic concern) or changing every adapter's own sequence bookkeeping (out of this task's `vision-application`-only scope) — documented honestly rather than silently assumed away. Functionally harmless: `StreamPipeline`'s own sampling modulo (`frame.sequence() % sampleEveryNthFrame`) still works correctly against the reset sequence, it just restarts its cycle.
  - **A brief, bounded, non-leaking race is possible between an explicit `stop()` and an in-flight reopen attempt** — `SupervisedPublisher.stop()` sets `stopped=true` and cancels the pending `ScheduledFuture`, but if a scheduled retry's `openAndSubscribe` had *already* passed its own `stopped.get()` check (a narrow window, since `stop()` runs synchronously and immediately after `DefaultStreamService.stop()`'s map removal, while a retry can only fire after its own backoff delay elapses) before `stop()` ran, that one attempt still calls `opener.get()`/`subscribe()`. This never leaks: `DefaultStreamService#stop`/`UsageTracker#unsubscribeTelemetry` unconditionally call the underlying port's own `close(id)` afterward regardless of supervision state, and every real adapter's `close`/`open` pair is keyed by the same `StreamId`/`DeviceId`, so whatever the stray attempt opened gets closed by that same call. `StreamPipeline.onSubscribe` was **not** touched to add a matching guard, since `StreamPipeline` has no visibility into `SupervisedPublisher`'s `stopped` flag at all (by design — see above) and doesn't need one, this race is fully absorbed one layer down.
- **The `/live` stop-freeze bug (docs/MVP2-PLAN.md §S, user-reported) was a real backend bug, found and fixed in this task, not (only) a frontend one** — `DefaultStreamService#stop` used to call `VideoSourcePort#close(streamId)` **synchronously**, on whatever thread called `stop()` (a Spring MVC request thread for `DELETE /api/streams/{streamId}`, per `StreamController`). `adapter-rtsp`'s `FfmpegVideoSource.StreamRuntime#close` joins its native grab thread with a **20-second** timeout (`CLOSE_JOIN_TIMEOUT_MILLIS`) after a best-effort `Thread#interrupt()` that its own javadoc admits "native `grab()` may not respond to" — meaning a genuinely stuck RTSP read (exactly the ESP32/flaky-camera scenario this whole cycle is about) could block that request thread for up to 20s. Combined with a browser's small (typically 6) per-origin HTTP/1.1 connection limit, one stuck `DELETE` holding a connection open with no response starves every other poller (asset list, streams, detections, telemetry) queued behind it on the same origin — which reads, from the browser's Network panel, exactly like "the whole app froze," not "one request is slow." Fixed by `stop()` (and `UsageTracker#unsubscribeTelemetry`, called synchronously from the same `stop()`) doing only fast, in-memory work before returning (map removal, `SupervisedPublisher#stop()`, the `STREAM_STOPPED` event, closing the `AssetUsage`) and deferring the actual `StreamPipeline#close()`/port `close()` calls to a fire-and-forget virtual thread — see `DefaultStreamServiceTest#stopReturnsPromptlyEvenWhenSourceTeardownBlocksForAWhile` for a test that reproduces the exact shape of the bug (a `close()` mock blocked on a latch) and proves `stop()` now returns in well under a second regardless.

2. **`FleetSummaryService`/`DefaultFleetSummaryService`** (new, see its own API-surface entry above) — composes `AssetService`, `StreamService`, `UsageTracker`, `DetectionEventRepositoryPort` (4-arg ctor, within the 5-arg cap) rather than reaching past them to repositories.

docs/REALTIME-PLAN.md **§4 done** (server-push data plane, application half — backend of Phase R-c, replacing steady-state polling of fleet/telemetry/detections/events): this module's job was purely **emission at the natural seams that already mutate this state** — no new types, no new read models, the new `LiveUpdatePublisherPort` (vision-domain) is announced from exactly three places:

1. **`StreamPipeline#onDetectionResult`** — every completed result (empty or not, mirroring the existing `eventEngine`/`latestDetections` update right alongside it) calls `liveUpdatePublisherPort.publishDetections(assetId, result)`, gated on *both* `assetId`/`liveUpdatePublisherPort` being non-null. New 12-arg public ctor (+`AssetId assetId`, +`LiveUpdatePublisherPort liveUpdatePublisherPort`, both nullable, same convention as `overlayPort`/`eventEngine`); the pre-existing 11-arg package-private test-seam ctor was extended in place to 13 args (two new params inserted before `nanoTimeSource`) rather than kept alongside a second, parallel test constructor — its five call sites in `StreamPipelineTest` (all inside small private `pipeline(...)`/`manualPipeline(...)` helper methods) were updated to pass `null, null` for the two new positions.
2. **`DefaultStreamService#start`** — resolves the device's owning `AssetId` **once**, via the already-held `usageTracker.resolveAsset(deviceId)`, and threads it plus `liveUpdatePublisherPort` into the `StreamPipeline` it constructs. The resolution itself is skipped entirely (not just discarded) unless *both* `usageTracker` and `liveUpdatePublisherPort` are configured — a lookup nobody could ever read is never attempted. New 10-arg public ctor (+`LiveUpdatePublisherPort`, nullable, same convention as `overlayPort`/`detectionEventRepositoryPort`); its own package-private test-seam ctor grew from 11 to 12 args the same way (the new param inserted before the two backoff longs), with one call site in `DefaultStreamServiceTest` updated.
3. **`UsageTracker#applySample`** — the single write path for a telemetry sample (persist + usage-summary fold) now also calls `liveUpdatePublisherPort.publishTelemetryAppended(assetId, sample)` right alongside. New 6-arg public ctor (+`LiveUpdatePublisherPort`, nullable); its own test-seam ctor grew from 7 to 8 args (new param inserted before the two backoff longs), one call site updated in `UsageTrackerTest`.

**Deliberately *not* touched by this task**: `DefaultAssetService`/`DefaultDeviceService` — both already sit at (or, for `DefaultAssetService`, above) the constructor-parameter ceiling (`.claude/skills/java-clean-code/SKILL.md` §3), and neither needed a new raw dependency here. Asset/device CRUD's "fleet changed" signal instead flows through a `vision-app`-only decorator wrapping the pre-existing `AuditTrailPort` (every mutating asset/device operation already records exactly one `AuditEntry`, whether or not it also raises an `Event`) — see vision-app/MODULE.md's `LiveUpdateAuditTrail`/`LiveUpdateEventPublisher` entries for the full reasoning and why this was the cleaner seam than adding a constructor parameter to either service.
