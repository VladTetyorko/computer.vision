# vision-application

Control-plane services orchestrating `vision-domain` ports: asset/device/stream management, the per-stream pipeline runtime, and usage/telemetry tracking.

**One interface + one `Default*` implementation per service area** — there is no inbound-port package and no `*UseCase` type. Commands and read models are top-level records, not types nested in interfaces. See `.claude/skills/java-clean-code/SKILL.md`.

**Depends on:** vision-domain (only) · **Used by:** adapters (adapter-simulation, adapter-rtsp, adapter-publish-hls, adapter-discovery, adapter-cv-grpc, adapter-overlay, adapter-persistence), vision-app, vision-api
**Build/test:** `./mvnw -B -pl vision-application test`

Types below are grouped by service; see the Package structure table above for which package each lives in.

validated: `speedMps` positive when given, `route` null-or-≥2 waypoints, defensively copied), `RouteMode` enum `{LOOP, BOUNCE, ONCE}` (top-level, docs/CYCLES-PLAN.md §7, mirrors `SimulationTransport`'s top-level-enum convention; - **`AssetService`** (interface) → **`DefaultAssetService`**
  - `DefaultAssetService(AssetRepositoryPort, CategoryRepositoryPort, AssetUsageRepositoryPort, AuditTrailPort, DeviceService, StreamService)` — reaches devices through `DeviceService`, never the device repository, so a source's rules (stop its stream, write an audit line) live in one place
  - `Asset create(AssetSpec, Ownership, UserId actor)` — validates the category, registers each `AssetSpec#devices()` entry, and (backend follow-up batch) assigns each `AssetSpec#existingDeviceIds()` entry via the same eligibility check `#assignDevice` uses (`requireAssignable`, private, shared by both) — must exist, not be soft-deleted, not already belong to another asset — folded into this asset's one initial save/audit rather than a separate assign+audit cycle per device; audits `CREATED`
  - `List<AssetSummary> assets()` / `assets(boolean includeDeleted)` — soft-deleted excluded by default; status from `streamService.activeDeviceIds()`
  - `List<AssetSummary> assets(VisibilityScope scope, boolean includeDeleted)` (docs/U-SCOPE-PLAN.md, U-e slice 2, feature 1) — the **scoped** read for user-facing callers: reuses the unscoped `assets(includeDeleted)` result and keeps only `scope.includes(asset)`. An `unbounded()` scope returns it unchanged (the slice's guardrail). Internal/system callers (`SimulationService#resumeAll`, `vision-api`'s live snapshot) keep calling the unscoped `assets(...)` — its signature is unchanged
  - `AssetDetails details(AssetId)` — `NoSuchElementException` if unknown; up to 20 (`RECENT_USAGES_LIMIT`) most-recent usages
  - `AssetDetails details(VisibilityScope scope, AssetId)` (docs/U-SCOPE-PLAN.md, U-e slice 2, feature 1) — the **scoped** detail read: `details(id)` then, if `!scope.includes(asset)`, throws `NoSuchElementException` **with the same "Unknown asset" message as the unknown-id case** — a 404, deliberately not a 403, so a scoped read never reveals an out-of-scope asset's existence. `unbounded()` behaves exactly as `details(AssetId)`. (Contrast the command gate below, which 403s on purpose.)
  - `Asset update(AssetId, AssetEdit, UserId)` — partial; audits `UPDATED` with changed fields only, and writes nothing when nothing changed
  - `Asset setState(AssetId, LifecycleState, UserId)` — idempotent; stops streams when leaving service; `DELETED → ACTIVE` throws `IllegalStateException` (restore first)
  - `AssetDeletion delete(AssetId, UserId)` — **soft**: marks the asset and its devices `DELETED`, keeps usages/telemetry; idempotent
  - `StreamId startStream(AssetId, DeviceId, PipelineConfig)` — `device` nullable: resolves the asset's single **active** `VIDEO`-capable device, `IllegalArgumentException` (naming candidates) if zero or >1; `IllegalStateException` if the asset is not in service
  - `void stopStream(AssetId)` — stops every active stream on the asset's devices; unknown asset is a no-op
  - `Asset assignDevice(AssetId, DeviceId, UserId actor)` (docs/CYCLES-PLAN.md §8's pinned contract) — the device must exist (`NoSuchElementException` otherwise) and not be soft-deleted (`IllegalArgumentException` otherwise: restore it first); `AssetRepositoryPort.findByDeviceId` must be empty — a device already owned by *any* asset (including this one) is refused with `IllegalStateException` naming the owning asset (→409); adds the device via `Asset.withDevices`, audits `UPDATED`. These three checks live in a private `requireAssignable(DeviceId)` helper (backend follow-up batch), shared with `#create`'s `existingDeviceIds` path so the two "assign an existing device" entry points can never drift
  - `Asset unassignDevice(AssetId, DeviceId, UserId actor)` (docs/CYCLES-PLAN.md §8's pinned contract) — the device must currently belong to this asset (`IllegalArgumentException` otherwise); removing it must leave at least one device, or `IllegalStateException` (the reduced set is built *before* the `Asset.withDevices` call, since the record's own compact ctor is what actually enforces non-empty); audits `UPDATED`. The device itself is untouched (not soft-deleted) — unassigning just breaks the asset↔device link, mirroring how `DeviceService#delete` never needs an asset-side special case

- **`CategoryService`** (interface) → **`DefaultCategoryService`**
  - `DefaultCategoryService(CategoryRepositoryPort)`
  - `List<DeviceCategory> categories()` — thin pass-through over `CategoryRepositoryPort.findAll()`, sorted by `CategoryId.slug()` for a stable UI order

- **`DeviceService`** (interface) → **`DefaultDeviceService`**
  - `DefaultDeviceService(DeviceRepositoryPort, StreamService, AuditTrailPort, EventPublisherPort)`
  - `Device register(DeviceRegistration, UserId actor)` — assigns `DeviceId.random()`, saves, publishes `DEVICE_ONLINE`, audits `CREATED`
  - `List<Device> devices()` / `devices(boolean includeDeleted)`; `Optional<Device> find(DeviceId)`
  - `Device update(DeviceId, DeviceEdit, UserId)` — partial; a running stream keeps its settings until the next start
  - `Device setState(DeviceId, LifecycleState, UserId)` — idempotent; stops the device's stream when leaving service; `DELETED → ACTIVE` throws `IllegalStateException`
  - `Device delete(DeviceId, UserId)` — **soft**; the device stays a member of its asset, so removing an asset's last source is never refused

- **`GeofenceService`** (interface) → **`DefaultGeofenceService`** (docs/OPS-CORE-PLAN.md §G) — CRUD/list over `GeofenceZone`s; zones are global reference data (no ownership, no audit trail — nothing in the plan calls for one), so this is a thin pass-through over `GeofenceRepositoryPort` plus keeping `GeofenceMonitor`'s cache current
  - `DefaultGeofenceService(GeofenceRepositoryPort, GeofenceMonitor)`
  - `List<GeofenceZone> zones()` — sorted by name (case-insensitive), same "stable management-panel order" reasoning as `CategoryService#categories()`
  - `Optional<GeofenceZone> find(ZoneId)`
  - `GeofenceZone create(GeofenceZoneSpec)` — assigns `ZoneId.random()`, saves, then `geofenceMonitor.refresh()`
  - `GeofenceZone update(ZoneId, GeofenceZoneSpec)` — wholesale replace (the wire contract's update request is the same shape as create); `NoSuchElementException` if unknown; refreshes the monitor afterward
  - `void delete(ZoneId)` — `NoSuchElementException` if unknown (checked before calling the otherwise-idempotent `GeofenceRepositoryPort#deleteById`, exactly the same "service enforces 404, port stays idempotent" split `AssetService`/`DeviceService` already use); refreshes the monitor afterward

- **`GeofenceMonitor`** (public, final, no interface — docs/OPS-CORE-PLAN.md §G) — evaluates live telemetry against the enabled `GeofenceZone` set and raises `GEOFENCE_BREACH` events on edge transitions; called from `UsageTracker#applySample`, the same hot path that already persists/live-announces every sample. Public (unlike the similarly-shaped `DetectionEventEngine`) because `UsageTracker`'s own public constructor takes one as a nullable collaborator, so `vision-app`'s wiring must be able to construct it directly
  - `GeofenceMonitor(GeofenceRepositoryPort, EventPublisherPort, LiveUpdatePublisherPort)` — the latter two nullable, same nullable-collaborator convention as `UsageTracker`'s own `liveUpdatePublisherPort`: `null` means breach transitions are simply never announced through that port
  - `void refresh()` — reloads the enabled-zone cache from `GeofenceRepositoryPort#findAll()` (filtered to `enabled()`); called by `GeofenceService` after every create/update/delete
  - `void evaluate(AssetId, Telemetry)` — ignores a sample with no `latitude`/`longitude` entirely (no state change, no repository read even); otherwise self-populates the cache lazily on first use if `GeofenceService` never called `refresh()` yet (e.g. zones already existed in storage before this JVM booted), then evaluates every enabled zone. Breach rules (frozen, docs/OPS-CORE-PLAN.md §G): `KEEP_OUT` breaches iff inside the polygon, at any altitude (`maxAltitudeMeters` has no effect on a `KEEP_OUT` zone); `KEEP_IN` breaches iff **at least one enabled `KEEP_IN` zone exists** and the position is outside **every** enabled `KEEP_IN` zone (the union is the allowed area, computed once per sample and shared across every enabled `KEEP_IN` zone), **or** the position is inside this particular zone but its altitude exceeds this zone's own `maxAltitudeMeters`. Per-`(assetId, zoneId)` breach state is in-heap only (`ConcurrentHashMap`); only a state change (edge transition) raises one `Event(GEOFENCE_BREACH, streamId=null, attributes={assetId, zoneId, zoneName, kind, direction})` (`direction` = `"enter"`/`"exit"`) via both `EventPublisherPort#publish` and `LiveUpdatePublisherPort#publishEvent` — staying in the same state (still breaching, or still compliant) is silent

- **`MarkService`** (interface) → **`DefaultMarkService`** (docs/TACTICAL-MARKS-PLAN.md §2, Wave M3 — **revised** post-review for the FPV-operator/PILOT persona, see below) — the shared operational picture: geolocated tactical `Mark`s, structurally mirroring `GeofenceService`'s CRUD/list shape (a `Mark` is a point version of a `GeofenceZone`) — including, now, `GeofenceService#zones()`'s own **unscoped** list shape, not `AssetService`'s scoped one. `Ownership`/`UserId actor` are still separate method parameters, never constructor state
  - `DefaultMarkService(MarkRepositoryPort, UsageTracker, LiveUpdatePublisherPort)` — 3-arg, well under the cap; holds no mutable state
  - `List<Mark> list()` — **deployment-wide, no scope parameter at all**: every `MarkStatus#ACTIVE` mark (a `CLEARED` one drops off the list — "clients drop the pin"), newest-first. The original M3 design group-filtered this (mirroring `AssetService`'s scoped reads); revised because a PILOT's `VisibilityScope` is `ASSIGNED_ASSETS`, which carries **no group at all** (`includesGroup` is hard-`false` for that kind) — group-filtering silently hid every mark from the primary persona this whole feature is for (the FPV operator), including their own. The shared operational picture means everyone at the command point sees the *same* marks, so this now mirrors `GeofenceService#zones()`'s own unscoped shape, and is consistent with the `"marks"` SSE topic, which already broadcasts deployment-wide exactly like the pre-existing `fleet`/`event` topics (docs/TACTICAL-MARKS-PLAN.md §5/Open Q4) — REST list and the live stream now agree. The multi-tenant "everyone sees everyone's marks" limitation is accepted and documented (same caveat as the `fleet`/`event` topics), not this feature's to fix
  - `Mark create(MarkSpec spec, Ownership ownership, UserId actor)` — unchanged: `new Mark(MarkId.random(), spec.position(), spec.kind(), spec.label(), spec.note(), ownership, Instant.now(), ACTIVE, MANUAL)`, saves, `publishMarkCreated`. `ownership` is supplied by the caller (mirrors `AssetService#create` exactly — never derived from `scope` internally). Open to any authenticated actor, who becomes the mark's owner
  - `Mark geolocate(GeolocateSpec spec, Ownership ownership, UserId actor)` — unchanged: reads `usageTracker.latestTelemetry(spec.assetId())`; `Optional.empty()`, or a present sample missing `latitude`/`longitude`/`headingDegrees`, or `altitudeMeters` absent/≤0, all throw the same `IllegalArgumentException("cannot geolocate: telemetry incomplete")` (→ 400) **before** any `Mark` is built or saved — this null-checking is this method's job, not `GeoProjection`'s (see that class's own javadoc: it accepts no nullable telemetry). Otherwise builds the drone's `GeoPosition` from the sample, calls `GeoProjection.project(drone, heading, altitude, spec.depressionDegrees())`, and saves a `Mark` at the projected ground point with `source=DETECTION`, `status=ACTIVE`; `publishMarkCreated`. Does **not** default `spec.label()` — a blank/absent label surfaces as `Mark`'s own `IllegalArgumentException` via `GeolocateSpec`'s duplicated validation; a caller-side default ("Contact", the asset's display name, …) is a wire/UI-layer decision, not made here
  - `Mark update(MarkId id, MarkPatch patch, UserId actor, VisibilityScope scope)` — **revised**: `require(id)` (`NoSuchElementException`/404 for an unknown id, **no group-visibility gate any more**), then `requireCreatorOrManager` applies to the **whole** edit — every field, including a plain annotation/drag-to-correct with no status change, not only a `status` transition as the original design had it. Present patch fields (`kind`/`label`/`note`/`position`) are folded via `Mark#withDetails`; a present `patch.status()` (either direction) is applied via `withStatus` after the same gate. Always saves and always publishes once the gate passes — `publishMarkCleared` when the saved mark's net status is `CLEARED`, else `publishMarkUpdated` — regardless of whether the patch was a no-op, matching `DefaultGeofenceService#update`'s own unconditional-save-and-refresh precedent rather than `AssetService#update`'s change-detecting audit
  - `void delete(MarkId id, UserId actor, VisibilityScope scope)` — **unchanged** (already had the shape `update` was revised to match): `require(id)` → `NoSuchElementException`, then the same creator-or-manager gate, else `AccessDeniedException`. `markRepository.deleteById(id)`, then `publishMarkCleared(mark)` using the **pre-deletion** mark instance as `require(id)` returned it (its in-memory `status` may still read `ACTIVE`) — presenting the wire payload's `status` as `"CLEARED"` for a delete (docs/TACTICAL-MARKS-PLAN.md §5) is `LiveUpdateRegistry`'s job in M4, not this method's
  - **Authorization, revised**: a private `requireCreatorOrManager(Mark, UserId, VisibilityScope)` — `actor.equals(mark.ownership().ownerId())` (the creator may always manage their own mark, **regardless of scope/group** — the fix: a PILOT with an `ASSIGNED_ASSETS` scope now passes this on their own mark) **or** `scope.canManageOrg()` (a manager/admin may manage **any** mark, not only one whose subtree contains it), else `AccessDeniedException` (403) — now the **single** gate shared by all of `update`'s fields and `delete`, not split between an open-annotate/gated-status-change split the original design had

  **Design history worth keeping** (why this changed after first landing): the original M3 group-filtered `list` and confined the creator-or-manager gate to `update`'s status-transition branch only, both mirroring how `AssetService` threads `VisibilityScope`. That combination had a hard consequence, caught in review: since `VisibilityScope#includesGroup` is hard-`false` for `ASSIGNED_ASSETS` and both `UNBOUNDED`/`GROUPS` already have `canManageOrg()==true` unconditionally, a PILOT could never pass the group-visibility gate at all — not even to see or annotate their **own** mark — while the status-transition gate was, by construction, unreachable for anyone who *did* pass it (they were already a manager/admin). Since marks are a tactical, pilot-facing feature (the FPV operator dropping/correcting/clearing their own contacts is the primary use case, per this plan's own opening narrative), this was a real functional regression for the primary persona, not an edge case — fixed by dropping group-scoping from reads entirely (deployment-wide `list()`, matching how the live `"marks"` topic already broadcasts) and by gating the *entire* `update`/`delete` surface uniformly on creator-or-manager instead of splitting annotate (open) from status-change (gated).

The two failures are split by *where* they are thrown: pre-flight validation (400) vs the port rejecting an attempted command (409). A not-commandable vehicle reports `modeSelectSupported()=false`, so the mode check is skipped and it stays 409 (either from `resolveForCommand`'s no-`supports`-device guard, or from the port throwing `IllegalArgumentException` on the attempt → rethrown `IllegalStateException`).

- **`ManualControlService`** (interface) → **`DefaultManualControlService`**, plus **`ManualControlSession`** (interface, one private `Default*`-style inner-class implementation) and **`WatchdogListener`** (interface) — docs/RC-CONTROL-PHASE1-PLAN.md, RC-CONTROL Phase 1 R2: a guarded, stateful, watchdog-supervised RC-channel-override relay session, the streaming/ack-less opposite of `FlightCommandService`'s request→ack one-shots. Reuses `DefaultFlightCommandService`'s own scope-gate/device-resolution/audit idiom verbatim rather than inventing a new one.
  - `ManualControlSession engage(AssetId, UserId actor, VisibilityScope scope, WatchdogListener onWatchdog)` — resolves the asset via `AssetService#details(AssetId)` (`NoSuchElementException` for an unknown asset), then, if `!scope.includes(asset)`, audits `DENIED:out of scope` and throws `AccessDeniedException` (403) — identical gate to `DefaultFlightCommandService`'s command gate, not the scoped-read 404. Resolves the first of the asset's **active** devices `ManualControlPort#supports` claims (`Device::isActive` + `manualControlPort::supports`, same filter shape as `firstCommandableDevice`); zero matches, **or** the port rejecting the resolved device as unreachable (`ManualControlPort#engage` throwing `IllegalArgumentException`, rethrown here as `IllegalStateException` with the identical message), both surface as `IllegalStateException` — neither is audited (no attempt was ever actually relayed, same "guard before an attempt" rule `DefaultFlightCommandService` already uses). On success: opens the link, constructs the session, audits `ENGAGE`, arms the watchdog, returns the live session.
  - **One session per service handle**: this instance holds at most one active `ManualControlSession`; a second `engage()` while one is active throws `IllegalStateException` without touching the port, and the slot frees again once that session ends (release or watchdog). Since `vision-app`'s wiring constructs exactly **one** `ManualControlService` bean (a singleton, like every other service here), this in practice serializes manual-control relaying to one connection at a time app-wide — a deliberate Phase 1 simplification (single SITL operator), not an oversight; concurrent multi-operator relays would need a per-connection service instance instead of a shared singleton, flagged for whoever picks that up later.
  - **`ManualControlSession`**: `void onChannels(List<Double> axes, List<Double> buttons, long seq, long tSent)` — maps `axes`/`buttons` through the session's `ChannelMap` (`ChannelMap.defaultMap()` today — no per-operator calibration yet) and forwards the result to `ManualControlPort#send` as the newest frame (latest-wins, no per-frame throttle — the fixed-rate wire cadence is the adapter's job), and resets the watchdog deadline; `seq`/`tSent` are accepted only to satisfy the frozen client-frame shape (docs/RC-CONTROL-PHASE1-PLAN.md §4) — the caller already holds both to build its own `ack` and does not need them echoed back. No-op once `active()` is `false`. `void release()` — `ManualControlPort#release`, cancels the pending watchdog check, audits `RELEASE`; idempotent (a second call, or one racing a watchdog trip, is a safe no-op, never a second audit line). `ChannelMap channelMap()` — the map to echo in the client's `engaged` frame. `boolean active()`.
  - **Watchdog mechanism**: a single self-rescheduling `ScheduledFuture` per session, not a cancel-and-reschedule-per-`onChannels` scheme. `armWatchdog()` (called once, right after `engage` succeeds) schedules the first check `watchdogTimeoutMs` out; each firing re-reads the session's live `lastInput` timestamp and either releases (elapsed ≥ timeout — audits `WATCHDOG`, then calls `WatchdogListener#watchdogTripped()`) or reschedules itself for exactly the remaining time. A steady ~30 Hz stream of `onChannels` calls therefore never touches the scheduler at all — it only ever writes `lastInput`. At most one `ScheduledFuture` is outstanding per session at any time.
  - **Concurrency**: `onChannels`, an explicit `release()`, and a scheduled watchdog check can each run on a different thread. An `AtomicBoolean released` guards the one release path (`doRelease`, private) with `compareAndSet(false, true)` — only the first caller to win actually calls `ManualControlPort#release`, cancels the pending future, audits, notifies the caller's session-cleared callback, and (watchdog path only) calls `WatchdogListener#watchdogTripped()`; every later caller is a safe no-op. `lastInput` is `volatile` purely for cross-thread *visibility* (single writer — `onChannels` — single reader — the watchdog-check thread); no further synchronization is needed for it. `engage()`/session-cleared both synchronize on the enclosing service's own lock, so the "one session per handle" check and the slot-freeing callback can never race each other.
  - **Constructors** (`Objects.requireNonNull` each collaborator): a 3-arg production convenience ctor `(AssetService, ManualControlPort, AuditTrailPort)` — `Clock.systemUTC()` + one dedicated daemon `"rc-watchdog"` scheduler (mirrors `UsageTracker`'s own `"telemetry-supervisor"` scheduler field) + the default timeout; a 5-arg test/wiring seam `(..., Clock, ScheduledExecutorService)` — same default timeout, the frozen §2 signature tests inject a mutable clock + a recording fake scheduler through; a 6-arg canonical ctor additionally taking an explicit `long watchdogTimeoutMs` (both other ctors delegate to it), following this codebase's own "N-1-arg convenience constructor" idiom (`PipelineConfig`/`SimulationSpec` in vision-domain/this module) rather than adding a fourth, disconnected overload. **`DEFAULT_WATCHDOG_TIMEOUT_MS = 300`** (public constant, docs/RC-CONTROL-PHASE1-PLAN.md §2's frozen default) — the 3-/5-arg ctors always use it; `vision-app`'s wiring should call the 6-arg ctor directly with the resolved `vision.rc.watchdog-timeout-ms` property (default 300) for that property to actually take effect, since the two frozen-shape ctors hard-code the default and have no property-reading of their own (application services stay Spring/property-free by convention — this module never reads `vision.*` properties itself, `vision-app`'s wiring layer does).
  - **Audit**: mirrors `DefaultFlightCommandService#audit` exactly — `AuditEntry.of(actor, AuditAction.UPDATED, AuditTargetType.ASSET, assetId, summary, attrs)`, `attrs = {assetId, command:"MANUAL_CONTROL", result}`, `result ∈ {ENGAGE, RELEASE, WATCHDOG, DENIED:out of scope}`. No new `AuditAction` value (none exists for "commanded", same decision the flight-command flow already made).
  - **`WatchdogListener`**: single method `void watchdogTripped()` — called at most once per session, on whatever thread the watchdog scheduler runs on; by the time it fires the session is already released and the release is already audited, so the listener only needs to notify its own caller (e.g. push a `watchdog` WebSocket frame), never release anything itself.

- **`DetectionEventEngine`** (package-private, final, no interface — docs/MVP2-PLAN.md §E, E-a) — per-stream debounce rule engine: collapses a tracked label's consecutive-qualifying-`DetectionResult` streak into an open/close `DetectionEvent` lifecycle
  - `DetectionEventEngine(StreamId, DeviceId, EventRuleConfig, UsageTracker, DetectionEventRepositoryPort)` — `UsageTracker` nullable (no geolocation/asset resolution when absent, same convention as `DefaultStreamService`'s own field of the same name); `DetectionEventRepositoryPort` required
  - `void accept(DetectionResult)` (`synchronized`, mirrors `DetectionExtrapolator`'s threading note) — for every label in `EventRuleConfig#labels()`: a result whose peak confidence for that label is ≥ `confidenceThreshold` counts toward a consecutive streak; reaching `consecutiveToOpen` opens an event (`firstSeen` = the streak's first qualifying result, not the opening one); while already open, each further qualifying result advances `lastSeen`/raises `peakConfidence` (`DetectionEvent#withObservation`); a non-qualifying result resets the streak count to 0 and, if an event is open, checks the gap since its `lastSeen` against `absenceToClose` — reaching it closes the event (`DetectionEvent#closed()`, `lastSeen` left exactly as the last real observation, not moved forward). Every timestamp comes from `DetectionResult#capturedAt()`, never wall-clock time — no clock injection needed for tests. `assetId`/`position` are resolved **once, at open time only**, via `usageTracker.resolveAsset(deviceId)`/`usageTracker.latestPosition(assetId)` — frozen on the event thereafter even while it stays open and the asset keeps moving. - **`SupervisedPublisher<T>`** (package-private, final, generic, no interface — docs/MVP2-PLAN.md §S, S-a) — the source-supervision mechanism behind "a started stream survives source failures; only an explicit Stop ends it." A `Flow.Publisher<T>` decorator wrapping a re-openable source (`VideoSourcePort`/`TelemetrySourcePort`), used by both `DefaultStreamService#start` (video) and `UsageTracker#subscribeTelemetry` (telemetry) — one shared class rather than two near-identical ones, since the backoff/retry/stop machinery is identical in shape between them
  - `SupervisedPublisher(Supplier<Flow.Publisher<T>> opener, Consumer<Throwable> onOutageBegan, ScheduledExecutorService scheduler)` — production ctor, uses `INITIAL_BACKOFF_NANOS`(1s)/`MAX_BACKOFF_NANOS`(30s); a package-private 5-arg ctor takes explicit backoff bounds instead (test seam, mirrors `StreamPipeline`'s own `LongSupplier`-taking test ctor) — both `DefaultStreamService`/`UsageTracker` gained their own matching package-private test-seam constructors purely to thread smaller bounds through for fast tests, production always uses the defaults
  - `subscribe(Flow.Subscriber<? super T> subscriber)` — opens the source (`opener.get()`) and forwards `onSubscribe`/`onNext` straight through to `subscriber`, untouched; `onError`/`onComplete` are intercepted, **never forwarded downstream** — the wrapped subscriber (`StreamPipeline`/`UsageTracker`'s `TelemetrySubscriber`) never sees a source ending at all, only the normal traffic. On interception: `onOutageBegan` runs **exactly once per outage** (not once per failed retry — mirrors `StreamPipeline`'s own detection-outage and `MediamtxStreamPublisher`'s own publish-outage "one log/event per outage" convention, chosen for consistency with those two pre-existing precedents), then a retry is scheduled after the current backoff, which then doubles (capped). The outage ends — and backoff resets to `initialBackoffNanos` — the moment an item actually flows again (`onNext`), not merely once a reopen attempt starts (a source can fail again immediately after a superficially successful resubscribe)
  - `stop()` — cancels any pending scheduled retry (`ScheduledFuture#cancel(false)`) and permanently disables further retries via an `AtomicBoolean`; idempotent; does **not** close whatever source/subscription is currently open — that stays the caller's own responsibility, unchanged from the unsupervised case
  - A synchronous exception from `opener.get()` itself (not just an async `onError`) is caught and funneled through the exact same `ended(...)` path — otherwise a `ScheduledExecutorService` silently swallows an uncaught exception from a fire-and-forget scheduled `Runnable`, permanently and invisibly ending retries
  - **What it deliberately doesn't do:** publish any event itself — `onOutageBegan` is the caller's own callback (`DefaultStreamService` publishes `PIPELINE_ERROR`; `UsageTracker` passes a no-op, see its own entry below for why)
- **`DetectionExtrapolator`** (package-private, final, no interface — docs/CYCLES-PLAN.md §12, CP-c) — internal collaborator of `StreamPipeline`, one instance per pipeline; smooths burned-in boxes between completed inferences instead of freezing them at the latest result until the next one lands
  - `void accept(DetectionResult result)` — keeps only the two most recent results (previous `P`, latest `L`); a `result.frameSequence()` &le; the current `L`'s is ignored (detection completions can land out of order relative to sampling order)
  - `List<Detection> at(Instant t)` — no result yet: `List.of()`. Only `L` (or `L`'s detections are empty): `L.detections()` unchanged. Both `P` and `L`, non-empty `L`: greedy nearest-box-center matching of `L`'s detections to `P`'s (same `label`, gated at **0.15** normalized center distance, each side matches at most once); a matched detection's center is extrapolated along `Δcenter/Δt` (velocity) to `min(t, L.capturedAt()+800ms)` (`MAX_EXTRAPOLATION_MILLIS`, package-private) — `L`'s width/height are kept, `x`/`y` clamped to `BoundingBox`'s `[0,1]` per-component range; a zero/negative `Δt` between `P` and `L` (degenerate/duplicate timestamps) skips extrapolation entirely (returns `L.detections()`). Unmatched `L` detections pass through as-is; `P`-only detections are dropped. Never throws, never returns `null`.
  - Both methods `synchronized` — called at most once per sampled/published frame by `StreamPipeline`, never on a hot loop.

  - **Overlay burn-in** (docs/MVP1-PLAN.md §C8 bullet 2, smoothed per docs/CYCLES-PLAN.md §12 CP-c, optional per docs/MVP2-PLAN.md §V, V-e, telemetry input added by the backend follow-up batch, `overlayIfNeeded`): every completed detection result feeds a private `DetectionExtrapolator` (`extrapolator.accept(result)`, same call site as the `latestDetections` update) — this happens **unconditionally**, regardless of `overlayBurnIn`, since it's cheap bookkeeping over at most two results, not the cost the flag exists to avoid (see below). Before every `streamPublisherPort.publish`, if `overlayPort != null` **and** `config.overlayBurnIn()` is `true` **and** either `extrapolator.at(frame.capturedAt())` is non-empty **or** a telemetry sample resolves (see next paragraph), the frame is rendered via `overlayPort.render(new AnnotatedFrame(frame, detections, telemetry))` and the renderer's returned instance is published instead of the raw frame; otherwise (no `overlayPort`, burn-in disabled, or nothing to draw at all) the raw frame is published unchanged. Detection sampling always runs against the **raw** frame, never the rendered one. A renderer exception is swallowed (never a pipeline failure): the raw frame publishes instead, and a plain boolean latch (`overlayFailureLogged`, reset on the next successful render) limits the `WARNING` log to once per failure run rather than once per frame — rendering itself is still retried on every frame (unlike detection's outage/backoff skip policy), only the logging is throttled. **What `overlayBurnIn=false` actually skips** (V-e, verified by reading `overlayIfNeeded` rather than assumed): the `extrapolator.at(...)`/telemetry-sample lookups themselves (box matching/velocity-extrapolation math, the supplier call), `OverlayPort#render`'s Java2D work (decode/allocate a fresh `BufferedImage`, draw boxes/OSD, re-encode), and the extra `VideoFrame` instance `render` returns — every publish instead falls straight through to the already-decoded raw frame from the source.   - **Two distinct failure policies** (docs/MVP1-PLAN.md §C7 bullet 3 — a failing/absent CV service can never kill or degrade the video path):
    - **Source errors** (`onError`) and any `RuntimeException` thrown synchronously while publishing are fatal, unchanged from before: one `PIPELINE_ERROR` event, then `close()` (cancels the subscription, signals `streamEnded`).
    - **Detection failures** (an exceptionally-completed `CompletionStage` from `DetectionPort#detect`, including timeouts) never close the pipeline and never touch the video path — a failed frame's detections are simply absent. The first failure enters a detection **outage**: exactly one `PIPELINE_ERROR` event (message names the cause), and until recovery, sampled frames are withheld from `DetectionPort` entirely — skipped as an in-flight-bound skip is, and likewise never counted against `maxInFlightInferences` or queued — while an exponential backoff counts down: `INITIAL_BACKOFF_NANOS`=1s, doubling on each failed probe, capped at `MAX_BACKOFF_NANOS`=10s (both package-private). Once the backoff deadline passes, **exactly one probe inference** is attempted (an internal `probeInFlight` flag, guarded together with the deadline check under one `synchronized` block, prevents a second concurrent probe even if several sampled frames land inside the same window): success ends the outage (logged via `System.Logger` at `INFO`, no second event) and detection resumes normally; failure doubles the backoff and the outage continues under the single original event. Subsequent failures during an outage — whether the probe's or from a call already in flight when the outage began — are counted (`outageFailureCount`, surfaced in the recovery log line) but never raise a second event; only a failed **probe** doubles the backoff, so a stray already-in-flight failure can't perturb a backoff a probe has already advanced. Any successful detection, in or out of an outage, resets the backoff to its initial interval. A later, independent outage raises its own new single event.
    - All outage/backoff state (`inOutage`, `probeInFlight`, `backoffNanos`, `nextProbeAtNanos`, `outageFailureCount`) is plain (non-volatile/non-atomic) fields guarded by one dedicated lock object (`outageLock`), not volatile/`Atomic*` like the frame-cadence fields — unlike `onNext`'s per-signal serialization, outage-entry/probe decisions and detect() completion callbacks race genuinely (completions can land on an arbitrary executor thread), and the relevant checks (e.g. "claim the probe slot AND read the deadline") must be one atomic step; a `synchronized` block was chosen over hand-rolled volatile-publish ordering for reviewability, and contention is a non-issue since it's only entered around sampled-frame decisions and (in/out of) outage transitions, never on the hot per-frame publish path. All backoff timing runs off the same injectable `LongSupplier nanoTimeSource` seam as the frame-cadence measurement, so tests drive it synthetically (see Gotchas).
  - **Live per-stream CV control** (docs/CV-CONTROL-PLAN.md, Wave C): the `config` field is now **`volatile`**, not `final` — every per-frame read already went straight through the field (`inferenceFps`/`maxInFlightInferences` in sampling, `overlayBurnIn`/`overlayTelemetry` in `overlayIfNeeded`/`telemetrySampleFor`, the whole `config` passed into `detectionPort.detect`), so a `volatile` write is visible to the very next frame with no lock, no restart, and no stream/usage-session/SSE disruption.
    - `PipelineConfig config()` — the current live config; the merge base `DefaultStreamService#updateConfig` folds a `PipelineConfigPatch` onto.
    - `void updateConfig(PipelineConfig next)` — swaps `config`. **detectionEnabled/labelFilter/confidence/inferenceFps** are hot: nothing else runs, the next sampled frame's live reads simply see the new values. **Model-id change** (`next.model().id()` differs from the running model): additionally clears this pipeline's own model-bound bookkeeping — `extrapolator.reset()` (new package-private method on `DetectionExtrapolator`, clears both remembered results) and `latestDetections` back to `List.of()` — so no stale, wrong-model detection lingers (extrapolated against, shown, or persisted) across the swap; `latestDetections()` reads empty again until the new model's first result completes. The very next sampled frame's `detectionPort.detect(frame, next)` call already carries the new model, per `DetectionPort`'s own per-call contract.
      - **Re-arm limitation, honestly documented (not a full session teardown+reopen)**: `DetectionPort` (vision-domain) exposes only `detect(frame, config)` — no per-stream session lifecycle method a generic caller can invoke (deliberately: "batching, streaming, and connection reuse are adapter concerns," per that port's own javadoc). The `streamEnded(StreamId)` lifecycle hook the CV-CONTROL-PLAN references (adapter-cv-grpc/MODULE.md) exists only on the **concrete** `GrpcDetectionPort` class, never on the `DetectionPort` interface `StreamPipeline`/`DefaultStreamService` are wired against — and this module must not depend on adapter-cv-grpc to reach it. So this pipeline cannot force whatever adapter-side session a concrete `DetectionPort` implementation keeps to actually close and reopen; clearing this pipeline's own state plus passing the new model on every subsequent call is the cleanest re-arm expressible from `vision-application` alone. Whether an adapter's session actually switches models on the very next call, versus keeping one cached against the stream's first-seen model, is that adapter's own concern — verified (at the time of writing) for cv-service, whose `ModelRegistry.resolve(request.model_id)` already resolves **per request**, not per gRPC session, so passing a new model id through already routes correctly there without any adapter change. A future adapter that genuinely needs an explicit close+reopen signal would need a lifecycle method added to `DetectionPort` itself — a `vision-domain` change, out of Wave C's file scope.
  - **`maybeDetect` gates on `config.detectionEnabled()` first**, before the outage/in-flight logic: `false` returns immediately, so a disabled stream spends zero CPU on inference and stops probing during an outage too (nothing below the check ever runs — no `DetectionPort` call, no outage-probe attempt). Re-enabling resumes on the next sampled frame, exactly where the (frozen, untouched) outage/backoff state left off — outage state is not reset by a detection on/off toggle, only by an actual detection success/failure.
  - **`labelFilter` enforcement — the dormant-field fix** (docs/CV-CONTROL-PLAN.md §A): a private `applyLabelFilter(DetectionResult)` drops every detection whose label is not in `config.labelFilter()` (empty = keep all, unchanged semantics), called **once, centrally**, at the top of `onDetectionResult` — before the result reaches `latestDetections`, `extrapolator.accept` (and therefore overlay burn-in), `eventEngine`, `liveUpdatePublisherPort`, or persistence/the `DETECTION` event. Every downstream consumer therefore sees the same filtered set uniformly; returns the same `DetectionResult` instance unchanged when nothing was actually dropped (no allocation in the common no-filter/all-match case).

Audited once per attempt (`DENIED:out of scope` or `STARTED`) against `AuditTargetType.MODEL` keyed by the generated job id (an opaque target id, per that enum's own javadoc), `AuditAction.CREATED` — a new job resource, unlike `promote`'s update-shaped `AuditAction.UPDATED` over an existing model reference. Progress updates, upload-phase notes, and terminal completion are **not** individually audited — a poller already observes them via `job(jobId)`, and auditing every tick would flood the trail for no security benefit
  - `List<TrainingJobView> jobs()` / `Optional<TrainingJobView> job(String jobId)` — unscoped, unaudited reads (any authenticated caller may poll), mirroring `ModelRegistryService#models()`'s precedent; `jobs()` is newest-first by `startedAt`. Backed by a `ConcurrentHashMap<String, TrainingJobView>` — a job's entry is *replaced*, never mutated in place, on every update, so a reader never sees a torn read across its fields. **Bounded retention**: finished jobs (terminal `SUCCEEDED`/`FAILED`) are tracked oldest-first in a companion `ConcurrentLinkedDeque`; once more than `MAX_FINISHED_JOBS` (package-private, 50) have finished, the oldest is evicted from the map — a still-`RUNNING` job is never evicted, only completions count toward the cap. Best-effort, not a hard invariant (two completions racing the size check can rarely leave the map one entry over; self-corrects on the next completion)

## Conventions
- No Spring/framework imports anywhere in this module (Spring only appears in adapters/vision-app/vision-api).
- **The acting user is a method parameter (`UserId actor`), never a constructor dependency** — it varies per request; the API edge resolves it from the token and passes it down.
- Constructor injection only; every collaborator is wrapped in `Objects.requireNonNull(x, "x must not be null")` **except** `DefaultStreamService`'s `usageTracker`/`overlayPort`/`detectionEventRepositoryPort`/`liveUpdatePublisherPort`, `StreamPipeline`'s `overlayPort`/`eventEngine`/`assetId`/`liveUpdatePublisherPort`, `UsageTracker`'s own `liveUpdatePublisherPort`/`geofenceMonitor`, `DetectionEventEngine`'s own `usageTracker`, and `GeofenceMonitor`'s own `eventPublisher`/`liveUpdatePublisherPort`, all deliberately left nullable so the classes stay trivially testable/usable without those collaborators.
- Injected collections are defensively copied at construction (`List.copyOf`/`Map.copyOf`): `VideoSourceRegistry.sources`, `DefaultDiscoveryService.portsByMethod`, `UsageTracker.telemetrySources`.
- Virtual threads: `DefaultDiscoveryService.scanAsync` starts one `Thread.ofVirtual()` per requested discovery port per scan call; a hung adapter's thread is never tracked or interrupted (cheap + daemon, so it never blocks JVM shutdown). Same idiom, docs/MVP2-PLAN.md §S, S-a: `DefaultStreamService#stop`/`UsageTracker#unsubscribeTelemetry` each fire one `Thread.ofVirtual()` to run the actual (possibly slow) `close()` calls off the caller's thread.
- Concurrency primitives: `ConcurrentHashMap` for shared registries (`DefaultStreamService.activeStreams`/`streamByDevice`, `UsageTracker.trackingByAsset`); `AtomicInteger`/`AtomicBoolean` for pipeline counters/close-flags; `volatile` for single-writer/many-reader fields (`StreamPipeline.latestDetections`/`subscription`). docs/MVP2-PLAN.md §S, S-a added this module's first `ScheduledExecutorService` usage (previously only in adapters, e.g. `adapter-simulation`'s per-instance schedulers) — `DefaultStreamService`/`UsageTracker` each own **one** dedicated daemon-thread `Executors.newSingleThreadScheduledExecutor`, shared across every stream/subscription that class supervises, scheduling `SupervisedPublisher`'s reopen retries; see that class's own Gotcha entry for why one shared thread per service is judged sufficient rather than per-stream.
- `Flow.Subscriber` pattern used identically in two places — `StreamPipeline` (video) and `UsageTracker.TelemetrySubscriber` (telemetry) — both request exactly one item at a time and re-request after processing.
- Per-asset mutable state in `UsageTracker` (`Tracking`) is synchronized on the `Tracking` instance itself, not a module-wide lock — different assets' start/stop/telemetry never contend.

## Gotchas
- `StreamPipeline`'s sampling rate is driven by a *measured* source cadence (EWMA of inter-frame-arrival deltas), not a fixed assumption — but the measurement only starts being trusted after `WARMUP_FRAMES`=5 frames, and the EWMA is seeded directly from the first observed delta (not blended toward the 30fps fallback) so a constant-cadence source converges immediately once warmup ends, rather than drifting in slowly. A source whose rate changes *during* a stream still tracks (recomputed every frame), but a source that starts, drifts wildly, then stabilizes will have a skewed effective inference FPS for its first 5 frames.
- In-flight inference bound is **skip-not-queue**: once `maxInFlightInferences` in-flight calls are outstanding, `StreamPipeline` drops the sampled frame outright rather than buffering it — a slow `DetectionPort` degrades detection *rate*, never blocks the video path. Frames skipped because of an in-flight detection outage's backoff window are likewise never counted as in-flight — they never reach `inFlightInferences` at all, only the separate `probeInFlight` flag applies to them.
- `StreamPipeline.close()`/source-error handling both funnel through one `AtomicBoolean` CAS; a detection completing *after* close is a silent no-op regardless of outage state (`closed.get()` re-checked inside the `whenComplete` callback, before any outage/backoff bookkeeping runs).
- **A detection failure never closes `StreamPipeline`** (docs/MVP1-PLAN.md §C7 — changed from the pre-C7 behavior where any detection failure closed the pipeline exactly like a source error). Only `onError` (source) and a synchronous `RuntimeException` from `publish()`/the sampling call are still fatal. Get this wrong and a flaky/absent CV service takes the whole video path down with it, defeating the point of the outage/backoff machinery.
- **One `PIPELINE_ERROR` event per outage, not per failed frame.** The event fires exactly once, on the transition into outage (`inOutage` false→true); every failure after that — including every failed retry probe — is silently counted (`outageFailureCount`) and never raises a second event. Don't be tempted to move the event into the probe-failure branch "for visibility" — that reintroduces per-frame spam under a sustained outage, exactly what this design avoids.
- **Only a failed *probe* doubles the backoff** — a detection call that was already in flight (not gated by the outage) when the outage began can still complete with a failure afterward, and that failure must be counted silently *without* touching `backoffNanos`/`nextProbeAtNanos`, or a slow straggler could stomp a backoff a probe already advanced.
- **Exactly one probe in flight at a time.** `probeInFlight` and the deadline check (`nextProbeAtNanos`) are read/claimed together inside one `synchronized (outageLock)` block in `outageDecision()` — checking them as two separate lock-free reads would let a racing thread observe `inOutage` freshly `true` before its paired backoff fields are visible, either starting a second concurrent probe or skipping the very first backoff window outright.
- `DefaultStreamService` allows only one active stream per device (Phase 0 scope) — starting a second throws `IllegalStateException` rather than replacing the existing stream.
- `UsageTracker` drops a telemetry sample that arrives after its usage has closed (`tracking.usage == null`) instead of reopening a new usage for it.
- **`UsageTracker.onStreamStarted`'s `streamId` param is only ever recorded on the call that opens the usage** (docs/MVP2-PLAN.md R-a2) — for an asset with several devices, only the **first** device's stream is ever visible on `AssetUsage#streamId`; a second/third device starting later (while the usage is already open) passes its own `streamId` in, but that argument is simply discarded on that path. This mirrors the pre-existing "first currently-active device opens the usage" rule exactly — no new asymmetry, just extended to a new field.
- **Overlay rendering is now wired in** (docs/MVP1-PLAN.md §C8 bullet 2 — supersedes the earlier "not wired in yet" note): `StreamPipeline`'s `overlayPort` is nullable, so a caller that never passes one (or explicitly passes `null`, `DefaultStreamService`'s own default) sees zero behavior change. **Telemetry burn-in is now reachable too** (backend follow-up batch — supersedes this Gotcha's own earlier "still not reachable" note, and the matching note in adapter-overlay/MODULE.md, which this module's file scope cannot update but which is now stale): `StreamPipeline` gained a nullable `telemetrySupplier` constructor parameter (13-arg public ctor), and `DefaultStreamService#start` builds one from `usageTracker.latestTelemetry(assetId)` whenever `usageTracker`, `overlayPort`, and a resolved owning `assetId` are all present. `AnnotatedFrame`'s `telemetry` component is `null` exactly when any of `overlayPort`/`config.overlayTelemetry()`/`telemetrySupplier` is absent, or the supplier itself returns/throws nothing usable — otherwise it activates.
- **`StreamPipeline` now has two distinct detection surfaces — do not conflate them** (docs/CYCLES-PLAN.md §12, CP-c): `latestDetections()` is the raw, most-recently-completed result (unchanged since C7/C8, and what REST/audit/persistence consumers should read), while overlay burn-in renders `DetectionExtrapolator.at(frame.capturedAt())` — a *smoothed* view with the same element count as `latestDetections()` (every `L` detection yields exactly one output, matched-and-extrapolated or unmatched-as-is; `P`-only detections are simply never in `L`'s list to begin with) but whose **positions** can differ (a matched detection's box is moved toward its predicted position, frozen once `MAX_EXTRAPOLATION_MILLIS` past `L.capturedAt()` elapses) while `latestDetections()` stays exactly as last set either way. Wiring a new consumer of "what's currently detected" onto the wrong one of these two is an easy, silent bug — only the overlay renderer wants the extrapolator's output.
- **`DetectionExtrapolator.accept`'s out-of-order guard is `frameSequence` &le;, not `<`** — a detection completion whose `frameSequence` equals the current latest's (e.g. a duplicate/retried completion for the same sampled frame) is ignored exactly like a strictly-older one, not treated as a legitimate update. This mirrors `StreamPipeline`'s own tolerance for inference completions racing/landing out of order (see the detection-outage Gotchas above) — sampling order and completion order are not guaranteed to match once more than one inference can be in flight (`PipelineConfig#maxInFlightInferences`).
- `DefaultDiscoveryService` cross-method merge only triggers for a group spanning 2+ *distinct* methods — two candidates from the *same* method that happen to land in the same network-identity group (e.g. two mDNS services on one host) are intentionally left unmerged, passed through exactly as the exact-`(method,address)` dedup pass would have produced them.
- `DiscoveredDevice.method`'s compact constructor only rejects blank/null — no single-token or lower-case pattern (unlike `StreamDescriptor.protocol` or `CategoryId.slug`) — so a merged, `"+"`-joined value like `"mdns+onvif"` is valid without any `vision-domain` change. `DeviceDiscoveryPort.method()`'s own javadoc ("stable lower-case key") still applies to each *individual* port's method key, not to this merged/derived field.
- `UsageTracker.TelemetrySubscriber.onError` is an empty method (comment-only) by design — a telemetry source failure is completely silent, not even logged, because best-effort telemetry must never affect stream/usage lifecycle.
- **`DefaultSimulationService`'s RX-side timeout augmentation is not optional, and is RTSP-only.** `FfmpegVideoSource`'s default RTSP `timeout`/`rw_timeout` is 10s; running it (RX) in the same JVM as `RtspFeedTransmitter` (TX) against the same mediamtx path — exactly what `transport=RTSP` creates — causes the transmitter's own grab/record loop to stall for ~10s before mediamtx drops the connection and the transmitter's next write fails with EPIPE. `DefaultSimulationService.RTSP_RX_TIMEOUT_MICROS` ("2000000" = 2s) is added to the transmitter-returned `StreamDescriptor`'s options for exactly this reason — see adapter-rtsp/MODULE.md Gotchas for the full empirical writeup this fix is based on. `transport=MJPEG` never gets this augmentation: the mjpeg TX/RX pair has no same-JVM contention (proven by adapter-mjpeg's own in-process round-trip IT and by `MjpegSimulationSmokeTest` in vision-app), so its `StreamDescriptor` is registered exactly as the transmitter returned it.
- **`DefaultSimulationService.RTSP_FEED_ESTABLISH_DELAY_MILLIS` (1000ms) is an empirically-required fixed delay, also RTSP-only**, paid only when `transport=RTSP` and `autoStart=true`, between `feedTransmitter.start()` returning and `assetService.startStream()` opening the RX side: `RtspFeedTransmitter`'s transmit thread takes on the order of tens of milliseconds to reach mediamtx's ANNOUNCE/SETUP/RECORD handshake, and mediamtx answers an RX `DESCRIBE` for a not-yet-published path with a bare 404 — not a "retry me" signal. `FfmpegVideoSource` has no reconnect logic (a single failed connect permanently kills that `StreamPipeline`, emitting one `PIPELINE_ERROR` event), so without this delay `startStream` reliably raced ahead of the transmitter and the simulated stream died before a single frame flowed (reproduced while writing `RtspSimulationDockerE2ETest` in vision-app: the RX side logged `avformat_open_input()` failing with a 404 within ~15ms of `STREAM_STARTED`, while the transmitter's own "Transmitting..." log line didn't appear until ~50-80ms later). This is exactly the caller-side responsibility `FeedTransmitterPort#start`'s own javadoc calls out ("callers that need frames to actually be flowing before opening the RX side must poll or retry rather than assume readiness"); a fixed delay matching the margin adapter-rtsp's own `MediamtxDockerIntegrationTest` already validated empirically is the simplest thing that could work, given `vision-application` must stay framework/dependency-free (so no FFmpeg-based readiness probe belongs here). A manually-started stream (`autoStart=false`, started later via a separate call) never pays this delay and doesn't need to — by then the feed has long since been established. `MjpegFeedTransmitter#start` only returns once its HTTP context is registered on an already-listening server, so `transport=MJPEG` never needs (or pays) an equivalent delay — its very first RX connection attempt already succeeds.
- **`FeedTransmitterRegistry.transmitterFor` probes every candidate's `supports()` in order until one matches**, exactly like `VideoSourceRegistry` — an earlier-registered transmitter that doesn't support the requested protocol still has `supports()` called on it (a real interaction, visible to a strict mock verification) even though it is never `start()`ed/`stop()`ped.
- **`DefaultSimulationService.feedByAsset` is pure in-memory bookkeeping — a `transport=RTSP`/`MJPEG` simulation's TX feed never survives a JVM restart on its own, even with `vision.persistence.enabled=true`.** Originally found investigating a real "frozen video" report: an RTSP-loopback simulated asset (category `simulated`, video device `protocol="rtsp"`, `uri=rtsp://<rtsp-push-base>/feed-<uuid>`) survived a backend restart in Postgres exactly as designed (docs/MVP2-PLAN.md P-a/P-b), but its `RtspFeedTransmitter` push to mediamtx did not — mediamtx showed nothing publishing that path, and `adapter-rtsp`'s RX side (whatever re-requested the stream after the restart — a user action or the frontend's own reconnect logic) retried `DESCRIBE` against it forever, 404 every time (see adapter-rtsp/MODULE.md's own Gotcha for the RX-side silent-endless-retry half of this, now fixed to at least log it). **Root cause, by file:line**: `feedByAsset` (`private final Map<AssetId, TrackedFeed> feedByAsset = new ConcurrentHashMap<>()`, this class, populated only in `simulate()` and read/removed only in `stop()`) is the *only* record of "this asset's video device is backed by a live TX transmitter, started from this file, with this `FeedId`" — and it lives purely in this service instance's JVM heap. A restart starts with an empty map.
  - **Why it can't be trivially bolted on**: nothing persisted distinguishes "this RTSP-protocol device is one of our own TX-fed simulation feeds" from "this is a real external RTSP camera" — both are just `Device(protocol="rtsp", uri=<something>)` once written to `AssetRepositoryPort`/`DeviceRepositoryPort`. `AssetSpec#attributes`' `source` key (the resolved video file path, set for *any* non-null-`videoPath` transport including plain `DIRECT`/`file`) isn't transport-specific either. The one honestly-reliable signal is structural, not stored: an RTSP device whose `uri` host:port matches the app's own configured mediamtx push target (`VisionPublishProperties.Mediamtx#rtspBase()`, vision-app) is *always* one of this app's own feed-transmitted assets — this architecture never registers a real external camera against mediamtx's own RTSP ingest port, only ever pushes *to* it — and the `feed-<uuid>` path segment already round-trips a valid `FeedId.of(String)` (vision-domain).
  - **Fixed (backend follow-up batch): `#resumeAll()`** — exactly the heuristic above, implemented: for each persisted, `ACTIVE`, `simulated`-category asset whose video device's `uri` matches the mediamtx push-base, parses `FeedId.of(...)` back out of the URI's `feed-` segment, rebuilds a `FeedSpec` from `attributes.source` (the video file path) + protocol `"rtsp"`, and calls `feedTransmitters.transmitterFor(feedSpec).start(feedId, feedSpec)` — deliberately *not* going through `simulate()` (which always creates a brand-new asset+devices) or a fresh `FeedId.random()` (which would orphan the persisted device's own already-stored URL). `vision-app`'s `SimulationResumeRunner` (an `ApplicationRunner`, gated on `vision.persistence.enabled` **and** the new `vision.simulation.resume-on-boot`, both must be true — the in-memory profile has nothing to restore after a restart anyway, its `feedByAsset`/repositories are both wiped together) calls it once the context is up. See `#resumeAll`'s own API-surface entry above for the full mechanics, and `vision-app`/MODULE.md for the runner/property.
- **`DefaultReplayService.timeline`'s detections are real as of docs/MVP2-PLAN.md R-a2** — `AssetUsage#streamId` (vision-domain) is the join key, recorded once at open time by `UsageTracker`; a `null` `streamId()` (a usage opened before R-a2, or by an asset with no video device) still yields an honestly empty detections list rather than a guessed join — there remains no reliable fallback for those. Unlike telemetry's fetch-then-filter workaround, the detections query *is* genuinely time-bounded (`DetectionRepositoryPort#query` takes `from`/`to` directly), so it doesn't share telemetry's "silently drops whatever's past the fetch cutoff" failure mode — but it has the mirror-image one: the port's real implementations return newest-first with `limit` already applied, so a stream with more than `DETECTION_FETCH_LIMIT` (20,000) results *inside* the requested window loses its **earliest** ones, not its latest. `DetectionQuery#to()`'s own javadoc calls it exclusive, but `DefaultReplayService` passes the resolved window's `to` straight through as-is, relying on every real `DetectionRepositoryPort` implementation actually treating it as inclusive (see `adapter-persistence`'s `JpaDetectionRepository` javadoc/MODULE.md) — exactly the same inclusive-both-ends semantics this class already uses for telemetry, so the two series stay consistent at the window edges.
- **`DefaultReplayService`'s telemetry fetch is a workaround, not a real time-bounded query** — `TelemetryRepositoryPort#findByUsage(usageId, limit)` has no `from`/`to` parameters at all, and its `limit` selects the usage's **earliest** samples (see the port's javadoc and `adapter-persistence`'s `JpaTelemetryRepository`, which deliberately preserves this exact semantic). `DefaultReplayService` fetches up to `TELEMETRY_FETCH_LIMIT` (20,000) samples and filters/thins the requested window out of that fetch in memory. For a usage with more than 20,000 total telemetry samples (at 1Hz, ~5.5 hours of continuous flight), any window whose data falls after that cutoff is silently missing from the response, **even if the caller's `to` explicitly asks for it** — there is no way to detect or signal this truncation from inside this method, since the port gives no total-count or "more available" signal either. The real fix is a time-bounded query added to `TelemetryRepositoryPort` (`adapter-persistence/MODULE.md` already flags the `findByUsage` ordering oddity as a future contract-cleanup item for exactly this reason) — not attempted here, per this task's explicit instruction not to change the port.
- **`ReplayService#timeline`'s `to` default for an open usage is resolved eagerly, once, at call time** (`Instant.now()`) — there is no clock/`Supplier<Instant>` injection seam (unlike `StreamPipeline`'s `nanoTimeSource`), since a single wall-clock read per request has no meaningful test-flakiness risk here; tests bracket the call with `Instant.now()` calls before/after instead of injecting a fake clock.
- **`DetectionEventEngine.accept`'s per-label absence check only ever runs when a new `DetectionResult` completes** (docs/MVP2-PLAN.md §E, E-a) — there is no background timer independently ticking `absenceToClose` forward. Under normal operation this is a non-issue (completed results keep arriving at roughly `inferenceFps`, so a genuine absence is detected within about one sampling interval of the configured window), but during an actual `StreamPipeline` detection **outage** (see that class's own outage/backoff Gotchas), sampled frames are withheld from `DetectionPort` entirely and no results complete at all — an event left open when the outage began stays open, un-evaluated, until detection recovers and the next completed result's timestamp reveals the gap. This mirrors the deliberate "no extra threads for a soft/cosmetic concern" posture already established for overlay rendering, rather than adding scheduler machinery to this module (which must stay framework-free).
- **`DetectionEvent#position` is frozen at open time, not live-tracked** (docs/MVP2-PLAN.md §E, E-a) — `DetectionEventEngine.open` calls `usageTracker.latestPosition` exactly once, when the event transitions from candidate-streak to `OPEN`; every subsequent `withObservation` call (while the event stays open) only touches `lastSeen`/`peakConfidence`, never `position`. An event open for a long-moving asset therefore reports where it *was* when first confidently seen, not where it *is now* — judged an acceptable first-cut tradeoff (the map can separately show "where is it now" from the asset's own live position), not an oversight; live-tracking the position would mean re-querying `usageTracker` on every still-open update, which is easy to add later if a real need shows up.
- **`PipelineConfig#eventRule`'s labels are independent of `labelFilter`** — `labelFilter` (existing, gates what `DetectionPort` even returns) and `EventRuleConfig#labels` (new, gates what `DetectionEventEngine` debounces into events) are two separate label sets with no cross-validation between them. Configuring `labelFilter={"car"}` while `eventRule.labels()` still defaults to `{"person","car"}` is valid but means "person" events can never actually open (the label never reaches the engine in the first place) — this is not treated as a configuration error, since a filtered-out label silently having no events is the same "no data, not a failure" shape every other empty-result path in this class already has.

- **docs/MVP2-PLAN.md §S, S-a — source supervision, what survives a reconnect vs. what re-establishes.** The whole mechanism is one `Flow.Publisher` decorator (`SupervisedPublisher<T>`, see its own API-surface entry) interposed **before** the pipeline/subscriber is ever constructed, not a change to `StreamPipeline`/`TelemetrySubscriber` themselves — `StreamPipeline.java` has **zero** lines changed by this task. Concretely, per reconnect:
  - **Survives untouched, exactly once per stream (never repeated by a reconnect):** the `StreamPublisherPort` session — `streamStarted`/`streamEnded` fire only at `DefaultStreamService#start`/`#stop`, since `StreamPipeline.start()` (which calls `streamStarted`) is invoked exactly once and a reconnect never calls it again, it just resubscribes the *same* still-running pipeline instance to a freshly-opened publisher. This was explicitly called out as "even better" if achievable, and it falls out for free from the decorator design rather than needing special-casing — confirmed by reading `MediamtxStreamPublisher`, which would otherwise reset its cadence-measurement/GOP state on every `streamStarted` (see that adapter's own `StreamState`). Also surviving untouched: the `UsageId`/`AssetUsage`/`streamId` (`UsageTracker#onStreamStarted`/`#onStreamStopped` likewise fire only once per stream, never on a reconnect — a device's "active" count in `UsageTracker.Tracking` never changes during supervised retries, so the usage-open/close accounting has nothing to react to); `StreamPipeline`'s own detection-outage/backoff state, `latestDetections()`, and the `DetectionExtrapolator`/`DetectionEventEngine` instances (all pipeline-instance state, and the pipeline instance itself never changes).
  - **Re-establishes on every reconnect:** only the actual source-side `Flow.Publisher`/`Flow.Subscription` — a fresh `VideoSourcePort#open`/`TelemetrySourcePort#open` call each time, each producing whatever fresh per-open state the *adapter* itself resets (see the frame-sequence Gotcha below).
  - **`PIPELINE_ERROR` policy: once per outage, not once per failed attempt** — the same choice `StreamPipeline`'s own detection-outage machinery and `MediamtxStreamPublisher`'s own publish-outage machinery already made, for consistency with two pre-existing precedents in this exact codebase rather than inventing a third convention. Telemetry supervision (`UsageTracker`) does **not** publish `PIPELINE_ERROR` at all, even though the video path does — `UsageTracker` has no `EventPublisherPort` dependency and no `StreamId` to publish an event against (telemetry is tracked per-device/asset, not per-stream), and `TelemetrySubscriber#onError` was already, deliberately, a silent no-op *before* this task (see below) — adding a brand-new constructor dependency purely to emit an event for a class whose failures were always silent by design was judged out of scope; reconnection with backoff is the actual resilience requirement and is fully delivered either way.
  - **Backoff: 1s→30s, doubling, uncapped in count** (`SupervisedPublisher.INITIAL_BACKOFF_NANOS`/`MAX_BACKOFF_NANOS`) — a deliberately different magnitude from `StreamPipeline`'s own detection-outage backoff (1s→10s) and `MediamtxStreamPublisher`'s own publish backoff (500ms→10s): reconnecting a whole video/telemetry *source* (a real network/USB/process-level operation) is more expensive to hammer than either of those two finer-grained, in-process retry loops, and 30s matches this row's own plan text verbatim.
  - **Frame/sample sequence numbers are *not* guaranteed monotonic across a reconnect, and this task does not fix that** — `StreamPipeline` never generates `VideoFrame#sequence()` itself, the *adapter* does (e.g. `adapter-rtsp`'s `FfmpegVideoSource` keeps a per-`StreamRuntime` `AtomicLong` that starts fresh at 0 on every `open()` call), and `SupervisedPublisher` calls `open()` again on every retry, creating a brand-new adapter-side runtime each time. Fixing this would mean either renumbering frames in the wrapper (extra allocation/complexity on the hot per-frame path, for a cosmetic concern) or changing every adapter's own sequence bookkeeping (out of this task's `vision-application`-only scope) — documented honestly rather than silently assumed away. Functionally harmless: `StreamPipeline`'s own sampling modulo (`frame.sequence() % sampleEveryNthFrame`) still works correctly against the reset sequence, it just restarts its cycle.
  - **A brief, bounded, non-leaking race is possible between an explicit `stop()` and an in-flight reopen attempt** — `SupervisedPublisher.stop()` sets `stopped=true` and cancels the pending `ScheduledFuture`, but if a scheduled retry's `openAndSubscribe` had *already* passed its own `stopped.get()` check (a narrow window, since `stop()` runs synchronously and immediately after `DefaultStreamService.stop()`'s map removal, while a retry can only fire after its own backoff delay elapses) before `stop()` ran, that one attempt still calls `opener.get()`/`subscribe()`. This never leaks: `DefaultStreamService#stop`/`UsageTracker#unsubscribeTelemetry` unconditionally call the underlying port's own `close(id)` afterward regardless of supervision state, and every real adapter's `close`/`open` pair is keyed by the same `StreamId`/`DeviceId`, so whatever the stray attempt opened gets closed by that same call. `StreamPipeline.onSubscribe` was **not** touched to add a matching guard, since `StreamPipeline` has no visibility into `SupervisedPublisher`'s `stopped` flag at all (by design — see above) and doesn't need one, this race is fully absorbed one layer down.
- **`GeofenceMonitor`'s per-`(assetId, zoneId)` breach state is in-heap only and resets on every restart** (docs/OPS-CORE-PLAN.md §G) — an asset that was already inside a `KEEP_OUT` zone when the JVM restarted is treated as freshly entering it on the very next sample afterward (a spurious "enter" event, not a missing one), and conversely a zone deleted/disabled while an asset was breaching it never gets a synthetic "exit": its state entry is simply never touched again once the zone drops out of the enabled cache. Documented as an honest limitation, not fixed here — persisting breach state was judged out of scope for this cycle (mirrors `UsageTracker.trackingByAsset`/`DefaultSimulationService.feedByAsset`'s own precedent of unbounded, restart-losing in-heap maps elsewhere in this exact module).
- **`GeofenceMonitor`'s enabled-zone cache has two refresh paths, and both matter** — `GeofenceService` calls `refresh()` synchronously after every create/update/delete, so a CRUD change is visible to the very next telemetry sample; independently, `evaluate()` self-populates the cache lazily on its own very first call if `refresh()` was never called yet (e.g. zones already existed in storage before this JVM booted, or a `GeofenceMonitor` is wired without ever being handed to a `GeofenceService` in a given deployment). Skipping either path is a real bug: without the CRUD-triggered refresh, a newly-created zone would never be enforced until some unrelated later event happened to call `refresh()`; without the lazy self-populate, a monitor constructed after zones already exist in storage would silently enforce nothing until the first CRUD write.
- **A `KEEP_IN` breach with more than one enabled `KEEP_IN` zone configured can fire one event per zone simultaneously** — the "outside every enabled `KEEP_IN` zone" condition is computed once per sample and shared across every enabled `KEEP_IN` zone's own per-zone state entry, so crossing out of the union when 2+ such zones exist raises 2+ near-identical breach events in the same `evaluate()` call (one per zone, all with the same `direction`). This is a known, accepted edge case rather than a bug: the plan's own frozen breach rule is stated as a single asset-level "outside all of them" condition, not a per-zone one, and there is no specified way to attribute a single "left the combined area" event to one particular zone. The common case — exactly one `KEEP_IN` zone — is unaffected (it collapses to the obvious per-zone check).
- **`maxAltitudeMeters` only has an effect on a `KEEP_IN` zone** — a `KEEP_OUT` zone breaches "at any altitude" the moment a position is inside it (per the plan's own frozen wording), so a `maxAltitudeMeters` value stored on a `KEEP_OUT` zone is accepted (the domain record does not forbid it) but never consulted by `GeofenceMonitor.isBreached`.
- **The `/live` stop-freeze bug (docs/MVP2-PLAN.md §S, user-reported) was a real backend bug, found and fixed in this task, not (only) a frontend one** — `DefaultStreamService#stop` used to call `VideoSourcePort#close(streamId)` **synchronously**, on whatever thread called `stop()` (a Spring MVC request thread for `DELETE /api/streams/{streamId}`, per `StreamController`). `adapter-rtsp`'s `FfmpegVideoSource.StreamRuntime#close` joins its native grab thread with a **20-second** timeout (`CLOSE_JOIN_TIMEOUT_MILLIS`) after a best-effort `Thread#interrupt()` that its own javadoc admits "native `grab()` may not respond to" — meaning a genuinely stuck RTSP read (exactly the ESP32/flaky-camera scenario this whole cycle is about) could block that request thread for up to 20s. Combined with a browser's small (typically 6) per-origin HTTP/1.1 connection limit, one stuck `DELETE` holding a connection open with no response starves every other poller (asset list, streams, detections, telemetry) queued behind it on the same origin — which reads, from the browser's Network panel, exactly like "the whole app froze," not "one request is slow." Fixed by `stop()` (and `UsageTracker#unsubscribeTelemetry`, called synchronously from the same `stop()`) doing only fast, in-memory work before returning (map removal, `SupervisedPublisher#stop()`, the `STREAM_STOPPED` event, closing the `AssetUsage`) and deferring the actual `StreamPipeline#close()`/port `close()` calls to a fire-and-forget virtual thread — see `DefaultStreamServiceTest#stopReturnsPromptlyEvenWhenSourceTeardownBlocksForAWhile` for a test that reproduces the exact shape of the bug (a `close()` mock blocked on a latch) and proves `stop()` now returns in well under a second regardless.
- **A model-id re-arm (docs/CV-CONTROL-PLAN.md §5/§A, Wave C) does not actually close/reopen any adapter-side detection session — it can't from here, and this is deliberate, not an oversight.** `StreamPipeline#updateConfig`'s javadoc documents the full reasoning; the short version: `DetectionPort` (vision-domain) exposes only `detect(frame, config)`, no per-stream lifecycle method, and the `streamEnded(StreamId)` hook the plan text references lives only on the concrete `GrpcDetectionPort` class (adapter-cv-grpc/MODULE.md), never on the port interface this module is wired against — reaching it would mean either adding a method to `DetectionPort` (a `vision-domain` change) or importing adapter-cv-grpc from `vision-application` (an ArchUnit-forbidden dependency direction). What Wave C actually does on a model change: clears `StreamPipeline`'s own `DetectionExtrapolator`/`latestDetections` (so no stale, wrong-model detection lingers) and lets the volatile config swap carry the new model into the very next `detect()` call, per that port's own per-call contract. Whether a given `DetectionPort` implementation genuinely re-resolves its model per call (verified true for cv-service's `ModelRegistry.resolve(request.model_id)`, called per-request inside its existing `DetectStream` bidi handler) or would need an explicit close+reopen is that implementation's own concern, not something this module can verify or force. If a future adapter needs the latter, `DetectionPort` needs a new lifecycle method first — flagged here for whoever picks that up, not built in Wave C.
- **`maybeDetect`'s `detectionEnabled` gate does not reset outage/backoff state** — toggling `PipelineConfig#detectionEnabled()` off then back on leaves `inOutage`/`backoffNanos`/`nextProbeAtNanos` exactly where they were: if the backoff deadline already elapsed while detection was off, the very next sampled frame after re-enabling immediately attempts a probe (rather than waiting out a "fresh" backoff); if it hadn't elapsed yet, the frame is still skipped until it does. This is a deliberate non-goal, not a bug — the outage/backoff machinery answers "is the CV service healthy," a question that doesn't reset just because the operator flipped a local on/off switch.

**Design decisions, as instructed to record:**
- **`AuthService` keeps both `find(UserId)` and `loadByUsername(String)`** rather than collapsing to one — they serve two different wave-3 callers (a security adapter re-resolving the current session's principal by id on every request, vs. Spring Security's own `UserDetailsService` bridge, which is always keyed by username) and neither can stand in for the other. Only `authenticate` gets the "never throw, never distinguish the failure reason" treatment; `find`/`loadByUsername` are ordinary `Objects.requireNonNull`-guarded pass-throughs for trusted internal callers, not untrusted login input.
- **`GroupService` has no `tree()`** — deferred to slice 2 with the rest of hierarchy management, per the plan. `list()`'s flat, name-sorted list is the only read model slice 1 needs.
- **`UserSpec` validates only `rawPassword` non-blank** (plus `memberships` defensive-copy null-check) — every other field's shape is left to `User`'s own compact constructor once `DefaultUserService#create` builds the aggregate, rather than duplicating those checks a second time in the spec (unlike `AssetSpec`/`GeofenceZoneSpec`, which do duplicate their target's invariants for fail-fast reasons) — `rawPassword` is the one field the record can't defer, since `User` never sees the plaintext, only the hash.
- **`DefaultUserService#create`'s duplicate-username check runs against the already-built candidate `User`'s normalized username**, not `spec.username()` directly — this both reuses `User`'s own shape validation (a blank/malformed username throws before the duplicate check ever runs) and avoids re-implementing the lower-casing normalization `User`'s compact ctor already performs.

## docs/RC-CONTROL-PHASE1-PLAN.md Wave R2 done (application half — service + watchdog/deadman/audit/session)

Depends on Wave R1 (`vision-domain`'s `ManualControlPort`/`ManualControlLink` out-ports + `RcChannels`/`ControlBinding`/`ChannelMap` value model, already done). Delivers the frozen §2 contract: `ManualControlService`/`DefaultManualControlService`, `ManualControlSession` (one private inner-class implementation, `DefaultManualControlService.DefaultManualControlSession`, mirroring `SupervisedPublisher`'s own `SupervisingSubscriber` precedent for "an implementation class that only needs the enclosing instance's collaborators, not its own constructor bloat"), and `WatchdogListener` — see their own API-surface entries above for the full engage/onChannels/release/watchdog/audit contract.

**Design decisions worth recording:**
- **A single self-rescheduling watchdog timer per session, not cancel-and-reschedule-per-`onChannels`.** The frozen contract's wording ("each `onChannels` ... (re)schedules a deadline check") could read either way; a naive cancel-then-reschedule-every-call implementation would create/cancel a `ScheduledFuture` at the browser's own input rate (~20–30 Hz) and, worse, is racy (a cancel can lose to an already-firing check). Instead `armWatchdog()` schedules exactly one check, and every firing re-reads the session's live `lastInput` and either releases or reschedules itself for the *remaining* time — `onChannels` only ever writes `lastInput`, never touches the scheduler. At most one `ScheduledFuture` is outstanding per session at any time; this is the mechanism the watchdog test suite (see below) actually exercises and asserts on.
- **"One session per handle" is enforced at the `DefaultManualControlService` instance, not per `ManualControlSession`.** Since `vision-app`'s wiring (R4) is expected to construct exactly one `ManualControlService` singleton bean — the same convention every other service in this package follows — this in practice serializes manual-control relaying to one connection app-wide, not merely "one per WebSocket connection" the way the interface javadoc's parenthetical might first read. Called out explicitly in the API-surface entry above and repeated here so R4 doesn't miss it: a future multi-operator requirement needs a per-connection service instance, not a shared singleton, and that is a bigger wiring change than R4's own scope.
- **The watchdog timeout is a sixth, canonical constructor parameter, not baked into either frozen-shape constructor.** The plan text names exactly two public constructors (a 5-arg `Clock`+`ScheduledExecutorService` test seam, a 3-arg production convenience ctor) but separately says `vision-app`'s wiring should read `vision.rc.watchdog-timeout-ms` "to size the watchdog" — those two statements only both hold if a third entry point exists for the resolved property value to actually reach the scheduler-arming logic. Added a 6-arg canonical ctor `(..., Clock, ScheduledExecutorService, long watchdogTimeoutMs)`, with the two frozen-shape ctors delegating to it with `DEFAULT_WATCHDOG_TIMEOUT_MS=300`, following this codebase's own established "N-1-arg convenience constructor" idiom rather than inventing a new shape. **Flagged for R4**: wire the bean via the 6-arg ctor with the resolved property if the property should ever differ from 300 in practice; the 3-/5-arg ctors are permanently pinned to the default.

## docs/CV-TRAINING-PLAN.md Phase 2 — `TrainingJobService` done (application half — start + off-thread run + pollable job state)

Depends on `TrainingPort`/`TrainingJobSpec`/`TrainingProgress`/`JobState` (`vision-domain`, already done + green, untouched by this wave) and reuses `DefaultModelRegistryService`'s manager-gate/audit idiom plus `DefaultManualControlService`'s off-thread/executor + in-memory session-state idiom, per docs/CV-TRAINING-PLAN.md §7. Delivers `TrainingJobService`/`DefaultTrainingJobService` and the `TrainingJobView` read-model record — see their own API-surface entries above for the full method-by-method contract.

**Locally-generated job id vs. the wire job id, the central design call**: `TrainingPort#startTraining` blocks for the job's entire lifetime, so `start` cannot wait for cv-service to assign its own `TrainingProgress#jobId()` before answering — that would make the "start a job" call itself long-running, defeating the purpose. `start` therefore mints a fresh `UUID` locally *before* submitting anything, registers the initial job state under it, and returns it at once; the run is submitted to an `ExecutorService` whose task closes over that same local id for every subsequent `updateJob` call. The wire `jobId` a `TrainingProgress` message carries is read nowhere in this class — it is informational only, exactly as the task brief anticipated — so the local and wire ids may legitimately differ, and a test (`terminalSucceededLandsUnderTheLocalJobIdEvenThoughTheWireJobIdDiffers`) exercises exactly that with two different id strings to prove polling by the local id still works.

**Retention**: finished (terminal) jobs are capped at `MAX_FINISHED_JOBS = 50` (package-private constant), tracked oldest-first in a `ConcurrentLinkedDeque` alongside the `ConcurrentHashMap<String, TrainingJobView>` the map itself is; a still-`RUNNING` job is never evicted, only completions count toward the cap. Chosen as a round, generous number for a control-plane job registry (Phase 2 training runs are operator-initiated, not high-frequency) — documented as a best-effort, not a hard, invariant, since two completions racing the size check can rarely leave the map one entry over the bound (self-corrects on the next completion). No persistence — like every in-memory-only collaborator in this module (`DefaultManualControlService`'s one active session, `GeofenceMonitor`'s breach-state map), job state does not survive a JVM restart; a plan revision to persist it would need a new port, out of this wave's scope.

**Audit action choice**: `start` uses `AuditAction.CREATED` (a new job resource is being created under the locally-generated id), not `AuditAction.UPDATED` the way `DefaultModelRegistryService#promote`/`DefaultFlightCommandService`'s command verbs use — those mutate an *existing* resource (a model reference, an asset) and have no dedicated action value to fall back to; starting a job is create-shaped, and `AuditAction.CREATED` already exists and fits. Applied uniformly to both the `DENIED:out of scope` and `STARTED` outcomes (mirroring `promote`'s own "one action value for the whole operation, regardless of outcome" convention), keyed by the generated job id against `AuditTargetType.MODEL` (the closest existing target kind — there is no dedicated "training job" `AuditTargetType`, and a training job's whole purpose is producing a model). Only `start` is audited; progress ticks and terminal completion are not, since a poller already observes them through `job(jobId)`.
